# Прогон lock-demo.sh (PostgreSQL 18.4, pg_repack 1.5.3, 2026-07-22)
# Таблица ~2M строк, раздута UPDATE. Пока идёт операция, шлём точечные SELECT-ы
# (WHERE id=1) и считаем, сколько прошло и какова макс. задержка.

### VACUUM FULL — держит ACCESS EXCLUSIVE всю операцию
      [проба #1: 4.52 c]
    проб прошло: 1, макс. задержка точечного SELECT: 4.52 c
# Единственная проба повисла на все 4.52 с — до самого конца VACUUM FULL.
# Читатели полностью заблокированы: в проде это прямой простой.

### pg_repack — онлайн
      [проба #6: 3.19 c]
    проб прошло: 39, макс. задержка точечного SELECT: 3.19 c
# 39 проб из ~40 прошли — читатели работают почти всю операцию.
# Одна заметная задержка (проба #6) пришлась на служебную фазу pg_repack
# (создание инфраструктуры/захват в начале); дальше чтение свободно.
# pg_repack берёт ACCESS EXCLUSIVE лишь короткими окнами (setup, финальный swap),
# а не на всё время переписывания.

# Вывод: по возвращаемому месту VACUUM FULL и pg_repack равны (см. 04-vacuum-repack.txt),
# но по доступности таблицы различаются принципиально: VACUUM FULL = простой на всю
# операцию, pg_repack = почти без простоя (ценой удвоения места на диске и требования PK).
