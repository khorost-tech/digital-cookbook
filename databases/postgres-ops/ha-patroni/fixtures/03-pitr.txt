# Прогон pitr-pgbackrest.sh + pitr-walg.sh (PostgreSQL 18.4, 2026-07-22)
# Point-in-Time Recovery: откат базы на момент ДО ошибочной операции.
# pgBackRest 2.58.0 и wal-g v3.0.8 — оба на отдельных single-node инстансах.

## Сценарий (одинаков для обоих)
# 1. базовый бэкап; 2. хорошие данные (1000 строк 'good') → точка T1;
# 3. ошибочные данные (500 строк 'OOPS') после T1; 4. restore --type=time на T1.

## pgBackRest
до восстановления:  good|1000   OOPS|500
restore --type=time --target=T1 --delta
после:              good|1000              ← OOPS откачены, good целы

## wal-g
до восстановления:  good|1000   OOPS|500
backup-fetch LATEST + recovery_target_time=T1 (restore_command='wal-g wal-fetch %f %p')
после:              good|1000              ← тот же результат

# Оба инструмента решают одну задачу — PITR через базовый бэкап + архив WAL:
#   pgBackRest — декларативная конфигурация (stanza), инкрементальные бэкапы,
#     параллельный архив, встроенная верификация. Команда restore одношаговая.
#   wal-g — Go-бинарник, ориентирован на облачные хранилища (S3/GCS/…), лёгкий;
#     восстановление = backup-fetch + штатный recovery PostgreSQL по restore_command.
#
# Эксплуатационный нюанс 2026: pgBackRest в апреле был архивирован автором, затем
# возрождён коалицией спонсоров (актуальная линия 2.59.x). Это довод держать в проде
# знание и второго инструмента (wal-g) — на случай смены статуса зависимости.
#
# В HA-кластере (соседний docker-compose) archive_command так же настраивается в Patroni;
# здесь PITR вынесен на single-node, потому что это про бэкап, а не про репликацию,
# и потому что pgBackRest и wal-g спорят за единственный archive_command.
