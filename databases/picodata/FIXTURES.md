# FIXTURES — числа и факты стенда Picodata

Единственный источник чисел для статей. Каждый факт снят на этом стенде
23.07.2026, если не сказано иное. Абсолютное время выполнения запросов здесь не
публикуется как характеристика системы: один хост, Docker Desktop на Windows,
цифры годятся только для сравнения внутри одного прогона.

## PostgreSQL-протокол

- **Клиент `psql` из образа `postgres:18.4` подключается к Picodata 26.1.3 без
  каких-либо адаптеров**: `psql "postgres://admin:...@picodata-1:5432/picodata?sslmode=disable"`
  и обычные SQL-запросы работают. Ровно тот же клиент используется для
  настоящего PostgreSQL-источника этого стенда.
- **Загрузчик `loader/` ходит в обе базы одним и тем же `pgx/v5`**: отличие
  только в строке DSN. 200 000 строк загружены в кластер за **1,54 с** и
  **1,55 с** на двух прогонах (партиями по 500 строк, multi-row `INSERT`).
- Пароль администратора должен содержать заглавную букву: `picodata`
  отвергается с сообщением
  `invalid password: password should contain at least one uppercase letter`.

**Границы совместимости — проверенное и документированное.** Стенд подтвердил
работу ровно двух клиентов: `psql` и `pgx`. Обобщать это до «весь
PostgreSQL-инструментарий работает» нельзя:

- для DBeaver Picodata рекомендует
  [собственный JDBC-драйвер](https://docs.picodata.io/picodata/devel/tutorial/dbeaver/)
  (`io.picodata.jdbc.Driver`, схема URL `jdbc:picodata://`), а не штатный
  PostgreSQL-драйвер;
- по документации совместимость **частичная**: системные каталоги реализованы
  не полностью, из методов аутентификации по PG-протоколу доступны `md5` и
  `ldap`, режим работы — autocommit;
- **команды управления транзакциями — заглушки.** Проверено на стенде: `BEGIN`,
  `INSERT`, `ROLLBACK` выполняются без единой ошибки, `ROLLBACK` отчитывается
  успешно, после чего `SELECT count(*)` возвращает **1** — вставленная строка
  на месте. Это худший вид несовместимости: не отказ, а тихо другое поведение.
  Отсюда следствие: миграционные утилиты PostgreSQL не переносятся по
  умолчанию — они опираются на транзакционный DDL и системные каталоги.
  Проверка автоматизирована — шаг 4 в `verify/verify.sh`; если однажды
  `ROLLBACK` начнёт откатывать по-настоящему, шаг упадёт, и это будет сигналом
  не о поломке стенда, а о том, что поведение изменилось и текст статьи требует
  пересмотра.

## Плагин на Rust

Плагин `near_data` решает ту же задачу, что Lua-хранимка
`top_products_by_category` из стенда Tarantool: топ товаров категории по
просмотрам. Механизм другой — плагин выполняет распределённый SQL, хранимка
идёт по вторичному индексу локально.

- **Результат совпал с источником истины построчно** при `limit` = 5, 10 и 25,
  включая порядок. Тай-брейк для равных `views` — по убыванию `id`, как и в
  стенде Tarantool.
- Строк наружу: наивный путь отдал бы клиенту всю категорию — **33 276**,
  плагин при `limit=5` отдаёт **5**. Отношение **6655** (то же свойство и та же
  формула `размер_категории / limit`, что в стенде Tarantool).
- Собранная библиотека требует максимум **GLIBC_2.28**, неразрешённых
  зависимостей в образе кластера — **0** (`ldd` внутри образа Picodata).

## Встроенная наблюдаемость

Один флаг `--http-listen` включает сразу две вещи, и **плагины для этого не
нужны** — проверено на кластере с нулём установленных плагинов
(`SELECT count(*) FROM _pico_plugin` = 0):

- **Веб-интерфейс** на корне порта: отдаётся страница с `<title>Picodata</title>`,
  собственными ассетами и конфигом по `/api/v1/config`.
- **Экспорт метрик в формате Prometheus** на `/metrics`: **144 семейства**
  метрик на голом кластере (39,9 КБ текста), из них `pico_*` — 33 семейства,
  `tnt_*` — 93, `lj_*` — 19 (LuaJIT). С установленным плагином — 145 семейств:
  шаблон `pike` подключает `prometheus` и добавляет свои метрики в тот же
  эндпоинт.

Семейства `pico_*` (полный список снят с живого кластера):

| Группа | Метрики |
|---|---|
| Raft | `pico_raft_state`, `pico_raft_leader_id`, `pico_raft_term`, `pico_raft_applied_index`, `pico_raft_commit_index` |
| Кластер | `pico_instance_state`, `pico_governor_changes_total`, `pico_info_uptime` |
| PG-протокол | `pico_pgproto_connections_opened_total`, `..._closed_total`, `pico_pgproto_statements_opened_total`, `..._closed_total`, `pico_pgproto_portals_opened_total`, `..._closed_total` |
| Распределённый SQL | `pico_sql_query_total`, `pico_sql_query_duration`, `pico_sql_global_dml_query_total`, `..._retries_total`, `pico_sql_temp_table_leases_total`, `pico_sql_temp_table_lock_waits_total` |
| Кэш планов | `pico_router_cache_hits_total`, `..._misses_total`, `..._statements_added_total`, `..._statements_evicted_total`, `pico_storage_cache_misses_total`, `..._statements_added_total`, `..._statements_evicted_total` |
| RPC плагинов | `pico_rpc_request_total`, `pico_rpc_request_duration`, `pico_rpc_request_errors_total` |
| CAS | `pico_cas_ops_duration`, `pico_cas_records_total` |

**Состояние Raft видно именно в метриках, а не в SQL.** Живые значения с
разных узлов одного кластера:

```
pico_raft_leader_id{instance_name="default_1_1"} 1
pico_raft_state{state="Leader",instance_name="default_1_1"} 1
pico_raft_term{instance_name="default_1_1"} 2

pico_raft_leader_id{instance_name="default_1_2"} 1
pico_raft_state{state="Follower",instance_name="default_1_2"} 1
```

Кроме того, с любого узла видно состояние всех инстансов кластера:
`pico_instance_state{instance="default_2_2",state="Online",...} 1` — насчитывается
4 инстанса в состоянии `Online`.

⚠️ **Но опрашивать один узел нельзя.** Кластерная здесь только часть метрик.
`tnt_*`, `lj_*`, raft-роль и счётчики запросов относятся к тому инстансу, у
которого метрики забрали. Снято одновременно с четырёх портов одного кластера:

| Порт | Семейств | из них `tnt_*` | Инстанс и роль |
|---|---:|---:|---|
| 8081 | 154 | 97 | `default_1_1` Leader |
| 8082 | 148 | 97 | `default_2_1` Follower |
| 8083 | 146 | 97 | `default_2_2` Follower |
| 8084 | 145 | 97 | `default_1_2` Follower |

Наборы различаются и по составу, и по значениям — это разные измерения, а не
разные представления одного. Документация Picodata требует того же:
[под каждый инстанс нужен отдельный адрес сбора метрик](https://docs.picodata.io/picodata/25.2/admin/monitoring/),
и пример конфигурации Prometheus перечисляет все узлы как отдельные цели.
Опрос одного узла оставит слепую зону на остальных.

Попутная деталь: номер контейнера не соответствует репликасету по порядку —
порт 8082 отдал `default_2_1`, а 8084 — `default_1_2`. Привязка инстансов к
репликасетам от пересоздания к пересозданию не гарантирована.

Это уточняет вывод стенда `performance/inmemory`, где Raft-статус снимался
через `picodata admin`: через **SQL** его действительно не видно
(`_pico_instance` не содержит признака лидера, а `current_master_name` в
`_pico_replicaset` — это мастер репликасета для записи vshard, другое понятие),
но для мониторинга admin-консоль не нужна — есть штатный эндпоинт метрик.

Проверяется скриптом `verify/observability.sh`. Он падает, если у любого из
четырёх инстансов меньше 100 семейств метрик, меньше 50 семейств `tnt_*`, нет
собственной raft-роли, — а также если роли на разных узлах не различаются: в
живом кластере обязаны быть и `Leader`, и `Follower`, иначе метрики оказались бы
общим снимком, а не измерением конкретного инстанса.

## Матрица PostgreSQL-совместимости (подстенд `pg-compat/`)

59 проб × 5 клиентов (`psql`, `pgx`, `psycopg`, PostgreSQL-JDBC 42.7.4,
`picodata-jdbc` 5.1.0). Полная таблица — в `pg-compat/RESULTS.md`.

**Главный результат уровня SQL: все пять клиентов совпали построчно на всех 59
пробах, расхождений ноль.** Граница совместимости проходит по серверу, выбор
драйвера на неё не влияет. Принято 42 пробы, отвергнуто 17.

**Не поддерживается** (с точными сообщениями сервера):

| Конструкция | Ответ сервера |
|---|---|
| `current_database()`, `current_schema()` | `SQL function ... not found` |
| `information_schema.*`, `pg_catalog.*` | ошибка разбора на имени схемы |
| `WITH RECURSIVE` | ошибка разбора |
| коррелированный подзапрос (`EXISTS ... WHERE q.id=p.id`) | `column with name "id" and scan Some("p") not found` |
| `INTERSECT` | ошибка разбора |
| `OFFSET` | ошибка разбора |
| `ORDER BY` по колонке вне списка выборки | `column with name "views" not found` |
| `rank() OVER (...)` | `window function rank does not exist` |
| `now()` | `SQL function now not found` |
| `SHOW` | ошибка разбора |
| `ALTER TABLE ... DROP COLUMN` | `unsupported DDL: ALTER TABLE _ DROP COLUMN is not yet supported` |
| `INSERT ... RETURNING` | ошибка разбора |
| `INSERT ... ON CONFLICT` (upsert) | ошибка разбора |

**Работает вопреки ожиданиям:** `ORDER BY` по позиции (`ORDER BY 1`) и по
колонке из проекции, `ORDER BY` по выражению и по алиасу, `EXCEPT`,
некоррелированный `EXISTS`, `CTE` (нерекурсивный), `LEFT JOIN`, `ILIKE`,
`string_agg`, `count(DISTINCT ...)`, `EXPLAIN`, `SET`, `TRUNCATE`,
многострочный `INSERT`.

**Оконные функции поддерживаются частично, и отказ не о них.** `row_number()`
проходит на подзапросе из 99 строк и падает на полной таблице с сообщением
`Exceeded maximum number of rows (5000) in virtual table: 66751` — это лимит на
материализацию промежуточной таблицы, а не отсутствие функции. А вот `rank()`
действительно отсутствует: `window function rank does not exist`.

### Метаданные JDBC — вот зачем фирменный драйвер

SQL-пробы у обоих драйверов совпали полностью, различие целиком в
`DatabaseMetaData` — том самом, по которому GUI-клиенты строят дерево объектов:

| Вызов | PostgreSQL-JDBC 42.7.4 | picodata-jdbc 5.1.0 |
|---|---|---|
| `getDatabaseProductName()` | `PostgreSQL 15.0` | `Picodata 15.0` |
| `getTables()` | ошибка (ходит в `pg_catalog`) | 1 таблица |
| `getColumns()` | ошибка | 7 колонок `products` |
| `getSchemas()` | ошибка | 1 |
| `getPrimaryKeys()` | ошибка | 1 |
| `getTypeInfo()` | ошибка | 16 типов |
| `supportsTransactions()` | **`true`** | **`false`** |

Последняя строка — самая опасная: штатный драйвер **заявляет поддержку
транзакций**, которых у Picodata нет. Инструмент, который спрашивает драйвер о
возможностях вместо того, чтобы их проверить, построит неверную модель молча.

### Прикладные инструменты

- **`pg_dump` 18.4 не работает**: падает на самом первом запросе, не дойдя до
  схемы — `SELECT pg_catalog.set_config('search_path', '', false)` отвергается
  разбором. Оба режима (`--schema-only`, `--data-only`) дают код возврата 1.
- **Мигратор `goose` v3.22.1 не работает**: падает на создании собственной
  таблицы версий — `id integer PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY`
  отвергается разбором. Ни миграция, ни журнал версий не создаются. То есть
  проблема не в тексте миграции, а в том, что мигратор не может завести учёт.
- **Метакоманды `psql` вроде `\dt` не работают** — они разворачиваются в запросы
  к `pg_catalog` (`pg_get_userbyid`). Список таблиц берётся из `_pico_table`.

## Что сломалось и почему (воспроизводимо)

1. **Сборка вне AlmaLinux.** Образ Picodata — AlmaLinux 8.10 с glibc 2.28.
   Библиотека, собранная в WSL (glibc 2.39), потребует более новую версию и не
   загрузится. Стенд собирает плагин в контейнере на той же базе.

2. **Имя тома.** Compose префиксует имя тома именем проекта
   (`picodata-cookbook_picodata-share`). Скрипт сборки писал в том без префикса
   и создавал второй, пустой; кластер отвечал
   `Error while discovering manifest ... No such file or directory`. Лечится
   явным `name:` у тома.

3. **Аннотации миграций ищутся по всему файлу.** Упоминание имени аннотации в
   обычном комментарии роняет установку:
   `unexpected 'pico.UP' annotation, it must be at the start of the line`.

4. **Порядок жизненного цикла.** Без применения миграций включение отвергается:
   `cannot enable plugin 'near_data:0.1.0': need to apply migrations first
   (applied 0/1)`. Рабочий порядок: `CREATE PLUGIN` → `ADD SERVICE ... TO TIER`
   → `MIGRATE TO` → `ENABLE`.

5. **`LIMIT` не параметризуется.** `sql::query("... LIMIT ?").bind(n)` падает с
   `sbroad: rule parsing error` с указанием позиции знака вопроса. Значение в
   `WHERE` биндится нормально. В стенде `limit` подставляется в текст запроса —
   безопасно, потому что это `u32`.

6. **Лимит опкодов VDBE.** Дефолт `sql_vdbe_opcode_max = 45000` не выдерживает
   сортировку по категории из 33 276 строк:
   `Reached a limit on max executed vdbe opcodes. Limit: 45000`. Стенд ставит
   5 000 000 (`ALTER SYSTEM SET ... FOR ALL TIERS`).
   **Важно:** ошибка одинаковая и у внешнего SQL-клиента, и у плагина —
   распределённую часть планирует sbroad, локальную исполняет VDBE ядра, и
   лимит считается именно там. Это подтверждает двухслойность движка на
   наблюдаемом поведении, а не на предположении.

7. **Подмена библиотеки под работающим процессом.** Пересборка `.so` поверх
   загруженного файла с последующим `docker restart` уронила инстанс с
   `crash_signal_cb`. Штатный путь обновления — новая версия плагина, а не
   замена файла на месте.

8. **Версия каталога в share_dir должна совпадать с версией пакета.** Реестр
   сервисов внутри библиотеки регистрирует их под `CARGO_PKG_VERSION`. Сборка
   пакета 0.2.0, положенная в каталог `0.1.0`, устанавливается наполовину:
   манифест кластер находит, а сервисы — нет:
   `Failed to install plugin 'near_data:0.1.0': Plugin partial load (some of
   services not found: ["near_data_service"])`. В `builder/build.sh` добавлена
   проверка: запрошенная версия сверяется с версией в `plugin/Cargo.toml`, при
   расхождении сборка падает.

## Blue-green обновление

Проверено переходом `0.1.0` → `0.2.0` (во второй версии добавлено поле
`served_by_version` в ответ, чтобы видеть, кто реально обслужил запрос).

- Обе версии присутствуют в `_pico_plugin`, но **включённой может быть только
  одна**. Попытка включить новую, не выключив старую:
  `plugin 'near_data:0.2.0' is already enabled with a different version 0.1.0`.
- `MIGRATE TO` на версию с тем же набором миграций проходит без повторного
  применения.
- **RPC-эндпоинты версионированы.** В журнале: снимается
  `near_data.near_data_service:v0.1.0/top_products`, регистрируется
  `...:v0.2.0/top_products`. Переключение немедленное.
- **HTTP-маршруты версии не несут.** После переключения HTTP продолжал отвечать
  `"served_by_version":"0.1.0"`, хотя в `_pico_plugin` включена 0.2.0. Новая
  версия начала отвечать только после перезапуска инстанса. Это свойство
  шаблона `pike` (общий HTTP-сервер, маршруты без версии), а не Picodata: если
  blue-green нужен без рестарта, точкой входа должен быть RPC.

## Границы

- Замеры времени не публикуются как характеристика Picodata.
- Коммерческие плагины (Radix — Redis, Sirin — Cassandra, Ouroboros, Franz) на
  этом стенде **не проверялись**: они не входят в открытую часть.
- Отказоустойчивость **проверена** (`failure/failure.sh`): потеря одного узла
  репликасета — ответ полный; потеря обоих — молча неполный результат.
  Восстановление проверяется как ДВА события: данные снова доступны И вернулся
  ровно один Raft-лидер. Они расходятся — Raft стабилизируется не сразу
  (наблюдался Candidate без лидера, пока SQL уже отдавал полный ответ).
- **Состояние 3000/0 (все бакеты на одном репликасете) — гонка bootstrap.**
  Признаков «4 Online + один Raft-лидер + репликасеты ready» НЕДОСТАТОЧНО: при
  них ребалансировщик мог ещё не разложить бакеты (в журнале — «увидел ноль
  активных бакетов на момент bootstrap» и остановился). Лечение — **барьер
  готовности** `cl_wait_ready` в `ops/cluster-lib.sh`: ждёт Online + одного
  лидера + КАЖДЫЙ репликасет ready и с ненулевым ВЕСОМ + карту
  «репликасет → бакеты» (реплики согласованы, ни один репликасет не пуст, сумма
  по уникальным репликасетам = 3000). После загрузки `cl_check_data` сверяет
  `count(*)`, совпадение реплик и сумму строк. Вызывается в `ops/up.sh`, в
  предусловиях и в уборке failure/scale.

- ⚠️ **Распределение СТРОК по репликасетам остаётся НЕПОСТОЯННЫМ даже после
  барьера — это открытый вопрос, а не решённый.** При неизменных 1500 бакетах
  на репликасет наблюдались: **99776/100224** (0,2%), **123103/76897** (~1,6:1),
  **124807/75193** (~1,7:1), **133249/66751** (~2:1). Это ПЕРЕЧЕНЬ наблюдавшихся
  исходов, а не распределение частот: систематической серии прогонов с подсчётом
  вероятности каждого исхода не проводилось, поэтому слов «чаще/реже» в статье
  нет. Каждый исход повторялся в нескольких прогонах подряд — то есть это не
  разовые выбросы.

  Что известно точно: строки по ДИАПАЗОНАМ `bucket_id` делятся детерминированно
  — `SELECT sum(CASE WHEN bucket_id<=1500 …)` даёт 100224/99776, и иначе быть не
  может (номер бакета = хеш ключа). Значит объём на репликасете определяется
  тем, КАКИЕ бакеты ему достались (непрерывный диапазон / чередование / иное).
  Механизм назначения стендом НЕ установлен — в статье подано как наблюдение
  без объяснения. Прежние утверждения «ровно 2:1» и «ровное и воспроизводимое»
  ОБА ошибочны и сняты.

  Число `66751` в virtual table JOIN-а (раздел про sbroad) — результат
  конкретного прогона.
- Расширение кластера **проверено** (`scale/scale.sh`). На кластере, прошедшем
  барьер готовности, бакеты появлялись на новых узлах уже при ПЕРВОЙ проверке;
  итог — три репликасета по 1000 бакетов (6000 по узлам с учётом реплик),
  200 000 строк на месте. Прежние «медленные» прогоны, где бакеты не двигались
  минутами при `The cluster is balanced ok`, признаны НЕВАЛИДНЫМИ: они
  снимались либо с кластера без барьера готовности, либо с неподнявшимися
  узлами (баг пути compose под MSYS — `-f` получал Unix-путь и docker искал
  `G:\g\7\...`). Готовность нового узла определять по фактическому числу
  бакетов, а не по статусу Online и не по выставленному весу.
- **Не проверялись:** `BACKUP` и `picodata restore` (требуют конфигурационного
  файла инстанса — на кластере, поднятом флагами, `BACKUP` отвергается с
  `No config found for local backup`), обновление кластера между версиями, TLS,
  готовые правила алертинга.
- Матрица `pg-compat` проверяет **принимаемый синтаксис**. Совпадение
  результатов с PostgreSQL и постусловия DML — отдельная проверка,
  `pg-compat/results.sh` (11 пар запросов + 7 постусловий).
