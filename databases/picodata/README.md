# Picodata: плагин на Rust и вычисления рядом с данными

Живой стенд к серии «Picodata» на [khorost.tech](https://khorost.tech).

Picodata — распределённая СУБД на форке ядра Tarantool. Ядро открыто (BSD),
основной протокол взаимодействия — **PostgreSQL wire protocol**, расширяется
**плагинами на Rust**. Этот стенд показывает на живом кластере четыре вещи:

1. клиенты PostgreSQL работают с Picodata без адаптеров — `psql` и `pgx`
   подключаются к ней тем же кодом, что к настоящему PostgreSQL;
2. собственный плагин на Rust считает топ товаров категории **в кластере**,
   отдавая наружу `limit` строк вместо всей категории — та же задача, что решает
   Lua-хранимка в стенде `performance/inmemory/tarantool`, но другим механизмом;
3. как выглядит blue-green обновление плагина и где оно срабатывает не так,
   как ожидаешь;
4. что даёт встроенная наблюдаемость: веб-интерфейс и экспорт метрик в формате
   Prometheus включаются одним флагом, без плагинов и экспортеров.

Все числа — в `FIXTURES.md`. Там же список того, что сломалось по дороге, с
точными сообщениями об ошибках.

## Запуск

Нужны Docker и Go. Один вызов поднимает всё: источник истины, датасет, кластер,
сборку плагина и его установку.

```bash
bash ops/up.sh 0.1.0
```

Второй и последующие разы датасет можно не перегенерировать:

```bash
SKIP_DATASET=1 bash ops/up.sh 0.1.0
```

Самопроверка — сверяет топ от плагина с источником истины, проверяет поведение
транзакций в PG-протоколе и падает при любом расхождении:

```bash
export ORIGIN_DSN="postgres://picodata:picodata@127.0.0.1:5434/catalog?sslmode=disable"
export PICO_HTTP="http://127.0.0.1:8081"
bash verify/verify.sh
```

Встроенная наблюдаемость — веб-интерфейс, экспорт метрик и состояние Raft:

```bash
bash verify/observability.sh
```

Обновление версии плагина:

```bash
bash builder/build.sh 0.2.0
bash verify/blue-green.sh 0.1.0 0.2.0
```

Остановить:

```bash
docker compose -f compose/cluster.yml down -v
docker compose -f compose/origin.yml down -v
```

## Топология и порты

| Сервис | Роль | С хоста |
|---|---|---|
| `picodata-origin` | PostgreSQL 18.4, источник истины | `5434` |
| `pd-1` | Picodata, репликасет `default_1` | PG `5442`, HTTP `8081`, iproto `3402` |
| `pd-2` | Picodata, репликасет `default_1` | PG `5443`, HTTP `8082` |
| `pd-3` | Picodata, репликасет `default_2` | PG `5444`, HTTP `8083` |
| `pd-4` | Picodata, репликасет `default_2` | PG `5445`, HTTP `8084` |

Порт `5434` выбран намеренно: `5432` занят стендами `databases/*`, `5433` —
стендом `performance/inmemory`.

**Четыре инстанса, а не три.** При факторе репликации 2 три инстанса
структурно не дают шардирования: один репликасет добирает двух членов, второй
остаётся с одним и весом 0, и vshard не раздаёт ему бакеты. Это установлено
живым прогоном в стенде `performance/inmemory` и здесь принято как данность.

## Устройство

```
compose/     origin.yml — источник истины; cluster.yml — кластер из 4 инстансов
builder/     Dockerfile сборочного образа + build.sh
plugin/      сам плагин: манифест, сервис, обработчики, миграции
loader/      перекачка датасета из источника в кластер (pgx в обе стороны)
dataset/     генератор датасета, копия из performance/inmemory (seed=42)
verify/      самопроверка и сценарий blue-green
ops/         up.sh (полный подъём) и install-plugin.sh (жизненный цикл плагина)
```

### Почему сборка идёт в отдельном образе

Образ Picodata собран на **AlmaLinux 8.10 (glibc 2.28)**. Плагин — динамическая
библиотека, которую грузит именно этот процесс, поэтому собирать её надо против
того же glibc. Сборка в WSL с Ubuntu (glibc 2.39) даёт `.so` с требованием более
новой версии, и включение плагина падает на загрузке библиотеки. Поэтому
`builder/Dockerfile` — это AlmaLinux 8.10 с rustup и `cargo pike`, а
собранная библиотека проверяется `ldd` внутри образа кластера: неразрешённых
зависимостей должно быть ноль.

Каталог называется `builder/`, а не `build/`, потому что `build/` исключён
корневым `.gitignore` репозитория как каталог артефактов Gradle.

### Жизненный цикл плагина

Порядок обязателен, и он не тот, который кажется очевидным:

```
CREATE PLUGIN near_data 0.1.0
ALTER PLUGIN near_data 0.1.0 ADD SERVICE near_data_service TO TIER default
ALTER PLUGIN near_data MIGRATE TO 0.1.0
ALTER PLUGIN near_data 0.1.0 ENABLE
```

Без `MIGRATE` включение отвергается: `need to apply migrations first
(applied 0/1)`. Сервис привязывается к **тиру**, а не к репликасету.

### Где стенд спотыкался

Полный список с точными сообщениями — в `FIXTURES.md`, раздел «Что сломалось».
Коротко, чтобы не повторять:

- имя тома у Compose получает префикс проекта — задавайте `name:` явно;
- имя аннотации миграции, упомянутое в обычном комментарии, роняет установку;
- `LIMIT ?` в распределённом SQL не принимается, хотя `WHERE ... = ?` работает;
- дефолтный `sql_vdbe_opcode_max = 45000` не выдерживает сортировку по 33 тысячам
  строк — и одинаково для внешнего клиента, и для плагина;
- пересборка `.so` поверх загруженного файла с рестартом роняет инстанс;
  обновляться нужно новой версией плагина;
- версия каталога в `share_dir` должна совпадать с версией в `Cargo.toml`, иначе
  плагин ставится наполовину: манифест найден, сервисы — нет.

### Наблюдаемость из коробки

Флаг `--http-listen` включает и веб-интерфейс, и экспорт метрик Prometheus на
`/metrics`; ни плагинов, ни отдельного экспортера не требуется — проверено на
кластере с нулём установленных плагинов. На голом кластере отдаётся 144
семейства метрик: `pico_*` про Raft, состояние инстансов, PG-протокол,
распределённый SQL и кэш планов; `tnt_*` про memtx, vinyl, сеть и CPU ядра;
`lj_*` про сборщик мусора LuaJIT.

Практическая деталь: **состояние Raft видно именно здесь**. Через SQL роль
инстанса не получить, а `pico_raft_state`, `pico_raft_leader_id` и
`pico_raft_term` отдаются штатно.

⚠️ При этом **опрашивать нужно каждый инстанс отдельно**. Кластерная только
часть метрик (`pico_instance_state` перечисляет весь кластер с любого узла);
`tnt_*`, `lj_*`, raft-роль и счётчики запросов принадлежат опрошенному
инстансу. Документация Picodata требует отдельного адреса сбора метрик под
каждый инстанс. Скрипт проверки обходит все четыре порта и убеждается, что у
каждого свой полный набор и что роли различаются.

### Что показал blue-green

Обе версии живут в кластере, включена ровно одна. RPC-эндпоинты
версионированы и переключаются сразу. А HTTP-маршруты из шаблона `pike`
версии не несут: после переключения запрос продолжает обслуживать обработчик
из старой библиотеки, пока инстанс не перезапустят. Если обновление без
рестарта принципиально — точкой входа должен быть RPC.

## Матрица PostgreSQL-совместимости — `pg-compat/`

Отдельный подстенд отвечает на вопрос «что из привычного PostgreSQL здесь
работает». Один набор из 59 проб (`probes.tsv`) прогоняется **пятью
независимыми клиентами**: `psql`, `pgx`, `psycopg`, штатный PostgreSQL-JDBC и
фирменный `picodata-jdbc`. Смысл именно в пяти: так отделяется «сервер не
умеет» от «драйвер не умеет».

```bash
bash pg-compat/run-all.sh        # прогон всеми клиентами -> pg-compat/RESULTS.md
bash pg-compat/tools/pg_dump.sh  # снимется ли дамп штатным pg_dump
bash pg-compat/tools/migrator.sh # сможет ли работать мигратор goose
```

### Барьер готовности — почему он важнее, чем кажется

`ops/up.sh` не грузит данные сразу после `compose up`. Сначала отрабатывает
барьер `cl_wait_ready` из `ops/cluster-lib.sh`, который ждёт четыре условия:
все инстансы Online, ровно один Raft-лидер, все репликасеты `ready`, и —
главное — **у каждого узла ненулевое число бакетов**. После загрузки
`cl_check_data` сверяет `count(*)`, совпадение реплик внутри репликасета и
сумму строк по уникальным репликасетам.

Без этого стенд измерял переходное состояние: наблюдался кластер, где при
Online, лидере и `ready` все 3000 бакетов лежали на одном репликасете, и туда же
уезжали все 200 000 строк. Числа выглядели правдоподобно, хотя описывали гонку
инициализации.

⚠️ Барьер снял состояние 3000/0, но **не** сделал распределение строк
постоянным: при неизменных 1500 бакетах на репликасет наблюдаются и
99 776 / 100 224, и 123 103 / 76 897, и 124 807 / 75 193, и 133 249 / 66 751 —
перечень исходов, а не их частоты. Это открытый вопрос,
см. `FIXTURES.md` — числа строк из конкретного прогона нельзя выдавать за
характеристику Picodata.

**Первые две пробы в наборе — контрольные:** заведомо валидная и заведомо
невалидная. Раннер, который не дал `OK` на первой и `FAIL` на второй, не
различает исходы; `report.py` отказывается собирать по нему отчёт и выходит с
кодом 1. Без этой проверки матрица выглядела бы убедительно и не значила бы
ничего.

**Пробы исполняются из файлов, а не из строк shell.** На разведке `LIKE 'too%'`,
записанный через вложенные кавычки в `docker exec sh -c`, превратился в
идентификатор и дал ложный отказ «column not found». Раннер `psql.sh` подаёт SQL
на стандартный ввод именно поэтому.

Итог прогона — в `pg-compat/RESULTS.md`, ключевые числа продублированы в
`FIXTURES.md`.

## Границы

- Абсолютное время выполнения запросов не публикуется как характеристика
  Picodata: один хост, Docker Desktop на Windows.
- Коммерческие плагины (Radix — совместимость с Redis, Sirin — с Cassandra,
  Ouroboros, Franz) здесь **не проверялись**: они не входят в открытую часть.
- Отказ узла и потеря репликасета **проверены** — `failure/failure.sh`. Потеря
  одного узла — ответ полный; потеря обоих — молча неполный результат. После
  восстановления сценарий отдельно проверяет ДВА события: доступность данных и
  возврат ровно одного Raft-лидера — они не совпадают, лидер стабилизируется не
  сразу (наблюдался узел в роли Candidate). Оба сценария пересоздают кластер за
  собой.
- Расширение кластера **проверено** — `scale/scale.sh`. На корректном исходном
  кластере (с барьером) бакеты уезжали на новый репликасет сразу: 1000 на узел
  при первой же проверке, итог 6×1000. Ранее наблюдавшиеся «медленные» прогоны
  снимались с кластеров БЕЗ барьера готовности либо с неподнявшимися узлами
  (баг пути compose под MSYS) — доверять им нельзя. Готовность узла определять
  по числу бакетов, а не по Online и весу.
- **Не проверялись:** резервное копирование и восстановление (`BACKUP` требует
  конфигурационного файла, стенд запускает узлы флагами), обновление кластера
  между версиями, TLS, правила алертинга.
