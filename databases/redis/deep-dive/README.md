# Redis/Valkey: глубокое погружение — стенды

Живые стенды к серии статей «Redis/Valkey: глубокое погружение» на
[khorost.tech](https://khorost.tech). Redis
(`redis:8.8`, AGPLv3) и Valkey (`valkey/valkey:8.1`, BSD) рассматриваются как
равноправная, API-совместимая пара — стенды по умолчанию воспроизводимы на
обоих образах через `REDIS_IMAGE`, различия в поведении фиксируются явно там,
где они есть.

## Топология

Базовая топология (`compose/base.yml`): master + replica на выделенной сети
`redis-cookbook-net`.

| Сервис | Образ | Внутри сети | С хоста |
|---|---|---|---|
| `redis-master` | `${REDIS_IMAGE:-redis:8.8}` | `redis-master:6379` | `localhost:6379` |
| `redis-replica` | `${REDIS_IMAGE:-redis:8.8}` | `redis-replica:6379` | `localhost:6380` |

`redis-master` запускается с `--save 60 1 --appendonly yes --appendfsync
everysec` (RDB + AOF). `redis-replica` — `--replicaof redis-master 6379`,
поднимается после `service_healthy` мастера.

Более сложные топологии (Cluster, Sentinel) — отдельные compose-файлы
(`compose/cluster.yml`, `compose/sentinel.yml`), появятся в Стенде #4.

## Оба образа: Redis/Valkey

Образ параметризуется переменной окружения `REDIS_IMAGE` (используется
только в compose, не в Go-коде):

```bash
REDIS_IMAGE=redis:8.8 docker compose -f compose/base.yml up -d
# ...
REDIS_IMAGE=valkey/valkey:8.1 docker compose -f compose/base.yml up -d
```

### Версии (сверено живьём 2026-07-16, Task 1)

| Компонент | Версия | Как проверено |
|---|---|---|
| Redis (образ) | `redis:8.8` | пин явный (не `latest`); `docker exec redis-master redis-cli info server \| grep redis_version` → `redis_version:8.8.0` |
| Valkey (образ) | `valkey/valkey:8.1` | пин явный; `docker exec redis-master redis-cli info server` → `valkey_version:8.1.8` (поле `redis_version` в Valkey — совместимостное, показывает `7.2.4`, не путать с реальной версией) |

Оба образа проверены живьём: топология `compose/base.yml` поднята на каждом
по отдельности, `PING` на master/replica, запись на master → чтение на
replica через `--replicaof` подтверждают репликацию. Подробности —
`.superpowers/sdd/task-1-report.md` в `khorost.tech`.

## Датасет

`dataset/` — детерминированный генератор синтетических событий
(`user_id`/`session_id`/`ts`/`kind`/`payload`), общий для стендов #1/#3/#5.

```bash
cd dataset
go run . -users 2000 -events-per-user 50            # NDJSON в stdout
go run . -users 2000 -events-per-user 50 -load -addr 127.0.0.1:6379  # загрузка в Redis
```

Загрузка кладёт каждое событие как hash (`event:<user_id>:<i>`) + индекс по
времени в sorted set `events:by-ts`.

## Стенд #1

`structures/` — Go-модуль, инспектирует внутренние кодировки Redis/Valkey
(listpack, intset, quicklist, skiplist, hashtable) и живьём находит точки
перехода между ними по `OBJECT ENCODING`, сверяя с `CONFIG GET` для
соответствующих порогов.

```bash
cd structures
REDIS_ADDR=127.0.0.1:6379 go run . -scenario listpack-threshold
REDIS_ADDR=127.0.0.1:6379 go run . -scenario intset-threshold
REDIS_ADDR=127.0.0.1:6379 go run . -scenario memory-per-structure
```

Адрес читается из `REDIS_ADDR` (по умолчанию `127.0.0.1:6379`) — единый
контракт для всех стендов начиная с этой задачи.

Прогнано живьём на `redis:8.8` и `valkey/valkey:8.1` (топология —
`compose/base.yml`, без изменений). **Точки перехода кодировок совпали
побитово** на обоих образах — общий движок структур данных:

| Структура | Порог (config) | Значение | Точка перехода (набл.) |
|---|---|---|---|
| hash → hashtable (по числу полей) | `hash-max-listpack-entries` | 512 | `count=513` |
| hash → hashtable (по длине значения) | `hash-max-listpack-value` | 64 | `len=65` |
| list → quicklist | `list-max-listpack-size` | `-2` (8 КиБ/узел) | `count=1328` (короткие элементы `eN`) |
| zset → skiplist (по числу элементов) | `zset-max-listpack-entries` | 128 | `count=129` |
| zset → skiplist (по длине member) | `zset-max-listpack-value` | 64 | `len=65` |
| set (int) → hashtable | `set-max-intset-entries` | 512 | `count=513` |
| set: intset + нечисловой элемент, N=5 | `set-max-listpack-entries=128` | — | `intset → listpack` |
| set: intset + нечисловой элемент, N=138 | `set-max-listpack-entries=128` | — | `intset → hashtable` (138 > 128) |

Числа для `list` не совпадают напрямую с числом из `CONFIG GET
list-max-listpack-size` (`-2`), потому что для списков этот параметр — лимит
по байтам на узел quicklist (8 КиБ), а не по числу элементов; переход на
`count=1328` — эмпирически найденная точка для коротких элементов вида `eN`,
и она зависит от их суммарного размера, а не только от количества.

`MEMORY USAGE` на 10/100/1000 элементов — числа очень близки между образами,
кроме `stream`: у Valkey у стрима заметно больше базовый оверхед на пустом/
малом размере (константное значение `4296` байт и на 10, и на 100 записях —
похоже на предвыделение под radix-tree узел), у Redis рост более линейный от
`398` байт. Разница честно зафиксирована в `FIXTURES.md`, не выровнена
искусственно. Это единственное количественное сравнение образов на n=1 во
всей серии, которому можно доверять: `MEMORY USAGE` детерминирован для
конкретной сборки (без сэмплирования, в отличие от вытеснения в Стенде #5),
константа `4296` повторяется на двух разных N — структурная сигнатура, не
шум, — и разрыв на порядок не спишешь на разброс. Подробное обоснование — в
`FIXTURES.md`.

Полные логи прогонов — `scratchout/structures-redis.log` и
`scratchout/structures-valkey.log` (не коммитятся, воспроизводятся командами
выше). Числа для статьи — в `FIXTURES.md`, раздел «Стенд #1: структуры
данных».

## Стенд #2

`eventloop/` — Go-модуль, измеряет три вещи на живом инстансе: латентность
одиночной команды без пайплайна, выигрыш от пайплайнинга, и разницу
throughput при `io-threads 1` (дефолт) vs `io-threads 4` под конкурентной
нагрузкой.

```bash
cd eventloop
REDIS_ADDR=127.0.0.1:6379 go run . -scenario no-pipeline -n 10000
REDIS_ADDR=127.0.0.1:6379 go run . -scenario pipeline -n 10000
REDIS_ADDR=127.0.0.1:6379 go run . -scenario threaded-io -n 10000 -concurrency 8
```

`threaded-io` сам по себе не перезапускает контейнер — сам процесс не может
поменять `io-threads` без рестарта redis-server (это параметр только
времени запуска). Сценарий печатает фактические `CONFIG GET io-threads` /
`io-threads-do-reads` сервера, к которому подключился, — так в логе видно,
какой прогон к какой конфигурации относится. Смена конфигурации — снаружи:

```bash
# io-threads=1 (дефолт из compose/base.yml)
REDIS_IMAGE=redis:8.8 docker compose -f compose/base.yml up -d
cd eventloop && REDIS_ADDR=127.0.0.1:6379 go run . -scenario threaded-io -n 10000 -concurrency 8
cd .. && docker compose -f compose/base.yml down -v

# io-threads=4 io-threads-do-reads yes — тот же образ, только master,
# команда переопределена через `docker compose run` (без правки base.yml)
REDIS_IMAGE=redis:8.8 docker compose -f compose/base.yml run --rm -d --name redis-master \
  --service-ports redis-master redis-server --port 6379 \
  --save 60 1 --appendonly yes --appendfsync everysec \
  --io-threads 4 --io-threads-do-reads yes
cd eventloop && REDIS_ADDR=127.0.0.1:6379 go run . -scenario threaded-io -n 10000 -concurrency 8
cd .. && docker stop redis-master && docker rm redis-master && docker network rm redis-cookbook-net
```

Прогнано живьём на `redis:8.8` и `valkey/valkey:8.1`, каждый threaded-io
прогон — по 2 повтора на конфигурацию (проверка разброса между запусками, а
не только между образами). **Честный результат: на этой нагрузке (N=10000,
concurrency=8, localhost) эффект `io-threads 4` — в пределах шума на Redis и
слабый, но направленно устойчивый на Valkey** (оба повтора Valkey с
`io-threads=4` дали более высокий throughput, чем оба повтора с
`io-threads=1`; на Redis повторы с `io-threads=4` дали то самый высокий, то
самый низкий throughput среди всех четырёх прогонов). При двух повторах на
конфигурацию это не статистически надёжный вывод, а честно зафиксированное
наблюдение — подробности и все числа в `FIXTURES.md`.

**Методологическая оговорка (важно для цитирования абсолютных чисел).**
Стенд запущен с хост-машины Windows через Docker Desktop — сетевой путь
клиент→контейнер проходит через виртуализованный сетевой стек, а не голый
TCP-loopback на Linux. Абсолютная латентность одиночной команды (`p50≈500
мкс` без пайплайна) заметно выше, чем типичные цифры для Redis на
bare-metal Linux (обычно десятки-сотни мкс) — это оверхед платформы
измерения, а не свойство Redis/Valkey. Относительные сравнения (пайплайн
vs без пайплайна, Redis vs Valkey, io-threads=1 vs 4) в рамках одного и
того же измерительного стенда остаются валидными.

Полные логи — `scratchout/eventloop-redis.log`,
`scratchout/eventloop-valkey.log` (не в git, воспроизводимы командами
выше). Числа для статьи — `FIXTURES.md`, раздел «Стенд #2».

## Стенд #3

`persistence/` — Go-модуль, измеряет, что реально теряется при `kill -9` в
каждом durability-режиме (RDB-only, AOF `always`/`everysec`/`no`, гибрид
RDB+AOF). Центральная цифра серии — контраст «Redis как кеш vs Redis как
источник истины» строится на этих числах.

```bash
cd persistence
REDIS_ADDR=127.0.0.1:6379 go run . -scenario durability-loss -n 5000 -container redis-master -mode <label>
# ... рестарт контейнера на том же volume ...
REDIS_ADDR=127.0.0.1:6379 go run . -scenario count-recovered -container redis-master -mode <label> -confirmed <K>
```

`durability-loss` пишет `dur:<i>` монотонным счётчиком без пайплайна, на
середине (`i=n/2`) сразу после подтверждённого `SET` убивает контейнер
настоящим `docker kill -s SIGKILL` (не `docker stop` — SIGTERM дал бы
Redis шанс сохранить всё перед выходом и фиктивный «ноль потерь» на любом
режиме) и проверяет через `docker inspect`, что контейнер реально умер
(`Status=exited`, `ExitCode=137` = 128+9). `count-recovered` подключается
после рестарта того же контейнера на том же volume, ждёт готовности и
считает `DBSIZE` (в БД кроме `dur:*` ничего нет — `FLUSHALL` в начале
`durability-loss`).

Режим персистентности задаётся снаружи, через env `compose/base.yml`
(команда `redis-server` в `base.yml` параметризована: `REDIS_APPENDONLY`,
`REDIS_APPENDFSYNC`, `REDIS_SAVE_SECONDS`, `REDIS_SAVE_CHANGES` — дефолты
не меняют исходное поведение, `save 60 1 --appendonly yes --appendfsync
everysec`, это же и есть режим `hybrid`). `redis-master` теперь держит
`/data` в именованном volume (`redis-master-data`) — рестарт `docker
compose up -d redis-master` без пересоздания контейнера гарантированно
использует тот же диск.

Полная матрица (5 режимов × образ) — одной командой:

```bash
cd databases/redis/deep-dive
./ops/persistence-kill-matrix.sh redis:8.8
./ops/persistence-kill-matrix.sh valkey/valkey:8.1
```

Образ — единственный аргумент скрипта (`$1`); скрипт сам выставляет
`REDIS_IMAGE` перед каждым `docker compose up`, отдельно передавать
`REDIS_IMAGE=...` не нужно. Скрипт для каждого режима
(`rdb-only`/`aof-always`/`aof-everysec`/`aof-no`/`hybrid`): поднимает
`redis-master` с нужными env, пишет 5000 ключей с килом на середине,
рестартует контейнер на том же volume, считает восстановленное число
ключей, затем `down -v` — чистый volume перед следующей ячейкой матрицы.

Прогнано живьём на `redis:8.8` и `valkey/valkey:8.1`, каждая полная матрица
(5 режимов) — по 2 независимых прохода на образ (проверка разброса, не
единичный прогон).

**Честный результат — и он верен только для того сбоя, который здесь
измеряли (`kill -9` ПРОЦЕССА, не потеря питания и не падение ОС):**

| Режим | Потеряно из 2501 подтверждённой записи |
|---|---:|
| `rdb-only` | **2501†** |
| `aof-always` | 0* |
| `aof-everysec` | 0* |
| `aof-no` | 0* |
| `hybrid` | 0* |

**`*`** — ноль это свойство краха процесса, а не надёжности режима:
`write()` уже отдал данные в page cache ядра, а ядро при `kill -9` живо и
дописывает их на диск. При потере питания `everysec` теряет до 1с записей,
`no` — всё, что накопилось в page cache. **Этот стенд такой сбой не
воспроизводит; не цитировать как «`appendfsync no` ничего не теряет».**

**`†`** — цифра о соотношении окна теста и интервала снапшота, не о
свойстве RDB: `save 60 1` ждёт 60с, тест укладывается в ~0.8с, снапшот с
данными не успевает сработать ни разу. **Не цитировать как «RDB теряет
100%».**

Одинаково на обоих образах, во всех 4 полных проходах, без разброса. Это не
подгонка и не ошибка: `kill -9` убивает процесс, а не ОС, а `write()` в
AOF-файл отдаёт данные ядру (page cache) синхронно при выполнении команды,
независимо от политики `appendfsync` — которая управляет только тем, когда
page cache физически сбрасывается на диск. Разница между режимами fsync
проявилась бы при падении ОС/отключении питания (page cache теряется вместе
с ядром), не при убийстве процесса.

Чего стенд **не** показывает по построению: рваный/усечённый AOF. Килл
прилетает строго после подтверждённого `SET`, ни одна команда не «в полёте»,
поэтому хвост AOF всегда цел и `tail check` гарантированно даёт `10/10` —
это следствие методики, а не свойство AOF.

Побочная находка: `appendfsync always` без пайплайна пишет на порядок
медленнее остальных режимов (≈9.5с против ≈0.7–0.9с на те же 2501 записи,
≈262 ops/s против ≈2800–3500 ops/s) — синхронный fsync перед каждым `OK`.
Весь durability-выигрыш `always` над `everysec`/`no`, отсутствующий в этом
методе измерения (`kill -9` процесса), проявился бы именно при
падении ОС/питания — там `always` защищает, а `everysec` теряет до 1с
записей, а `no` — сколько накопилось в page cache.

**Методологическая оговорка** — та же, что в Стенде #2: Docker Desktop на
Windows виртуализует и сеть, и файловую систему (WSL2/Hyper-V backend), так
что абсолютная скорость записи выше типичных bare-metal цифр. Наблюдаемое
поведение (write() переживает `kill -9` процесса независимо от fsync)
согласуется с задокументированной моделью Unix page cache, поэтому в данном
случае виртуализация не выглядит источником искажения — но это
предположение: проверка потребовала бы реального падения ОС/хоста, вне
рамок этой задачи.

Полные логи — `scratchout/persistence-redis.log`,
`scratchout/persistence-valkey.log` (не в git, воспроизводимы командами
выше). Полная матрица потерь и скорости записи по режимам — `FIXTURES.md`,
раздел «Стенд #3».

## Стенд #4

`topology/` — Go-модуль, и `ops/topology-demo.sh` — оркестрация: полный
live-прогон Cluster (resharding под нагрузкой, failover убийством мастера),
Sentinel (failover убийством мастера) и попытки воспроизвести split-brain.
Не концептуальный обзор: все числа ниже — из реальных событий топологии.

### Топологии

`compose/cluster.yml` — 6 узлов (3 мастера + 3 реплики, `--cluster-replicas
1`), сеть `redis-cluster-net`, порты `7001..7006` на хосте.

`compose/sentinel.yml` — `redis-master` + `redis-replica-1/-2` + `sentinel-1/2/3`
(`quorum 2`), сеть `redis-sentinel-net` с **явной подсетью** `172.28.0.0/16` и
**статическими IP** (`172.28.0.10/.11/.12`).

**Почему Sentinel здесь мониторит мастер по IP, а не по имени.** Первая
версия стенда использовала `sentinel monitor mymaster redis-master 6379` с
`resolve-hostnames yes`, и **failover не случился ни разу (0 из 2 попыток)**,
`sentinel_tilt:1` на момент 80-секундного дедлайна. После перехода на
статические IP failover заработал (~7с, 2 из 3 прогонов).

**Что здесь измерено, а что — гипотеза (важно не спутать).** Измерено:
(а) после `docker kill` встроенный DNS Docker отдаёт по имени мёртвого
контейнера ошибки и таймауты — но это видно **в логе Go-клиента**
(`lookup redis-master: i/o timeout`), а не Sentinel; (б) 0/2 промоушена на
DNS-конфигурации против 2/3 на IP-конфигурации; (в) `sentinel_tilt:1` в обоих
случаях. **Не измерено:** что именно резолв имени задерживал event loop
Sentinel — инструмента, который бы это показал, у стенда нет, и Sentinel
такой метрики не отдаёт. Более того, **TILT возникает и на статических IP**
(1/3 у redis, 3/3 у valkey), то есть DNS в любом случае не единственная
причина и спутан с загрузкой хоста. Выборки крошечные (2 и 3 прогона).

Поэтому: «мониторить по IP» — **разумная предосторожность, подкреплённая
наблюдаемой корреляцией**, а не доказанный причинно-следственный вывод. См.
`FIXTURES.md` и комментарий в `compose/sentinel.yml`.

### Запуск

```bash
cd databases/redis/deep-dive
./ops/topology-demo.sh reshard           redis:8.8
./ops/topology-demo.sh cluster-failover  redis:8.8 3   # 3 повтора
./ops/topology-demo.sh sentinel-failover redis:8.8 3
./ops/topology-demo.sh split-brain       redis:8.8
./ops/topology-demo.sh all               valkey/valkey:8.1 3
```

Go-клиент запускается **внутри контейнера** в сети топологии, а не с хоста:
узлы Cluster объявляют себя внутренними docker-адресами (`172.x.x.x`), которые
с Windows-хоста через Docker Desktop недостижимы (проверено: прямое
TCP-соединение с хоста на такой адрес — `NOT REACHABLE`). Клиент собирается
**один раз** в `topology/bin/topology` (gitignored) до сценариев: с `go run`
компиляция занимала 15–30с, и килл прилетал раньше, чем клиент успевал
подключиться — сценарий не мерил ничего.

Все docker-level проверки (kill, `inspect`, `cluster nodes`, опрос Sentinel)
делает скрипт **снаружи**, с хоста: это независимый ground truth. Go-клиент
внутри видит только то, что видел бы обычный клиент приложения.

### Что измеряется и как

| Сценарий | Что делает | Чем подтверждается реальность события |
|---|---|---|
| `reshard` | `redis-cli --cluster reshard` переносит 2000 слотов, одновременно клиент пишет 100000 ключей | `cluster slots` до/после; каждый ключ верифицируется `GET` |
| `cluster-failover` | `docker kill -s SIGKILL` мастера во время записи | `docker inspect` → `exited 137`; промоушен реплики виден на **другом** мастере через `cluster nodes` |
| `sentinel-failover` | `docker kill -s SIGKILL` мастера во время записи | `docker inspect` → `exited 137`; `SENTINEL get-master-addr-by-name` опрашивается **с хоста**, независимо от клиента |
| `split-brain` | партиция мастера от Sentinel-кворума | `sentinel master mymaster` (флаги/`status`), `INFO sentinel` (`sentinel_tilt`), `INFO replication` (`role`) |

**Ключевой момент методики — как ловится «окно недоступности».** Живьём
выяснилось, что недоступность мастера **не обязательно доезжает до клиента
как ошибка**: клиент может просто **заблокировать один вызов `Set()`** на всё
время недоступности и потом успешно вернуть `OK` — не «ошибка записи», а
«одна аномально долгая успешная запись». Так вело себя **не всё подряд**:

- **Sentinel** (`FailoverClient`) — именно такой случай: `failed=0 stalled=1`,
  один вызов висел 10.64с и вернул `OK`. Детектор «только по ошибкам» этот
  инцидент **не увидел бы вообще**.
- **Cluster** (`ClusterClient`) — наоборот: во **всех 6** прогонах длинный
  вызов в итоге **возвращал ошибку** (`failed=1 stalled=0`, maxLatency
  41.5–48.4с). Тут детектор по ошибкам сработал бы.

Поэтому деградация детектируется **двумя** признаками сразу: `err != nil`
**или** длительность одного вызова > 300мс — заранее полагаться на то, что
ошибка будет, нельзя.

**Отдельно и не путать:** в Cluster-прогонах ошибка была **ровно одна на
279597 попыток** (0.0004%). То есть инцидент на 45 секунд невидим для
мониторинга **по доле ошибок**, хотя сама ошибка в логе есть.

### Результаты (живьём, `redis:8.8` и `valkey/valkey:8.1`)

Полные числа, спред по повторам и оговорки — в `FIXTURES.md`, раздел
«Стенд #4». Кратко:

- **Resharding** идёт без потерь: 100000 ключей, 0 потеряно, все
  верифицированы `GET`; клиент видит реальные `MOVED` (46 и 14 за прогон) и
  переподключается сам. `ASK` в финальных прогонах поймать не удалось
  (`ASK=0` на обоих образах — окно миграции конкретного ключа слишком узкое).
- **Cluster failover** отрабатывает всегда (3/3 повтора на обоих образах),
  но клиентское окно недоступности (**~42–49с**) в **2+ раза длиннее**
  серверного промоушена (**~18–23с**). Разницу создаёт **не кластер**: это
  сочетание ненастроенного go-redis (дефолтные таймауты пула, который долго
  долбится в мёртвый IP) и docker-bridge, дающего `no route to host`.
- **Sentinel failover** на исправленной (IP) конфигурации — промоушен за
  **~7с**, клиент восстанавливается за **~10.6с**. Но **не в каждом
  прогоне**: в части повторов Sentinel уходил в **TILT** и не промоутил
  вообще (redis 2/3, valkey 0/3 — это про среду, не про движки).
- **Split-brain: на `valkey/valkey:8.1` воспроизведён полностью, на
  `redis:8.8` — нет.** На Valkey возникли **два мастера одновременно**:
  Sentinel промоутил новый (T+8.7с), а изолированный старый продолжал
  принимать записи — **80 из 80 записей подтверждены клиенту, а на новом
  мастере уцелело 5**; остальные 75 для клиентов, идущих за Sentinel,
  не видны. На Redis второго мастера не возникло вовсе: Sentinel сидел в
  TILT, не пометил мастер `s_down` и не начал failover — расходиться было
  нечему. **Не цитировать «split-brain не воспроизвёлся» как результат
  стенда: это верно только для redis-прогона и только из-за TILT.**
  Подробности и все оговорки — в `FIXTURES.md`.

Полные логи — `scratchout/topology-redis.log`, `scratchout/topology-valkey.log`
(не в git, воспроизводятся командами выше).

## Стенд #5

`memory-eviction/` — Go-модуль, `ops/eviction-demo.sh` — оркестрация:
`maxmemory-policy` живьём. Контейнер поднимается с реальным лимитом
(`--maxmemory 64mb`, через `REDIS_MAXMEMORY`/`REDIS_MAXMEMORY_POLICY` в
`compose/base.yml`), клиент заливает ключи до тех пор, пока сервер не начнёт
вытеснять — или, на `noeviction`, отказывать. Все числа ниже — из реальных
прогонов, не из документации.

### Запуск

```bash
cd databases/redis/deep-dive
./ops/eviction-demo.sh redis:8.8
./ops/eviction-demo.sh valkey/valkey:8.1
```

Матрица: `allkeys-lru` / `allkeys-lfu` / `volatile-ttl` / `noeviction`, плюс
отдельный прогон `volatile-ttl` **без единого TTL** (проверка вырождения).
Под каждую ячейку — свежий контейнер и `down -v`, чтобы счётчики и keyspace
не протекали между ячейками.

### Три класса ключей

| Класс | Сколько | Что с ним делают |
|---|---|---|
| `hot:N` | 200 × 1 КиБ | перечитываются `GET`-ом каждые 20 раундов — сигнал для LRU (свежий idle) и LFU (счётчик обращений) |
| `cold:N` | 2000 × 1 КиБ | записаны один раз и больше не тронуты. TTL получают **только** при `volatile-ttl` (300–420с — заведомо дольше прогона, чтобы истечение по часам не подмешивалось к вытеснению) |
| `filler:N` | 4 КиБ, тысячи | непрерывно доливаются, создавая само давление |

### Что здесь фатально, а что — результат

`"OOM command not allowed"` на `noeviction` — это **измеряемый результат**, он
ловится и фиксируется. Та же ошибка на `allkeys-lru` означала бы, что сервер
не вытесняет там, где обязан, — **сломанный прогон**, `os.Exit(1)`.
Аналогично: `evicted_keys=0` под вытесняющей политикой, или
`used_memory_peak`, не дотянувший до 90% `maxmemory`, завершают прогон с
ошибкой, а не печатают «0 вытеснено» как находку.

### Результаты (живьём, оба образа)

Полные числа, разброс по повторам и оговорки — в `FIXTURES.md`, раздел
«Стенд #5». Кратко:

- **Главный результат — `allkeys-lfu` не отличает холодное от filler вообще,
  и это измерено, а не выведено из исходников.** `OBJECT FREQ`: у `cold`
  счётчик `min=медиана=max`, у `filler` — **ровно тот же**
  (4/4/4 либо 5/5/5 в зависимости от прогона), у `hot` — **16** (медиана).
  Оба класса записаны по одному разу, счётчик совпадает **до единицы**, и
  выбор между ними у LFU вырождается в случайный. Совпадение держится во
  **всех** прогонах на **обоих** образах — самый устойчивый результат стенда.
- **`volatile-ttl` — та же неразличимость**, по той же причине: TTL у `cold`
  и `filler` берутся из **одного диапазона** [300,420)с, так что «ближайшее
  истечение» их не разделяет. Высокая выживаемость `cold` под LFU и
  `volatile-ttl` — **не защита, а неразличимость** плюс численное
  доминирование `filler` (~85% keyspace).
- **`allkeys-lru` — единственная политика, которая `cold` реально
  различает:** возраст работает как дискриминатор, `cold` собирает
  **53–62%** вытеснений, удерживая **11–14%** keyspace — перевес
  **≈×4–5.6** (точное значение зависит от того, брать за базу стартовую долю
  ~14% или финальную ~11%). Знак перекоса **одинаков во всех прогонах** на
  обоих образах. У LFU перевес всегда **кратно меньше** (×0.6–2.7).
- **`hot` выжили на 100% — но цитировать это как «LRU защищает горячее»
  нельзя.** Под `volatile-ttl` и `noeviction` это вообще **не измерение**:
  `hot` пишутся без TTL, то есть под `volatile-*` невытесняемы **по
  построению**. Под `allkeys-*` это наблюдение, но `hot` защищены **двумя**
  неразделёнными механизмами — сигналом обращения и тем, что составляют
  1.4% keyspace (шанс попасть в выборку из 5 ≈ 7%).
- **`volatile-ttl` без единого TTL вырождается в `noeviction` — проверено
  живьём:** `"OOM command not allowed"`, `evicted_keys=0`. Вытеснять
  нечего — volatile-множество пусто.
- **`noeviction`:** `"OOM command not allowed"`, `evicted_keys=0`, все 2200
  hot+cold целы. Точка отказа почти детерминирована: redis — `filler:12120`
  в **3 прогонах из 3**; valkey — `12196`/`12196`/**`12163`**, то есть
  побайтовой повторяемости **не показал**.
- **Сравнивать образы по выживаемости этот стенд НЕ позволяет.** Разброс
  между прогонами одного образа (у redis LFU — до **7.4 п.п.**) перекрывает
  всю наблюдавшуюся разницу между образами. Первая редакция публиковала
  «устойчивое расхождение redis/valkey» — оно **снято** как артефакт
  выборки из 2–3 прогонов, см. `FIXTURES.md`, «РЕТРАКЦИЯ».
- **`mem_fragmentation_ratio` читать как фрагментацию нельзя:** 1.40–1.42
  (redis) / 1.27–1.28 (valkey) при `allocator_frag_ratio` = **1.00–1.01**.
  jemalloc не фрагментирует практически совсем; разрыв даёт
  `rss_overhead_ratio` (1.19–1.24 / 1.13–1.17) — накладные расходы процесса,
  на Docker Desktop под Windows в основном артефакт среды. `MEMORY DOCTOR`
  при этом ложно тревожит **на обоих образах** (пункт `may be due to Lua
  scripts or Modules` — при полном отсутствии Lua и модулей в стенде), а
  набор его пунктов у valkey беднее **только** из-за непройденного порога
  1.4, а не из-за другой логики. Вердикт перекидывается и **между прогонами
  одного образа**.

Полные логи — `scratchout/memory-eviction-redis.log`,
`scratchout/memory-eviction-valkey.log` (не в git, воспроизводятся командами
выше).

## Стенд #6

`streams-lua/` — Go-модуль: consumer groups (`XREADGROUP`/`XPENDING`/
`XCLAIM`, реальный at-least-once), атомарность `EVAL` против настоящей
гонки, `EVAL` против `FUNCTION`. Топология — тот же `compose/base.yml`, без
дополнительных профилей.

### Запуск

```bash
cd databases/redis/deep-dive
REDIS_IMAGE=redis:8.8 docker compose -f compose/base.yml up -d
cd streams-lua
go run . -scenario consumer-groups
go run . -scenario race-without-lua -workers 20 -iterations 500
go run . -scenario atomic-with-lua  -workers 20 -iterations 500
go run . -scenario eval-vs-function
go run . -scenario eval-vs-function -swap-order   # обратная ориентация серий
cd .. && docker compose -f compose/base.yml down -v
# повторить REDIS_IMAGE=valkey/valkey:8.1
```

### Сценарии

| Сценарий | Что показывает |
|---|---|
| `consumer-groups` | `XADD` 1000 сообщений, 3 консьюмера в группе, один (`consumer-2`) обрабатывает батч и «падает» без `XACK` — `XPENDING` видит зависшее, `XCLAIM` передаёт другому консьюмеру, который переобрабатывает те же ID: реальные дубликаты at-least-once |
| `race-without-lua` | `-workers` горутин делают read-modify-write над общим счётчиком раздельными `GET`+`SET` — реальные потерянные инкременты |
| `atomic-with-lua` | тот же сценарий одним атомарным `EVAL`. Оба сценария доказывают, что горутины реально пересекались во времени, прежде чем публиковать «0 потерь» как результат |
| `eval-vs-function` | latency одного и того же скрипта через `EVAL` (кеш по SHA после первого вызова) и через `FUNCTION LOAD`+`FCALL` (функция загружена заранее). `-swap-order` разворачивает порядок серий — отделяет эффект команды от эффекта порядка |

### Что здесь фатально, а что — результат

Потерянный инкремент в `race-without-lua` — это **не ошибка команды**: `GET`
и `SET` оба отрабатывают успешно, эффект теряется из-за гонки между ними.
Это измеряемое явление, не брак прогона. Фатально (`os.Exit(1)`) — другое:
любая настоящая ошибка команды; `race-without-lua`/`atomic-with-lua`, где
окна `GET`/`SET`(`EVAL`) разных горутин пересеклись **менее чем в 50%
попыток** (конкурентность не доказана — «0 потерь» тогда ничего не значит;
порог взят долей, а не «хоть одно пересечение», чтобы проходить с запасом,
а не на границе — фактически наблюдается 99.4–99.9%);
`atomic-with-lua` с итоговым значением выше теоретического максимума;
`consumer-groups` с дубликатами `0` после `XCLAIM` (падение не
индуцировано) или с `XPENDING`, не опустевшим после финального `XACK`.

### Результаты (живьём, оба образа)

Полные числа, разброс по повторам и методология — в `FIXTURES.md`, раздел
«Стенд #6». Кратко:

- **`consumer-groups`:** доставлено 1000/1000 на обоих образах, у
  `consumer-2` зависло 50 сообщений без `XACK`. После `XCLAIM` (`consumer-1`,
  форс, `MINIDLE 0`) — **ровно 50 реальных дубликатов** (те же ID обработаны
  дважды), 950 обработаны один раз, `XPENDING` после этого пуст. Одинаково
  на `redis:8.8` и `valkey/valkey:8.1` — сценарий детерминированный (раунд-
  робин, не параллельные горутины).
- **`race-without-lua`: 9044–9064 потерянных инкремента из 10000 попыток
  (90.4–90.6%)** на обоих образах, три прогона на каждом — три разных числа
  (реальный разброс, не одна удобная цифра). Конкурентность в каждом прогоне
  доказана: 99.4–99.9% попыток пересеклись во времени с попыткой другой
  горутины.
- **`atomic-with-lua`: 0 потерь во всех 6 прогонах** (3× `redis:8.8`, 3×
  `valkey/valkey:8.1`), при той же (99.4–99.9%) доказанной конкурентности.
  Атомарность `EVAL` подтверждена измерением, а не взята из документации.
- **`eval-vs-function`: большой разницы между `EVAL` и `FCALL` нет** — всё в
  пределах ≈3% от средней латентности вызова (~390мкс на этой машине).
  Ожидаемо: после первого вызова сервер кеширует тело `EVAL`-скрипта по SHA1
  и дальше исполняет тот же скомпилированный чанк, что и `FCALL`. Но
  **«разницы нет вообще» сказать нельзя**: на `redis:8.8` устойчиво держится
  **+10.8мкс в пользу `FCALL`** (6/6 прогонов одного знака, в обеих
  ориентациях `-swap-order` → это эффект команды, а не порядка серий; t=4.31,
  p≈0.008). Скучное и правдоподобное объяснение — `EVAL` шлёт 138 байт тела
  скрипта в каждом вызове против короткого имени у `FCALL`; при этом, если
  механизм такой, то это скорее **цена записи в сокет на стороне клиента**, а
  не работа сервера — «`EVAL` дороже обходится Redis» эти данные **не
  показывают**. **На `valkey/valkey:8.1` данных не хватает**: +1.9мкс с ДИ
  **[−7.7, +11.5]**, который накрывает и ноль, и redis-овские +10.8 — тот же
  эффект там не подтверждён и **не опровергнут** (контраст образов p≈0.08).
  **Строить на 11мкс архитектурные решения не стоит**: `FUNCTION` выбирают за
  версионирование, деплой и `FUNCTION DUMP`/`RESTORE`, а не за эти
  микросекунды.
- **Артефакт часов и почему первая редакция этого стенда мерила неправильно.**
  На этой машине `time.Since()` вокруг реального round-trip к Redis
  регулярно возвращает ровно 0 при честно выполненной команде (**34.9–46.4%**
  замеров в прогонах ниже). Нули вносят в сумму 0, поэтому среднее по
  ненулевым замерам завышено **ровно в `1/(1−доля_нулей)` раз** — это
  тождество, а не гипотеза, и здесь это ×1.54…×1.87, **по-разному у разных
  серий**. Первая редакция отбрасывала нули и публиковала перцентили
  выживших — то есть **сама порождала** тот «разброс ±200мкс», который тогда
  был списан на виртуализационный шум среды. Исправлено: главным числом
  печатается `elapsed/attempts` (берёт только две отметки времени — начало и
  конец серии, от распределения нулей внутри не зависит); перцентили
  печатаются с долей нулей и множителем смещения рядом. **Механизм появления
  нулей не диагностирован** (все ненулевые значения кратны 100нс, а часы с
  шагом 100нс не могут округлить ~390мкс до нуля) — и для корректности замера
  он не нужен.

Полные логи — `scratchout/streams-lua-redis.log`,
`scratchout/streams-lua-valkey.log` (не в git, воспроизводятся командами
выше).

docker compose -f compose/base.yml down -v

# Повторить всё выше на REDIS_IMAGE=valkey/valkey:8.1.

# backup/restore — отдельный полный цикл: скрипт сам поднимает и уничтожает
# redis-master, образ берёт из своего аргумента (REDIS_IMAGE задавать не нужно).
./ops/ops-demo.sh redis:8.8
./ops/ops-demo.sh valkey/valkey:8.1

### Java-реактор

`java/pom.xml` — родительский pom (`tech.khorost:redis-deep-dive-parent`)
для Java-стендов серии; пока единственный модуль — `ops-stand/java`
(`<module>../ops-stand/java</module>`, относительный путь — модули
реактора лежат не в одном каталоге с родителем, `ops-stand/` и `java/` —
соседние директории `redis/deep-dive/`). Lettuce `7.6.0.RELEASE` — та же
версия, что у соседнего стенда `databases/redis/client-resilience`
(другая статья, но одна и та же технология — версия совпадает намеренно).
commons-pool2 `2.13.1`.

Локальная сборка на Windows-хосте — через WSL (см. `local-toolchains-verification`
в памяти проекта): системный JDK там 17, для `maven.compiler.release=21`
нужен portable `~/jdk21`; сборка **обязательно** на нативной FS WSL
(`~/osvbuild`), не на `/mnt/...` — иначе Maven не может писать
`target/*.class` (баг drvfs). `ops/verify-static.sh`, наоборот, собирает
Java **докеризованным** Maven (`maven:3.9-eclipse-temurin-21`) — портативно,
без зависимости от WSL, работает и на self-hosted runner.

### Сценарии

| Сценарий | Что показывает |
|---|---|
| `pool-sizing` (Go и Java) | 50 горутин/потоков одновременно пишут через клиент с `PoolSize`/`GenericObjectPool` 5/20/50 — throughput, латентность успешных операций (несмещённое среднее + p50/p95/p99), число ошибок "pool timeout" на каждый размер |
| `monitoring` (Go) | живой снимок `INFO clients`/`CLIENT LIST`/`SLOWLOG GET`/`LATENCY HISTORY`+`LATEST` после гарантированно медленной реальной операции (`KEYS` над 300000 ключами) |
| `ops/ops-demo.sh <образ>` | полный backup/restore-цикл: живой снапшот (`redis-cli --rdb`), `down -v`, доказательство удаления, restore в свежий volume, проверка DBSIZE+содержимого |

### Что здесь фатально, а что — результат

Ошибка "pool timeout" при тесном пуле — это **не сбой** (не `os.Exit(1)`,
не `RuntimeException`): она ожидаема и явно исключена из "прочих ошибок".
Фатально — любая ДРУГАЯ ошибка команды после того, как соединение уже
получено (и на Go-, и на Java-стороне это отдельный try/catch вокруг самой
команды). Для `ops-demo.sh` фатально: DBSIZE после restore не совпал с
DBSIZE до backup; содержимое точечного ключа после restore не совпало
побайтово; "доказательно пустой" инстанс оказался не пуст (значило бы, что
`down -v` не уничтожил данные по-настоящему).

### Результаты (живьём, оба образа, оба клиента)

Полные числа, методология и разбор находок (масштабирующий эффект
`PoolTimeout`, найденный эффект порядка на Java-стороне, цензурирование
выборки в перцентилях, грабли обёрнутых Lettuce-соединений, молчаливый
провал AOF-restore, `LATENCY HISTORY` против `SLOWLOG`) — в `FIXTURES.md`,
раздел «Стенд #7».

**Оговорка ко всем абсолютным числам ниже: Docker Desktop на Windows
(WSL2), а не нативный Redis** (на голом Linux по loopback round-trip — на
два порядка меньше). Надёжны только относительные сравнения внутри одного
прогона. Кратко:

- **Pool-sizing (Go, `-pool-timeout 2ms`, обе ориентации × 3 повтора на
  образ = 12 прогонов):** size=5 — **52.3–54.0%** ошибок pool timeout,
  size=20 — **2.8–8.2%**, size=50 — **0.0%** во всех 12 (пул ==
  конкурентность, очереди нет по построению). Число ошибок **целиком
  зависит от выбранного `PoolTimeout`** — на 1мс те же размеры дали
  73.2%/41.3%/0.0%, на 5мс — 0.4%/0.2%/0.0%. **Порядок арм на Go-стороне
  не значит ничего** (прямая 52.3–53.7% против обратной 53.1–54.0% на
  size=5).
- **Pool-sizing (Java/Lettuce, тот же `PoolTimeout`): то же направление,
  но найден эффект порядка.** ≈74% / ≈42% / 0% (среднее по обеим
  ориентациям). В отличие от Go, у Java ориентация значит: size=5 даёт
  78.0–78.6% первой армой и 70.2–70.3% последней — интервалы не
  пересекаются, разрыв ≈8 п.п. Прогрев JVM — правдоподобный, но **не
  диагностированный** механизм. **Одна ориентация врала бы на ≈8 п.п.** —
  ради этого и гонялись обе.
- **Go↔Java по абсолюту сравнивать нельзя:** окружения не выровнены (Go
  нативно на хосте, Java в WSL2 — разные сетевые пути к тому же порту),
  реализации пула разные (семафор на канале vs `GenericObjectPool`), и
  эффект порядка измерен у Java, но не у Go. Три оси разом; стенд их не развязывает.
  Совпадает **направление**, и оно устойчиво во всех 24 прогонах.
- **Латентность при разных размерах пула стенд сравнимо НЕ меряет.**
  Перцентили считаются по успешным операциям, а доля успешных у арм разная
  (46.7% на size=5 против 100% на size=50 у Go) — выборки цензурированы
  по-разному. Java-арма с более сильным цензурированием даёт **обратный**
  порядок p50 (0.842мс на size=5 против 1.659мс на size=50). Честный вывод
  этого стенда — только **доля отказов**.
- **go-redis сам ретраит после pool timeout — по умолчанию.** Проверено
  живьём: на `PoolSize=1` внутренний счётчик пула насчитал 1660 таймаутов
  ожидания за прогон, а вызывающий код увидел только 30 ошибок. С
  ретраями "число pool timeout ошибок" почти всегда занижено на порядок —
  стенд явно выключает ретраи (`MaxRetries: -1`), чтобы измерить реальную
  остроту контеншна, а не то, что от него осталось после автоповтора.
- **Backup/restore: полный цикл на 6001 ключе, оба образа.** Снапшот через
  `redis-cli --rdb` (717372/717373 байт), `down -v`, доказанное удаление
  (`DBSIZE=0`, точечный ключ отсутствует), restore, DBSIZE и содержимое
  ключа совпали побайтово.
- **Находка, а не гипотеза: AOF молча съедает RDB-restore.** С дефолтным
  `--appendonly yes` (как в `compose/base.yml`) сервер, запущенный на
  пустом volume с ОДНИМ только `dump.rdb`, **игнорирует его целиком** —
  создаёт пустой AOF base file и стартует с `DBSIZE=0`, без единой ошибки
  в логе (`BGSAVE done, 0 keys saved`). Восстановление сработало только
  после временного `REDIS_APPENDONLY=no` на время загрузки. Без явной
  проверки `DBSIZE` этот провал остался бы незамеченным.
- **Мониторинг: `SLOWLOG` поймал `KEYS`, `LATENCY HISTORY` — нет.**
  `KEYS` над 300000 ключами занял 38.6мс (redis) / 25.3мс (valkey)
  серверного времени и честно попал в `SLOWLOG`. В `LATENCY HISTORY` его
  **нет вообще**: там хранится максимум за секунду, а `KEYS` разделил
  секунду с более медленным севом. На valkey все три команды уложились в
  одну секунду — и `LATENCY HISTORY` показал **одну запись на три
  команды**. Вывод: `LATENCY HISTORY` — не журнал команд, его молчание
  ничего не доказывает. `DEBUG SLEEP` для демонстрации не подошёл —
  заблокирован на непривилегированных инстансах (`enable-debug-command`
  неизменяем через `CONFIG SET`).

Полные логи — `scratchout/ops-redis.log`, `scratchout/ops-valkey.log`
(Go), `scratchout/ops-java-redis.log`, `scratchout/ops-java-valkey.log`
(Java), `scratchout/ops-demo-redis.log`, `scratchout/ops-demo-valkey.log`
(backup/restore) — не в git, воспроизводятся командами выше.

## Типовые инциденты

Синтез уже полученных чисел этого Phase 1 — новых прогонов здесь нет,
только сведение вместе того, что уже измерено по стендам #3–#7.

| Инцидент | Что происходит | Числа (откуда) |
|---|---|---|
| **Мастер падает (Cluster)** | Кластер сам находит нового мастера и промоутит реплику — но клиент видит недоступность **дольше**, чем длится сам промоушен | Серверный промоушен **18.5–23.0с**, клиентское окно недоступности **41.7–48.6с** (Стенд #4) — go-redis `ClusterClient` без настроенных таймаутов продолжает биться в мёртвый узел `~42–48с`, прежде чем перечитать топологию. Один-единственный вызов `Set()` может провисеть **41.5с** |
| **Мастер падает (Sentinel)** | На этой машине (Docker Desktop/Windows) Sentinel регулярно уходит в TILT и **не делает failover вообще** | redis: 2/3 успешных промоушена, valkey: **0/3** (Стенд #4) — не «Sentinel ненадёжен», а конкретно эта виртуализованная среда со скачущими часами триггерит защитный механизм TILT. Матрицы redis и valkey гонялись **в разное время при разной загрузке хоста** — 2/3 против 0/3 не читается как «Sentinel надёжнее на Redis, чем на Valkey» |
| **`maxmemory` исчерпан, `noeviction`** | Новые записи начинают отказывать с `OOM command not allowed`, **чтения продолжают работать** | Точка отказа на 64МиБ лимите — `filler:12120` (redis, 3/3 прогона), `12196/12196/12163` (valkey) (Стенд #5). Не «сервис упал» — упали только новые записи |
| **`maxmemory` исчерпан, `allkeys-lru`/`allkeys-lfu`** | Старые данные молча вытесняются, включая ещё не устаревшие | Выживаемость `hot`-ключей — 100% под обеими политиками, но это наблюдение только там, где ключи вообще были вытесняемы (Стенд #5). Между `allkeys-lru` и `allkeys-lfu` числа `cold` (77.1–83.7% / 90.8–98.2%) **нельзя** читать как ранжирование политик: `allkeys-lru` реально различает `cold` по возрасту (перевес вытеснений `cold` ×4–5.6), а высокая выживаемость `cold` под `allkeys-lfu` — не защита, а неразличимость `cold` и `filler` по `OBJECT FREQ` (у обоих классов совпадающий счётчик) при численном перевесе `filler` в keyspace. `evicted_keys` в `INFO memory` — единственный надёжный сигнал, что вытеснение вообще происходит |
| **`dump.rdb` есть, а сервис после рестарта пустой** | Восстановление из RDB-бэкапа молча проваливается при включённом AOF | Проверено живьём (Стенд #7): пустой volume + `dump.rdb` + `--appendonly yes` → `DBSIZE=0`, ни одной ошибки в логе. Лечится временным `--appendonly no` на время загрузки |
| **`KEYS *`/тяжёлый скрипт вешает сервис** | Redis однопоточный — O(N)-команда занимает сервер целиком на время исполнения | `KEYS` над 300000 ключей — 38.6мс (redis) / 25.3мс (valkey) **серверного** времени, пойман `SLOWLOG` (Стенд #7; Docker Desktop/Windows — на проде с миллионами ключей счёт идёт на секунды). **В `LATENCY HISTORY` его НЕТ** — там хранится максимум за секунду, и `KEYS` заслонила более медленная соседняя команда: отсутствие в `LATENCY HISTORY` ничего не доказывает, для «какая команда тормозила» нужен `SLOWLOG` |
| **Пул соединений слишком мал под всплеском (Go/go-redis)** | Запросы либо ждут свободное соединение, либо получают ошибку по `PoolTimeout` | Пул в ⅒ от конкурентной нагрузки — **52.3–54.0%** запросов ловят pool timeout; пул в ⅖ — **2.8–8.2%**; пул размером с нагрузку — **0%** (Стенд #7, `redis:8.8`+`valkey/valkey:8.1`, обе ориентации). Оговорки: `PoolTimeout` туго выставлен в **2мс** (на 5мс те же пулы дают 0.4%/0.2%/0.0%), автоповтор go-redis **выключен** (`MaxRetries:-1`) — с дефолтными ретраями до приложения дошла бы малая часть отказов |
| **Тот же всплеск, Java/Lettuce+commons-pool2** | То же самое, но **числа другие** | ≈**74%** / ≈**42%** / **0%** на тех же размерах (Стенд #7). **С Go-строкой выше НЕ сравнивать**: окружения не выровнены (Go нативно на хосте, Java в WSL2 — разные сетевые пути), реализации пула разные, и у Java измерен эффект **порядка** ≈8 п.п. (JIT-прогрев — правдоподобная гипотеза, стендом не диагностирован). Совпадает только **направление** |

## Redis или…

Карта на основе всей серии (обобщение, не новый прогон) — когда Redis/Valkey
подходящий выбор, а когда нет, с указанием на стенд, который это показал.

| Задача | Redis/Valkey | Альтернатива | Почему |
|---|---|---|---|
| Кеш, сессии, rate-limiting | ✅ да | — | Родная область: низкая латентность одиночной операции и кратный выигрыш от пайплайнинга (Стенд #2 — относительные сравнения внутри стенда надёжны, абсолютные мс несут оверхед измерительной среды и не публикуются как эталон производительности), богатые структуры данных с предсказуемыми кодировками (Стенд #1) |
| Очередь задач малого/среднего масштаба | ✅ да (Streams) | Kafka, Postgres+`SKIP LOCKED` | Consumer groups с at-least-once и `XCLAIM` работают (Стенд #6), но не рассчитаны на терабайты истории — для лога событий на годы вперёд смотреть Kafka |
| Источник правды для денег/учёта | ⚠️ осторожно | PostgreSQL, любая ACID-СУБД | AOF `everysec` теряет до секунды **при падении ОС/питания**; Стенд #3 такой сбой не воспроизводил — под `kill -9` процесса потерь нет ни в одном AOF-режиме (`always`/`everysec`/`no`), разница между ними проявляется только при потере page cache ядра; `everysec`/`always` — компромисс durability/латентность, который нужно выбирать осознанно, не по умолчанию |
| Геораспределённая строгая консистентность | ❌ нет | CockroachDB, Spanner-подобные | Cluster/Sentinel failover — счёт на **десятки секунд** клиентской недоступности (Стенд #4): у Cluster — при дефолтных таймаутах (`cluster-node-timeout=15000`, ненастроенный клиент), у Sentinel — даже со сниженным `down-after-milliseconds=5000` (с дефолтными 30000 было бы дольше); не про синхронную мультирегиональность |
| Datasets, не помещающиеся в RAM | ❌ нет | ClickHouse, Postgres+индексы | Redis/Valkey — in-memory по природе; `maxmemory`+eviction — это управление ограниченным горячим набором (Стенд #5), не подмена дисковой БД |
| Аналитика/агрегации по большим объёмам | ❌ нет | ClickHouse, Postgres | Нет колоночного хранения и оптимизатора запросов; `KEYS`/`SCAN` по большому keyspace — однопоточная блокирующая операция (Стенд #7) |
| Пул соединений под сильно всплесковой нагрузкой | ⚠️ считать заранее | — | Маленький пул относительно пиковой конкурентности даёт либо очередь, либо отказы по `PoolTimeout` — направление предсказуемо, конкретные числа нужно мерить на своей нагрузке (Стенд #7) |
| Быстрый прототип с гибкой моделью данных | ✅ да | — | Пять структур данных "из коробки" без ORM и миграций (Стенд #1); плата — те же ограничения durability/масштаба, что выше |
