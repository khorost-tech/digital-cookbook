## Стенд #1: структуры данных

Источник: `structures/main.go`, три сценария (`-scenario listpack-threshold |
intset-threshold | memory-per-structure`), прогнаны против `redis-master`
живой топологии `compose/base.yml` — сначала на `redis:8.8`, затем (после
`down -v` и повторного `up -d` с `REDIS_IMAGE=valkey/valkey:8.1`) на Valkey.
Сырые логи: `scratchout/structures-redis.log`,
`scratchout/structures-valkey.log` (не в git, воспроизводимы).

### Конфигурация по умолчанию (`CONFIG GET`, идентична на обоих образах)

| Параметр | Значение |
|---|---|
| `hash-max-listpack-entries` | 512 |
| `hash-max-listpack-value` | 64 |
| `list-max-listpack-size` | -2 (лимит по байтам на узел quicklist, 8 КиБ) |
| `zset-max-listpack-entries` | 128 |
| `zset-max-listpack-value` | 64 |
| `set-max-intset-entries` | 512 |
| `set-max-listpack-entries` | 128 |
| `set-max-listpack-value` | 64 |

### Точки перехода кодировок (`listpack-threshold`, `intset-threshold`)

Идентичны на `redis:8.8` и `valkey/valkey:8.1` — совпадение подтверждено
построчным сравнением обоих логов.

| Сценарий | Переход | Наблюдаемая точка |
|---|---|---|
| hash по числу полей | `listpack` → `hashtable` | `count=513` (порог `hash-max-listpack-entries=512`, переход на `512+1`) |
| hash по длине значения одного поля | `listpack` → `hashtable` | `len=65` (порог `hash-max-listpack-value=64`) |
| list по числу элементов (короткие `eN`, ~4-6 байт) | `listpack` → `quicklist` | `count=1328` (байтовый лимит `-2`/8 КиБ, не лимит по числу элементов — см. ниже) |
| zset по числу элементов | `listpack` → `skiplist` | `count=129` (порог `zset-max-listpack-entries=128`) |
| zset по длине member | `listpack` → `skiplist` | `len=65` (порог `zset-max-listpack-value=64`) |
| set из целых чисел по числу элементов | `intset` → `hashtable` | `count=513` (порог `set-max-intset-entries=512`; напрямую в `hashtable`, минуя `listpack`, т.к. 513 > `set-max-listpack-entries=128`) |
| set: 5 целых + 1 нечисловой элемент | `intset` → `listpack` | сразу (5 < `set-max-listpack-entries=128`) |
| set: 138 целых + 1 нечисловой элемент | `intset` → `hashtable` | сразу (138 > `set-max-listpack-entries=128`) |

**List — отдельное замечание.** `list-max-listpack-size=-2` — это не число
элементов, а лимит в байтах на узел quicklist (8 КиБ). Прямой бинарный поиск
через `redis-cli` (короткие элементы `e1`..`eN`) дал:

| N элементов | `OBJECT ENCODING` | `MEMORY USAGE` |
|---|---|---|
| 1250 | `listpack` | 7690 |
| 1300 | `listpack` | 8040 |
| 1326–1327 | `listpack` | — |
| 1328 | `quicklist` | — |
| 1330 | `quicklist` | 8385 |
| 1350 | `quicklist` | 8525 |
| 2000 | `quicklist` | — |

Переход происходит между 1327 и 1328 короткими элементами — то есть примерно
на границе суммарного размера ~8 КиБ, что согласуется с
`list-max-listpack-size=-2`. Для более крупных элементов переход наступит при
меньшем числе элементов — порог всегда байтовый, не количественный.

### `MEMORY USAGE` по структурам (`memory-per-structure`, байты)

| Структура | N | Redis 8.8 | Valkey 8.1 |
|---|---|---:|---:|
| string (значение из N байт) | 10 | 48 | 48 |
| string | 100 | 152 | 152 |
| string | 1000 | 1064 | 1064 |
| hash (N полей) | 10 | 119 | 128 |
| hash | 100 | 1019 | 1056 |
| hash | 1000 | 46060 | 42024 |
| list (N элементов) | 10 | 79 | 80 |
| list | 100 | 529 | 544 |
| list | 1000 | 5929 | 6176 |
| set (N целых) | 10 | 60 | 64 |
| set | 100 | 240 | 256 |
| set | 1000 | 37170 | 33896 |
| zset (N элементов) | 10 | 99 | 112 |
| zset | 100 | 729 | 800 |
| zset | 1000 | 78680 | 69336 |
| stream (N записей) | 10 | 398 | 4296 |
| stream | 100 | 1298 | 4296 |
| stream | 1000 | 12113 | 15860 |

**Честно зафиксированное расхождение (stream).** У Valkey `MEMORY USAGE` для
стрима на N=10 и N=100 дало одинаковое значение — `4296` байт: похоже на
предвыделение под структуру radix-tree/consumer-group метаданные, которое не
меняется, пока стрим не вырастет за пределы одного блока. У Redis рост более
плавный: `398` → `1298` → `12113`. При N=1000 оба образа растут (Redis
`12113`, Valkey `15860`), но абсолютные числа не совпадают. Остальные
структуры (string/hash/list/set/zset) дают близкие, но не идентичные числа —
ожидаемо: разные билды/аллокаторы, точки перехода кодировок при этом
идентичны, так как это вопрос движка структур данных, а не байт-в-байт
раскладки памяти.

**Почему этому сравнению образов на n=1 можно доверять (в отличие от
большинства других в серии).** Правило «на 1–4 прогонах redis и valkey не
сравнивать» (Стенд #5, Стенд #7) — про **сэмплирующие**/шумные измерения:
приближённое вытеснение, конкурентные failover-тайминги, латентность под
конкуренцией. `MEMORY USAGE` — не такое: это детерминированная функция от
состояния структуры данных и конкретной сборки, без выборки и без
зависимости от нагрузки хоста, то есть повторный прогон на той же сборке дал
бы то же число. Константа `4296` байт, совпавшая у Valkey и на N=10, и на
N=100 записей, — структурная сигнатура (похоже на фиксированное
предвыделение под radix-tree/consumer-group метаданные), а не два случайно
совпавших шумных замера. И разрыв здесь на **порядок** (398 против 4296), а
не «пара процентов», которые случайный разброс мог бы объяснить. Это не
повод пропускать повторные прогоны в будущих задачах, но именно для этого
конкретного числа природа замера снимает обычную осторожность.

### Чего стенд НЕ измерял

- **Стримы на N бóльше 1000.** Если предвыделение `4296` байт у Valkey —
  правда про фиксированный блок radix-tree, оно должно кончиться при
  дальнейшем росте (стрим станет больше блока и Redis/Valkey сравняются или
  разойдутся иначе) — это не проверено.
- **Причину расхождения по стримам инструментально.** «Похоже на
  предвыделение под radix-tree узел» — правдоподобная гипотеза по форме
  чисел, не подтверждённая чтением исходников/профилировщиком.
- **Поведение под конкурентной записью или изменением ключей.** Все
  сценарии — один клиент, ключи пишутся один раз и не меняются; это стенд
  про кодировки и память в состоянии покоя, не про throughput (для этого —
  Стенды #2 и #7).
- **Точки перехода для элементов другой формы/длины.** Бинарный поиск
  порога `list` сделан только на коротких элементах `eN`; для более крупных
  элементов порог наступит раньше (см. оговорку выше), но конкретные числа
  не измерены.

Реальные команды воспроизведения — в `README.md`, раздел «Стенд #1».

## Стенд #2: event loop, пайплайнинг, threaded I/O

Источник: `eventloop/main.go`, три сценария (`-scenario no-pipeline |
pipeline | threaded-io`), прогнаны против `redis-master` — `no-pipeline` и
`pipeline` живой топологии `compose/base.yml`, `threaded-io` — и на той же
топологии (`io-threads=1`, дефолт), и на одиночном `redis-master`,
поднятом через `docker compose run` с переопределённой командой
(`--io-threads 4 --io-threads-do-reads yes`), без правки `base.yml`. Сырые
логи: `scratchout/eventloop-redis.log`, `scratchout/eventloop-valkey.log`
(не в git, воспроизводимы командами из `README.md`).

**Методология.** `no-pipeline`/`pipeline`: N=10000 команд `SET` (ключ+значение
`"v"`), один клиент, без конкуренции; `no-pipeline` — по одной команде за
раз (латентность = время самой команды), `pipeline` — батчами по 100 через
`rdb.Pipeline()` (латентность = время батча / 100, т.е. средняя латентность
на слот внутри батча, не latency отдельной сетевой операции). `threaded-io`
— то же самое (`no-pipeline` и `pipeline`, N=10000, батч=100), но
поделенное на 8 параллельных горутин (`-concurrency 8`) на одном клиенте с
пулом соединений ≥16. Throughput везде = N / общее время стенки. Каждый
`threaded-io`-прогон повторён дважды на одной конфигурации — проверка
разброса между запусками, не только между образами/конфигурациями.

**Оговорка по абсолютным числам.** Стенд запущен с Windows-хоста через
Docker Desktop — путь клиент→контейнер идёт через виртуализованный сетевой
стек, не голый TCP-loopback на Linux. `p50≈500 мкс` на одиночный `SET` без
пайплайна — это оверхед платформы измерения (выше типичных цифр bare-metal
Linux), не свойство Redis/Valkey. Относительные сравнения внутри одного и
того же стенда (пайплайн vs без, Redis vs Valkey, io-threads=1 vs 4)
валидны.

**Не раскрыто: прогрев соединения.** Ни `no-pipeline`, ни `pipeline`, ни
`threaded-io` не делают "холостых" операций перед стартом замера — первая же
команда уже пишется в измеряемое окно, включая стоимость первого
TCP-рукопожатия и первого прохода клиентского кода. При N=10000 это
пренебрежимо (одна операция на фоне десяти тысяч заведомо не сдвигает
p50/throughput), но явно нигде не оговорено — стоило бы одной строкой.

**Дрейф базового throughput между сессиями (не отмечен нигде явно).**
Одноклиентный `no-pipeline` здесь даёт **2520.3 ops/s** (p50≈499.6µs,
`eventloop-redis.log`). Стенд #3 в режиме `aof-everysec` меряет номинально
то же самое (`SET` без пайплайна, один клиент, тот же хост и та же
топология) и получает **≈3053 ops/s** (`persistence-redis.log:140`,
≈316µs) — на 20–25% быстрее. Оба числа корректны в рамках своих собственных
оговорок (Docker Desktop/Windows), но ни один раздел не фиксирует, что
базовая скорость одиночной операции **сдвинулась между сессиями
измерения** — тот же класс между-сессионного дрейфа, который Стенд #6
отдельно документирует для своих чисел (см. «Оговорка про абсолютные
числа» там); здесь он тоже есть, просто не назван.

### `no-pipeline` vs `pipeline` (без конкуренции, один клиент, N=10000)

| Метрика | Redis 8.8 no-pipeline | Redis 8.8 pipeline (batch=100) | Ускорение | Valkey 8.1 no-pipeline | Valkey 8.1 pipeline (batch=100) | Ускорение |
|---|---:|---:|---:|---:|---:|---:|
| elapsed | 3.968s | 64.933ms | ×61.1 (по времени) | 4.034s | 57.124ms | ×70.6 |
| p50 | 499.6µs | 5.013µs | ×99.7 | 499.5µs | 5.622µs | ×88.8 |
| p95 | 1.021ms | 10.464µs | ×97.6 | 1.0271ms | 10.661µs | ×96.3 |
| p99 | 1.1215ms | 15.282µs | ×73.4 | 1.1205ms | 11.177µs | ×100.3 |
| throughput | 2520.3 ops/s | 154005.1 ops/s | ×61.1 | 2479.0 ops/s | 175057.5 ops/s | ×70.6 |

Пайплайнинг батчами по 100 даёт **на два порядка** выше throughput на обоих
образах — ожидаемо: без пайплайна каждая команда платит полный
round-trip, с пайплайном round-trip один на 100 команд. Redis и Valkey
здесь практически неотличимы: p50/p95 без пайплайна совпадают до десятых
микросекунды, разница в throughput с пайплайном (154005 vs 175057, Valkey
выше на ~14%) — в пределах шума одного прогона (повтора для этой пары
сценариев не делалось, только для `threaded-io`).

### `threaded-io`: io-threads=1 vs io-threads=4, concurrency=8, N=10000 (два повтора на конфигурацию)

**Redis 8.8**

| Конфигурация | Прогон | no-pipeline throughput | pipeline throughput (batch=100) |
|---|---|---:|---:|
| io-threads=1 (дефолт) | #1 | 12910.5 ops/s | 500999.5 ops/s |
| io-threads=1 (дефолт) | #2 | 12149.9 ops/s | 472806.5 ops/s |
| io-threads=4, do-reads yes | #1 | 13119.5 ops/s | 605759.6 ops/s |
| io-threads=4, do-reads yes | #2 | 10856.6 ops/s | 367647.1 ops/s |

**Valkey 8.1**

| Конфигурация | Прогон | no-pipeline throughput | pipeline throughput (batch=100) |
|---|---|---:|---:|
| io-threads=1 (дефолт) | #1 | 13227.9 ops/s | 387718.6 ops/s |
| io-threads=1 (дефолт) | #2 | 13031.5 ops/s | 357490.1 ops/s |

**Честный вывод.** На Redis 8.8 разброс между двумя повторами **на одной и
той же** конфигурации (`io-threads=4`: 605759.6 vs 367647.1 ops/s —
разброс ~40%) больше, чем разница средних между конфигурациями
(io-threads=1 avg pipeline ≈486903, io-threads=4 avg pipeline ≈486703 —
практически идентично). При этой нагрузке (localhost, N=10000,
concurrency=8, маленькие значения) `io-threads` не даёт измеримого эффекта
на Redis — шум перекрывает сигнал.

На Valkey 8.1 картина направленно другая: **оба** повтора с
`io-threads=4` дали более высокий throughput, чем **оба** повтора с
`io-threads=1`, и на no-pipeline (13979.9 avg vs 13129.7 avg, +6.5%), и
особенно на pipeline (605421.9 avg vs 372604.4 avg, +62%). Направление
устойчиво в обоих повторах, но при N=2 повторах на конфигурацию это
наблюдение, а не статистически надёжный вывод — не публиковать как «Valkey
X% быстрее с threaded I/O» без дополнительных повторов вне рамок этой
задачи.

**Побочная находка (`io-threads-do-reads`).** У обоих образов `CONFIG GET
"io-threads*"` возвращает только `io-threads` — параметра
`io-threads-do-reads` в выдаче нет (`<нет такого параметра>` в логе). Тем не
менее передача `--io-threads-do-reads yes` аргументом командной строки при
старте `redis-server` не вызывает ошибку и не мешает старту — сервер её
молча принимает. Похоже, что в этих версиях (Redis 8.8 / Valkey 8.1) чтения
потоками ввода-вывода включены неявно, когда `io-threads > 1`, и отдельный
переключатель `io-threads-do-reads` стал устаревшим — не найден
задокументированным. Ещё одна честно зафиксированная асимметрия: сразу
после старта с `--io-threads 4` `INFO server` показывает
`io_threads_active:1` на Redis, но `io_threads_active:0` на Valkey (до
проверки под нагрузкой) — расхождение не исследовано глубже в рамках этой
задачи, зафиксировано как наблюдение.

## Стенд #3: персистентность (RDB/AOF под `kill -9`)

Источник: `persistence/main.go`, два сценария (`-scenario durability-loss |
count-recovered`), оркестрация — `ops/persistence-kill-matrix.sh` (5 режимов
× оба образа, полностью автоматизировано). Сырые логи:
`scratchout/persistence-redis.log`, `scratchout/persistence-valkey.log` (не в
git, воспроизводимы командой из `README.md`). Каждая ячейка матрицы прогнана
**дважды** (два независимых полных прохода на каждый образ) — проверка
разброса, не единичный прогон.

**Методология.** `durability-loss`: `FLUSHALL`, затем `SET dur:<i> i` без
пайплайна, один клиент, i = 0..4999 (N=5000 запланировано). На i=2500
(середина) — сразу после того, как `SET` подтвердил запись (`OK`) —
`docker kill -s SIGKILL <container>` (настоящий SIGKILL, не `docker stop`,
который посылает SIGTERM и даёт Redis сохранить всё перед выходом). Итог:
**2501 подтверждённая запись (индексы 0..2500)** в каждом прогоне, кил
подтверждён (`docker inspect` → `Status=exited`, `ExitCode=137` = 128+9 —
однозначный признак настоящего SIGKILL, не какого-то другого завершения).
Контейнер поднимается заново на том же volume (`docker compose up -d
redis-master` с теми же env — конфигурация не меняется, значит контейнер не
пересоздаётся, а стартует тот же самый, с тем же диском). `count-recovered`
ждёт готовности (`PING`), затем `DBSIZE` (в БД кроме `dur:*` ничего нет —
`FLUSHALL` перед стартом) + проверка `INFO persistence` + присутствие 10
последних перед килом ключей (суффиксная потеря vs дыры).

Режим персистентности задаётся через env `compose/base.yml`
(`REDIS_APPENDONLY`/`REDIS_APPENDFSYNC`/`REDIS_SAVE_SECONDS`/
`REDIS_SAVE_CHANGES`):

| Режим | `--save` | `--appendonly` | `--appendfsync` |
|---|---|---|---|
| `rdb-only` | `60 1` | `no` | — (AOF выключен) |
| `aof-always` | `3600 1000000` (не успевает сработать) | `yes` | `always` |
| `aof-everysec` | `3600 1000000` | `yes` | `everysec` |
| `aof-no` | `3600 1000000` | `yes` | `no` |
| `hybrid` | `60 1` (дефолт `base.yml`) | `yes` | `everysec` |

### Матрица потерь под `kill -9` **процесса** (не при падении ОС/потере питания), из 2501 подтверждённой записи (2 прогона на ячейку)

| Режим | Redis 8.8, прогон #1 | Redis 8.8, прогон #2 | Valkey 8.1, прогон #1 | Valkey 8.1, прогон #2 |
|---|---:|---:|---:|---:|
| `rdb-only` | **2501†** (0 восстановлено) | **2501†** | **2501†** | **2501†** |
| `aof-always` | 0* | 0* | 0* | 0* |
| `aof-everysec` | 0* | 0* | 0* | 0* |
| `aof-no` | 0* | 0* | 0* | 0* |
| `hybrid` | 0* | 0* | 0* | 0* |

**`*` — ноль здесь это свойство краха ПРОЦЕССА, а не доказательство
надёжности режима.** `write()` уже отдал данные в page cache ядра, а ядро
при `kill -9` живо и спокойно допишет их на диск. При потере питания или
падении ОС `no` и `everysec` теряют данные (до 1с записей у `everysec`,
сколько накопилось в page cache — у `no`). **Этот стенд такой сбой не
воспроизводит.** Не цитировать как «`appendfsync no` ничего не теряет».

**`†` — это цифра о соотношении окна теста и интервала снапшота, а не
свойство RDB.** `save 60 1` требует 60с после первого изменения, весь тест
укладывается в ~0.8с — снапшот физически не успевает сработать ни разу. При
киле через 61с потеря была бы принципиально другой. Не цитировать как «RDB
теряет 100%».

Полностью воспроизводимо: 4 независимых полных прохода (2×redis, 2×valkey),
ни один режим не дал разброса между прогонами. Хвостовая проверка (10
последних ключей перед килом) в каждом прогоне с потерей 0 показала
`10/10 присутствуют`; в `rdb-only` — `0/10` (в БД после рестарта вообще нет
ключей `dur:*`, `DBSIZE`=0).

**Чего этот стенд принципиально НЕ показывает: рваный/усечённый AOF.** По
конструкции сценария килл прилетает строго после подтверждённого `SET`, и в
этот момент ни одна команда не находится «в полёте» — поэтому хвост AOF
всегда остаётся целым, а `tail check` гарантированно чист (`10/10`) в любом
режиме. Это следствие методики, а не свойство AOF: **читателю нельзя
выводить отсюда «крах никогда не рвёт AOF»**. Усечённый хвост AOF —
реальное явление (на то есть `aof-load-truncated`), для его воспроизведения
нужен килл посреди незавершённой записи/`fsync`, чего этот стенд намеренно
не делает.

### Скорость записи до килла (SET без пайплайна, один клиент, до i=2500)

| Режим | Redis 8.8 | Valkey 8.1 |
|---|---:|---:|
| `rdb-only` | 760–791ms (≈3160–3290 ops/s) | 736–754ms (≈3320–3400 ops/s) |
| `aof-always` | **9.52–9.53s (≈262–263 ops/s)** | **9.38–9.61s (≈260–267 ops/s)** |
| `aof-everysec` | 799–831ms (≈3010–3130 ops/s) | 829–853ms (≈2930–3020 ops/s) |
| `aof-no` | 840–895ms (≈2790–2980 ops/s) | 717–786ms (≈3180–3490 ops/s) |
| `hybrid` | 821–896ms (≈2790–3050 ops/s) | 799–830ms (≈3010–3130 ops/s) |

**Честный и важный вывод, требующий пояснения: почему `everysec` и `no` тоже
дали 0 потерь.** Это не ошибка методологии и не натянутый результат — это
задокументированное поведение Unix-подобных ОС и самого Redis. `kill -9`
убивает **процесс**, а не операционную систему. `write()` записи в AOF-файл
отдаёт данные ядру (в page cache) синхронно, при выполнении самой команды —
**независимо от политики `appendfsync`**: `fsync` управляет только тем,
когда page cache физически сбрасывается на диск, а не тем, когда write()
данные покидают процесс. Page cache — это память ядра, а не память
процесса Redis: `kill -9` уничтожает процесс, но не трогает ядро, поэтому
уже сделанные `write()`-вызовы переживают убийство процесса и видны сразу
после рестарта того же контейнера на том же диске. Разница между `always`/
`everysec`/`no` проявилась бы только при потере самого page cache — то есть
при **падении ОС или отключении питания**, не при убийстве процесса. Этот
стенд намеренно тестирует durability против падения процесса (`kill -9`,
как в задаче), а НЕ durability против падения ОС/питания — для последнего
потребовался бы другой метод (реальный краш VM/хоста), выходящий за рамки
этой задачи. **Не экстраполировать «`appendfsync no` теряет 0» на сценарий
отключения питания** — там всё иначе, и именно там разница между режимами
проявится.

Единственный режим, реально потерявший всё, — `rdb-only`: `save 60 1`
требует 60 секунд после первого изменения, а весь тест укладывается в
~0.8с — снапшот с данными физически не успевает сработать ни разу. Это тоже
честный и ожидаемый результат: RDB как единственный механизм
персистентности не защищает от сбоя, произошедшего раньше следующего
запланированного снапшота — и это ровно то, ради чего стенд задуман.

**Что реально лежит на диске (измерено, а не выведено теоретически).**
`count-recovered` печатает фактический листинг `/data` в контейнере. В
режиме `rdb-only` после рестарта там:

```
-rw------- 1 redis redis   88 Jul 16 07:54 dump.rdb
--- appendonlydir:
(нет appendonlydir)
```

То есть `dump.rdb` **существует** и весит 88 байт (пустой RDB: заголовок +
метаданные, без единого ключа), `appendonlydir/` отсутствует — AOF выключен.
Отдельной проверкой (`ls /data` до и сразу после `FLUSHALL` на свежем
контейнере) установлено, что этот пустой `dump.rdb` создаёт **сам
`FLUSHALL`** в начале сценария, а не сработавшее правило `save 60 1` и не
рестарт: Redis сохраняет пустой RDB при `FLUSHALL`, если сконфигурирована
хотя бы одна save-точка (файл появляется и при `save 3600 1000000`, которое
за время теста заведомо сработать не может). Так что «на диске пустой
`dump.rdb`» — правда, но по причине, не имеющей отношения к durability
самого RDB: это артефакт подготовки стенда. Ключей `dur:*` в нём нет ни
одного, `DBSIZE`=0 после рестарта.

**Побочная находка (`appendfsync always` тяжелее «by design», не только по
семантике).** Запись до килла заняла **≈9.5с при `always`** против
**≈0.7–0.9с у всех остальных режимов** — то есть `always` **на порядок**
медленнее без пайплайна (fsync на каждую команду синхронно перед `OK`), при
том что durability-выигрыш `always` над `everysec`/`no` при `kill -9` в
данном методе измерения не наблюдается (см. вывод выше) — весь выигрыш
`always` проявился бы только при падении ОС/питания. Это ключевая иллюстрация
компромисса «латентность записи vs защита от последнего класса сбоев (не
процесс, а ОС/питание)».

**Методологическая оговорка (Docker Desktop на Windows).** Как и в Стенде
#2, абсолютные числа скорости записи (≈2800–3500 ops/s без пайплайна,
одиночный клиент) несут оверхед виртуализованного сетевого стека Docker
Desktop — не bare-metal Linux цифры. Относительные сравнения (always
медленнее на порядок; RDB-only теряет всё; AOF-режимы при `kill -9` не
теряют ничего) остаются в силе. Файловая система тоже виртуализована
(WSL2/Hyper-V backend), поэтому семантика fsync теоретически могла бы
отличаться от bare-metal — но наблюдаемое поведение (write() переживает
`kill -9` процесса вне зависимости от fsync) полностью согласуется с
задокументированной моделью Unix page cache, так что в данном случае
виртуализация не выглядит источником искажения; тем не менее это
предположение, а не проверенный факт (проверка потребовала бы реального
падения ОС/хоста, вне рамок задачи).

Реальные команды воспроизведения — в `README.md`, раздел «Стенд #3».

## Стенд #4: репликация, Cluster, Sentinel

Источник: `topology/main.go` (4 сценария) + `ops/topology-demo.sh`
(оркестрация). Сырые логи: `scratchout/topology-redis.log`,
`scratchout/topology-valkey.log` (не в git, воспроизводимы командами из
`README.md`). Cluster-failover и Sentinel-failover прогнаны по **3 повтора**
на каждый образ — failover-тайминги по своей природе разбросаны, и ниже
приводится **спред по повторам, а не одно удобное число**.

**Главная оговорка ко всем таймингам этого стенда.** Времена failover — это
**следствие конфигурации**, а не свойство Redis/Valkey:

| Параметр | Значение здесь | Что определяет |
|---|---|---|
| `cluster-node-timeout` | `15000` (дефолт) | когда Cluster признаёт мастер упавшим и начинает выборы |
| Sentinel `down-after-milliseconds` | `5000` (снижено с дефолтных 30000) | когда Sentinel признаёт мастер `s_down` |
| Sentinel `failover-timeout` | `10000` (снижено с дефолтных 180000) | ограничения на процесс failover |
| Sentinel `quorum` | `2` из 3 | сколько Sentinel должны согласиться |
| **Клиент go-redis: `redis.ClusterOptions{Addrs: addrs}`** | **всё по умолчанию** — `DialTimeout`/`ReadTimeout`/`MaxRetries`/`MaxRedirects` НЕ настраивались (`topology/main.go`) | **как долго клиент висит на мёртвом узле, прежде чем перечитает топологию** |
| **Сетевой режим отказа: docker bridge** | контейнер удалён из bridge → `connect: no route to host` | как быстро сокет узнаёт о смерти узла |

С дефолтными 30000/180000 Sentinel-числа были бы принципиально другими. **Не
цитировать как «Sentinel переключается за 7 секунд» без указания
`down-after-milliseconds=5000`.**

**Две последние строки таблицы — не формальность, а половина заголовочной
цифры этого стенда.** Клиентское окно 42–49с — это свойство **ненастроенного
клиента на виртуализованном bridge**, а не свойство `ClusterClient` как
такового: клиент создаётся как `redis.NewClusterClient(&redis.ClusterOptions{
Addrs: addrs})`, без единого таймаута, а docker-bridge при удалении
контейнера даёт `no route to host` — то есть режим отказа, не совпадающий ни
с мгновенным `ECONNREFUSED` мёртвого процесса на живом хосте, ни с молчаливым
таймаутом мёртвого хоста. С выставленными `DialTimeout`/`ReadTimeout`/
`MaxRetries` окно было бы другим. **Не цитировать «go-redis восстанавливается
45 секунд» как свойство библиотеки.**

**Методологическая оговорка (Docker Desktop на Windows) — здесь она сильнее,
чем в Стендах #2/#3.** Стенд гоняется на Windows-хосте через Docker Desktop
(WSL2), сеть и таймеры виртуализованы. Для этого стенда это не фон, а
действующее лицо: (1) партиция делается через `docker network disconnect`, а
не реальным сетевым разрывом — это НЕ эквивалент потери пакетов на реальной
сети, интерфейс выдёргивается целиком; (2) Sentinel на этом хосте регулярно
уходит в TILT (см. ниже) — на bare-metal Linux этого, скорее всего, не было
бы. Всё, что ниже — правда про **эту** среду.

### Резюме: что получилось, а что нет

| Сценарий | redis:8.8 | valkey/valkey:8.1 |
|---|---|---|
| Resharding под нагрузкой | ✅ 0 потерь | ✅ 0 потерь (1 прогон из 2 упал, см. ниже) |
| Cluster failover | ✅ 3/3 промоушена | ✅ 3/3 промоушена |
| Sentinel failover | ⚠️ **2/3**† (1 прогон — TILT, промоушена нет) | ❌ **0/3**† (все — TILT) |
| Split-brain | ❌ **не воспроизвёлся**† (TILT не дал промоушена) | ✅ **воспроизвёлся**†: 2 мастера, из 80 подтверждённых записей на новом мастере видны 5 |

**`†` — это НЕ сравнение движков.** TILT — свойство среды (загрузка хоста,
стабильность таймеров), а матрицы redis и valkey гонялись **в разное время
при разной загрузке хоста** (valkeevская — позже, на более нагруженном
хосте). «2/3 против 0/3» и «не воспроизвёлся против воспроизвёлся» не
означают «Sentinel надёжнее на Redis» или «split-brain специфичен для
Valkey» — на Redis split-brain не возник ровно потому, что TILT сорвал
failover первым, то есть это два симптома одной и той же причины
(перегруженный виртуализованный хост), а не независимые находки про два
движка. Подробности — в разделах «Sentinel failover» и «Split-brain» ниже.

### Resharding под нагрузкой (1 прогон на образ, без повторов)

`redis-cli --cluster reshard` переносит **2000 слотов**, одновременно клиент
пишет **100000 ключей** `resh:<i>` через `redis.ClusterClient`.

| Метрика | Redis 8.8 | Valkey 8.1 | Сравнимо между образами? |
|---|---:|---:|---|
| Время `--cluster reshard` (2000 слотов) | **27274 мс** | **4973 мс** | ❌ **нет** — спутано нагрузкой, см. ниже |
| Запись 100000 ключей | 40.811 с (2450.3 ops/s) | 22.109 с (4523.1 ops/s) | ❌ **нет** — спутано тем же, см. ниже |
| `MOVED`-редиректов (реально посчитано) | **46** | **14** | ❌ **нет** — следствие разной длины окна reshard |
| `ASK`-редиректов | 0 | 0 | — |
| Ошибок записи, дошедших до клиента | 0 | 0 | ✅ да |
| Верификация `GET` каждого из 100000 | `missing=0 wrong=0` | `missing=0 wrong=0` | ✅ да |

**Три верхние строки НЕЛЬЗЯ цитировать как сравнение образов** — ни «Valkey
решардит в 5 раз быстрее», ни «Valkey пишет в 1.8 раза быстрее». Причина у
всех трёх одна: reshard и запись идут **одновременно и мешают друг другу**.
Чем дольше длится reshard, тем больше данных успевает налиться в переезжающие
слоты (дороже каждый следующий слот) и тем дольше клиент платит за миграцию
своими записями. Это **одна связка**, а не три независимых измерения: у Redis
reshard (27.3с) перекрыл около двух третей окна записи (40.8с), у Valkey
(5.0с) — примерно четверть (22.1с). Отсюда и `MOVED` 46 vs 14. Что здесь
причина, а что следствие, этот стенд развязать не может.

Для честного сравнения и скорости resharding, и throughput записи нужен
отдельный стенд: фиксированный датасет, reshard без конкурентной записи и
запись без конкурентного reshard — вне рамок этой задачи.

**Что цитировать можно:** resharding под нагрузкой **не теряет записи** на
обоих образах. 100000 из 100000 ключей прочитаны обратно с верным значением.
Клиент видит реальные `MOVED` и переподключается сам — приложение ничего не
замечает.

**Побочная находка: у Valkey resharding под нагрузкой падал.** В первом
прогоне матрицы `redis-cli --cluster reshard` на `valkey/valkey:8.1`
свалился на ~196-м слоте из 2000 с ошибкой:

```
clusterManagerMoveSlot failed: NOREPLICAS Not enough good replicas to write.
```

При этом `min-replicas-to-write=0` (проверено `CONFIG GET`) — то есть
классический триггер этой ошибки выключен, и почему она возникла, **я не
установил**. Воспроизвести по требованию не удалось: повторные resharding на
том же кластере — и без нагрузки (100 слотов), и под нагрузкой (300 слотов) —
прошли успешно, и полный повторный прогон матрицы тоже прошёл (4973 мс, код
возврата 0). Фиксирую как **наблюдавшийся, но не воспроизводимый по требованию
сбой Valkey 8.1**, механизм неизвестен; в единственном redis-прогоне (n=1)
такого не наблюдалось — это отсутствие свидетельства, а не свидетельство
отсутствия. Это честная «открытая точка», а не вывод.

### Cluster failover: убийство мастера (3 повтора на образ)

`docker kill -s SIGKILL` мастера во время тугой записи. Килл подтверждён во
**всех 6 прогонах**: `docker inspect` → `Status=exited`, `ExitCode=137`
(128+9). Промоушен подтверждён на **другом живом мастере** (`redis-c2`) через
`cluster nodes` — строка реплики меняет роль `slave` → `master`.

**Серверный промоушен** (от `docker kill` до появления `master` в
`cluster nodes` на свидетеле):

| Прогон | Redis 8.8 | Valkey 8.1 |
|---|---:|---:|
| #1 | 18496 мс | 20880 мс |
| #2 | 22933 мс | 18855 мс |
| #3 | 22962 мс | 20710 мс |
| **спред** | **18.5–23.0 с** | **18.9–20.9 с** |

**Клиентское окно недоступности** (go-redis `ClusterClient`, от первой
деградации до восстановления записи):

| Прогон | Redis 8.8 | Valkey 8.1 |
|---|---:|---:|
| #1 | 41.656 с | 45.597 с |
| #2 | 46.612 с | 44.760 с |
| #3 | 48.582 с | 46.677 с |
| **спред** | **41.7–48.6 с** | **44.8–46.7 с** |

**Почему в `scratchout/topology-redis.log` cluster-failover-прогонов ЧЕТЫРЕ, а
в таблице три.** Четвёртый — верификационный: после правки `writeLoop`
(отчёт о самом длинном эпизоде деградации вместо последнего) сделан один
контрольный прогон на `redis:8.8`, чтобы убедиться, что замер не поехал. Его
числа — промоушен **19852 мс**, окно **45.603 с**, `failed=1 stalled=0
эпизодов_деградации=1` — попадают **внутрь** обоих спредов выше, то есть
правка ничего не сдвинула. В таблицу он не внесён сознательно: это проверка
инструмента, а не четвёртый повтор матрицы, и подмешивать его к трём
прогонам, снятым одним заходом при одинаковых условиях, было бы
некорректно.

**Главный вывод стенда, и он не про Redis, а про клиента.** Клиентское окно
(**~42–49 с**) в **2+ раза длиннее** серверного промоушена (**~18–23 с**).
Кластер уже давно выбрал нового мастера и раздаёт корректную топологию, а
клиент всё ещё недоступен. Причина видна в логах go-redis: пул соединений
продолжает долбиться в IP мёртвого узла, и один вызов `Set()` висит
**41.5–48.4 с** (`maxLatency` в логе), прежде чем вернуть ошибку и заставить
клиент перечитать топологию:

```
redis: connection pool: failed to dial after 5 attempts: dial tcp 172.19.0.6:6379: connect: no route to host
cluster-failover-writes: итог — attempts=279597 success=279596 failed=1 stalled=0 maxLatency=41.503994733s
```

Обратите внимание: `failed=1`. **Одна-единственная ошибка за весь прогон** —
и она же 41.5 секунды простоя. Отсюда практический вывод: мониторинг,
считающий **долю ошибочных запросов**, такой инцидент не покажет — 1 ошибка
из 279597 это 0.0004%, любой разумный порог по error rate останется зелёным,
пока клиент 45 секунд не может писать. Смотреть надо на **латентность
хвоста**, а не на процент ошибок.

**Чего здесь НЕ происходило (важно, легко приписать лишнее).** В
Cluster-сценарии длинный вызов **всё-таки возвращал ошибку** — во **всех 6
прогонах** `failed=1 stalled=0`. То есть детектор «только по ошибкам» этот
инцидент бы **заметил** (одну ошибку он бы увидел); не заметил бы его
мониторинг по **доле** ошибок. Это разные вещи, и путать их нельзя.

Случай, когда клиент **вообще не отдаёт ошибку** и возвращает `OK` после
многосекундной блокировки, на этом стенде поймался **в Sentinel-сценарии**, а
не в Cluster: `failed=0 stalled=1 maxLatency=10.641790839s` (2 прогона redis
из 3). Вот там детектор по ошибкам не увидел бы **ничего**, и ровно ради
таких случаев в `writeLoop` сделан двойной детектор (ошибка ИЛИ аномально
долгий вызов). **Не цитировать «go-redis возвращает OK после 45-секундного
Cluster-failover» — логи этого стенда такое опровергают.**

Redis и Valkey тут **неразличимы**: спреды перекрываются (41.7–48.6 vs
44.8–46.7), разница внутри разброса между повторами одного образа.

### Sentinel failover: убийство мастера (3 повтора на образ)

`docker kill -s SIGKILL redis-master`. Килл подтверждён во всех 6 прогонах
(`exited 137`). Промоушен опрашивается **с хоста** через
`SENTINEL get-master-addr-by-name`, независимо от Go-клиента.

| Прогон | Redis 8.8: промоушен (host-опрос) | Redis 8.8: окно клиента | Valkey 8.1 |
|---|---:|---:|---|
| #1 | **6983 мс** | 10.642 с | ❌ TILT, промоушена нет за 80с |
| #2 | ❌ TILT, промоушена нет за 80с | — | ❌ TILT, промоушена нет за 80с |
| #3 | **7294 мс** | 10.644 с | ❌ TILT, промоушена нет за 80с |

Где промоушен состоялся, картина устойчивая: **Sentinel промоутит за ~7 с**
(при `down-after-milliseconds=5000` — то есть ~5с на признание `s_down` + ~2с
на выборы и переключение), **клиент восстанавливается за ~10.6 с**. Разрыв
между «Sentinel уже знает нового мастера» и «клиент снова пишет» — **4.3–4.9 с**
(в логе: `разница между обнаружением через SENTINEL и восстановлением записи
клиента = 4.939208257s` и `= 4.316670572s` в двух состоявшихся прогонах).

Заметьте контраст с Cluster: у Sentinel клиентское окно **10.6 с**, у Cluster
— **42–49 с**. Это не «Sentinel быстрее Cluster вообще»: у Sentinel
`down-after-milliseconds` снижен до 5000, у Cluster `cluster-node-timeout`
оставлен дефолтным 15000, плюс `FailoverClient` узнаёт новый адрес от
Sentinel явно, а `ClusterClient` вынужден сначала упереться в таймаут пула.

**❌ TILT — и это самая важная находка стенда.** В части прогонов Sentinel
**вообще не делал failover**. Причина зафиксирована инструментально (вывод
`split-brain`, где диагностика печатается каждые 10с):

```
диагностика T+11602ms: sentinel_tilt:1 master0:name=mymaster,status=ok,address=172.28.0.10:6379,slaves=2,sentinels=3
  флаги мастера по sentinel-1: master
диагностика T+45159ms: sentinel_tilt:1 master0:name=mymaster,status=odown,address=172.28.0.10:6379,slaves=2,sentinels=3
```

Мастер физически мёртв/отрезан, а Sentinel держит `status=ok` и флаг `master`
и **не помечает его `s_down`**. Это задокументированное поведение: TILT —
защитный режим, в который Sentinel входит, если задержка итерации его event
loop превысила 2с (или часы прыгнули назад). В TILT Sentinel продолжает
собирать информацию, но **перестаёт действовать**, потому что не доверяет
собственным измерениям времени. На перегруженном виртуализованном хосте
(Docker Desktop/WSL2 + 6–8 контейнеров + клиент, льющий сотни тысяч операций)
событие «event loop задержался >2с» происходит регулярно.

**Про `0/3` у Valkey против `2/3` у Redis: это НЕ сравнение движков.** TILT —
свойство среды (загрузка хоста и стабильность таймеров), а матрицы Redis и
Valkey гонялись **в разное время при разной загрузке хоста**. Валкеевская
матрица шла позже, когда хост был нагружен сильнее. Утверждать «у Valkey
Sentinel хуже» на этих данных нельзя, и я этого не утверждаю. Честная
формулировка: **на этом хосте TILT сорвал 1 из 3 прогонов Redis и 3 из 3
прогонов Valkey**, механизм в обоих случаях один и тот же.

**Практический вывод, который тут действительно есть:** TILT — не
экзотика. Если Sentinel живёт на шумном/переподписанном по CPU хосте или в
VM со скачущими часами, он может **молча не выполнить failover** — при живом
кворуме, корректном конфиге и полностью мёртвом мастере. Проверяется одной
командой: `redis-cli -p 26379 info sentinel | grep tilt`.

#### DNS-имя vs статический IP в `sentinel monitor`: корреляция есть, механизм — гипотеза

Первая версия `compose/sentinel.yml` мониторила мастер по имени (`sentinel
monitor mymaster redis-master 6379` + `resolve-hostnames yes`), и failover не
случился **ни разу**. После перехода на статические IP заработал (~7с).
Разложим, что здесь факт, а что домысел — потому что соблазн склеить их в
красивую причинно-следственную цепочку большой.

**Измерено (есть в логах):**

| Наблюдение | Откуда |
|---|---|
| DNS Docker после убийства контейнера отдаёт по его имени ошибки и **таймауты** | лог **Go-клиента**: `lookup redis-master on 127.0.0.11:53: no such host`, `lookup redis-master: i/o timeout` |
| DNS-конфигурация: **0 промоушенов из 2** попыток | лог прогона |
| IP-конфигурация: **2 промоушена из 3** (redis), ~7с | лог матрицы |
| `sentinel_tilt:1` на момент дедлайна в DNS-прогоне, `sentinel_total_tilt:4` | лог прогона |

**НЕ измерено (гипотеза):** что резолв имени задерживал **event loop
Sentinel**. Таймауты DNS видны **со стороны Go-клиента**, а не Sentinel;
инструмента, который показал бы «Sentinel потратил N мс на resolve внутри
итерации», у стенда нет, и сам Sentinel такой метрики не отдаёт. Механизм
«hostname → синхронный resolve → задержка итерации >2с → TILT» правдоподобен
и согласуется с наблюдениями, но **прямых доказательств у меня нет**.

**Что прямо мешает считать DNS единственной причиной:** TILT возникает и **на
статических IP** — 1/3 прогонов redis и 3/3 valkey, где DNS в пути мониторинга
нет вообще. Значит DNS в лучшем случае **усугубляющий фактор**, спутанный с
загрузкой хоста, а не корень. Выборки крошечные (2 прогона DNS, 3 IP), обе
конфигурации гонялись в разное время при разной загрузке.

Дополнительно (интерактивная проверка, не в логе — как доказательство не
цитируется): на простаивавшем DNS-стенде наблюдалось `sentinel_total_tilt:92`
примерно за 10 минут.

**Честный вывод:** мониторить мастер в Sentinel **по IP, а не по DNS-имени**
— дешёвая и разумная предосторожность, за которой стоит наблюдаемая
корреляция (0/2 против 2/3) и правдоподобный механизм. Но это **не
доказанная причинность**, и «DNS ломает Sentinel» из этих данных не следует.

### Split-brain

Механизм партиции: `redis-master` подключён к **двум** сетям
(`redis-sentinel-net` — Sentinel и реплики; `redis-splitbrain-direct` — только
изолированный писатель). `docker network disconnect redis-sentinel-net
redis-master` снимает **только первый** интерфейс: Sentinel и реплики теряют
мастер, а изолированный писатель продолжает его видеть. Без такой
двухсетевой схемы `docker network disconnect` убрал бы **оба** пути сразу, и
«клиента, который продолжает писать в изолированный мастер», показать было бы
нельзя.

**На `redis:8.8` split-brain воспроизвести НЕ удалось — и причина измерена, а
не додумана.** Sentinel всё время партиции сидел в TILT (`sentinel_tilt:1`,
см. диагностику выше) и не промоутил реплику. Второго мастера не возникло,
расходиться было нечему:

| Что | Наблюдалось |
|---|---|
| Изолированный писатель | 80 из 80 `SET` — `ok` (старый мастер спокойно принимает записи) |
| Промоушен новой реплики | **не произошёл** за 60 с партиции (`sentinel_tilt:1`, `status` дошёл до `odown` только на T+45с, но действий нет) |
| После воссоединения | старый мастер остался `role:master`, все 80 ключей на месте |

Это честный отрицательный результат: **при заблокированном TILT-ом Sentinel
split-brain не возникает** — цена в другом (failover не происходит вообще).

**На `valkey/valkey:8.1` split-brain воспроизвёлся полностью — вот цифры.**
Здесь Sentinel TILT не помешал, и получилось ровно то, ради чего сценарий
писался: **два мастера одновременно**.

| Событие | Значение |
|---|---|
| Партиция (`docker network disconnect`) | T+0 |
| **Sentinel промоутит `172.28.0.12`** | **T+8663 мс** (в первом прогоне — T+8834 мс) |
| Старый мастер (`172.29.0.10`, изолированный) | продолжает считать себя `master` и принимать записи |
| Изолированный писатель | **80 из 80 `SET` подтверждены (`ok`)** |
| После воссоединения: ключи на **старом** мастере | **80** |
| После воссоединения: ключи на **новом** мастере (`172.28.0.12`) | **5** |

**Цена split-brain, измеренная: из 80 записей, которые изолированный мастер
ПОДТВЕРДИЛ клиенту (вернул `OK`), на новом мастере — том, за которым идут все
клиенты, спрашивающие адрес у Sentinel, — оказалось 5. Остальные 75
подтверждённых записей этим клиентам не видны.** Уцелевшие 5 — те, что
писатель успел сделать до того, как партиция реально вступила в силу
(писатель стартует за 3 с до `disconnect`, интервал 500 мс), и они успели
дореплицироваться.

**Формулировка «75 записей потеряны/исчезли» была бы неточной, и вот почему.**
На момент конца прогона эти 75 записей **физически существуют** — они лежат на
старом мастере, который **всё ещё отвечает и всё ещё сообщает `role:master`**
(`master_failover_state:no-failover`). За 60 с после воссоединения он **не
стал** репликой. То есть наблюдалось **расхождение двух живых узлов, которое
не сошлось за окно наблюдения**, а не уничтожение данных: полного цикла
«демоушен → ресинк → затирание расходящейся истории» этот прогон **не
показал**. Точная формулировка: **75 записей не видны клиентам, идущим за
Sentinel**. Что с ними стало бы после демоушена и ресинка — этот стенд не
измерял (ожидаемо их бы затёрло, но это ожидание, а не результат).

Почему демоушен не случился за 60 с — **не установлено**. Вероятный кандидат
— тот же TILT, но инструментально я это не подтвердил и поэтому не утверждаю.

**Важно: одну ложную находку тут пришлось выбросить.** В первом прогоне
воссоединение делалось командой `docker network connect redis-sentinel-net
redis-master` **без `--ip`** — docker выдавал вернувшемуся контейнеру **новый**
адрес из пула, а Sentinel мониторит `172.28.0.10`. Старый мастер возвращался
«не туда», Sentinel его не находил и в принципе не мог демоутить. Результат
выглядел как содержательный вывод про поведение Redis/Valkey («старый мастер
не демоутится, данные остаются»), но был **дефектом стенда**: настоящая
сетевая партиция адрес узла не меняет. Исправлено на `docker network connect
--ip 172.28.0.10`; числа выше — из прогона уже с фиксированным адресом.

**Оговорка про механизм партиции.** `docker network disconnect` выдёргивает
интерфейс целиком — это ближе к «выдернули кабель», чем к типичной сетевой
партиции с потерей пакетов, blackhole-маршрутами или односторонней
связностью. Реальная партиция может выглядеть иначе (например, TCP-соединения
не рвутся мгновенно, а висят до таймаута), и поведение Sentinel/клиента в ней
может отличаться. **Не экстраполировать эти числа на «любую сетевую
аварию».**

### Побочные наблюдения

- **`INFO sentinel` у Valkey беднее:** есть `sentinel_tilt:`, но **нет**
  `sentinel_total_tilt:` (у Redis 8.8 есть оба). Мелочь, но если мониторинг
  считает накопленное число входов в TILT — на Valkey метрики не будет.
- **`ASK`-редиректы поймать почти не удалось:** за все прогоны `ASK`
  встретился лишь однажды (`ASK=2` в отладочном прогоне на redis, не вошедшем
  в финальную матрицу; в финальных прогонах `ASK=0` на обоих образах). `ASK`
  живёт только в узком окне, пока конкретный ключ мигрирует между узлами, и
  попасть в него случайной записью маловероятно. `MOVED` же ловится стабильно
  (14–46 за прогон).
- **Как вообще посчитаны `MOVED`/`ASK`:** go-redis `ClusterClient`
  обрабатывает редиректы прозрачно, вызывающий код их не видит. Счётчик
  вешается через `ClusterClient.OnNewNode` — хук на **каждый узловой**
  `*redis.Client`, то есть на ту функцию, которую редирект-цикл дёргает на
  каждой попытке. Это реальные ответы сервера, а не оценка.

Реальные команды воспроизведения — в `README.md`, раздел «Стенд #4».

## Стенд #5: память и вытеснение (`maxmemory-policy`)

Источник: `memory-eviction/main.go` (сценарии `fill-until-oom`,
`volatile-ttl-degenerate`), оркестрация `ops/eviction-demo.sh`. Каждая ячейка
матрицы — **свежий** `redis-master` из `compose/base.yml`, поднятый с
`--maxmemory 64mb --maxmemory-policy <policy>`, и `down -v` после. Сырые
логи: `scratchout/memory-eviction-redis.log`,
`scratchout/memory-eviction-valkey.log`, `scratchout/eviction-*-lfu-freq.log`
(не в git, воспроизводимы).

### Методика

| Класс ключей | Объём | Обращения |
|---|---|---|
| `hot:N` | 200 × 1 КиБ | `GET` по всем каждые 20 раундов |
| `cold:N` | 2000 × 1 КиБ | одна запись, больше не трогаются |
| `filler:N` | 4 КиБ × тысячи | непрерывный долив — источник давления |

TTL ставится **только** при `volatile-ttl` (на `cold` и `filler`), и
намеренно длинный — 300–420с при прогоне в десятки секунд. Так истечение по
часам не может подмешаться к вытеснению: единственный способ ключу исчезнуть
в этом прогоне — быть вытесненным.

Условие остановки для вытесняющих политик: `evicted_keys > 0` **и**
`used_memory ≥ 90%` от `maxmemory` на двух последовательных проверках, затем
ещё 200 раундов «на статистику». Для `noeviction` — первый
`"OOM command not allowed"`.

### Конфигурация (`CONFIG GET`, идентична на обоих образах)

| Параметр | Значение |
|---|---|
| `maxmemory` | 67108864 (64.0 МиБ) |
| `maxmemory-samples` | **5** |
| `lfu-log-factor` | 10 |
| `lfu-decay-time` | 1 (минута) |
| `mem_allocator` | jemalloc-5.3.0 (оба образа) |

**`maxmemory-samples=5` — ключ к чтению всех чисел ниже.** LRU и LFU в
Redis/Valkey **приближённые**: при нехватке памяти сервер берёт **случайную
выборку из 5 ключей** и вытесняет худший **в ней**, а не глобально худший.
Поэтому результат зависит не только от «заслуг» ключа, но и от того, как
часто его класс вообще попадает в выборку — то есть от **доли класса в
keyspace**.

### Как читать колонку `hot` (иначе таблица соврёт)

`hot`-ключи пишутся **всегда с `ttl=0`** (`fillHotAndCold`, `main.go`). Отсюда:

- Под **`allkeys-lru` / `allkeys-lfu`** 100% выживаемости `hot` — **настоящее
  наблюдение**: ключи были вытесняемы и не вытеснены.
- Под **`volatile-ttl`** `hot` **вообще не в volatile-множестве**, то есть
  **невытесняемы по построению сценария**. 100% там — арифметическая
  неизбежность, а не результат работы политики.
- Под **`noeviction`** не вытесняется вообще ничего.

В таблицах ниже эти две ячейки помечены **«н/п»** (не применимо). Их **нельзя**
цитировать как «политика сберегла горячие ключи».

### Выживаемость по политикам (`redis:8.8`)

**Четыре независимых прогона матрицы** (`volatile-ttl` — три). Диапазон — по
**всем** прогонам; см. ниже «Разброс», это важнее самих границ. Разбивка
вытеснений по классам приводится **как значение конкретного прогона** (в
скобках — из какого), а не диапазоном: часть ранних прогонов шла без этой
инструментовки, и сводить их в диапазон значило бы дорисовывать числа
вычитанием.

| Policy | hot выжило | cold выжило (все прогоны) | evicted hot/cold/filler | OOM |
|---|---|---|---|---|
| `allkeys-lru` | 200/200 (100%) — **наблюдение** | 1542–1653/2000 (**77.1–82.7%**) | 0 / 347 / 304 (Σ651) | нет |
| `allkeys-lfu` | 200/200 (100%) — **наблюдение** | 1817–1964/2000 (**90.8–98.2%**) | 0 / 183 / 354 (Σ537) | нет |
| `volatile-ttl` | **н/п** (`hot` без TTL → невытесняемы) | 1923–1932/2000 (**96.2–96.6%**) | 0 / 68 / 345 (Σ413) | нет |
| `noeviction` | **н/п** (не вытесняется ничего) | 2000/2000 (100%) | 0 / 0 / 0 | **filler:12120** (3/3 прогонов) |

### Выживаемость по политикам (`valkey/valkey:8.1`)

| Policy | hot выжило | cold выжило (все прогоны) | evicted hot/cold/filler | OOM |
|---|---|---|---|---|
| `allkeys-lru` | 200/200 (100%) — **наблюдение** | 1625–1673/2000 (**81.2–83.7%**) | 0 / 375 / 228 (Σ603) | нет |
| `allkeys-lfu` | 200/200 (100%) — **наблюдение** | 1861–1883/2000 (**93.0–94.2%**) | 0 / 138 / 288 (Σ426) | нет |

### Разброс: почему эти диапазоны нельзя сужать

Первая редакция этого раздела публиковала **гораздо более узкие** диапазоны
(redis LRU 77.1–80.2%, redis LFU 97.5–98.2%) — они были получены на **2–3**
прогонах. Четвёртый прогон вышел **за границу обоих**: LRU дал 82.7%, LFU —
90.8%. Диапазоны выше расширены до всех наблюдений, но **и они не «истинные
границы»** — они лишь то, что успело попасться на 3–4 прогонах.

Практический вывод, который тут действительно заслужен: **выживаемость под
сэмплирующим вытеснением заметно шумит от прогона к прогону** (у redis LFU
разброс достигает **7.4 п.п.**) при неизменных конфиге и нагрузке. Любые
сравнения «на пару процентов» между политиками или образами на таких выборках
**не значат ничего**.

### Доказательство, что вытеснение реально сработало

Без этого все проценты выше — пустые. По каждой вытесняющей ячейке:

| Признак | Значение (redis, `allkeys-lru`, прогон 4) |
|---|---|
| `used_memory` на финале | 67044040 из `maxmemory` 67108864 — **99.9%** |
| `used_memory_peak` | 67128192 — **упёрлось в лимит** |
| `evicted_keys` | **651** (за прогон; baseline снят после `FLUSHALL` и вычтен) |
| `expired_keys` | **0** — во **всех 16** прогонах (проверяется явно, см. ниже) |
| `dbsize` на финале | 14049 = hot 200 + cold 1653 + filler 12196 |

Сценарий **падает с ошибкой** (не печатает результат), если
`evicted_keys=0` под вытесняющей политикой, если `used_memory_peak` не
дотянул до 90% `maxmemory`, если на `noeviction` не случилось OOM, **или если
`expired_keys≠0`**. Последнее — не формальность: число вытесненных `cold`
считается **вычитанием** выживших из исходных, поэтому истёкший по TTL ключ
молча приплюсовался бы к «вытесненным» и завысил бы мнимую разборчивость
политики. Во всех прогонах `expired_keys=0`, то есть TTL (300–420с) ни разу не
вмешался в результат. «0 вытеснено» здесь не может выглядеть как находка.

### Почему `hot` выжили на 100% — и почему это НЕ «LRU точно защищает горячее»

Под `allkeys-*` (там, где это вообще наблюдение — см. «Как читать колонку
`hot`») результат чистый, и именно поэтому его легко переоценить. `hot`
защищены **тремя** механизмами, и стенд их **не разделяет**:

1. **Сигнал обращения** — `hot` перечитываются, у них свежий idle (LRU) и
   высокий счётчик LFU (медиана 16 против 4–5 у остальных).
2. **Редкость в выборке** — `hot` составляют **1.4%** keyspace. Вероятность,
   что случайная выборка из 5 ключей содержит хоть один `hot`, ≈ **7%**.
3. **Полная невытесняемость под `volatile-*`** — `hot` пишутся без TTL, то
   есть под `volatile-ttl` не входят в volatile-множество вообще. Здесь
   «выживание» не имеет отношения ни к политике, ни к обращениям.

Вклад (1) против (2) **этим стендом не измерен**; (3) — вообще не свойство
Redis, а свойство сценария. Утверждать «LRU надёжно защищает горячие ключи» на
основании этих 100% нельзя: при другой доле горячего в keyspace (скажем, 60%
вместо 1.4%) картина может быть иной. Приближённость LRU/LFU в этих прогонах
проявилась **не** на `hot`, а на различении `cold` и `filler` — см. ниже.

### Где приближённость видна: `allkeys-lru` против `allkeys-lfu`

**LRU различает `cold` по возрасту — это видно в перекосе вытеснений, и знак
перекоса одинаков во всех прогонах на обоих образах.**

| Прогон | `cold` в вытеснениях | доля `cold` в keyspace (финал) | перевес |
|---|---|---|---|
| redis, №4 | 347 из 651 = **53.3%** | 11.8% | ×4.5 |
| redis, ранний | 458 из 741 = **61.8%** | 11.0% | ×5.6 |
| valkey, №3 | 375 из 603 = **62.2%** | 11.5% | ×5.4 |

Возраст работает как дискриминатор: `cold` никто не трогал с момента записи,
их idle монотонно растёт, и в выборке они систематически худшие.

**Оговорка про базу перевеса — она сдвигает цифру заметно.** Доля `cold` в
keyspace **не постоянна**: на старте вытеснения ≈**14%**, к финалу проседает
до **11–12%** (сами вытеснения её и уменьшают). От финальной доли перевес
выходит **×4.5–5.6**, от стартовых 14% — **×3.8–4.4**. Честный диапазон с
учётом обеих баз — **≈×4–5.6**; одного точного числа тут нет.

**У LFU перевес кратно меньше — но про его «стабильность» на этих данных
говорить нельзя.** Наблюдения (по одному-двум прогонам с этой
инструментовкой на образ):

| Прогон | `cold` в вытеснениях | доля в keyspace | перевес |
|---|---|---|---|
| redis, ранний | 36 из 419 = **8.6%** | 13.8% | **×0.6** |
| redis, №4 | 183 из 537 = **34.1%** | 12.8% | **×2.7** |
| valkey, №3 | 138 из 426 = **32.4%** | 13.0% | ×2.5 |
| valkey, ранний | 139 из 427 = **32.6%** | 13.2% | ×2.5 |

Два redis-прогона разошлись **вчетверо** (×0.6 против ×2.7) — при неизменных
конфиге и нагрузке. Valkey на двух прогонах дал ×2.5 дважды. **Делать из
этого вывод «у LFU перекос нестабилен, а у valkey стабилен» нельзя: 1–2
прогона на ячейку для суждений о стабильности не годятся** (см. «Разброс» —
на большем числе прогонов узкие интервалы уже один раз развалились).

Что **можно** сказать по этим данным: перевес `cold` у LFU (×0.6–2.7) во всех
прогонах **меньше**, чем у LRU (×4.5–5.6), и никогда не достигает его уровня.
Почему — измерено ниже, и вот это измерение от разброса не зависит.

**LFU `cold` от `filler` не отличает вообще. Это измерено `OBJECT FREQ`, а не
выведено из исходников:**

| Класс | `OBJECT FREQ` min / медиана / max (redis) | (valkey) |
|---|---|---|
| `hot` | 12 / **16** / 21 | 11 / **16** / 24 |
| `cold` | 4 / **4** / 4 | 5 / **5** / 5 |
| `filler` | 4 / **4** / 4 | 5 / **5** / 5 |

Выборка — **первые 2000** ключей класса по индексу (для `filler` это самые
**старые** из ~12400; направление консервативное: у старых счётчик имел больше
всего времени просесть, и если уж они не отличаются от `cold`, то свежие тем
более).

`cold` и `filler` записаны **по одному разу каждый**, и счётчик у них
**совпадает до единицы, без разброса вообще**. Для LFU это буквально
неразличимые ключи, и выбор между ними вырождается в случайный. Отсюда и
«хорошая» выживаемость `cold` при LFU: LFU её **не защищал** — он не мог
отличить `cold` от `filler`, а `filler` численно доминирует (~85% keyspace) и
потому забирает большинство вытеснений.

**Абсолютное значение счётчика гуляет между прогонами — 4 или 5 — и это тоже
измерение.** `lfu-decay-time=1` минута: в более медленных прогонах счётчик
успевает просесть с 5 до 4. Но проседает он **у `cold` и `filler`
одновременно**, так что различать их это не помогает — в каждом отдельном
прогоне они всё равно равны друг другу. Совпадение сохраняется на **обоих**
образах и во **всех** прогонах — это самый устойчивый результат стенда.

**Практический вывод, который стоит формулировать осторожно:** LFU выигрывает
у LRU там, где у ключей **разная частота** обращений. Там, где всё записано по
разу и больше не читалось, LFU вырождается: разделить «старое, но записанное
однажды» и «новое, записанное однажды» ему нечем. LRU в этом же сценарии
дискриминатор имеет — возраст.

### Расхождение между образами: РЕТРАКЦИЯ

**В первой редакции здесь утверждалось, что redis и valkey устойчиво
расходятся по выживаемости `cold` (интервалы не пересекаются), с инверсией
знака между LRU и LFU. Это утверждение снято: оно не подтвердилось.**

Оно опиралось на 2–3 прогона на ячейку. Четвёртый прогон каждой ячейки увёл
значения за прежние границы, и интервалы **перекрылись**:

| Policy | cold выжило, redis (все прогоны) | cold выжило, valkey (все прогоны) | Пересекаются? |
|---|---|---|---|
| `allkeys-lru` | 77.1–**82.7%** | **81.2**–83.7% | **да** (81.2–82.7) |
| `allkeys-lfu` | **90.8**–98.2% | 93.0–94.2% | **да** (valkey целиком внутри redis) |
| `volatile-ttl` | 96.2–96.6% | 96.5–97.0% | да |

**Никакого расхождения между образами этот стенд не показал.** Разброс внутри
одного образа (redis LFU: 7.4 п.п.) **перекрывает** всю наблюдавшуюся «разницу»
между образами. Прежний вывод был артефактом малой выборки — классический
случай, когда 2–3 прогона выглядят как чистое разделение просто потому, что
не успели показать хвосты.

**Что это стоит запомнить:** сэмплирующее вытеснение шумит достаточно, чтобы
на паре прогонов «нарисовать» межпродуктовую разницу, которой нет. Сравнивать
Redis и Valkey по выживаемости на таких выборках — нельзя.

### `volatile-ttl`: ровно та же неразличимость, что у LFU

Выживаемость `cold` под `volatile-ttl` (96.2–97.0%) выглядит как «политика
бережёт `cold` лучше всех». **Это не так, и причина ровно та же, что у LFU.**

`volatile-ttl` вытесняет ключ с **ближайшим истечением**. В сценарии:

| Класс | TTL | Формула (`main.go`) |
|---|---|---|
| `cold:i` | случайный в **[300,420)** с | `300 + i%120` |
| `filler:round` | случайный в **том же [300,420)** с | `300 + round%120` |
| `hot:i` | **нет TTL** | всегда `0` |

Распределения TTL у `cold` и `filler` **совпадают**. Значит «ближайшее
истечение» **не может** служить дискриминатором между ними — как счётчик LFU
не мог. И 96% выживаемости `cold` объясняются тем же самым: `filler` численно
доминирует (~85% keyspace) и собирает большинство вытеснений.

**Слабый перекос в сторону `cold` всё же есть — и он объясним:**

| Прогон | `cold` в вытеснениях | доля в keyspace | перевес |
|---|---|---|---|
| redis, №4 | 68 из 413 = **16.5%** | 13.6% | ×1.21 |
| redis, ранний | 77 из 419 = **18.4%** | 13.6% | ×1.35 |
| valkey, №3 | 61 из 410 = **14.9%** | 13.6% | **×1.10** |
| valkey, ранний | 64 из 413 = **15.5%** | 13.6% | ×1.14 |

Итого перевес — **×1.10–1.35** по обоим образам (против ≈×4–5.6 у LRU), то
есть почти пропорционально доле в keyspace. Причина не в «разборчивости»
политики, а в том, что TTL у `cold` проставлены на **десятки секунд раньше**
(они пишутся в начале прогона, `filler` — по ходу), поэтому истекают чуть
раньше при том же
номинале. Это артефакт порядка заливки, а не свойство `volatile-ttl`.

**Вывод: колонку `cold выжило` НЕЛЬЗЯ читать как ранжирование политик.** Из
четырёх ячеек содержательно различает `cold` только `allkeys-lru`. У
`allkeys-lfu` и `volatile-ttl` высокая выживаемость `cold` — следствие
неразличимости плюс численного доминирования `filler`, а не защиты.

### `volatile-ttl` без TTL вырождается в `noeviction` — проверено, не процитировано из доков

Сценарий `volatile-ttl-degenerate`: политика `volatile-ttl`, но **ни у одного
ключа нет TTL**.

| Образ | Результат |
|---|---|
| `redis:8.8` | `"OOM command not allowed"` на `filler:12128`, `evicted_keys=0`, `used_memory_peak=67121296` |
| `valkey/valkey:8.1` | `"OOM command not allowed"` на `filler:12169`, `evicted_keys=0`, `used_memory_peak=67114200` |

Вытеснять нечего: volatile-множество пусто, а `volatile-*` политики
**не трогают ключи без TTL**. Сервер с настроенным `maxmemory-policy` и
64 МиБ лимита ведёт себя ровно как `noeviction` — начинает отказывать в
записи. Это тот случай, когда «политика вытеснения настроена» в конфиге и
«вытеснение работает» — **разные утверждения**.

### `noeviction`: точка отказа почти детерминирована — но «до записи» только у redis

| Образ | OOM на записи, по прогонам | `evicted_keys` | hot+cold целы |
|---|---|---|---|
| `redis:8.8` | `12120` / `12120` / `12120` — **совпало 3 из 3** | 0 | 2200/2200 |
| `valkey/valkey:8.1` | `12196` / `12196` / **`12163`** | 0 | 2200/2200 |

**Здесь тоже пришлось снять более сильное утверждение.** В первой редакции
стояло «точка отказа воспроизводима **до записи** на обоих образах» — на
основании двух совпавших прогонов у каждого. Третий прогон valkey дал
**12163** вместо 12196: расхождение в **33 записи** (~130 КиБ). У redis
совпадение держится (3/3), у valkey — **нет**.

Честная формулировка: заполнение **почти** детерминировано (фиксированный
размер значения, нет фонового вытеснения), и точка отказа воспроизводится с
точностью **лучше 0.3%** — но утверждать побайтовую повторяемость нельзя,
valkey её не показал. Чем вызван сдвиг у valkey — **не установлено**.

Разница redis/valkey (12120 против 12163–12196, т.е. **~43–76 записей** /
~170–300 КиБ) правдоподобно объясняется накладными расходами на
ключ/структуры, а **не** «у valkey больше памяти».

**Но и это сравнение образов стоит брать с оговоркой — с учётом урока
предыдущего раздела.** Собственный дрейф valkey между прогонами
(12196 → 12163 = **33 записи**) — **того же порядка**, что и сам
межпродуктовый разрыв (43–76). Диапазоны пока не пересекаются, и в пользу
разрыва играет то, что здесь нет сэмплирования, а redis дал нулевой разброс
(3/3), — но при n=3 на образ запас прочности **невелик**. Направление
(«valkey вмещает чуть больше записей до отказа») подтверждено всеми
прогонами; величину разрыва цитировать как точную — не стоит.

**Что здесь важно для статьи:** под `noeviction` **чтения продолжают
работать**, отказывают только записи, увеличивающие потребление. Все 2200
hot+cold остались на месте — сервер не «упал», он перестал принимать новое.

### `MEMORY DOCTOR` и фрагментация — где метрика вводит в заблуждение

| Метрика | `redis:8.8` | `valkey/valkey:8.1` |
|---|---|---|
| `mem_fragmentation_ratio` | **1.40–1.42** | **1.27–1.28** |
| `allocator_frag_ratio` | **1.00–1.01** | **1.00–1.01** |
| `rss_overhead_ratio` | 1.19–1.24 | 1.13–1.17 |
| `used_memory_rss` | ~94.3 МБ | ~85.5 МБ |

**`mem_fragmentation_ratio` 1.41 — это не фрагментация на 41%.**
`allocator_frag_ratio` = **1.00–1.01** означает, что jemalloc не фрагментирует
практически совсем. Весь разрыв даёт `rss_overhead_ratio` — RSS процесса
против того, что держит аллокатор: код, стеки, буферы, накладные расходы
среды. Читать `mem_fragmentation_ratio` как «надо запускать
`activedefrag`» — ошибка; разделять их умеет `allocator_frag_ratio`.

Вердикты `MEMORY DOCTOR` (снят `docker exec ... redis-cli memory doctor`
**с хоста**, независимо от Go-клиента). Доктор выдаёт **список** пунктов, и
считать надо каждый пункт отдельно, а не «вердикт образа» целиком
(`grep -c` по логам ячеек, последняя матрица):

| Пункт | Порог | `redis:8.8` | `valkey/valkey:8.1` |
|---|---|---|---|
| `High total RSS` | `mem_fragmentation_ratio` > **1.4** | **5 из 5 ячеек** | **0 из 5** |
| `High process RSS overhead` | `rss_overhead_ratio` > **1.1** | **5 из 5 ячеек** | **5 из 5** |

**Диагноз valkey — строгое подмножество диагноза redis, а не «другой
вердикт».** Разницу создаёт **ровно один порог**: `mem_fragmentation_ratio` у
redis 1.40–1.42 — **за** границей 1.4, у valkey 1.27–1.28 — **не доходит**.
Второй порог (`rss_overhead_ratio` > 1.1) переступают **оба**: 1.19–1.24 у
redis, 1.13–1.17 у valkey.

Отсюда два вывода, и оба важно не перепутать:

- **`High total RSS` у redis — ложноположительный для этой нагрузки.** Доктор
  сам оговаривается: `If the problem is a large peak memory, then there is no
  issue` — а peak здесь упирается в `maxmemory` **по построению сценария**.
- **`High process RSS overhead` с формулировкой `may be due to Lua scripts or
  Modules` печатают ОБА образа** — при том что ни Lua-скриптов, ни модулей в
  стенде нет вообще. **Это не причуда valkey.** В первой редакции этот пункт
  был приписан valkey как его особенность — неверно, логи показывают его и у
  redis в каждой ячейке.

**Нестабильность между прогонами — отдельное наблюдение.** В одной из более
ранних матриц ячейка `allkeys-lfu` на valkey дала `Hi Sam, I can't find any
memory issue in your instance.` — то есть пункт `High process RSS overhead` не
сработал. В последней матрице это **не воспроизвелось** (5 из 5). Валкеевский
`rss_overhead_ratio` = **1.13–1.17** идёт вплотную к порогу **1.1**, так что
перекидывание вердикта от прогона к прогону ожидаемо. (Порог `1.1` — про
`rss_overhead_ratio`; `mem_fragmentation_ratio` 1.27–1.28 к нему отношения не
имеет — в первой редакции эти две метрики были здесь спутаны.)

**Вывод про `MEMORY DOCTOR`:** оба пункта, которые он выдал на этой нагрузке,
указывают на **RSS-накладные расходы**, а не на проблему аллокатора
(`allocator_frag_ratio` = 1.00–1.01 везде), и один из них у redis прямо
ложноположительный. Что именно загорится — определяется парой порогов
(1.4 / 1.1), к которым обе метрики подходят вплотную, поэтому вердикт
меняется и между образами, и между прогонами одного образа. Как «сигнал
тревоги» брать нельзя без проверки `allocator_frag_ratio`.

**Чего эта таблица НЕ показывает:** различия «по существу» между Redis и
Valkey в диагностике памяти. Набор пунктов у valkey беднее **только** потому,
что его `mem_fragmentation_ratio` не дотянул до 1.4 — то есть из-за значения
метрики, а не из-за другой логики доктора. Не цитировать как «доктор в Valkey
работает иначе».

**Оговорка про абсолютные числа памяти (та же, что в Стендах #1–#3).**
Прогон — Docker Desktop на Windows (WSL2). `used_memory_rss` и
`rss_overhead_ratio` в такой среде завышены относительно нативного Linux, и
переносить их на прод **нельзя**.

Что здесь **надёжно** (не зависит ни от хоста, ни от разброса прогонов):

- **`OBJECT FREQ`: `cold` ≡ `filler` во всех прогонах на обоих образах.**
  Самый устойчивый результат стенда.
- **`allocator_frag_ratio` ≈ 1.00 при `mem_fragmentation_ratio` ≈ 1.4** —
  качественный разрыв, а не пара процентов.
- **Вырождение `volatile-ttl` без TTL в OOM** — бинарный факт, воспроизведён
  на обоих образах.
- **Устойчивый знак перекоса у LRU** (`cold` всегда перевешивает) против
  **отсутствия устойчивого знака у LFU**.

Что **ненадёжно** и цитировать нельзя: любые сравнения выживаемости «на
несколько процентов» — ни между политиками, ни между образами. Разброс между
прогонами (до 7.4 п.п.) их перекрывает. См. «Разброс» и «Расхождение между
образами: РЕТРАКЦИЯ».

### Чего этот стенд НЕ измерял

- **`allkeys-random` / `volatile-random` / `volatile-lru` / `volatile-lfu`** —
  не гонялись, в матрице только 4 политики из брифа.
- **Затухание LFU на длинной дистанции.** Само затухание в прогонах видно
  (`lfu-decay-time=1` мин: в более медленном redis-прогоне счётчики просели
  5 → 4, см. раздел про `OBJECT FREQ`) — но проседают `cold` и `filler`
  **одновременно**, и на дистанции прогона это их не разделяет. Разделит ли
  затухание `cold` и `filler` через **10+ минут** простоя, когда разница в
  возрасте станет много больше `lfu-decay-time`, — **не проверено**.
- **Влияние `maxmemory-samples`.** Все прогоны — на дефолтной пятёрке.
  Насколько выживаемость улучшится на `maxmemory-samples=10`, **не измерено**.
- **Разделение вкладов «сигнал обращения» и «редкость в выборке»** в 100%
  выживаемости `hot` — см. выше.
- **Выживаемость `hot` под `volatile-*` как свойство политики** — сценарий
  пишет `hot` без TTL, поэтому там они невытесняемы по построению. Чтобы это
  измерить, нужен отдельный прогон с TTL у `hot`.
- **Сравнение образов по выживаемости.** Прогонов (3–4 на ячейку) не хватает:
  внутренний разброс перекрывает межпродуктовую разницу. Нужны десятки
  прогонов и доверительные интервалы — этого здесь нет.
- **Причина сдвига точки OOM у valkey** (12196 → 12163) — не установлена.

Реальные команды воспроизведения — в `README.md`, раздел «Стенд #5».

## Стенд #6: streams (consumer groups), Lua-атомарность, EVAL против FUNCTION

`race-without-lua`, `atomic-with-lua`, `eval-vs-function`. Топология —
`compose/base.yml` без изменений (без persistence/maxmemory-профилей
предыдущих стендов). Сырые логи: `scratchout/streams-lua-redis.log`,

### Consumer groups: реальный at-least-once после XCLAIM

Методика: `XADD` 1000 сообщений в `cg:orders`, группа `cg:workers` создана
с `0` (видит весь уже существующий стрим как новый). Три консьюмера
(`consumer-1`, `consumer-2`, `consumer-3`) читают батчами по 50 через
`XREADGROUP ... COUNT 50 STREAMS cg:orders >` по очереди (детерминированный
раунд-робин, не параллельные горутины — семантика consumer group от этого
не меняется, а результат становится воспроизводимым). `consumer-2` нормально
обрабатывает и подтверждает (`XACK`) первые 2 своих батча (100 сообщений), а
на третьем — обрабатывает (реальный побочный эффект: `HINCRBY` по ID
сообщения) и **не делает `XACK`**, дальше не читает («падает на середине»).
Обработка каждого сообщения = `HINCRBY cg:processed <id> 1`, поэтому число
обработок каждого ID — это измеренный факт, а не предположение.

Результат идентичен на обоих образах (сценарий детерминированный):

| | `redis:8.8` | `valkey/valkey:8.1` |
|---|---|---|
| Доставлено всего | 1000/1000 | 1000/1000 |
| Зависло у `consumer-2` (без XACK) | 50 | 50 |
| `XPENDING` summary после падения | `count=50`, `consumers=map[consumer-2:50]` | `count=50`, `consumers=map[consumer-2:50]` |
| `XPENDING` idle на момент `XCLAIM` | 249ms (все 50 записей) | 250ms (все 50 записей) |
| `XCLAIM` (`consumer-1`, `MINIDLE 0`, форс) | забрал 50/50 | забрал 50/50 |
| `XPENDING` после финального `XACK` | `count=0` | `count=0` |
| Обработано ровно 1 раз | 950 | 950 |
| **Обработано ДВАЖДЫ (реальные дубликаты)** | **50** | **50** |

`MINIDLE 0` в `XCLAIM` — намеренно: сценарий симулирует оператора, который
уже подтвердил (например, по внешнему health-check) что `consumer-2` мёртв,
и забирает его PEL немедленно, не дожидаясь произвольного порога простоя.
В проде `XCLAIM`/`XAUTOCLAIM` обычно ждут `min-idle-time` в диапазоне
десятков секунд — здесь это заменено явным форс-клеймом, потому что
«падение» уже синхронно и подтверждено внутри самого прогона.

**Почему дубликатов ровно 50, а не 0 и не иначе:** это ровно те 50
сообщений, которые `consumer-2` успел обработать (`HINCRBY`) ДО падения, но
не успел подтвердить. После `XCLAIM` их забирает `consumer-1` и
обрабатывает заново — тот же ID получает второй `HINCRBY`. Прогон
падает с `os.Exit(1)` (см. `main.go`, `consumerGroups`), если: доставлено не
ровно 1000; `stuckIDs` пуст (падение не индуцировано); `XPENDING` до/после
не совпадает с ожидаемым; дубликатов 0 или их число не совпадает с размером
зависшего батча; PEL после финального `XACK` не пуст. Ни один из этих
случаев не встретился ни на одном образе.

**Как читать «50 на обоих образах» — важная оговорка.** Число 50 — это
`-batch` (размер батча `XREADGROUP`), то есть **параметр**, а не измеренная
величина: падение по построению происходит ровно на границе батча, поэтому
зависнуть может только целый батч. Более того, равенство
«дубликатов = размер зависшего батча» **фатально проверяется** самим
сценарием. Поэтому совпадение redis и valkey здесь — это **выполнение
инварианта**, а не независимо измеренный межобразный результат: если бы
образ повёл себя иначе, прогон бы упал, а не показал другое число.
Содержательный результат здесь — **сам факт**, что после `XCLAIM`
переобработка происходит и дубликаты реальны (at-least-once работает как
задокументировано), а не конкретная цифра 50.

### Гонка: `race-without-lua` против `atomic-with-lua`

Методика: `-workers 20 -iterations 500` = 10000 попыток read-modify-write
над общим ключом. Без Lua — раздельные `GET`+`SET` (гонка возможна между
ними); с Lua — один `EVAL` (тот же `GET`+условие+`SET`, атомарно на
сервере). Условие `v < limit` с `limit = workers*iterations` подобрано так,
чтобы оно было истинным на каждой из 10000 попыток (реальное значение
физически не может обогнать число уже состоявшихся записей) — то есть
теряются именно **честные** попытки записи, а не отфильтрованные условием.

**Доказательство, что гонка реально гонялась, а не «просто не пересеклась».**
Каждая попытка — это окно `[t0 начала GET/EVAL, t1 конца SET/EVAL]`. После
прогона код (`detectCrossWorkerOverlaps`) считает, у скольких попыток было
хотя бы одно активное окно **другой** горутины в момент начала. Если
пересеклось **менее 50%** попыток, прогон падает с `os.Exit(1)`:
конкурентность не доказана, и «0 потерь» тогда ничего не значит. Порог взят
долей, а не «хоть одно пересечение»: при пороге `> 0` тест проходил бы и в
вырожденном случае одного пересечения из 10000. Во всех 12 прогонах ниже
пересеклось **99.4–99.9%** попыток (9944–9994 из 10000) — то есть guard
проходит с большим запасом, а не на границе; конкурентность подтверждена
измерением, не предположена.

| Прогон | Образ | Сценарий | attempts | final | **lost** | overlaps (доказательство гонки) |
|---|---|---|---|---|---|---|
| 1 | redis:8.8 | race-without-lua | 10000 | 956 | **9044** | 9990/10000 |
| 2 | redis:8.8 | race-without-lua | 10000 | 942 | **9058** | 9985/10000 |
| 3 | redis:8.8 | race-without-lua | 10000 | 940 | **9060** | 9993/10000 |
| 4 | valkey:8.1 | race-without-lua | 10000 | 951 | **9049** | 9991/10000 |
| 5 | valkey:8.1 | race-without-lua | 10000 | 948 | **9052** | 9993/10000 |
| 6 | valkey:8.1 | race-without-lua | 10000 | 936 | **9064** | 9994/10000 |
| 7 | redis:8.8 | atomic-with-lua | 10000 | 10000 | **0** | 9981/10000 |
| 8 | redis:8.8 | atomic-with-lua | 10000 | 10000 | **0** | 9963/10000 |
| 9 | redis:8.8 | atomic-with-lua | 10000 | 10000 | **0** | 9949/10000 |
| 10 | valkey:8.1 | atomic-with-lua | 10000 | 10000 | **0** | 9972/10000 |
| 11 | valkey:8.1 | atomic-with-lua | 10000 | 10000 | **0** | 9986/10000 |
| 12 | valkey:8.1 | atomic-with-lua | 10000 | 10000 | **0** | 9944/10000 |

**Разброс `race-without-lua`: 9044–9064 потерянных инкремента из 10000
попыток (90.4–90.6%)** — на обоих образах, разброс между прогонами
небольшой (±10 при доказанной почти-100%-ной конкурентности), но это всё
равно РАЗБРОС, не одно число: три прогона на `redis:8.8` дали три разных
значения, три прогона на `valkey:8.1` — тоже три разных. Такой высокий
процент потерь (не единичные проценты) ожидаем: 20 горутин непрерывно
читают-пишут один и тот же ключ без бэкоффа, окно гонки (между `GET` и
`SET`) остаётся открытым практически на всё время round-trip, поэтому
почти каждая попытка «наступает» на чужую.

**`atomic-with-lua`: 0 потерь во всех 6 прогонах (оба образа), при
доказанной конкурентности 99.4–99.9%.** Это не теоретический вывод из
документации — каждый прогон явно проверяет `final > limit` (фатально,
если сервер вообще нарушил атомарность) и печатает фактическое `lost`,
которое оказалось нулевым во всех 6 случаях.

### `eval-vs-function`: latency EVAL против FUNCTION

Методика: один и тот же Lua-скрипт (138 байт — условный `GET`+`SET`, тот же
текст, что и в `atomic-with-lua`) вызывается двумя способами: `EVAL` (тело
скрипта в каждом вызове, сервер кеширует по SHA после первого исполнения) и
`FUNCTION LOAD REPLACE` + `FCALL` (библиотека загружена заранее, как при
деплое). Один клиент, без конкуренции (латентность вызова, не пропускная
способность под нагрузкой). `op count=2000`, `warmup=200` отброшено перед
каждой серией. Перед измерением — `SCRIPT FLUSH`.

> **Важно про историю этого раздела.** Первая редакция стенда отбрасывала
> нулевые замеры и публиковала перцентили выживших. Это оказалось **ошибкой
> измерения**, которая сама и порождала «разброс ±200мкс», списанный тогда на
> «виртуализационный шум». Ниже — исправленный замер и разбор ошибки; старые
> числа не восстанавливаются, потому что они были артефактом фильтра.

#### Артефакт часов: что наблюдается и что из этого следует

На этой машине (Docker Desktop/Windows) `time.Since()` вокруг реального
round-trip к Redis регулярно возвращает **ровно 0**, при том что команда
честно выполняется. Доля таких замеров — **34.9–46.4%** в 12 сериях ниже
(6 прогонов × 2 серии; число печатается каждым прогоном, взято из логов).
Это **наблюдаемый разброс именно этих серий, а не граница**: доля не
является стабильной константой среды и в других прогонах выходила за
диапазон. Поэтому любой замер здесь имеет смысл читать только вместе с
напечатанной для него долей нулей.

**Механизм не установлен, и стенд его не устанавливает.** Наблюдение —
только само наличие нулей и их доля. Известно встречное свидетельство
против наивного «низкое разрешение часов»: **все ненулевые значения кратны
100нс**, а часы с шагом 100нс физически не могут округлить ~390мкс до нуля.
Что именно происходит (Hyper-V, QPC, планировщик) — **не диагностировано**
и здесь не утверждается.

**И, что важно, для дальнейшего это и не нужно.** Всё, что ниже, следует из
арифметики, без всякой гипотезы о механизме часов:

- Нулевые замеры вносят в сумму ровно 0. Значит среднее по выжившим
  (ненулевым) замерам = `сумма/nonZero` = `elapsed/nonZero` =
  `(elapsed/attempts) × (attempts/nonZero)` = **`среднее/(1−доля_нулей)`**.
  Это **тождество**, а не модель: отбрасывание нулей завышает среднее
  выживших ровно в `1/(1−доля_нулей)` раз. Проверка на `redis:8.8`, прогон 1,
  серия EVAL: `elapsed/nonZero` = 777.745мс/1170 = **664.7мкс**, и
  `388.872/(1−0.415)` = **664.7мкс** — сходится точно.
- Доля нулей у разных серий **разная** (34.9–46.4%), поэтому множитель
  завышения у них тоже разный (**×1.54…×1.87**), и разница перцентилей между
  сериями отражает прежде всего **разницу долей нулей**, а не латентность
  вызова. Симметричный код при асимметричной доле артефакта — это не
  несмещённое сравнение. Проверка на старых данных: в 4 прогонах из 5
  бóльшую `p50` имела та серия, у которой была бóльшая доля нулей.
- **Несмещённая оценка — `elapsed/attempts`**: она вообще не зависит от того,
  как часы распределили время между отдельными замерами, потому что берёт
  только две отметки — начало и конец серии.

**Про печатаемое «отношение суммы замеров к elapsed = 1.000» — что оно на
самом деле значит.** Это **не** свидетельство аляйзинга: сумма
`Σ(T(конецᵢ)−T(началоᵢ))` телескопируется в `T(конец)−T(начало)` минус
межвызовные промежутки **при любых часах** — идеальные часы без единого нуля
напечатают те же 1.000. Проверка полезна другим: она подтверждает, что
межвызовные накладные расходы (`append`, сам `time.Now()`) пренебрежимы
(~0.01% от 780мс), то есть что `elapsed/attempts` — это действительно
среднее время **вызовов**, а не вызовов вперемешку с оверхедом цикла.
Именно так она и описана в выводе стенда.

`p50/среднее` = **1.77…1.95**, то есть во **всех 12 сериях** чуть выше
предсказанного — распределение правостороннее, и удаление нулей сдвигает
медиану сильнее, чем множитель для среднего. Порядок величины
сходится, точное значение — нет, и выдавать это за точное совпадение
не следует. Так или иначе это цена фильтра.

#### Разделение эффекта «руки» и эффекта «порядка»

Серии идут последовательно, поэтому в одном прогоне «медленнее» может
значить и «эта команда дороже», и «эта серия шла первой». Чтобы разделить,
каждая конфигурация прогнана ещё и в **обратной ориентации**
(`-swap-order`: сначала FCALL, потом EVAL). Если бы лидировал порядок, знак
Δ при развороте бы **сменился**.

| Образ | Ориентация | Δ (EVAL−FCALL), среднее по 3 | Знак |
|---|---|---|---|
| redis:8.8 | EVAL первой | **+11.33µs** | 3/3 положительных |
| redis:8.8 | FCALL первой (`-swap-order`) | **+10.21µs** | 3/3 положительных |
| valkey:8.1 | EVAL первой | +6.58µs | 2/3 положительных |
| valkey:8.1 | FCALL первой (`-swap-order`) | −2.71µs | 1/3 положительных |

Две ориентации дают систему: `Δ_прямая ≈ эффект_руки + эффект_порядка`,
`Δ_обратная ≈ эффект_руки − эффект_порядка`. Отсюда для `redis`:
**эффект руки ≈ +10.77мкс, эффект порядка ≈ +0.56мкс** — то есть порядок
серий здесь практически ни при чём, а разница держится на самой команде.

| Образ | Δ (EVAL−FCALL), n=6 | sd | sem | t | 95% ДИ |
|---|---|---|---|---|---|
| redis:8.8 | **+10.77µs** | 6.13 | 2.50 | **4.31** (p≈0.008) | **[+4.3, +17.2]** |
| valkey:8.1 | +1.94µs | 9.15 | 3.74 | 0.52 (p≈0.62) | **[−7.7, +11.5]** |

**Что отсюда следует — и, что важнее, чего НЕ следует:**

- **`redis:8.8`: `EVAL` дороже `FCALL` примерно на 10.8мкс (2.8% от
  ~385мкс).** 6/6 прогонов одного знака, эффект держится в **обеих**
  ориентациях (разворот порядка знак не поменял: +11.33 → +10.21), ДИ не
  накрывает ноль, и воспроизвелось в двух сессиях с разными базовыми
  уровнями. Это **измеренный результат**, а не шум.
- **Правдоподобное и скучное объяснение**: `EVAL` шлёт 138 байт тела скрипта
  в **каждом** вызове, `FCALL` — только короткое имя функции. Лишние ~128
  байт на запрос. Важная оговорка: если механизм такой, то это, скорее
  всего, **стоимость записи в сокет на стороне клиента**, а не работа
  сервера — утверждать «`EVAL` дороже обходится Redis» эти данные **не
  позволяют**.
- **`valkey/valkey:8.1`: сказать, что эффекта нет, НЕЛЬЗЯ.** Среднее +1.94мкс
  с ДИ **[−7.7, +11.5]**, который **накрывает и ноль, и redis-овские
  +10.8мкс**. Разброс на `valkey` в этом стенде в полтора раза выше (sd 9.15
  против 6.13), и мощности просто не хватает: контраст образов даёт
  t≈1.97 (p≈0.08) — **не значим**. Это **отсутствие свидетельства, а не
  свидетельство отсутствия**: те же ~11мкс на `valkey` этими данными
  одинаково не подтверждаются и не опровергаются.

Ранее в этом разделе «`valkey` эффект не воспроизводит» подавалось как
установленный факт, и на нём же строился вывод «измерено, но не объяснено»
(раз лишние байты не объясняют расхождение образов — значит загадка). **Это
было неверно дважды:** расхождения образов стенд не показал, а без него и
загадки нет. Честное чтение — скучное: `redis` показывает эффект,
согласующийся с гипотезой лишних байт; данных по `valkey` не хватает, чтобы
что-то сказать.

#### Что из этого стоит уносить

**Большой разницы между `EVAL` и `FCALL` нет**: всё укладывается в ≈3% от
средней латентности вызова. Это согласуется с устройством движка — после
первого исполнения сервер кеширует тело `EVAL`-скрипта по SHA1 и в
установившемся режиме исполняет **тот же скомпилированный Lua-чанк**, что и
`FCALL`. Разница между способами вызова — **не** про «компиляцию каждый раз».

Но и «разницы нет вообще» сказать нельзя: на `redis:8.8` устойчиво держатся
~11мкс в пользу `FCALL`, скорее всего — цена лишних байт на проводе.
**Строить на 11мкс архитектурные решения не стоит**: выбирать `FUNCTION`
вместо `EVAL` имеет смысл по другим причинам (версионирование, деплой,
`FUNCTION DUMP`/`RESTORE`, отсутствие «а вдруг скрипт вымыло из кеша»), а не
ради этих микросекунд.

**Оговорка про абсолютные числа.** ~390мкс на round-trip — это Docker
Desktop на Windows, и это **не** нативная латентность Redis (на голом Linux
loopback — единицы-десятки микросекунд). Переносить абсолют на прод нельзя;
надёжна только относительная часть **внутри одного прогона**. Абсолютные
средние заметно дрейфовали и между сессиями (серия swap на `redis` шла на
334–386мкс против 373–392мкс в прямой) — ещё одна причина смотреть на
внутрипрогонную дельту, а не на абсолют.

#### Что стенд НЕ измерял

- **Пропускную способность под конкурентной нагрузкой** — только latency
  одного клиента без конкуренции.
- **Чередование серий (interleaving).** Ориентации прогнаны обе, но внутри
  прогона серии идут блоками, а не вперемешку; медленный дрейф среды внутри
  блока не скомпенсирован.
- **Механизм артефакта часов** — зафиксировано сохранение времени и
  кратность 100нс, но что именно аляйзит (Hyper-V/QPC/планировщик), не
  установлено.
- **Механизм расхождения redis и valkey** по эффекту руки — не установлен.
- **Скрипты существенно крупнее 138 байт**, где перевес `FCALL` по числу
  байт на проводе мог бы стать заметнее.
- **Latency `EVAL` без `SCRIPT FLUSH`** — в проде скрипт почти всегда уже в
  кеше; наш «холодный» замер намеренно наихудший.

Реальные команды воспроизведения — в `README.md`, раздел «Стенд #6».

### Pool-sizing (Go/go-redis): методология

50 горутин (по заданию) одновременно пишут `SET` через клиент с `PoolSize`
5/20/50 — три отдельных клиента, не один растущий пул. Три решения,
без которых сравнение было бы нечестным или пустым (все — проверено
живьём, не из документации):

1. **`MaxActiveConns` = `PoolSize`.** В go-redis v9 `PoolSize` — это только
   «базовое» число соединений: если их не хватает, пул **растёт сверх
   PoolSize**, если `MaxActiveConns` не задан отдельно (см. `options.go`,
   v9.21.0). Без этой строки 5/20/50 были бы тремя одинаково безлимитными
   пулами — ни один размер не дал бы ни одного таймаута.
2. **`MaxRetries: -1` (ноль повторов).** По умолчанию go-redis сам
   повторяет команду после таймаута пула. Проверено живьём на `PoolSize=1`,
   `-pool-timeout 1ms`: клиентская `PoolStats().Timeouts` (внутренний
   счётчик семафора) насчитала **1660** таймаутов ожидания за прогон, а до
   вызывающего кода в виде ошибки дошло только **30** — 1630 повторов
   ретрай тихо поглотил ценой добавленной латентности, а не видимой ошибки.
   С ретраями «число pool timeout ошибок» почти всегда занижено на порядок
   и не отражает реальную остроту контеншна. Здесь ретраи выключены, чтобы
   первая же неудача была видна как есть.
3. **`PoolTimeout` — явный и одинаковый для всех трёх размеров, а не дефолт
   go-redis** (`ReadTimeout+1с`, обычно ≈4с — слишком щедрый, чтобы
   истощение уместилось в разумное время теста при реальной, а не
   искусственно замедленной, латентности `SET`).

**Несмещённая средняя латентность попытки** — здесь НЕ `overallElapsed /
attempts` (как в последовательном `streams-lua`): горутины работают
**параллельно**, и глобальный elapsed/attempts был бы оценкой throughput
наоборот, а не латентности. Вместо этого — средневзвешенное по горутинам
их **собственных** `elapsed/attempts` (внутри одной горутины операции
строго последовательны, поэтому трюк работает так же, как в
`streams-lua/main.go`): `meanPerAttempt = Σ(elapsed_горутины) /
Σ(attempts)`. Перцентили p50/p95/p99 — только по **успешным** операциям;
таймауты пула туда не подмешаны, считаются отдельным числом.

**Все абсолютные числа этого раздела — Docker Desktop на Windows (WSL2), а
не нативный Redis.** На голом Linux по loopback латентность round-trip —
единицы-десятки микросекунд, здесь — единицы миллисекунд, то есть на два
порядка больше. Ни одну строку с `ops/s`, `p50/p95/p99` или `мс` из этого
раздела **нельзя цитировать как производительность Redis** — надёжны
только относительные сравнения **внутри одного прогона**. Та же оговорка
действует и для round-trip в разделе «Мониторинг» ниже.

**Сравнимость арм: две меры, обе обязательные.**

1. **`FLUSHDB` перед каждой армой.** Все армы пишут одни и те же 10000 имён
   ключей. Без очистки первая арма создавала бы их с нуля (и при тесном
   пуле успевала бы создать лишь часть), а следующие — **перезаписывали**
   уже существующие; создание и перезапись — разная работа для сервера, то
   есть армы отличались бы не только размером пула.
2. **Обе ориентации порядка арм (`-swap-order`).** Армы идут
   последовательно в одном процессе, поэтому позиция в очереди —
   потенциальный конфаундер. Прогнаны обе ориентации (5→20→50 и 50→20→5)
   по 3 повтора каждая; тот же приём и тот же флаг уже применяются в
   `streams-lua` (eval-vs-function). **Это не формальность — на Java-стороне
   конфаундер реально нашёлся, см. ниже.**

### Pool-sizing (Go): чувствительность к выбору `PoolTimeout`

Сценарий прогонялся с тремя значениями `-pool-timeout` (redis:8.8, по
одному прогону на значение, тем же бинарником, что и основная матрица) —
это не шум, а демонстрация того, что «число pool timeout ошибок»
**целиком зависит от выбранного порога**, и цитировать его без порога
рядом нечестно:

| `-pool-timeout` | size=5 | size=20 | size=50 |
|---|---:|---:|---:|
| 1мс | 73.2% | 41.3% | 0.0% |
| 2мс (выбрано для таблиц ниже) | 53.3% | 6.7% | 0.0% |
| 5мс | 0.4% | 0.2% | 0.0% |

Направление везде одно и то же (меньше пул → больше таймаутов, `size ==
concurrency` → ноль), но абсолютные проценты меняются в разы при сдвиге
порога на несколько миллисекунд. **2мс** зафиксирован для итоговых таблиц
как значение, дающее содержательный контраст между всеми тремя размерами
на этой машине — не как «типичный прод-таймаут» (в проде `PoolTimeout`
обычно выше, порядка сотен мс — секунд, и здесь таймаутов было бы
на порядки меньше при той же латентности `SET`).

### Pool-sizing (Go): результаты (обе ориентации × 3 повтора на образ, `-pool-timeout 2ms -ops 200`)

| Образ | Ориентация | size=5 | size=20 | size=50 |
|---|---|---:|---:|---:|
| redis:8.8 | прямая (5→20→50) | 53.3 / 52.3 / 53.7% | 4.9 / 3.3 / 8.2% | 0.0% ×3 |
| redis:8.8 | обратная (50→20→5) | 53.3 / 54.0 / 53.1% | 5.1 / 3.9 / 5.0% | 0.0% ×3 |
| valkey:8.1 | прямая (5→20→50) | 52.7 / 54.0 / 53.9% | 2.8 / 6.8 / 6.0% | 0.0% ×3 |
| valkey:8.1 | обратная (50→20→5) | 54.0 / 54.0 / 53.8% | 3.0 / 3.9 / 3.3% | 0.0% ×3 |

**Порядок арм на Go-стороне не значит ничего:** size=5 даёт 52.3–53.7% в
прямой ориентации и 53.1–54.0% в обратной — интервалы практически
совпадают; size=20 — 3.3–8.2% против 3.9–5.1%, полностью перекрываются.
То есть эффект — свойство **размера пула**, а не позиции армы в очереди.

Сводно по обоим образам и обеим ориентациям: **52.3–54.0%** на size=5,
**2.8–8.2%** на size=20, **0.0%** на size=50 во всех 12 прогонах (пул ==
конкурентность — очереди не возникает по построению). Разброс между
повторами одного образа шире, чем разница между образами — то же
наблюдение, что и в предыдущих стендах: **сравнивать redis/valkey по этому
числу нельзя**.

### Pool-sizing (Go): латентность — и почему её нельзя читать наивно

redis:8.8, прямая ориентация, прогон #1. Абсолютные числа — Docker Desktop
на Windows (см. оговорку выше), не нативный Redis.

| size | доля успешных | throughput | среднее по ВСЕМ попыткам (Σelapsed/Σattempts) | p50 | p95 | p99 | нулевых |
|---|---:|---:|---:|---:|---:|---:|---:|
| 5 | 46.7% | 24032 ops/s | 2.050мс | 2.062мс | 2.806мс | 3.288мс | 1.4% |
| 20 | 95.1% | 23333 ops/s | 2.106мс | 2.097мс | 3.140мс | 4.201мс | 0.4% |
| 50 | 100% | 30942 ops/s | 1.556мс | 1.371мс | 2.717мс | 3.903мс | 0.7% |

**Читать эту таблицу как «size=50 быстрее» нельзя, и вот почему.** Столбцы
меряют разные вещи над **разными выборками**:

- **«среднее по ВСЕМ попыткам»** — знаменатель включает и попытки, которые
  закончились таймаутом (на size=5 это 53.3% всех попыток). Это НЕ
  «латентность успешной операции» — это стоимость средней попытки, включая
  провалившиеся, которые обрываются на ≈`PoolTimeout` и потому **дешевле**
  успешных.
- **p50/p95/p99** — только по успешным. И вот здесь ловушка: на size=5
  «успешные» — это **выжившая половина** (46.7%), то есть те, кому
  соединение досталось быстро; медленные попытки в эту выборку не попали,
  они стали таймаутами. На size=50 в выборке **все 100%** попыток. Это
  **цензурирование выборки**, и оно систематически занижает перцентили
  тесных пулов.

Насколько это существенно — видно из **собственной Java-армы этого же
стенда**, где цензурирование сильнее (успешных на size=5 всего ~22%):
там p50 идёт в **обратную** сторону — **0.842мс** на size=5 против
**1.659мс** на size=50 (`ops-java-redis.log`). Тот же сценарий, тот же
`PoolTimeout`, противоположный порядок p50. Поэтому первая редакция этого
раздела, утверждавшая «без очереди успешные операции быстрее **по
построению**», **снята**: это было теоретическое рассуждение, поданное как
измерение, и оно опровергается соседней армой того же стенда.

**Что можно утверждать честно:** доля отказов монотонно падает с ростом
пула — у Go: 52.3–54.0% → 2.8–8.2% → 0.0%, у Java: ≈74% → ≈42% → 0%
(абсолютные числа разные, направление одно и то же), устойчиво, в обеих
ориентациях, на обоих образах, в обоих клиентах. Про латентность при разных
размерах пула этот
стенд **сравнимых** чисел не даёт — для этого нужен замер, где все армы
имеют одинаковую долю успешных (например, `PoolTimeout`, при котором
таймаутов нет нигде, — но тогда исчезает и сам изучаемый эффект).

**Про артефакт часов** (`time.Since()` иногда возвращает ровно 0, см.
`streams-lua/main.go`) — доля нулевых замеров здесь мала (0.2–1.4%,
множитель смещения ×1.00–1.01), заметно меньше, чем в `streams-lua`
(34.9–46.4%). Механизм не диагностирован, как и там.

### Pool-sizing (Java/Lettuce): методология и грабли обёрнутых соединений

`ops-stand/java/` — тот же сценарий на
`GenericObjectPool<StatefulRedisConnection<String,String>>`
(commons-pool2 2.13.1) поверх Lettuce 7.6.0.RELEASE:
`GenericObjectPoolConfig.setMaxTotal(poolSize)`,
`setMaxWait(pollTimeout)` — прямой аналог `MaxActiveConns`/`PoolTimeout`
у go-redis. `FLUSHDB` и обе ориентации порядка (`OPS_SWAP_ORDER`) —
зеркало Go-стороны.

**Исчерпание пула отличается от сбоя по ТИПУ исключения, а не «по
допущению».** `pool.borrowObject()` считается таймаутом пула **только**
при `java.util.NoSuchElementException`; любое другое исключение —
фатально. Оба конца проверены живьём, а не взяты из сигнатуры (она
объявляет широкий `throws Exception`):

| Ситуация | Что бросает `borrowObject()` |
|---|---|
| Пул исчерпан (держим единственное соединение, `maxWait=2ms`) | `java.util.NoSuchElementException: Timeout waiting for idle object, maxWaitDuration=PT0.001845335S` |
| Сервер мёртв (порт без слушателя) | `io.lettuce.core.RedisConnectionException: Unable to connect to 127.0.0.1/<unresolved>:6399` |

Это не педантизм: первая редакция стенда ловила здесь `catch (Exception)`
целиком, и тогда **умерший на середине сервер, сбой создания соединения
или OOM отрисовались бы как аккуратные «81% pool timeout» с кодом возврата
0** — то есть провалившийся прогон выглядел бы как честный результат.
Таблица выше показывает, что эти случаи действительно различимы, и узкий
`catch` их не проглотит.

**Реальная ошибка при разработке, стоит зафиксировать.**
`ConnectionPoolSupport.createGenericObjectPool(supplier, config)` по
умолчанию отдаёт **обёрнутые** соединения — вызов `close()` у обёртки
**сам** возвращает объект в пул (см. официальный wiki Lettuce,
Connection-Pooling). Первая версия стенда использовала одновременно
try-with-resources (то есть `close()`) **и** явный `pool.returnObject()` —
комбинация даёт `IllegalStateException: Object has already been returned
to this pool or is invalid` на первой же попытке. Исправлено: только
`close()`/try-with-resources, `pool.returnObject()` нигде не вызывается
явно.

### Pool-sizing (Java): результаты — и найденный конфаундер порядка

Обе ориентации × 3 повтора на образ, тот же `-pool-timeout` 2мс:

| Образ | Ориентация | size=5 | size=20 | size=50 |
|---|---|---:|---:|---:|
| redis:8.8 | прямая (5→20→50) | 78.2 / 78.0 / 78.6% | 44.0 / 47.4 / 43.6% | 0.0% ×3 |
| redis:8.8 | обратная (50→20→5) | **70.2 / 70.2 / 70.3%** | **39.4 / 40.9 / 38.8%** | 0.0% ×3 |
| valkey:8.1 | прямая (5→20→50) | 77.8 / 77.4 / 79.6% | 46.5 / 42.8 / 45.2% | 0.0% ×3 |
| valkey:8.1 | обратная (50→20→5) | **74.5 / 70.7 / 70.8%** | **36.9 / 39.6 / 41.5%** | 0.0% ×3 |

**Вот ради чего нужны были обе ориентации: на Java-стороне порядок арм
значит, и заметно — в отличие от Go.** На `redis:8.8` size=5 даёт
78.0–78.6% первой армой и **70.2–70.3%** последней — интервалы **не
пересекаются**, разрыв ≈8 п.п.; size=20 — 43.6–47.4% против 38.8–40.9%,
тоже без пересечения. На `valkey` — то же направление (77.4–79.6% против
70.7–74.5%). Знак везде один: **чем позже арма идёт в процессе, тем меньше
у неё отказов**.

Правдоподобный механизм — прогрев JVM (JIT компилирует горячий путь по
ходу процесса, поздние армы работают уже скомпилированным кодом), но
**этот стенд его не диагностировал**: замера, отделяющего JIT от прочего
разогрева (пулы, сокеты, кеши ОС), здесь нет. Зафиксировано как
**измеренный факт наличия эффекта порядка**, а не как объяснённый
механизм. На Go-стороне того же эффекта нет — что с гипотезой о JIT
согласуется, но её не доказывает.

Практическое следствие для чтения таблицы: **одна ориентация у Java врала
бы примерно на 8 п.п.** Оценка, свободная от порядка, — среднее по обеим
ориентациям: ≈74% (size=5), ≈42% (size=20), 0% (size=50) на `redis:8.8`.

**Направление совпадает с Go** (меньше пул → больше отказов, `size ==
concurrency` → ноль во всех 12 прогонах), но **абсолютные проценты выше**:
≈74% против 52.3–54.0% у Go на size=5, ≈42% против 2.8–8.2% на size=20. **Это НЕ
вывод «Lettuce хуже go-redis под контеншном».** Сравнение не выровнено
сразу по трём осям:

1. **Окружение.** Go-бинарник исполняется нативно на Windows-хосте, Java —
   внутри WSL2; оба бьют в один и тот же опубликованный порт `6379`, но по
   **разным сетевым путям** (прямой localhost против WSL2 vNIC).
2. **Реализация пула.** Семафор на канале у go-redis против
   `GenericObjectPool` из commons-pool2 — разные алгоритмы ожидания и
   разная точность соблюдения `maxWait`.
3. **Эффект порядка.** У Java он измерен (см. выше), у Go — нет. Механизм не установлен; JIT-прогрев — гипотеза.

Ни один из трёх вкладов этот стенд не изолирует. **Что можно утверждать
честно** — направление эффекта воспроизводится в обоих клиентах, на обоих
образах, в обеих ориентациях: маленький пул под контеншном даёт кратно
больше отказов, чем пул размером с конкурентность.

**Побочное наблюдение (выброс, не результат).** В одном прогоне из 12
(`ops-java-redis.log`, прямая ориентация, повтор 3, size=50)
`overall_elapsed` составил **3782мс** против ~420мс во всех остальных
армах size=50 — throughput 2644 ops/s против ~24000. При этом среднее на
попытку осталось нормальным (2.091мс), то есть встала не работа, а
wall-clock всей армы — разовый стопор среды (JVM/WSL2/планировщик).
Механизм не установлен; в выводы не берётся, но и не вычищен из лога.

### Backup/restore: методология и результат

`ops/ops-demo.sh <образ>`: свежий `redis-master`, сеет 300×20=6000 событий
через `dataset/` (+1 zset `events:by-ts` = 6001 ключ), снимает **живой**
снапшот через `redis-cli -h redis-master --rdb <файл>` (SYNC по сети, без
`docker exec`/`BGSAVE`+`docker cp` — так проще и не требует доступа к
файловой системе контейнера), затем:

1. `down -v` — уничтожает именованный volume целиком.
2. **Доказательство, что данные РЕАЛЬНО исчезли**: свежий `redis-master` на
   новом volume (тот же путь `down→up`, что и restore, но без
   восстановления файла) — `DBSIZE` и точечный ключ `event:user-00000:0`
   обязаны отсутствовать, иначе скрипт падает фатально. Подтверждено на
   обоих образах: `DBSIZE=0`, `EXISTS event:user-00000:0` = `0`.
3. Restore: свежесть тома **проверяется** (`docker volume inspect` обязан
   не найти его — иначе фатально: `docker volume create` молча вернул бы
   существующий том со старыми данными, и restore «восстановил» бы то, что
   и так лежало), затем `docker volume create` + копия `dump.rdb` в `/data`
   одноразовым `alpine`-контейнером **до** первого старта сервера.
4. Проверка: `DBSIZE` после restore == `DBSIZE` до backup **и** содержимое
   точечного ключа (`HGETALL`, отсортировано) побайтово совпадает с
   сохранённым до backup — независимые друг от друга проверки, обе
   фатальны при несовпадении.

| | `redis:8.8` | `valkey/valkey:8.1` |
|---|---|---|
| DBSIZE до backup | 6001 | 6001 |
| Размер снапшота | 717372 байт | 717373 байт |
| DBSIZE на доказательно-пустом инстансе | 0 | 0 |
| `event:user-00000:0` на доказательно-пустом инстансе | отсутствует | отсутствует |
| Строка загрузки при restore | `Done loading RDB, keys loaded: 6001, keys expired: 0` | `Done loading RDB, keys loaded: 6001, keys expired: 0` |
| DBSIZE после restore | 6001 | 6001 |
| Содержимое `event:user-00000:0` после restore | побайтово совпало | побайтово совпало |

**Главная находка стенда, и это не гипотеза из документации, а
воспроизведённый живьём сбой.** `compose/base.yml` по умолчанию поднимает
`redis-master` с `--appendonly yes`. Если положить `dump.rdb` в **пустой**
volume (только сам файл, без каталога `appendonlydir`) и поднять сервер с
этим дефолтом, сервер **полностью игнорирует** наш `dump.rdb`: создаёт
пустой AOF base file и стартует с `DBSIZE=0`, **без единой ошибки или
предупреждения** — лог показывает только `BGSAVE done, 0 keys saved, 0
keys skipped, 88 bytes written` (сервер честно сохраняет пустое текущее
состояние, а не наше). Это ровно тот сценарий «restore молча ничего не
восстановил», о котором стоит предупреждать заранее — и он не бросается в
глаза без явной проверки `DBSIZE`. Обойти: `ops-demo.sh` поднимает сервер
для restore с `REDIS_APPENDONLY=no` — на этом же volume и с тем же файлом
это даёт `Done loading RDB, keys loaded: 6001` и корректный `DBSIZE`.
Практический вывод: план восстановления «положить `dump.rdb` в data dir и
поднять сервис» **молча не работает**, если AOF включён конфигом по
умолчанию — нужно либо временно выключить `appendonly` на время загрузки,
либо убедиться, что каталога `appendonlydir` нет до первого старта.

**Оговорка про `--rdb`-снапшот.** `redis-cli --rdb` — это SYNC-снимок на
момент запроса; если между `SET`-ами датасета и снапшотом на сервере шла
запись от кого-то ещё, снапшот отражает состояние на момент завершения
передачи, а не строго момент вызова команды. В этом стенде между севом и
снапшотом никто больше не писал (единственный клиент — сам скрипт), так
что это не повлияло на результат, но это НЕ гарантия «снапшот = момент T»
в общем случае, а частный факт про изолированный прогон.

### Мониторинг: живые сигналы (SLOWLOG/LATENCY/CLIENT LIST)

`ops-stand/go -scenario monitoring`: `CONFIG SET
latency-monitor-threshold 1`, `slowlog-log-slower-than 1000` (1мс, явно
занижено против дефолтных 10мс), затем — гарантированно медленная реальная
операция: `KEYS ops:mon:scan:*` над 300000 предварительно засеянными
одноразовыми ключами (не `DEBUG SLEEP` — он заблокирован на
непривилегированных инстансах: `enable-debug-command` — protected config,
неизменяем через `CONFIG SET` даже с правами по умолчанию, проверено
живьём: `ERR CONFIG SET failed ... can't set immutable config`).

| | `redis:8.8` | `valkey/valkey:8.1` |
|---|---|---|
| Клиентское время `KEYS` (round-trip) | 65.386мс | 53.632мс |
| `SLOWLOG GET`: время `KEYS` (серверный таймер) | 38561мкс (**38.6мс**) | 25328мкс (**25.3мс**) |
| `KEYS` попал в `SLOWLOG`? | **да** | **да** |
| `KEYS` попал в `LATENCY HISTORY command`? | **НЕТ** | **НЕТ** |
| `LATENCY HISTORY command` фактически | `[[1784206322 410] [1784206323 313]]` — 2 записи: сев (411мс) и очистка (314мс) | `[[1784206361 402]]` — **1 запись**: сев (402мс) |
| `LATENCY LATEST` | `command`/`aof-write`/`aof-write-alone` | `command`/`aof-write`/`aof-write-alone` |

**Находка: `SLOWLOG` поймал `KEYS`, а `LATENCY HISTORY` — нет. Это не сбой
стенда, а устройство latency-monitor, и это ловушка.** Latency-monitor
хранит по событию **максимум за секунду**, а не каждое событие. `KEYS`
(38.6мс) исполнился в ту же секунду `1784206322`, что и сев (411мс) —
максимум забрал сев, и `KEYS` в историю **не попал вообще**. На `valkey`
видно ещё нагляднее: сев (402мс), `KEYS` (25.3мс) и очистка (274мс) все
уложились в одну секунду `1784206361`, и `LATENCY HISTORY` содержит
**одну-единственную запись** — три команды, один максимум.

Практический вывод, который стоит унести: **`LATENCY HISTORY` — не журнал
команд.** Медленная команда, попавшая в одну секунду с более медленной
соседкой, в нём не появится, и её отсутствие там **ничего не доказывает**.
Для «какая команда тормозила» — `SLOWLOG` (у него отдельная запись на
команду); `LATENCY HISTORY` отвечает на другой вопрос — «насколько плохо
было в секунду N». Первая редакция этого раздела утверждала, что `KEYS`
пойман обоими механизмами — **снято как неверное**, опровергается
собственным логом стенда (`ops-redis.log`, `ops-valkey.log`).

**`KEYS` над 300000 ключами — однопоточная O(N) операция**, и 38.6мс
серверного времени — это время, в течение которого сервер занят только ей.
Тот же механизм виден и на севе/очистке (`EVAL`-цикл на 300000 ключей —
411мс/314мс в `SLOWLOG`). Оговорка: конкурентных клиентов во время `KEYS`
стенд **не запускал**, то есть «все остальные запросы ждали» здесь —
известное свойство однопоточного цикла событий, а не отдельно
**измеренный** в этом прогоне факт. Измерено: сколько сервер занят.

Клиентское время `KEYS` (65.4мс) заметно больше серверного (38.6мс) —
разница уходит на передачу 300000 строк по сети клиенту, а не на
исполнение. **Абсолюты — Docker Desktop на Windows** (см. оговорку в
начале раздела), не нативный Redis.

### Что стенд НЕ измерял

- **Латентность при разных размерах пула — сравнимо.** Выборки успешных
  операций цензурированы по-разному (46.7% против 100% на Go, ~22% против
  100% на Java), и Java-арма даёт обратный порядок p50 относительно Go —
  см. «латентность» выше. Стенд честно меряет только **долю отказов**.
- **Пропускную способность пула под РЕАЛЬНЫМ (не искусственно тесным)
  `PoolTimeout`** — прод-значения на порядок выше 2мс, и там таймаутов
  почти не будет при такой латентности `SET`; стенд специально сузил порог,
  чтобы получить измеримый контраст на утилите быстрого локального Redis.
- **Что именно** в разнице Go/Java (WSL2-сеть vs нативный хост, семафор vs
  commons-pool2, прогрев JVM) даёт больший вклад — три оси разом, стенд их
  не развязывает (см. оговорку выше).
- **Механизм эффекта порядка на Java-стороне** — факт наличия измерен
  (≈8 п.п. между ориентациями), JIT-прогрев остаётся гипотезой.
- **Чередование серий (interleaving).** Тот же блочный дизайн, что и у
  Стенда #6: обе ориентации прогнаны, но внутри каждой ориентации серии идут
  блоком, а не вперемешку — медленный дрейф среды/JVM внутри блока не
  скомпенсирован. Этому стенду раскрытие нужнее, чем Стенду #6: здесь
  реально найден эффект порядка (≈8 п.п. на Java), и часть его в принципе
  могла быть session drift, а не позицией арм. Есть аргумент **против**
  чистого дрейфа: size=50 (арма без единого pool timeout — контеншн тут
  роли не играет) даёт `overall_elapsed` **634/569/588мс**, когда это
  **первая** арма в обратной ориентации (более позднем по времени блоке),
  против **~420мс**, когда это **последняя** арма в прямой ориентации
  (более раннем блоке) — `ops-java-redis.log`. Если бы дело было в чистом
  дрейфе среды по времени (независимо от позиции), связь с позицией арм
  внутри двух отдельных JVM-прогонов была бы совпадением; устойчивая
  привязка разницы именно к позиции (первая/последняя), повторившаяся в 3
  повторах каждой ориентации на обоих образах, лучше согласуется с
  эффектом порядка (прогрев JIT), чем с монотонным дрейфом хоста по
  часам. Это не доказательство — оба фактора могли действовать вместе.
- **Блокировку конкурентных клиентов во время `KEYS`** — стенд меряет
  время занятости сервера, но параллельных клиентов в этот момент не
  запускал.
- **`BGSAVE`+`docker cp`-путь backup** — задание допускало оба варианта
  (`redis-cli --rdb` или `BGSAVE`+копия из volume), стенд использует только
  первый (не требует доступа к файловой системе контейнера).
- **Восстановление на ДРУГОЙ версии/образе**, чем снят снапшот (redis→valkey
  или наоборот) — не проверялось, снапшот и восстановление всегда на одном
  и том же образе в рамках одного прогона `ops-demo.sh`.
- **AOF-совместимый путь restore** (переиграть AOF поверх RDB-базы) — стенд
  проверяет только чистый RDB-restore с временно выключенным AOF.

Реальные команды воспроизведения — в `README.md`, раздел «Стенд #7».
