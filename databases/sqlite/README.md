# sqlite

Стенд к статье «SQLite и встраиваемые БД: когда файл бьёт сервер» (`databases/sqlite-embedded-databases`).

## Что показывает стенд

Три плеча в одном бинарнике `bench` (SQLite-файл на локальном диске,
Postgres через unix-сокет, Postgres через TCP по Docker bridge-сети между
контейнерами `bench` и `postgres` — это не loopback, серверы разные
контейнеры) плюс отдельный
бинарник `olap` (SQLite vs DuckDB на одинаково засеянном наборе). Четыре
сценария:

1. **Латентность и цена сетевого хопа** (`run-latency.sh`) — чтение/вставка
   по трём плечам, при полной и ослабленной долговечности.
2. **Граница одного писателя** (`run-writers.sh`) — рост числа конкурентных
   писателей от 1 до 16, две согласованные по гарантии пары (SQLite
   NORMAL / Postgres off и SQLite FULL / Postgres on).
3. **Отказоустойчивость с litestream** (`run-restore.sh`,
   `run-restore-app-only.sh`) — сколько строк теряется при одновременной
   гибели писателя и репликатора при сохранном объектном хранилище (bench
   и litestream убиваются одной командой `docker kill`, MinIO остаётся жив
   в том же Compose-проекте) против гибели только приложения (litestream
   жив и дотягивает хвост WAL). Это НЕ модель гибели хоста целиком — та
   унесла бы и MinIO тоже.
4. **SQLite vs DuckDB** (`run-olap.sh`) — аналитическая агрегация по 1 млн
   строк (профиль колоночного хранения) и точечное чтение по первичному
   ключу (профиль строкового хранения), с `EXPLAIN QUERY PLAN` для SQLite.

## Запуск

```bash
cd databases/sqlite
docker compose up -d --build
bash scripts/smoke.sh
```

`smoke.sh` обязателен перед остальными сценариями: проверяет, что оба плеча
Postgres (TCP и unix-сокет) реально ведут в один и тот же сервер
(`system_identifier`) — иначе сравнение TCP/UDS было бы бессмысленным.

⚠️ **litestream поднимается вместе со стендом** (`docker compose up -d`
стартует его как обычный сервис) и работает непрерывно — тикает раз в
секунду и участвует в чекпойнтах WAL всё то время, пока идут остальные
сценарии. У Postgres-плеч сопоставимого сайдкара нет. Для латентности и
писателей это посторонняя нагрузка на плечо SQLite, которой нет у
соперника: для чистого сравнения останавливайте его перед замером
(`docker compose stop litestream`) и поднимайте обратно, когда он снова
нужен (`docker compose start litestream`) — сценарий 3 без него не имеет
смысла, поднимайте перед ним обязательно.

**Порядок сценариев и сброс состояния.** Все четыре сценария пишут в
общий `SQLITE_PATH=/data/bench.db` (том `benchdata`), поэтому они не
независимы: `run-writers.sh` и `run-restore*.sh` оставляют в таблице
`events` сотни тысяч строк, и следующий сценарий меряется уже на другой,
не пустой базе. `run-restore.sh` в частности оставляет после
восстановления около четверти миллиона строк — если запустить
`run-latency.sh` сразу после него, читается уже прогретая и заметно
большая база, а не та, что описана в разделе 1. Рекомендуемый порядок:

```bash
docker compose down -v && docker compose up -d --build
bash scripts/smoke.sh
bash scripts/run-latency.sh
docker compose down -v && docker compose up -d --build   # сброс перед следующим сценарием
bash scripts/run-writers.sh
docker compose down -v && docker compose up -d --build
bash scripts/run-restore.sh
docker compose down -v && docker compose up -d --build
bash scripts/run-restore-app-only.sh
docker compose down -v && docker compose up -d --build
bash scripts/run-olap.sh
```

**Именование фикстур.** Каждый `run-*.sh` пишет в `fixtures/<имя>.txt` по
умолчанию (например, `run-latency.sh` → `fixtures/latency.txt`), но
допускает переопределение через переменную окружения `OUT`, что и
позволяет сохранить несколько независимых прогонов без перезаписи:

```bash
OUT=fixtures/latency-run2.txt bash scripts/run-latency.sh
```

Файлы `latency-run1.txt`/`latency-run2.txt`, `restore-run1.txt` —
`restore-run3.txt` в этом репозитории — результат именно такого
переопределения `OUT` на нескольких прогонах одного и того же сценария,
не отдельные скрипты.

Остановка:

```bash
docker compose down -v
```

### Windows / Git Bash

Запускайте скрипты с `MSYS_NO_PATHCONV=1` — без этого Git Bash перегоняет
POSIX-подобные аргументы (`/var/run/postgresql`, `/data/bench.db` и т. п.)
через путепреобразование MSYS, и это ломает сами скрипты изнутри, а не
только сырые команды `docker run` с явными путями. Все `scripts/*.sh`
выставляют `export MSYS_NO_PATHCONV=1` сами, но если вызываете `docker
compose exec` вручную — выставьте переменную в своей сессии:

```bash
export MSYS_NO_PATHCONV=1
```

## Сценарии

Каждый скрипт запускается с хоста (через `docker compose exec`), пишет
фикстуру в `fixtures/` и работает в обеих формах записи:

### 1. Латентность и цена сетевого хопа

```bash
./scripts/run-latency.sh
bash scripts/run-latency.sh
```

Что смотреть: три круга по каждой комбинации плечо × операция × гарантия,
порядок плеч внутри круга ротируется по латинскому квадрату (см. функцию
`perm` в `run-latency.sh`: за три круга каждое плечо стоит на первой,
второй и третьей позиции ровно по разу). Чтение SQLite — характерно около
11–15 мкс p50 (48 910–68 550 оп/с), чтение Postgres через unix-сокет —
около 173–210 мкс, через TCP через bridge-сеть Docker — рядом, 190–218 мкс
(это не loopback: `bench` и `postgres` разные контейнеры). Разрыв
SQLite/Postgres без всякой сети (сокет) — больше порядка величины: 12.6–19.1
раза по p50 в каждом из шести кругов.

Цену самого сетевого хопа (TCP минус unix-сокет) НЕ УДАЛОСЬ назвать числом:
по шести кругам (`latency-run1.txt`, `latency-run2.txt`) разница дала −9,
+20, +12, +8, +13, +20 мкс — знак меняется, в одном круге TCP оказался
быстрее сокета. Это не позиционный артефакт ротации (в том самом круге,
где знак перевернулся, порядок плеч совпал с порядком старой
нечередующейся методики, где хоп раньше стабильно давал +18…+20 мкс) — это
более шумное состояние хоста в данном прогоне: абсолютные числа сокета
выросли примерно на четверть по сравнению с более ранними замерами той же
серии. На фоне этого шума цена хопа в bridge-сети Docker неразличима.
Остаток разницы между SQLite и Postgres — это не только клиент-серверный
слой, но и различия самих движков (MVCC и планировщик Postgres против
более простой модели SQLite); стенд не умеет разделить эти два вклада
порознь, и с учётом шума в сетевом хопе делить их дальше смысла нет.

При полной долговечности (`synchronous=FULL` / `synchronous_commit=on`)
вставка сходится у всех трёх плеч к 1.91–2.04 мс p50, и по пропускной
способности SQLite (426–464 оп/с) на каждом круге чуть уступает обоим
Postgres-плечам (476–539 оп/с) — здесь fsync доминирует, и преимущества у
SQLite нет.

Контрольный прогон с остановленным litestream
(`fixtures/latency-no-litestream.txt`) переснят на той же сбалансированной
ротации, что и основной (seed 777, латинский квадрат; более ранняя версия
этого файла использовала нечередующийся порядок и сравнивать её напрямую
с ротированным основным прогоном было бы той же методической ошибкой, из-за
которой пришлось переснимать latency-run1/run2 — старая версия заменена
целиком). Litestream остановлен командой `docker compose stop litestream`,
остальные сервисы стенда работали как обычно, после замера litestream
запущен обратно.

Результат: SQLite — 460–475 оп/с по трём кругам, Postgres — 466–544 оп/с
(нижняя граница — один просевший круг у pg-uds, p99 которого подскочил до
6.3 мс; в двух остальных кругах Postgres держится на 538–544). SQLite
проигрывает в каждом из трёх кругов контроля, включая просевший. Разрыв по
кругам тем же методом, что и в основном прогоне (ops/sec SQLite круга
против среднего ops/sec двух Postgres-плеч того же круга, не «лучший
SQLite против худшего Postgres» — так вышла бы заниженная оценка) — 12.6%,
5.4%, 14.8% (в среднем около 10.9%) — против 12.6–15.8% (в среднем около
13.8%) в основном прогоне при живом litestream. Диапазоны пересекаются, но
не совпадают: без litestream средний разрыв не вырос, а слегка сократился,
и то за счёт одного шумного круга Postgres, а не ускорения SQLite. Если бы
сайдкар litestream объяснял отставание SQLite, его остановка должна была
бы заметно сузить разрыв — вместо этого SQLite тем же порядком величины
проигрывает и без litestream. Но это отдельный трёхкруговой прогон на
другом, более шумном состоянии хоста, а не парный A/B-тест на одинаковых
условиях — полностью исключить влияние сайдкара он не может. Из него
следует ровно одно: контроль не подтвердил, что litestream объясняет
наблюдаемое отставание SQLite. Более ранняя формулировка «разрыв
практически тот же» сравнивала данные разных методик ротации и снята;
формулировка «litestream ни при чём» была бы той же ошибкой в другой
форме — отсутствие подтверждения не равно доказательству невиновности.

### 2. Граница одного писателя

```bash
./scripts/run-writers.sh
bash scripts/run-writers.sh
```

Что смотреть: `busy_errors` и `ops_per_sec` по мере роста числа писателей
(1 → 16) в двух парах, согласованных по гарантии долговечности. При полной
долговечности пропускная способность SQLite падает с ростом конкуренции
(480 → 419 операций/с на характерном прогоне), а не растёт: ошибки
блокировки (`SQLITE_BUSY`) появляются уже при 2 писателях. У Postgres в той
же паре пропускная способность растёт (554 → 4646). На ослабленной гарантии
Postgres обгоняет SQLite уже при 4 писателях (19423 против 17298
операций/с) — контрольный прогон с `busy-timeout 0` в конце файла
подтверждает, что рост `busy_errors` не артефакт таймаута.

История методики: первая версия этого замера сравнивала пары с разными
гарантиями (SQLite `synchronous=NORMAL` против Postgres
`synchronous_commit=on`) и прятала границу — SQLite с ослабленной гарантией
успевал отработать запрос до столкновения с другим писателем чаще, чем против
равного по гарантии соперника. Таблицы в статье — после выравнивания пар.

### 3. Отказоустойчивость с litestream

```bash
./scripts/run-restore.sh
bash scripts/run-restore.sh

./scripts/run-restore-app-only.sh
bash scripts/run-restore-app-only.sh
```

Что смотреть: строку «потеряно: N» в конце фикстуры. Одновременное убийство
писателя и репликатора при сохранном объектном хранилище (`run-restore.sh`
убивает bench и litestream одним `docker kill`, MinIO остаётся жив в том же
Compose-проекте) стабильно теряет данные — по трём прогонам потеряно от 2216
до 5593 строк (реплика не успевает дотянуть хвост WAL, который не пережил
SIGKILL вместе с источником). Это НЕ гибель хоста целиком — та унесла бы и
MinIO, и восстанавливать было бы уже неоткуда; сценарий моделирует отказ
приложения/узла при удалённом (внешнем) объектном хранилище. Гибель только
приложения (`run-restore-app-only.sh`, litestream остаётся жив) в единственном
прогоне потеряла 0 строк — живой litestream досинхронизирует хвост сам, без
нашего участия; это один прогон, а не диапазон по нескольким кругам, как для
сценария выше.

⚠️ Приём с одновременным убийством контейнеров (`docker kill id1 id2` одной
командой — но команда одна, а не гарантия атомарности между двумя SIGKILL)
проверен только на Windows/Git Bash. На другой платформе поведение `docker
kill` с несколькими ID стоит перепроверить перед тем, как опираться на
числа.

### 4. SQLite vs DuckDB

```bash
./scripts/run-olap.sh
bash scripts/run-olap.sh
```

Что смотреть: `EXPLAIN QUERY PLAN` перед числами показывает, какой план
выбрал SQLite (по умолчанию — `SCAN events USING INDEX idx_events_user`; с
`NOT INDEXED` — полный скан с `TEMP B-TREE FOR GROUP BY`). На характерном
прогоне на этой машине: агрегация по индексу — 1448910 мкс p50, агрегация
без индекса — 395264 мкс, агрегация DuckDB — 2578 мкс. Эффект плана (индекс
против его отсутствия у SQLite) — по порядку величины около 3.7 раза;
разрыв между движками на агрегации (SQLite без индекса против DuckDB) — по
порядку величины около 153 раз — на этом запросе и на этом стенде; колоночная
раскладка DuckDB — вероятная, но не доказанная здесь причина, поскольку
сравниваются два целиком разных движка (планировщик, исполнитель), а не
чистый эффект ориентации хранения. Эти множители — оценка порядка на 10 замерах
(`p95`/`p99` для агрегации не публикуются намеренно: при `n=10` метод
nearest-rank даёт один и тот же индекс для обоих перцентилей), их
перемножать не нужно — это не одно измерение, а два разных эффекта на
разных выборках. Точечное чтение по первичному ключу — обратная картина:
SQLite около 8 мкс p50 против DuckDB около 636 мкс — колоночный движок
платит за поиск одной строки.

## Известные ограничения

- Таблица Postgres в сценарии латентности общая для обоих плеч (UDS и TCP) —
  на хвосты (`p95`/`p99`) вставок опираться не стоит, обе конкурируют за
  одну и ту же строку/таблицу; для медиан (`p50`) и порядка величины это не
  критично.
- Приём одновременного убийства контейнеров в сценарии отказа проверен
  только на Windows — см. предупреждение в разделе 3.
- litestream работает непрерывно рядом со стендом — постороннняя нагрузка на
  плечо SQLite в сценариях латентности и писателей, которой нет у Postgres.
  Контрольный прогон с остановленным litestream (`fixtures/latency-no-litestream.txt`,
  та же ротация, что и в основном прогоне) даёт SQLite тот же порядок
  отставания от Postgres (5.4-14.8% по кругам против 12.6-15.8% в основном
  прогоне — диапазоны пересекаются, средний разрыв без litestream не растёт,
  а слегка ниже) — см. раздел 1. Если меняете стенд или сценарий, контроль
  стоит переснять, а не полагаться на этот один раз.
- Абсолютные числа (латентность, ops/sec, стоимость fsync) — характерный
  прогон на одной машине (Docker Desktop на Windows). Опирайтесь на порядок
  разрыва и на то, сходятся ли плечи, а не на миллисекунды как на константу.
