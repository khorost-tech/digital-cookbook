# FIXTURES — реальные выводы прогонов стенда databases/cockroachdb

Единственный источник чисел для серии «CockroachDB: глубокое погружение»
(семь статей в `databases/`). Всё, чего здесь нет, в статьях появиться не может;
всё, что здесь есть, получено живым прогоном на этой машине, а не переписано
из документации или из отчётов по задачам.

**Дата прогонов: 2026-08-12.**
**Машина:** Windows 11 + WSL2 (Ubuntu 24.04), 16 ядер, 62 ГБ памяти, Docker 29.6.2,
compose v5.3.1. Все кластеры — в докере на одном хосте.

Абсолютные величины зависят от железа. Смысл имеют **соотношения между режимами**,
а не сами значения.

### Ответы на вопросы фактчек-гейта

1. **SERIALIZABLE — уровень по умолчанию?** Да.
2. **READ COMMITTED принимается и остаётся им?** Да. Проверено поведением, а не настройкой:
   `BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED; SHOW transaction_isolation;` возвращает
   `read committed`. Молчаливого повышения до SERIALIZABLE нет.
3. **Минимальный `range_max_bytes`?** 64 МиБ (67108864 байт).

### Лицензия (проверено по документации 2026-08-12, перепроверить перед публикацией)

Self-hosted Core упразднён с версии 24.3. Многоузловой кластер без ключа работает
**7 дней**, дальше троттлится до 5 одновременных SQL-транзакций. Одноузловой dev-кластер
ключа не требует. На бесплатной лицензии телеметрия обязательна и отключению не подлежит.
Стенд эфемерный, в грейс укладывается; **троттлинг после грейса здесь не измерялся** —
для этого пришлось бы ждать неделю.

### Ловушка: node_id не равен номеру в имени контейнера

Идентификаторы узлов раздаются в порядке присоединения к кластеру. На этом стенде
в разных прогонах получалось, например:

```
container       node_id
crdb1:26257     1
crdb3:26257     2
crdb2:26257     3
```

Первая версия артефакта 01 гасила контейнер `crdb3`, считая аренды на `node_id = 3` —
то есть на живом узле. Замер давал «аренды не переезжают за 235 с», что неверно.
Все скрипты теперь спрашивают идентификатор у кластера (`node_id_of` в `lib.sh`)
и печатают соответствие первой строкой.

### Ловушка: crdb_internal закрыт

В 26.x обращение к `crdb_internal` и `system` отвергается:

```
ERROR: Access to crdb_internal and system is restricted.
HINT: These interfaces are unsupported in production. To proceed, set the session
variable allow_unsafe_internals = true (not recommended)
```

Все замеры переведены на поддерживаемые `SHOW CLUSTER RANGES ... WITH DETAILS`,
`SHOW RANGES FROM TABLE ... WITH DETAILS` и метрики `/_status/vars`.

## Артефакт 01 — архитектура: диапазоны, split, отказ узла

Команда: `bash scripts/01-ranges.sh`

### A. Распределение по трём узлам

```
node_id  replicas
1        62
2        62
3        62

lease_holder  leases
1             26
2             15
3             21
```

Реплики разложены строго поровну; аренды — неравномерно, потому что их распределение
зависит от того, кто и когда обращался к диапазону.

### B. Split под ростом таблицы

Таблица `bulk_rows` (`id INT8 PRIMARY KEY, payload STRING`), 700 000 строк по 256 байт,
зона `range_min_bytes = 32 МиБ, range_max_bytes = 64 МиБ` (меньше 64 МиБ поставить нельзя).

```
до налива:    диапазонов 1
после налива: диапазонов 6

range_id  size_mb  lease_holder  replicas
163       33.6     2             {1,2,3}
164       33.6     2             {1,2,3}
165       33.6     2             {1,2,3}
166       33.6     2             {1,2,3}
167       33.6     2             {1,2,3}
168       31.7     2             {1,2,3}
```

Диапазоны делятся примерно пополам от предельного размера (33.6 МиБ при пределе 64 МиБ).
Число диапазонов от прогона к прогону отличается — в более раннем прогоне на тех же
700 000 строках их вышло 5, причём последний дорос до 65.2 МиБ: деление асинхронно,
и к моменту замера оно может быть не закончено.

### C. Гашение узла-арендатора

Аренда диапазона с ключом `id = 1` явно переносится на узел, который будет погашен
(`ALTER RANGE <id> RELOCATE LEASE TO <node>`), затем контейнер останавливается,
а пробник в цикле читает этот самый ключ.

```
проб всего: 268 (успешных: 268, неуспешных: 0)
максимальный разрыв между успешными чтениями: 2.2 с
проб с явной ошибкой: 0
```

Разрыв по четырём прогонам: **1.1 с, 1.7 с, 1.7 с, 2.2 с**. Клиент не получил ни одной ошибки —
пауза прошла для него незаметно. Аренда целевого диапазона после гашения оказалась
на живом узле.

**Отрицательный результат.** Вопрос «за сколько аренды покидают мёртвый узел» этим
инструментом не отвечается: счётчик аренд на погашенном узле обнуляется мгновенно
(0 с на первом же опросе), потому что недоступный узел просто перестаёт фигурировать
в `SHOW CLUSTER RANGES`. Ноль здесь означает отсутствие данных, а не завершённую
миграцию.

## Артефакт 02 — время: HLC, follower reads, сборка мусора

Команда: `bash scripts/02-time.sh`

### A. Отставание closed timestamp

```
4.200
4.200
4.200
4.200
4.200
```

Секунды, пять замеров подряд, `SELECT now() - follower_read_timestamp()`. Величина
ровно выводится из настроек: `target_duration` 3 с + `propagation_slack` 1 с +
`side_transport_interval` 0.2 с = 4.2 с.

### B. Чтение с leaseholder против follower read

**Сначала — подтверждение, что читала реплика.** `AS OF SYSTEM TIME
follower_read_timestamp()` задаёт лишь метку в прошлом; обслужить такой запрос может и
арендатор. Признак — счётчик `follower_reads_success_count`:

```
повторов, где счётчик вырос: на обычном чтении 0 из 7, на follower 7 из 7
прирост на follower-запрос: +21…+25
historical в плане: присутствует во всех follower-запросах
```

Обслуживание репликой подтверждено, обычное чтение к ней не обращалось ни разу.

**Latency — неустойчива.** Два прогона дали противоположный порядок (режимы
чередуются, по 7 повторов):

```
прогон 1:  обычное 212, 231, 249, 227, 195, 201, 198   медиана 212
           follower 388, 257, 292, 233, 252, 237, 237  медиана 252

прогон 2:  обычное 619, 656, 768, 317, 1700, 221, 251  медиана 619
           follower 507, 792, 313, 321, 364, 264, 259  медиана 321
```

Во втором прогоне машина была занята соседними профилями, разброс на обычном чтении —
от 221 мс до 1.7 с. **Вывод: на этом стенде latency двух режимов устойчиво не
различается.** Прежнее утверждение «follower read медленнее» опиралось на один прогон
и снято.

### C. Глубина AS OF SYSTEM TIME

```
-10s:  ЧИТАЕТСЯ
-1m:   ЧИТАЕТСЯ
-10m:  ЧИТАЕТСЯ
-30m:  ЧИТАЕТСЯ
-1h:   ОТКАЗ — таблицы в тот момент ещё не было (возраст стенда, а не GC)
-2h:   ОТКАЗ — таблицы в тот момент ещё не было
-4h:   ОТКАЗ — таблицы в тот момент ещё не было
-5h:   ОТКАЗ — таблицы в тот момент ещё не было
```

Текст отказа — `ERROR: relation "bulk_rows" does not exist`. Это **возраст таблицы**,
а не порог сборки мусора. Первая версия замера печатала только «отказ» и выдавала бы
границу стенда за свойство СУБД.

### C2. Порог сборки мусора ленив

Таблица `gc_probe`, `gc.ttlseconds` опущен до 30 с, пять поколений версий, ожидание 300 с:

```
-30s: ЧИТАЕТСЯ (снимок старше порога, но версии ещё не собраны)
-1m:  ЧИТАЕТСЯ
-2m:  ЧИТАЕТСЯ
-3m:  ЧИТАЕТСЯ
-5m:  ОТКАЗ — порог GC уехал вперёд
```

При пороге в 30 секунд снимок трёхминутной давности читается, пятиминутный — уже нет.
**`gc.ttlseconds` задаёт минимальную гарантию хранения версий, а не момент, с которого
чтение в прошлом перестаёт работать.** Реальный горизонт зависит от того, дошёл ли
сборщик до этих диапазонов; он ходит по объёму мусора, а не по таймеру.

В более раннем прогоне (ожидание те же 300 с, но сразу после понижения порога) читался
и снимок `-5m` — то есть порог сдвигается с задержкой в разы относительно ttl.

### D. Uncertainty restarts — ноль, и это результат

Кластер перезапущен с `--max-offset=2s` (дефолт — 500 мс), применение подтверждено
проверкой аргументов запуска. Писатель на `crdb1`, читатель на `crdb2`, 30 секунд:

```
писатель: {"mode":"hot","ops":2100,"retries":0,"p50_ms":108.1,"p99_ms":164.6}
читатель: {"mode":"read-hot","ops":15024,"retries":0,"p50_ms":14.5,"p99_ms":44.2}

txn_restarts_readwithinuncertainty до:    0
txn_restarts_readwithinuncertainty после: 0 (прирост 0)
```

Нагрузка состоялась — 15 024 операции чтения через отдельный узел-шлюз. Ретраев
по неопределённости нет.

**Почему их нет и почему это невоспроизводимо на одной машине.** Цепочка проверена,
а не взята из памяти:

1. Все контейнеры делят `CLOCK_REALTIME` ядра хоста — расхождение равно нулю, и
   попадать в окно неопределённости нечему, каким бы широким его ни сделать.
2. `CLONE_NEWTIME` (time namespace) в Linux виртуализирует только монотонные часы,
   не реальные.
3. `libfaketime` перехватывает вызовы libc и на Go-бинарь не действует. Проверено
   опытом в контейнере `almalinux:10`:

```
обычный date:       2026-08-12T06:11:26Z
faketime +10h date: 2026-08-12T16:11:26Z     <- C-бинарь сдвинулся
обычный Go:         2026-08-12T06:11:26Z
faketime +10h Go:   2026-08-12T06:11:26Z     <- Go не сдвинулся
```

CockroachDB написан на Go. **Вывод для статьи: uncertainty-ретраи — симптом настоящего
распределённого развёртывания с независимыми часами, а не свойство распределённой СУБД
как таковой.** Защитная остановка узла при выходе часов за предел по той же причине
не измерялась.

## Артефакт 03 — распределённые транзакции

Команда: `bash scripts/03-txn.sh`

### A. Однооператорная запись в горячую строку

`UPDATE hot_counter SET hits = hits + 1 WHERE id = 1`, по 30 секунд:

| Воркеров | ops | retries | p50, мс | p99, мс |
|---|---|---|---|---|
| 1 | 2926 | 0 | 9.5 | 19.1 |
| 4 | 3026 | 0 | 37.9 | 55.1 |
| 16 | 2986 | 0 | 156.6 | 211.3 |
| 32 | 3010 | 0 | 314.5 | 393.5 |

**Ретраев ноль при любой конкуренции.** Пропускная способность упирается в потолок,
задержка растёт линейно: конкуренты не отменяются, а встают в очередь на ключе.

### B. Прочитал — записал прочитанное (SERIALIZABLE)

`SELECT hits ...` затем `UPDATE ... SET hits = <прочитанное+1>`, по 30 секунд:

| Воркеров | ops | повторов у клиента | отвалилось | прирост `writetooold` | p50, мс | p99, мс |
|---|---|---|---|---|---|---|
| 1 | 2559 | 0 | 0 | 0 | 10.2 | 24.0 |
| 4 | 1725 | 1859 | 17 | +1877 | 53.9 | 285.7 |
| 16 | 1255 | 6679 | 244 | +6928 | 176.7 | 756.5 |
| 32 | 747 | 9324 | 680 | +10020 | 288.3 | 947.5 |

Прирост серверного счётчика снят **до и после каждого прогона отдельно**. Остальные
четыре класса (`serializable`, `txnpush`, `txnaborted`, `readwithinuncertainty`) не
сдвинулись ни разу.

Клиентские повторы и серверные перезапуски систематически расходятся: 1859 против 1877,
6679 против 6928, 9324 против 10020. Сервер считает больше — это разные величины.

«Отвалилось» — транзакции, исчерпавшие предел в 10 повторов.

**ОТОЗВАНО (ревью 2026-08-12).** Здесь стояла таблица `txn.restarts.*` с абсолютным
значением `writetooold = 48781`, снятая **один раз после всех прогонов**. Это
накопительный счётчик с момента старта узла: приписывать его одному замеру нельзя,
в него входили все предыдущие прогоны раздела.

Дополнительно: серверный `txn.restarts.*` и клиентский счётчик повторов — **разные
величины** и совпадать не обязаны. Клиент считает итерации своего retry-цикла, сервер —
перезапуски транзакций, включая внутренние, которых клиент не видит.

Скрипт переписан: счётчики снимаются до и после **каждого** прогона, печатается только
прирост. Числа будут внесены после перепрогона.

### C. SERIALIZABLE против READ COMMITTED — цена отсутствия ретраев

Одна и та же нагрузка, 16 воркеров, 30 секунд. Счётчик обнуляется перед каждым замером
и обязан совпасть с числом подтверждённых транзакций:

| Уровень | ops | повторов | отвалилось | счётчик | коды ошибок | итог |
|---|---|---|---|---|---|---|
| SERIALIZABLE | 1327 | 6911 | 236 | 1327 | `other:236` | расхождения нет |
| READ COMMITTED | 1209 | **0** | **0** | **76** | нет | **потеряно 1133** |

Под READ COMMITTED — ноль неуспешных транзакций и пустой список кодов: потери
происходят молча, приложение о них не узнаёт.

**Расхождение в бо́льшую сторону наблюдалось не всегда.** В более раннем прогоне счётчик
оказался 1293 при 1292 подтверждённых транзакциях (+1); в этом прогоне расхождения нет
вовсе. Кода `40003` не было ни разу, поэтому неоднозначным коммитом это не объявляется.

`other:266` под SERIALIZABLE — это транзакции, исчерпавшие предел в десять повторов
(ошибка генератора, не сервера). Кода `40003` нет, поэтому расхождение в единицу
неоднозначным коммитом **не объявляется**.

READ COMMITTED убирает ретраи полностью — и теряет **94 %** инкрементов.

**Расхождение счётчика в бо́льшую сторону — НЕ доказанный неоднозначный коммит
(ревью 2026-08-12).** В одном из прогонов под SERIALIZABLE счётчик оказался 2004 при
2003 подтверждённых транзакциях. Прежняя редакция объявляла это неоднозначным коммитом,
не проверяя ничего: ни `SQLSTATE`, ни этап, на котором отвалилась транзакция, ни наличие
сетевого сбоя. Тот же результат совместим с завершением по контексту и с особенностями
клиентского учёта.

Что сделано: генератор нагрузки теперь собирает `SQLSTATE` **всех** неуспешных
транзакций, а неоднозначный коммит объявляется только при наличии кода `40003`
(`statement_completion_unknown`). Если его нет — печатается «причина не установлена».

Чего по-прежнему нет: управляемой инъекции сбоя (обрыв соединения в момент коммита).
Без неё явление не воспроизводится по требованию, а только наблюдается случайно.

### D. Форма первичного ключа при одном диапазоне — замер несостоятелен

45–68 тысяч узких строк, обе таблицы остаются в **одном диапазоне**:

| Прогон | `insert-seq` | `insert-uuid` | Отношение |
|---|---|---|---|
| первый | 68697 | 66869 | 1.03 |
| второй | 62939 | 61048 | 1.03 |
| третий | **41088** | **69907** | **1.70 в пользу UUID** |

У обеих таблиц во всех прогонах по одному диапазону. **Замер нестабилен**: первые два
прогона читались бы как «разницы нет», третий — как «UUID быстрее почти вдвое».
Прежняя формулировка «при одном диапазоне разницы быть не может» опровергнута третьим
прогоном и снята.

Что здесь на самом деле не так. Горячий хвост при одном диапазоне НИКУДА НЕ ДЕВАЕТСЯ:
монотонные вставки по-прежнему бьют в один конец ключевого пространства. Не существует
другого — возможности ИЗМЕРИТЬ выигрыш от распределения записи между диапазонами, потому
что распределять не по чему. Прежняя формулировка «горячего хвоста не существует, когда
хвост один на всю таблицу» смешивала эти два утверждения и снята. Замер оставлен
намеренно: он ловит распространённое заблуждение.

### D2/D3. Форма ключа: крупного штрафа за монотонность не обнаружено

**ПЕРЕДЕЛАНО после ревью 2026-08-13.** Две предыдущие редакции сообщали разницу
в 8–9 и в 10–12 раз. Обе неверны: сравнивались не формы ключа.

Смешение 1 — место генерации. `mono` брал значение из серверного `nextval()`,
`randint` — с клиента. Различались место генерации, форма `INSERT`, число
параметров и конкуренция за последовательность.

Смешение 2 — состояние таблиц. Между раундами таблицы не очищались, режим,
отработавший последним, стартовал на самой большой таблице.

Исправленная постановка: у всех трёх вариантов ключ генерируется НА КЛИЕНТЕ и
уходит одним и тем же `INSERT` с тремя параметрами.

- `acct_mono` — `INT8`, атомарный счётчик клиента (продолжается с `max(id)`);
- `acct_randint` — `INT8`, `rnd.Int63()`;
- `acct_rand` — `UUID` v4, собран на клиенте.

Пара mono/randint различается прежде всего порядком, пара randint/rand — типом и
размером. Слово «изолирует» здесь неуместно: генераторы у всех трёх разные и работают
ВНУТРИ измеряемой транзакции, так что сравниваются три клиентские стратегии целиком.

#### D2. Равные условия: крупного штрафа не обнаружено

Таблицы очищаются и переразбиваются перед КАЖДЫМ прогоном. 16 воркеров, 45 с,
три раунда с циклическим сдвигом порядка:

| Раунд | Монотонный INT8 | Случайный INT8 | UUID |
|---|---|---|---|
| 1 | 60340 | 54438 | 60202 |
| 2 | 43933 | 43549 | 44076 |
| 3 | 44341 | 43778 | 43846 |

Крупного штрафа именно за монотонность не обнаружено. Говорить «крупной разницы между
формами ключа нет» нельзя: в первом раунде разброс достигает 10.8 %, и он не в ту
сторону, о которой предупреждает совет.

**Но знак ДЕРЖИТСЯ**, и в предыдущей редакции здесь стояло обратное. Ниже всех во всех
трёх раундах оказывается контрольный случайный INT8: монотонный выше его на 10.8 / 0.9 /
1.3 %, UUID — на 10.6 / 1.2 / 0.2 %. Между монотонным и UUID знак действительно меняется:
+0.2 / -0.3 / +1.1 %. То есть выпадает не монотонный вариант, а контрольный; причина на
трёх раундах не устанавливается (стоимость генератора, раскладка аренд или настоящий
небольшой эффект).

Первый раунд быстрее остальных у ВСЕХ трёх режимов (60340 против 43933 и 44341).
Причина НЕ установлена; прогревом это называть неверно — при прогреве быстрее были бы
последующие раунды. Эффект раунда, задевший все три режима одинаково. В предыдущем прогоне того же сценария при тех же настройках раунды дали
65929 / 65590 / 67120. Сравнивать можно только числа ВНУТРИ одного прогона; абсолютные величины
отсюда брать нельзя.

Размещение строк (снимается сразу после каждого режима — до очистки перед следующим):

```
acct_mono:    60356       0       0       0
acct_randint: 13633   13799   13580   13440
acct_rand:    15046   14990   15031   15145
```

(первый раунд ТОГО ЖЕ прогона)

Сверка учёта по первому раунду — цепочка проверяемая целиком:

| Режим | строк в таблице | ops | rows - ops | deadline_or_unknown | errors |
|---|---|---|---|---|---|
| mono | 60356 | 60340 | 16 | 16 | 0 |
| randint | 54452 | 54438 | 14 | 16 | 0 |
| rand | 60212 | 60202 | 10 | 16 | 0 |

`deadline_or_unknown` = 16 в каждом прогоне — ровно по одной незавершённой транзакции на
воркер в момент дедлайна. Из них зафиксировалось на сервере 16, 14 и 10: разница
`rows - ops` объясняется полностью и без остатка. Ошибок ноль во всех девяти прогонах
D2, так что ни одна серверная ошибка в эту корзину не попала.

#### D3. Накопление: нисходящего тренда не обнаружено, эквивалентность не доказана

Интервалы идут подряд без очистки, переменная — рост таблицы. Оба режима работают
В ОДНОМ интервале, порядок внутри интервала инвертируется, серий две — с обратным
стартовым режимом.

| Интервал | С1 mono | С1 randint | С2 mono | С2 randint |
|---|---|---|---|---|
| 1 | 44184 | 44609 | 45333 | 43341 |
| 2 | 45365 | 44471 | 45054 | 43627 |
| 3 | 44464 | 44327 | 44987 | 43219 |
| 4 | 44898 | 43037 | 43801 | 43142 |
| 5 | 44354 | 43551 | 44817 | 43891 |

Нисходящего тренда нет ни у одного режима: все двадцать чисел укладываются в 5.4 % от
минимума (43037) до максимума (45365).

Нисходящего тренда на десяти интервалах не обнаружено — это и есть результат; «доказано
отсутствие деградации» было бы сильнее данных. И отсутствия РАЗНИЦЫ отсюда тоже не
следует: монотонный вариант выше случайного в 9 парах из 10, а во второй серии — во всех
пяти, на 1.5–4.6 %. Отличить
стоимость генератора от размещения аренд и от небольшого эффекта ключа двумя сериями
нельзя; для утверждения об эквивалентности нужен заранее заданный порог и заметно больше
независимых повторов. Итог серии 1: `acct_mono` 223345 строк в 7
диапазонах, `acct_randint` 220068 в 6. Серии 2: 224061 в 5 и 217281 в 5.

**ОТМЕНЁННЫЙ РЕЗУЛЬТАТ.** Предыдущая версия D3 гоняла пять интервалов mono подряд,
затем пять randint, и дала «случайный ключ проседает 67337 -> 48711». Это артефакт
порядка: вторая серия шла во второй половине прогона, когда кластер отработал уже
полчаса. С чередованием эффект исчез полностью.

#### Что можно и чего нельзя утверждать

**Можно:** на ненасыщенном стенде при неконтролируемом размещении аренд клиентского
штрафа за монотонный ключ не обнаружено — ни при равных условиях, ни при накоплении.
Размещение строк при этом ровно теоретическое.

**Нельзя:** называть это доказанным отсутствием эффекта. Наблюдалось устойчивое смещение
в 1–4.6 % в пользу монотонного варианта, причина которого не установлена.

**ГРАНИЦА ВЫВОДА (добавлено 2026-08-13).** Измерена КЛИЕНТСКАЯ пропускная способность
при НЕКОНТРОЛИРУЕМОМ размещении аренд. Случайный ключ выигрывает только если его
диапазоны обслуживают разные арендаторы, а балансировка аренд по нагрузке работает с
интервалом около минуты при длительности прогона 45 секунд — нужной раскладки замер не
дожидался. Горизонтальное масштабирование форм ключа этим замером НЕ проверено.
Сценарий печатает арендаторов каждого диапазона до и после каждого прогона (раньше
раскладка снималась один раз до всего замера, то есть до первого TRUNCATE, и к
измеряемым диапазонам уже не относилась).

**Нельзя:** что совет неверен. Горячий хвост становится узким местом, когда единственный
арендатор насыщается; наша нагрузка (44184 операции за 45 секунд — 982 оп/с на таблицу,
три узла на одной машине) до этого не дошла.

**Отдельно снято:** аргумент «монотонная таблица разделилась с 4 диапазонов до 16,
значит разделение растаскивало хвост». Неверно. Документация CockroachDB прямо
описывает обратное: при последовательном ключе разделение хвост не устраняет, а
ПЕРЕМЕЩАЕТ — новые записи идут в единственный крайний диапазон, и точка едет от
диапазона к диапазону и от узла к узлу (moving hotspot). Штатное средство —
hash-sharded индексы.

#### Ловушки стенда, стоившие трёх прогонов

1. **Место генерации.** `mono` брал значение из серверного `nextval()`, остальные — с
   клиента. Вклад конкуренции за последовательность отделить от вклада порядка ключей
   тот замер не позволял; отдельного изолирующего эксперимента не ставилось.
   Полной изоляции нет и сейчас: `mono` использует общий атомарный счётчик, `randint` —
   PRNG каждого воркера, `rand` — третий генератор со строковым представлением, и вся
   генерация идёт ВНУТРИ измеряемой транзакции. Корректно говорить о сравнении трёх
   клиентских стратегий целиком; для изоляции одной переменной ключи надо готовить
   заранее и подавать из массива.
2. **Состояние таблиц.** Без очистки между раундами последний режим стартовал на самой
   большой таблице.
3. **Порядок серий в D3.** Серии подряд не отличают форму ключа от дрейфа машины.
4. **Счётчик в процессе.** `monoSeq` не переживал перезапуск генератора: счётчик
   стартовал с 1 и бился в существующие ключи. Прогон дал «деградацию» 68031 -> 26819
   -> 9890 -> 3475 -> ноль, которая была лавиной 23505 (duplicate key). Замер упал с
   явной ошибкой, а не соврал молча. Лечение: инициализация из `max(id)`.
5. **TRUNCATE теряет разбиение.** В CockroachDB он пересоздаёт таблицу, а с ней исчезает
   ручное `SPLIT AT`. Без переразбиения после каждой очистки у таблицы снова один
   диапазон, и сравнение разваливается молча.
6. **Учёт на границе дедлайна.** Поле `aborted_by_deadline` переименовано в
   `deadline_or_unknown`: исход таких транзакций НЕИЗВЕСТЕН — часть могла зафиксироваться
   на сервере, не дойдя ответом до клиента, и именно этим объясняется разница
   `rows - ops` в 10–16 строк. Классификация идёт по ошибке через `errors.Is`
   (DeadlineExceeded/Canceled), а не по факту «контекст уже истёк»: прежняя версия делала
   второе, и настоящая серверная ошибка, пришедшая за миг до дедлайна, молча попадала в
   эту же корзину.

## Артефакт 05 — геораспределение

Команда: `bash scripts/05-geo.sh`
Топология: 9 узлов, три «региона» (`ru-central`, `ru-west`, `ru-east`) по три зоны.

### Чего этот артефакт НЕ измеряет

**Цену расстояния.** Все девять узлов стоят на одной машине, и задержки между ними нет:

```
внутри-ru-central       RTT ср. 0.098 мс
ru-central->ru-west     RTT ср. 0.101 мс
ru-central->ru-east     RTT ср. 0.088 мс
```

Эмулировать задержки не удалось: ядро WSL2 `5.15.167.4-microsoft-standard-WSL2`
собрано **без планировщиков трафика вообще**.

```
tc qdisc replace dev eth0 root netem delay 30ms  -> Error: Specified qdisc kind is unknown.
tc qdisc replace dev eth0 root handle 1: prio    -> Error: Specified qdisc kind is unknown.
ls /lib/modules/$(uname -r)/kernel/net/sched/    -> каталога нет
```

Ни `netem`, ни `prio`. Все latency-числа ниже — это **пол** соответствующих величин,
то, чего они стоят без географии.

### A. REGIONAL BY ROW

Регион строки берётся из региона узла-шлюза — видно в определении таблицы:

```
crdb_region public.crdb_internal_region NOT VISIBLE NOT NULL
    DEFAULT default_to_database_primary_region(gateway_region())
```

Запись через три разных шлюза, по 20 секунд каждый:

| Шлюз | ops | p50, мс | p95, мс |
|---|---|---|---|
| ru-central | 3384 | 41.6 | 87.9 |
| ru-west | 4453 | 31.6 | 66.6 |
| ru-east | 4528 | 31.2 | 62.1 |

Строки легли по регионам своих шлюзов:

```
crdb_region   rows
ru-central    3391
ru-east       4536
ru-west       4454
```

Поштучная сверка: 3384 против 3391, 4453 против 4454, 4528 против 4536 — расхождение
до 0.2 %, всегда в одну сторону (строк больше, чем подтверждённых клиенту транзакций).
Точного совпадения быть и не должно: клиент считает транзакции, о которых **получил
ответ**. Прежняя формулировка «совпадение построчное» неверна и заменена; скрипт теперь
сверяет поштучно с допуском в процент, а не проверяет «регионов ровно три».

### B. Цели выживания: меняется число ГОЛОСУЮЩИХ реплик

**ИСПРАВЛЕНО после ревью 2026-08-12.** Прежняя редакция утверждала «пять реплик при
обеих целях, меняется концентрация 3 → 2» и считала длину массива `replicas`. Это
неверно: в кворуме участвуют только **голосующие** реплики, и колонка `voting_replicas`
лежала в том же выводе `SHOW RANGES ... WITH DETAILS`.

Объявленные конфигурации зон партиции (`SHOW ZONE CONFIGURATION FOR PARTITION "ru-east"
OF INDEX users@users_pkey`):

```
цель ЗОНА:
    num_replicas = 5,
    num_voters = 3,
    constraints       = '{+region=ru-central: 1, +region=ru-east: 1, +region=ru-west: 1}',
    voter_constraints = '[+region=ru-east]',
    lease_preferences = '[[+region=ru-east]]'

цель РЕГИОН (партиция ru-east):
    num_replicas = 5,
    num_voters = 5,
    constraints       = '{+region=ru-central: 2, +region=ru-east: 2, +region=ru-west: 1}',
    voter_constraints = '{+region=ru-east: 2}',
    lease_preferences = '[[+region=ru-east]]'
```

**ВАЖНО.** Строка `constraints` попала в фикстуры только 2026-08-13. До этого
сценарий выбирал из вывода `SHOW ZONE CONFIGURATION` три строки — `num_replicas`,
`num_voters`, `voter_constraints`, — и `constraints` не оказывалась в логе ни разу.
Из-за этого раскладка 3/2/0 была ошибочно названа «формально не нарушающей
конфигурацию»: `voter_constraints` она удовлетворяет, а `constraints` (действует
на ВСЕ реплики, требует 2+2+1) — нарушает. Сценарий печатает конфиг целиком,
включая каждую партицию.

| Цель выживания | Реплик | Голосующих | Требование к голосующим | Кворум |
|---|---|---|---|---|
| `SURVIVE ZONE FAILURE` | 5 | **3** | все в родном регионе | 2 из 3, внутри региона |
| `SURVIVE REGION FAILURE` | 5 | **5** | не менее двух в родном, не менее одного в каждом | 3 из 5, через границу |

Ограничения задают **минимум**, а не максимум: `{+region=ru-east: 2}` читается как
«хотя бы два». Но минимумы, расставленные по всем трём регионам сразу, в сумме
дают жёсткую раскладку: 2 + 2 + 1 = 5 = `num_replicas`, свободы не остаётся. Это и
есть документированная целевая раскладка для пяти реплик по трём регионам.

#### Фактическая раскладка: семь прогонов, три разных исхода

**ИСПРАВЛЕНО после ревью 2026-08-13.** Прежняя редакция утверждала «цель РЕГИОН сошлась».
Это было верно для того прогона и неверно как утверждение: прогонов стало семь, и они
не согласуются между собой.

| Прогон | Диапазонов с 5 голосующими | Раскладка |
|---|---|---|
| 1 | 7 из 7 | 2/2/1 или 2/1/2 — цель достигнута |
| 2 | 2 из 7 | у сошедшегося 2/2/1 |
| 3 | 0 из 7 | — |
| 4 | 7 из 7 | у диапазона 83 **3/2/0** — нарушает constraints (2+2+1) |
| 5 | 0 из 7 (максимум 4) | — |
| 6 | 1 из 7 | 2/1/2, но дома 1 голосующий вместо 2 |
| 7 | 1 из 7 | диапазон 86: central 2, west 2, east 1 — ровно 2+2+1 |

Отбор диапазонов для утверждения — по ПОКРЫТИЮ конфигурацией, а не по наличию
строк. Прежний фильтр `range_size > 0` неверен: конфигурация партиции покрывает
диапазон ключей, и пустой диапазон внутри партиции обязан ей удовлетворять. Вне
утверждения остаются пограничные диапазоны, начинающиеся с `/PrefixEnd`. Полнота
печатается явно: прогон 7 — цель ЗОНА 3 из 5, цель РЕГИОН 4 из 7.

Цель ЗОНА не сошлась **ни разу** за все семь прогонов: требуется 3 голосующих в родном

#### Ловушка счёта: пять голосующих ≠ цель достигнута

Прогон 4 отрапортовал полную сходимость по числу голосующих. Локальности диапазона 83:

```
range_id  voting_replicas  replica_localities
83        {1,2,5,7,3}      ru-central/a, ru-central/b, ru-west/b,
                           ru-central/c, ru-west/a
```

Три голоса из пяти в ru-central, два в ru-west, в ru-east ноль. Потеря ru-central
уносит большинство — цель «пережить регион» не достигнута.

**Конфигурация при этом НАРУШЕНА.** В черновике здесь стояло обратное — что
`voter_constraints = '{+region=ru-central: 2}'` требует «не менее двух» и трое ему
удовлетворяют. Рассуждение неполное: рядом стоит `constraints`, действующая на ВСЕ
реплики и требующая при цели REGION раскладки 2+2+1. Ноль реплик в ru-east нарушает
её прямо. Ошибка держалась на том, что сценарий выбирал из вывода три строки и
`constraints` в лог не попадала (см. выше).

Что остаётся верным: проверка по ЧИСЛУ голосующих пропускает нарушение, видимое по их
РАСПРЕДЕЛЕНИЮ. Пять голосующих у всех семи диапазонов — и раскладка, не соответствующая
объявленному и не переживающая потерю региона.

Прогон 6: раскладка 2/1/2 — по регионам большинство нигде не собирается, но дома один
голосующий вместо двух, то есть `voter_constraints` нарушен. Прогон 7: диапазон 86 дал
central 2, west 2, east 1 — ровно по конфигурации своей партиции.

**Как считать правильно.** Глобального максимума по таблице мало: он проходит, если хотя
бы один диапазон разложен верно. Утверждать надо по КАЖДОМУ диапазону, покрытому
конфигурацией партиции, независимо от наличия строк: конфигурация покрывает диапазон
КЛЮЧЕЙ, и пустой диапазон внутри партиции обязан ей удовлетворять так же. Отбор по
`range_size > 0`, стоявший здесь в предыдущей редакции, неверен — он отбирает по данным,
а не по действию конфигурации. Вне утверждения остаются только пограничные диапазоны,
начинающиеся с `/PrefixEnd`: они лежат за концом партиции, и её конфигурация на них не
распространяется. Домашний регион диапазона берётся не из
текста ключа — `crdb_region` это ENUM, в ключе стоит его физический байт; карта
«байт -> регион» строится через `SHOW RANGE ... FOR ROW`, а диапазон, начинающийся с
начала таблицы, принадлежит ПЕРВОЙ партиции (брать байт из `end_key` нельзя — он уже
от следующей).

**Причина отказов установлена и воспроизвелась во всех семи прогонах.** Кластер сообщает
её сам:

```
queue_replicate_addreplica_error{store="1"}   190
queue_replicate_process_failure{store="1"}    194
ranges_underreplicated{store="1"}              26
queue_replicate_addreplica_error{store="6"}     7
```

Текст отказа в файловых логах узла (`cockroach-data/logs/cockroach.log`, не в
`docker logs`):

```
queue processing resulted in non-benign error: 8 matching stores are currently
throttled: [s2: suspect, s4: suspect, s5: suspect, s9: suspect, s6: suspect,
            s3: suspect, s7: suspect, s8: suspect]
```

Восемь или девять узлов из девяти помечены `suspect` — так CockroachDB помечает узел,
чьи сигналы живости приходят с опозданием. Аллокатор отказывается размещать на них
реплики.

Это **непосредственная** причина, она установлена точно. Корневая — почему узлы стали
подозрительными — стендом НЕ изолирована: правдоподобно, что девять экземпляров на одной
машине конкурируют за процессор и диск, но для проверки нужны задержки и отказы самих
сигналов живости, загрузка процессора, задержки диска. Ничего из этого не снималось.

Диагностическая цепочка воспроизводима в любом кластере: несходящаяся раскладка →
`queue_replicate_*` и `ranges_underreplicated` → текст отказа в логах узла.

### B. Миграция PG-схемы: 8 прошло, 6 отказало

Каждый оператор сверяется со **своим** ожиданием (`-- EXPECT: pass|fail` в файле схемы),
а не только по общему числу отказов: одинаковое количество совпало бы и при перепутанных
местами результатах. В прогоне все четырнадцать операторов дали ожидаемый исход.

| Прошло | Отказало (с текстом ошибки) |
|---|---|
| `CREATE EXTENSION IF NOT EXISTS pg_trgm` | `MONEY`: `at or near "not": syntax error: unimplemented: this syntax` |
| `SERIAL PRIMARY KEY` | `XML`: `at or near ")": syntax error: unimplemented: this syntax` |
| `GENERATED ALWAYS AS IDENTITY` | `DEFERRABLE INITIALLY DEFERRED`: `at or near "deferrable": syntax error` |
| Частичный индекс `WHERE total > 1000` | `CREATE RULE`: `syntax error: unimplemented: this syntax` |
| `CREATE FUNCTION` на PL/pgSQL | `pg_advisory_lock()`: `unknown function` |
| `CREATE TRIGGER` | `pg_size_pretty()`: `unknown function` |
| `CREATE MATERIALIZED VIEW` | |
| `CREATE DATABASE` | |

Во что превратился `SERIAL`:

```sql
CREATE TABLE public.customers (
    id INT8 NOT NULL DEFAULT unique_rowid(),
    email STRING NOT NULL,
    created TIMESTAMPTZ NOT NULL DEFAULT now():::TIMESTAMPTZ,
    CONSTRAINT customers_pkey PRIMARY KEY (id ASC),
    UNIQUE INDEX customers_email_key (email ASC)
);
```

Сам CockroachDB при этом предупреждает:

```
NOTICE: using sequential values in a primary key does not perform as well as
using random UUIDs.
```

Прямая перекличка с артефактом 03-D2/D3, где разницы между формами ключа не нашлось.

Подмена образа по одному узлу, **53 секунды**. Промежуточные состояния:


**Доступность во время обновления (замерена пробником, ревью 2026-08-12).** Прежняя
редакция писала «простоя не было», опираясь лишь на то, что контейнеры вернулись в

Пробник ходит в ops1 — узел, который сам перезапускается. Это худший случай: клиент без

сработавшая автоматика. С отключённой автофинализацией версия оставалась прежней до
явной команды:

```

после:                            26.2
```

### Про загрузку узлов в замере формы ключа

Сценарий снимает `rebalancing_writespersecond` и `rebalancing_cpunanospersecond` по
каждому store, но **вывод о распределении работы по узлам из них не следует**: метрика
CPU смешивает работу узла-шлюза (разбор SQL и координация транзакций для всей нагрузки)
с работой арендатора. В прогонах со случайным ключом загрузка первого узла оказывалась
выше, чем с монотонным, — тогда через него шло гораздо больше операций.

Поэтому прежнее утверждение «два узла при монотонном ключе простаивают» **снято**.

Числа про «вдесятеро больше операций» и «восьми-девятикратную разницу» относились к
той редакции замера, которая сравнивала не формы ключа (см. D2/D3 выше): разницы
между ними на равных условиях не оказалось вовсе. Из этого раздела остаётся один
методический вывод: `rebalancing_cpunanospersecond` смешивает работу шлюза с работой
арендатора, и делать по ней вывод о распределении работы по узлам нельзя.
