# citus

Стенд к статье «Шардирование на практике» (`databases/sharding-in-production`).

## Что демонстрирует

PostgreSQL-кластер, шардированный через [Citus](https://www.citusdata.com/)
14.1: координатор + воркеры, распределённые и колоцированные таблицы,
референсные (реплицируемые на каждый воркер) справочники. Пять артефактов по
порядку прогона:

1. **`scatter-gather-demo.sh`** — запрос по ключу шардирования (один шард) против
   запроса не по ключу (все 32 шарда, `scatter-gather`).
2. **`colocation-demo.sh`** — join двух колоцированных таблиц (локален на каждом
   шарде) против join таблиц из разных групп колокации (требует репартиции).
3. **`reference-demo.sh`** — тот же контраст локальности join, но через другой
   механизм: референсная (реплицированная) таблица против распределённой копии
   того же справочника.
4. **`pagination-demo.sh`** — `LIMIT`/`OFFSET` поверх шардов: цена глубокой
   пагинации и разнонаправленный эффект от сортировки по ключу шардирования.
5. **`rebalance-demo.sh`** — добавление узла в кластер и явный ребаланс шардов;
   доступность данных по ключу шардирования измеряется ДВУМЯ пробами в
   переезжающий шард, читающей и пишущей (режимы переноса Citus различаются
   по ЗАПИСЯМ, и одной читающей пробы для утверждения о них не хватает).
   ⚠️ Пробы идут всё время жизни ЗАДАЧИ ребаланса, но **с фазой переноса
   конкретного шарда не соотнесены**: скрипт следит за состоянием job'а, а не
   за прогрессом отдельных перемещений. Поэтому «во время переноса» здесь
   означает «пока job не завершился», а не «ровно в момент переключения
   шарда». Границы этого утверждения — в `FIXTURES.md`, раздел «Артефакт 5».

Все числа по каждому артефакту — в [`FIXTURES.md`](FIXTURES.md), взяты из
живого прогона на этой машине, а не из документации Citus.

## Как поднять

Docker и `psql` — только через WSL2.

```bash
cd databases/citus
bash scripts/up.sh
```

`up.sh` идемпотентен: поднимает координатор + два воркера, регистрирует их
(`citus_add_node`), распределяет таблицы (`create_distributed_table`/
`create_reference_table`) и наполняет данными. Повторный запуск на уже
поднятом стенде не падает и не дублирует данные.

- Образ: `citusdata/citus:14.1.0-pg17` (Citus 14.1-1, PostgreSQL 17.6).
  **Готовый образ под PostgreSQL 18 существует — это НЕсуффиксированный тег
  `citusdata/citus:14.1.0`.** Проверено по метаданным образа: `PG_MAJOR=18`,
  `PG_VERSION=18.4-1.pgdg13+1`, `CITUS_VERSION=14.1.0.citus-1`. Отдельного
  тега `14.1.0-pg18` нет именно потому, что 18-я ветка лежит в основном
  теге; суффиксы `-pg16` / `-pg17` — это СТАРШИЕ ветки PostgreSQL, а не
  «самая новая поддерживаемая». Собирать ничего не нужно.

  ```bash
  docker inspect citusdata/citus:14.1.0 --format '{{range .Config.Env}}{{println .}}{{end}}'
  ```

  Стенд СОЗНАТЕЛЬНО пинован на `14.1.0-pg17`: замеры делаются на одной
  фиксированной версии PostgreSQL, чтобы числа между прогонами были
  сопоставимы.
- Порт координатора: **15435** (`postgresql://shard:shard@localhost:15435/shard`).
- **Воркеры наружу не публикуются намеренно** — к кластеру положено ходить
  только через координатор.
- Наполнение: `customers` 200, `orders` 4000, `shipments` 4000, `carriers`
  (референсная) 5 строк.

Проверка фактического API Citus (регистрация функций ребаланса и т.п.):

```bash
bash scripts/api-probe.sh
```

## Порядок прогона демонстраций

```bash
cd databases/citus

bash scripts/scatter-gather-demo.sh   # артефакт 1: шард vs scatter-gather
bash scripts/colocation-demo.sh       # артефакт 2: колокация vs репартиция
bash scripts/reference-demo.sh        # артефакт 3: референсная vs распределённая копия
bash scripts/pagination-demo.sh       # артефакт 4: LIMIT/OFFSET поверх шардов — идёт МИНУТЫ
                                       #   (создаёт и удаляет собственную таблицу на 1 млн строк)
bash scripts/rebalance-demo.sh        # артефакт 5: добавление узла и ребаланс — идёт МИНУТЫ,
                                       #   временно поднимает третий узел (см. предупреждение ниже)
```

Артефакты 1–3 занимают секунды, каждый прогоняет обе демонстрируемые ветки
дважды и завершается ненулевым кодом, если структурные величины (`Task
Count`, `MapMergeJob`, число шардов/размещений) не воспроизвелись — не
публикуйте вывод такого прогона как есть, разбирайтесь в причине.

**Артефакты 4 и 5 занимают минуты, а не секунды** (наполнение и три
внутренних прогона у пагинации; ожидание фонового ребаланса и опустошения
узла у пятого). На прогретом хосте (образ `citus-w3` уже скачан, стенд уже
поднят) весь набор из пяти артефактов занимает **порядка 3 минут** (по
факту: ~7 с / ~4 с / ~5 с / ~1.5 мин / ~1.2 мин — измерено несколько
прогонов подряд, устойчиво). Больше всего времени уходит на артефакты 4 и
5 — закладывайте на них по 1–2 минуты каждый. При первом запуске (когда
Docker ещё не скачал образ для профиля `grow`, `citus-w3`) время артефакта
5 будет больше на время `docker pull`.

Скрипты пишут в общую БД `shard`, но каждый работает с собственными
таблицами (`orders_big`, `carriers_sharded` создаются и удаляются самими
скриптами 3 и 4) — параллельный запуск друг с другом не проверялся и не
рекомендуется, запускайте строго последовательно.

## ⚠️ Профиль `grow` и артефакт 5

Стенд по умолчанию живёт на **двух** воркерах (`citus-w1`, `citus-w2`).
Артефакт 5 (`rebalance-demo.sh`) сам поднимает **третий** воркер (`citus-w3`,
compose-профиль `grow`: `docker compose --profile grow up -d worker3`),
регистрирует его в кластере, гоняет ребаланс — и **сам же убирает узел** по
завершении (`citus_drain_node` → ожидание фактического опустошения →
`citus_remove_node` → остановка и удаление контейнера `citus-w3`), причём и
при обычном завершении, и по `trap` на аварийный выход.

Уборка (и по нормальному завершению, и по `trap` на прерывание — Ctrl+C,
падение хоста, `kill`) не просто вызывает `citus_drain_node`, а **ждёт
фактического опустошения узла** от размещений РАСПРЕДЕЛЁННЫХ таблиц
(опрашивает `pg_dist_placement` до раза в 5 секунд, до 60 попыток), прежде
чем снять регистрацию. На штатном прогоне это ожидание короткое (секунды —
десятки секунд, пропорционально числу шардов, которые реально нужно
перенести с осушаемого узла обратно).

**⚠️ Раньше это ожидание было сломано и стоило 5 минут на КАЖДОМ штатном
прогоне, не только на прерванном.** Прежняя версия цикла ждала нуля ВСЕХ
размещений на `citus-w3`, включая копию референсной таблицы `carriers` —
а `citus_drain_node` копии референсных таблиц не трогает принципиально
(она остаётся на узле до `citus_remove_node`, который снимает узел вместе
с её последним размещением). Ноль был структурно недостижим, и цикл
выжигал все 60 попыток × 5 с = 300 с впустую при каждом обычном
завершении скрипта — это не описывалось как баг README, потому что со
стороны выглядело как «уборка просто работает» (скрипт действительно
доводил её до конца, только вхолостую тратил пять минут). Исправлено:
цикл ждёт опустошения только от размещений распределённых таблиц —
референсная копия дождётся `citus_remove_node`, для неё отдельного
ожидания не нужно. Подробности — в `FIXTURES.md`, раздел «Артефакт 5»,
оговорка 5.

Если процесс убит `SIGKILL` (`kill -9`), `trap` не сработает вовсе, и
кластер может остаться на трёх узлах с недренированным `citus-w3` —
соседние артефакты (в первую очередь `reference-demo.sh`, он берёт число
воркеров из `pg_dist_node` динамически) в этом случае начнут падать или
давать другие числа.

Проверка и восстановление вручную:

```bash
# Кластер должен быть на двух воркерах, без осиротевших записей уборки:
docker exec -i citus-coord psql -U shard -d shard -c \
  "SELECT nodename FROM pg_dist_node WHERE isactive; SELECT count(*) FROM pg_dist_cleanup;"

# Если состояние не восстановилось (третий узел жив, pg_dist_cleanup > 0,
# или reference-demo.sh падает) — пересобрать стенд начисто:
docker compose -f compose/compose.yml --profile grow down -v
bash scripts/up.sh
```

## wal_level=logical — почему это в `compose.yml`, а не костыль скрипта

Citus умеет переносить шарды двумя способами: логической репликацией
(`shard_transfer_mode` = `auto` / `force_logical`) и через `COPY` с
блокировкой ЗАПИСЕЙ (`block_writes`). Требование к `wal_level` относится
ТОЛЬКО к первому. Стенд не меняет режим, то есть работает на `auto`, —
именно он позволяет избежать блокировки ЗАПИСЕЙ, и именно он требует
`wal_level=logical`. При `block_writes` этого требования нет.

⚠️ Режимы различаются по ЗАПИСЯМ, не по чтениям: читать переезжающий шард
можно в обоих. Поэтому артефакт 5 во время ребаланса шлёт не только
читающую, но и ПИШУЩУЮ пробу (`INSERT` в переезжающий шард + проверка
видимости записанного) — одной читающей пробы для разговора о режимах не
хватает структурно.

**⚠️ Но «преимущество `auto`» стенд НЕ показывает, и утверждать это нельзя.**
Контрольного прогона в режиме `block_writes` здесь НЕТ — режим не менялся ни
разу. Показано ровно одно: **при `auto` пишущие пробы проходят и записанное
видно**. Что при `block_writes` они бы НЕ прошли — не проверялось, это взято
из документации Citus, а не измерено.

К этому добавляется вторая неоднозначность: успешный `INSERT` мог сначала
ЖДАТЬ блокировку, а потом завершиться — `statement_timeout` в пробах не
задан. Поэтому ноль отказов не отличает «блокировки не было» от «блокировка
была короткой и проба её пересидела». Без разбора `pg_locks` и без корреляции
с фазой конкретного шарда измерение остаётся неоднозначным. Подробный разбор
— в `FIXTURES.md`, раздел «Артефакт 5».

В этом стенде `wal_level=logical` включён на ВСЕХ ЧЕТЫРЁХ СЕРВИСАХ compose
(`coordinator`, `worker1`, `worker2`, `worker3`) через `command:
["postgres", "-c", "wal_level=logical"]` — правка внесена один раз в
инфраструктуру и не требует ничего от того, кто просто прогоняет
демонстрации.

**Граница измерения.** PostgreSQL предъявляет требование `wal_level=logical` к стороне
ПУБЛИКАЦИИ; к подписчику — нет
(https://www.postgresql.org/docs/17/logical-replication-config.html).
Какой узел публикует в конкретной операции переноса Citus, стенд НЕ
проверяет. Опыт изолировал ровно два состояния: `replica` ВЕЗДЕ против
`logical` ВЕЗДЕ, — роли (координатор против воркеров, отправитель против
получателя) в нём не разделены. Что проверено: с `replica` везде перенос
не идёт, с `logical` везде идёт. Что НЕ установлено: минимально
необходимый набор ролей. Настройка на всех сервисах — выбор
КОНСЕРВАТИВНЫЙ, а не доказанное требование к каждому из них. Это разрыв
между измерением и выводом, и закрывается он оговоркой, а не догадкой.

Если поднимаете кластер из чужого/своего `compose.yml` без этой настройки:
ребаланс не упадёт читаемой ошибкой, а **зависнет** — задача
`replicate_reference_tables` уходит в повтор с «logical decoding requires
wal_level >= logical» и блокирует собой все запланированные перемещения
шардов. Живьём наблюдалось 8 повторов и 20 заблокированных задач дольше
5 минут без прогресса; наблюдение прервано вручную, поэтому доказан
ЗАТЯЖНОЙ повтор без прогресса, а не бесконечный цикл. Подробности — в
`FIXTURES.md`, раздел «Артефакт 5».

## Тесты

Отдельных Go/юнит-тестов у этого стенда нет — все демонстрации самопроверяемы
(каждый скрипт падает с ненулевым кодом, если структурные величины не
воспроизвелись) и являются одновременно и демонстрацией, и проверкой.
