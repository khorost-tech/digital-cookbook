# Стенд distributed-sql

Четыре движка distributed SQL и одиночный PostgreSQL под одними и теми же замерами —
к статье [«Distributed SQL и NewSQL: CockroachDB, YugabyteDB, TiDB и OceanBase»](https://khorost.tech/databases/distributed-sql-newsql/).

Стенд отвечает не на вопрос «кто быстрее», а на три других:

1. **Сколько стоит одна операция**, когда данные лежат в консенсус-группах на разных
   узлах, и как эта цена растёт с расстоянием между узлами.
2. **Что движок даёт по умолчанию** — какой уровень изоляции и ловит ли он write skew.
3. **Где протекает совместимость** с PostgreSQL и MySQL, если подключиться штатным драйвером.

Всё, что попало в статью, лежит в [`FIXTURES.md`](FIXTURES.md) и в `fixtures/` — с командой,
давшей каждый вывод.

## Требования

- Docker с compose. Снято на Docker Desktop под macOS (arm64), 10 CPU, **7,7 ГБ** памяти VM.
- Профили поднимаются **по одному**: три кластера одновременно в такую память не входят.
  `up.sh` сам гасит предыдущий кластер.
- Свободные порты хоста: 16257 (CockroachDB), 16433 (YugabyteDB), 16400 (TiDB),
  16881 (OceanBase), 16432 (PostgreSQL), 16306 (MySQL). Все замеры идут изнутри сети
  `dsql`, порты нужны только для ручного подключения.
- Ядро VM Docker должно уметь `tc netem` и `prio` — `netem.sh` это проверяет пингом.
  У Docker Desktop под macOS умеет; у WSL2 из коробки — нет.

## Профили

| Профиль | Что внутри | Память |
|---|---|---|
| `crdb` | CockroachDB `v26.2.5`, 3 узла | ~1,2 ГБ |
| `yb` | YugabyteDB `2026.1.2.0`, 3 узла (yb-master + yb-tserver в каждом), RF=3 | ~2 ГБ |
| `tidb` | TiDB `v8.5.8`: 1 PD, 3 TiKV, 1 tidb-сервер | **~6,5 ГБ** — TiKV держит 1,8–2,3 ГБ на узел даже на пустой базе |
| `ob` | OceanBase CE `4.4.2-lts`, **один** observer в режиме mini | ~4,3 ГБ |
| `pg` | PostgreSQL 17, одиночный — базовая линия | ~0,1 ГБ |
| `mysql` | MySQL 8.4 — эталон для проверки совместимости | ~0,5 ГБ |

**OceanBase — один узел.** Кластер из трёх observer в 7,7 ГБ не помещается. На стенде он
участвует только в проверках MySQL-wire, совместимости и изоляции; о его распределённости
стенд ничего не утверждает.

## Как запускать

```bash
bash scripts/up.sh crdb                 # поднять профиль (гасит другой кластер)
bash scripts/probe.sh crdb              # версии, узлы, изоляция по умолчанию
bash scripts/01-distribution.sh crdb    # таблица kv на 4 диапазона, раскладка лидеров
bash scripts/02-latency.sh crdb         # p50/p99 при RTT 0 / 2 / 30 мс между узлами
bash scripts/03-isolation.sh crdb       # write skew: по умолчанию, SERIALIZABLE, FOR UPDATE
bash scripts/04-compat.sh crdb          # список конструкций штатным драйвером
bash scripts/05-failover.sh crdb        # docker kill узла с лидером под потоком записей
bash scripts/06-java.sh crdb            # retry-цикл на JDBC (только crdb и yb)
bash scripts/down.sh                    # снести всё
```

Каждый сценарий перезаписывает свой файл в `fixtures/` и печатает то же самое в терминал.

## Инструменты

- `bench/` — Go, один бинарник на все движки: `pgx/v5` для PG-wire, `go-sql-driver/mysql`
  для MySQL-wire. Собирается в образ `dsql-bench` и запускается в сети `dsql`, поэтому Go
  на хосте не нужен. Режимы: `latency`, `skew`, `compat`, `failover`.
- `netem/` — образ с `iproute2`. `netem.sh` запускает его в сетевом пространстве каждого
  узла и вешает задержку **только на трафик к соседям по кластеру**: путь клиент → шлюз
  остаётся чистым.
- `javaretry/` — JDBC, переводы между двумя счетами из четырёх потоков под SERIALIZABLE
  с повтором по SQLSTATE `40001`.

## Методика и оговорки

- **Раскладка лидеров задаётся явно** (`place-leaders.sh`): диапазоны 0 и 2 — на втором
  узле, 1 и 3 — на третьем, на шлюзе — ни одного. У TiDB шлюз (tidb-сервер) данных не
  держит вообще, и только так путь операции у всех кластеров одинаков:
  клиент → шлюз → лидер на другом узле. После замера `02` снимает раскладку ещё раз —
  видно, не увела ли её ребалансировка.
- **Задержки назначенные, а не измеренные.** RTT 2 мс моделирует узлы в разных зонах
  одного региона, 30 мс — в разных регионах. Это модель, а не география: сколько стоит
  ваша сеть, стенд не знает.
- **Один клиент, одно соединение, операции по очереди.** Меряется цена операции, а не
  пропускная способность. Сравнивать движки по абсолютным миллисекундам при RTT 0 не стоит:
  урезанные лимиты памяти и разные настройки по умолчанию на одной машине. Смысл имеют
  соотношения — во сколько раз растёт операция с RTT и с числом диапазонов.
- **Отказ — `docker kill`**, то есть внезапная смерть процесса, без корректного
  завершения. Таймаут попытки в `failover` 30 с: запрос, застрявший на погибшем лидере,
  дожидается нового, и пауза между коммитами меряет восстановление, а не таймаут клиента.
- **CockroachDB без лицензионного ключа**: многоузловой кластер работает 7 дней грейса,
  стенд эфемерный и в него укладывается. Телеметрия на бесплатной лицензии включена и
  отключению не подлежит.
