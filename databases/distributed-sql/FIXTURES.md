# FIXTURES — что снято на стенде distributed-sql

Единственный источник чисел для статьи
[«Distributed SQL и NewSQL»](https://khorost.tech/databases/distributed-sql-newsql/).
Сырой вывод — в `fixtures/`, у каждой секции первая строка `# cmd:` с командой,
которая её дала. Здесь — сводка и то, как её читать.

**Дата прогонов: 2026-10-04.** **Машина:** macOS, Docker Desktop 29.8.0 (arm64),
VM Docker — 10 CPU, 7,7 ГБ памяти. Все кластеры — на одном хосте, по одному за раз.

Абсолютные миллисекунды зависят от железа и урезанных лимитов памяти. Смысл имеют
соотношения: рост с RTT, разница между видами операций, раунд-трипы.

## 01 — распределение (`fixtures/01-distribution-*.txt`)

Таблица `kv`, 4000 строк, границы 1e6 / 2e6 / 3e6. Лидеры разнесены
`place-leaders.sh`: диапазоны 0 и 2 → второй узел, 1 и 3 → третий, на шлюзе — ни
одного. У TiDB переносить нечего: шлюз данных не держит.

- CockroachDB: 4 range, реплики `{1,2,3}`; всего в кластере 86 range.
  `node_id` ≠ номер контейнера (на прогоне 2 = `crdb3`, 3 = `crdb2`).
- YugabyteDB: 4 tablet; лидеры удерживаются вне шлюза через `set_preferred_zones z2 z3`.
- TiDB: 4 region, лидеры на разных store.
- OceanBase: 4 партиции → 4 таблетки → **один** лог-стрим `1001`.

## 04 — совместимость (`fixtures/04-compat-*.txt`)

Ключевые протечки (полные списки — в файлах):

- CockroachDB: `SERIAL` → `unique_rowid()` (`1215889313195163649,…`); нет `LISTEN/NOTIFY`,
  `pg_advisory_lock`, `EXCLUDE`; DDL в транзакции не откатывается и коммитит
  предшествующий `INSERT` (`autocommit_before_ddl = on`); `REPEATABLE READ` → `serializable`.
- YugabyteDB: `LISTEN/NOTIFY is disabled`; `EXCLUDE` не поддержан; DDL не откатывается,
  DML вокруг него откатывается (`yb_ddl_transaction_block_enabled = off`).
- TiDB: `CHECK` вставляет нарушающую строку (предупреждение `tidb_enable_check_constraint is off`);
  `FULLTEXT` принят с предупреждением 1214 — индекса нет; нет триггеров, процедур,
  `SPATIAL`, `EVENT`, XA; `SERIALIZABLE` → `ERROR 8048`.
- OceanBase: весь список MySQL-проверок пройден.

## 05 — отказ узла с лидером (`fixtures/05-failover-*.txt`)

`docker kill` (SIGKILL) узла с лидером диапазона ключа 1 на 10-й секунде, таймаут попытки 30 с.
Проверка сохранности: прирост `v` должен лежать в [подтверждено; подтверждено + неизвестный исход].

| Движок | Пауза в последнем прогоне | Ошибки | Сохранность (последний прогон) |
|---|---|---|---|
| CockroachDB | 3.71 с | 1 × `40003 result is ambiguous` | подтверждено 37276, неизвестно 1, прирост 37277 — запись с неизвестным исходом прошла |
| YugabyteDB | 15.11 с | нет | подтверждено 12787, прирост 12787 |
| TiDB | 11.74 с | нет | подтверждено 40432, прирост 40432 |

История прогонов (пауза): CockroachDB 3.41 (таймаут попытки 3 с — не в зачёт) / 3.77 (10 с) /
3.65 / 3.71; YugabyteDB 15.43 (таймаут 10 с — пауза больше таймаута, не в зачёт) / 15.13 / 15.11;
TiDB 23.34 / 11.74 — разброс вдвое, одно число движок не характеризует.
Проверка сохранности появилась в bench только к последнему прогону.

После съёмки исправлен учёт в `failover`: результат запроса, завершившегося после
конца окна, раньше отбрасывался до подсчёта (его изменение попало бы в итоговое `v`,
а подтверждение — нет). На снятые прогоны это не повлияло: во всех трёх последний
запрос завершился на 40-й секунде, внутри окна (`t=40s ok=1`), и был учтён.

## 06 — Java, retry (`fixtures/06-java-*.txt`)

Иллюстрация паттерна, с Go не сравнивается. 4 потока × 25 переводов, SERIALIZABLE.
Сняты с драйвером `org.postgresql` 42.7.4; после съёмки драйвер поднят до 42.7.13
(уязвимости аутентификации, к стенду без паролей не относятся). Контрольный прогон
`crdb rmw` на 42.7.13: 100/100, 116 × 40001, максимум 7 попыток — в пределах разброса.

| Движок | Режим | Успешно / сдались / оборваны лимитом, не применены / исход неизвестен / не начаты | Повторов | Макс. попыток среди успешных | Заняло |
|---|---|---|---|---|---|
| CockroachDB | update | 100 / 0 / 0 / 0 / 0 | 0 | 1 | 0.3 с |
| CockroachDB | rmw | 100 / 0 / 0 / 0 / 0 | 118 (40001) | 5 | 0.3 с |
| YugabyteDB | update | 41 / 0 / 4 / 0 / 55 — ОСТАНОВЛЕНО лимитом 10 мин | 104 (40P01) | 10 | 600.8 с |
| YugabyteDB | rmw | 100 / 0 / 0 / 0 / 0 | 142 (141 × 40P01 + 1 × 40001) | 18 | 10.5 с |

Остановка: остаток до дедлайна пересчитывается перед каждым оператором (таймаут
оператора, округлён вверх), `commit()` ограничен `setNetworkTimeout`. Исходы разведены:
«оборваны лимитом, не применены» — коммит не отправлялся либо база явно сообщила об
откате (40001/40P01, в том числе на commit()); «исход неизвестен» —
ошибка во время/после отправки коммита (в этих прогонах — 0). Итоги печатаются после
завершения всех потоков, графы складываются в 100. Повторы считаются в момент ошибки.

Предыдущий прогон YugabyteDB update тем же измерителем (до переименования категории):
38 / 0 / 4 / 0 / 58 за 600.5 с — достоверен, картина та же.

Более ранние прогоны YugabyteDB update (100/100 за 599.6 с, 44/100 за 660.1 с, 52/100 за
600.4 с) сняты измерителем без детерминированной остановки или без разделения исходов
и как итог остановленного теста недостоверны; в статье не используются.

Go-цикл `txnRows` после съёмки 02 переписан: ключи выбираются до цикла повторов, лимит 10 попыток,
пауза с джиттером. На числа 02 это не влияет — там `retries=0` во всех прогонах.

Первая версия цикла повторяла только `40001` и на YugabyteDB теряла потоки на `40P01`.
Первый прогон на 4 × 100 у YugabyteDB в режиме `update` не уложился в 10 минут —
объём уменьшен до 4 × 25, а лимит теперь печатается явно, если сработал. Подписи метрик
уточнены: «максимум попыток среди успешных», «ошибки по кодам».

## Чего здесь нет

- Пропускной способности и рейтинга движков.
- OceanBase как распределённой системы (один узел).
- HTAP (TiFlash не поднимался).
- Измеренной географии: RTT назначен, а не измерен.
