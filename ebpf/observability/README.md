# ebpf/observability — Beyla, OTEL SDK и eBPF-профилировщик против эталона

Стенд к статье [«Наблюдаемость через eBPF: профилирование и трейсинг без инструментирования»](https://khorost.tech/infrastructure/ebpf-observability/).
Тестовый Go-сервис (HTTP, gRPC, PostgreSQL) в двух сборках: `svc-plain` без
инструментирования — его видит Beyla 3.38 (eBPF); `svc-sdk` — с OTEL SDK. Оба
отдают трейсы в OTEL Collector 0.162, который пишет их в `out/traces.jsonl`.
Профили — Grafana Alloy 1.20 (`pyroscope.ebpf`) → Pyroscope 2.3. Генератор
запросов (`cmd/gen`) и сжигатель CPU (`cmd/burn`) сами знают свой счёт — с ним
сверяется всё остальное.

**Почему `privileged` и `pid: host`** у `beyla`, `alloy` и `tools`: eBPF-программы
и доступ к процессам других контейнеров; `tools` читает счётчики программ через
bpftool. «Хост» для eBPF — ядро VM Docker (на Mac — LinuxKit 7.0, aarch64).

## Что внутри

```
svc/               сервис: /users/{id} (SELECT), /orders (INSERT), /fail (500), /health,
                   /warmup (прогрев), :8081 /v2/users/<id> без шаблона маршрута, gRPC health
svc/otel.go        инструментирование OTEL SDK (сборка с тегом otel)
cmd/gen/           генератор: план запросов по маршрутам, счёт отправленного и статусов
cmd/burn/          сжигатель: 3 : 1 итераций в burnA / burnB (self — цикл внутри, shared — общая work)
config/            otelcol.yaml (выгрузка в файлы), config.alloy (профилировщик)
scripts/           раннеры осей, разбор с контролями, проверки, диверсии
fixtures/          замеры; manifests/ — сводки сессий; RUN-COMPLETE — маркер
expected.json      гипотезы до прогона, факты проб, расхождения
```

## Как прогнать

Нужны Docker (Linux-ядро с BTF) и Python 3.8+. Ось профилей поднимает профиль
compose `profiling` (пять сжигателей CPU, Alloy, Pyroscope) только на время замера.

```sh
bash scripts/run-all.sh                      # всё разом, маркер последним
FRESH=1 bash scripts/run-all.sh              # то же с пустых томов
python3 scripts/run-traces.py                # одна ось
python3 -m unittest discover -s scripts -p "test_*.py"
python3 scripts/sabotage.py
```

## Что замерено

Две сессии полного прогона (вторая — с пустых томов) совпали по
опубликованному (`fixtures/manifests/`).

**Ось 1 — трейсы** (`traces.jsonl`). Перед нагрузкой раннер шлёт запросы на
`/warmup`, пока спан не появится в выгрузке: строка `instrumenting process` в
журнале Beyla появляется раньше, чем зонды начинают работать (без прогрева
Beyla увидела 195 серверных спанов из 1100 ожидаемых — 950 HTTP и 150 gRPC). После
прогрева Beyla и SDK
насчитали каждый маршрут, статус и gRPC-вызов ровно по счёту генератора.
`http.route` у Beyla — шаблон ServeMux (`/users/{id}`); на порту без шаблона
300 разных путей свернулись эвристикой в `/v2/users/*`. SQL: SELECT 300,
INSERT 200 у обоих; SDK видит и `CREATE TABLE` при старте, Beyla — нет (раннер
перезапускает сервисы после сброса выгрузки, Beyla цепляется к новому процессу позже). SQL-спаны
Beyla в том же трейсе, что HTTP-запрос, но родитель по `parentSpanId` не
найден ни у одного; у SDK — у всех. На каждый HTTP-запрос у Beyla ещё два
служебных спана.

**Ось 2 — профили** (`profiles.jsonl`). Доли burnA / burnB в допуске ±5 п.п. от
75 / 25 у Go 1.26 (с символами и без) и у Go 1.27 с символами — хотя
профилировщик пишет `unsupported Go version go1.27.1 (need … <= 1.26)`. Go 1.27
без символов — имён функций нет (сэмплы ядра то есть, то нет). Режим `shared` (burnA / burnB вызывают общую
листовую `work`): burnA и burnB в профиле нет — на arm64 у листовой функции
без кадра адрес возврата в регистре, и раскрутка теряет прямого вызывающего.

**Ось 3 — цена** (`cost.jsonl`). `kernel.bpf_stats_enabled`: Beyla загружает
полторы сотни программ; без нагрузки за 20 с срабатываний от нуля до нескольких
десятков — меньше 1% срабатываний под нагрузкой; под нагрузкой срабатывают
около тридцати, порядка двадцати срабатываний и десяти–двадцати
микросекунд в программах на обращение — 1100 обращений: 950 HTTP и 150 gRPC (точные
числа от прогона к прогону разные).

## Чего эти числа не значат

- **Время в программах — не задержка запроса**: это время ядра в eBPF-коде,
  задержку сервиса стенд не мерил.
- **Связь сервисов** через несколько процессов (распространение контекста
  Beyla между сервисами) не замерялась — здесь один сервис и база.
- **arm64**: потеря вызывающего у листовой функции — особенность раскрутки на
  arm64; на x86-64 адрес возврата всегда на стеке.
- **Версии:** Beyla 3.38.0 (OBI 0.14.0), Alloy 1.20.1, Pyroscope 2.3.2,
  OTEL Collector contrib 0.162.0, OTEL Go SDK 1.47.0, PostgreSQL 18.6,
  Go 1.27.1 и 1.26.9, ядро 7.0.12-linuxkit (aarch64).
