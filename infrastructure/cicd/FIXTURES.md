Единственный источник чисел для статей серии «CI/CD на практике»

что есть, получено живым прогоном на этой машине (Windows 11 + WSL2 Ubuntu +
Docker Desktop; PostgreSQL раздела 2A проброшен на `localhost:5457`), а не
переписано из планов.

**Дата прогона: 2026-08-11.** Файл переработан в тот же день по итогам ВОСЬМИ
внешних технических ревью.

Первое: снято неверное объяснение про «задержку подхвата триггера» (артефакт 5а),
добавлен контрольный замер пола оснастки (артефакт 6), раздел DORA пересобран под
актуальную пятиметровую модель, версии actions подняты с пиннингом по commit SHA.

Второе (три блокера в связках «эксперимент → вывод»): expand-contract доведён до

Третье-восьмое (уровень 2B и инструменты наблюдения): kubernetes-сценарий доведён до трёхступенчатого
выката с промежуточной версией — двух образов не хватало ни для обещания

переведён с последовательности id на программный (sequence выдаётся вне MVCC);
мониторинг регрессий параметризован по уходящему образу, иначе второй выкат
проверялся фильтром по ушедшей версии и давал неизбежный ноль.

Каждое демо самопроверяемо: печатает падающий вариант и завершается с ошибкой,
если ожидаемого контраста нет. Абсолютные времена host-зависимы — переносится
характер зависимости, не сами числа.

# Раздел 1: github-actions

⚠️ **Чего здесь нет по построению.** Тайминги job'ов в облаке GitHub Actions и
реальный OIDC-обмен локально честно не воспроизвести — их в стенде нет. Локальные
секунды ниже — это тот же МЕХАНИЗМ (кэш зависимостей, кэш слоёв), замеренный без
облака; на CI переносится характер (тёплый кэш заметно дешевле холодного; порядок
слоёв определяет глубину инвалидации), не абсолютные числа.

## Артефакт 1: валидация workflow (actionlint)

Команда: `./scripts/lint-workflows.sh`.

```
actionlint v1.7.12

=== РАБОЧИЙ ВАРИАНТ: реальные workflow стенда ===
  .github/workflows/ci.yml
  .github/workflows/reusable-build.yml
actionlint: чисто — все workflow валидны.

=== ПАДАЮЩИЙ ВАРИАНТ: workflow с битым выражением ===
.github/workflows/broken-demo.XXXXXX.yml:9:24: property "nonexistent" is not defined in object type {} [expression]
  |
9 |       - run: echo "${{ inputs.nonexistent }}"
  |                        ^~~~~~~~~~~~~~~~~~
actionlint правильно отверг битый workflow (ненулевой код выше).
```

**Разбор.** Реальные workflow стенда (reusable workflow + caller с matrix +
composite action + OIDC-публикация) проходят actionlint. Падающий вариант —
временный workflow с обращением к контексту `inputs` там, где он недоступен (вне
`workflow_call`): actionlint ловит это статически, до первого запуска в облаке.
Ни `hugo build` статьи, ни человеческий глаз в ревью такую ошибку в `${{ }}` не
замечают.

**Падающий вариант**: если бы actionlint не проверял выражения, битый workflow
прошёл бы (код 0) — скрипт на этот случай завершается с ошибкой.

## Артефакт 2: эффект кэша зависимостей

Команда: `./scripts/cache-effect-demo.sh`. `GOCACHE`/`GOMODCACHE` во временных
каталогах (холодный старт честно пуст), `go build ./...`.

Четыре прогона, включая независимое воспроизведение ревьюером:

| Прогон | холодный | тёплый (без правок) | после правки кода |
|---|---|---|---|
| 4 (ревьюер, независимо) | 18.808 с | 10.388 с (**×1.8**) | — |
| 3 | 11.619 с | 5.367 с (×2.2) | 5.776 с (×2.0) |
| 1 | 29.254 с | 5.571 с (×5.3) | 6.400 с (×4.6) |
| 2 | 12.328 с | 5.593 с (×2.2) | 7.266 с (×1.7) |

**Разбор.** Тёплый кэш во всех прогонах заметно быстрее холодного, а сборка
после правки исходника — быстрее холодной: build-кэш пакета инвалидируется, но
модули берутся из `GOMODCACHE`, качать заново не нужно.

**⚠️ Оговорка про абсолютные числа.** Холодное время сильно варьируется (29.3 с
против 12.3 с в двух прогонах): в него входит скачивание зависимости через
GOPROXY, которое зависит от прогрева кэша прокси и сети. Устойчивая, переносимая
часть — **тёплый кэш заметно дешевле холодного, а правка кода не роняет кэш
зависимостей**. Величину выигрыша обобщать нельзя: по четырём прогонам (включая
независимый прогон ревьюера) она колеблется от **×1.8 до ×5.3**, потому что в
холодное время входит скачивание зависимостей — оно зависит от сети, прогрева
прокси и загрузки машины. Слово «кратно» для нижней границы этого диапазона уже
слишком сильное; в статьях используется «заметно/в разы» с указанием диапазона.
Самопроверка скрипта требует лишь `тёплый < холодный` — то есть проверяет
наличие эффекта, а не его величину.

**Падающий вариант**: если бы кэш не действовал, тёплая сборка не была бы быстрее
холодной — скрипт на этот случай завершается с ошибкой.

# Раздел 2: zero-downtime

## Уровень A — локально (compose + loadgen)

PostgreSQL 18.4 в compose (`localhost:5457`), Go-загрузчик постоянного трафика,
запуск из WSL. Стенд перед прогоном пересоздан начисто (`docker compose down -v
&& up -d`).

### Артефакт 4: наивное переименование под нагрузкой (падающий вариант)

Команда: `./scripts/naive-rename-demo.sh`. Загрузчик по старой схеме
(`amount_cents`), 6 с, `RENAME` на 3-й секунде.

Два живых прогона:

```
Прогон 1: выполнено=618 ошибок=582
Прогон 2: выполнено=623 ошибок=576
первая ошибка: ERROR: column "amount_cents" ... does not exist (SQLSTATE 42703)
```

**Разбор.** После `ALTER TABLE ... RENAME COLUMN amount_cents TO total_cents`
все запросы старого кода к `amount_cents` падают. За ~3 секунды под нагрузкой это
~580 ошибок. Тезис: zero-downtime ломает не факт деплоя, а несовместимое
изменение СХЕМЫ под работающим старым кодом.

**Падающий вариант** — это и есть данный сценарий; число ошибок host-зависимо
(576–582 в двух прогонах), но качественный факт (сотни ошибок) устойчив. Скрипт
завершается с ошибкой, если ошибок вышло 0.

### Артефакт 5: expand-contract под нагрузкой (рабочий вариант)

Команда: `./scripts/expand-contract-demo.sh`. Та же нагрузка, переход через три
версии кода (old → dual → new) и шесть шагов схемы: expand → dual-write →
backfill → переключение чтения → contract → возврат `NOT NULL`.

Живые прогоны дали идентичный результат:

```
old:  выполнено≈800 ошибок=0
dual: выполнено≈800 ошибок=0
new:  выполнено≈600 ошибок=0
ИТОГ: ошибок old=0, dual=0, new=0, всего=0
backfill: 6 батчей
итоговая схема: total_cents:NO
```

**⚠️ Шаг 6 и проверка схемы добавлены по итогам второго ревью.** До этого демо
доказывало только «перешли без ошибок» и умалчивало, что приходило к ДРУГОЙ
схеме: наивный `RENAME` сохраняет исходный `NOT NULL`, а expand начинается с
nullable-колонки и `NOT NULL` не возвращал. Прямая проверка это подтвердила —
после наивного `RENAME` `total_cents` имела `is_nullable=NO`, после
expand-contract `YES`. Сравнение двух способов было нечестным: они давали разный
результат.

Инвариант теперь восстанавливается после contract, и не прямым `SET NOT NULL`
(он сканирует таблицу под `ACCESS EXCLUSIVE` — ровно тот простой, которого мы
избегаем), а безопасной последовательностью:

```sql
ALTER TABLE orders ADD CONSTRAINT total_cents_not_null
      CHECK (total_cents IS NOT NULL) NOT VALID;   -- без скана существующих строк
ALTER TABLE orders VALIDATE CONSTRAINT total_cents_not_null;  -- скан под SHARE UPDATE EXCLUSIVE
ALTER TABLE orders ALTER COLUMN total_cents SET NOT NULL;     -- PG 12+: скана нет
ALTER TABLE orders DROP CONSTRAINT total_cents_not_null;
```

Скрипт завершается с ошибкой, если итоговая схема не равна ровно
`total_cents:NO`, — то есть эквивалентность результата теперь проверяется, а не
подразумевается.

**Разбор.** То же переименование, что в артефакте 4, под той же нагрузкой, но
без единой ошибки. Единственная переменная против наивного варианта — способ
перехода. Ключевые решения, найденные живым прогоном:

- **dual-write делает КОД (промежуточная версия `-schema=dual`)** — как при
  настоящем деплое промежуточной версии. Альтернатива (синхронизация колонок
  триггером БД) тоже работоспособна; чем именно они отличаются и чего триггер
  НЕ делает — отдельный замер, артефакт 5а.
- **contract атомарен**, а `amount_cents` заранее переведён в nullable в expand —
  иначе новый код, не пишущий `amount_cents`, упал бы на `NOT NULL`.

## Артефакт 5а: когда начинает действовать триггер, созданный под нагрузкой

Команда: `./scripts/trigger-timing-demo.sh`.

**⚠️ Этот раздел заменяет неверное утверждение из первой редакции файла.** Там
было записано: «часть открытых соединений подхватывает новый триггер с задержкой
— 210 из 500 вставок прошли мимо него». Число было настоящим, **объяснение —
ложным**. PostgreSQL инвалидирует кэш системного каталога для всех сессий, и
после `COMMIT` команды `CREATE TRIGGER` применимый row-level триггер срабатывает
для каждой следующей изменяемой строки независимо от возраста соединения. Прежний
замер просто считал все строки с `NULL` за окно нагрузки, не разделяя их моментом
коммита DDL, — то есть в «пропущенные» попали строки, вставленные **до** того,
как триггер вообще появился.

**⚠️ Метод переделан дважды, по итогам двух ревью.**

Версия 1 делила вставки по метке `clock_timestamp()`, снятой той же командой,
что создаёт триггер. Это НЕ момент commit: оператор выполняется внутри
транзакции, а commit происходит после него.

Версия 2 делила по `max(id)`. Тоже не строго: значения sequence выдаются **вне
MVCC** (`nextval` не ждёт commit и не откатывается), а `SELECT max(id)` видит
только закоммиченные строки — поэтому строка могла получить id до commit DDL, а
стать видимой после, и попасть не в ту половину. Вдобавок `loadgen` выполняет
операции строго последовательно, так что заявление про «те же соединения пула»
под КОНКУРЕНТНОЙ нагрузкой на нём проверить было нельзя.

Версия 3 (текущая) снимает обе претензии. Барьер программный, а не по данным, и
нагрузка честно конкурентная — отдельный `trigger-probe` (Go) держит N
соединений, у каждого своё:

```
фаза A — N воркеров пишут customer=before, соединения открыты и прогреты;
         в это время выполняется CREATE TRIGGER;
барьер — probe ждёт строку в stdin; скрипт пишет её ТОЛЬКО после того, как
         команда CREATE TRIGGER вернула управление, то есть после COMMIT;
фаза B — ТЕ ЖЕ соединения делают фиксированное число вставок customer=after.
```

Живой прогон (8 воркеров, по 25 вставок в фазе B):

```
пул открыт: 8 соединений
фаза A (до барьера): вставлено=3484
фаза B (после барьера): вставлено=200
ошибок=0

фаза A (до барьера):    всего=3484  из них total_cents IS NULL=3460
фаза B (после барьера): всего=200  из них total_cents IS NULL=0
```

**Разбор.** В фазе B мимо триггера не прошла ни одна вставка — при том, что
писали их 8 соединений, открытых ДО создания триггера, и писали конкурентно.

Показательна деталь фазы A: из 3484 строк заполнено 24. Это вставки, попавшие в
промежуток между commit DDL и снятием барьера, — прямое свидетельство, что
триггер начал применяться сразу после commit, ещё до того, как скрипт перевёл
воркеров в фазу B. Никакой «задержки подхвата» нет.

Практический вывод для expand-contract: триггер как механизм двойной записи
работает надёжно, но он не закрывает окно между началом expand и своим
появлением — эти строки остаются незаполненными, и их подбирает backfill (шаг 3).
Выбор «код против триггера» решается не надёжностью срабатывания, а другими
соображениями: где держать логику перехода, как её выкатывать и откатывать.

**Падающий вариант**: если бы открытые соединения подхватывали триггер с
задержкой, ненулевое число `NULL` было бы и после коммита DDL. Скрипт завершается
с ошибкой, если такое встретится (а также если нагрузка не покрыла обе стороны
момента DDL — тогда замер несостоятелен).

**Урок метода.** Числа были верны в обоих замерах; разошлись выводы. Отличила их
не перепроверка арифметики, а вопрос «с чем именно сравнивается» — и контрольная
точка, разделяющая наблюдение по моменту события.

Прогон переснят 2026-10-23 с рекомендуемой функцией синхронизации
(`sql/sync-trigger.sql`). После добавления в неё проверки конфликта при INSERT
замер повторён и прошёл с той же картиной (фаза A 1663 / 1639 с `NULL`, фаза B
200 / 0); выше оставлены числа прогона, на которые ссылается статья. Вставки
замера задают одну колонку, и новая ветка их не касается.

## Артефакт 5б: триггер двойной записи и UPDATE

Команда: `./scripts/trigger-update-demo.sh`.

Правило «заполнить пустую колонку из заполненной» (первая редакция стенда)
годится только для INSERT. При UPDATE обе колонки уже заполнены, и оно ничего
не делает: старая версия приложения меняет `amount_cents` со 100 на 200,
`total_cents` остаётся 100. Замер триггера по вставкам этого не видел.
Рекомендуемая функция разбирает UPDATE по тому, какую колонку изменил запрос, а
расхождение обеих отвергает — и при UPDATE, и при INSERT (проверка вставки
добавлена по второму ревью: заданные обе и разные колонки первая редакция
функции пропускала). Скрипт гоняет одни и те же обновления на обеих
функциях; наивная обязана показать расхождение, иначе контрпример ничего не
проверяет.

```
$ ./scripts/trigger-update-demo.sh
=== наивная функция (только IS NULL) ===
  ok    INSERT старым кодом: 100/100
  UPDATE старым кодом, amount_cents = 200: 200/100
  ok    наивная функция показывает расхождение: 200/100
=== рекомендуемая функция (sql/sync-trigger.sql) ===
  ok    INSERT старым кодом: 100/100
  ok    UPDATE старым кодом, amount_cents = 200: 200/200
  ok    UPDATE новым кодом, total_cents = 300: 300/300
  ok    UPDATE обеих колонок одним значением: 400/400
  ok    UPDATE обеих колонок разными значениями: отвергнут
  ok    строка после отвергнутого UPDATE: 400/400
  ok    INSERT новым кодом (только total_cents): 700/700
  ok    INSERT обеих колонок одним значением: 800/800
  ok    INSERT обеих колонок разными значениями: отвергнут
  ok    строк 'conflict' после отвергнутого INSERT: 0
OK: наивная функция теряет UPDATE старого кода (200/100), рекомендуемая синхронизирует
обе стороны и отвергает расходящиеся значения обеих колонок — при UPDATE и при INSERT.
```

**Падающий вариант**: любая ошибка означает необратно-совместимый переход; скрипт
завершается с ошибкой, если сумма ошибок > 0.

### Артефакт 6: блокирующий CREATE INDEX против CONCURRENTLY

Команда: `./scripts/blocking-ddl-demo.sh`. Таблица на 800000 строк (чтобы
построение индекса заняло ощутимое время), запись стартует во время построения.

Три живых прогона; третий — после добавления **контрольного замера** (три
`INSERT` без всякого DDL), который даёт пол измерения:

| Прогон | контроль без DDL | блокирующий `CREATE INDEX` | `CREATE INDEX CONCURRENTLY` |
|---|---|---|---|
| 1 | — | 761 мс, ожиданий в логе: 1 | 120 мс, 0 |
| 2 | — | 760 мс, ожиданий в логе: 1 | 115 мс, 0 |
| 3 | **116 мс** | 860 мс, ожиданий в логе: 1 | 123 мс, 0 |

За вычетом пола оснастки (прогон 3): блокирующий — **+744 мс** сверх контроля,
`CONCURRENTLY` — **+7 мс**.

**Разбор.** `CREATE INDEX` берёт на таблицу блокировку, конфликтующую с записью:
пока индекс строится, запись ждёт, и лог PostgreSQL фиксирует 1 ожидание
блокировки. `CREATE INDEX CONCURRENTLY` записи не блокирует: ожиданий в логе 0,
а задержка неотличима от контрольной.

**Контрольный замер добавлен по итогам ревью** — в первой редакции здесь стояло
утверждение, что 115–120 мс «почти целиком накладные расходы оснастки», но
замера, который бы это показал, не было. Теперь есть: контроль 116 мс,
`CONCURRENTLY` 123 мс — разница 7 мс, то есть утверждение подтверждено числом, а
не догадкой.

**⚠️ Оговорка про `CONCURRENTLY`.** «Не блокирует запись» ≠ «бесплатен». Он
делает два прохода по таблице, ждёт завершения транзакций, начатых до него,
дольше грузит систему, не может выполняться внутри транзакционного блока, а при
сбое оставляет индекс в состоянии `INVALID`, который нужно удалять и строить
заново. Переносимая величина — **контраст по блокировке записи**, а не
абсолютные миллисекунды.

**Падающий вариант** — сам блокирующий `CREATE INDEX`; скрипт завершается с
ошибкой, если блокирующий вариант не задержал запись заметно дольше CONCURRENTLY.

## Уровень B — k8s-volga (окно сосуществования версий в rolling update)

Живой прогон на тестовом кластере **k8s-volga** (Talos v1.13.6, Kubernetes
v1.36.2, containerd 2.2.5, 3 CP + 3 worker). Приложение — Deployment на 3
реплики, **три образа** из одного Dockerfile (`SCHEMA=old|dual|new`), выкат в
две ступени: `v1` → `dual` → `v2`. Оба сценария **переисполнены
2026-08-11 после правок по ревью** — на том же кластере, теми же образами
(`:v1`/`:v2` в Harbor не пересобирались), с изменёнными манифестами
(`emptyDir` вместо `nfs-csi`, `securityContext` под PodSecurity restricted).
Версии кластера при переисполнении те же; числа не изменились. Приложение — Deployment на 3 реплики, образы v1
(SCHEMA=old, `amount_cents`) и v2 (SCHEMA=new, `total_cents`); readiness
`/healthz` обращается к своей колонке. Rolling update с `maxUnavailable=0,
maxSurge=1`. Каждый прогон стартует с чистого namespace и убирает его за собой.

**⚠️ Что именно измеряется.** Метрика уровня B — **readiness подов**, а не
клиентский трафик и не фактическая доступность сервиса. Под, ушедший в
`NotReady`, исключается из endpoints Service, то есть регрессия readiness
означает сокращение обслуживающих реплик; но сколько при этом получил ошибок
реальный клиент, здесь не замерялось. Ошибки клиента под нагрузкой меряет
уровень A (артефакты 4–5), на локальном PostgreSQL.

**Сигнал = регрессия старых подов.** Считаем максимум одновременно v1-подов,
у которых readiness=false И которые НЕ в состоянии Terminating (`deletionTimestamp`
пуст) — то есть под ДОЛЖЕН обслуживать, но не может. Это отсекает две нормальные
для любого rolling update ситуации: транзиторно НЕготовые новые v2-поды при
старте и штатно завершающиеся старые поды. (Первые редакции критерия считали
любой НЕготовый под и давали ложные срабатывания — 2 у expand-contract из-за
стартующих v2 и завершающегося v1; уточнение до «живой v1 без deletionTimestamp»
их убрало.)

### Артефакт 9: наивный выкат роняет старые поды (падающий вариант)

Команда: `./k8s/naive-rollout-demo.sh`. Несовместимая миграция (`RENAME
amount_cents TO total_cents`) + `kubectl set image` на v2.

Живые прогоны: **максимум НЕготовых старых (v1) подов = 3 и 2** (исходная пара)
и **3 и 2** при переисполнении после правок по ревью — числа воспроизвелись
без изменений.

**Разбор.** После RENAME все живые v1-поды обращаются к пропавшей `amount_cents`,
их `/healthz` отдаёт 503 → readiness падает. При `maxUnavailable=0` они ещё не
удалены (rolling ждёт готовности новых), поэтому наблюдаются одновременно
НЕготовыми: до 3 из 3 реплик. Разброс 2–3 между прогонами — от шага опроса
(0.3 с) относительно скорости, с которой rolling заменяет упавшие реплики
новыми; воспроизводимо здесь то, что регрессия старых подов наблюдается, а не её
точная величина — четырёх прогонов мало для более сильного утверждения.

**Падающий вариант** — это данный сценарий; скрипт завершается с ошибкой, если
ни один старый под не регрессировал (0).

### Артефакт 10: expand-contract выкат без регрессии и с безопасным откатом

Команда: `./k8s/expand-contract-rollout-demo.sh`. Сценарий **трёхступенчатый**:
`v1` → `dual` → `v2`, где `dual` собран с `SCHEMA=dual` — пишет ОБЕ колонки и
читает переходным `COALESCE(total_cents, amount_cents)`.

Почему двух образов было мало (найдено четвёртым ревью):

- `v1` пишет только старую колонку, `v2` — только новую. После начала выката
  `v2` строки новой версии не имеют старой колонки, и откат на `v1` формально
  проходит, а фактически теряет данные. Промежуточная версия — условие
  обещания «откат безопасен», а не украшение.
- Читать в промежуточной версии просто `total_cents` тоже нельзя: пока идёт
  выкат, старые поды продолжают писать только `amount_cents`, и у таких строк
  новая колонка пуста. Отсюда `COALESCE` — переходное чтение, которое берёт
  новое значение, а при его отсутствии старое.
- Readiness во всех версиях теперь падает, если читаемое **бизнес-значение**
  пусто. Прежняя проба принимала `NULL` за успех и тем самым маскировала ровно
  ту поломку, которую должна была ловить: «0 NotReady» доказывал наличие
  колонки, но не доступность данных.

**Два живых прогона (2026-08-11, после переработки):**

| Замер | Прогон 1 | Прогон 2 |
|---|---|---|
| строк с `total_cents IS NULL` после выката `dual` (добор) | 250 | 229 |
| строк без `amount_cents` во время работы `dual` | **0** | **0** |
| строк без `amount_cents` после выката `v2` | 310 | 361 |
| регрессировавших `v1`-подов в выкате 1 (`v1`→`dual`) | **0** | **0** |
| регрессировавших `dual`-подов в выкате 2 (`dual`→`v2`) | **0** | **0** |
| итоговая схема | `total_cents:NO` | `total_cents:NO` |

Контрольный наивный выкат в тех же условиях: **2** регрессировавших пода.

**Три доводки инструментов (по шестому и восьмому ревью).**

1. `cleanup_watch_files` теперь СНАЧАЛА останавливает монитор и дожидается его,
   и только потом удаляет файлы. Прежний порядок был опасен: цикл монитора
   крутится, пока НЕТ `STOPFILE`, поэтому удаление файла первым закрепляло
   условие продолжения — при аварийном выходе (ошибка `set image`, `wait_rollout`
   или DDL между стартом и остановкой) процесс оставался опрашивать кластер.

2. `psql_ddl` отличает таймаут блокировки от прочих ошибок. Раньше stderr
   подавлялся, и синтаксическая ошибка, нарушение ограничения или обрыв
   соединения трижды описывались как «блокировка не взята». Теперь повтор идёт
   только на `lock timeout`/`55P03`, а любая другая ошибка PostgreSQL выводится
   как есть и завершает шаг сразу.

   **⚠️ Первая редакция этой проверки была несостоятельной, и это отдельный
   урок.** Классификация писалась как `out="$(psql ...)"` отдельной строкой, а
   следом `rc=$?`. Под `set -e` (а все демо запускаются именно с ним) статусом
   присваивания становится статус команды, и оболочка завершает скрипт ПРЯМО
   на нём — до классификации и печати `$out`. Проверочный скрипт при этом
   `set -e` не включал, поэтому дефект не воспроизводился и был записан как
   «проверено». Нашло внешнее ревью, воспроизведя на реальном стенде.

   Исправлено переносом присваивания в условный контекст
   (`if out="$(...)"; then`). **Перепроверено ПОД `set -e`** — со строками
   `BEFORE`/`AFTER` вокруг вызова, чтобы видеть, что скрипт доживает до
   классификации: возврат ненулевой, ретраев нет (0 с вместо ≥4 с), в stderr
   исходное `ERROR: syntax error at end of input`.

   Метод-вывод: **проверку поведения при ошибке надо гонять в том же режиме
   оболочки, в каком работает боевой скрипт.** Иначе проверяется не тот код,
   который выполняется.

**Монитор регрессий сделан fail-closed (по пятому ревью).** Прежняя версия
крутила фиксированные 60 опросов (~18 с) при выкате до 120 с — хвост окна
оставался ненаблюдаемым; а `wait ... || true` глушил сбой фонового процесса, и
недоступность кластера давала «0 регрессий», неотличимый от их отсутствия.
Теперь монитор работает до явного сигнала остановки, считает выборки (в
прогонах — 20–23 за окно) и завершает сценарий ошибкой при любом сбое опроса.
Поведение проверено подменой `kubectl` на заведомо падающий: функция возвращает
ненулевой код, а не ноль.

3. Опрос кластера идёт с `--request-timeout=5s`: по умолчанию у `kubectl` он
   равен нулю, то есть без предела, и зависший API-сервер подвесил бы монитор
   вместе с ожидающим его `wait` — заявленный fail-closed превратился бы в
   «висим молча». Дополнительно `stop_watch` ждёт завершения не бесконечно, а
   до 10 с, после чего снимает процесс жёстко и возвращает ошибку; аварийный
   `cleanup` даёт 3 с grace и тоже добивает `kill -KILL`.

**Каждый выкат проверяется по СВОЕЙ уходящей версии.** Прежняя функция жёстко
фильтровала образ `v1`, поэтому на втором выкате (`dual`→`v2`) она давала
неизбежный ноль: `v1`-подов там уже нет, и проверка ничего не значила. Теперь
образ передаётся параметром (`not_ready_image_pods`), а счётчики раздельные —
`MAX_V1` и `MAX_DUAL`.

**Разбор.** Обе колонки на месте весь переход, и переходное чтение делает
данные доступными обеим работающим версиям — окна несовместимости нет ни на
одном из двух выкатов, и это подтверждено раздельными замерами.

Ключевая строка — **0 строк без `amount_cents`, пока работает `dual`**: в тот
момент откат на предыдущую версию не потерял бы ни одной записи. Скрипт падает,
если там окажется не ноль. Строка ниже (321 и 379 после выката `v2`) показывает
**границу**: как только промежуточная версия ушла, откат «через ступень» данные
бы уже потерял. Безопасен откат НА ОДНУ СТУПЕНЬ и только ДО contract; после
`DROP COLUMN` возврат к версии, читающей старую колонку, — это восстановление из
резервной копии, а не откат.

**⚠️ Ранее найденный дефект (сохранён как урок).** Добор backfill появился не
сразу: проверка итоговой схемы уронила прогон с `VALIDATE CONSTRAINT ... is
violated by some row`. Причина была в данных — строки, записанные `v1`-подами во
время выката, оставались с `NULL`, и `DROP COLUMN` потерял бы их (276 строк в том
прогоне). Переносимый вывод: **финальный backfill перед сужением схемы
обязателен, и проверять его надо постусловием.**

**Падающий вариант**: скрипт завершается с ошибкой, если в окне любого из двух
выкатов регрессировал хоть один под уходящей версии, если итоговая схема не
равна `total_cents:NO` или если во время работы `dual` нашлись строки без
`amount_cents`.

## Артефакт 8: пять метрик DORA и разоблачение KPI-театра

Команда: `./dora/dora-demo.sh`. Калькулятор (Go, покрыт тестами) на двух
фикстурах: честной (8 деплоев за 14 дней) и «театральной» (те же изменения,
каждый деплой разбит надвое — 16 деплоев).

**⚠️ Модель переработана по итогам ревью.** Первая редакция описывала «четыре
ключа» с MTTR — это устаревшая модель. Актуальная (DORA, 2024) содержит **пять**
метрик: MTTR в 2023 переименована и переопределена как *failed deployment
recovery time* (прежнее определение не отличало отказ, вызванный изменением, от
отказа по внешней причине), а в 2024 добавлена *deployment rework rate*.
Группировка тоже иная: recovery time относится к throughput, а не к стабильности.
Источники: [руководство DORA](https://dora.dev/guides/dora-metrics-four-keys/),
[история модели](https://dora.dev/insights/dora-metrics-history/).

Театральная фикстура считается в **двух вариантах разметки**: A — обе копии
аварийного деплоя помечены `rework`; B — только одна (вторая считается плановой).
Дробление в обоих одинаковое, отличается лишь классификация копий.

| Метрика | группа | честно | театр A | театр B |
|---|---|---|---|---|
| Deployment frequency | throughput | 0.571 деплоя/день | **1.143** | **1.143** |
| Change lead time (медиана) | throughput | 3h30m0s | 3h30m0s | 3h30m0s |
| Failed deployment recovery time (медиана) | throughput | 2h0m0s | 2h0m0s | 2h0m0s |
| Change fail rate | instability | 12.5% (1 из 8) | **6.2%** (1 из 16) | **6.2%** (1 из 16) |
| Deployment rework rate | instability | 12.5% (1 из 8) | 12.5% (2 из 16) | **6.2%** (1 из 16) |

**Разбор.** Дробление деплоев поднимает частоту вдвое и вдвое уполовинивает
change fail rate: инцидент один, а деплоев стало больше — вырос только
знаменатель. (В коде change fail rate считается по числу РАЗЛИЧНЫХ деплоев,
вызвавших хотя бы один инцидент, а не по числу инцидентов, — см. `FailedDeployIDs`.)

Устойчивы к этой накрутке в **обоих** вариантах разметки только **change lead
time** и **failed deployment recovery time**: коммиты и инцидент те же. Именно их
несогласованность с выросшей частотой и выдаёт подлог.

**⚠️ Вывод об устойчивости rework rate был артефактом фикстуры — исправлено по
второму ревью.** Прежняя редакция утверждала, что эта доля устойчива «по
построению», потому что дробление делит и числитель, и знаменатель. Верно это
только при разметке A. Определение метрики не предписывает, как классифицировать
копии, и при разметке B доля падает вдвое — ровно как change fail rate (12.5%
против 6.2% в таблице). То есть устойчивость следовала из выбранной
классификации, а не из свойства метрики. Оба варианта теперь считаются в демо,
и самопроверка изменена: она требует не неизменности rework rate (это закрепляло
бы артефакт), а того, чтобы A и B **различались**, — иначе зависимость вывода от
разметки нечем показать.

**⚠️ Границы того, что демо доказывает.** Оно показывает узкое: конкретная
стратегия накрутки — дробление деплоев — обнаруживается несогласованностью
метрик, опирающихся на разные события. Оно **не** доказывает, что метрики вообще
нельзя подделать: границу деплоя, классификацию rework, привязку инцидентов к
релизам и момент фиксации коммита выбирает тот же, кто отчитывается. DORA и сама
предупреждает, что метрики не должны становиться целями и требуют контекста
конкретного приложения или сервиса.

**Падающий вариант**: скрипт завершается с ошибкой, если частота театра не выше
честной (нет нарезки), если lead time или recovery time разошлись между честной
фикстурой и любым из вариантов театра, либо если rework rate в A и B совпала.
Числа детерминированы — расчёт по фикстуре, не замер живой системы.

**Валидация входных данных (добавлена по ревью).** Инцидент, ссылающийся на
несуществующий `deploy_id`, прежде мог раздуть числитель и дать change fail rate
выше 100%. Теперь такие идентификаторы не учитываются в расчёте, а `ValidateIncidents`
явно возвращает ошибку; рваный CSV, неразбираемая дата, повторяющийся `id` и
неположительный `periodDays` дают внятную ошибку вместо паники или тихого
искажения. Всё это покрыто тестами (`go test ./...` зелёный).
