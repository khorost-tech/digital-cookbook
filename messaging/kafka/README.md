# Kafka: глубокое погружение — стенды

Живые стенды к серии статей «Kafka: глубокое погружение» на [khorost.tech](https://khorost.tech).
Этот каталог — фундамент: 3-брокерный KRaft-кластер + каркасы Go/Java-клиентов,
на которые встанут следующие стенды серии (producer/consumer, consumer groups, EOS,
партиционирование, rack-awareness, отказоустойчивость и т.д.).

## Топология кластера

3 combined-ноды (`broker,controller`, без ZooKeeper), один общий `CLUSTER_ID`,
все три — voters в контроллерном кворуме.

| Нода   | node.id | rack   | internal (compose-сеть) | controller | host        |
|--------|---------|--------|--------------------------|------------|-------------|
| kafka1 | 1       | rack-a | `kafka1:9092`            | `:9093`    | `localhost:19092` |
| kafka2 | 2       | rack-b | `kafka2:9092`            | `:9093`    | `localhost:19093` |
| kafka3 | 3       | rack-c | `kafka3:9092`            | `:9093`    | `localhost:19094` |

- Сеть compose: `kafka-cookbook-net`.
- `CLUSTER_ID`: `r0mrt307TrOiv10ImOQjHw` (сгенерирован `kafka-storage.sh random-uuid`, зашит в compose).
- Bootstrap для клиентов **внутри** сети (контейнеры на `kafka-cookbook-net`):
  `kafka1:9092,kafka2:9092,kafka3:9092`.
- Bootstrap **с хоста**: `localhost:19092,localhost:19093,localhost:19094`.
- Порты `19092-19094` выбраны свободными на момент создания стенда (2026-07-08) —
  в репозитории заняты 5432/5433/5440/5441/5442 (postgres) и 9092/9096 (kafka,
  single-node стенд `java-deep-dive/docker/compose.yml`). При конфликте на другой
  машине — поменяйте порты в `compose/compose.yml` и переменные `KAFKA_ADVERTISED_LISTENERS`.

### Дефолты надёжности

`KAFKA_DEFAULT_REPLICATION_FACTOR=3`, `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=3`,
`KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR=3`, `KAFKA_TRANSACTION_STATE_LOG_MIN_ISR=2`,
`KAFKA_MIN_INSYNC_REPLICAS=2` — кластер переживает потерю одного брокера без потери
доступности на запись (RF=3, min.insync.replicas=2). `broker.rack` задан разным на
каждой ноде — заготовка для демонстрации rack-aware размещения реплик в одном из
следующих стендов серии.

## Как поднять кластер

```bash
docker compose -f kafka/compose/compose.yml up -d
docker compose -f kafka/compose/compose.yml ps        # дождаться "healthy" на всех трёх
docker compose -f kafka/compose/compose.yml down -v   # снести вместе с volumes
```

## Стенд #1: лог, топики, партиции (`log-basics`)

Демонстрирует ментальную модель лога Kafka: топик `demo-log` (3 партиции,
RF=3), детерминированное `key → partition` (дефолтный партиционер — murmur2
хэш ключа), и то, что offset строго монотонно растёт **в пределах одной
партиции** (глобального порядка по топику нет). Сценарий один и тот же на
Go (`go/log-basics/main.go`, franz-go) и Java (`java/log-basics/`,
kafka-clients) — оба шлют по 5 сообщений на каждый из 6 ключей
(`user-1`…`user-6`), чередуя ключи по раундам, затем читают весь топик с
начала и печатают `(partition, offset, key, value)`.

Программные ассерты (падают при расхождении): все сообщения одного ключа —
в одной партиции; offset в партиции растёт на 1 без пропусков; отправлено ==
получено.

### Запуск

```bash
# Go
docker run --rm --network kafka-cookbook-net -v "$(pwd)/go:/app" -w /app golang:1.25 \
  go run ./log-basics -brokers=kafka1:9092,kafka2:9092,kafka3:9092

# Java
docker run --rm --network kafka-cookbook-net -v "$(pwd)/java:/app" -w /app maven:3.9-eclipse-temurin-25 \
  sh -c "mvn -q -pl log-basics -am package -DskipTests && java -jar log-basics/target/log-basics.jar"
```

Оба клиента идемпотентно пересоздают `demo-log` перед прогоном (delete+create),
так что вывод воспроизводим с чистого листа при повторном запуске.

### Реальный прогон (проверено живьём 2026-07-08)

Распределение ключей по партициям **детерминировано**: `murmur2(key) % 3` — чистая функция от байтов ключа и числа партиций, поэтому даст ровно этот результат на любом хосте и в любом прогоне (при тех же ключах и числе партиций). Это НЕ host-зависимая величина, в отличие от throughput/latency в поздних стендах серии.

30 сообщений отправлено / 30 получено на обоих клиентах. Распределение
ключей по партициям **совпало между Go (franz-go) и Java (kafka-clients)
день в день, offset-в-offset**:

```
partition 0: (пусто)
partition 1: user-4, user-5
partition 2: user-1, user-2, user-3, user-6
```

Оба клиента сошлись на этом распределении и на одинаковых офсетах внутри
партиций (0..9 в partition 1, 0..19 в partition 2) — идентичный вывод byte
in byte, кроме языка рантайма.

> **Content-note.** Ключ гарантирует **одну и ту же** партицию для
> одинакового ключа (упорядоченность в пределах ключа) — это подтверждено
> прогоном: `user-4` всегда в partition 1, `user-1` всегда в partition 2 и
> т.д. Но **разные** ключи НЕ гарантированно попадают в разные партиции:
> дефолтный партиционер — это `(murmur2(key) & 0x7fffffff) % partitions`, и
> в этом прогоне все 6 ключей схлопнулись всего в 2 из 3 партиций
> (`partition 0` не досталось ни одного ключа) — чистая коллизия хэша на
> конкретных строковых ключах, не баг стенда. При других ключах или другом
> числе партиций распределение будет другим — это демонстрирует именно
> отсутствие гарантии равномерности, а не её наличие.
>
> Распределение Go↔Java совпало не случайно: franz-go по умолчанию
> использует `UniformBytesPartitioner` с `keys=true`, который для записей с
> ключом хэширует **тем же алгоритмом и той же формулой**, что дефолтный
> партиционер Java-клиента (`KafkaHasher` в franz-go — прямая ссылка на
> `org.apache.kafka.clients.producer.internals.DefaultPartitioner` в
> исходниках библиотеки). Это подтверждено и по исходному коду
> (`pkg/kgo/partitioner.go` в franz-go v1.21.5), и живым прогоном выше —
> при использовании другого партиционера (например, ручного или
> sticky-без-ключа) результат мог бы отличаться.

## Стенд #2: consumer groups и ребалансировка (`consumer-groups`)

Демонстрирует consumer groups на топике `demo-groups` (6 партиций, RF=3):
join/leave-ребаланс, четыре стратегии назначения партиций (eager vs
incremental cooperative), static membership (`group.instance.id`) и разницу
auto-commit / ручного commitSync. Сценарий идентичен на Go (`franz-go`) и
Java (`kafka-clients`), реализован как 4 независимых сценария (свой
`group.id` у каждого, топик общий) — `rebalance` | `strategies` | `static` |
`commits` | `all` (по умолчанию).

Во всех сценариях продюсинг в топик идёт **во время** работы консьюмеров
(не только до старта) — см. content-note ниже про то, зачем это важно для
наглядности живого перераспределения чтения.

### (1) Ребаланс при подключении/отключении

`consumer-1` в одиночку получает все 6 партиций; подключаем `consumer-2`,
затем `consumer-3` — ребаланс, партиции перераспределяются; отключаем их по
одному — обратный ребаланс. Стратегия зафиксирована на `range` (классика,
eager) — самый простой случай для первого знакомства с revoke/assign.
Логируется каждое `ASSIGNED`/`REVOKED`-событие через `ConsumerRebalanceListener`
(Java) / хуки `kgo.OnPartitionsAssigned`/`OnPartitionsRevoked` (Go).

### (2) Стратегии назначения: range / roundrobin / sticky / cooperative-sticky

3 консьюмера стабилизируют назначение на выбранной стратегии, затем
подключается четвёртый — сравниваем, что именно каждая стратегия отзывает у
уже работающих членов:

- **range / roundrobin / sticky** — eager-протокол: у ВСЕХ существующих
  членов отзывается **всё** их текущее назначение (stop-the-world), даже у
  тех, чьи партиции в итоге не поменялись, — потом происходит повторный
  `JoinGroup`/`SyncGroup` и назначение считается заново с нуля (sticky
  отличается от range/roundrobin только тем, ЧТО именно назначается заново,
  а не тем, КАК проходит сам ребаланс — revoke всё равно полный).
- **cooperative-sticky** — incremental-протокол (KIP-429): у члена, чьи
  партиции не переезжают, `onPartitionsRevoked` вызывается с **пустым**
  множеством (либо не вызывается вовсе); переезжает только реально нужное
  подмножество, причём двумя раундами — сначала прежний владелец явно
  отзывает ровно то, что должно переехать (и только это), затем во втором
  раунде это подмножество достаётся новому члену.

Классификация revoke-события в стенде (`ВСЁ` / `ПУСТО` / `ЧАСТЬ`)
вычисляется не по признаку "пусто/не пусто", а сравнением размера revoke-сета
с фактическим размером назначения члена ДО этого события — иначе
непустой-но-частичный cooperative-revoke ошибочно классифицируется как
"stop-the-world" (это реальный баг ранней версии стенда, пойманный на живом
прогоне: cooperative-sticky отозвал `[4]` у члена с `[0 4]`, что НЕ "всё
назначение", а инкрементальный переезд одной партиции).

### (3) Static membership (`group.instance.id`)

Два статических члена стабилизируют назначение; один делает graceful
`close()` и почти сразу переподключается с **тем же** `group.instance.id` —
в пределах `session.timeout.ms`. Ассерты: (a) рестартовавший член получает
**точно те же** партиции обратно; (b) второй член **не получает ни одного**
`revoke`/`assign`-события за всё время — группа не ребалансировалась. Для
контраста тут же — та же процедура **без** `group.instance.id`: рестарт
триггерит немедленный ребаланс у второго члена (graceful `close()` шлёт
`LeaveGroupRequest` для динамических членов, но НЕ для статических — KIP-345
в Java, тот же принцип в franz-go, см. content-notes).

### (4) Commit offset: auto vs manual

- **auto-commit** (риск at-most-once): консьюмер раздаёт полученные записи
  в фоновые "воркеры" (имитация асинхронной обработки) и сразу возвращается
  за следующей пачкой, не дожидаясь их завершения; короткий
  `auto.commit.interval.ms` гарантированно обгоняет обработку. При "краше"
  до завершения воркеров офсет уже закоммичен дальше — потерянные записи
  никогда не будут переданы повторно.
- **ручной commitSync-аналог** (at-least-once): autocommit выключен, коммит
  — синхронный вызов **после** обработки всей пачки. При "краше" до коммита
  необработанная (точнее, необзафиксированная) пачка передоставляется
  заново новому консьюмеру той же группы — дубли обработки возможны, потерь
  нет. Отдельно измеряется content-note: N коммитов по одной записи
  ощутимо медленнее одного батч-коммита на N записей (N сетевых round-trip'ов
  вместо одного).

### Реальный прогон (проверено живьём 2026-07-08, `-scenario=all` / `all`)

**Сценарий 1 (range, eager) — join/leave.** `consumer-1` в одиночку получает
`[0 1 2 3 4 5]`. `consumer-2` подключается → у `consumer-1` `REVOKED [0 1 2]`
(всё текущее), затем `ASSIGNED [0 1 2]` `consumer-1` / `ASSIGNED [3 4 5]`
`consumer-2` — итог `c1=[0 1 2] c2=[3 4 5]`. `consumer-3` подключается →
снова полный revoke у обоих, итог `c1=[0 1] c2=[2 3] c3=[4 5]`. Отключаем
`consumer-3`, затем `consumer-2` — партиции возвращаются `consumer-1`
целиком. На всех шагах: 6 партиций покрыты ровно одним консьюмером, без
пересечений (ассерт зелёный).

**Сценарий 2 — стратегии, ключевой лог (Go, идентично на Java):**

```
--- стратегия: range (IsCooperative=false) ---
[3.213s] consumer-a revoked при вступлении consumer-d: [0 1] — ВСЁ текущее назначение (stop-the-world, eager)
[3.213s] consumer-b revoked при вступлении consumer-d: [2 3] — ВСЁ текущее назначение (stop-the-world, eager)
[3.213s] consumer-c revoked при вступлении consumer-d: [4 5] — ВСЁ текущее назначение (stop-the-world, eager)

--- стратегия: roundrobin (IsCooperative=false) ---
[6.929s] consumer-a revoked при вступлении consumer-d: [0 3] — ВСЁ текущее назначение (stop-the-world, eager)
... (аналогично b, c — все полностью)

--- стратегия: sticky (IsCooperative=false) ---
[10.745s] consumer-a revoked при вступлении consumer-d: [0 4] — ВСЁ текущее назначение (stop-the-world, eager)
... (аналогично b, c — все полностью; sticky отличается лишь тем, ЧТО
     назначается заново — a=[0] после revoke [0 4] — а не тем, КАК ребаланс
     проходит)

--- стратегия: cooperative-sticky (IsCooperative=true) ---
[12.118s] consumer-a REVOKED [] (пусто — инкрементальная ребалансировка ничего не забрала)
[12.118s] consumer-b REVOKED [] (пусто)
[12.118s] consumer-c REVOKED [] (пусто)
[12.121s] consumer-a revoked при вступлении consumer-d: [] — ПУСТО (партиции не переезжали)
[12.121s] consumer-a REVOKED [4] текущее назначение: [0]   <- второй раунд: только реально переезжающая партиция
[12.626s] consumer-d ASSIGNED [4]                          <- досталась новому члену только теперь
```

Для eager-стратегий (range/roundrobin/sticky) **все три** уже работавших
консьюмера получили `REVOKED` со своим **полным** текущим назначением при
каждом вступлении нового члена — классический stop-the-world. Для
cooperative-sticky — `REVOKED []` (пусто) у всех троих в первом раунде,
затем **только у одного** (`consumer-a`) непустой, но частичный revoke
(`[4]`, при этом `[0]` остался при нём), и лишь во втором раунде эта
партиция попадает к `consumer-d`. Реального stop-the-world НЕ было ни разу.

**Сценарий 3 — static membership.** Оба клиента (Go и Java) подтвердили:
рестарт `static-a` с тем же `group.instance.id` занял `166–512ms`
(host-зависимо, оба укладываются на порядки меньше `session.timeout=12s`),
партиции вернулись **той же** статике `[0 3 4]`/`[0 1 2]` без изменений, а
`static-b` за всё время **не получил ни одного** revoke/assign-события.
Контрольный контраст без `group.instance.id`: та же процедура — `dynamic-d`
немедленно получил revoke/assign при рестарте `dynamic-c` (в Go, где
дефолтный балансировщик franz-go — `cooperative-sticky`, `dynamic-d` отделался
пустым `REVOKED []`/`ASSIGNED []` — событие всё равно засчитано и
зафиксировано; в Java, где дефолт классического протокола фактически
eager, `dynamic-d` получил **полный** `REVOKED [3 4 5]` и пересобрал
назначение заново).

**Сценарий 4 — commit offset.** auto-commit (интервал 100мс,
"обработка" 400мс/запись в фоновом воркере): в обоих прогонах (Go и Java)
консьюмер успел раздиспатчить все 20 сообщений, но auto-commit закоммитил
позицию чтения раньше, чем воркеры закончили; после "краша" новый консьюмер
группы не увидел уже ничего нового (топик прочитан до конца) — Go-прогон
потерял **все 20/20** сообщений (0 обработано до краша, 0 передоставлено),
Java-прогон в одном из прогонов потерял **17/20** (3 воркера успели
финишировать до `close()`). Оба варианта — валидная демонстрация
at-most-once, конкретное число host-зависимо.

> **Оговорка.** Параметры демо (`auto.commit.interval.ms=100` и задержка
> обработки воркера 400мс/запись) укорочены нарочно — чтобы детерминированно
> и быстро воспроизвести потерю сообщений при auto-commit. Это **не**
> прод-дефолты: реальный дефолт Kafka для `auto.commit.interval.ms` — 5000мс.
> В проде с типичным интервалом коммита окно между "закоммичено" и "реально
> обработано" меньше относительно интервала между крахами, поэтому потеря
> конкретной записи менее вероятна — но сама семантика at-most-once
> (возможность потери при крахе между коммитом и обработкой) сохраняется
> при любых значениях интервала.

Ручной commitSync-аналог:
обработали синхронно 12 из 20 сообщений, коммитили батчами **после**
обработки, "упали" ровно на 12-й обработанной записи — 3 из 12 успели
попасть в ранее закоммиченные пачки, а последняя пачка (9 из этих 12) осталась
незакоммиченной — новый консьюмер передоставил незакоммиченный хвост (9
дублей + 8 новых = 17 записей), покрытие **20/20 без потерь** (ассерт
зелёный, at-least-once подтверждён на обоих клиентах). Замер латентности
коммита (10 записей): по одной — `11.7–13.4ms` (`~1.2–1.3ms`/коммит), одним
батчем — `~1.1ms` — на порядок быстрее (N round-trip'ов против одного).

### Content-notes

1. **Продюсинг во время работы консьюмеров — не опция, а необходимость.**
   Если продюсить только ДО подключения второго консьюмера, первый успевает
   вычитать всё до того, как второй присоединится, и живое
   перераспределение чтения между ними в логе не видно (см. урок из
   `java-deep-dive/messaging`, где именно так и получилось — `consumer-1`
   успел прочитать все 40 сообщений в одиночку). Здесь продюсер стартует
   ПОСЛЕ первого стабильного назначения и работает непрерывно весь сценарий.
2. **Eager vs incremental cooperative — не просто термины, а измеримая
   разница в логе.** Eager обязан отозвать у всех членов ИХ ПОЛНОЕ текущее
   назначение перед любым ребалансом, даже если конкретный член ничего не
   теряет по факту нового распределения — это и есть stop-the-world:
   работавшие консьюмеры простаивают, пока весь `JoinGroup`/`SyncGroup`
   не завершится заново. cooperative-sticky отзывает СТРОГО минимум и в
   два раунда, поэтому члены, чьи партиции не переезжают, продолжают
   читать без паузы всё это время.
3. **per-record commitSync ощутимо медленнее батч-коммита** — 10
   последовательных синхронных коммитов заняли на два порядка больше
   времени, чем 1 коммит на все 10 записей разом (каждый `commitSync` —
   отдельный сетевой round-trip до координатора группы). Абсолютные
   миллисекунды host-зависимы, сам факт (N round-trip'ов вместо одного) —
   нет.
4. **Что разошлось между franz-go и Java (честно, по фактическому прогону,
   не по документации):**
   - **Дефолтный балансировщик отличается.** franz-go по умолчанию
     использует ТОЛЬКО `CooperativeStickyBalancer` (подтверждено по
     исходнику `pkg/kgo/config.go`); kafka-clients по умолчанию
     фактически ведёт себя как eager на начальных ребалансах classic-протокола
     (см. сценарий static membership выше: одна и та же процедура без
     `group.instance.id` дала пустой инкрементальный revoke у Go и полный
     stop-the-world revoke у Java). Стенды сценариев "rebalance" и
     "strategies" поэтому явно фиксируют стратегию (`Balancers(...)` /
     `partition.assignment.strategy`), а не полагаются на дефолт, — кроме
     сценария "static", где дефолт оставлен намеренно, чтобы зафиксировать
     именно эту разницу.
   - **auto-commit демонстрация:** Go-прогон детерминированно терял 100%
     "в полёте" сообщений при выбранных таймингах (интервал автокоммита
     100мс ≪ задержка обработки 400мс), Java в части прогонов теряла
     чуть меньше (несколько фоновых воркеров успевали финишировать до
     `close()`) — оба честны и оба демонстрируют риск, разница чисто в
     таймингах JVM/goroutine-планировщика, не в семантике клиента.
   - Остальное — назначения стратегий (range/roundrobin/sticky/cooperative-sticky),
     static membership (KIP-345-поведение), commitSync-семантика — совпало
     между клиентами один в один.
5. **Числа host-зависимы** (латентность коммита, точный момент "краша"
   относительно фоновых воркеров, миллисекунды рестарта static-члена) — но
   САМ ФАКТ каждой демонстрируемой гарантии (eager stop-the-world vs
   incremental cooperative; static membership не триггерит ребаланс в
   пределах session timeout; at-most-once риск auto-commit; at-least-once
   гарантия ручного commit-после-обработки) детерминирован протоколом и
   воспроизводится на любом прогоне.

## Стенд #3: репликация и надёжность (`replication`)

Демонстрирует ISR-репликацию, `acks`, durability и последствия падения брокера
на топике `demo-repl` (1 партиция — чтобы "лидер партиции" был однозначен,
RF=3, `min.insync.replicas=2`). В отличие от стендов #1/#2, часть сценариев
требует убивать/поднимать брокеров `docker kill`/`docker start` С ХОСТА между
вызовами клиента (у клиента внутри контейнера нет доступа к docker socket) —
это делает bash-скрипт `ops/broker-kill.sh`. Аналог по духу — WAL
SIGKILL-стенд (`../wal/postgres/recovery-test.sh`): count строк до/после
жёсткого падения; здесь — count acked-сообщений до/после падения лидера
партиции, при живой ISR-репликации. Используется `docker kill` (SIGKILL, без
grace period), а не `docker stop` — иначе Kafka успевает выполнить controlled
shutdown с явным переносом лидерства ДО завершения процесса, что не является
настоящим крахом.

Сценарии — реализованы идентично на Go (`franz-go`) и Java (`kafka-clients`)
как набор "фаз" (`-scenario=setup|describe|acks-bench|produce|verify|minisr-produce|set-unclean`),
которые дирижирует `ops/broker-kill.sh`:

1. **acks 0 vs 1 vs all** — относительный throughput/latency (характерный
   прогон, host-зависимый) + durability-семантика.
2. **Broker-kill durability (ядро стенда):** записать N сообщений с
   `acks=all`, убить лидера партиции, показать failover на ISR-реплику и что
   count подтверждённых (acked) сообщений НЕ изменился.
3. **acks=1 + падение лидера:** попытка показать потерю неотреплицированного
   хвоста.
4. **`min.insync.replicas=2` + убить 2 из 3:** producer с `acks=all` должен
   получить `NOT_ENOUGH_REPLICAS` — durability > availability.
5. **Идемпотентный producer:** нет дублей при ретраях после падения лидера.
6. **Unclean leader election:** конфиг-переключатель + рассуждение о
   split-brain.

### Реальный прогон (проверено живьём 2026-07-08)

**(1) acks-bench.** Go (`franz-go`, 200 сообщений/уровень, последовательные
`ProduceSync`, без искусственного пайплайнинга):

```
acks=0   acked=200/200 throughput=6715.3 msg/s avg_latency=148.9µs
acks=1   acked=200/200 throughput=1463.8 msg/s avg_latency=683.2µs
acks=all acked=200/200 throughput=364.8  msg/s avg_latency=2.741ms
```

Java (`kafka-clients`) на том же топике:

```
acks=0   acked=200/200 throughput=143.9 msg/s avg_latency=6.949ms
acks=1   acked=200/200 throughput=156.3 msg/s avg_latency=6.396ms
acks=all acked=200/200 throughput=130.6 msg/s avg_latency=7.656ms
```

Go даёт чёткий монотонный порядок `0 < 1 < all` (ожидаемо: `0` не ждёт ответа
брокера вовсе, `1` — записи на диск лидера, `all` — подтверждения всех ISR).
У Java `acks=0` неожиданно НЕ самый быстрый — это эффект прогрева JVM
(тестировался первым, до JIT-разогрева); `acks=all` при этом стабильно
медленнее всего в обоих клиентах, что и есть содержательный факт. Абсолютные
числа host-зависимы (single-node docker на одной машине, без сетевой
задержки между "разными" брокерами) — не показатель прод-throughput.

**(2) Broker-kill durability — ядро стенда.** Топик `demo-repl-durability`,
30 сообщений `acks=all`, лидер до падения — `kafka-cookbook-3` (node.id=3):

```
[produce] итого: acked=30 failed=0 из 30 (acks=all idempotent=true)
--- docker kill kafka-cookbook-3 ---
[describe] leader=1(kafka-cookbook-1) replicas=[3 1 2] isr=[1 2] offline=[3]
[verify] топик demo-repl-durability: прочитано 30 записей
[verify] OK: прочитано == ожидалось == 30
```

Реальный failover: лидер `3 → 1`, ISR `[3,1,2] → [1,2]`, `3` помечен
`offline`. **Count до падения (30 acked) == count после failover (30
прочитано)** — ни одно подтверждённое сообщение не потеряно. Идентичный
результат на Java-клиенте (тот же топик, отдельный прогон):
`acked=30 failed=0` → после `docker kill` лидера `leader=3(kafka-cookbook-3)
→ leader=1(kafka-cookbook-1) isr=[1 2]` → `[verify] OK: прочитано ==
ожидалось == 30`.

**(3) acks=1 + падение лидера — честная оговорка.** Несколько живых попыток
поймать потерю неотреплицированного хвоста (синхронный producer с
`RecordRetries(0)` под `docker kill` в разных точках потока; асинхронный
fire-and-forget до 500 000 записей с намеренной паузой между отправками,
чтобы растянуть окно) — **не воспроизвели потерю ни разу**. Самая
показательная попытка: 1000 записей `acks=1`, задержка 5мс между отправками,
`docker kill` лидера в середине потока — `176 acked` (индексы 0–175),
`84 callback-ошибки` (176–259, честная эвиденция реального обрыва потока),
`740` без ответа за отведённое время. После перезапуска и восстановления
кластера consumer прочитал **ровно те же 176 индексов** (0–175) — ни один
acked не потерян. Аналогично на acks=all/idempotent-off с throttled
producer'ом — один из бордер-запросов застрял на **9.47s** (явный признак
реального retry/failover), но в итоге успешно записался без дубля.
**Вывод, а не оправдание:** окно потери у `acks=1` реально существует по
дизайну (leader пишет и подтверждает ДО того, как фолловеры зафетчили
запись), но на быстрой локальной сети с частым fetch-поллингом фолловеров
это окно узкое — поймать его через `docker kill` "снаружи" оказалось
сложнее, чем ожидалось. Это не делает `acks=1` безопасным — это лишь
означает, что наша конкретная попытка воспроизвести редкую гонку не
выиграла её в этот раз; гарантии как не было, так и нет.

> **Асимметрия Go/Java для этой охоты за гонкой.** Сценарий `produce-ff`
> (асинхронный fire-and-forget, нужен именно для попыток (2) и (3) выше —
> поймать acks=1-tail-loss и non-idempotent-дубль в узком окне) реализован
> **только в Go** (`go/replication/producer.go` — `produceFireAndForget`).
> Java-эквивалент сознательно не строился: окно гонки узкое независимо от
> клиента (см. вывод выше), и повторение той же самой неудачной попытки на
> Java не изменило бы вывод — оба клиента одинаково "не поймали" гонку по
> одной и той же причине (fetch-поллинг фолловеров успевает раньше `docker
> kill` с хоста). Дублировать код ради идентичного отрицательного результата
> сочли неоправданным. Все остальные сценарии стенда (setup/describe/
> acks-bench/produce/verify/minisr-produce, включая durability и оба
> minisr-сценария через `ops/broker-kill.sh -client=go|java`) реализованы и
> прогнаны живьём на **обоих** языках — асимметрия ограничена ровно этой
> одной, специфической для гонки, фазой.

**(4) `min.insync.replicas` — ДВА сценария, разный результат.**

По сценарию стенда (RF=3, топик `demo-repl-minisr-literal`, убить 2 из 3):
producer с `acks=all` **НЕ получил чистый `NOT_ENOUGH_REPLICAS`** —
`record failed after being retried too many times` за `6.07s`. Причина —
реальная и важная: в этой топологии все 3 ноды — combined broker+controller,
все три — voters контроллерного KRaft-кворума. Убийство 2 из 3 ломает
МАЖОРИТАРНОСТЬ кворума контроллера тоже (остаётся 1 живой voter из 3) — ISR
не может быть официально сжат (`AlterPartition` к контроллеру не проходит,
кворуму не хватает голосов на commit в metadata log), поэтому `describe`
после kill **не показывает** `offline`-реплики (`isr=[1 2 3] offline=[]`,
устаревшая информация), а producer просто зависает в ожидании ack от мёртвых
реплик и в итоге падает по исчерпанию ретраев/таймауту — не по чистому коду
ошибки. Живьём проверено: `kafka-metadata-quorum.sh describe --status` и
`kafka-topics.sh --describe` при 2 из 3 живых voters **сами виснут** (таймаут
`DisconnectException: ... due to node 3 being disconnected`).

*Контраст* (RF=2, `min.insync.replicas=2`, топик `demo-repl-minisr-contrast`,
убить ровно ОДНУ реплику-держателя, кворум контроллера остаётся 2 из 3 живых
— цел): ISR корректно сжимается контроллером до одного элемента
(`isr=[1] offline=[2]`), и producer с `acks=all` получает **чистый**
`NOT_ENOUGH_REPLICAS` за **58–813мс** (Go: 58мс, Java: 813мс) —
`Messages are rejected since there are fewer in-sync replicas than
required` — ровно так, как описано в теории. Разница между двумя
сценариями — не баг стенда, а реальный урок: **min.insync.replicas
защищает от потери данных только если контроллер способен обработать
ISR-изменение**; в минимальной 3-нодовой connected-топологии совмещение
broker+controller ролей означает, что потеря большинства брокеров ==
потеря кворума управления кластером одновременно — availability деградирует
раньше и грязнее, чем предполагает учебное объяснение "просто получите
`NOT_ENOUGH_REPLICAS`".

**(5) Идемпотентность.** Топик `demo-repl-idem-on`
(`enable.idempotence=true`, `acks=all`, дефолтные ретраи), 500 записей с
задержкой 5мс, `docker kill` лидера в середине: `499 acked` (1 ранняя ошибка
`COORDINATOR_LOAD_IN_PROGRESS` при инициализации producer ID сразу после
создания топика — не связана с kill), **0 дублей** среди 499 уникальных
индексов. Контрольный топик `demo-repl-idem-off`
(`enable.idempotence=false`, тот же сценарий): `500/500 acked`, один
запрос застрял на **9.47s** на границе kill (реальное доказательство
ретрая/failover), **0 дублей** среди 500. Как и с acks=1-потерей — не
удалось живьём поймать именно дубль (для этого нужна редкая гонка "ack
потерян ПОСЛЕ реального коммита на диск"), но сам факт срабатывания
retry/failover-механизма подтверждён живым 9.47-секундным таймаутом.

**(6) Unclean leader election.** Живьём подтверждён механизм переключения:
`kafka-configs.sh --describe` после `AlterConfigs` показывает
`unclean.leader.election.enable=true sensitive=false
synonyms={DYNAMIC_TOPIC_CONFIG:...=true, DEFAULT_CONFIG:...=false}` —
конфиг применяется на лету поверх кластерного дефолта `false`. Сам сценарий
потери данных через unclean election (реплика, отставшая и выбывшая из ISR,
становится лидером и "молча" откатывает хвост) **не продемонстрирован
живьём, честно** — по причине, найденной в пункте (4): для его
демонстрации нужно убить ДОСТАТОЧНО реплик, чтобы единственным выжившим
остался отставший фолловер, а в 3-нодовой connected-топологии это то же
самое действие ("убить 2 из 3"), которое ломает кворум контроллера
целиком — в этом состоянии контроллер физически не может провести НИКАКОЕ
переизбрание лидера, ни чистое, ни грязное. Полноценная демонстрация
unclean election потребовала бы кластер с отдельным (более широким)
controller-кворумом, не совмещённым с брокерами 1:1 — вне охвата этого
стенда.

### Content-notes

1. **`acks=all` + `min.insync.replicas` — это контракт с ДВУМЯ сторонами.**
   Он защищает данные, только если контроллер способен обработать
   ISR-изменения. В минимальном 3-нодовом кластере, где брокер и контроллер
   совмещены 1:1, потеря большинства узлов ломает ОБЕ подсистемы разом —
   практический урок для дизайна прод-кластера (контроллеров обычно
   держат нечётное число ОТДЕЛЬНО от брокеров, чтобы такого совпадения не
   было).
2. **`acks=1` — не "почти безопасно".** Мы не поймали потерю живьём в этом
   прогоне, но окно потери существует по дизайну протокола, а не по
   недосмотру: leader ack не эквивалентен репликации. Числа throughput
   `acks 0/1/all` показывают цену, которую платишь за закрытие этого окна.
3. **Идемпотентность защищает от дублей КОНКРЕТНО из-за retry САМОЙ
   client-библиотеки** (переотправка того же producer PID+sequence при
   неоднозначном исходе запроса) — не от повторной отправки на уровне
   приложения (это другая проблема, решается идемпотентностью бизнес-логики
   / дедупликацией по ключу).
4. **`docker kill` vs `docker stop`.** Мы сознательно использовали
   `docker kill` (SIGKILL, без grace period) везде, где нужен настоящий
   крах — `docker stop` даёт Kafka время на controlled shutdown с явным
   переносом лидерства, что не то же самое, что реальное падение ноды.
5. **Честность важнее эффектности.** Два сценария (acks=1-потеря,
   idempotence-дубль) не воспроизвелись — несмотря на реальные попытки с
   реальными доказательствами прерывания потока (сотни неотвеченных
   запросов, 9.47s таймаут). Мы не стали изображать успех — сам факт
   "гонку сложно поймать снаружи" тоже содержательный вывод.
6. **Где именно кончается симметрия Go/Java.** Все "фазовые" сценарии
   (setup/describe/acks-bench/produce/verify/minisr-produce) и оба
   оркестрированных broker-kill сценария (durability, minisr-contrast)
   реализованы и прогнаны живьём на обоих клиентах — `ops/broker-kill.sh`
   умеет гонять их через `-client=go|java`. Единственное исключение —
   `produce-ff` (асинхронный fire-and-forget для охоты за acks=1-tail-loss и
   idempotence-дублем): он есть только в Go, потому что окно гонки узкое
   независимо от языка клиента, и Java-повтор дал бы тот же отрицательный
   результат по той же причине — дублировать код ради идентичного "не
   поймали" не стали.

```bash
# Java — отдельная фаза (пример)
```

`java/replication/target/replication.jar` (`mvn package`) при первом

по умолчанию `go`), восстанавливает убитых брокеров (`docker start` + ждёт
`healthy`) в конце каждого сценария — кластер остаётся исправным после

ни для одного клиента (см. content-note 6 выше про асимметрию Go/Java).

## Стенд #4: хранение — retention, log compaction, компрессия (`storage`)

Демонстрирует, как Kafka физически хранит и чистит данные на диске: удаление
старых сегментов по `retention.ms`/`segment.bytes` (`cleanup.policy=delete`),
схлопывание версий по ключу + удаление ключей через tombstone
(`cleanup.policy=compact`), и относительный размер лога при разных
`compression.type`. Как и стенд #3 (`replication`), часть демонстраций
требует, чтобы ХОСТ инспектировал реальные файлы сегментов брокера и менял
dynamic broker-конфиги МЕЖДУ вызовами клиента (у клиента внутри контейнера
нет доступа к docker socket) — это делает `ops/inspect-segments.sh`.

### ⚠️ Живые открытия, изменившие дизайн стенда

1. **`segment.bytes` имеет жёсткий минимум брокера — 1048576 (1MiB).**
   Проверено живьём: `segment.bytes=2048` → `INVALID_CONFIG` (`Value must be
   at least 1048576`, `LogConfig.validate`). Ниже этого значения топик
   создать нельзя ни клиентом, ни `kafka-topics.sh`.
2. **`log.retention.check.interval.ms` — НЕ dynamic-alterable.** Попытка
   `kafka-configs.sh --entity-type brokers --entity-default --alter` падает
   с `InvalidRequestException: Cannot update these configs dynamically`.
   Дефолт брокера — 300000мс (5 мин), непригодно для живой демонстрации —
   поэтому задан статически в `compose/compose.yml`
   (`KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS=2000`).
3. **`log.cleaner.backoff.ms` — dynamic (cluster-wide default), но НЕ
   переживает пересоздание контейнеров.** У `compose/compose.yml` нет
   персистентного volume под `/tmp/kafka-logs` — `docker compose up -d`,
   который ПЕРЕСОЗДАЁТ (не просто рестартует) контейнеры, форматирует
   storage заново, и любой dynamic-конфиг, выставленный `kafka-configs.sh`
   ранее (он хранится в KRaft `__cluster_metadata`, не в
   `server.properties`), теряется. Поймано живьём: после смены
   `compose.yml` компакция вернулась к дефолтному backoff (15с) без видимой
   причины, пока не сверили `kafka-configs.sh --describe`. `ops/inspect-segments.sh`
   поэтому переустанавливает `log.cleaner.backoff.ms=1000` в начале КАЖДОГО
   прогона сценария compaction — идемпотентно, не полагается на состояние
   предыдущих запусков.
4. **franz-go по умолчанию сжимает батчи Snappy, если явно не указать
   `NoCompression()`.** Найдено при отладке retention-сценария: заполнитель
   значений (`pad-bytes` из повторяющегося символа) — крайне сжимаемые
   данные, и с дефолтной Snappy-компрессией франз-го реальный размер на
   диске оказывался в ~15 раз меньше расчётного (341 байт/запись вместо
   ~5000), roll сегментов по `segment.bytes` срабатывал в разы позже
   ожидаемого. Исправлено — `newSyncProducer` без явного кодека теперь
   явно ставит `NoCompression()` (см. `go/storage/producer.go`).
5. **Физическое удаление tombstone-маркера требует ВТОРОГО прохода log
   cleaner'а** над сегментом, который его содержит — задокументированный
   механизм Kafka (предохранитель от гонки с отстающими консьюмерами,
   см. [KAFKA-3137](https://issues.apache.org/jira/browse/KAFKA-3137)).
   Проход 1 схлопывает версии живых ключей, но ОСТАВЛЯЕТ tombstone; проход 2
   физически его удаляет — но сам не запускается без новых "грязных" данных
   у лога. На "тихом" топике (без новых записей после первой компакции)
   tombstone может не исчезать МИНУТАМИ (проверено живьём: ждали 4+ минуты
   без изменений). Стенд форсирует проход 2 явно — вторым раундом
   filler-записей (см. ниже).

### Сценарии — идентичны на Go (`franz-go`) и Java (`kafka-clients`)

Фазы (`-scenario=retention-setup|retention-produce|offsets|compact-setup|
compact-produce-business|compact-produce-filler|compact-consume|
compress-setup|compress-produce`), дирижирует `ops/inspect-segments.sh`:

1. **Retention (время/размер).** Топик `demo-storage-retention`:
   `segment.bytes=1048576` (минимум брокера), `retention.ms=8000`,
   `segment.ms` намеренно большой (roll управляется только размером —
   детерминизм демо). 600 записей без ключа, ~5000 байт значения каждая,
   БЕЗ компрессии (см. открытие 4 выше) → 3 закрытых сегмента ~1MiB. После
   ожидания `retention.ms` + `log.retention.check.interval.ms` — все три
   сегмента помечены `.log.deleted`, `earliest` offset сдвигается `0 → 600`.
   Продемонстрирована **временнáя** retention (`retention.ms`); размерная
   (`retention.bytes` — удаление старых сегментов по суммарному размеру лога)
   в стенде явно отключена (`retention.bytes=-1`) и отдельно не показана —
   механика удаления сегмента идентична, отличается лишь триггер (суммарный
   размер vs возраст).
2. **Log compaction (ЯДРО стенда).** Топик `demo-storage-compact`:
   `cleanup.policy=compact`, агрессивные `min.cleanable.dirty.ratio=0.01`,
   `delete.retention.ms=100`, `max.compaction.lag.ms=8000`. 8 ключей × 4
   раунда обновлений + 2 tombstone → "до"-снимок (сегмент ещё активен,
   компакция физически невозможна) → filler форсирует roll → проход 1
   (версии схлопнуты, tombstone жив) → второй filler форсирует ещё один
   roll → проход 2 (tombstone физически удалён) → "после"-снимок + ассерт.
3. **Компрессия.** 4 топика (`none`/`gzip`/`lz4`/`zstd`), одни и те же
   3000 записей (шаблонные JSON-подобные значения, реалистично сжимаемые),
   асинхронная батч-отправка (даёт клиенту накопить реальные батчи — иначе
   компрессия почти не работает, см. `producer.go:produceBatchedAsync`) →
   сравнение размера партиции на диске (`kafka-log-dirs.sh`).
4. **Tiered storage** — попытка + честный итог (см. ниже).

### Реальный прогон (проверено живьём 2026-07-08)

**(1) Retention.** Go: `segment.bytes=1048576`, `retention.ms=8000`, 600
записей × 5000 байт:

```
[produce] topic=demo-storage-retention: отправлено 600 записей без ключа, ~5000 байт значения каждая
[offsets] до: topic=demo-storage-retention earliest=0 latest=600 (записей сейчас читаемо: 600)
```

Сегменты ДО ожидания (broker 1, `/tmp/kafka-logs/demo-storage-retention-0/`):

```
00000000000000000000.log   1044420 байт
00000000000000000206.log   1044420 байт
00000000000000000412.log    953160 байт
00000000000000000600.log         0 байт  (активный)
```

После ожидания `retention.ms` (8с) + `log.retention.check.interval.ms` (2с,
статический) + запаса (~14с всего) — все три закрытых сегмента помечены
`.log.deleted`:

```
[offsets] после: topic=demo-storage-retention earliest=600 latest=600 (записей сейчас читаемо: 0)
[assert] OK: earliest=600 > 0 — retention сдвинул earliest offset вперёд
```

Java-клиент (топик `demo-storage-retention-java`, идентичные параметры) дал
**побайтово идентичные** размеры сегментов (`1044420 / 1044420 / 953160`) и
тот же результат ассерта — подтверждает, что оба клиента пишут одинаково
предсказуемые данные без скрытой компрессии.

**(2) Log compaction — ЯДРО СТЕНДА.** Топик `demo-storage-compact`, 8 ключей
× 4 раунда (32 записи) + 2 tombstone = 34 бизнес-записи. "До" (сегмент ещё
активен, компакция невозможна):

```
[compact-consume] до-компакции: всего читаемо 34 записей
  key=biz-key-1 (4 записей): ...-round0-... | ...-round1-... | ...-round2-... | ...-round3-...
  ...
  key=biz-key-7 (5 записей): ...-round0-... | ... | ...-round3-... | offset=32:<tombstone/null>
  key=biz-key-8 (5 записей): ...-round0-... | ... | ...-round3-... | offset=33:<tombstone/null>
```

После filler-раунда 1 (форсирует roll, закрывает сегмент с бизнес-данными) и
~6с ожидания — проход 1 схлопнул версии, но tombstone ЕЩЁ ЖИВ (см. открытие 5):

```
[compact-consume] после-прохода-1: всего читаемо 256 записей
  key=biz-key-1 (1 записей): offset=24:...-round3-...
  ...
  key=biz-key-6 (1 записей): offset=29:...-round3-...
  (+ 250 filler-записей roll-filler-*, не показаны построчно)
```

(В отдельном прогоне тот же промежуточный снимок показал tombstone ещё
присутствующим explicitно — тайминг между проходом 1 и 2 плавающий, иногда
Kafka успевает оба прохода за секунды, иногда — нет; отсюда явный второй
filler-раунд, а не расчёт на удачу.) После filler-раунда 2 (нумерация
ключей продолжена с 250 — иначе второй раунд просто перезаписал бы те же
filler-ключи первого) и ~8с ожидания — проход 2 физически удалил tombstone:

```
[compact-consume] после-компакции: всего читаемо 506 записей
  key=biz-key-1 (1 записей): offset=24:biz-key-1-round3-...(len=5000)
  key=biz-key-2 (1 записей): offset=25:biz-key-2-round3-...(len=5000)
  key=biz-key-3 (1 записей): offset=26:biz-key-3-round3-...(len=5000)
  key=biz-key-4 (1 записей): offset=27:biz-key-4-round3-...(len=5000)
  key=biz-key-5 (1 записей): offset=28:biz-key-5-round3-...(len=5000)
  key=biz-key-6 (1 записей): offset=29:biz-key-6-round3-...(len=5000)
  (+ 500 filler-записей roll-filler-*, не показаны построчно)
[assert] OK: 6 живых ключей — ровно по 1 записи (последняя версия, маркер "-round3-"); 2 tombstone-ключей — отсутствуют полностью
```

**6 живых ключей: 32 обновления → 6 итоговых записей (по одной, последний
раунд). 2 tombstone-ключа: полностью отсутствуют — ни значения, ни самого
tombstone-маркера.** Java-клиент (топик `demo-storage-compact-java`,
идентичный сценарий) дал **тот же результат**: `[assert] OK: 6 живых
ключей — ровно по 1 записи ...; 2 tombstone-ключей — отсутствуют полностью`.

**(3) Компрессия.** 3000 записей × ~300 байт шаблонных JSON-подобных
значений (`order_id=N-user=user-N-status=OK-region=eu-west-1-...`),
асинхронная батч-отправка. Размер партиции на диске (`kafka-log-dirs.sh`):

| codec  | Go (байт) | Go, во сколько раз меньше `none` | Java (байт) | Java, во сколько раз меньше `none` |
|--------|-----------|-----------------------------------|-------------|--------------------------------------|
| none   | 930016    | 1×                                  | 930538      | 1×                                     |
| gzip   | 28638     | ~32.5×                             | 46409       | ~20.1×                                |
| lz4    | 41557     | ~22.4×                             | 63790       | ~14.6×                                |
| zstd   | 17039     | ~54.6×                             | 29635       | ~31.4×                                |

Порядок одинаков на обоих клиентах — `zstd` лучше всех, `none` хуже всех,
`gzip` между `zstd` и `lz4`. Абсолютные коэффициенты различаются между
клиентами заметно (Java сжимает ощутимо слабее Go на тех же данных) — это
эффект РАЗМЕРА БАТЧА, не кодека: `franz-go` и `kafka-clients` по умолчанию
собирают батчи по-разному (`linger.ms`/`batch.size`), а компрессия работает
ПО БАТЧУ — чем больше однородных записей в одном батче, тем больше общих
паттернов сжимающему алгоритму есть на чём экономить. Характерный прогон:
абсолютные числа — host/клиент/данные-зависимы, но ОТНОСИТЕЛЬНЫЙ порядок
кодеков и сам факт "размер батча существенно влияет на сжатие" — content, а
не шум.

**(4) Tiered storage — честный итог: НЕ продемонстрировано.** Проверено
живьём на `apache/kafka:4.3.1`:

```
remote.log.storage.system.enable=false sensitive=false synonyms={DEFAULT_CONFIG:remote.log.storage.system.enable=false}
remote.log.storage.manager.class.name=null sensitive=false synonyms={}
```

`remote.log.storage.system.enable` — статический broker-конфиг (не
dynamic-alterable), по умолчанию выключен. Даже если его включить,
`remote.log.storage.manager.class.name=null` — плагин `RemoteStorageManager`
(конкретная реализация, которая физически копирует сегменты во внешнее
хранилище — S3, HDFS, локальный тест-плагин) НЕ сконфигурирован. Поиск по
образу (`find /opt/kafka/libs -iname "*tiered*" -o -iname "*remote-storage*"`)
не нашёл НИ ОДНОГО подходящего jar — только `kafka-storage-4.3.1.jar` и
`kafka-storage-api-4.3.1.jar` (core-фреймворк/интерфейсы RemoteLogManager,
без конкретной реализации). Референсный плагин Kafka (`LocalTieredStorage`)
живёт в исходниках/тестовом модуле проекта, не поставляется в релизном
Docker-образе. Полноценная демонстрация потребовала бы: собрать/достать
рабочий `RemoteStorageManager`, положить его jar в classpath брокера,
статически включить `remote.log.storage.system.enable=true` и
перезапустить ВСЕ 3 брокера с новой конфигурацией — риск для общего
кластера, которым пользуются остальные стенды серии, и объём работы за
рамками "из коробки". Решение: **не пытаться на живом shared-кластере**,
зафиксировать статус честно.

### Content-notes

1. **Retention ≠ compaction — разные вопросы, разные ответы.** Retention
   отвечает "сколько хранить" (время/размер), compaction — "что хранить"
   (последнее состояние по ключу вместо истории). Топик может использовать
   оба одновременно (`cleanup.policy=compact,delete` — не показано в этом
   стенде, но валидная комбинация для событийных стримов с TTL по ключу).
2. **Компакция — не "мгновенная дедупликация".** Она работает партиями
   (проходами log cleaner'а) над ЗАКРЫТЫМИ сегментами; активный
   (пишущийся) сегмент компакции не подлежит НИКОГДА. На топике с
   постоянным потоком записи roll происходит сам по себе; на "тихом"
   топике без нового трафика последний сегмент может годами оставаться
   некомпактированным.
3. **Tombstone — двухфазное удаление, не однократное.** Проход 1 замечает
   tombstone и устанавливает "горизонт удаления"; проход 2 (после
   `delete.retention.ms` и при наличии новых "грязных" данных) физически
   его убирает. На затихшем топике это может не случиться МИНУТАМИ или
   вообще никогда без внешнего "толчка" (новых записей) — операционная
   деталь, которую стоит знать, если бизнес-логика полагается на то, что
   удалённый ключ гарантированно исчезнет из лога за конкретное время.
4. **Компрессия — компромисс CPU против диска/сети, а НЕ бесплатный
   выигрыш.** `zstd` дал лучшее сжатие в обоих клиентах, но требует больше
   CPU на упаковку/распаковку, чем `lz4` (спроектирован для скорости) или
   `gzip` (средний вариант, широкая совместимость). Выбор кодека —
   инженерный компромисс под конкретную нагрузку (CPU-bound продюсер vs
   IO/сеть-bound кластер), не "всегда бери самый маленький размер".
5. **Размер батча — скрытый параметр компрессии.** Коэффициент сжатия у
   ОДНОГО И ТОГО ЖЕ кодека на одних и тех же логических данных заметно
   отличался между Go и Java клиентами (см. таблицу выше) — целиком из-за
   разных дефолтов батчинга (`linger.ms`/`batch.size`). Компрессия — per
   batch, не per record; мелкие батчи почти не сжимаются, крупные — сильно.
6. **`segment.bytes` имеет жёсткий пол в 1MiB.** Нельзя сделать "игрушечные"
   сегменты по несколько килобайт для более быстрой демонстрации —
   `LogConfig.validate` отвергнет топик. Демо этого стенда компенсирует это
   размером данных (padding), не размером сегмента.
7. **Tiered storage в Kafka 4.3.1 — не "включил и работает".** Это
   pluggable-архитектура (`RemoteStorageManager` + `RemoteLogMetadataManager`),
   и официальный релизный образ не поставляется с готовой реализацией
   плагина хранения — только с фреймворком/интерфейсами. Это НЕ "фича
   выключена по умолчанию из осторожности" (как unclean leader election в
   стенде #3), а "фича требует дополнительной интеграции, которую нужно
   принести самому" — принципиально другой уровень готовности к продакшену.

## Стенд #5: exactly-once и транзакции (`eos`)

Демонстрирует EOS (exactly-once semantics) на топиках `demo-eos-txn`
(3 партиции, RF=3) и паре `demo-eos-cpp-input`/`demo-eos-cpp-output`
(3 партиции, RF=3 каждый): транзакционный producer (`transactional.id`,
begin/commit/abort), разницу `read_committed` vs `read_uncommitted`, и ядро
стенда — атомарный consume-process-produce (прочитать из input, обработать,
записать в output + закоммитить offset input в ОДНОЙ транзакции), включая
**реальное `docker kill`/SIGKILL процесса-клиента строго между produce и
commit**, чтобы показать отсутствие частичного состояния. Реализовано
идентично на Go (`franz-go`) и Java (`kafka-clients`).

### (1)/(2) Транзакции: commit / abort / retry

Батч A (`transactional.id`, `beginTransaction`) коммитится штатно. Батч B на
первой попытке абортится посередине (симуляция сбоя обработки на 3-й из 5
записей — записи уже ушли на брокер синхронно, `abortTransaction()`
помечает их control-record'ом ABORT, а не откатывает физическую запись).
Батч B пересылается повторно и коммитится. Тот же сценарий, что EOS-демо в
`java-deep-dive/messaging` (15 физ / 10 логич на тех параметрах) — здесь
батч по 5, три попытки (5 + 3 + 5 = 13 физически, 5 + 5 = 10 логически).

### (3) ⚠️ Атомарный consume-process-produce — ядро стенда

Читаем `n` записей из `demo-eos-cpp-input` в составе consumer-группы,
обрабатываем (`processed:<value>`), пишем в `demo-eos-cpp-output` + коммитим
offset input в ОДНОЙ транзакции:

- **Java** — явно: `producer.sendOffsetsToTransaction(offsets,
  consumer.groupMetadata())` перед `commitTransaction()`. Нужно вручную
  собрать `Map<TopicPartition, OffsetAndMetadata>` из последней прочитанной
  позиции по каждой партиции.
- **franz-go** — `kgo.GroupTransactSession`: `Begin()` → `PollFetches()` →
  `ProduceSync()` → `End(ctx, kgo.TryCommit)`. Явного вызова, аналогичного
  `sendOffsetsToTransaction`, НЕТ — сессия сама помнит, что было вычитано
  этим клиентом с последнего `Begin()` (через внутренние
  `CommittedOffsets()`/`UncommittedOffsets()`), и коммитит именно эту дельту
  внутри `End()`. Та же гарантия (offset input и запись в output в одном
  `EndTxnRequest` на брокере), другая форма API.

**Демонстрация атомарности (`ops/eos-kill.sh cpp`):** попытка A читает `n`
записей, пишет их в output (**физически** попадают на диск партиции под
открытой транзакцией), печатает маркер `READY-TO-COMMIT`, затем **спит** —
в это окно host-скрипт делает `docker kill` (SIGKILL) контейнера-клиента,
обрывая процесс МЕЖДУ produce и commit. Попытка B стартует с ТЕМ ЖЕ
`transactional.id`/`TransactionalID` и ТОЙ ЖЕ consumer-группой:

- Java: `producer.initTransactions()` попытки B фенсит/абортит зависшую
  транзакцию попытки A (KIP-98 — бампает producer epoch, брокер сам
  проактивно абортит старую транзакцию как часть обработки
  `InitProducerIdRequest`).
- franz-go: тот же протокольный механизм срабатывает НЕЯВНО внутри первого
  `BeginTransaction()` попытки B (внутри `maybeRecoverProducerID`) — в
  franz-go нет отдельного вызова, аналогичного `initTransactions()`.

Поскольку попытка A так и не закоммитила offset input (это происходит
только внутри commit-пути), попытка B, вступая в ТУ ЖЕ группу, вычитывает
**те же самые** записи заново — реальное, а не выдуманное восстановление.

### Реальный прогон (проверено живьём 2026-07-08, оба клиента)

**(1)/(2) Транзакции**, `bash ops/eos-kill.sh -client=go|java txn`:

```
[txn] батч batchA: commit — 5 сообщений подтверждено
[txn] батч batchB: сбой в середине -> abort — 3 записи физически ушли, логически ничего не подтверждено
[txn] батч batchB: commit — 5 сообщений подтверждено
[txn] физически отправлено записей: 13, логически подтверждено: 10
[txn-verify] read_committed=10 read_uncommitted=13
[txn-verify] OK: read_committed == закоммиченное (10), read_uncommitted (13) строго больше
```

Числа **побайтово совпали** на Go (`franz-go`) и Java (`kafka-clients`):
`read_committed=10`, `read_uncommitted=13` на обоих. Это далось не сразу —
см. content-note про синхронный `send().get()` ниже.

**(3) Consume-process-produce, `bash ops/eos-kill.sh -client=go|java cpp`:**

```
--- попытка A (фон): consume+process+produce, ЗАТЕМ пауза 60с ДО commit ---
[cpp-attempt] вычитано из demo-eos-cpp-input: 10 записей
[cpp-attempt] обработано и записано в demo-eos-cpp-output: 10 записей (ФИЗИЧЕСКИ на диске, транзакция ещё ОТКРЫТА)
READY-TO-COMMIT n=10
--- маркер пойман — docker kill попытки A (SIGKILL, ДО commit) ---
--- exit code попытки A: 137 (SIGKILL, реальный крах) ---

--- verify ДО повтора ---
[cpp-verify после-kill-до-повтора] output read_committed=0 read_uncommitted=10(физически) committed-offset=0
[cpp-verify после-kill-до-повтора] OK: частичного состояния нет

--- попытка B: тот же txn-id (фенсит A) и та же группа (перечитывает те же записи), commit сразу ---
[cpp-attempt] session.End(TryCommit)/commitTransaction -> output И committed-offset input продвинуты АТОМАРНО

--- verify ПОСЛЕ повтора ---
[cpp-verify после-повтора] output read_committed=10 read_uncommitted=20(физически) committed-offset=10
[cpp-verify после-повтора] OK: частичного состояния нет
```

Идентично на Go и Java (только формат маркера commit отличается —
`session.End(TryCommit) -> committed=true` vs
`sendOffsetsToTransaction+commitTransaction`). Ключевой снимок — ДО и ПОСЛЕ
повтора:

| Момент | output `read_committed` | output `read_uncommitted` (физически) | committed-offset группы на input |
|---|---|---|---|
| после kill A, до retry | **0** | 10 | **0** |
| после commit B | **10** (ровно один раз, без дублей) | 20 (10 от A + 10 от B) | **10** |

Ни разу не наблюдалось промежуточное состояние (например «5 видно, offset=3»)
— офсет и видимость output продвигаются строго вместе, за один прыжок, как
и должна работать транзакция.

### Content-notes

1. **Физически записано ≠ логически видно (снова, как в стенде #4, но на
   уровне транзакций, а не retention/compaction).** Аборт НЕ откатывает уже
   отправленные на брокер байты — он лишь дописывает control-record ABORT,
   который `read_committed`-консьюмер использует, чтобы пропустить диапазон.
   `read_uncommitted` видит буквально всё, включая абортнутое и дубли от
   убитых попыток (см. таблицу выше: 20 физически при 10 логически видимых
   после полного цикла kill+retry).
2. **⚠️ Живая находка: `KafkaProducer.abortTransaction()` откатывает ещё НЕ
   подтверждённые брокером записи КЛИЕНТСКИ, а не только логически.**
   Javadoc: «Any unflushed produce messages will be aborted...». Первая
   версия `Txn.java` использовала обычный асинхронный `producer.send(...)`
   без ожидания ack — и живой прогон показал `read_uncommitted=10`, а не
   ожидаемые `13`: 3 записи абортнутого батча, ещё сидевшие в буфере
   продюсера (не отправленные на брокер), при `abortTransaction()` были
   отброшены клиентом и физически на диск НЕ попали вовсе. Franz-go в этом
   стенде использует `ProduceSync` (синхронный, ждёт ack) — чтобы сравнение
   «физически записано» было яблоки-к-яблокам, а не артефактом разной
   буферизации по умолчанию, Java-версия исправлена на синхронный
   `send(...).get()` — после чего `read_uncommitted=13` совпало с Go
   один-в-один. Это НЕ баг протокола Kafka и НЕ отличие клиентов — это
   особенность конкретного теста (когда именно записи физически долетают до
   брокера относительно момента abort), которую легко упустить.
3. **franz-go vs kafka-clients — разные формы одного и того же API.**
   - Явный `initTransactions()` (Java) vs неявная инициализация/восстановление
     producer id внутри первого `BeginTransaction()` (franz-go,
     `maybeRecoverProducerID`) — функционально одно и то же (протокол
     `InitProducerIdRequest` один), разница чисто в форме вызова.
   - Явный `sendOffsetsToTransaction(offsets, groupMetadata)` (Java) vs
     `GroupTransactSession`, которая сама отслеживает вычитанное и коммитит
     дельту внутри `End()` (franz-go) — Java требует вручную собрать карту
     офсетов, franz-go выводит её из истории клиента.
   - **Идемпотентность обязательна при заданном transactional-id в обоих
     клиентах — и оба одинаково это ЗАПРЕЩАЮТ отключить явно** (симметрично, не
     «разное оформление»): franz-go возвращает ошибку конфигурации при попытке
     скомбинировать `TransactionalID(...)` с `DisableIdempotentWrite()`; Java
     тоже бросает `ConfigException("Cannot set a transactional.id without also
     enabling idempotence.")` при `enable.idempotence=false` + `transactional.id`
     (`ProducerConfig.postProcessAndValidateIdempotenceConfigs`). Если
     `enable.idempotence` не трогать, оба берут дефолт `true` — но явная попытка
     выключить падает в обоих.
   - **Автокоммит офсетов группы:** franz-go автоматически выставляет
     `autocommitDisable=true`, как только задан `TransactionalID` (сверено по
     исходнику `pkg/kgo/config.go`, комментарий "true if autocommit was
     disabled or we are transactional") — программисту нельзя случайно
     оставить автокоммит включённым при транзакционном потреблении. В Java
     `enable.auto.commit=false` нужно выставить РУКАМИ — если забыть, фоновый
     автокоммит может продвинуть offset группы МИМО транзакции. Реальный
     footgun Java API, которого в franz-go структурно не существует.
4. **Границы EOS: внешние сайд-эффекты НЕ покрываются транзакцией Kafka.**
   Всё вышеописанное — гарантия ВНУТРИ Kafka (топик-топик, топик-offset).
   Если шаг обработки пишет ещё и в постороннюю систему (БД, HTTP-вызов,
   кеш) — эта запись НЕ часть Kafka-транзакции и может задвоиться или
   потеряться независимо от исхода commit/abort в Kafka. Стандартный паттерн
   для таких случаев — outbox (см. будущую статью про паттерн
   transactional-outbox в Phase 2 серии) — здесь не реализован, только
   зафиксирован как граница ответственности.

## Стенд #6: эксплуатация — метрики, reassignment, тюнинг (`ops`)

Демонстрирует то, чем реально занимается оператор Kafka-кластера после того,
как код уже написан: consumer lag (главный симптом отставания обработки),
ручную и автоматическую перебалансировку партиций/leadership, rack-awareness
как основу отказоустойчивости по зонам, тюнинг producer/consumer, quotas,
KRaft-кворум контроллера (и почему он не даёт split-brain) и исторический
контекст ZooKeeper→KRaft.

**Разделение клиент/CLI, сознательное.** Consumer lag и тюнинг
producer/consumer — это эффекты клиентской БИБЛИОТЕКИ (batch.size,
fetch.min.bytes и т.д.), поэтому у них есть Go (`go/ops`, franz-go) и Java
(`java/ops`, kafka-clients) реализации — те же 6 сценариев
(`seed`/`seed-continuous`/`lag-consume`/`tuning-producer`/`tuning-consumer`/`quota-produce`)
на обоих клиентах. Ручная/автоматическая перебалансировка партиций,
rack-awareness и KRaft-кворум — это операции над БРОКЕРОМ/кластером
(`kafka-reassign-partitions.sh`, `kafka-topics.sh`, `kafka-metadata-quorum.sh`),
не producer/consumer API — там намеренно нет клиентского кода вообще, только
`ops/*.sh` через `docker exec`, тот же принцип, что в стендах #3/#4 для
`docker kill`/инспекции сегментов.

### (1) Consumer lag: рост при отставании, падение при догоне

Топик `demo-ops-lag` (3 партиции, RF=3): фоновый продюсер пишет с постоянным
темпом, пока фоновый консьюмер группы `ops-lag-group` обрабатывает первые N
записей ИСКУССТВЕННО МЕДЛЕННО (имитация тяжёлой обработки, коммит офсета
сразу после каждой записи — чтобы `kafka-consumer-groups.sh --describe`,
колонка `LAG`, отражала реальный прогресс, а не просто позицию чтения), затем
переключается в быстрый режим и вычитывает backlog. Хост
(`ops/lag-demo.sh`) поллит `--describe` каждые 4с, пока консьюмер работает.

**Реальный прогон (Go, продюсер 20 запис/с × 40с = 800 записей, консьюмер:
первые 300 записей по 150мс/запись, затем без задержки):**

```
[poll t=+8s]  SUM(LAG)=153
[poll t=+15s] SUM(LAG)=239
[poll t=+22s] SUM(LAG)=325
[poll t=+29s] SUM(LAG)=421
[poll t=+36s] SUM(LAG)=500
[poll t=+42s] SUM(LAG)=550   <- пик: продюсер уже закончил (40с), консьюмер ещё в МЕДЛЕННОЙ фазе
[poll t=+51s] SUM(LAG)=448   <- consumer переключился в быстрый режим, лаг падает
[poll t=+57s] SUM(LAG)=0
[final-poll]  SUM(LAG)=0
[assert] OK: лаг вырос до 550 > 0, затем упал ровно до 0
```

Идентичная форма кривой на Java (пик `SUM(LAG)=449` на t=+43s, затем падение
к `0` на t=+56s) — абсолютные пиковые числа host-зависимы (соотношение
темпа продюсера/задержки консьюмера/докер-планировщика), но сама форма
(рост, пока консьюмер отстаёт → падение к нулю после ускорения) —
детерминированное следствие механики commit-offset/HWM, не совпадение.

**Under-replicated partitions** (переиспользует механику `docker kill` из
стенда #3): `kafka-topics.sh --describe --under-replicated-partitions` на
живом топике `demo-ops-lag`. ⚠️ Живая находка: `replica.lag.time.max.ms`

### (3) Автоматическая перебалансировка leadership (`auto.leader.rebalance.enable`)

`auto.leader.rebalance.enable=true` — дефолт брокера, уже включён. Проверяет
периодичность контроллер по `leader.imbalance.check.interval.seconds`
(дефолт **300с/5мин** — непригодно для живой демонстрации, тот же случай, что
`log.retention.check.interval.ms` в стенде #4: **НЕ dynamic-alterable**,
проверено живьём — `kafka-configs.sh --alter` падает с `Cannot update these
configs dynamically`). Поэтому `compose/compose.yml` статически задаёт
`KAFKA_LEADER_IMBALANCE_CHECK_INTERVAL_SECONDS=5` (кластер пересоздан
`docker compose up -d` ПОСЛЕ добавления — storage переформатирован заново,
что ожидаемо и безопасно: топики предыдущих стендов пересоздаются идемпотентно
самими стендами при следующем запуске).

Топик `demo-ops-leader` (3 партиции, RF=3): убиваем брокера, который является
`preferred`-лидером (`replicas[0]`) партиции 0 → leadership вынужденно
переезжает на другую ISR-реплику → восстанавливаем убитого брокера →
ждём, пока контроллер САМ (без ручного `kafka-leader-election.sh`) вернёт
leadership на preferred.

**Реальный прогон (Go):**

```
--- партиция 0: preferred (replicas[0]) leader = 2 ---
--- docker kill kafka-cookbook-2 ---
[poll 2] failover подтверждён: leader=3
--- восстанавливаю kafka-cookbook-2, healthy ---
[poll 1, t=+3s] leader партиции 0 = 2
[assert] OK: leadership вернулось к preferred-реплике 2 автоматически
```

Идентично на Java (preferred=1, failover→2, восстановление→leadership
вернулось к 1 за то же одно окно проверки ~3с). Оба клиента: leadership
вернулось автоматически В ПРЕДЕЛАХ ПЕРВОГО же 5-секундного цикла проверки
контроллера — заметно быстрее дефолтных 5 минут.

**Cruise Control — обзорно, НЕ развёрнут.** Cruise Control — надстройка над
`kafka-reassign-partitions.sh`/leader election, которая автоматически
считает и исполняет ребалансировку на основе метрик нагрузки брокеров
(CPU/диск/сеть/размер партиций), а не только количества партиций/лидеров.
Разворачивать отдельный сервис (плюс его собственный Kafka-топик метрик)
поверх учебного 3-брокерного стенда сочли непропорциональным объёму этого
стенда — статус зафиксирован честно, без имитации вывода.

### (4) Rack awareness

Топология стенда — **1 брокер = 1 rack** (`kafka1`/rack-a, `kafka2`/rack-b,
`kafka3`/rack-c, см. `compose/compose.yml`), подтверждено живьём
(`kafka-configs.sh --describe --all`, `broker.rack=rack-a|rack-b|rack-c`).

```
Топик demo-ops-rack-rf3 (6 партиций, RF=3):
  partition=0: replicas=[1,2,3] -> 1:rack-a 2:rack-b 3:rack-c (ВСЕ разные)
  partition=1: replicas=[2,3,1] -> 2:rack-b 3:rack-c 1:rack-a (ВСЕ разные)
  ... (все 6 партиций — по 3 разных rack)
[assert] OK: во всех партициях реплики на РАЗНЫХ rack

Топик demo-ops-rack-rf2 (3 партиции, RF=2):
  partition=0: replicas=[2,3] -> 2:rack-b 3:rack-c
  partition=1: replicas=[3,1] -> 3:rack-c 1:rack-a
  partition=2: replicas=[1,2] -> 1:rack-a 2:rack-b
[assert] OK: во всех партициях реплики на РАЗНЫХ rack
```

**⚠️ Честная оговорка про топологию.** В этом стенде broker-id и rack связаны
бекцией (у каждого rack ровно один брокер) — это значит, что ЛЮБОЙ набор из N
*различных* broker-id структурно ОБЯЗАН покрывать N различных rack, и
результат выше НЕ демонстрирует "интеллект" rack-aware алгоритма размещения
реплик, а лишь то, что в этой топологии иначе физически быть не может.
Rack-aware replica-placement алгоритм реально ВЫБИРАЕТ между брокерами
только когда на одном rack их несколько (например, 6 брокеров на 3 rack по
2) — он должен активно ИЗБЕГАТЬ размещения двух реплик на брокерах одного
rack, а не просто расставить реплики по трём произвольным брокерам. Такая
топология (несколько брокеров на rack) — за пределами этого стенда.

### (5) Тюнинг producer/consumer

**Producer** (`demo-ops-tuning-producer`, 5000 записей × 500 байт), 4
конфигурации `batch.size`/`linger.ms`/`compression.type`:

| # | batch.size | linger.ms | compression | Go msg/s (MB/s) | Java msg/s (MB/s) |
|---|---|---|---|---|---|
| 1 | 16384 (дефолт-подобный) | 0 | none | 36973.9 (17.63) | 9535.3 (4.55) |
| 2 | 65536 | 20 | none | 12038.4 (5.74) | 10899.1 (5.20) |
| 3 | 65536 | 20 | lz4 | **68703.4 (32.76)** | 10586.7 (5.05) |
| 4 | 2048 (маленький) | 0 | none | **4543.1 (2.17)** | **2626.7 (1.25)** |

Комбинация (4) — самая медленная на ОБОИХ клиентах (маленький batch =
частые сетевые round-trip'ы вместо накопления). Комбинация (3) — самая
быстрая на Go (компрессия поверх большого батча выигрывает за счёт меньшего
объёма по сети). ⚠️ **Честная аномалия, не подчищена:** на Go комбинация (2)
(бОльший batch + linger=20мс, БЕЗ компрессии) оказалась МЕДЛЕННЕЕ комбинации
(1) (12038 против 36974 msg/s) — на коротком одноразовом прогоне (5000
записей, суммарно 2.5МБ, укладывается в считаные батчи по 3 партициям)
`linger.ms=20` добавляет фиксированную задержку НА КАЖДЫЙ батч независимо от
того, готовы ли данные раньше — на коротком burst-прогоне эта задержка не
успевает окупиться накоплением, в отличие от установившейся нагрузки в
проде, где буфер заполняется быстрее linger.ms и задержка не набегает. На
Java эта аномалия НЕ проявилась (2 быстрее 1, как "ожидалось" по теории) —
это иллюстрирует ровно то, что и должно: `linger.ms` — это **компромисс
латентности за throughput**, а не безусловный выигрыш, и его эффект зависит
от соотношения темпа данных и самого значения linger, не только от языка
клиента. Числа throughput — характерный прогон (host-зависимый).

**Consumer** (`demo-ops-tuning-consumer`, ОДИН РАЗ засеян 20000 записей ×
500 байт, дальше читается разными consumer group), 3 конфигурации
`fetch.min.bytes`/`max.poll.records`:

| # | fetch.min.bytes | max.poll.records | Go avg-records/poll | Java avg-records/poll |
|---|---|---|---|---|
| 1 | 1 | 500 | 487.8 | 425.5 |
| 2 | 1 | 50 | **49.9** | **49.8** |
| 3 | 65536 | 500 | 487.8 | 416.7 |

`max.poll.records`/`PollRecords`-лимит — чёткий, воспроизводимый эффект на
ОБОИХ клиентах (ограничивает размер пачки один в один: ~50 против ~488).
**`fetch.min.bytes` эффекта НЕ показал** (487.8 что при 1, что при 65536
байт) — и это ЧЕСТНЫЙ, объяснимый результат, а не баг стенда: топик
пре-засеян ПОЛНОСТЬЮ ДО того, как консьюмер начал читать, поэтому уже на
ПЕРВОМ fetch-запросе у брокера в наличии куда больше данных, чем любой
разумный `fetch.min.bytes` — порог тривиально удовлетворён мгновенно
независимо от значения. `fetch.min.bytes`/`fetch.max.wait.ms` меняют
поведение только тогда, когда данные поступают МЕДЛЕННЕЕ, чем консьюмер
успевает вычитывать (лог трикл-пишется, а не лежит целиком заранее) — это
не воспроизведено в данном прогоне; зафиксировано как ограничение методики
теста, а не как "fetch.min.bytes не работает".

### (6) Quotas (`producer_byte_rate`)

Демонстрируется через `kafka-configs.sh --entity-type clients
--entity-name <client-id> --alter --add-config producer_byte_rate=100000`
(без клиентского кода — чистый broker-конфиг) + `tuning-producer` с
конкретным `client.id` (Kafka сопоставляет квоту по client-id — при
unauthenticated PLAINTEXT-кластере "user"-часть квоты — анонимный дефолт,
`entity-type=clients` работает без SASL).

**⚠️ Живая находка (порог burst-кредита).** Дефолтное окно квоты —
`quota.window.num=11` окон по `quota.window.size.seconds=1` ≈ 11с "бесплатного"
burst-кредита ≈ `producer_byte_rate × 11` ≈ 1.1МБ при 100000 Б/с. Первая
попытка (n=2000 записей × 1000 байт = 2МБ — чуть больше номинального окна, но
всё ещё в пределах инерции sensor'а) throttling НЕ показала вовсе — что на
franz-go, что на официальном `kafka-producer-perf-test.sh` (тот же паттерн:
первые ~3400 записей быстро, throttling начинается ПОЗЖЕ). Финальный прогон
взял объём **заведомо больше порога** (n=8000 × 1000 байт = 8МБ):

```
--- (1) БЕЗ quota ---
[tuning-producer] БЕЗ-quota n=8000 -> throughput=16712.6 msg/s (15.94 MB/s)     # Go
[tuning-producer] БЕЗ-quota n=8000 -> throughput=9052.6 msg/s (8.63 MB/s)       # Java
--- применяю producer_byte_rate=100000 (~97.7 КБ/с) для client-id=quota-demo-client ---
--- (2) С quota ---
[tuning-producer] С-quota n=8000 -> throughput=327.0 msg/s (0.31 MB/s)         # Go
[tuning-producer] С-quota n=8000 -> throughput=322.7 msg/s (0.31 MB/s)         # Java
```

**~51× (Go) / ~28× (Java) падение throughput**, и — важно — throttled-throughput
**СОВПАДАЕТ между клиентами** (0.31 MB/s на обоих) с точностью до
округления: квота — broker-side механизм, throttling НЕ зависит от клиентской
библиотеки, только от `client.id` в заголовке запроса. Итоговые ~0.31 MB/s
несколько выше номинальных ~0.0977 MB/s — остаточный эффект burst-кредита
внутри самого 8МБ-прогона (первая ~1.1МБ ушла почти без задержки, экономию
время съедает мгновенно набежавшая на протяжении остальных ~6.9МБ выдержка) —
направление и порядок величины эффекта детерминированы, точная цифра — нет.

### (7) KRaft-кворум и split-brain

`kafka-metadata-quorum.sh describe --status` — тот же кворум, что
зафиксирован ранее, но опрошен заново на текущем (пересозданном под
задачу leader-imbalance) кластере:

```
ClusterId:              r0mrt307TrOiv10ImOQjHw
LeaderId:               3
CurrentVoters:          [{"id": 1, ...}, {"id": 2, ...}, {"id": 3, ...}]
CurrentObservers:       []
```

```
NodeId  LogEndOffset  Lag  Status
3       1188          0    Leader
1       1188          0    Follower
2       1188          0    Follower
```

**Почему KRaft не даёт split-brain контроллера.** Контроллер — это Raft
group (`__cluster_metadata` в KRaft-режиме): решение (кто лидер, какая
запись закоммичена) принимается ГОЛОСОВАНИЕМ БОЛЬШИНСТВА voters, а не по
факту "кто первый ответил" или конфигу "кто главный". При 3 voters кворум —
любые 2 из 3; ОДНА группа узлов не может получить commit без согласия
большинства, поэтому сеть, разбитая на две половины (ни в одной из которых
нет большинства), просто НЕ ИЗБИРАЕТ лидера ни в одной из половин — вместо
двух конкурирующих "лидеров", пишущих несовместимые истории (классический
split-brain), получается ПРОСТОЙ (недоступность на запись метаданных) до
восстановления связности. Это структурное свойство алгоритма Raft, не
специфика Kafka — то же обоснование справедливо для etcd/Consul/CockroachDB
и любого другого Raft-based консенсуса.

### ZooKeeper — исторический контекст (НЕ демонстрируемый режим)

Kafka 4.3.1 (версия этого стенда) — **KRaft-only**: ZooKeeper удалён из
кодовой базы в Kafka 4.0 (не просто отключён по умолчанию), поднять его
"живьём" на этом образе НЕВОЗМОЖНО — это честно НЕ попытка, а зафиксированный
факт архитектуры. Контекст — для понимания, ПОЧЕМУ KRaft вообще появился:

- **Что делал ZooKeeper (до KRaft).** Внешний координационный сервис
  (собственный кворум, отдельный от брокеров Kafka): хранил метаданные
  топиков/партиций/ACL, отвечал за выбор **Controller**-брокера (один из
  брокеров Kafka, а не отдельный процесс) через эфемерные ноды/watch'и,
  координировал ISR-изменения через этого Controller'а.
- **Почему заменили — [KIP-500](https://cwiki.apache.org/confluence/display/KAFKA/KIP-500).**
  Два кворума вместо одного (ZK-кворум + Kafka-брокеры) — двойная
  операционная сложность (два разных вида нод для мониторинга/апгрейда/бэкапа),
  масштабирование метаданных упиралось в ZooKeeper (Controller при рестарте
  кластера с сотнями тысяч партиций мог загружать метаданные ИЗ ZooKeeper
  минутами — известная боль крупных инсталляций), и разделение "кто
  контроллер" (ZK) от "кто фактически применяет изменения" (сам Controller-брокер)
  создавало класс гонок при failover'е контроллера.
- **Таймлайн.** KRaft — GA (production-ready) с Kafka **3.3** (октябрь 2022,
  KIP-833). ZooKeeper-режим **deprecated** с Kafka **3.5** (июнь 2023,
  KIP-833 same). ZooKeeper **физически удалён из кодовой базы** в Kafka
  **4.0** (март 2025) — этот стенд (4.3.1) на несколько минорных версий
  младше точки невозврата.
- **Миграция ZK→KRaft** (для кластеров &lt;4.0, которые ещё на ZK) —
  штатно поддерживаемый путь через `kafka-storage.sh` в режиме миграции:
  bridge-release с ОБОИМИ режимами одновременно (ZK остаётся источником
  истины, KRaft-контроллеры запускаются в "migration mode" и реплицируют
  метаданные ИЗ ZK), затем финализация переключает источник истины на
  KRaft-кворум и ZK можно вывести из эксплуатации — без даунтайма кластера
  данных (брокеры продолжают обслуживать produce/consume всё время миграции).
- **Split-brain в ZK-эпоху — тот же принцип большинства, но с непрямым КОНТРОЛЕМ.**
  ZooKeeper САМ использует ZAB (ZooKeeper Atomic Broadcast — консенсус на основе
  большинства голосов, родственный Raft по гарантиям, но НЕ производный от него:
  ZAB старше, спроектирован ~2008, Raft опубликован в 2014; оба независимо
  восходят к Paxos-подобным идеям) для СВОЕГО кворума — split-brain в ZK-слое так же
  предотвращался большинством. Но Kafka-специфичная гонка была НЕ в
  ZK-консенсусе, а в связке ZK↔Controller: "мёртвый", но ещё не
  отфейловеренный Controller-брокер (например, после долгой GC-паузы) мог
  временно НЕ ЗНАТЬ, что уже потерял ZK-сессию/лидерство, и продолжать
  считать себя контроллером ("zombie controller") — источник исторических
  багов класса "два брокера одновременно думают, что они controller" в
  ранних версиях Kafka, закрытых epoch-фенсингом (controller epoch),
  который де-факто стал предвестником архитектуры KRaft. KRaft устраняет
  сам класс проблемы: controller — не "роль поверх внешнего кворума", а
  ЛИДЕР Raft-группы, и Raft-эпоха фенсит устаревшего лидера структурно, на
  уровне самого консенсуса, а не отдельным вспомогательным механизмом.

### Rolling upgrade — что воспроизведено, что описано

**Воспроизведено живьём (частично, как побочный эффект других демо этого
стенда):** одиночный цикл "graceful вывод ноды из ротации → она отсутствует
→ возврат в кластер → полная ресинхронизация" — именно ЭТО ядро одного шага
rolling upgrade — многократно продемонстрирован в этом стенде (kill/restart
вокруг lag-demo под-репликации, вокруг auto-leader-rebalance) и в стенде #3
(`broker-kill.sh`): кластер остаётся ДОСТУПЕН на всё время, пока хотя бы
`min.insync.replicas` реплик живы, отсутствующий брокер полностью
ресинхронизируется (ISR/leadership) после возврата.

**НЕ воспроизведено — честно, полный многоброкерный upgrade между ДВУМЯ
разными версиями образа:** в стенде используется единственная версия образа
(`apache/kafka:4.3.1`) — нет второго закреплённого тега для проверки
реального смешанного кластера (частично 4.3.1, частично другая версия) в
процессе апгрейда. Полный процесс **описан**, не имитирован:

1. Обновить по одному брокеру за раз (не все разом) — на каждом шаге
   кластер остаётся доступным, пока живо большинство контроллерного
   кворума и `min.insync.replicas` реплик каждой партиции.
2. Порядок: сначала non-controller брокеры, controller-лидер — последним
   (или явно передать лидерство перед остановкой — `docker stop`, НЕ `kill`,
   даёт controlled shutdown с явным переносом лидерства ДО завершения
   процесса, см. content-note стенда #3).
3. `inter.broker.protocol.version`/`message.format.version` — в
   KRaft-режиме отслеживаются через `metadata.version` (`kafka-features.sh`);
   при межверсионном апгрейде — не поднимать `metadata.version` до финализации
   ВСЕХ брокеров новой версии (иначе старые версии не смогут присоединиться
   обратно при откате).
4. Проверка здоровья на каждом шаге — та же механика, что demo здесь: URP
   пуст, ISR полон, `kafka-metadata-quorum.sh describe --status` показывает
   всех voters живыми, прежде чем переходить к следующему брокеру.

### Content-notes

1. **Lag — не просто число, а РАЗНОСТЬ committed-offset и HWM.** Он растёт,
   когда consumer МЕДЛЕННЕЕ producer, и падает только когда consumer
   реально коммитит прогресс (не просто читает) — auto-commit с редким
   интервалом покажет лаг менее точно, чем частый/ручной коммит.
2. **Ручная vs автоматическая перебалансировка — разные инструменты для
   разных задач.** `kafka-reassign-partitions.sh` двигает ДАННЫЕ между
   брокерами (меняет состав replica-set) — тяжёлая операция (копирование
   байт), нужна throttle. `auto.leader.rebalance.enable` двигает только
   ЛИДЕРСТВО (кто из УЖЕ существующих реплик обслуживает read/write) —
   лёгкая операция (нет копирования данных), происходит на фоне сама.
3. **Rack-awareness = отказоустойчивость по зонам, НЕ по машинам.** Смысл
   `broker.rack` — гарантировать, что потеря целой зоны (rack/AZ/дата-центра)
   не роняет partition ниже `min.insync.replicas`; но (см. честную оговорку
   в разделе (4) выше) сама гарантия зависит от РЕАЛЬНОГО распределения
   брокеров по зонам, а не от факта присвоения `broker.rack`.
4. **KRaft-кворум vs ZK-эпоха.** И то, и другое — консенсус на основе большинства
   голосов под капотом (KRaft = Raft напрямую; ZAB в ZooKeeper — родственный
   по гарантиям, но самостоятельный протокол, старше Raft, не его производная);
   разница НЕ в "split-brain
   защите" (она была в обоих), а в том, что KRaft убирает ПОСРЕДНИКА
   (Controller как отдельная роль поверх внешнего кворума) — контроллер сам
   есть Raft-лидер, а не клиент стороннего консенсуса.
5. **Quotas — broker-side, не client-side.** Проверено живьём: throttled
   throughput практически идентичен между Go и Java клиентами (0.31 MB/s на
   обоих) — потому что throttling применяется на брокере по `client.id` в
   заголовке запроса, а не зависит от того, как устроен клиент.

## Стенд #7: экосистема — Kafka Connect + Schema Registry (`ecosystem`)

Демонстрирует три компонента экосистемы Kafka, которые обычно НЕ пишутся
руками, а берутся готовыми: Schema Registry (контракты на формат данных +
эволюция схем), Kafka Connect (интеграция с внешними системами без своего
кода) и относительную цену форматов сериализации. В отличие от стендов
#1-#6, здесь нет отдельного Go/Java "клиента, повторённого на двух языках" —
Schema Registry и Connect управляются напрямую через REST API (bash+curl,
`ops/ecosystem-demo.sh`), а сравнение сериализации — одна Go-программа
(`go/ecosystem/serialization`), т.к. предмет сравнения (байтовый размер по
готовой схеме) не зависит от клиентской библиотеки.

### Выбор Schema Registry: apicurio, не Confluent cp-schema-registry

Постановка стенда прямо указывала на риск: Confluent `cp-schema-registry` заточен под

Проверено живьём: `apicurio/apicurio-registry:latest-release` (3.2.6) с
`APICURIO_STORAGE_KIND=kafkasql` и

поднялся с ПЕРВОЙ попытки против живого 3-брокерного `apache/kafka:4.3.1`
кластера — лог подтверждает, что реестр САМ создал и использует топики на
ЭТОМ ЖЕ кластере (не отдельное хранилище):


Confluent `cp-schema-registry` отдельно НЕ пробовался — apicurio завёлся с

НЕ содержит `wget`/`curl` — healthcheck через `wget -q -O-` падал

### 1. Schema Registry: регистрация + эволюция (ccompat v7 API)

Схема `User` (`ecosystem/schemas/user-v1.avsc`: `id: long, name: string,
email: string`) регистрируется под subject `ecosystem-user-value` с явно
выставленным `compatibility=BACKWARD`. Дальше — две попытки эволюции:

- **v2 (`user-v2-compatible.avsc`):** добавлено `age` — `["null","int"]` с
  `default: null`. Optional-поле с default — классический BACKWARD-совместимый
  случай (новый читатель, столкнувшись со старыми данными без `age`,
  подставляет default вместо ошибки).
- **v3 (`user-v3-incompatible.avsc`):** тип `id` меняется `long -> string`.
  Смена типа поля — несовместимое изменение в обе стороны (данные,
  физически записанные как 8-байтный long, не читаются как строка).

### Реальный прогон (проверено живьём 2026-07-09)

```
--- (1) регистрирую v1 (id/name/email) ---
{"id":3}
HTTP_STATUS:200

--- (2) регистрирую v2: +age optional (default=null) — ДОЛЖНО пройти (BACKWARD-совместимо) ---
{"id":2}
HTTP_STATUS:200

--- (3) регистрирую v3: тип id меняется long -> string — ДОЛЖНО быть ОТКЛОНЕНО (409) ---
{"message":"io.apicurio.registry.rules.violation.RuleViolationException: Incompatible artifact: ecosystem-user-value [AVRO], num of incompatible diffs: {1}, list of diff types: [reader type: STRING not compatible with writer type: LONG at /fields/0/type]","error_code":409}
HTTP_STATUS:409

--- (4) версии subject после эволюции ---
[1,2]
```

**v2 зарегистрирована (версия 2 у subject), v3 отклонена HTTP 409** с
диагностикой ОТ РЕЕСТРА, указывающей ровно на конфликтующее поле
(`/fields/0/type`, `reader type: STRING not compatible with writer type:
LONG`) — не общая ошибка, а точный diff. `id:3`/`id:2` в ответах — ГЛОБАЛЬНЫЙ
счётчик схем во всём реестре (не номер версии subject'а — это отдельное
число `[1,2]` в п.4); несовпадение по возрастанию — побочный эффект того,
что перед этим прогоном чистился тестовый subject, не баг.

### 2. Kafka Connect: FileStreamSource → topic → FileStreamSink + SMT

Distributed worker (`connect-distributed.sh`, тот же образ `apache/kafka:4.3.1`,
что и брокеры — никакого отдельного Confluent-образа) с двумя коннекторами
"из коробки" (без единой строчки своего кода):

- **Source** (`FileStreamSourceConnector`): читает `/data/source/input.txt`
  построчно → топик `ecosystem-connect-demo`. SMT-цепочка
  `hoist,insertOrigin`: `HoistField$Value` оборачивает сырую строку в
  `Struct{line: "..."}` (сам FileStreamSourceConnector отдаёт значение как
  примитив `Schema.STRING`, а `InsertField` умеет добавлять поле только в
  Struct/Map — отсюда двухшаговая цепочка), затем `InsertField$Value`
  добавляет статическое поле `ingest_source=filestream-source-connector`.
- **Sink** (`FileStreamSinkConnector`): читает тот же топик → пишет в
  `/data/sink/output.txt`.

### Реальный прогон (проверено живьём 2026-07-09)

```
--- статус коннекторов (REST /connectors/{name}/status) ---
{"name":"ecosystem-file-source","connector":{"state":"RUNNING",...},"tasks":[{"id":0,"state":"RUNNING",...}],"type":"source"}
{"name":"ecosystem-file-sink","connector":{"state":"RUNNING",...},"tasks":[{"id":0,"state":"RUNNING",...}],"type":"sink"}

--- содержимое output.txt (после SMT: line + ingest_source) ---
{ingest_source=filestream-source-connector, line=line-01 hello kafka connect}
{ingest_source=filestream-source-connector, line=line-02 second record}
{ingest_source=filestream-source-connector, line=line-03 third record}
...
{ingest_source=filestream-source-connector, line=line-10 tenth record}

--- счётчик: вход=10 выход=10 ---
[assert] OK: оба коннектора RUNNING, N in (10) == N out (10)
```

Оба коннектора `RUNNING` (и `connector`, и единственный `task`), 10 строк на
входе → 10 записей на выходе, каждая — с добавленным SMT-полем
`ingest_source` и переименованным полем `line` (эффект `HoistField`).
Перенос данных между файлом и файлом через Kafka — без единой строчки
producer/consumer кода.

⚠️ **Живая находка (главная методологическая находка стенда).**
`FileStreamSourceConnector` хранит позицию чтения файла (byte offset) в
internal-топике `connect-offsets`, ключ = **имя коннектора + путь файла** —
НЕЗАВИСИМО от жизненного цикла самого коннектора. Первая версия скрипта
делала просто `DELETE` + повторный `POST` того же коннектора с тем же
файлом того же размера — источник молча не эмитил НИ ОДНОЙ записи, т.к.
позиция "конец файла" уже была сохранена с предыдущего прогона (`n_in=10
n_out=0`, assert упал). Симметрично для sink: committed-офсет его
consumer-группы (имя группы = имя коннектора) тоже переживает
удаление/пересоздание коннектора. Исправлено явным сбросом через REST API
управления офсетами ([KIP-875](https://cwiki.apache.org/confluence/display/KAFKA/KIP-875%3A+First-class+offsets+support+in+Kafka+Connect),
доступен в Kafka Connect с 3.6, есть в 4.3.1): `PUT .../stop` (коннектор
обязан быть в состоянии STOPPED, иначе `DELETE .../offsets` отвечает 400) →
`DELETE .../offsets` → `DELETE` самого коннектора, плюс пересоздание топика
`ecosystem-connect-demo` — тот же идемпотентный delete+create, что и в
остальных стендах серии.

### 3. Сериализация: относительный размер JSON vs Avro vs Protobuf

Одни и те же 5 записей `User` (`id/name/email`) закодированы тремя
способами: `encoding/json` (стандартная библиотека Go), `hamba/avro/v2` по
СТРОГО ТОЙ ЖЕ Avro-схеме, что зарегистрирована в Schema Registry в части 1
(`ecosystem/schemas/user-v1.avsc`), и Protobuf wire-формат — низкоуровневым
`google.golang.org/protobuf/encoding/protowire` (те же самые байты, что
выдал бы `protoc`-сгенерированный `Marshal()` для эквивалентного
proto3-сообщения `message User { int64 id=1; string name=2; string
email=3; }`, но БЕЗ `protoc`-тулчейна и кодогенерации — см. content-notes).

### Реальный прогон (проверено живьём 2026-07-09)

```
=== Размер ОДНОГО сообщения (байт), по каждой записи ===
record                   JSON     Avro Protobuf
user-1                     67       41       44
user-2                     61       35       38
user-3                     69       43       46
user-4                     73       47       50
user-5                     67       41       44

=== Суммарно по 5 записям (байт) и относительно JSON ===
```

заметно (на треть) компактнее JSON. Размер **детерминирован схемой и
данными** — в отличие от throughput/latency-замеров в других стендах серии,
этот результат не зависит от хоста и будет идентичным на любой машине с той
же схемой и теми же данными. Оба бинарных формата выигрывают засчёт
отсутствия имён полей в потоке (схема передаётся сторонам ОТДЕЛЬНО — то,
что и делает Schema Registry из части 1) и компактного кодирования чисел
(varint вместо ASCII-цифр JSON).

### ksqlDB — обзорно, НЕ развёрнут

Как и было решено заранее: ksqlDB — отдельный сервис (собственный
REST/CLI поверх Kafka Streams), разворачивать поверх учебного стенда ради
одной демонстрации SQL-поверх-потоков сочли непропорциональным (тот же
принцип, что Cruise Control в стенде #6). SQL-запросы к потокам данных —
концептуально то же самое, что программный Kafka Streams API (ksqlDB
компилирует SQL в топологию Kafka Streams под капотом); полноценная живая
демонстрация потоковой обработки — предмет будущей статьи о Kafka Streams
(`data-streaming` в Phase 2 серии), не этого cookbook-стенда.

### Content-notes

1. **Schema Registry — это контракт, а не просто хранилище файлов.**
   Ценность не в том, что схема ГДЕ-ТО лежит, а в том, что реестр АКТИВНО
   отклоняет несовместимые изменения на этапе регистрации (409 с точным
   diff), а не тогда, когда consumer в проде падает на непонятных байтах.
2. **BACKWARD/FORWARD — не абстракция, а конкретное направление
   совместимости.** BACKWARD (что демонстрирует этот стенд): НОВЫЙ читатель
   должен уметь прочитать СТАРЫЕ данные — поэтому под BACKWARD можно
   **добавлять optional-поля с default** (новый читатель использует default
   для старых записей) И **удалять ЛЮБОЕ поле** (новый читатель просто не
   знает об удалённом поле старых данных), но нельзя менять тип
   существующего поля. FORWARD — обратная гарантия (старый читатель понимает
   НОВЫЕ данные), с зеркальным набором: под FORWARD можно **добавлять любое
   поле** (старый читатель его игнорирует), но **удалять — только
   optional-поля** (иначе старому читателю нечем заполнить пропавшее поле).
   Кратко (таблица Confluent): BACKWARD → удаление полей + добавление
   optional; FORWARD → добавление полей + удаление optional.
3. **Connect-офсеты — скрытое состояние, переживающее удаление коннектора.**
   Самая дорогая находка стенда: "просто пересоздать коннектор" НЕ значит
   "начать с чистого листа" — источник и sink хранят прогресс НЕЗАВИСИМО от
   регистрации коннектора в кластере. Для чистого повторного прогона нужен
   явный сброс офсетов (KIP-875) или физически новый connector name/topic.
4. **SMT-цепочки часто требуют промежуточного шага.** `InsertField` не
   работает на примитивном значении (`Schema.STRING` у сырой строки из
   файла) — нужен `HoistField`, чтобы сначала обернуть значение в
   Struct/Map. Частая ошибка новичка с FileStream-коннекторами и SMT.
5. **Protobuf здесь — БЕЗ protoc.** Сознательный компромисс: `protowire`
   даёт те же самые wire-байты, что и полный `protoc`-тулчейн, без
   необходимости тащить кодогенерацию ради одного замера размера — постановка
   стенда прямо допускала "ручной" способ сравнения сериализации.
6. **Что взять готовым, что писать самому — практическое правило этого
   стенда.** Контракты на формат данных (Schema Registry) и интеграция с
   внешними системами без специфики бизнес-логики (Kafka Connect
   source/sink + стандартные SMT) — типично готовые компоненты экосистемы,
   не то, что стоит писать с нуля. Специфичная бизнес-трансформация данных
   (не влезающая в готовый SMT) — единственное место, где всё ещё пишут
   свой код (custom SMT или Kafka Streams/consumer+producer).

## Стенд #8: клиенты в разных языках (`clients`)

Демонстрирует три родословные Kafka-клиентов на живом одинаковом сценарии —
**11 драйверов на 7 языках** против общего кластера. Задача одна и та же
везде: producer с ключом и (где поддерживается) идемпотентностью отправляет
12 сообщений (4 ключа × 3 раунда, ключи `order-1`…`order-4`) → consumer в
group с РУЧНЫМ коммитом (auto-commit выключен явно) читает их обратно и
печатает `(partition, offset, key)`. Каждый язык/драйвер — свой Docker-образ
(без хостовых тулчейнов), свой топик (`demo-clients-<язык>[-<драйвер>]`, 3
партиции, RF=3), свой `group.id`.

### ⚠️ Главная живая находка: ТРИ разные "дефолтные" схемы key→partition

Один и тот же набор ключей (`order-1`…`order-4`) даёт **три разных, но
внутренне консистентных** распределения по партициям — не потому что
кто-то "сломан", а потому что JVM-референс, librdkafka и sarama используют
разные реализации хеш-партиционера по умолчанию:

- **JVM-семья** (kafka-clients, franz-go — с `UniformBytesPartitioner`,
  повторяет murmur2-формулу Java-клиента, см. content-note стенда #1;
  segmentio/kafka-go — только если явно поставить `Murmur2Balancer{}`,
  что и сделано в этом стенде; kafka-python-ng): `order-1→1, order-2→0,
  order-3→0, order-4→2`.
- **librdkafka-семья** (Python confluent-kafka, Rust rdkafka, C#
  Confluent.Kafka, C++ modern-cpp-kafka, Go confluent-kafka-go — все
  одним и тем же C-движком): `order-1→1, order-2→0, order-3→2, order-4→2`
  — те же order-1/order-2, но order-3 и order-4 **оба** уходят в
  partition 2 (librdkafka по умолчанию — `consistent_random`/собственная
  вариация хеша, отличная от Java `DefaultPartitioner`).
- **sarama** — третий, ещё один вариант: `order-1→1, order-2→1,
  order-3→0, order-4→0` (собственный FNV1a-based хешер, не совпадает ни с
  JVM, ни с librdkafka).

Все пять librdkafka-обёрток (Python/Rust/C#/C++/Go-confluent) дали
**побайтово идентичное** распределение — сильное подтверждение, что это
один и тот же C-движок под разными языковыми обёртками, а не пять
независимых реализаций.

### ⚠️ Живые находки при сборке (честно, что стоило крови)

1. **segmentio/kafka-go: `Conn.ReadPartitions()` тихо авто-создаёт топик.**
   Метод жёстко зашивает `AllowAutoTopicCreation:true` в протокольный
   запрос (`conn.go`, не настраивается снаружи) — использование его как
   "проверка, исчез ли топик после delete" тихо пересоздаёт топик с
   дефолтным `num.partitions` брокера (=1) РАНЬШЕ явного
   `CreateTopics(partitions=3)`. Пойман живьём: первый прогон создал топик
   с 1 партицией вместо 3. Фикс — не пробировать состояние вообще, просто
   ретраить `CreateTopics` с фиксированным интервалом.
2. **C# Confluent.Kafka: аналогичный класс проблемы** с
   `AdminClient.GetMetadata(topic, ...)` как пробой существования —
   первый прогон упал с `Topic already exists` при явном `CreateTopics`
   сразу после `DeleteTopics`. Тот же фикс (ретраить `CreateTopics`, не
   пробировать) сработал.
3. **rdkafka (Rust) 0.36 + feature `dynamic-linking` НЕ собрался**: apt
   `librdkafka-dev` в образе `rust:1` (Debian trixie) даёт librdkafka
   2.8.0, а `rdkafka-sys` v4.10.0 требует системную `librdkafka >= 2.12.1`
   — `pkg-config` падает несовпадением версий. Рабочий вариант — БЕЗ
   `dynamic-linking`: крейт сам собирает librdkafka из bundled
   C-исходников (нужны только `cmake`+`perl`+`gcc`, apt librdkafka-dev
   вообще не нужен).
4. **Kafka-clients требует `retries != 0` при `enable.idempotence=true`.**
   Пойман на Scala/fs2-kafka: `ConfigException: Must set retries to
   non-zero when using the idempotent producer` — дефолт `retries=0` у
   fs2-kafka `ProducerSettings` конфликтует с идемпотентностью, нужно
   явно `.withRetries(n)`.
5. **fs2-kafka 3.6.0: `ProducerResult[K,V]` — НЕ case class с полем
   `.records`** (как в более старых версиях библиотеки), а type alias на
   `Chunk[(ProducerRecord[K,V], RecordMetadata)]`. Паттерн доступа
   (`.head.get._2`) взят прямо из исходника самой библиотеки
   (`KafkaProducer.scala`, `ProducerOps.produceOne_`).
6. **JVM в базовом образе `scala-cli` печатает кириллицу как `?????`**
   побайтово (не визуальный артефакт терминала — проверено `xxd`,
   реальные байты `0x3f`), потому что `System.out` использует НЕ-UTF-8
   charset по умолчанию. Фикс — `//> using javaOpt
   -Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8`.
7. **modern-cpp-kafka (C++): `kafka::Properties` не строится из
   initializer-list `{{"k","v"}, ...}`** напрямую (explicit-конструктор
   внутреннего `ValueType` не даёт неявную конвертацию из `const char*`)
   — нужна явная цепочка `.put(key, value)`. `RecordMetadata::offset()`
   возвращает `std::optional<long>` — нужен `.value()`, а не голый вызов.
8. **segmentio/kafka-go: `WriteMessages` не возвращает partition/offset**
   отправленной записи (в отличие от franz-go/sarama/confluent-kafka-go)
   — паритет фич беднее не только по идемпотентности, но и по
   observability самого API.

### Content-notes

1. **Паритет фич по убыванию свежести — подтверждён на реальных находках,
   не на репутации.** JVM-референс (kafka-clients) получает фичи первым и
   не имеет пробелов. librdkafka-обёртки (5 из 11 клиентов) — второй
   эшелон, но фактически полнофункциональны (EOS/cooperative-sticky
   есть везде, где проверено). Чистые реализации — там, где паритет
   реально проседает: segmentio/kafka-go **не имеет** ни идемпотентности,
   ни cooperative-sticky (оба факта подтверждены по исходнику, не по
   слухам); kafka-python-ng имеет только классический eager sticky
   (KIP-54), а не incremental cooperative (KIP-429).
2. **"Обёртка над одним и тем же C-движком" — не маркетинг, а измеримый
   факт.** Пять независимых языковых обёрток над librdkafka
   (Python/Rust/C#/C++/Go) дали побайтово идентичное распределение
   ключей по партициям — потому что партиционер физически один и тот же
   C-код, а не пять переписанных реализаций одного алгоритма.
3. **Нативная зависимость — не бинарный вопрос "да/нет", а спектр.**
   Разброс в этом стенде: (а) обязательна и требует ручной установки в
   образе сборки — Go confluent-kafka-go, C++ modern-cpp-kafka; (б)
   формально есть, но скрыта от пользователя пакетным менеджером — Python
   confluent-kafka (manylinux wheel), C# Confluent.Kafka (NuGet
   `librdkafka.redist`); (в) опциональна — Rust rdkafka без
   `dynamic-linking` компилирует C-библиотеку сама, вообще не требуя
   системного пакета (ценой более долгой сборки).
4. **Ретраить вместо пробирования — универсальный урок про admin API.**
   Два независимых клиента (Go segmentio/kafka-go и C# Confluent.Kafka)
   упали на одном и том же классе бага: использование "безобидного"
   metadata-запроса как проверки состояния после `DeleteTopics` тихо
   меняло это состояние (авто-создание/гонка) раньше, чем успевал
   отработать явный `CreateTopics`. Рабочий паттерн везде один — не
   спрашивать состояние, а ретраить целевую операцию с фиксированным
   интервалом до успеха или дедлайна.
5. **API-стиль — реальный архитектурный выбор, не синтаксический сахар.**
   Sync-блокирующий (Java, C# `.Result`-стиль вызовов при желании),
   callback/delivery-report (sarama, confluent-kafka-go, C++), полностью
   async/await (Rust tokio, C# `async`), функциональные потоки (Scala
   fs2) — каждый стиль по-разному ведёт себя под нагрузкой (backpressure,
   упорядоченность колбэков, что блокирует event loop), что не видно на
   демо из 12 сообщений, но становится критичным на масштабе.
6. **Числа партиционирования детерминированы, не host-зависимы** (в
   отличие от throughput/latency в стенде #3) — при тех же ключах, том же
   числе партиций и том же алгоритме партиционера результат воспроизводим
   на любой машине. Различия между семьями — свойство алгоритмов, не шум
   среды.

## Стенд #9: MirrorMaker 2, два кластера, гео/DR (`mm2`)

Демонстрирует репликацию между **ДВУМЯ независимыми KRaft-кластерами**
через MirrorMaker 2 — не внутрикластерную ISR-репликацию (та уже показана в
стенде #3), а межкластерную, для гео-распределения и disaster recovery.
`us-east` — уже поднятый 3-брокерный кластер стендов #1-#8 (`compose/compose.yml`,
используется как есть, ни одна нода не пересоздавалась). `us-west` — новый
**single-node** KRaft-кластер (`mm2/compose-us-west.yml`), отдельная сеть
(`kafka-cookbook-west-net`), отдельный `CLUSTER_ID`, порт `29092`.

**Почему us-west single-node, а не 3 брокера, как us-east.** Предмет этого
стенда — механика MM2 (репликация топика, трансляция offset, failover,
active-active), а не повторная демонстрация ISR/кворумной отказоустойчивости
target-кластера (это уже сделано в стенде #3 на топологии us-east). Один
брокер как MM2-target — штатная конфигурация для демо/DR-полигона: MM2
работает через обычный клиентский API (producer/consumer/admin), для него
принципиально не важно, сколько брокеров у target, только его bootstrap-адрес.
Экономия ресурсов хоста (1 нода вместо 3) не меняет ни одну из
демонстрируемых гарантий.

MM2 запущен в **dedicated-режиме** (`connect-mirror-maker.sh mm2.properties`,
`mm2/compose-mm2.yml`) — отдельный процесс, НЕ то же самое, что Kafka Connect
distributed worker стенда #7 (`kafka-connect`, `ecosystem.yml`): у dedicated
MM2 свой внутренний Connect-кластер на каждую пару `<source>-mm2`/`<target>-mm2`.
Единственный контейнер стенда, которому нужен доступ к ОБОИМ кластерам сразу —
подключён сразу к двум compose-сетям (`kafka-cookbook-net` + `kafka-cookbook-west-net`).

### ⚠️ Точка риска: MM2 на apache/kafka 4.3.1 — завёлся с первой попытки

`connect-mirror-maker.sh` присутствует в образе и работает без единой
живой находки/фикса: три коннектора (**MirrorSourceConnector**,
**MirrorCheckpointConnector**, **MirrorHeartbeatConnector**) поднялись
одновременно, лог не показал ни одной ERROR/Exception за весь стенд (обе
фазы — active-passive и active-active).

### mm2.properties — что настроено явно (не дефолты)

- `topics`/`groups` — **точный список**, не `.*` по умолчанию: на us-east
  уже живут топики/группы 8 предыдущих стендов (`demo-log`, `demo-groups`,
  `demo-repl-*`, `demo-storage-*`, `ecosystem-*`, `demo-clients-*`) — тащить
  их через MM2 в этот демо-полигон незачем. Фильтр ограничен `orders`
  (топик) и `orders-cg.*` (группа).
- `sync.group.offsets.enabled=true` — **ключевая настройка для failover**:
  помимо checkpoint-топика (`emit.checkpoints.enabled`, дефолт true), MM2
  ДОПОЛНИТЕЛЬНО пишет транслированный offset ПРЯМО в `__consumer_offsets`
  target-кластера для той же группы — consumer с тем же `group.id`,
  стартовавший на target "с нуля", подхватывает позицию автоматически, без
  явного вызова `RemoteClusterUtils.translateOffsets` из кода.
- Интервалы (`refresh.topics.interval.seconds`, `emit.checkpoints.interval.seconds`,
  `sync.group.offsets.interval.seconds` и т.д.) сокращены до 5с — дефолты
  MM2 (минуты) непригодны для живой демо-съёмки, тот же принцип, что
  `KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS` в фундаменте стенда #4.
- `replication.factor`/`*.storage.replication.factor` = 1 везде — us-west
  single-node физически не может дать больше.
- `sync.topic.acls.enabled=false` — оба кластера PLAINTEXT без Authorizer,
  синхронизировать ACL там, где их нет, бессмысленно.

### 1. Репликация топика `orders` (ядро стенда)

Топик `orders` (3 партиции, RF=3) создан на us-east, 200 сообщений
записаны `acks=all` (`kafka-verifiable-producer.sh`). MM2 подхватил новый
топик по `refresh.topics.interval.seconds=5` и реплицировал его на us-west
под именем **`us-east.orders`** (`replication.policy` по умолчанию —
префикс `<source>.<topic>`), с сохранением числа партиций (3) и
поразделного номера партиции записи (данные шли в партицию 0 — реплика
тоже легла в партицию 0 `us-east.orders`).

### 2. Трансляция offset + симуляция failover (ядро стенда)

Consumer группы `orders-cg` прочитал **120 из 200** сообщений `orders` на
us-east (`kafka-console-consumer.sh --group`, auto-commit) и остановился —
`kafka-consumer-groups.sh --describe` подтвердил `CURRENT-OFFSET=120,
LOG-END-OFFSET=200, LAG=80`.

Через `sync.group.offsets` (interval=5с) MM2 сам записал транслированный
offset для той же группы `orders-cg` на us-west (топик `us-east.orders`) —
**без** отдельного вызова `RemoteClusterUtils.translateOffsets` из
какого-либо кода: `kafka-consumer-groups.sh --describe --group orders-cg`
на us-west сразу показал существующий committed offset.

**Failover:** consumer той же группы `orders-cg` стартовал на us-west,
топик `us-east.orders`, **без** `--from-beginning` — взял committed offset
из группы автоматически, дочитал оставшееся до конца и корректно вышел на
`LAG=0`.

### Content-note: транслированный offset — консервативный, не точный

Source committed offset = **120**, транслированный (реально применённый на
target) offset = **102** — на **18 меньше**, не байт-в-байт. Это не баг
стенда, а задокументированное поведение MM2: `OffsetSync`-записи, из
которых строится трансляция, фиксируются периодически (не на каждую
запись), и `translateOffsets`/`sync.group.offsets` интерполируют offset
**консервативно вниз** — гарантия "ни одна непрочитанная запись не будет
пропущена" важнее точного совпадения номеров (нумерация на двух кластерах
в принципе независима, offset-в-offset соответствие не гарантируется даже
при полностью синхронной репликации). Практическое следствие, подтверждено
живьём: consumer на us-west перечитал записи `102..119` (18 повторов —
already-processed на source) плюс новые `120..199` (80, ещё не читанные) —
**at-least-once через границу failover, ноль потерь, ноль пропущенных**.

```
[us-east] группа orders-cg: CURRENT-OFFSET=120 LOG-END-OFFSET=200 LAG=80
[us-west] группа orders-cg (транслировано sync.group.offsets): CURRENT-OFFSET=102 topic=us-east.orders
[assert] OK: 0 < транслированный offset (сумма по партициям, 102) <= source committed (120) — консервативная трансляция, без потери непрочитанного
[failover] consumer orders-cg на us-west с offset=102 дочитал 98 записей (102..199)
[us-west] группа orders-cg после failover: CURRENT-OFFSET=200 LOG-END-OFFSET=200 LAG=0
[assert] OK: суммарный LAG по всем партициям == 0 — failover-consumer полностью догнал us-west
```

### Content-note (ревью): LAG=0 — программный ассерт, не только печать

Предыдущая версия стенда печатала финальный `--describe` после failover и
считала "LAG=0" по глазам — ассерта в коде не было, `exit 0` наступал
независимо от реального значения LAG. Кроме того, расчёт "сколько
сообщений дочитать" держался на непроверенном допущении "все записи
`orders` легли в партицию 0" — верном для одного конкретного прогона на
чистом топике, но не гарантированном (sticky-партиционер размещает пачку
без ключа в одну партицию за раз, но НЕ обязательно в партицию 0, и не
обязательно всегда в одну и ту же).

Фикс: `sum_group_col()` суммирует нужную колонку `kafka-consumer-groups.sh
--describe` (`CURRENT-OFFSET` или `LAG`) по ВСЕМ партициям топика, а не по
захардкоженной партиции `0`. И трансляция offset, и остаток для
failover-консьюмера, и финальный LAG теперь считаются как суммы по всем
партициям — сценарий больше не ломается при неровном распределении записей
по партициям. Проверено живьём повторно на "грязном" топике (700 записей,
распределены `200/500/0` по трём партициям, не `all-in-0`) — суммарный LAG
после failover сошёлся в `0` по всем трём партициям, ассерт зелёный.

Дополнительно (не основной механизм failover в этом стенде, а честная
иллюстрация "как выглядит checkpoint-топик изнутри"): прямое чтение
`us-east.checkpoints.internal` на us-west показывает записи с ключом,
содержащим **читаемые** фрагменты `orders-cg` / `us-east.orders`
(остальные байты ключа/значения — бинарный формат `Checkpoint`-записи,
не JSON и не строка):

```
.	orders-cg..us-east.orders.... | .........x.......f..
.	orders-cg..us-east.orders.... | ....................
```

2 checkpoint-записи для нашей группы за время демо (по одной на каждый цикл
`sync.group.offsets`/`emit.checkpoints`, где офсет группы менялся).

### 3. Лаг репликации (характерный прогон)

Ещё 300 сообщений в `orders` на us-east — продюсинг (`acks=all`) занял
**1945мс**. us-west (`us-east.orders`) достиг того же суммарного count
(500 записей во всех партициях) при первой же проверке опроса, снятой
**~1870мс** после завершения продюсинга. Абсолютные миллисекунды —
host-зависимы (single-host docker, без реальной межрегиональной сети); сам
факт (MM2 — асинхронная репликация, конечный, измеримый лаг, а не
мгновенная синхронная запись) — нет.

### 4. Active-active: репликация в обе стороны, защита от циклов

Отдельный локальный топик `orders` создан **на us-west** (не реплика, а
собственные "западные" данные), MM2 переключен на `mm2-active-active.properties`
(`us-west->us-east.enabled=true` в дополнение к прежнему направлению).

⚠️ **Живая находка.** Dedicated MM2 не подхватывает новую пару кластеров "на
лету" — какие направления (`SourceAndTarget`-herders) поднимать, решается
один раз при старте процесса по `enabled=true` в конфиге. Включить
`us-west->us-east` потребовало **пересоздания** контейнера `mm2` с новым
файлом (`docker compose ... up -d --force-recreate mm2`), не hot-reload.
В Connect-режиме (MM2 как коннекторы поверх уже работающего Connect-кластера,
не dedicated) можно было бы добавить пару через `POST /connectors` без
рестарта воркера — но это другой режим запуска MM2, вне охвата этого стенда.

50 сообщений в локальный `orders` на us-west реплицировались на us-east под
именем **`us-west.orders`** (50/50, тот же принцип префикса). Проверка
защиты от циклов — список топиков на обоих кластерах **не содержит**
`us-west.us-east.orders` ни `us-east.us-west.orders`:

```
[us-east topics] orders, us-west.orders, us-west.checkpoints.internal, us-west.heartbeats, ...
[us-west topics] orders, us-east.orders, us-east.checkpoints.internal, us-east.heartbeats, ...
[assert] OK: us-west.orders на us-east = 50/50 записей, циклов нет (0 топиков вида <cluster>.<remote>.orders)
```

**Честно про механизм защиты в ЭТОМ стенде.** У самого MM2 есть встроенная
эвристика против циклов (`DefaultReplicationPolicy` распознаёт префикс
топика и по умолчанию не реплицирует "чужие" уже-префиксированные топики
обратно тому же кластеру-источнику). Но в этом стенде реальный барьер —
**explicit `topics=orders`** (точное имя, не regex `.*`) с ОБЕИХ сторон:
`us-east.orders`/`us-west.orders` физически не совпадают со строкой
`orders`, поэтому не попадают под фильтр повторного направления независимо
от встроенной эвристики. Это наш собственный выбор конфигурации, а не
демонстрация исключительно внутренней защиты MM2 — сказано прямо, чтобы не
переоценивать то, что проверено.

### Что MM2 переносит (проверено живьём в этом стенде) vs что нет

| Перенесено и проверено | НЕ проверено в этом стенде | НЕ переносит (по докам, автоматически) |
|---|---|---|
| Данные топика (offset-в-offset внутри партиции, порядок сохранён) | ACL (`sync.topic.acls.enabled=false` — оба кластера без Authorizer) | Автоматический client-failover — переключение продюсеров/консьюмеров на другой bootstrap делает приложение/оператор, не MM2 |
| Consumer offset (checkpoint + `sync.group.offsets` — прямая запись в `__consumer_offsets` target) | Конфиги топика через `sync.topic.configs` (включено дефолтом, отдельно не гонялось) | Данные, записанные ДО того, как MM2 узнал о топике (`refresh.topics.interval.seconds`-задержка обнаружения) |
| Число партиций (сохранено 1:1) | | |

### RPO/RTO — оговорка по фактам этого стенда

MM2 асинхронный: лаг репликации (раздел 3) — это и есть окно потенциальной
потери при внезапном исчезновении source-региона (RPO > 0, не ноль). В
демо, где источник жив и просто отстаёт локально в docker, это не
проверялось напрямую (потребовало бы `docker kill` кластера-источника
целиком — вне охвата этого стенда, us-east нужен исправным для fixtures
следующей задачи серии), но сам механизм — прямое следствие раздела 3:
если source исчезнет ДО того, как MM2 догонит, непереехавший хвост
потерян. **Failback** (вернуться на восстановленный us-east) в этом стенде
не демонстрировался — по докам он сложнее failover (нужно долить
накопившееся на target обратно, не задвоив), задокументировано как
content-note, не проверено живьём.

### Content-notes

1. **Stretch-кластер vs репликация кластеров — не показано напрямую в
   стенде** (это отдельный, не-MM2 сценарий — синхронный `acks=all` между
   зонами через `broker.rack`, ближе к теме стенда #3), но контраст явный
   по фактам: MM2 здесь ни разу не тормозит запись на source (она идёт
   локально, независимо от состояния target), а лаг (раздел 3) — это цена,
   которую платит именно ЧТЕНИЕ на target, не запись на source.
2. **Транслированный offset — гарантия "не пропустить", не "быть точным".**
   Раздел 2 — не абстрактное утверждение из документации, а измеренный
   живой разрыв (120 vs 102) с объяснением механизма (периодичность
   OffsetSync) и подтверждённым итогом (0 потерь, 0 пропусков, LAG=0 после
   дочитывания).
3. **Однонаправленный demo-топик vs active-active — разные конфиг-файлы,
   не runtime-переключение.** Dedicated MM2 требует пересоздания процесса
   для смены набора активных направлений репликации — практический урок
   для эксплуатации, не только для этого стенда.
4. **RPO > 0 — не гипотеза, а прямое следствие раздела 3.** Раз лаг
   репликации измеримо ненулевой (пусть и суб-секундный на локальном
   docker), то у "внезапной потери source-региона" всегда есть окно потерь
   размером с этот лаг — стенд специально не подменяет теорию
   бенчмарком нулевой задержки.

  `output read_committed=0`, `committed-offset группы=0` — несмотря на 10

## Проверено живьём (`mm2`, 2026-07-09)

- **MM2 на apache/kafka 4.3.1 (dedicated-режим) завёлся с первой попытки** —
  ни одной живой находки/фикса не потребовалось (редкий случай для этой
  серии): три коннектора (Source/Checkpoint/Heartbeat) стартовали
  одновременно, ноль ERROR/Exception в логе за весь стенд.
- **Репликация топика `orders`:** 200/200 записей на us-east → `us-east.orders`
  на us-west, 200/200 (партиция сохранена: все записи в партиции 0 на
  обеих сторонах). Второй раунд (active-active) — 50/50 в обратную
  сторону (`us-west.orders`).
- **Трансляция offset + failover — реальный, не имитированный, LAG=0 —
  программный ассерт (не печать).**
  `sync.group.offsets.enabled=true` перенёс committed offset группы
  `orders-cg` с us-east (120) на us-west автоматически, БЕЗ отдельного
  Java/Go-инструмента с `RemoteClusterUtils.translateOffsets` — сам MM2
  пишет транслированный offset прямо в `__consumer_offsets` target.
  Транслированное значение (102, сумма по всем партициям) оказалось
  **консервативно меньше** source (120) — честно задокументированная
  особенность (периодичность `OffsetSync`, не байт-в-байт трансляция).
  Failover-consumer на us-west дочитал с offset=102 до конца (98 записей,
  `102..199`), ноль потерь, ноль пропусков (18 записей `102..119` —
  законный повтор, at-least-once через границу failover). **Ревью-фикс:**
  раньше суммарный `LAG=0` только печатался (`--describe` без парсинга,
  `exit 0` независимо от результата) и расчёт остатка держался на
  допущении "всё в партиции 0". Теперь `sum_group_col()` суммирует
  `CURRENT-OFFSET`/`LAG` по ВСЕМ партициям топика, и в конце — реальный
  `[assert]` на суммарный `LAG == 0` с `exit 1` при провале; проверено
  повторно на неровном распределении по партициям (`200/500/0`), ассерт
  зелёный.
- **Active-active без циклов, подтверждено списком топиков на ОБЕИХ
  сторонах:** ни `us-west.us-east.orders`, ни `us-east.us-west.orders` не
  появились. Реальный барьер в этом стенде — явный `topics=orders` фильтр
  с обеих сторон (реплицированные топики уже несут префикс и не совпадают
  со строкой-фильтром), не только встроенная эвристика MM2 — сказано
  прямо, не переоценено.
- **Живая находка про dedicated-режим:** новая пара кластеров
  (`us-west->us-east`) не подхватывается на лету — нужно пересоздание
  контейнера `mm2` с новым `mm2-active-active.properties`. Не баг —
  задокументированная особенность dedicated connect-mirror-maker.sh.
