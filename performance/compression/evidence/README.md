# evidence — манифест

Файлы этого каталога отслеживаются git явными исключениями из общего
правила `*.log`/`*.csv` (см. `.gitignore` стенда и корневой `.gitignore`,
секция `performance/compression/evidence/`). Состав проверяется
`git ls-files evidence/` в гейте (`ops/verify-static.sh`), не `ls` —
файл на диске и файл в репозитории не одно и то же (см. предупреждение в
`.gitignore` и урок `feedback_...` про стенд `inmemory`, где 20 логов лежали
на диске, но не в git).

Рабочие каталоги прогонов (`scratchout*/`) не коммитятся — там сырые данные
всех повторов, включая прогревочные и отладочные. Каждый файл в этом
манифесте либо публикует **весь** измеренный разброс (сводные CSV с
колонками `*_median`/`*_min`/`*_max`), либо явно помечен ниже как
**один прогон из серии**.

## Чего здесь нет

Честно — где опубликован один прогон или часть разброса, а не всё измеренное:

- **`dictionary` — только один прогон, без повторной серии.** В отличие от
  остальных пяти сценариев, для `dictionary` не собиралась серия
  прогревочный+N-зачётных: сценарий сам по себе — сжатие 180 000 отдельных
  сообщений (без склейки, см. комментарий в `codecs/dictionary.go`), это уже
  многократный вызов компрессора, но не многократный запуск **бинарника**.
  Воспроизводимость размеров подтверждена только тем, что размеры совпали
  между `evidence/dictionary-summary.csv` и рабочим логом того же прогона —
  не независимой серией повторов, как у остальных сценариев. Читателю,
  которому нужна такая проверка, придётся прогнать бинарник самому (команда
  в `README.md`).
- **`dictionary` — скорость не измерялась вообще**, не «измерена и вышел
  ноль». `compress_mbs`/`decompress_mbs` в CSV — `0.00` по конструкции:
  сценарий отвечает на вопрос о размере (эффект словаря), а не о скорости —
  см. комментарий над `RunDictionary` в `codecs/dictionary.go`. Значение
  `0.00` — не измерение, публиковать его как «скорость словарного сжатия»
  нельзя.
- **`columnar` — 4 прогона выполнены (`col-r0`…`col-r3` в `scratchout/`,
  не коммитятся), но ни один не был исключён как прогревочный.** В отличие
  от `matrix`/`zstd-impl`/`incompressible`, где методика «отбросить первый
  прогон» установлена диагностикой (`task-3-drift-diagnosis.md`) и применена
  явно, для `columnar` это решение отдельно не принималось. Сведённая
  `columnar-summary.csv` в этой задаче (Задача 8) пересчитана из всех 4
  прогонов как медиана+min–max **без исключений** — честно, но это означает
  более широкий диапазон, чем если бы прогревочный прогон был выброшен:
  разброс сжатия доходит до **60%** (`table-col`, zstd) — шире, чем
  максимум по всей матрице `matrix` (33.7%, см. `FIXTURES.md`). До этой
  задачи в `evidence/columnar-summary.csv` были опубликованы числа ровно
  **одного** прогона (`col-r1`) без пометки об этом — исправлено при сборке
  манифеста.
- **`matrix`/`zstd-impl`/`incompressible` — нет отдельного «представительного»
  лога.** У этих трёх сценариев в `evidence/` только сводные CSV, ни одного
  сырого stderr-лога отдельного прогона: при публикации медианы+диапазона
  один лог из четырёх-пяти выглядел бы как произвольно выбранный «эталонный»
  прогон, что противоречит смыслу диапазона (см. `task-6-compression-report.md`,
  раздел «Отклонения», п.3). Сырые логи каждого прогона лежат в `scratchout/`
  и `scratchout{2..11}/` — не коммитятся, воспроизводимы командами из
  `README.md`.
- **`http-transport` — 2 прогона, не 4.** HTTP sweep по 8 полосам с 5
  повторами на точку — другой масштаб задачи (двумя контейнерами, живой
  сетевой путь), два независимых прогона были признаны достаточными, потому
  что оба согласны в главном выводе (диапазон перелома gzip/zstd), см.
  `task-7-compression-report.md`.
- **Сырые CSV отдельных прогонов** (`col-r0/columnar.csv`…`col-r3/columnar.csv`,
  `matrix-run{1..5}.log`, прогревочные прогоны `zstd-impl`/`incompressible`)
  — в `scratchout*/`, не коммитятся. Числа, вошедшие в сводные CSV этого
  каталога, проверяемы построчным пересчётом из них (см. отчёты задач
  3/4/6/8), но сами файлы читателю репозитория недоступны — только повторным
  прогоном.
