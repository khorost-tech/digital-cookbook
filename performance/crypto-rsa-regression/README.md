# crypto/rsa: регрессия Go 1.20 и как её ловить

Стенд к статье [«Go 1.20 и RSA: что на самом деле замедлилось — и как ловить регрессии производительности»](https://khorost.tech/performance/go-crypto-rsa-regression/).

Go 1.20 перевёл `crypto/rsa` с `math/big` на constant-time `crypto/internal/bigmod`
(защита от тайминговых атак) и просел по скорости. Стенд снимает одинаковый набор
бенчмарков на **шести версиях Go** и показывает: просели **обе** стороны RSA, но
несимметрично — публичные verify/encrypt в 5–7 раз, приватная подпись на +34…+61%;
ECDSA/HMAC значимо не изменились; восстановление к 1.23 (у 4096 — неполное). Плюс
`regression-gate.sh` — CI-гейт, который поймал бы это до прода.

Только stdlib — код компилируется одинаково на Go 1.19…1.26 без внешних модулей.
RS256 (подпись JWT) — это `rsa.SignPKCS1v15` + SHA-256; `golang-jwt` под капотом зовёт
ровно их.

## Матрица (медиана `ns/op`, одна машина; фикс-ключи, 8 раундов с ротацией порядка версий)

| Операция | 1.19 | 1.20 | 1.21 | 1.23 | 1.25 | 1.26 |
|----------|-----:|-----:|-----:|-----:|-----:|-----:|
| RSA-2048 **verify** | 49µs | **246µs** | 140µs | 36µs | 36µs | 39µs |
| RSA-2048 **encrypt** | 51µs | **261µs** | 143µs | 38µs | 40µs | 40µs |
| RSA-4096 **verify** | 146µs | **1000µs** | 1014µs | 481µs | 470µs | 540µs |
| RSA-4096 **encrypt** | 143µs | **1006µs** | 1025µs | 490µs | 469µs | 542µs |
| RSA-2048 sign | 1.42ms | 1.91ms | 1.42ms | 1.28ms | 1.25ms | 1.35ms |
| RSA-4096 sign | 8.01ms | 12.89ms | 8.03ms | 7.21ms | 7.34ms | 7.92ms |
| RS256 round-trip | 1.47ms | 2.21ms | 1.43ms | 1.32ms | 1.36ms | 1.37ms |
| ECDSA-P256 sign | 25µs | 25µs | 24µs | 24µs | 33µs | 35µs |
| ECDSA-P256 verify | 75µs | 73µs | 74µs | 70µs | 76µs | 74µs |
| HMAC-SHA256 | 1490ns | 1422ns | 793ns | 793ns | 822ns | 837ns |

Все различия **по RSA** на 1.19→1.20 значимы (p≤0.001, `benchstat`). Просели **обе**
стороны RSA: публичные verify/encrypt — в 5–7 раз (+405…+602%), приватная подпись —
+34% (2048) и +61% (4096). В измеренном наборе крупную регрессию показал только RSA:
ECDSA **P-256** и HMAC значимо не изменились (p>0.4). ⚠️ Охват: мерили только P-256, а
release notes Go 1.20 отмечают рост CPU у ECDSA на 5–30% преимущественно для
**P-384/P-521** — эти кривые здесь не проверялись. RSA-2048-verify
к 1.23 восстановился ниже 1.19; RSA-4096-verify на 1.26 всё ещё **+271%**.

**Про протокол (важно):** эти числа получены только после смены методики. Когда версии
гонялись подряд, разброс по подписи доходил до ±60–70%, а разница 1.19→1.20 выходила
статистически **незначимой** (p≈0.1). С раундами и **ротацией порядка версий** разброс на
baseline упал до ±4–18%, и просадка подписи стала значимой. Прежде чем объявить «эффекта
нет», проверьте свой протокол замера.

Атрибуция: вилку +15–45% release notes Go 1.20 дают для **расшифровки** (не подписи);
Go 1.21 notes подтверждают регрессию и расшифровки, и подписи. RS256 round-trip (+50%)
измеряет sign+verify вместе, не подпись отдельно.

Ключи **фиксированы** (`testdata/*.pem`), версии чередуются по раундам **с ротацией
порядка** (в раунде r список циклически сдвигается) — чтобы ни одна версия не занимала
всегда один и тот же тепловой слот. Опубликованная выборка снята при `ROUNDS=8`: каждая
версия проходит все шесть позиций, но две позиции достаются ей повторно. Дефолт скрипта
теперь `ROUNDS=12` (кратно числу версий) — это полностью сбалансированный план, каждая
позиция ровно по два раза. Полный трёхколоночный `benchstat` (sec/op + B/op +
allocs/op, с p-value) — в `results/benchstat-summary.txt`. Аллокации: RSA-2048-подпись
108→2, RSA-4096 — 122→53: bigmod экономнее по памяти.

## Почему публичные

Не потому, что «bigmod считает любой экспонент одинаково» — его возведение в степень
проходит по всем байтам экспонента, работа растёт с длиной (constant-time = независимость
от *значений* битов при данной длине, а не равная цена публичной и приватной операции).
Подтверждённый факт из исходника (Go 1.20.14, rsa.go ~L455–465): публичная операция
(`encrypt`/`verify`) строит `bigmod.Modulus` НА КАЖДОМ вызове, а приватный путь модуль
кеширует после `Precompute`. Но «per-call надбавки у приватного нет» было бы неверно: само
constant-time возведение (оконный проход + предподсчёт таблицы степеней в `bigmod.Exp`)
платится на каждом вызове, включая приватный. Инженерный вывод — про ОТНОСИТЕЛЬНУЮ цену:
публичная операция дёшева (короткий `e=65537`), и общая стоимость нового алгоритма
(построение модуля + оконный проход + таблица) для неё огромна на фоне её крошечной
работы; у приватной та же стоимость тонет в миллисекундах основного modexp. Отсюда кратная
просадка именно на verify/encrypt.

## Запуск

Матрица версий — через Docker (полные патч-теги `golang:1.19.13…1.26.4`). Хостовый Go
нужен только для быстрой правки бенча. Гоняйте на НЕнагруженной машине.

```bash
# вся матрица: пишет results/go<patch>.txt, печатает сводку. ~12 минут.
# ROUNDS раундов с ротацией порядка версий (round-robin) против теплового дрейфа.
bash matrix.sh
# подмножество версий / другое число раундов:
VERSIONS="1.19.13 1.20.14 1.26.4" ROUNDS=6 bash matrix.sh

# CI-гейт: роняет сборку при регрессии медианы > порога (дефолт 50%) или исчезновении бенча.
bash regression-gate.sh results/go1.19.13.txt results/go1.20.14.txt   # -> FAIL (verify/encrypt)
bash regression-gate.sh results/go1.21.13.txt results/go1.26.4.txt    # -> OK
```

`regression-gate.sh` рядом с гейт-решением (по медиане, без внешних зависимостей)
печатает `benchstat` (честная A/B-статистика), если доступен Docker.

Быстрая проверка бенча на хосте (без матрицы):

```bash
go test -bench=. -benchmem -count=10 -run='^$' ./...
```

## Дисциплина замеров

- Спайк 1.20 огромен и устойчив к шуму — подаётся уверенно.
- Тонкую кривую восстановления (1.20→1.26) — только через `benchstat` (8 независимых
  раундов по `-count=1` каждый,
  доверительные интервалы) и как «один прогон на одной машине»: Docker-на-Windows и
  тепловой троттлинг шумят. См. `measurement-cache-traps`.
- `matrix.sh` fail-loud: печатает `go version`, проверяет, что нужная версия и бенчи
  реально в выводе, падает при любом сбое.

## Версии/окружение

Официальные образы `golang:*`. Короткие теги `golang:1.X` **изменяемы** — конкретный
прогон снят на этих патч-версиях (их же печатает `matrix.sh` в конце):

`go1.19.13` · `go1.20.14` · `go1.21.13` · `go1.23.12` · `go1.25.12` · `go1.26.4`

Замеры на Windows 11 + Docker 29.6.1, AMD Ryzen 7 5800X3D, контейнеры linux/amd64.
Абсолютные `ns/op` у вас будут другими — важны соотношения.
