# Стенд: data-oriented design и CPU-кэши

Стенд к статье [«Data-oriented design и CPU-кэши»](https://khorost.tech/performance/data-oriented-design-cpu-cache/).
Одни и те же ядра написаны дважды — на Go (`go/main.go`) и на C (`c/dod.c`, clang -O2). C служит проверкой
воспроизводимости: эффект, который есть и в Go, и в C, не сводится к особенностям одного компилятора. Причину это
не устанавливает — оба компилятора могут упираться в одно ограничение или делать похожие преобразования, — поэтому
объяснения опираются на отдельные контроли, машинный код (ось `codegen`) и счётчики. Генератор у обоих один
(splitmix64), поэтому контрольные суммы двух языков обязаны совпасть — стенд это проверяет.

Два хоста — две архитектуры:

| хост | процессор | линия кэша | запуск |
|---|---|---|---|
| `mac` | Apple M5, arm64 | 128 байт (`hw.cachelinesize`) | нативно: Apple clang, Go 1.27.2 |
| `devproxy` | AMD Ryzen 9 7940HS (Zen 4) в ВМ Proxmox с CPU type `host`, amd64 | 64 байта | `docker run --privileged` с образом из `Dockerfile`: clang 19, Go 1.27.2, `perf` 6.12 |

Аппаратные счётчики (`perf stat`) есть только на втором хосте: в ВМ с обобщённым типом CPU (`qemu64`,
`x86-64-v2-AES`) и в Docker Desktop на Mac все аппаратные события отвечают `<not supported>`.

## Ядра

| ядро | что делает |
|---|---|
| `chase ws=N` | зависимый обход по одному циклу Саттоло: узел — слово на 128 байт, рабочее множество от 16K до 256M |
| `seq ws=N` | последовательная сумма того же объёма |
| `aos` / `soa` / `ptr n=N fields=1\|8 [shuffled=0\|1]` | сумма одного или всех восьми полей частицы (8 × float64 = 64 байта): массив структур, структура массивов, срез указателей на отдельно выделенные объекты (по порядку выделения или вперемешку) |
| `cross n=N split=0\|1` | сколько частиц пересечёт границу за шаг (`x + vx >= 1000`): частица целиком (64 байта) или горячие `x`, `vx` отдельным массивом по 16 байт, холодные шесть полей — в другом |
| `fs dist=D` | две нити, атомарный инкремент двух счётчиков на расстоянии D байт от базы, выровненной на 256 |
| `branch` / `branchless n=N sorted=0\|1` | сумма байтов ≥ 128 — через условие и через маску |
| `filter` / `filter_branchless n=N sorted=0\|1` | отбор байтов ≥ 128 в выходной массив — через условие и через безусловную запись со сдвигом индекса |
| `pad` | размер `cpu.CacheLinePad` из `golang.org/x/sys/cpu` для архитектуры (только Go) |

Каждое ядро печатает одну строку JSON: медиана нс на операцию из 7 замеров после прогрева, число операций,
контрольная сумма. Один замер — не меньше 2^24 операций (короткое ядро повторяется), перед всеми замерами — 2 с
разгона частоты. `reps=0` — только подготовка данных: `perf stat` снимает счётчики при `reps=0` и `reps=3`, и
разность делится на число прогонов ядра — так счётчики относятся к ядру, а не к заполнению массивов.

## Оси

| ось | вопрос |
|---|---|
| `control` | суммы C и Go совпадают; другое зерно меняет сумму (контроль сверки); линия по системе и паддинг x/sys/cpu; счётчики есть в `--privileged` и отсутствуют без него |
| `hierarchy` | 16K и 32K — одно плато; задержка шага растёт до RAM; 256M к 16K; случайный обход к последовательному на 128 байт |
| `aos_soa` | за кэшем SoA быстрее при одном поле; SoA не выигрывает, когда нужны все поля; вровень, когда данные в кэше; срез указателей вперемешку и по порядку; горячие поля отдельно от холодных за кэшем быстрее частицы целиком |
| `false_sharing` | во сколько раз 8, 16, 32, 64, 128 байт медленнее, чем 256 |
| `branch` | несортированные данные к отсортированным: сумма и отбор, с условием и без; прямое сравнение отбора с условием и без условия на одних данных |
| `codegen` | машинный код тем компилятором, что собирает ядра на хосте (`clang -O2 -g -S`, `go build -gcflags=-S`): есть ли условный переход среди инструкций строки с условием; векторизована ли сумма в C; контроль детектора — отбор без условия |
| `counters` | только devproxy, на операцию: cache-misses обхода 16K и 256M, cache-misses и cache-references AoS и SoA, branch-misses суммы и отбора; все ли события считались всё время (доля времени работы счётчика из `perf stat -x`, без мультиплексирования). Разность двух процессов — оценка вклада ядра после вычитания подготовки, а не точное выделение событий цикла |

Публикуются отношения, корзины и пороги — не нс конкретной машины. Медианы и точные отношения лежат в полях
с `~`: они меняются от прогона к прогону и в сравнение сессий не входят. Гипотезы — в `expected.json` до
первого запуска ядер, пересмотры (`revision_*`) — до сессий.

## Запуск

Нужны: на Mac — Xcode Command Line Tools (clang) и Go (нужная версия подтянется по `toolchain` в `go.mod`);
Linux-хост с аппаратными счётчиками, доступный по ssh, с docker (по умолчанию через `sudo -n`).

```bash
DOD_REMOTE=user@host scripts/run-all.sh    # оба хоста, все оси, сводка сессии, маркер, тесты, диверсии
python3 scripts/run-checks.py false_sharing  # одна ось, без записи фикстуры
```

Одно ядро руками:

```bash
clang -O2 -pthread -o dod-c c/dod.c && ./dod-c fs dist=64
cd go && go build -o ../dod-go . && cd .. && ./dod-go fs dist=64
```

## Уборка

```bash
rm -rf out
ssh "$DOD_REMOTE" sudo docker image rm dod-stand:1
```
