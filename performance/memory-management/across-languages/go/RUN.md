# Управление памятью в Go — стенд

Go-часть стенда к статье «Управление памятью в разных языках». Демонстрирует
поведение трассирующего сборщика мусора Go на трёх опорах.

- **Тулчейн:** `go version` = `go1.26.3 windows/amd64`
- **Машина замеров:** AMD Ryzen 7 5800X3D, `goos=windows goarch=amd64`
- Перед сборкой: `export GOPROXY=https://go.khorost.tech,direct`
- cgo/`-race` не нужны.

Числа ниже — **реальный вывод прогонов на этой машине**. `ns/op` и абсолютные
величины пауз машинозависимы; `allocs/op` — результат конкретного бенчмарка (для
`sync.Pool` не гарантия: пул чистится при GC), но контраст 1 против 0 устойчив,
как и факт сборки цикла.

---

## Опора 1 — трассирующий GC собирает циклическую структуру

Строим 200 000 пар узлов со взаимными ссылками (`A.other=B`, `B.other=A` — цикл
длины 2), снимаем `runtime.ReadMemStats`, обнуляем единственный корень, вызываем
`runtime.GC()` дважды и снимаем память снова. Reference counting такой цикл бы не
собрал (счётчики друг друга держат >0); трассирующий GC идёт от корней и собирает
всё недостижимое.

> Финализаторы на узлы цикла НЕ вешаем: в Go вызов финализатора для объекта в
> цикле не гарантирован. Доказательство — падение HeapAlloc/HeapObjects, а не финализатор.

```
$ go run ./cmd/cycle
```

Наблюдаемый вывод:

```
go version: go1.26.3
pairs=200000 (взаимные ссылки A.other=B, B.other=A -> 400000 узлов, 200000 циклов длины 2)
[baseline] HeapAlloc=0.33 MB  HeapObjects=290
[после постройки] HeapAlloc=32.40 MB  HeapObjects=400321
[после roots=nil + GC x2] HeapAlloc=0.35 MB  HeapObjects=320
[reclaimed] 32.05 MB  400001 объектов освобождено
ВЫВОД: циклический граф собран трассирующим GC (reference counting здесь бы утёк).
```

**Что доказывает:** ~32 МБ и 400 001 объект освобождены после того, как граф стал
недостижим. Циклические ссылки не помешали сборке.

## Опора 2a — escape analysis (стек против кучи)

`escape.go`: `stackLocal` берёт адрес локала, но не выпускает его из кадра —
объект остаётся на стеке; `heapEscape` возвращает `&point` — объект обязан уехать
в кучу. Решения компилятора видны в `-gcflags='-m'`.

```
$ go build -gcflags='-m' ./...
```

Строки по `escape.go` (полный вывод в `escape.txt`):

```
./escape.go:23:7: &point{...} does not escape
./escape.go:32:2: moved to heap: p
```

**Что доказывает:** один и тот же тип `point` компилятор кладёт на стек, когда
указатель не убегает (`does not escape`), и в кучу, когда убегает (`moved to heap`).
Стековые объекты сборщик не трогает — они освобождаются на выходе из функции.

## Опора 2b — давление на аллокатор, allocs/op ± sync.Pool

`pool_test.go`: `BenchmarkNoPool` аллоцирует буфер 4 КБ на каждой операции (и уводит
его в глобал, чтобы escape analysis не оставил на стеке); `BenchmarkPool` берёт буфер
из `sync.Pool` и возвращает.

```
$ go test -bench=. -benchmem -run='^$' ./...
```

Наблюдаемый вывод (полный — в `bench.txt`):

```
goos: windows
goarch: amd64
pkg: memmgmt
cpu: AMD Ryzen 7 5800X3D 8-Core Processor
BenchmarkNoPool-16    	 1788718	       686.8 ns/op	    4096 B/op	       1 allocs/op
BenchmarkPool-16      	100000000	        11.30 ns/op	       0 B/op	       0 allocs/op
PASS
ok  	memmgmt	3.074s
```

**Что доказывает:** детерминированное `allocs/op` — **1** без пула против **0** с пулом
(и 4096 B/op против 0 B/op). Пул убирает аллокацию с горячего пути, а значит и будущую
работу сборщика. `ns/op` здесь машинозависим и не абсолютизируется.

## Опора 3 — паузы GC (ОДИН прогон, качественно)

Аллокационно-тяжёлый ворклоад (200 раундов × 50 000 короткоживущих срезов). Программа
читает **реальные длительности** STW-пауз через `runtime/debug.ReadGCStats`
(поле `PauseQuantiles` — настоящие наносекунды, а не грубая оценка по границам бакетов
гистограммы `runtime/metrics`); дополнительно полезен `GODEBUG=gctrace=1`.

```
$ GODEBUG=gctrace=1 go run ./cmd/gcpauses
```

Наблюдаемый вывод — **канонический прогон**, linux/amd64 (в Docker `golang:1.26`;
он же сохранён целиком в `gcpauses.txt`):

```
циклов GC за процесс: 356; суммарная пауза STW: 64.971301ms
длительности STW-пауз (реальные, этот прогон):
  min ~ 69.603µs
  p50 ~ 139.61µs
  p90 ~ 260.554µs
  p99 ~ 328.212µs
  max ~ 371.148µs
```

**Что доказывает:** в этом прогоне STW-паузы — десятки–сотни микросекунд (медиана
~140 мкс, p99 ~330 мкс). В других прогонах максимум отдельных пауз заходил в низкие
миллисекунды (0.5–3 мс) — поэтому программа НЕ печатает прошитый вывод «субмиллисекундные»,
а даёт только измеренные значения.

**Caveat (важно — ловушка измерения):** это замер ОДНОГО прогона; абсолютные числа
host-зависимы НА ПОРЯДКИ.

- На **windows/amd64** те же паузы p50/p90 читаются как `0s`: системный таймер Windows не
  разрешает суб-миллисекундные интервалы, короткие STW округляются в ноль (виден лишь ~1 мс
  выброс). Именно поэтому первоначальный windows-прогон ошибочно выглядел как «доли микросекунды».
- Поэтому паузы снимаем на linux (Docker), а в статью выносим только **качественную границу**
  (суб-миллисекунда против десятков мс у stop-the-world сборщиков), не конкретное число.
- [Go GC Guide](https://go.dev/doc/gc-guide) перечисляет несколько источников GC-latency и
  единого «диапазона пауз» не даёт.
