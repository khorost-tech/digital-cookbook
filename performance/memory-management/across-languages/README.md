# Управление памятью в разных языках: одна структура, четыре модели

Стенд к статье [«Куча, стек и сборщик мусора: как языки управляют памятью»](https://khorost.tech/performance/memory-management-across-languages/).

Один и тот же простой сценарий — **узел графа со взаимной ссылкой** (`node ↔ node`, цикл длины 2) — прогнан на **C++**, **Rust**, **Go** и **Java**, чтобы сравнивать не задачи, а модели памяти. Свидетельства снимаются с живого прогона: счётчики деструкторов, отчёты санитайзера, вывод компилятора, дельта кучи — а не «на словах».

Три опоры:

1. **Цикл ссылок** — собирает ли его освободитель памяти;
2. **Давление на аллокатор и раскладка** — счётчики аллокаций (`allocs/op` — результат конкретного бенчмарка, надёжнее машинозависимого `ns/op`) и байты раскладки;
3. **Паузы GC** — один прогон, качественная граница (не свойство языка).

## Опора 1 — цикл ссылок: подсчёт ссылок течёт, трассирующий GC собирает

Два узла ссылаются друг на друга, внешние ссылки отброшены. С точки зрения программы оба — мусор.

| Механизм | Язык | Цикл собран? | Свидетельство (живой прогон) |
|---|---|---|---|
| подсчёт ссылок | C++ (`shared_ptr`) | **нет** | 0 вызовов деструктора; LeakSanitizer: 80 байт в 2 аллокациях |
| подсчёт ссылок | Rust (`Rc<RefCell>`) | **нет** | 0 вызовов `Drop` |
| трассирующий GC | Go | **да** | HeapAlloc 32.40 → 0.35 МБ, освобождено 400 001 объектов после `runtime.GC()` |
| трассирующий GC | Java | **да** | used-heap 37.5 → 1.3 МБ (reclaimed 34.5), сработали все 400 000 `Cleaner` |

Чинится подсчёт ссылок разрывом цикла: владелец держит потомка сильной ссылкой, обратная ссылка — слабая (`weak_ptr` / `Weak`). Тогда C++ и Rust вызывают деструкторы обоих узлов (счётчик = **2**).

Тонкость C++ (задокументирована в `cpp/RUN.md`): LeakSanitizer консервативно сканирует стек как корни, поэтому цикл строится в отдельной функции и стек затирается — иначе остаточный указатель в кадре `main` маскирует настоящую утечку ложноотрицательным результатом. Тонкость Go: финализаторы на узлы цикла намеренно **не** вешаются (для циклов их вызов не гарантирован) — сборка доказывается дельтой кучи.

## Опора 2 — характерный баг: где ловится

**Ровно один и тот же** use-after-free в обоих языках: взять указатель на элемент `vector`/`Vec`, затем `push_back`/`push`, реаллоцирующий буфер, затем прочитать висячий указатель.

- **Rust** — не компилируется: `rustc borrow_error/uaf.rs` → `error[E0502]`, код возврата 1, бинарь не создан. Borrow checker ловит на этапе компиляции.
- **C++** (`uaf.cpp`, тот же паттерн с `std::vector`) — компилируется молча, падает в рантайме под ASan: `heap-use-after-free` на 12-байтовом старом буфере (3×`int`), с тремя стеками (use / free=`push_back` / alloc).

## Опора 2 (Go/Java) — давление на аллокатор и раскладка

- **Go, escape analysis** (`go build -gcflags=-m`): один тип `point` остаётся на стеке (`does not escape`), когда указатель не убегает, и `moved to heap`, когда возвращается наружу.
- **Go, allocs/op** (`go test -bench=. -benchmem`): цикл, аллоцирующий буфер на каждой операции, — **1 alloc/op (4096 B)**; он же через `sync.Pool` — **0 alloc/op (0 B)** в этом бенчмарке. Оговорка: `sync.Pool` вправе очиститься при любом GC, поэтому ноль — результат конкретного прогона под нагрузкой, а не гарантия на каждый вызов; но `allocs/op` для контраста надёжнее машинозависимого `ns/op`.
- **Java, JOL**: узел с одним `int` и одной ссылкой — **24 байта** (12 из них заголовок + выравнивание). Autoboxing: `Integer[]` на 10 000 элементов — 200 016 байт против 40 016 у `int[]`, **ровно 5.00×**, 160 000 байт оверхеда только на боксинге.

## Опора 3 — паузы GC (один прогон, качественно)

Абсолютные числа зависят от машины и нагрузки — важна качественная граница, не секунды.

- **Go** (`debug.ReadGCStats`, реальные длительности; linux/amd64 в Docker): в каноническом прогоне медиана STW-паузы ~140 мкс, p99 ~330 мкс, max ~370 мкс; в других прогонах отдельные паузы заходят в низкие миллисекунды. ⚠️ На windows/amd64 короткие паузы тонут в разрешении таймера и читаются как `0s` — отсюда числа снимаем на linux (см. `go/RUN.md`). Программа печатает только измеренные значения, без прошитого вывода.
- **Java** (`-Xlog:gc`, куча 512 МБ), один и тот же ворклоад: **G1** (поколенческий) — паузы молодого поколения ~3.4–6.9 мс; **ZGC** (в JDK 21 непоколенческий, `-XX:+UseZGC`) — 0.003–0.020 мс (сбор конкурентный). Разница — три порядка.

## Запуск

Тулчейн-специфика (Docker для C++/ASan, WSL/нативная ФС для Rust/Java из-за drvfs) — в `RUN.md` каждого языка. Канонические команды:

### C++ (gcc:13 в Docker; LeakSanitizer/ASan)
```bash
cd cpp && bash build.sh          # cycle_leak (утечка+LSan), cycle_fixed (weak_ptr), uaf (ASan)
```

### Rust (rustc 1.96.1)
```bash
cd rust && cargo run --bin cycle             # DROPS: 0 (Rc-цикл течёт) → 2 (Weak чинит)
rustc --edition 2021 borrow_error/uaf.rs     # error[E0502], бинарь не создан
```

### Go (go 1.26.3)
```bash
cd go
go run ./cmd/cycle                           # цикл собран: reclaimed ~32 МБ / 400 001 объект
go build -gcflags='-m' ./...                 # escape analysis: stack vs moved to heap
go test -bench=. -benchmem -run='^$' ./...   # allocs/op: 1 без пула → 0 с sync.Pool
GODEBUG=gctrace=1 go run ./cmd/gcpauses      # паузы STW (один прогон)
```

### Java (JDK 21, Maven, JOL)
На обычной машине (JDK 21 + Maven в PATH, доступный `~/.m2`) достаточно:
```bash
cd java && bash build.sh && bash run.sh      # Опора 1 (Cleaner), JOL-раскладка, GC-логи G1/ZGC
```
Скрипты берут путь из своего расположения и принимают переопределения через env.
На среде автора (WSL, `~/.m2` под root, drvfs на `/mnt/*`) нужны все три:
```bash
cd java
MAVEN_REPO="$HOME/.m2-osv" BUILD_DIR="$HOME/osvbuild/mm-java" JAVA_HOME="$HOME/jdk21" bash build.sh
MAVEN_REPO="$HOME/.m2-osv" BUILD_DIR="$HOME/osvbuild/mm-java" JAVA_HOME="$HOME/jdk21" bash run.sh
```
`BUILD_DIR` уводит сборку на нативную FS (иначе drvfs повреждает `target/*.class`),
`MAVEN_REPO` — в доступный репозиторий (штатный `~/.m2` под root недоступен). Подробности — в `java/RUN.md`.
