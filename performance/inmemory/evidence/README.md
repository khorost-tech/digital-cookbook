# evidence — сырые логи живых прогонов

Представительные логи прогонов стенда. Файлы отслеживаются git через явное
исключение в корневом `.gitignore` (общее правило `*.log` их бы съело —
именно это и произошло при первой публикации: файлы лежали на диске, но в
репозиторий не попали, и проверять надо `git ls-files`, а не `ls`).

**Зачем.** README и `FIXTURES.md` ссылаются на живые прогоны и приводят из
них числа. Без опубликованных логов эти ссылки читателю репозитория
непроверяемы.

## Чего здесь НЕТ — честно

- **Picodata** (сценарии `topology`, `sharding`, `sql`) — представительного
  лога нет. Прогоны выполнялись живьём, но их stdout не сохранялся отдельным
  файлом, а рабочий отчёт задачи в git не входит. Числа Picodata в
  `FIXTURES.md` проверяются только повторным прогоном (`compose/picodata.yml`,
  команды — в README стенда).
- **Полные серии повторов.** Там, где число дано диапазоном по N прогонам
  (stampede 129–200 по 20; точка обнаружения отказа Aerospike `ram`
  50 000–190 000 по 9; `nsup-period` 25 прогонов; медианы по 51 повтору),
  здешний **лог** подтверждает один прогон из серии, а не весь разброс.
  Исключения, где серия опубликована целиком: `redis-stampede-multi.log`
  (серия внутри одного файла), `aerospike-nsup-period-25runs.csv` (все 25
  точек) и `compute-locality-ratios.csv` (все 24 итоговых замера).
- **Абсолютные времена** в логах присутствуют как диагностика прогона и
  намеренно не публикуются в статьях как факт о системах (причина — раздел
  «Границы метода» в `FIXTURES.md`).

Полный контекст каждого числа — сколько прогонов, какой разброс, какие
оговорки — в `FIXTURES.md`, а не здесь.

## CSV: серии повторов компактно

Вместо публикации сотен килобайт stdout — три таблицы с исходными точками
серий, на которые опираются диапазоны в `FIXTURES.md`.

| Файл | Что внутри |
|---|---|
| `aerospike-nsup-period-25runs.csv` | все **25** точек эксперимента `nsup-period` (5 периодов × 5 прогонов): период, номер прогона, номер записи, на которой обнаружен отказ |
| `aerospike-nsup-period-summary.csv` | сводка по каждому периоду: n, среднее, **оба** стандартных отклонения, min/max |
| `compute-locality-ratios.csv` | все **24** замера `compute-locality` (6 прогонов × 2 системы × 2 порядка): медианы naive/local, опубликованное отношение и его пересчёт из показанных колонок |

⚠️ **Про стандартное отклонение.** В `FIXTURES.md` опубликованы
**популяционные** значения (делитель `n`): 26 259 / 20 347 / 20 339 /
32 598 / 6 950. Если пересчитать привычной выборочной формулой (`n−1`),
получатся другие числа — 29 358 / 22 748 / 22 740 / 36 446 / 7 770, — и
может показаться, что данные не сходятся. Поэтому в сводном CSV приведены
**обе** колонки: `stddev_population` и `stddev_sample`.

⚠️ **Отдельных отсчётов внутри серий по 51 повтору не существует.** Код
измеряет 51 повтор и печатает **медиану**, не сохраняя сами замеры, поэтому
`compute-locality-ratios.csv` содержит именно медианы (по одной на замер), а
не 51 сырое значение. Восстановить их постфактум нельзя — только новым
прогоном с изменённым кодом.

⚠️ **`ratio_reported` из показанных колонок точно не воспроизводится.**
Длительности в CSV округлены до трёх знаков, а отношение считалось из
неокруглённых значений: 11 строк из 24 расходятся, максимум на 0,111.
Поэтому рядом стоит `ratio_from_shown_ms` — пересчёт именно из тех чисел,
которые видит читатель. Расхождение между колонками не признак ошибки, а
эффект округления; для выводов серии оно несущественно, так как выводы
строятся на диапазонах, а не на третьем знаке.
