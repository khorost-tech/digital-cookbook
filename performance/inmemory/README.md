# Вычисления в оперативной памяти — стенды

Живые стенды к серии статей «Вычисления в оперативной памяти» на
[khorost.tech](https://khorost.tech). Серия сравнивает несколько
in-memory/near-memory систем (Redis, Tarantool, Picodata, Aerospike, Ignite,
etcd) на общем датасете и общем источнике истины — PostgreSQL 18.4. Каждый
стенд отвечает за одну технологию, отдельный `benchmark/`-стенд сводит их
вместе на одной и той же нагрузке.

**Phase 1 (живые стенды) завершена.** Шесть стендов и три сценария сводного
бенчмарка построены, отревьюированы и воспроизводятся с нуля. Единственный
источник чисел для статей Phase 2 — `FIXTURES.md`: каждое число там взято
дословно из реального прогона, с отношением/разбросом и оговоркой, откуда
оно и на скольких прогонах подтверждено. Абсолютная latency нигде не
публикуется как факт о системе (см. `FIXTURES.md`, раздел «Границы метода»).

## Куда смотреть — этот файл длинный

Он совмещает две разные задачи, и читателю обычно нужна одна из них.

**Хочу запустить стенд** — раздел «Как запускать» (общая топология и датасет)
и раздел нужного стенда, там команда воспроизведения в начале. Разделы
самодостаточны: читать подряд не требуется.

**Хочу число для статьи или ссылку на факт** — не сюда, а в `FIXTURES.md`.
Там числа собраны компактно, с разбросом и указанием, на скольких прогонах
подтверждены. README дублирует часть из них в контексте своего стенда.

**Хочу понять, почему стенд устроен именно так** — разделы стендов после
команд запуска содержат историю живой отладки: какие конфигурации сервер не
принял, какие объяснения оказались неверными и были сняты после проверки,
где ассерт проходил по случайности. Это самая объёмная часть файла, и она
намеренно сохранена: без неё следующий человек повторит те же попытки.
Отдельно то же по всей фазе — разделы «Границы метода» и «Что не
воспроизвелось» в конце.

## Цель

Каждое число в серии должно быть взято из реального прогона на этом стенде,
а не из документации вендора. Общий датасет (`dataset/`) и общий источник
истины (`compose/origin.yml`, PostgreSQL) гарантируют, что разные
технологии сравниваются на одних и тех же данных, а не на подогнанных под
каждую систему синтетических наборах.

## Датасет

`dataset/` — детерминированный генератор (`math/rand.New(rand.NewSource(seed))`,
без `time.Now()` в данных), общий для всех стендов серии.

Схема:

```sql
CREATE TABLE products (
  id BIGINT PRIMARY KEY,
  sku TEXT NOT NULL,
  title TEXT NOT NULL,
  price_cents BIGINT NOT NULL,
  attrs JSONB NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL
);
CREATE TABLE views (
  product_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  ts TIMESTAMPTZ NOT NULL
);
```

Просмотры (`views`) распределены по товарам по Зипфу (`s=1.2`) — небольшое
число товаров получает большинство просмотров, что делает кэширование
осмысленным сценарием (равномерное распределение обесценило бы весь смысл
серии: hit rate любого кэша упал бы до доли рабочего набора в объёме кэша).

Размер по умолчанию: 200 000 products, 5 000 users, 20 views/user. Подобран
так, чтобы датасет заведомо не влезал в `maxmemory` сценария 1 — фактический
размер таблицы `products` зафиксирован в `.superpowers/sdd/task-1-report.md`
и используется как база для лимита памяти в Task 8.

```bash
cd dataset
export GOPROXY=https://go.khorost.tech,direct
go mod tidy

# NDJSON в stdout (детерминированно — два запуска дают одинаковый sha256)
go run . -out ndjson

# загрузка в PostgreSQL (ORIGIN_DSN из окружения либо -dsn)
export ORIGIN_DSN='postgres://inmemory:inmemory@127.0.0.1:5433/catalog?sslmode=disable'
go run . -load
```

## Стенд 2: Redis — кэш-паттерны

`redis-cache/` — Redis перед PostgreSQL строго в роли **кэша**: cache-aside,
write-through, cache stampede, leaderboard (ZSET), HyperLogLog. Внутренности
Redis (персистентность RDB/AOF, вытеснение, event loop, single-thread,
Lua/functions, streams, кодировки структур, Cluster/Sentinel) здесь **не
изучаются** — они уже разобраны на живых цифрах в соседнем стенде
`databases/redis/deep-dive`. Персистентность в `compose/redis.yml` намеренно
выключена (`--save "" --appendonly no`) — это не упущение, а следствие
границы задачи.

Топология: `inmemory-redis` (`redis:8.8`), сеть `inmemory-net` (общая с
`inmemory-origin`), порт `6381` на хосте (не дефолтный `6379` — он занят
стендом `redis/deep-dive`).

```
REDIS_ADDR=127.0.0.1:6381
```

### Разброс: почему `stampede` — диапазон, а не одно число

Первая редакция публиковала `origin_queries=105` для сценария без защиты как
единичный точный факт. Живой прогон **20 раз подряд** на этой же машине,
той же топологии, без изменений между прогонами (`scratchout/redis-stampede.log`)
дал:

```
134, 136, 174, 176, 176, 177, 179, 179, 184, 186,
186, 187, 188, 195, 200, 200, 200, 200, 200, 200
```

Диапазон **134–200**, медиана **186**. 105 — не типичное значение, а нижний
выброс: скорее всего один из первых прогонов (после старта контейнеров,
холодный пул соединений `pgxpool`), не показательный для устойчивого
поведения. Публиковать его как «измерение» вводило бы читателя в
заблуждение о стабильности — типичное поведение здесь: **почти все 200
горутин бьют в origin одновременно**, механика подтверждается на каждом из
20 прогонов (`unprotectedQueries < 2` ни разу не сработал).

**Отдельная находка: `с защитой` не было стабильно равно 1.** Проверка по
инструкции («если хоть раз не 1 — доложить») вскрыла настоящую гонку в
`getOrLoadProtected` (`redis-cache/main.go`), не связанную с 4-секундным
`deadline` фолбэка (полный прогон сценария укладывается в *доли секунды* —
таймаут физически не мог сработать). Живым прогоном с отладочными логами
подтверждено: после того как первый победитель гонки за `SETNX`-лок
завершает запрос в PG, заполняет кэш и снимает лок (`defer rdb.Del`),
"опоздавшая" горутина — которая успела сделать свой начальный `GET` (увидела
промах) ДО того, как победитель заполнил кэш, но добралась до `SetNX` ПОСЛЕ
того, как лок уже освободился, — получает `ok=true` на уже бесполезный лок и
уходит в PG повторно. Это классическая TOCTOU-гонка check-then-act между
начальным `Get` и `SetNX`. На 12 прогонах до исправления это давало
`origin_queries=2` в 6 из 12 (50%), один раз — `3` (три «победителя» подряд).

**Исправлено** двойной проверкой кэша сразу после получения лока (до похода
в PG) — если кэш уже заполнен настоящим победителем, «опоздавшая» горутина
возвращается без повторного запроса. После исправления: **20 из 20 прогонов
дали `origin_queries=1`** (`scratchout/redis-stampede.log`), гонка больше не
воспроизводится. Ассерт `protectedQueries != 1 → fatal` в исходном коде был

## Стенд 3: Tarantool — spaces и хранимки

`tarantool/` — Tarantool как in-memory СУБД: spaces с первичным и вторичным
индексами, хранимка на Lua, выполняемая рядом с данными, и сравнение
движков `memtx`/`vinyl`. Топология: `inmemory-tarantool`
(`tarantool/tarantool:3.8.0`), сеть `inmemory-net`, порт `3301`.

```
TARANTOOL_ADDR=127.0.0.1:3301
```

Схема (`tarantool/init.lua`) зеркалит PostgreSQL: space `products` (id, sku,
title, price_cents, category, views — категория и число просмотров
денормализованы прямо в кортеж, views агрегируется на стороне Go при
загрузке из `views`), первичный индекс по `id`, вторичный неуникальный по
`(category, views)`.

**Контракт для Task 9.** Хранимка `top_products_by_category(category, limit)`
возвращает топ товаров категории по просмотрам, выполняясь на сервере — по
сети уезжает только результат (`limit` кортежей), а не вся категория. Она
фиксирована здесь дословно и **сравнивается с вычиткой всей категории в приложение** в
сценарии 2 бенчмарка (Task 9, ещё не сделан) — менять сигнатуру или
семантику нельзя без пересмотра той задачи.

**Отклонение от дословного brief-кода (заведомо и обоснованно):**
1. `compose/tarantool.yml`: путь тома `./tarantool/init.lua` в брифе
   резолвится Docker Compose относительно каталога **compose-файла**, а не
   каталога запуска (`docker compose -f compose/tarantool.yml config`
   показал `.../compose/tarantool/init.lua` — файла там нет). Исправлено на
   `../tarantool/init.lua`.
2. Healthcheck-тест `... :ping() or os.exit(1)` — невалидный Lua:
   `expr or expr` не может быть statement (только присваивание или вызов
   функции), LuaJIT падает `unexpected symbol near 'or'` (живой прогон,
   `docker inspect` health-лог). Исправлено на
   `local ok = ...:ping(); os.exit(ok and 0 or 1)`.
3. `init.lua`: пользователю `app` добавлен грант `create,drop,alter` на
   `universe` (сверх `read,write,execute` из брифа) — без него сценарий
   `memtx-vinyl` падает `AccessDeniedError` при попытке создать сравнительные
   space на лету (живой прогон). Контрактные функции (`top_products_by_category`,
   `bump_views`) и схема `products` не тронуты.

**Особенность образа:** `TT_APP_NAME`/`TT_INSTANCE_NAME` заданы как ENV в
самом образе `tarantool/tarantool:3.8.0`, поэтому одноразовые
`tarantool -e "..."` (в т.ч. через `docker exec`) после выполнения скрипта
пытаются самостоятельно забутстрапиться как декларативный instance и падают
с `Startup failure: No cluster config received...` — вывод скрипта (то, что
успело напечататься) при этом корректен, но код возврата ненулевой. Обходится
явным `os.exit(0)` в конце одноразового скрипта; на здоровье самого сервера
(запущен как `tarantool /opt/tarantool/init.lua`, не через `-e`) это не
влияет — `box.cfg{}` отрабатывает как в 2.x, декларативный конфиг не
требуется.

Три сценария (`-scenario=...`), общий датасет с `spaces`/`storedproc`
(products=200 000 из PG, views агрегированы):

**Почему RAM vinyl мерена ДО `box.snapshot()`, а диск — ПОСЛЕ.** Только что
записанные кортежи в vinyl сначала лежат в памяти (L0-буфер), и движок
сбрасывает их на диск сам по порогу `vinyl_memory`/по таймеру, а не сразу
после записи. Дамп до/после сам по себе — фактическая демонстрация трейда
RAM↔диск, поданная как **три подписанные фазы**, а не как одна цифра:

1. **Пик RAM сразу после записи** (`tuple`+`level0`+служебные структуры, ДО
   `box.snapshot()`) — 21.58–21.65 МБ, сопоставимо с memtx (**ratio
   0.699–0.701**), но временно: в проде дамп случится по
   `vinyl_memory`/`checkpoint_interval` и это состояние не держится вечно.
2. **Устойчивое RAM после дампа** (ПОСЛЕ `box.snapshot()`) — `tuple` и
   `level0` уходят в 0 (L0-буфер сброшен), но `page_index`+`bloom_filter` —
   служебные структуры на смонтированные с диска run'ы — остаются
   **резидентными в RAM постоянно**: 288 359 байт (0.28 МБ), НЕ ноль.
   **Это заголовочное число серии**: vinyl держит тот же датасет в RAM в
   **55.0 раза меньше**, чем memtx (15.13 МБ). Прежняя версия стенда
   считала здесь только `tuple+level0` и получала 0 — фактически неверно
   (живой прогон продампленного `products_vinyl` снял ненулевые
   `page_index`/`bloom_filter` через `box.stat.vinyl().memory`), и это
   контринтуитивное "vinyl держит RAM больше memtx" было артефактом
   переходной фазы, а не честным сравнением.
3. **Диск после дампа** — 15.63 МБ (`disk.data`+`disk.index`) постоянно; у
   memtx между checkpoint'ами на диске в норме 0 байт.

Оба отношения (пик и устойчивое) считаются по одной и той же метрике memtx
(`items_used` delta) — без примеси более рыхлого `arena_used`, который
раньше давал второе, асимметричное отношение (0.882) к тому же "урезанному"
знаменателю vinyl. `arena_used` delta по-прежнему печатается в логе сценария
для справки, но не участвует в ratio.

**Почему числа теперь воспроизводимы (находка ревью, было DONE_WITH_CONCERNS
→ исправлено).** Первая версия сценария дропала и пересоздавала
`products_memtx`/`products_vinyl` перед каждым замером для идемпотентности
повторного прогона — но memtx освобождает память дропнутого space
**асинхронно**, фоновой GC-фиброй тюплов, а не в момент вызова `drop()`.
Живой прогон (`docker exec`, `net.box`, опрос `box.slab.info().items_used`
каждые 100мс сразу после `drop()`) показал: значение падает лишь частично
сразу после `drop()` и полностью стабилизируется уже к первому опросу
(~100мс), но **не мгновенно** — без ожидания повторный прогон сценария на
одном и том же инстансе мерил дельту "от ещё не освободившегося" baseline
и **молча занижал её**: 4 прогона подряд без ожидания дали `ratio 0.700 →
0.153 → 0.135 → 0.097` (числитель падал 15.86 → 3.45 → 3.06 → 2.20 МБ,
знаменатель vinyl стабилен). Это тот же класс дефекта, что гонка в Task 2 —
число верно в одном частном случае и рассыпается за его пределами, а скрипт
печатал `OK`, потому что ассерты проверяли только структуру (`len==200000`,
`disk>0`), не стабильность величины.

**Выбор фикса.** Рассматривались три варианта: (а) пересоздавать контейнер
перед каждым замером — надёжно, но тяжело и не объясняет механизм; (б)
мерить только один движок за прогон на чистом инстансе — устраняет
взаимное влияние, но требует двух отдельных прогонов и не даёт сравнить
memtx/vinyl в одном контексте; (в) **дождаться, пока `box.slab.info()`
устоится после `drop()`, прежде чем мерить baseline** — устраняет причину
дефекта напрямую (асинхронность GC-фибры), не требует пересоздания
контейнера и работает даже при повторных запусках подряд. Выбран вариант
(в): `waitMemtxSlabSettled` (`tarantool/main.go`) опрашивает `items_used`
каждые 100мс, считает состояние устоявшимся при 3 одинаковых показаниях
подряд (300мс), с budget 5с и явным предупреждением в выводе, если
устояться не удалось. **Проверено 12 прогонами подряд на одном и том же,
НЕ пересозданном контейнере**: `items_used` delta — **identично
15 861 160 байт во всех 12 прогонах**, `ratio_peak` — диапазон 0.699–0.701,
`ratio_steady` — 55.0× во всех 12. Полные числа — `.superpowers/sdd/task-3-report.md`,
раздел «Фиксы по ревью».

**Почему без раунда репитов для `spaces`/`storedproc`.** Оба сценария
выполняются строго последовательно одним клиентским процессом без горутин
пользовательского кода и без зависимости от таймингов — единственная
асинхронность в стенде (`loadIntoSpace`, конвейеризация `Do()`/`Get()`
пачками по 2000 запросов поверх одного TCP-соединения) не влияет на итоговый
результат: `REPLACE` идемпотентен и не зависит от порядка доставки ответов
сервера. `memtx-vinyl` — исключение (см. выше): единственный сценарий стенда
с реальной асинхронностью на стороне сервера (фоновая GC-фибра memtx),
поэтому именно для него сделан явный wait-for-settle и 12-кратная проверка
вместо "без раунда репитов".

Полные логи каждого сценария — `scratchout/tarantool-*.log` (в
`.gitignore`, не коммитятся) и сведены в `.superpowers/sdd/task-3-report.md`.

## Стенд 4: Picodata — кластер, Raft, шардирование

`picodata/` — Picodata как распределённая СУБД поверх Tarantool: живой
многоинстансный кластер, Raft-топология (governance-raft всего кластера,
отдельно от per-репликасет vshard-мастера), шардированная таблица через
распределённый SQL и распределённая агрегация со сверкой с источником
истины. **Это самая рискованная задача серии** (см. предупреждение в
`.superpowers/sdd/task-4-brief.md`) — Picodata не публикует релизов на
GitHub, образ только в собственном реестре, CLI-флаги брифа были написаны по
документации, не по факту образа. Итог: кластер **воспроизвёлся**, но с
существенными отклонениями от брифа на каждом шаге — все зафиксированы ниже.

Топология (`compose/picodata.yml`): 4 инстанса (не 3, см. «Отклонение 3»
ниже), сеть `inmemory-net`, порты с хоста — только у `picodata-1`
(`3401:3301` iproto, `5441:5432` PG-протокол); `picodata-2/3/4` доступны
только изнутри сети (используются через `docker exec`, см. ниже).

```
PICODATA_ADDR=127.0.0.1:5441
```

**Отклонение от брифа (значение по умолчанию):** интерфейс брифа задавал
`PICODATA_ADDR=127.0.0.1:3401` — это iproto-порт, не PG-wire. Сценарии
ходят в Picodata через `pgx` (SQL по PG-протоколу, не iproto), поэтому
дефолт исправлен на PG-порт `5441` (`picodata-1`: `pg-listen 0.0.0.0:5432`
→ хост `5441`). Имя переменной сохранено, значение — нет; переопределяется
как обычно через `-picodata-addr`/`PICODATA_ADDR`, если понадобится другой
адрес.

### Отклонения от брифа (все — по факту живого прогона)

**1. CLI-флаги `picodata run` не совпадают с брифом.** `picodata run --help`
фактического образа не знает `--data-dir`, `--listen`, `--advertise`,
повторяемый `--peer`. Реальные имена: `--instance-dir`, `--iproto-listen`,
`--iproto-advertise`, `--peer` (один флаг, comma-separated список, по
умолчанию равен `--iproto-advertise` — совпадающего с брифом достаточно
только для однонодового бутстрапа). `--pg-listen` в брифе совпал с образом
(единственное совпадение). Также entrypoint образа — уже `/usr/bin/picodata`
(`docker inspect .Config.Entrypoint`), поэтому команда в `command:`
начинается с `run`, а не с `picodata run`.

**2. Аутентификация: PG-протокол и iproto используют РАЗНЫЕ и
ВЗАИМОИСКЛЮЧАЮЩИЕ методы на одного пользователя.** Дефолтный `admin` создан
с `auth=["md5",""]` (пустой пароль). `ALTER USER "admin" WITH PASSWORD '...'`
без явного `USING <method>` переписывает auth на `md5` — годится для
PG-протокола (что и нужно сценариям), но **ломает** iproto/`net.box` CALL
(iproto ожидает `chap-sha1`). Explicit `USING chap-sha1` — обратная ситуация:
чинит iproto, ломает PG-протокол. Picodata хранит **один** auth-метод на
пользователя, не оба одновременно (проверено живьём в обе стороны). Итог:
`admin` держится на `md5` (PG-протокол — основной канал сценариев),
raft-статус (нужен только на чтение) снимается ЧЕРЕЗ ДРУГОЙ КАНАЛ (см.
ниже), не через iproto CALL — так необходимость второго auth-метода отпала.
Bootstrap-шаг (обязателен после каждого `up -d` с нуля, `admin.sock` не
требует пароля — доверенный локальный канал):

```bash
docker exec -i picodata-1 picodata admin /var/lib/picodata/admin.sock <<'EOF'
\sql
ALTER USER "admin" WITH PASSWORD 'CookbookPass123!' USING md5;
EOF
```

**3. Raft-лидер (`pico.raft_status()`) НЕ виден через SQL/PG-протокол —
структурно, не по недосмотру.** Проверено исчерпывающе: `"_pico_instance"`
не содержит leader-флага; `"_pico_replicaset"."current_master_name"` —
**другое** понятие (мастер РЕПЛИКАСЕТА для vshard-записи, per-shard, не
governance-raft всего кластера); box-уровневая `_raft_state` существует, но
НЕ экспортирована в sbroad SQL (`select * from "_raft_state"` — "table not
found"); iproto CALL к `pico.raft_status` с грантами упёрся в непокрытую
документацией комбинацию привилегий (`GRANT EXECUTE ON PROCEDURE` не
распространяется на встроенные `pico.*` Lua-функции, `Execute access...
denied` для свежесозданного пользователя без ясного способа выдать доступ).
Решение: raft-статус снимается **тем же каналом, что и Step 3 самого брифа**
— `docker exec <container> picodata admin <sock>` с `\lua
pico.raft_status()`, разбор YAML-ответа регулярками (`picodata/main.go`,
`probeContainer`). Это не выдумывание — тот же admin-console канал, которым
брифом верифицируется топология, просто используется и из Go-кода, а не
только вручную.

**4. Три инстанса при `--init-replication-factor 2` СТРУКТУРНО не дают
шардирования — понадобился четвёртый инстанс.** Брифовая топология (3
инстанса, RF=2) на практике даёт ОДИН полный репликасет (2 члена, `weight=1`,
`state=ready`) и ОДИН «хвостовой» из 1 члена (`weight=0`,
`state=not-ready`), который vshard **навсегда** исключает из распределения
бакетов — это не задержка ребалансировки, и это не сюрприз конкретно версии
26.1.6: репликасет получает бакеты только по достижении заданного фактора
репликации — прямое следствие механики vshard, задокументированной и
используемой в Picodata с версии 22.11.0. Арифметика предсказуема заранее
(3 не делится на RF=2 без остатка), поэтому ниже это подано как
**подтверждено живым экспериментом**, а не как неожиданное открытие —
ценность в том, что кластер молча рапортует «сбалансирован», имея половину
мощности в нуле, а не в самом факте нехватки инстансов.

**Атрибуция лога подтверждения — уточнена по независимому ревью и
перепроверена живьём (дважды: на исходном кластере и на пересозданном с
нуля).** Строку `"The cluster is balanced ok. Schedule next rebalancing
after 3600.000000 seconds"` печатает не `governor_loop`, а модуль
`vshard.rebalancer`/`vshard.storage` (видно по тегу в самой строке лога), и
печатает её узел, который на момент проверки держит роль vshard-мастера
соответствующего репликасета (`current_master_name` в `"_pico_replicaset"`)
— эта роль НЕ закреплена за `picodata-1`: на пересозданном с нуля кластере
она доставалась разным контейнерам. Проверочная команда (не полагаться на
конкретное имя контейнера):

```bash
for c in picodata-1 picodata-2 picodata-3 picodata-4; do
  echo "== $c =="; docker logs "$c" 2>&1 | grep "balanced ok"
done
```

И `"_pico_replicaset"` показывает `default_2 weight=0/not-ready` неизменно
(перепроверено с разрывом в минуты, не секунды). Первый прогон `sharding` с
3 инстансами дал `usedReplicasets=1` — ассерт `usedReplicasets < 2 → fatal`
сработал корректно, поймав ровно то, для чего он написан. Добавлен
`picodata-4` (`compose/picodata.yml`) — достраивает второй репликасет до
RF=2, после чего `_pico_replicaset` показывает ОБА репликасета
`weight=1/ready` сразу после бутстрапа. Проверено на **полностью
пересозданном с нуля** кластере (`down -v` → `up -d`) — воспроизводится
идентично. Ассерт `topology` (3 инстанса) обновлён на 4 — суть проверки
(«кластер собрался целиком») та же.

**5. `sql_vdbe_opcode_max` (дефолт 45000) слишком мал для распределённой
агрегации на этом объёме — найдено живым прогоном, не в брифе.**
`SELECT category, count(*) FROM products GROUP BY category` на полном
датасете (200 000 строк, 2 репликасета) падает:
`"Reached a limit on max executed vdbe opcodes. Limit: 45000"`.

**Причина — установлена ЧАСТИЧНО (по независимому ревью; более ранняя
версия этого раздела объясняла падение «полным сканом без индекса по
category» — опровергнуто живьём и убрано).** Доказана корреляция: порог
зависит от числа строк, попадающих в GROUP BY, а не от размера таблицы.
Конкретный VDBE-механизм не детализирован: `EXPLAIN` даёт текстуально
идентичный план для проходящего и падающего вариантов, профилировщика
опкодов нет — дальше «что видно» инструментами мы не продвинулись. Бисекция по числу строк,
реально попадающих в GROUP BY (`WHERE id < N`, без индекса на `category`,
дефолтный лимит 45000): `id < 6500` — проходит, `id < 7000` — падает; оба
исхода воспроизведены дважды подряд, детерминированно. Порог не зависит от
размера таблицы (200 000 строк) — только от числа строк, которые реально
агрегируются: похоже на по-строчную стоимость VDBE при локальной
группировке на каждом репликасете и последующем merge-motion между ними, а
не на характер скана (`SELECT count(*)` без `GROUP BY` по всем 200 000
строкам на том же лимите 45000 проходит без проблем — падает именно
`GROUP BY`, а не сам факт полного скана).

`CREATE INDEX ON products(category)` **не помогает и не годится как фикс —
проверено живьём** (то же самое независимо установил ревьюер): с индексом
тот же запрос падает уже на 9 строках (`WHERE id < 10`, лимит 45000), тогда
как БЕЗ индекса те же 9 строк проходят. Индекс здесь не снижает стоимость
`GROUP BY`, а увеличивает её — «добавьте индекс» не решает эту ошибку.

Бисекция итогового лимита (полный датасет, 200 000 строк): 45000 и 500000 —
падают, 1000000 — падает, 2000000 — проходит. Выставлено 5000000 (запас
2.5× над найденным порогом, не впритык). `ALTER SYSTEM SET
sql_vdbe_opcode_max = ...` работает и через PG-протокол (не только через
admin-консоль) — сценарии `sharding`/`sql` делают это сами
(`raiseVDBEOpcodeLimit`, идемпотентно, кластерная персистентная настройка),
отдельного ручного шага не требуется.

### Три сценария (`-scenario=...`)

| Утверждение | Сценарий | Фактическое число (живой прогон) | Ассерт |
|---|---|---|---|
| Кластер собрался целиком | `topology` | `"_pico_instance"`: 4 инстанса (2 репликасета × 2) | `len(instances) != 4` → fatal |
| Ровно один Raft-лидер, все инстансы согласны | `topology` | `pico.raft_status()` на всех 4 контейнерах: `leader_id` совпадает на всех, `raft_state=Leader` ровно у одного | расхождение `leader_id` ИЛИ `leaders != 1` → fatal |
| Данные шардированы (легли на ≥2 репликасета) | `sharding` | `default_1=99776`, `default_2=100224` (сумма 200000, совпадает с PG) — идентично на 10 повторных прогонах на одном кластере (проверяет идемпотентность перезаливки, не разброс — см. ниже) и на 2 независимых пересозданиях кластера с нуля | `usedReplicasets < 2` → fatal |
| Распределённая агрегация совпадает с источником | `sql` | picodata == PG по всем 6 категориям (`auto=33239, books=33550, garden=33495, kitchen=32944, sport=33496, tools=33276`) — **стабильно во всех 10 прогонах** | `!reflect.DeepEqual(picoAgg, pgAgg)` → fatal |

**Перекос по репликасетам — честное наблюдение, не подгонка.** 99776 против
100224 (разница 0.22% от 200000) — это разброс consistent-hashing по 3000
бакетам между 2 репликасетами на этом конкретном датасете (`id` 1..200000),
не намеренная демонстрация неравномерности. Оба зеркала внутри каждого
репликасета совпадают друг с другом побайтово по числу кортежей
(`box.space.products:len()` идентичен на обоих членах пары) — репликация
работает корректно.

**Почему «10 прогонов подряд» — не проверка разброса.** `CREATE TABLE ...
DISTRIBUTED BY (id)` считает `bucket_id` детерминированной хеш-функцией от
`id`; при одном и том же датасете и одном и том же назначении бакетов на
репликасеты распределение обязано совпасть на каждом прогоне — это
гарантия конструкции, а не результат измерения. 10 прогонов подряд на одном
и том же кластере (полная передрузка: `DROP TABLE IF EXISTS` + повторный
`INSERT`) проверяют идемпотентность перезаливки, а не разброс — они и не
могли дать другое число. Содержательное подтверждение —
**три независимых пересоздания кластера с нуля** (`down -v` → `up -d`):
порядок присоединения `picodata-2/3/4` друг к другу не гарантирован
(одновременный `depends_on: [picodata-1]`), и тем не менее итоговое
распределение бакетов между `default_1`/`default_2` совпало в обоих
случаях — `99776`/`100224`.

### Raft-failover — реальная демонстрация, не только статический снимок

Кто именно становится лидером — величина случайная в теории Raft, но
**в ЭТОЙ топологии** (compose `depends_on: [picodata-1]` у нод 2–4)
лидером на свежем бутстрапе **всегда** оказывается `picodata-1`
(`default_1_1`) — воспроизведено на 2 независимых пересозданиях кластера с
нуля. Причина не случайность выборов, а порядок старта: `picodata-1`
поднимается и самобутстрапится (никого не ждёт — единственный, кто НЕ
указывает `depends_on`) РАНЬШЕ, чем 2/3/4 успевают присоединиться, и
побеждает без реальной конкуренции за голоса. Это честный вывод из
эксперимента, а не предположение.

Чтобы увидеть **настоящую** смену лидера (не гипотетическую), лидер был
принудительно остановлен вживую:

```
docker stop picodata-1
# ждём переизбрания (~8с)
docker exec picodata-2 picodata admin /var/lib/picodata/admin.sock <<< $'\\lua\npico.raft_status()'
# leader_id=2 (default_1_2, был на picodata-3), raft_state=Leader, term вырос 2 → 3
docker start picodata-1
# picodata-1 переприсоединяется как Follower, term остаётся 3, лидер НЕ возвращается на picodata-1 автоматически
```

Результат: term вырос с 2 до 3, новый лидер — инстанс `default_1_2` (был на
контейнере `picodata-3` на тот момент), все 3 оставшихся инстанса были
согласны в момент отказа, `picodata-1` после рестарта вернулся Follower'ом
(лидерство НЕ переходит обратно автоматически — типичное поведение Raft,
новый лидер держит позицию, пока сам не откажет). Прогон `-scenario
topology` СРАЗУ ПОСЛЕ failover корректно обнаружил нового лидера без единой
жёстко закодированной идентичности — код опрашивает всех и берёт
`raft_state=Leader` откуда бы он ни пришёл.

## Стенд 5: Aerospike — гибрид RAM/flash

`aerospike/` — Aerospike Community Edition, один сервер, **два namespace**
на одном instance: `ram` (`storage-engine memory` — и индекс, и данные в
оперативной памяти) и `flash` (`storage-engine device` — данные на
файле-устройстве). Первичный индекс в Aerospike **всегда** резидентен в
RAM независимо от storage-engine — это архитектурное свойство сервера, не
опция конфига. Namespace `flash` демонстрирует именно эту гибридную модель
и остаётся героем Task 8 (сценарий «рабочий набор за границей RAM»).

```
AEROSPIKE_ADDR=127.0.0.1:3000
```

Конфиг (`aerospike/aerospike.conf`) собран не с нуля, а правкой фактического
дефолтного конфига образа (`docker run --rm aerospike/aerospike-server:8.1.2.3
cat /etc/aerospike/aerospike.conf`) — единственный дефолтный namespace `test`
заменён на `ram`/`flash`, остальные секции (`service`/`logging`/`network`)
оставлены как есть.

### Отклонения от брифа

**1. Путь монтирования конфига.** Брифовый `volumes:
./aerospike/aerospike.conf:/etc/aerospike/aerospike.conf:ro` не работает на
этом образе: `entrypoint.sh` при каждом старте рендерит
`/etc/aerospike/aerospike.template.conf` **поверх**
`/etc/aerospike/aerospike.conf` (envsubst-подобный шаблон, `bash_eval_template`)
и падает с `Read-only file system`, если целевой файл смонтирован `:ro`.
Живой прогон подтвердил ошибку дословно:

```
/entrypoint.sh: line 30: /etc/aerospike/aerospike.conf: Read-only file system
```

Исправление — монтировать готовый конфиг **на место шаблона**
(`/etc/aerospike/aerospike.template.conf:ro`), а не итогового файла; рендер
копирует его как есть (в конфиге нет `$(...)`/плейсхолдеров, которые
шаблонизатор мог бы подставить) в штатный путь. Также относительный путь
брифа (`./aerospike/...`) в `compose/aerospike.yml` разрешался бы от каталога
`compose/`, а не `performance/inmemory/` — исправлено на `../aerospike/...`
(та же схема, что и в `compose/tarantool.yml`).

**2. Имена полей info-протокола.** Бриф ожидал `asinfo`-поля
`memory_used_bytes` и `device_used_bytes`. Живой прогон `asinfo -v
"namespace/ram"` / `"namespace/flash"` на 8.1.2.3 показал, что таких полей
**нет** (сверено полным дампом ~450 полей на namespace, `grep -iE
"used|bytes"` — ничего с этими именами). Вместо них сервер 8.1.2.3 отдаёт:

- `index_used_bytes` — RAM, занятая первичным индексом. Есть у **обоих**
  namespace, включая `ram` — индекс учитывается отдельно от данных, даже
  когда `storage-engine=memory`;
- `data_used_bytes` — данные: для `ram` это данные **в памяти**
  (`storage-engine memory`), для `flash` — данные **на устройстве**
  (файл `flash.dat`).

Пересчёт публикуемых величин брифа на фактические поля:

- `ram` memory_used_bytes = `index_used_bytes + data_used_bytes` (оба
  резидентны в RAM у `storage-engine memory`);
- `flash` memory_used_bytes = `index_used_bytes` (единственное, что осталось
  в RAM у `storage-engine device` — и есть «цена индекса», ключевое число
  серии);
- `flash` device_used_bytes = `data_used_bytes` (данные физически на файле
  `/opt/aerospike/data/flash.dat`).

### Три сценария (`-scenario=...`)

**`namespaces`** — заливает полный датасет (200 000 products) в `ram` и
`flash` (`truncate` + ожидание `objects==0` перед заливкой, для
идемпотентности повторного прогона), затем снимает статистику обоих
namespace **после ожидания стабилизации** (см. ниже). Фактические числа
живого прогона:

```
ram   objects=200000 index_used_bytes=12800000 data_used_bytes=28798000 => memory_used_bytes(RAM)=41598000
flash objects=200000 index_used_bytes=12800000 data_used_bytes=28798000 => memory_used_bytes(RAM)=12800000 device_used_bytes=28798000
```

Индекс в `flash` стоит **12 800 000 байт RAM** против **41 598 000 байт**
для полного хранения того же набора в `ram` — **30,8 %** (индекс экономит
69,2 % RAM относительно полного in-memory хранения). Ассерты: число объектов
в `ram` и `flash` совпадает; `flash` memory_used_bytes строго меньше `ram`
memory_used_bytes.

**`hybrid`** — читает 1000 случайных ключей (seed фиксирован, `rand.Perm`)
из `flash` и сверяет с PostgreSQL (источник истины). Если `flash` ещё не
залит (объектов не столько же, сколько строк в PG) — сценарий заливает его
сам, что делает `hybrid` запускаемым независимо от `namespaces`. Результат
живого прогона: **0 расхождений из 1000** — `flash`-namespace читается
корректно, это не деградация хранения.

**`index-cost`** — растущий набор (10k/50k/100k/200k) заливается в `flash`
(namespace предварительно truncate’ится для чистого роста от нуля), на
каждом шаге снимается `index_used_bytes`:

```
  записей | index_used_bytes(RAM) | байт/запись (накопл.) | Δзаписей | Δbytes | байт/запись (Δ)
    10000 |         640000 |    64.00 |    10000 |     640000 |    64.00
    50000 |        3200000 |    64.00 |    40000 |    2560000 |    64.00
   100000 |        6400000 |    64.00 |    50000 |    3200000 |    64.00
   200000 |       12800000 |    64.00 |   100000 |    6400000 |    64.00
```

**Публикуемое: 64,00 байта RAM на запись**, идеально линейно на всех
четырёх шагах и во всех прогонах (см. ниже). Линейность здесь обязана быть
идеальной: Aerospike официально документирует фиксированный оверхед
первичного индекса — 64 байта метаданных на запись (digest 20 байт +
generation + void-time + last-update-time + состояние репликации + указатель
на данные), см. [Primary Index](https://aerospike.com/docs/server/architecture/primary-index)
и [Record Sizing](https://aerospike.com/docs/develop/data-modeling/record-sizing/).
Живое измерение этого стенда **подтверждает величину и линейность по числу
записей**: воспроизведено на нашем датасете на всех четырёх контрольных
точках без единого отклонения. ⚠️ **Независимость от размера bin’ов стенд НЕ
проверял** — четыре точки варьируют только количество записей, размер и
содержимое бинов при этом не менялись; независимость от размера bin’ов
(`sku`/`title`/`price_cents`/`category` разного размера дают тот же
64-байтовый прирост индекса на запись — ожидаемо, поскольку в индексе нет
самих данных). Это число определяет, сколько записей влезет в заданный
объём RAM у `flash`-namespace.

### Стабилизация метрик (проверено, не предположено)

Task 3 этой же серии (Tarantool, `memtx-vinyl`) научил: `ratio` там не
воспроизводился между прогонами (0.700 → 0.102) из-за асинхронного
освобождения памяти дропнутого space. По этому же поводу для Aerospike
добавлен `stabilizeStats` — опрос `namespace/<ns>` повторяется, пока два
последовательных снимка (objects/index_used_bytes/data_used_bytes) не
совпадут; иначе печатается явное предупреждение вместо тихого принятия
последнего значения. **Фактически** во всех прогонах (см. ниже, 12 на
сценарий) стабилизация занимала ровно 2 опроса (600 мс) — Aerospike
обновляет namespace-статистику синхронно относительно завершения записи в
рамках этого стенда, задержка на грани шума опроса не наблюдалась ни разу.

### Разброс: 12 прогонов на сценарий

Все три сценария прогнаны по **12 раз подряд** без пересоздания контейнера
(`scratchout/aerospike-{namespaces,hybrid,index-cost}-run{1..12}.log`, в
`.gitignore`, не коммитятся):

| Сценарий | Публикуемое число | Разброс по 12 прогонам |
|---|---|---|
| `namespaces` | flash 12 800 000 / ram 41 598 000 байт (30,8 %) | **идентично во всех 12** (`objects`/`index_used_bytes`/`data_used_bytes` побитово одинаковы) |
| `hybrid` | 0 расхождений из 1000 ключей | **0/1000 во всех 12** (12 000 сверок с PG суммарно) |
| `index-cost` | 64,00 байт/запись | **идентично во всех 12**, на всех 4 шагах (10k/50k/100k/200k) |

Разброса нет — что ожидаемо по конструкции: `index_used_bytes` определяется
числом объектов (fixed-size запись индекса), не содержимым bin’ов и не
активностью GC/дефрагментации на этом объёме данных (fresh-заливка на
чистый namespace, без TTL/eviction — `evicted=0` во всех логах сервера за
всю сессию). Один из 12 прогонов `index-cost` (run 4) в первой попытке был
оборван на середине не самим стендом, а внешним ограничением по времени
инструмента оркестрации — перезапущен, результат идентичен остальным 11.

## Стенд 6: Apache Ignite — data grid + compute grid

`ignite/` — единственный Java-стенд серии (остальные на Go), два узла
(`ignite-1`/`ignite-2`, `compose/ignite.yml`), образ `apacheignite/ignite:2.18.0`,

Ветка **2.x** выбрана намеренно: статья про зрелую модель collocated compute

**3.x существует** (полностью переписанное ядро, несовместимый API), но не
строится в этом стенде — не тот материал для статьи о зрелой 2.x-модели.

```
ORIGIN_DSN=postgres://inmemory:inmemory@inmemory-origin:5432/catalog?sslmode=disable  # внутри inmemory-net
```

Фактическая версия сервера (сверено живьём, лог `ignite-1`):

### Дискавери: мультикаст оказался рабочим, но стенд всё равно на статике

Дефолтный discovery образа — мультикаст (`TcpDiscoveryMulticastIpFinder`,
пустой `IgniteConfiguration` в штатном `default-config.xml` образа). Прежде
чем чинить, проверили дословно: два контейнера без какого-либо
кастомного конфига, на одной `inmemory-net`, действительно нашли друг
друга сами — `servers=2` на обоих с первого поднятия (Docker Desktop на
Windows, bridge-сеть). Это не гарантия для любого окружения: поведение
мультикаста в контейнерных сетях зависит от бэкенда (Linux bridge,
overlay, разные k8s CNI) и часто недоступно там, где Docker Desktop его
пропускает. Стенд **не полагается** на этот факт: рабочий конфиг —
статический `TcpDiscoveryVmIpFinder` (`ignite/config/default-config.xml`,
смонтирован в `$IGNITE_HOME/config/default-config.xml` обоих узлов) со
списком адресов `ignite-1:47500..47509` / `ignite-2:47500..47509` по
именам docker-сервисов. Живой прогон с этим конфигом:

```
[GridDiscoveryManager] Topology snapshot [ver=2, locNode=..., servers=2, clients=0, ...]
```

на **обоих** узлах — воспроизведено на полностью пересозданном с нуля
кластере (`down` → `up -d`, см. «Разброс» ниже).

### Отклонения от плана (все — по факту живого прогона)

**1. Тонкий клиент не имеет Affinity API и affinity-aware compute.**
Бриф предполагал `Ignition.startClient` (тонкий клиент) для всех трёх
сценариев. Сверка по фактическому `ignite-core-2.18.0.jar` (`javap`)
показала: `org.apache.ignite.client.IgniteClient` не имеет метода
`affinity(...)` вообще, а `ClientCompute` (`IgniteClient.compute()`) имеет
только `execute(taskName, arg)` — без affinity-варианта. И `Affinity.
mapKeyToNode`, и `IgniteCompute.affinityCall` — часть «толстого» API
(`org.apache.ignite.Ignite`). Поэтому `cache` использует тонкий клиент
(как в брифе), а `affinity`/`compute` — классическую клиент-ноду
(`IgniteConfiguration.setClientMode(true)`, тот же статический IP finder,
что у серверов).

**2. Peer class loading не подходит для ScanQuery-предиката.** Первая
попытка сценария `compute` — `peerClassLoadingEnabled=true` на клиенте и
серверах, P2P-деплой байткода `TopByCategoryTask`/`CategoryFilter` при
первом submit. `IgniteCompute.affinityCall` с этим прошёл, но наивный
вариант (`ScanQuery` с предикатом `CategoryFilter`) — нет: сервер падал с
`BinaryInvalidTypeException` → `ClassNotFoundException` при десериализации
запроса. Вместо отладки границ P2P-деплоя — классы стенда задеплоены на
classpath серверных нод заранее: `../ignite/target/original-ignite-stand.jar`
(тонкий jar без `ignite-core`, отдельно от шейдед `ignite-stand.jar`)
смонтирован в `$IGNITE_HOME/libs/` обоих `ignite-1`/`ignite-2`
(`compose/ignite.yml`) — путь, который Ignite сканирует автоматически при
старте JVM. `peerClassLoadingEnabled` в итоге не нужен (дефолт `false`
везде).

**3. Class file version 65 на JVM 11 — сервер убивает себя.** Самое
дорогостоящее из трёх: сборка изначально шла с `maven.compiler.release=21`
(проект пинует JDK 21 для сборки/запуска клиента). Но
`apacheignite/ignite:2.18.0` бандлит **JDK 11** внутри (`docker run --rm
apacheignite/ignite:2.18.0 java -version` → `Temurin-11.0.31+11`), а
`TopByCategoryTask`/`CategoryFilter` деплоятся НА СЕРВЕР через classpath
(отклонение 2). Class file version 65 (Java 21) на JVM 11 —
`UnsupportedClassVersionError` внутри `FailureProcessor`, и дефолтный
`StopNodeOrHaltFailureHandler` реагирует на `CRITICAL_ERROR`
**немедленным `Runtime.halt()`** — оба контейнера, `ignite-1` и `ignite-2`,
падали одновременно при первом же вызове `compute`. Фикс —
`maven.compiler.release=11` (только бинарная совместимость с JDK сервера;
JDK 21 сборки/клиента без проблем выполняет class file version 55, читать
вниз можно). Сопутствующая находка: после правки `pom.xml` `mvn package`
**без `clean`** молча оставил старый байткод (version 65) в
`target/classes` — maven-compiler-plugin сверяет мтайм `.java` файлов, а
не `pom.xml`, и не увидел повода перекомпилировать; `mvn clean package`
обязателен после смены `compiler.release`.

Пины версий образа/зависимостей из брифа (`apacheignite/ignite:2.18.0`,
`ignite-core:2.18.0`, порт `10800`) подтвердились без расхождений.

### Коллокация по категории — AffinityKey, не кастомный AffinityKeyMapper

Ключ кэша `products` — `AffinityKey<Long>(id, category)`. Ignite
распознаёт тип `AffinityKey` специально (`GridCacheDefaultAffinityKeyMapper`)
и считает партицию **по `affinityKey()` (category), а не по `key()` (id)** —
задокументированная механика ("Affinity Collocation" в доке Ignite), не
открытие этого стенда. Эффект: все товары одной категории физически лежат
на одной партиции (одном узле при `backups=1` с 2 узлами) — это и делает
`TopByCategoryTask` настоящим collocated-вычислением, а не «вызовом в
пустоту».

### Три сценария (`-scenario=...`)

**`cache`** — тонкий клиент, `PARTITIONED`-кэш `products`, `backups=1`,
заливка полного датасета (200 000 товаров) с ценами/категориями/
агрегированными просмотрами из PostgreSQL. Живой прогон:

Ассерт (размер кэша = число залитых товаров) и сверка 50 случайных ключей
с PostgreSQL проходят на каждом прогоне.

**`affinity`** — толстая клиент-нода, `ignite.affinity("products")
.mapKeyToNode(...)` для каждой из 6 категорий (взятых из фактических
данных, не хардкод) и распределение всех 200 000 ключей по узлам.
Фактический живой прогон (идентично на 10/10 прогонов, см. «Разброс»
ниже):

`tools` — ровно **33 276** товаров, как указано в брифе. Ключи легли на

ассерт `nodesUsed.size() >= 2` проходит.

Перекос 133k/66k — **не** свойство Ignite и **не** дисбаланс данных: категории
почти равны (32 944–33 550, разброс ≤2% от среднего 33 333; при идеально равных

данных. При коллокации по ключу высокой кардинальности (например, по `id`)
распределение было бы близко к 50/50.

**`compute`** — толстая клиент-нода, category=`tools` (та же проба, что и
`top_products_by_category` в `tarantool/init.lua`/`tarantool/main.go` —
Task 9 сравнивает оба стенда на одной семантике), limit=10. Два варианта:
наивный (`ScanQuery` всей категории в клиент, сортировка на клиенте) и
`TopByCategoryTask` (`compute().affinityCall("products", "tools", task)` —
задача выполняется на узле, где физически лежит партиция категории
`tools`, читает только `localEntries(CachePeekMode.PRIMARY)`). Живой
прогон:

```

```

**Главное число: 33 276 объектов по сети наивно против 10 у compute** —
в 3327,6 раза меньше. Топ-10 у обоих вариантов совпал побитово. В топе есть
ничья (id=84 и id=85, оба `views=93`) — тот же агрегированный `views`, что и в
Tarantool на этом датасете, что подтверждает: оба стенда читают одно и то же из
общего PostgreSQL. Но при `limit=10` оба члена ничьи попадают в топ **независимо**
от правила тай-брейка (следующий за ними id=105 имеет views=74) — то есть здесь
совпадение топов гарантировано конструкцией (один компаратор в обоих путях
naive/compute), а устойчивость самого тай-брейка на границе эта проба **не**
проверяет (в отличие от Tarantool `storedproc` с limit=9, где тай-брейк реально
решал состав топа). Тай-брейк здесь — DESC по
views, затем ASC по id; это **независимый** выбор от тай-брейка
`top_products_by_category` в Tarantool (там — PK DESCENDING, задокументи-
рованный артефакт её REQ-итератора по неуникальному индексу, см. Стенд 3).
Согласование семантики между Ignite и Tarantool — по-прежнему задача
Task 9, не этого стенда; здесь важно только внутреннее согласие naive vs
compute (ассерт `computeTop.equals(clientTop)`), которое проходит на
каждом прогоне.

## Стенд 7: etcd — координация, не прикладные данные

`etcd-coord/` — единственный стенд серии, который **не использует общий
датасет и не подключается к `compose/origin.yml`**. etcd в этой серии
показывается строго в роли координатора небольшого служебного состояния
(watch/lease/lock/ревизии), а не как хранилище каталога товаров — держать
там 200 000 `products` было бы демонстрацией не по назначению (etcd
официально не рекомендован как хранилище общего назначения, quota по
умолчанию 2 ГиБ). Топология: один узел `inmemory-etcd`
(`quay.io/coreos/etcd:v3.7.0`), сеть `inmemory-net`, порт `2379`.

```
ETCD_ENDPOINTS=127.0.0.1:2379
```

**Границы задачи.** Координационные примитивы: watch, lease, distributed
lock, MVCC-ревизии/компакция. Поведение etcd под несвойственной нагрузкой
(квота, отказ, восстановление) сюда сознательно не включено — это Task 10
(бенчмарк, сценарий «etcd не по назначению»), контраст показывается там.

Фактическая версия (сверено живьём):

```
API version: 3.7
```

### Разброс: `lock` — 20 прогонов, `revisions` — 3 прогона подряд

**`lock`.** Урок Task 2 этой же серии («ассерт может пройти по случайности
— гонка вскрылась только на 12 прогонах») применён напрямую: каждый вызов
`-scenario lock` внутренне прогоняет сценарий **10 раз подряд** на
отдельном ключе-префиксе (`/inmemory/lock-demo/run-NNN`, без переиспользования
состояния между прогонами), плюс отдельно проверен **вторым независимым
процессом** ещё 10 раз — итого **20/20 прогонов** дали `counter=10,
maxConcurrent=1`. Критическая секция намеренно НЕ атомарна сама по себе
(`counterVal++` без `atomic`, `time.Sleep(5ms)` внутри) — она защищена
только `concurrency.Mutex`; расширенное окно гонки специально увеличивает
шанс поймать сломанную блокировку, если бы она не держала. `maxConcurrent`
(отдельный счётчик входов в критическую секцию через `atomic`, независимый
от `counter`) — тот самый второй ассерт, который по инструкции брифа ловит
сломанную блокировку в случаях, когда `counter` мог бы случайно сойтись,
несмотря на реальную гонку.

**`revisions`.** Прогнан **3 раза подряд** без пересоздания контейнера
(`scratchout/etcd-revisions*.log`). Абсолютный размер базы «до» отличается
между прогонами (первый прогон стартовал с чистого `--data-dir`, 73728
байт; второй и третий — с уже продефрагментированной базы предыдущего
прогона, 24576 байт), но **паттерн идентичен на всех трёх**: `dbSize` не
меняется на `Compact`, падает только на `Defragment`; `dbSizeInUse` падает
сразу на `Compact`. **Размер после `Defragment` воспроизвёлся побитово**
на прогонах 2 и 3 (`dbSize=24576`, `dbSizeInUse=16384`) — это и есть
проверка «стабилизировался ли размер до снятия», которую требовал бриф
(урок Task 3: асинхронный процесс может испортить замер, если не
дождаться устоя). Замер `endpoint status` в каждой точке (`statusStable`)
опрашивается до 3 одинаковых показаний подряд (интервал 300мс, бюджет
10с) вместо однократного снятия сразу после операции — в этом стенде
устой всегда достигался за первые 1-2 опроса (`Compact`/`Defragment` в
etcd синхронны относительно ответа RPC на объёме этого стенда, задержки
на грани шума опроса не наблюдалось).

**Публикуемое число: сжатие базы после `Defragment`** — в примере прогона
897024 → 24576 байт (**-97.3%**) после 2000 перезаписей одного ключа без
компакции. Это иллюстрация «почему etcd без компакции растёт»: без
`Compact`+`Defragment` каждая перезапись ключа добавляет ревизию в MVCC-лог
и физический размер файла базы только растёт; `Compact` помечает старые
ревизии свободными (падает `dbSizeInUse`, растущий файл не уменьшается),
`Defragment` физически возвращает освобождённое место ОС (падает `dbSize`).
Порядок операций важен: `Compact` без `Defragment` НЕ уменьшает файл на
диске — это частая причина, почему администраторы, вызвавшие только
`Compact`, не видят эффекта.

Полные логи каждого сценария — `scratchout/etcd-*.log` (в `.gitignore`, не
коммитятся) и сведены в `.superpowers/sdd/task-7-report.md`.

## Стенд 8: бенчмарк — рабочий набор за границей RAM (сценарий 1)

`benchmark/` — первый сценарий сводного бенчмарка серии. В отличие от
стендов 2-7 (каждый — отдельная технология сама по себе), здесь несколько
систем нагружаются ОДНИМ и тем же растущим набором ОДНОВРЕМЕННО, при
ФИКСИРОВАННОЙ границе памяти на каждую. Вопрос не "кто быстрее" —
абсолютная latency здесь не измеряется вовсе (см. "Границы метода" ниже) —
а "что происходит, когда данные перестали помещаться": сколько записей
остаётся реально доступно, вытесняет ли система старое ради нового, или
отказывает. Три системы: Redis (`--maxmemory`+`allkeys-lru`), Aerospike
namespace `ram` (storage-engine memory — индекс и данные в RAM) и Aerospike
namespace `flash` (storage-engine device — индекс в RAM, данные на
устройстве, задокументированный факт 64,00 байт индекса/запись из Стенда 5
переиспользуется здесь дословно, не переоткрывается).

Отдельный, специфичный для Task 8 Aerospike-контейнер
(`compose/aerospike-workingset.yml`, `inmemory-aerospike-ws`, порт `3010`,
конфиг `aerospike/aerospike-workingset.conf`) — НЕ тот же, что у Стенда 5:
там лимиты намеренно большие (индекс/данные должны свободно вмещаться,
там сравнивается цена индекса), здесь — намеренно маленькие (набор обязан
упереться в границу). Redis переиспользует тот же контейнер, что и Стенд 2
(`inmemory-redis`, порт `6381`) — `maxmemory`/`maxmemory-policy`
настраиваются НА ЛЕТУ через `CONFIG SET` перед прогоном, сам
`compose/redis.yml` не меняется.

### Граница памяти: 512 МиБ — жёсткий минимум сервера, не выбор стенда

Бриф Step 1 просил границу Aerospike через `storage-engine.data-size`,
подобранную так, чтобы вмещалось ~25% датасета (34 МБ из Task 1 — граница
порядка нескольких МБ). Живой прогон это отверг: `data-size=8000000`
(8 МБ) на namespace `ram` (storage-engine memory) сервер не принимает
вообще —

```
CRITICAL (config): (cfg.c:1867) line 73 :: data-size must be >= 536870912 and <= 281474976710656, not 8000000
```

536 870 912 байт (512 МиБ) — жёсткий минимум сервера для этого storage
engine, не настраиваемый вниз никак. Опустить его до нескольких МБ
буквально по брифу невозможно; поднять реальный датасет до сотен МБ, чтобы
512 МиБ стали содержательной границей, означало бы залить единицы
миллионов записей — непропорционально демо-стенду. Вместо этого
`data-size` оставлен на минимуме, а точка отказа сдвинута ДРУГИМ, тоже
static (не настраиваемым динамически — `set-config` живьём вернул
`ERROR:4:invalid set-config parameter`) конфиг-параметром:
`storage-engine.stop-writes-used-pct` опущен с дефолта 70% до 1%. Живой
прогон показал: фактическая точка отказа при этом оказалась НЕ на ~1% от
512 МиБ (~5,4 МБ), как давала бы наивная пропорция, а заметно выше (см.
"Разброс" ниже, диапазон 50 000-170 000 записей) — разрыв между
настроенным процентом и фактическим порогом отказа не объяснён до конца
(открытых исходников сервера в этом стенде нет, глубже `asinfo`-полей
копать нечем) и явно помечен как неполное объяснение, а не выдуман.

**Раздутие датасета до 500 000 (снято по ревью).** Первая версия стенда
поднимала растущий набор до 500 000 записей (200 000 реальных + 300 000
синтетических) специально для того, чтобы абсолютная точка отказа ram
пришлась на "~25% от датасета", как буквально просил бриф. Независимое
ревью указало на концептуальную ошибку в этом ходе: все 6 живых прогонов
точки отказа ram (50 000, 110 000, 120 000, 130 000, 160 000, 170 000)
лежали СТРОГО внутри первых 200 000 реальных записей — синтетический
хвост (id 200001..500000) физически ни разу не был затронут. Значит,
раздувание набора не «сдвинуло перелом на 25%» — оно только увеличило
знаменатель дроби, а числитель (абсолютная точка отказа, заданная
конфигом) не менялся. Раздуй датасет до 2 000 000 — та же абсолютная точка
отказа дала бы «~3-8%», не «~25%»: процент оказался управляемой
переменной, подогнанной под целевое число из брифа, а не измеряемым
свойством системы. **Синтетический хвост убран**, сценарий работает на
ВСЕХ 200 000 реальных записях `products` из PostgreSQL (Task 1) без
наращивания — этого достаточно, чтобы показать все три исхода (redis
вытесняет / ram отказывает / flash не теряет ничего), и это честнее:
никакая часть датасета в статье не будет «фиктивным довеском ради круглого
процента». Подробности решения — `.superpowers/sdd/task-8-report.md`,
"Фиксы по ревью".

После ревью сценарий публикует **абсолютные числа записей и объём занятой
памяти**, а не проценты от размера датасета: точка отказа ram — свойство
конфигурации памяти Aerospike (~512 МиБ data-size / 1% stop-writes-used-pct),
а не функция того, сколько записей мы решили залить.

`flash.indexes-memory-budget` (единственный параметр памяти namespace,
подтверждённый живьём как настраиваемый динамически) выставлен в
14 400 000 байт — 200 000 записей × 64,00 байт индекса/запись (факт Task 5)
= 12 800 000 байт с запасом ~12,5%, так что `flash` гарантированно вмещает
ВЕСЬ реальный датасет без единого отказа.

### Живая находка: `stop_writes` не сбрасывается синхронно с `truncate()`

Первый повторный прогон сценария (второй запуск сразу после первого, без
паузы) провалился нагляднее некуда: `ram` отказывал НА ПЕРВОЙ ЖЕ порции
(10 000/10 000 записей), хотя namespace был только что усечён до 0
объектов. Причина — `objects` после `truncate()` действительно доходит до
0 за секунды (асинхронный фоновый дрейн), но флаг `stop_writes`
пересчитывается только на тике `namespace supervisor`
(`nsup-period`, в конфиге по умолчанию был 120с) — второй прогон стартовал
ДО того, как флаг успел сброситься с предыдущего высокого водяного знака,
и первая же порция новой заливки отказывала на физически пустом
namespace. Тот же класс дефекта, что и в Task 3 этой серии (Tarantool
`memtx-vinyl`: асинхронное освобождение памяти после `drop()` давало
заниженную дельту без ожидания устоя) — направление другое (здесь
"устаревшее `true`", там "устаревшее большое число"), причина та же:
асинхронный фоновый процесс, метрика/флаг снята до того, как он
завершился. Исправлено на двух уровнях: `nsup-period` в
`aerospike-workingset.conf` опущен со 120 до 5 секунд (обеим namespace), и
в сам `benchmark/main.go` добавлен явный `waitStopWritesClear` — опрашивает
`namespace/<ns>` до `stop_writes=false`, не полагаясь на конкретное
значение `nsup-period`. После фикса — 5 полных прогонов подряд (3 через
`go run`, 2 через `ops/working-set-demo.sh` с нуля), ни один не начинал с
ложного отказа на пустом namespace.

### Третий раунд внешнего ревью: `доступно≈50 133` было арифметически невозможно

Блокирующая находка: в одном и том же прогоне публиковались 200 000
залитых, `evicted_keys=159 793` и **`доступно≈50 133`** — но
200 000 − 159 793 = **40 207**, не 50 133. Расхождение ~9 926 ключей, число
не могло быть верным одновременно с остальными.

Причина — в способе измерения "доступно": оно снималось **выборкой**
(`sampleRedisAvailable` делал повторные `GET` по случайным id и
экстраполировал долю попаданий на весь датасет). У Redis с `allkeys-lru`
каждый такой `GET` **обновляет LRU-позицию прочитанного ключа** — то есть
само измерение вмешивалось в измеряемое состояние: ключи, прочитанные
выборкой, искусственно переживали последующие вытеснения, которые иначе
задели бы именно их. Плюс результат экстраполяции по выборке печатался как
точное число (`≈`, но без указания размера выборки рядом), а не как оценка.

Исправлено: Redis больше не выбирается — "доступно" считается `DBSIZE`
(точный подсчёт ключей на сервере, не оценка). Добавлен **ассерт-инвариант**:
раз ни один ключ не перезаписывается (id уникальны, TTL не используется), то
`DBSIZE` обязан ТОЧНО равняться (успешных `SET` − `evicted_keys`); если не
сходится — прогон падает с диагностикой, а не публикует красивое, но
невозможное число. Aerospike (`ram`/`flash`) тоже переведён на точный подсчёт
— поле `objects` из `namespace/<ns>` info (то же поле, которым стенд уже
пользовался для ожидания опустошения после `truncate()`, фактически
проверено, что оно существует и отдаётся сервером) — точного аналога
`DBSIZE` там нет, но `objects` даёт то же самое (число хранимых записей), так
что выборка не нужна и для Aerospike.

### Разброс: точка отказа `redis` стабильна, `ram` — нет

9 живых прогонов сценария на реальном датасете 200 000 записей (3× `go run`
до снятия синтетического хвоста + 6× `go run`/`ops/working-set-demo.sh`
после — см. `.superpowers/sdd/task-8-report.md`, "Фиксы по ревью"):

| Прогон | redis перелом (запись) | ram перелом (запись) | flash потери |
|---|---|---|---|
| 1 (go run, до снятия синтетического хвоста) | 40 000 | 170 000 | 0 |
| 2 (go run, сразу после 1 — вскрыл баг `stop_writes`) | 40 000 | 10 000 (артефакт, см. выше) | 0 |
| 3 (go run, после фикса `nsup-period`) | 40 000 | 130 000 | 0 |
| 4 (go run) | 40 000 | 140 000 | 0 |
| 5 (`ops/working-set-demo.sh`, с нуля) | 40 000 | 50 000 | 0 |
| 6 (`ops/working-set-demo.sh`, с нуля) | 40 000 | 110 000 | 0 |
| 7 (go run, ПОСЛЕ снятия синтетического хвоста, датасет=200 000) | 40 000 | 190 000 | 0 |
| 8 (go run, датасет=200 000) | 40 000 | 150 000 | 0 |
| 9 (go run, датасет=200 000) | 40 000 | 150 000 | 0 |

**У `redis` на КАЖДОМ из 9 прогонов вытеснение обнаружено после одной и той
же порции — 40 000 записей.** Объяснимо конструкцией: заливка идёт через
`Pipeline` строго последовательными порциями по 10 000 без внутреннего
параллелизма, датасет детерминирован, `maxmemory` одинаков.

⚠️ **Разрешение измерения — 10 000 записей.** `evicted_keys` снимается ПОСЛЕ
каждой порции, поэтому «40 000» означает «первая порция, после которой
обнаружено вытеснение», а фактическое пересечение `maxmemory` произошло где-то
в интервале **(30 000; 40 000]**. Девять попаданий в один и тот же интервал —
сильное свидетельство детерминированности (последовательная заливка без
внутреннего параллелизма, фиксированный датасет), но НЕ доказательство, что
момент совпадает до записи. Для точки нужен меньший шаг у границы или
фиксация первого изменения `evicted_keys` внутри порции — этого стенд не делает.

**`ram` перелом плавает в диапазоне 50 000-190 000 записей, кроме явно
объяснённого артефакта прогона 2.** Это НЕ путается с недоказательностью
сценария — `ram` отказывает всегда, всегда до конца набора (200 000
записей), всегда заметно раньше `flash`. Публикуем это как ДИАПАЗОН
абсолютных записей, а не как процент — знаменатель (размер датасета) не
менялся между прогонами, поэтому переводить диапазон в проценты здесь не
вводит в заблуждение, но и не добавляет информации: сама точка отказа
задаётся конфигурацией памяти Aerospike, а не долей набора.

**Причина разброса.** Версия README до ревью объясняла его
«недетерминированным порядком прибытия параллельных `Put` у 48 воркеров».
Независимое ревью справедливо указало: порядок конкурентных записей не
должен двигать момент пересечения ПОРОГА в разы — это механически слабое
объяснение. Проверено целевым экспериментом (throwaway-проба, НЕ часть
репозитория, протокол и полный вывод — `.superpowers/sdd/task-8-report.md`,
"Фиксы по ревью"): 25 живых прогонов прямой записи в namespace `ram` с
варьируемым `nsup-period` (1с/5с/15с/30с/60с × 5 повторов) на изолированном
контейнере.

- **Установлен механизм отказа, но НЕ причина разброса.** Все 25 прогонов упали
  с ОДНИМ и тем же кодом ошибки сервера (`SERVER_MEM_ERROR`), и серверный
  флаг `stop_writes` фиксировался как `true` в пределах ~100 мс (разрешение
  опроса) от первого клиентского отказа — на КАЖДОМ из 25 прогонов, включая
  `nsup-period=60`.
  ⚠️ **Это говорит только о том, КАК система отказывает.** Влияние
  конкурентности на МОМЕНТ пересечения (или обнаружения) порога эти
  наблюдения не исключают: чтобы её проверить, нужен контроль
  `1 воркер / 48 воркеров / фиксированный темп`, которого мы не ставили.
  Гипотеза о гонке конкурентных `Put` остаётся непроверенной, а не
  опровергнутой.
- **НЕ подтверждено (и это не гипотеза, которую подгоняли под ответ):**
  что именно `nsup-period` управляет РАЗМАХОМ разброса. Если бы это было
  так, разброс точки отказа (`stddev` по 5 прогонам на каждый период)
  рос бы вместе с периодом. По факту: `period=1s` → stddev≈26 300,
  `period=5s` → stddev≈20 300, `period=15s` → stddev≈20 300,
  `period=30s` → stddev≈32 600, `period=60s` → stddev≈6 950 — зависимости
  от периода НЕТ (наименьший разброс — у САМОГО ДЛИННОГО периода). Это
  согласуется с уже задокументированной находкой этого стенда (флаг
  `stop_writes` СБРАСЫВАЕТСЯ только на тике `nsup`, см. выше) при условии,
  что ВЗВЕДЕНИЕ флага (переход false→true при превышении порога) идёт по
  другому, более быстрому пути, не привязанному к `nsup-period` —
  асимметрия правдоподобна архитектурно (взведение — это немедленная
  реакция на нарушение бюджета памяти, а снятие требует полного
  пересчёта использования namespace), но это ПРЕДПОЛОЖЕНИЕ, не
  установленный факт.
- **Более вероятный (тоже не доказанный до конца) фактор:** нестабильный
  throughput записи под Docker Desktop. В тех же 25 прогонах throughput
  «последней секунды перед отказом» колебался между ~10 400 и ~29 300
  записей/сек между иначе идентичными прогонами (тот же датасет, тот же
  `nsup-period`, тот же стенд) — см. "Границы метода" ниже, тот же класс
  нестабильности, что и Docker Desktop network/disk overhead в целом.
  Если реальный порог отказа задан в байтах, а evaluation происходит не на
  каждой записи, разброс между "перешли порог" и "сервер это заметил и
  начал отклонять" пропорционален количеству записей, прошедших за это
  время — а оно прямо зависит от throughput, который на этой платформе
  нестабилен независимо от `nsup-period`.

Итог: заведомо неверное объяснение («порядок Put») убрано. Более сильная
гипотеза («период `nsup`») проверена и НЕ подтвердилась в этом виде —
причина точного размаха разброса (50 000-190 000) остаётся установленной
частично: механизм отказа (пороговая проверка памяти) доказан,
источник вариативности МОМЕНТА обнаружения — нет. Качественный исход (ram
ВСЕГДА отказывает заметно раньше конца набора, flash — никогда) от этого
разброса не зависит и совпадает на каждом из 9 прогонов.

### Ignite не участвует в этом сценарии — явное решение, не упущение

Бриф допускал участие Ignite ("скорее всего... Ignite опрашивай через
тонкий клиент или метрики") без строгого ассерта — все три обязательных
ассерта касаются только Redis и Aerospike (`ram`/`flash`). Живой прогон
Aerospike уже вскрыл два нетривиальных живых сюрприза (жёсткий минимум
`data-size` 512 МиБ, асинхронный `stop_writes` относительно `truncate()`)
— оценка: воспроизвести аналогичное для Ignite (кэш без persistence по
умолчанию использует off-heap `DataRegion` размером ~20% от ВСЕЙ памяти
хоста, не от `-Xmx`; чтобы получить содержательный отказ на демо-объёме
данных нужен отдельный XML-конфиг с маленьким `maxSize` — тот же класс
риска "конфиг-минимум", что уже нашёлся у Aerospike) не окупает эту задачу
не будучи ассертируемым результатом. Ignite остаётся в интерфейсах серии
(`compose/ignite.yml`, Стенд 6) и может быть добавлен в сценарий отдельным
шагом позже без изменения уже пройденных ассертов.

**Явно: этот сценарий сравнивает Redis и Aerospike (`ram`/`flash`) — это
НЕ полное сравнение всех in-memory/near-memory систем серии.** Tarantool,
Picodata и Ignite в сценарий `working-set` не входят; каждая из них
разобрана отдельно в своём стенде (2-7 выше). Формулировка выбрана
намеренно, чтобы не создавать впечатление исчерпывающего сравнения там,
где его нет.

Запуск:

```bash
# повторно, для сверки качественного исхода:
```

## Стенд 8, сценарий 2: цена выноса вычислений к данным (compute-locality)

`benchmark/ -scenario compute-locality` (Task 9) — второй сценарий сводного
бенчмарка. Одна и та же агрегация (топ-10 товаров категории `tools` по
просмотрам) двумя путями на ДВУХ системах серии одновременно:

- **наивно** — вычитать всю категорию по сети в приложение, отсортировать
  на клиенте (Go/Java);
- **локально** — вызвать то, что уже выполняется рядом с данными: хранимку
  Tarantool `top_products_by_category` (Стенд 3, Task 3, контракт не менялся)
  или affinity-задачу Ignite `TopByCategoryTask` (Стенд 6, Task 6, контракт
  не менялся).

Здесь оверхед платформы (Docker Desktop) работает НА честность: каждый
лишний round-trip платит его полную цену, поэтому разница между "вытащить
33 276 объектов" и "вытащить 10" видна ИМЕННО потому, что сеть дорогая — это
не скрыто, а прямо часть вывода (см. "Границы метода" ниже).

### Архитектура: Go оркестрирует Java-подпроцесс

`benchmark/main.go` — Go-программа. Для Tarantool она говорит с сервером
напрямую (`go-tarantool/v2`, тот же протокол, что и Стенд 3). Для Ignite —
НЕ пытается заново реализовать протокол Ignite thick-client в Go (у тонкого
клиента 2.18.0 нет Affinity API/`affinityCall`, см. Стенд 6): вместо этого
`compute-locality` запускает подпроцессом ТОТ ЖЕ `ignite-stand.jar`, тем же
способом, каким его запускает раздел "Как воспроизвести" (`docker run
--network inmemory-net ... java ... -jar target/ignite-stand.jar -scenario
compute`), и разбирает его stdout. `IgniteStand.java` получил параметр
`-order=naive-first|local-first` и раздельные замеры времени вокруг УЖЕ
существовавших блоков `ScanQuery`/`affinityCall` (Стенд 6) — сама
`TopByCategoryTask`, `CategoryFilter` и тай-брейк `TOP_ORDER` не изменены,
это чистая инструментация поверх готового и отревьюированного кода.

### Живой прогон: главное число

3 полных прогона `ops/compute-locality-demo.sh` подряд (каждый — свежие
контейнеры, свежая JVM, `docker compose down` между прогонами), в каждом —
оба порядка (прямой и `-swap-order`):

```
compute-locality: tarantool объектов по сети — наивно=33276, локально(хранимка)=10 (в 3327.6x меньше)
compute-locality: ignite объектов по сети — наивно=33276, локально(compute)=10 (в 3327.6x меньше)
```

**Идентично на всех 3 прогонах, в обоих порядках, на ОБЕИХ системах: 33 276
объектов наивно против 10 локально.** Число объектов детерминировано (та же
природа, что и `tools`=33 276 в Стенде 6/README "Стенд 6") и совпадает с
уже задокументированным фактом Task 6 — здесь оно подтверждено ЕЩЁ раз, для
Tarantool впервые. Round-trip в обоих путях на обеих системах — **1**
(один `SELECT`/`CALL` у Tarantool, один `ScanQuery`/`affinityCall` у
Ignite): разница НЕ в числе round-trip, а в объёме одного round-trip —
статья обязана сказать это прямо, а не подразумевать "наивно = много
round-trip".

### Тай-брейки: разные правила, один и тот же топ

Tarantool `top_products_by_category` тай-брейкает равные `views` по PK
DESCENDING (артефакт REQ-итератора вторичного индекса, Стенд 3). Ignite
`TopByCategoryTask` — по `views DESC`, затем `id ASC` (независимый выбор,
Стенд 6). Контракты **не унифицированы** — вместо этого сценарий
ДОКАЗЫВАЕТ экспериментом, что на пробе `category=tools, limit=10` разница
правил не имеет значения:

```
compute-locality: ТАЙ-БРЕЙКИ — множество id топ-10 СОВПАЛО между Tarantool (PK DESC на равных views)
и Ignite (views DESC, затем id ASC): [7 12 21 30 33 34 38 76 84 85]
```

Множество id совпало побитово на всех 3 живых прогонах. Единственная ничья
в категории `tools` — `views=93` у `id=84` и `id=85` (тот же факт, что и в
README Стенда 6) — при `limit=10` **оба** члена ничьей попадают в топ
независимо от того, какое правило тай-брейка их упорядочивает внутри топа
(следующий по рангу `id=105` имеет `views=74`, разрыв большой). Это
подтверждено здесь ВПЕРВЫЕ как межсистемная сверка (Стенд 6 проверял только
внутреннее согласие naive/compute на самой Ignite); граница, где тай-брейк
реально решает СОСТАВ (не только порядок) топа — `limit=9` — уже отдельно
проверена в Tarantool `storedproc` (Стенд 3).

### Защита от смещения порядка

Каждый прогон исполняет оба пути (наивно/локально) в обоих порядках —
внутри одного соединения/JVM И между двумя отдельными процессами
(`-swap-order` перезапускает `go run` и порождает свежий `docker run`
заново). Ассерт `|ratioDirect-ratioSwapped|/ratioDirect > 0.5 → fatal`
проходит на всех 3×2 запусках. Отношение считается как `ratio =
naive_median / local_median` (медиана из 51 повтора каждого пути, см. выше
"Живая находка"). Пример одного прогона — только отношения; сам скрипт
печатает в stdout ещё и абсолютные `naive_ms=`/`local_ms=`
(`compute_ms=` для Ignite), но это диагностика КОНКРЕТНОГО прогона на
Docker Desktop, не материал статьи (см. "Границы метода") — здесь не
приводятся:

```
ОТНОШЕНИЕ tarantool order=naive-first ratio=34.43
ОТНОШЕНИЕ tarantool order=local-first ratio=33.91
ОТНОШЕНИЕ ignite    order=naive-first ratio=1.62
ОТНОШЕНИЕ ignite    order=local-first ratio=1.56
```

**Наблюдение диагностической пробы (НЕ сохранена в репозитории, поэтому по опубликованным данным непроверяемо) —
`.superpowers/sdd/task-9-report.md`): замер локального пути Tarantool
(`CALL` хранимки, доли миллисекунды) распределён БИМОДАЛЬНО** — примерно
поровну между ~0.5мс и ~1.0мс (вероятно, две ветки TCP-стека WSL2/Docker
Desktop, с задержкой ACK и без — не установлено до конца). Первая версия
сценария измеряла каждый путь ОДИН раз за проход (медианы вообще не было) —
и на этом ловила ложный "ассерт смещения порядка" ДВАЖДЫ подряд: сразу
после свежей загрузки датасета единичный замер дал
`ratio(naive-first)=24.35` против `ratio(local-first)=48.88`; после того как
был добавлен один прогревочный вызов (гасит холодный старт соединения, см.
`main.go`), снова единичный замер — `ratio(naive-first)=17.71` против
`ratio(local-first)=38.83`. Не потому, что порядок реально влиял, а потому,
что единичный замер бимодального сигнала произвольно попадает в одну из
двух мод. Диагностика отдельной throwaway-пробой (51 интерливинг-повтор, 3
независимых группы) показала: при **N=51** разброс между порядками укладывался в единицы процентов. Это НЕ означает сходимости медианы
(разброс между порядками <3% против допуска 50%). Оба стенда
(`benchmark/main.go` и `IgniteStand.java`) считают время как медиану из 51
повтора каждого пути (не как единичный замер, как было в первой версии) —
абсолютное время публикуется ТОЛЬКО как основа отношения внутри прогона, не
как факт о системе (см. "Границы метода").

| 1 | 34.43 / 33.91 (наивно-первым), 34.43 / 33.08 (наивно-первым, swap-runе) | 1.62 / 1.56, 1.58 / 1.60 |

**Число объектов по сети (33276/10, обе системы) идентично на всех 3
прогонах — детерминировано, как и заявлено.** Отношение времён — НЕ
идентично: **Tarantool 53–123x, Ignite 0,90–1,92x** (числа ПОСЛЕ исправления

⚠️ **Причина разрыва НЕ установлена.** Напрашивающееся объяснение «per-call

Стенд не разделяет алгоритмический вклад и транспортный — для этого нужен
другой эксперимент.
**Это ключевой урок сценария: экономия по объёму данных и экономия по
времени — РАЗНЫЕ величины**, и смешивать их (публиковать только
"3327.6x" как будто это ускорение) вводило бы в заблуждение — статья обязана
показать оба числа раздельно, с явной оговоркой, что абсолютные мс здесь не
публикуются как факт о системах (Docker Desktop), только относительный
порядок величины ratio.

## Стенд 8, сценарий 3: etcd под несвойственной нагрузкой (etcd-misuse)

Третий и последний сценарий сводного бенчмарка. Подаёт на etcd ТОТ ЖЕ
профиль, что Redis держит штатно, и показывает, что происходит с размером
базы, MVCC и отказами. **Это не "etcd плохой" — это "etcd про другое"**:
etcd проектировался для небольшого, редко меняющегося координационного
состояния (Стенд 7 — watch/lease/lock), а не для профиля с частыми
перезаписями горячих ключей, для которого создан Redis.

### Профиль: горячий набор, а не 50 000 разных ключей

Бриф говорит "запись 50k ключей по 1 КБ" — реализовано как 50 000 ОПЕРАЦИЙ
записи по горячему набору из 5 000 ключей (`-misuse-hot-keys`, каждый
перезаписывается ~10 раз, `-misuse-write-ops`), 1 КБ на значение, ОДИН и
тот же профиль на обеих системах (`writeMisuseRedis`/`writeMisuseEtcd`,
`benchmark/main.go`). Это осознанное прочтение "того же горячего профиля
записи, что и у Redis" (не "50 000 РАЗНЫХ ключей единожды" — на таком
профиле у etcd просто не накопилось бы MVCC-истории, и разницы с Redis
почти не было бы, см. следующий абзац): счётчик/сессия/кэш — типовой
паттерн, где одни и те же ключи обновляются раз за разом.

Для Redis (`SET` перезаписывает значение НА МЕСТЕ) это стоит МАЛО —
`used_memory` растёт примерно до размера горячего набора и на этом
останавливается, сколько бы перезаписей ни было. Для etcd КАЖДАЯ
перезапись — НОВАЯ MVCC-ревизия, и все старые ревизии физически хранятся в
backend (bbolt-файле) до явной компакции — задокументированное поведение
etcd (см. Стенд 7, секция "revisions": там же показано, что `DbSizeInUse`
падает после `Compact`, а `DbSize`, физический файл, — только после
`Defragment`), НЕ открытие этой задачи. На перезаписываемом горячем профиле
это означает, что размер базы растёт БЕЗ ГРАНИЦ, пока не упрётся в квоту.

**Оговорка про число «10×».** Причина эффекта (etcd хранит историю
ревизий, Redis — только текущий снимок) универсальна для любого
перезаписываемого профиля. Но конкретное значение **10,0×**, наблюдаемое
ниже, — характеристика ИМЕННО этого профиля (50 000 операций / 5 000
ключей / 1 КБ) и ИМЕННО квоты 64 МиБ: квота подобрана так, чтобы отказ
пришёлся на конец профиля (round 9 из ~10), поэтому накопленная к этому
моменту MVCC-история близка к «естественному» максимуму для этого объёма
перезаписей. При другом числе операций, другом размере горячего набора или
другой квоте соотношение будет другим — это не универсальная константа
etcd-vs-Redis.

### Отдельный контейнер с квотой 64 МиБ

`compose/etcd-misuse.yml` — ОТДЕЛЬНЫЙ от `compose/etcd.yml` (Стенд 7)
контейнер (`inmemory-etcd-misuse`, порт `2382`, НЕ 2379):
`--quota-backend-bytes=67108864` (64 МиБ) вместо дефолтных 2 ГиБ —
искусственно занижена, чтобы упереться в неё за разумное время (~2,5
минуты живого прогона на профиле выше), как явно требует бриф Step 2.
Контейнер Стенда 7 (дефолтная квота, watch/lease/lock/revisions) этим
сценарием не трогается. Redis переиспользует общий `compose/redis.yml`

## Границы метода

- **Абсолютную latency не меряем как эталон** — стенд работает под Docker
  Desktop на Windows (WSL2/Hyper-V backend), сетевой и дисковый путь
  виртуализованы. Абсолютные числа (мс/мкс) не сопоставимы с bare-metal
  Linux и не публикуются как эталон производительности той или иной
  системы. Надёжны только относительные сравнения внутри одного и того же
  измерительного стенда (до/после, система А vs система Б на одной и той же
  машине в одном прогоне).
- **Оверхед Docker Desktop** — виртуализованные сеть и файловая система
  добавляют постоянный оверхед поверх измеряемой операции; он один и тот же
  для всех технологий стенда (все контейнеры внутри одного Docker Desktop),
  поэтому относительное сравнение технологий друг с другом остаётся
  валидным, но абсолютная цифра не переносится на прод-железо.
- **Нулевые отсчёты таймера** — на этой машине `time.Since()` вокруг
  быстрых операций иногда возвращает ровно 0 (наблюдалось в соседних
  стендах репозитория, см. `databases/redis/deep-dive/README.md`, Стенд #6).
  Стенды серии считают средние по `elapsed/attempts` (две отметки времени —
  начало и конец серии), а не по сумме отдельных замеров, там где это
  расхождение может исказить результат.

серии.

Task 10 (бенчмарк, сценарий 3 — etcd под несвойственной нагрузкой): все три
ассерта прошли на каждом из 7 живых прогонов (2 исходных подряд + 1
независимая ревью-проверка + 4 дополнительных для честной характеристики
разброса), без отклонений от брифа. Единственное осознанное прочтение —
"50k ключей по 1 КБ" реализовано не как 50 000 РАЗНЫХ ключей (на таком
профиле etcd не накопил бы MVCC-истории, и демонстрации бы не получилось),
а как 50 000 операций перезаписи горячего набора из 5 000 ключей (~10
перезаписей на ключ) — тот самый профиль, для которого создан Redis и
которым etcd НЕ создан. Квота 64 МиБ достигнута на всех 7 живых прогонах
(Step 2), точный текст `etcdserver: mvcc: database space exceeded` и alarm
`NOSPACE` — воспроизведены дословно на каждом, задокументированное
поведение подтверждено живым измерением, не переоткрыто как находка.
Процедура восстановления `Compact → Defragment → AlarmDisarm` сработала на
всех 7 прогонах (dbSize после −89.7%, до идентичных на каждом прогоне
6 914 048 байт, запись восстановилась).

**Фикс по независимому ревью.** Диапазон точки отказа и dbSize в момент
отказа, заявленные по первым 2 прогонам (48279-48287, «идентичный»
dbSize 67 112 960), оказались переоценены по точности — независимая
проверка (3-й прогон) вскрыла отказ на записи #48232 и dbSize 67 129 344
байт, оба за пределами заявленного диапазона. После 4 дополнительных
прогонов фактический диапазон по всем 7: точка отказа **48220-48287 из
50000** (≈0,13% профиля, шире исходной оценки, но не на порядки величины,
как у Aerospike в Task 8), dbSize в момент отказа **67 112 960-67 153 920
байт** (разброс ~10 страниц bbolt по 4 КБ, не «идентичный оба раза»).
Качественный исход при этом идентичен на всех 7 прогонах. Ratio etcd
dbSize / redis Δmem устойчиво округляется к **10,0×** на всех 7 — но это
число специфично для профиля (50k операций/5000 ключей/1 КБ) и квоты
(64 МиБ) этого сценария, не универсальная константа etcd-vs-Redis.
Источник разброса точки отказа не исследован отдельным экспериментом.
Подробности и полные числа по всем 7 прогонам — «Фиксы по ревью» в
`.superpowers/sdd/task-10-report.md`.
