# Замеры: WSL2 (Ubuntu) поверх Windows 11, Docker Desktop

Дата: 2026-08-01. Снято `./run.sh`.

```
ядро          Linux 5.15.167.4-microsoft-standard-WSL2
CPU           16 шт.
память        62.8 ГиБ
docker        клиент 29.6.1, сервер 29.6.1
go            go1.26.3
образ         postgres@sha256:4327b9fd2955...09e2 (закреплён по digest)
```

## Итог: 20 случаев, 4 повтора, порядок чередуется

| Вариант | Медиана | Разброс | Прогонов упало | Первым / вторым |
|---|---:|---:|---:|---:|
| `tmpl` — общий контейнер + `TEMPLATE` | 5.9 s | 5.7–5.9 | 0 из 4 | 2 / 2 |
| `naive` — контейнер на случай | 65.8 s | 65.8–66.6 | 1 из 4 (шёл первым) | 2 / 2 |

Отношение — **×11.2**.

Повторов именно четыре, а не три: порядок вариантов чередуется, и при нечётном числе
один из них оказывался бы первым чаще другого. После того как выяснилось, насколько
сильно порядок влияет (см. ниже), это перестало быть придиркой. Колонка «первым / вторым» показывает
НАЗНАЧЕННЫЕ позиции, а не успешные: иначе упавший прогон исчезал бы из баланса и
прятал бы ровно ту связь, ради которой колонка заведена. Единственное падение
случилось, когда наивный вариант шёл первым.

## Как эти числа получились и почему это важнее самих чисел

Инструмент пришлось чинить трижды, и каждая починка меняла результат. Порядок
важен: он показывает, насколько легко получить убедительное, но неверное число.

**1. Постоянный порядок (сначала `tmpl`, потом `naive`).** Шаблонный вариант
выглядел идеально стабильным — 0 падений из 3, — а наивный падал 1–2 раза из 3.
Вывод напрашивался: наивный вариант нестабилен по своей природе.

**2. Порядок стали чередовать.** Падать начали **оба**, по 2 прогона из 3. У
шаблонного отказ был другой:

```
reaper: new reaper: run container: ... No such container: ... could not start container
```

То есть стабильность шаблонного варианта в пункте 1 была артефактом: он всегда
шёл первым, по спокойному демону. Поставленный после наивного, он падал так же.

**3. Добавлено ожидание восстановления демона** между прогонами: уборка своих
контейнеров, затем ожидание, пока догорят реаперы прошлого прогона и `docker
info` начнёт отвечать быстрее полутора секунд. После этого разница стала
повторяемой, а падения — редкими: в итоговой таблице упал один наивный прогон
из четырёх, и он пришёлся на позицию «первым».

**Что из этого следует.** Падения по таймауту — функция состояния демона, а не
свойство варианта. Наивный вариант на отдохнувшем демоне медленный, но доходит
до конца; он же, запущенный сразу после чужой контейнерной молотьбы, разваливается
— и разваливает следующего за собой. В настоящем наборе тестов пакеты идут друг
за другом и параллельно, то есть живут именно во втором режиме.

## На чём падает, когда падает

Из лога прогона без паузы между вариантами:

```
--- PASS: TestNaive/case-05 (3.13s)
--- FAIL: TestNaive/case-06 (64.70s)
    get state: Get ".../containers/1a02ab.../json": context deadline exceeded
--- PASS: TestNaive/case-07 (3.11s)
```

Отказ не в том, что Postgres долго стартует: не ответил Docker API — запрос
состояния контейнера через сокет. Соседние случаи идут за 3.1 s, то есть демон
отвечает неравномерно, а не лежит.

Почему API перестаёт отвечать вовремя — исчерпание какого ресурса, очередь в
демоне, особенности WSL2 — стенд не показывает: метрики демона он не снимает.
Известно ровно то, что выше.

## 5 случаев, 2 повтора

| Вариант | Медиана | Разброс | Прогонов упало |
|---|---:|---:|---:|
| `tmpl` | 5.3 s | 5.2–5.4 | 0 из 2 |
| `naive` | 18.4 s | 18.2–18.5 | 0 из 2 |

Видно устройство: у `tmpl` время между 5 и 20 случаями почти не изменилось
(5.3 → 5.9), у `naive` выросло вчетверо (18.4 → 65.8). Фиксированная часть у
шаблонного варианта — подъём одного контейнера, дальше каждый случай стоит
десятки миллисекунд.

## Накопление контейнеров

Отдельный прогон с `STAND_LEAK=1` (наивный вариант перестаёт убирать за собой,
8 случаев):

```
своих до:                    0
своих сразу после прогона:   8
своих через 20 с:            0
```

Контейнеры копятся за время прогона; реапер убирает их после завершения процесса.

**Чего это не доказывает:** что накопление вызывает отказы Docker API. Отказы
воспроизводятся и при работающей уборке. Накопление — установленный факт и
правдоподобный усилитель, не причина.

## Как читать эти числа

Под WSL2 обращение к демону идёт через прослойку виртуализации, и цена жизненного
цикла контейнера там выше, чем на линуксовом хосте. На линуксовом раннере наивный
вариант будет быстрее и, вероятно, устойчивее, а отношение — скромнее. Порядок
эффекта сохранится, коэффициент — нет.
