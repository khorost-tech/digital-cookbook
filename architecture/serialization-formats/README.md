# serialization-formats

Стенд сравнивает JSON, Avro, Protobuf и JSON Schema на **одних и тех же
пяти канонических записях**, двумя независимыми реализациями (Go и
Java), по четырём осям:

1. **Размер** (`bench/run-size.sh` → `fixtures/size.txt`) — сколько
   весит запись и схема, до и под сжатием.
2. **Эволюция схемы** (`bench/run-evolution.sh` → `fixtures/evolution.txt`)
   — что происходит при чтении записи по изменённой схеме: тихая порча,
   явный отказ или честное совпадение.
3. **Доступность схемы** (`bench/run-need-schema.sh` → `fixtures/need.txt`)
   — что физически нужно иметь под рукой, чтобы прочитать байты, и что
   происходит, когда реестра схем нет.
4. **Перекрёстное чтение** (`bench/run-cross.sh` → `fixtures/cross.txt`)
   — читает ли реализация байты, записанные ДРУГОЙ реализацией, так же,
   как свои собственные.

Полные правила стенда — в `schemas/spec.md` (решения, обязательные для
любой реализации; вторая реализация писалась по этому документу, не по
исходнику первой). Этот README — не пересказ спеки, а паспорт того, что
стенд **фактически измерил**: числа ниже сверены с фикстурами
автоматическим тестом (`scripts/test_readme_matches_fixtures.py`), а не
набраны по памяти.

## Что стенд доказывает

- **Тихая порча — реальное и наблюдаемое поведение форматов, а не
  гипотеза.** На изменении `retype_message` Protobuf в обеих реализациях
  на записи №0 клетки `newer_reader` молча возвращает вложенное
  сообщение, собранное из байт исходной строки, вместо ошибки (`wrong`),
  а на записях №1–4 той же клетки — отказывает (`refused`): у Protobuf
  оба исхода принадлежат формату одновременно, и какой из них
  случится, зависит от конкретных байтов записи, а не от изменения схемы
  как такового (`fixtures/evolution.txt`, `schemas/spec.md` §15.2).
- **Одна и та же нотация Avro у двух независимых библиотек не имеет
  общего мнения о конфликте псевдонимов.** На `alias_conflict`, направление
  `newer_reader` (писатель хранит и `name`, и `email` отдельно; читатель
  объявляет `name` с псевдонимом `email`), `hamba/avro` (Go) молча
  связывает читательское имя с писательской почтой (`wrong` на всех 5
  записях), `org.apache.avro` (Java) отказывается читать вовсе (`refused`
  на всех 5 записях) — **независимо от того, какая из двух реализаций
  записала байты**: перекрёстная проба (`fixtures/cross.txt`) на том же
  направлении показывает, что исход не меняется от того, кто записал
  байты — только от того, кто их читает. Реестр схем (Apicurio 3.3.1) на
  той же паре схем даёт третий, ещё более ранний ответ — отказывается
  оценить совместимость вообще, до применения правила
  (`http_status=422`, `registry_verdict=schema_error`,
  `fixtures/need.txt`). Три независимые точки зрения на одну пару схем —
  три разных диагностических пути.
- **Без схемы Avro и Protobuf нечитаемы — это измерено отказом
  инфраструктуры, а не выведено рассуждением.** Реестр гасится сценарием
  МЕЖДУ двумя попытками чтения одних и тех же байтов: с поднятым реестром
  чтение проходит (`outcome=ok`, `registry_calls=1`), с погашенным —
  падает на транспортном уровне без запасного пути (`outcome=unavailable`,
  `fixtures/need.txt`, leg `registry_down`). Наивный декодер, не знающий
  про конверт реестра (маркер + 5-байтовый идентификатор схемы перед
  данными), не падает с ошибкой — он молча возвращает запись с пустыми и
  нулевыми полями (`prefix_len=5`, `outcome=wrong`).
- **Байтовое равенство между независимыми реализациями — не единое
  свойство, а три разных.** Пачка из пяти записей даёт одинаковый
  `batch_hash` между Go и Java у `avro` и `protobuf`, но РАЗНЫЙ — у `json`
  и `json-schema` (JSON не специфицирует порядок ключей объекта — это
  ожидаемо, а не находка). При этом `batch_content_hash` (хеш содержимого
  ПОСЛЕ расшифровки) совпадает между ВОСЕМЬЮ строками — оба языка,
  все четыре плеча: `b3ec6d0b8b4013c34e77086854338852b033c097731ae42b780a694d48540ced`
  (`fixtures/size.txt`). Это доказывает, что все четыре формата в обеих
  реализациях кодируют и декодируют один и тот же смысл, даже там, где
  байты на проводе расходятся по праву формата.
- **Бинарные форматы компактнее контроля и остаются компактнее под
  сжатием — направление устойчиво, точное число нет** (см. таблицу ниже
  и оговорку про пачку в разделе «Ограничения метода»).

## Чего стенд НЕ доказывает

- Что перечисленные поведения — единственно возможные для формата: это
  два конкретных клиента (`hamba/avro`+`org.apache.avro`,
  `google.golang.org/protobuf`+`protobuf-java`) на конкретных версиях, а
  не весь класс реализаций.
- Что цифры `zstd`/`batch_zstd` сравнимы МЕЖДУ Go и Java: у них разные
  библиотеки сжатия (см. «Ограничения метода», пункт 2).
- Что таблица эволюции покрывает всё пространство возможных изменений
  схемы: она покрывает девять конкретных изменений, два из которых
  (`alias_conflict`, `retype_message`) добавлены НАРОЧНО как контрпримеры
  к моделям стенда (см. «Ограничения метода», пункт 1, и `spec.md` §15).
- Что реестр Apicurio ведёт себя так для ЛЮБОЙ версии: образ снят по
  запиненному тегу `apicurio/apicurio-registry:3.3.1` (`bench/run-need-schema.sh`
  сверяет это же число с ответом `system/info` живого контейнера и
  останавливает прогон при расхождении — см. «Ограничения метода» ниже),
  и тройное расхождение на `alias_conflict` привязано именно к этой
  версии реестра, записанной в шапке `fixtures/need.txt`.

## Как запустить

Полный прогон с нуля, все четыре оси одним `RUN_ID`, полный набор тестов
(Python + Go + Java):

```bash
docker compose down -v   # если в стенде поднят рестарт-стейт (реестр этого не требует — он не в compose)
./bench/run-all.sh
python -m unittest discover scripts -v
```

`bench/run-all.sh` сам вызывает `go test ./...` и `mvn test` внутри
контейнера как часть прогона — команда выше про `python -m unittest`
дублирует последнюю проверку явно, чтобы не верить коду возврата
сценария на слово (см. `verification-before-completion`).

Отдельно, если нужна только одна ось (числа при этом НЕ будут помечены
`RUN_ID` сводного прогона):

```bash
./bench/run-size.sh
./bench/run-evolution.sh
./bench/run-need-schema.sh   # поднимает и гасит реестр Apicurio сам
./bench/run-cross.sh
```

Требуется: Go (см. `go/go.mod` — `go 1.25`), Docker (образ
`maven:3.9-eclipse-temurin-25` для Java-пробы, `apicurio/apicurio-registry:3.3.1`
для оси доступности), Python 3.

## Как читать каждую фикстуру

Все четыре фикстуры — построчный JSON (`json lines`) с комментариями
(`#`, игнорируются разбором) в начале и служебным маркером `COMPLETE`
последней строкой: его отсутствие означает, что прогон оборвался
посередине, и файл читать нельзя.

### `fixtures/size.txt` — ось размера

Одна строка `{"kind":"env",...}` (версии библиотек, уровень сжатия), 
затем по одной строке на пару «плечо, язык, каноническая запись»
(`--op=size`, координаты `--change=base --direction=same` — размер
мерит ОДНУ схему, не эволюцию, `spec.md` §10.3).

Ключевые поля: `bytes` (размер записи), `schema_bytes` (вес
КАНОНИЧЕСКОЙ формы схемы — Parsing Canonical Form у Avro, дескриптор без
`source_code_info` у Protobuf, минифицированный JSON без `title` у JSON
Schema), `schema_file_bytes` (вес файла как есть, с нашими отступами),
`batch_bytes`/`batch_zstd`/`batch_hash`/`batch_content_hash` (свойства
ВСЕЙ клетки — одно значение на пять строк, см. `spec.md` §10.3.2).

Запись 0 (первая каноническая запись, поле `record_index`), лишь
реализация Go — `zstd`/`batch_zstd` не сравнимы между реализациями
(разные библиотеки сжатия, см. «Ограничения метода», пункт 2):

| Плечо | bytes | zstd (Go/klauspost) | schema_bytes | schema_file_bytes | batch_bytes |
|---|---|---|---|---|---|
| `json` (контроль) | 53 | 66 | 0 | 0 | 276 |
| `json-schema` | 53 | 66 | 226 | 293 | 276 |
| `avro` | 27 | 40 | 162 | 221 | 146 |
| `protobuf` | 30 | 43 | 119 | 119 | 161 |

`bytes`, `schema_bytes`, `schema_file_bytes` и `batch_hash`/
`batch_content_hash` — часть межъязыкового контракта (обязаны совпасть
между Go и Java побайтово или посодержательно, `spec.md` §10.3–10.3.2);
разбор (`scripts/analyze-size.py`) это проверяет и превращает
расхождение в находку с ненулевым кодом возврата.

### `fixtures/evolution.txt` — ось эволюции схемы

9 изменений (без `base`) × 3 плеча (`avro`, `protobuf`, `json-schema` —
контрольное `json` в эту таблицу не входит, `spec.md` §13) × 2
направления (`newer_reader`, `newer_writer`) × 2 вида пробы (`compat`,
`roundtrip`) × 5 канонических записей × 2 реализации = **1080 строк**
данных (число объявлено в шапке фикстуры и сверяется разбором —
`scripts/analyze-evolution.py`).

Ключевые поля: `outcome` (`ok`/`refused`/`wrong`/`n/a`/`error` — §1
спеки), `want` (вычисленное ожидание), `got`/`record` (что фактически
прочиталось/записалось — без них `wrong` ничем не подтверждён),
`stage` (докуда дошла проба).

Разбор сверяет каждую клетку с `schemas/expected.json` и печатает
расхождение как находку (`schemas/expected-corrections.json` — журнал
уже принятых поправок с доводом).

### `fixtures/need.txt` — ось доступности схемы

Реестр Apicurio (протокол Confluent, API v3), только реализация Go
(вопрос оси — про поведение реестра и конверта провода, а не про
расхождение двух библиотек одного формата — то уже закрыто осью
эволюции). Строки трёх видов:

- `kind: registry_matrix` — попытка зарегистрировать вторую версию схемы
  с включённым правилом обратной совместимости (`http_status`,
  `registry_verdict`: `accepted`/`rejected`/`schema_error`);
- `kind: need` — попытка прочитать конверт при разных условиях
  (`leg`: `registry_up`, `registry_down`, `schema_local`, `no_schema`);
- `kind: envelope` — наивное декодирование конверта без учёта префикса
  (`prefix_len`, `decoder: naive`).

### `fixtures/cross.txt` — ось перекрёстного чтения

Две группы строк:

- `kind: cross` — байты кодирует один язык (`writer`), читает другой
  или тот же (`reader`/`lang`); 5 изменений × avro + 4 изменения ×
  protobuf (`alias_conflict` вырожден у Protobuf, `spec.md` §6.4) × 2
  направления × 4 сочетания писатель/читатель × 5 записей = 360 строк;
- `kind: identity-probe` — проба байтовой идентичности с контролем: одна
  реализация кодирует одну запись дважды и сравнивает сама с собой
  (`control_equal`), затем дайджесты сверяются между реализациями
  (`spec.md` §17.6). 4 плеча × 2 языка = 8 строк.

Итого 368 строк данных (шапка объявляет число заранее, разбор —
`scripts/analyze-cross.py` — сверяет).

**Диагональные строки (писатель = читатель) обязаны построчно совпасть**
с колонкой `compat` оси эволюции на тех же координатах — расхождение там
означает, что испортился файловый обмен, а не формат (`spec.md` §17.4).

## Ограничения метода

Их три, и ни одно не смягчается:

1. **Модель ожидания для Avro пересказывает правила разрешения схем
   самого Avro** (`spec.md` §6.2: «по имени, а если не совпало — по
   псевдонимам читателя»). Из девяти измеренных изменений семь
   исходных не заставляли эту модель разойтись с наблюдаемым поведением
   ни одной из двух библиотек — колонка Avro в исходной таблице
   получалась почти без `wrong` не потому, что реализации Avro не умеют
   молча портить данные, а потому что **мы измеряли правила Avro его же
   собственными правилами**, и совпадение было почти тавтологией, а не
   находкой. `alias_conflict` — контрпример, добавленный НАРОЧНО, чтобы
   разорвать это тождество (`spec.md` §15.1), и он показывает
   расхождение, а не то, что модель починили: правильная реализация всё
   равно не предсказывает, какая из двух настоящих библиотек Avro прочтёт
   `wrong`, а какая — откажет.
2. **Сжатый размер (`zstd`, `batch_zstd`) — свойство формата, данных И
   БИБЛИОТЕКИ СЖАТИЯ**, а не только формата и данных. Go использует
   `klauspost/compress`, Java — `zstd-jni` (обвязка над `libzstd`); обе
   реализуют один и тот же стандарт и уровень 3, но НЕ обязаны давать
   побайтово одинаковый результат (детали устройства энкодера — свойство
   библиотеки). Заявление вида «Avro под сжатием весит N байт» без имени
   библиотеки и уровня сжатия — не факт о формате Avro, а факт об одной
   конкретной сборке.
3. **Побайтовое совпадение между реализациями — разного происхождения
   для разных плеч, и это нельзя обобщать одним словом.** У `avro` оно
   следует из СПЕЦИФИКАЦИИ (Parsing Canonical Form + позиционная запись
   не оставляют места для расхождения порядка байт). У `protobuf` это
   ЭМПИРИЧЕСКОЕ наблюдение на двух конкретных реализациях при включённом
   детерминированном кодировании — не гарантия формата на будущее. У
   `json`/`json-schema` побайтовое совпадение ОТСУТСТВУЕТ и не
   предполагается: JSON не специфицирует порядок ключей объекта, и обе
   реализации вправе выбрать свой (замерено: `batch_hash` расходится
   между Go и Java у этих двух плеч, `batch_content_hash` — нет).

**Отдельная оговорка о версии.** Тройное расхождение на
`alias_conflict` (Go-Avro → `wrong`, Java-Avro → `refused`, реестр →
`schema_error`) снято на конкретной версии реестра — Apicurio 3.3.1
(шапка `fixtures/need.txt`). Образ запинен тегом
`apicurio/apicurio-registry:3.3.1` (`bench/run-need-schema.sh` сверяет
номер версии из ответа `system/info` живого контейнера с этим тегом и
останавливает прогон при расхождении — исключён класс ошибки «тег образа
не версия»: раньше тег был плавающим (`latest`), и прогон проверял бы
версию УЖЕ ПОСЛЕ того, как нужный (или ненужный) образ скачался).
Пиновка не делает находку вечной: более новый или более старый реестр
волен решить иначе, и утверждение «реестр даёт третий ответ» остаётся
привязанным именно к версии 3.3.1, а не является вечным свойством
протокола — просто теперь эта версия гарантированно ТА ЖЕ, что записана
в фикстуре, а не та, что случайно оказалась «последней» в момент
прогона.

## Структура

```
bench/            сценарии съёмки фикстур (по одному на ось + сводный run-all.sh)
fixtures/         снятые фикстуры (JSON lines + COMPLETE)
go/               реализация пробы на Go (cmd/probe, cmd/needprobe)
java/             реализация пробы на Java (Maven, org.apache.avro + protobuf-java)
schemas/          манифест, канонические записи, схемы всех версий, spec.md, expected.json
scripts/          разбор фикстур (analyze-*.py) и тесты (test_*.py)
```
