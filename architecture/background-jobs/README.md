# background-jobs

Стенд к серии «Фоновые задачи и планировщики» (`architecture/`).

## Что демонстрирует

Очередь задач на одной таблице PostgreSQL (`public.jobs`) с **арендой джобы**:
джоба выполняется минутами, воркер может умереть посередине, поэтому владение
джобой имеет срок (`leased_until`/`leased_by`), а не только факт. Схема — фундамент
для последующих артефактов серии: свой воркер на `SKIP LOCKED`, River для
контраста, планировщик на advisory-локе, LISTEN/NOTIFY вместо polling.

Все числа по каждому артефакту — в [`FIXTURES.md`](FIXTURES.md), взяты из
живого прогона, а не из документации.

⚠️ **Скрипты `scripts/*.sh` НЕ рассчитаны на параллельный запуск друг с
другом.** Все они делят одну таблицу `jobs`, делают `TRUNCATE jobs` в своей
первой строке и не убирают за собой после завершения — после прогона в
таблице обычно остаётся хотя бы одна строка (артефакт последней демонстрации).
Запускайте их строго последовательно, один за другим, и не одновременно с
чужим ручным запросом к `jobs` на этом же стенде.

## Как поднять

```bash
cd compose
docker compose up -d
# либо начисто, если стенд уже поднимался раньше:
# docker compose down -v && docker compose up -d
docker exec bj-postgres psql -U jobs -d jobs -c "\d jobs"
```

Требуется Docker (в этом окружении — через WSL2). Ждите, пока healthcheck
контейнера `bj-postgres` не станет `healthy` (`docker compose ps`), прежде
чем запускать демонстрации — сразу после `up -d` PostgreSQL может быть ещё
не готов принимать подключения.

- PostgreSQL: `18.4` (проверено фактическим latest в реестре на момент задачи)
- Порт: `5456` (5455 и ниже заняты соседними стендами)
- БД/пользователь/пароль: `jobs` / `jobs` / `jobs`

## Путь читателя: от пустой БД до всех демонстраций

```bash
cd architecture/background-jobs

# 1. поднять PostgreSQL
cd compose && docker compose up -d && cd ..

# 2. наполнить очередь (по умолчанию 20 джоб; необязательно перед
#    демо-скриптами — каждый из них сам делает TRUNCATE + свой seed,
#    этот шаг просто показывает, как выглядит таблица jobs с данными)
./scripts/seed.sh
# фолбэк, если exec-бит потерялся (например, после клонирования на файловой
# системе, не хранящей права Unix):
# bash scripts/seed.sh

# 3. запустить воркер вручную (по желанию, вне демо-скриптов)
cd worker && go run . -id w1 -work 2s -lease 5s
# go run . -id w1 -heartbeat=false   # без продления аренды (артефакт 2)
# go run . -reclaim                  # только вернуть истёкшие аренды
# go run . -id w1 -mode listen       # пробуждение по NOTIFY (артефакт 8)
cd ..

# 3а. запустить планировщик вручную (по желанию, вне scheduler-demo.sh) —
#     ensureTickLog (scheduler/main.go) сам создаёт tick_log при первом
#     запуске, поэтому реплику можно поднимать и по одной, без demo-скрипта
cd scheduler && go run . -id s1 -every 500ms -for 5s
# go run . -id s1 -every 500ms -for 5s -lock=false   # без координации (артефакт 9, падающий вариант)
cd ..

# 4. прогнать демонстрации по очереди (каждая сама пересобирает нужный
#    бинарник и делает TRUNCATE jobs — см. предупреждение о параллельности выше)
./scripts/lease-demo.sh        # артефакты 1–2: смерть воркера, heartbeat
./scripts/shutdown-demo.sh     # артефакт 3: graceful shutdown (SIGTERM)
./scripts/skip-locked-demo.sh  # артефакт 6: SKIP LOCKED vs FOR UPDATE
./scripts/notify-demo.sh       # артефакт 8: LISTEN/NOTIFY vs polling
./scripts/bloat-demo.sh        # артефакт 7: MVCC bloat от очереди
./scripts/scheduler-demo.sh    # артефакт 9 (доп. к спеке): advisory-лок
./scripts/throughput-demo.sh   # артефакт 10 (доп. к спеке): потолок джоб/сек
                               #   — идёт МИНУТЫ (4 значения N × 5 повторов)
./scripts/groupcommit-demo.sh  # артефакт 11 (доп. к спеке): сколько коммитов
                               #   едет на одном сбросе журнала — объясняет
                               #   форму кривой из артефакта 10, идёт ~5 минут
cd river && go run .           # River — готовая очередь как контраст
```

Для всех Go-команд в WSL2 выставляйте `GOPROXY=https://go.khorost.tech,direct`
(демо-скрипты делают это сами внутри себя).

## K8s-часть: артефакты 4 и 5

Демонстрации в `k8s/` показывают семантику **планировщика Kubernetes**
(`concurrencyPolicy`, `startingDeadlineSeconds`), а не наш код. PostgreSQL им
не нужен, compose поднимать не надо.

```bash
./k8s/concurrency-demo.sh   # артефакт 4: Allow / Forbid / Replace при перекрытии
                            #   — около 5 минут
./k8s/deadline-demo.sh      # артефакт 5: пропущенные срабатывания и дедлайн догона
                            #   — около 8-10 минут (в т.ч. 3 минуты паузы расписания)
```

Оба скрипта сами создают namespace `bj-cron`, работают только в нём и удаляют
его через `trap` — в том числе при прерывании.

### ⚠️ Кластер задаётся явно, и это не формальность

Скрипты **не используют** контекст из `~/.kube/config`. Путь к kubeconfig
берётся из переменной `KVOL_KUBECONFIG` (по умолчанию — тестовый кластер
автора), и дополнительно проверяется, что кластер именно тестовый: имена всех
узлов обязаны начинаться с `k8s-volga-`. Не совпало — скрипт падает с
ненулевым кодом **до** создания чего-либо.

Причина: в окружении автора голый `kubectl` бьёт в **боевой** кластер, потому
что `KUBECONFIG` не выставлен, а в `~/.kube/config` лежит единственный
контекст — продовый. Скрипт, создающий и удаляющий namespace, запущенный там
по ошибке, — недопустим.

Если воспроизводите у себя, поменяйте префикс проверки имён узлов на свой
(переменная в начале каждого скрипта) — **не убирайте саму проверку**.

```bash
KVOL_KUBECONFIG=/путь/к/вашему/kubeconfig ./k8s/concurrency-demo.sh
```

### Что нужно от кластера

Ничего особенного: рабочий CronJob-контроллер, доступ к Docker Hub за
`busybox:1.37` и права на создание namespace, CronJob и Job. Снималось на
Kubernetes v1.36.2 / Talos v1.13.6, 3 control-plane + 3 worker — но артефакты
от размера кластера не зависят, хватило бы и одного узла.

Расписания идут по **UTC**: `.spec.timeZone` в манифестах не задан. Учитывайте
при чтении времён в выводе.

### Известные особенности отдельных скриптов

- **`bloat-demo.sh`** на время демонстрации выключает `autovacuum` на
  таблице `jobs` (`ALTER TABLE jobs SET (autovacuum_enabled = off)`) — иначе
  автовакуум мог бы подчистить мёртвые версии строк до того, как скрипт их
  измерит. Настройка возвращается обратно (`RESET`) через `trap` в конце
  скрипта, в том числе при прерывании `SIGTERM` посреди прогона — но если
  процесс убить `SIGKILL` (`kill -9`), `trap` не сработает и `autovacuum`
  останется выключенным на этой таблице. В этом случае включите вручную:
  `docker exec bj-postgres psql -U jobs -d jobs -c "ALTER TABLE jobs RESET (autovacuum_enabled)"`.
- **`scheduler-demo.sh`** пересоздаёт таблицу `tick_log` (`DROP TABLE IF
  EXISTS` + `CREATE TABLE`) дважды за один прогон — перед рабочим вариантом
  (лок включён) и перед падающим (лок выключен), — а в конце удаляет её
  через `trap`. Таблица намеренно без `UNIQUE(slot)` в обеих ветках: см.
  `FIXTURES.md`, почему такое ограничение сделало бы демонстрацию
  бессмысленной.
- **`throughput-demo.sh`** в разведочной секции временно переключает
  `synchronous_commit` в `off` — и делает это через `ALTER SYSTEM`, то есть
  **глобально для всего сервера**, а не для одной таблицы. Настройка
  возвращается в `on` явно в конце секции и ещё раз через `trap`, но при
  `SIGKILL` (`kill -9`) `trap` не сработает, и сервер останется с выключенным
  ожиданием записи WAL на диск. Это опаснее, чем оставшийся выключенным
  `autovacuum` у `bloat-demo.sh`: следующие замеры на стенде тихо покажут
  завышенную пропускную способность, ничем себя не выдав. Проверить и
  вернуть:
  `docker exec bj-postgres psql -U jobs -d jobs -c "SHOW synchronous_commit"` и,
  если там `off`,
  `docker exec bj-postgres psql -U jobs -d jobs -c "ALTER SYSTEM RESET synchronous_commit" -c "SELECT pg_reload_conf()"`.
- Как и `bloat-demo.sh`, остальные demo-скрипты гасят свои фоновые процессы
  через `trap` при прерывании, но не восстанавливают состояние таблицы
  `jobs` — она общая для всей серии, и после любого прогона в ней может
  остаться от одной до нескольких строк.

## Тесты

```bash
cd worker && go test ./... -count=1
```

Интеграционные тесты требуют живого PostgreSQL (`bj-postgres` на 5456) и
падают явно, если он недоступен — пропуск только через явный
`BJ_SKIP_INTEGRATION=1`, тихого `t.Skipf` без него нет.
