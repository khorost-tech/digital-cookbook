# Стенд schema-migrators

Пять миграторов схемы против трёх СУБД с PostgreSQL-протоколом — к статье
[«Мигратор схемы: на чём он стоит и что ломается вне ванильного PostgreSQL»](https://khorost.tech/architecture/schema-migrators-across-databases/).

Стенд отвечает на один вопрос: **что требует от базы сам мигратор** — до того, как
дело дойдёт до ваших миграций. Миграции здесь нарочно тривиальны (создать таблицу,
добавить колонку, откатить), поэтому любой отказ — это отказ инструмента, а не SQL.

Всё, что попало в статью, — в [`FIXTURES.md`](FIXTURES.md) и в `fixtures/` вместе с
командой, давшей каждый вывод.

## Состав

| Инструмент | Версия | Подход |
|---|---|---|
| goose | v3.28.0 (собирается из исходников) | версионированные SQL-файлы |
| Flyway | 13.9.0, OSS Edition | версионированные SQL-файлы |
| Liquibase | 5.0.4 + JDBC-драйвер PostgreSQL через `lpm` | changelog (formatted SQL) |
| Atlas | 1.3.3, community build | версионированные файлы; инспекция схемы |
| Alembic | 1.20.0, SQLAlchemy 2.1.3, psycopg 3.3.6 | Python-ревизии; autogenerate |

| СУБД | Версия | Роль |
|---|---|---|
| PostgreSQL | 18.4 | контроль: здесь всё обязано работать |
| CockroachDB | v26.2.5, один узел | средний случай: PG-протокол, своё ядро и своя семантика DDL |
| Picodata | 26.1.3, один инстанс | дальний случай: PG-протокол поверх Tarantool и sbroad |

CockroachDB и Picodata подняты **одним узлом**: журнал версий, DDL и системные
каталоги, на которые опираются миграторы, от числа узлов не зависят.
`start-single-node` у CockroachDB к тому же не требует лицензионного ключа.

## Требования

Docker с compose. Около 2 ГБ памяти. Порты хоста не публикуются — всё ходит
внутри сети `smig`.

## Как запускать

```bash
bash scripts/up.sh            # сеть, образы инструментов, PostgreSQL и CockroachDB
bash scripts/control.sh       # контрольная проба: невалидная миграция обязана упасть
bash scripts/run.sh goose pico                     # одна ячейка матрицы
for e in pg crdb pico; do for t in goose flyway liquibase atlas alembic; do
    bash scripts/run.sh $t $e; done; done          # вся матрица
python3 scripts/report.py     # fixtures/matrix.md
bash scripts/probe.sh         # версии СУБД и инструментов
bash scripts/workarounds.sh   # обходные пути для отказов на CockroachDB
bash scripts/partial.sh       # миграция падает на середине: схема, журнал, повтор
bash scripts/recover.sh       # восстановление на CockroachDB: Liquibase и Flyway
bash scripts/down.sh
```

## Методика

- **Шаги одинаковые для всех:** `apply1` (CREATE TABLE probe), `journal` (появился
  ли собственный журнал версий инструмента), `apply2` (ADD COLUMN note),
  `introspect` (Alembic — `check`, сравнение схемы с моделью; Atlas — `schema inspect`,
  инспекция: проверяется лишь, что найдены таблица и колонка, а не эквивалентность
  схем), `rollback`.
- **Исход шага — не код возврата.** После каждого шага состояние базы проверяется
  отдельным SQL-запросом; исход — пара «что сказал инструмент + что в базе»:
  `ok`, `fail`, `false-ok` (сказал «готово», изменения нет), `applied-err` (сказал
  «ошибка», изменение есть), `edition` (функции нет в бесплатной редакции или
  открытой сборке), `no-pre` (сравнивать или откатывать нечего), `n/a`.
- **Контрольная проба.** Перед замерами каждый инструмент получает заведомо
  невалидную миграцию на PostgreSQL. Инструмент, вернувший на ней успех, к
  замерам не допускается.
- **Чистая база на каждый инструмент.** У PostgreSQL и CockroachDB — своя база,
  Picodata пересоздаётся целиком.
- Матрица фиксирует поведение **из коробки**: штатные образы, штатные драйверы,
  диалект `postgresql` у SQLAlchemy. Обходные пути — отдельно, в `workarounds.sh`.

## Чего стенд не делает

- Не меряет скорость применения миграций.
- Не проверяет платные редакции (Flyway Teams/Enterprise, Atlas Pro, Liquibase
  Secure): только бесплатные поставки и их сообщения об отказе.
- Не проверяет блокировку от параллельного применения с нескольких реплик.
- «Прошли» в матрице значит: успешные операции и обратный DDL дали ожидаемое
  состояние. Поведение при сбое на середине миграции — отдельно, в `partial.sh`.
