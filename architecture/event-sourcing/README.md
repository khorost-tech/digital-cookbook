# Event Sourcing на практике — стенд

Живой стенд к статье [«Event Sourcing на практике»](https://khorost.tech/architecture/event-sourcing-in-practice/)
и к серии **event-sourcing-deep-dive** на [khorost.tech](https://khorost.tech).

Postgres как event store: append с оптимистичной блокировкой, async-проектор баланса,
снапшоты, blue-green rebuild проекции. Всё — с ассертами (расхождение = `log.Fatalf`).

Домен нарочно узкий: **учёт кислорода в резервуарах лунной базы**. Один поток событий
(stream) = один резервуар. События (`TankRegistered` / `OxygenAdded` / `OxygenConsumed`)
неизменяемы, только append; текущий баланс — свёртка событий.

## Что демонстрирует

1. **Схема event store.** Таблица `events(stream_id, version, event_type, schema_ver, data jsonb,
   metadata jsonb, created_at, global_pos bigserial, PRIMARY KEY(stream_id, version))` + индекс по
   `global_pos`. Именно `PRIMARY KEY(stream_id, version)` даёт оптимистичную блокировку — без
   строковых локов и `SELECT ... FOR UPDATE`.
2. **Append с ожидаемой версией.** Команда несёт expected version; событие пишется с
   `version = expected + 1`. Конфликт по PK (`SQLSTATE 23505`) → «кто-то опередил» → перечитать/повторить.
   Стенд **реально провоцирует конфликт**: две горутины пишут `version=N` в один стрим — одна
   коммитится, вторая падает на PK.
3. **Async-проектор баланса.** Читает события по `global_pos` после чекпоинта, **идемпотентно**
   применяет (UPSERT в `balances` с guard `version = $ − 1`), сохраняет чекпоинт **в той же
   транзакции**. Первый экземпляр «падает» на середине, второй продолжает с чекпоинта — без потерь
   и дублей.
4. **Снапшоты.** Каждые N версий сохраняется снимок агрегата в `snapshots`. Загрузка агрегата =
   последний снапшот + хвост событий после него (а не реплей всей истории).
5. **Blue-green rebuild.** Новая проекция `balances_v2` собирается реплеем всей истории с
   `global_pos = 0`, не останавливая онлайн-проектор `balances`, затем атомарно переключается через
   транзакционный `RENAME`.
6. **Ассерты:** свёртка событий == проекция; конфликт версий реально происходит (ровно 1);
   проекция после rebuild == онлайн-проекции; агрегат из снапшота == полная свёртка.

## Структура

```
event-sourcing/
  compose/compose.yml     # Postgres 16, host-порт 5452, container es-postgres
  go/                     # основной стенд (полный сценарий 1–6)
    schema.go             # DDL event store и read-моделей
    store.go              # append с оптимистичной блокировкой, чтение стримов/по global_pos
    aggregate.go          # агрегат Tank + свёртка (fold) событий
    projector.go          # async-проектор: батч, чекпоинт-в-транзакции, идемпотентный UPSERT
    snapshot.go           # снапшоты + загрузка «снапшот + хвост»
    rebuild.go            # blue-green rebuild balances_v2 + атомарный swap
    main.go               # сценарий и ассерты
  java/                   # урезанный сценарий (append+optimistic+проектор) на чистом JDBC
```

Порт хоста **5452** выбран свободным на момент создания стенда — в репозитории уже заняты
5432/5433/5440/5441/5442/5450. При конфликте на другой машине поменяйте левую часть проброса в
`compose/compose.yml` и `DATABASE_URL`.

## Как поднять и прогнать

```bash
# 1. Postgres 16
docker compose -f event-sourcing/compose/compose.yml up -d      # ждать healthy
docker compose -f event-sourcing/compose/compose.yml ps

# 2. Go-стенд (полный сценарий)
cd event-sourcing/go
go build ./... && go vet ./...
go run .                                                        # localhost:5452

# 3. Java-стенд (урезанный сценарий) — опционально
cd ../java
mvn -q compile exec:java -Dexec.mainClass=tech.khorost.eventsourcing.Main

# снести
docker compose -f event-sourcing/compose/compose.yml down -v
```

Собственного Go/Maven-тулчейна на хосте не требуется — можно гонять контейнерами
(`golang:1.25`, `maven:3.9-eclipse-temurin-21`) на сети `es-cookbook_default`, передав
`DATABASE_URL` на сервис `es-postgres:5432`. Именно так стенд и проверялся: на машине сборки
host-проброс порта 5452 подтормаживал (особенность Docker Desktop/WSL), а из контейнера на общей
сети всё отработало без нареканий. С обычным рабочим host-пробросом достаточно `go run .`.

> Go-стенд и Java-стенд пересоздают схему при старте (`DROP … CREATE`), поэтому их можно
> перезапускать сколько угодно; но гонять их одновременно на одной БД не нужно — они делят
> таблицы `events`/`balances`.
