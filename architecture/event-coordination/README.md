# Хореография vs оркестрация — стенд

Живой стенд к статье [«Хореография vs оркестрация»](https://khorost.tech/architecture/choreography-vs-orchestration/)
на [khorost.tech](https://khorost.tech).

Один и тот же бизнес-сценарий — **оформить заказ** (оплата → резерв товара →
создание доставки → уведомление клиента) — реализован **двумя способами
координации**, чтобы наглядно увидеть контраст «где виден весь поток».

## Что демонстрирует

- **Оркестрация** — Temporal workflow (`go/orchestration.go`). Явный сценарий в
  ОДНОМ месте: шаги идут по порядку в функции `OrderWorkflow`, при ошибке —
  явная обработка (`return err`, а Temporal сам ретраит activity по политике).
  Весь поток читается сверху вниз в одной функции; состояние каждого заказа
  видно в Temporal UI (http://localhost:8233) по workflow ID.

- **Хореография** — сервисы реагируют на события через **in-process event-bus**
  (`go/choreography.go`) — простой pub/sub на подписках, **без внешнего
  брокера**, чтобы стенд был самодостаточным. `OrderPlaced`→оплата,
  `PaymentTaken`→резерв, `StockReserved`→доставка, `ShipmentCreated`→уведомление.
  Единого сценария нет НИГДЕ — порядок эмерджентный, складывается из того, кто на
  что подписан.

Оба варианта используют **одну и ту же бизнес-логику** шагов (функции `do*` в
`go/main.go`) — отличается только координация. Программа печатает оба прогона и
короткое резюме контраста по трём осям:

1. **Где виден весь поток** — в оркестрации собран в `OrderWorkflow`; в
   хореографии размазан по четырём независимым подпискам, восстанавливается
   только по логу «кто на что отреагировал».
2. **Как добавить шаг** — в оркестрации правка одного файла (вставить
   `ExecuteActivity`); в хореографии новая подписка + новое событие в нескольких
   местах.
3. **Отладка «на каком шаге застрял заказ»** — в оркестрации видно в состоянии
   workflow и в Temporal UI; в хореографии единого состояния нет, надо обойти
   подписчиков.

Ассерты (падают при расхождении): оба варианта доводят заказ до конца и дают
**идентичный итог** — разная только точка наблюдаемости.

> **Java намеренно не делается.** Go самодостаточно показывает контраст обоих
> стилей координации в одном бинаре; второй язык здесь ничего не добавил бы к
> сути сравнения (в отличие от стендов, где важна разница клиентов, как в
> `kafka/`).

## Версии (сверено живьём 2026-07-08)

| Компонент | Версия | Как проверено |
|---|---|---|
| Temporal (образ CLI) | `temporalio/temporal:1.7.2` | `docker pull` + `--version`: `temporal version 1.7.2 (Server 1.31.1, UI 2.49.1)`. Тег `1.7.2` = `latest` на дату (одинаковый digest). |
| Temporal Go SDK | `go.temporal.io/sdk v1.46.0` | `go get go.temporal.io/sdk@latest` → `go.mod` |
| Go | `1.25.4` (`go.mod`), сборка образом `golang:1.25` (`go1.25.12`) | минимальная версия из `go.mod`; собственного Go-тулчейна на хосте не требуется |

Dev-сервер Temporal (`server start-dev`) держит всё в памяти — ни Postgres, ни
Elasticsearch не нужно.

## Как поднять и запустить

```bash
# 1. Поднять Temporal dev-сервер (gRPC :7233, web-UI :8233)
docker compose -f compose/compose.yml up -d
docker compose -f compose/compose.yml ps        # дождаться "healthy"

# 2. Запустить оба сценария подряд
cd go
go run . -mode=both            # оба (по умолчанию)
go run . -mode=orchestration   # только Temporal
go run . -mode=choreography    # только event-bus (Temporal не нужен)

# 3. Снести
docker compose -f compose/compose.yml down
```

Флаг `-temporal=<host:port>` переопределяет адрес frontend (по умолчанию
`localhost:7233`).

Собственного Go-тулчейна на хосте можно не иметь — модуль собирается образом
`golang:1.25`. Прогон **оркестрации** из контейнера на сети compose (адрес
Temporal — по имени сервиса, `temporal:7233`):

```bash
docker run --rm --network compose_default \
  -v "$(pwd)/go:/app" -w /app -e GOFLAGS=-mod=mod golang:1.25 \
  sh -c "go run . -mode=both -temporal=temporal:7233"
```

> **Про доступ с хоста Windows.** В этом окружении (как и в `kafka/`)
> подключение локально собранного Go-бинаря к опубликованному `localhost:7233`
> временами блокируется на уровне ОС/файрвола — сам порт открыт, `docker exec`
> и CLI из контейнера-соседа работают. Надёжный способ прогнать оркестрацию —
> из контейнера на compose-сети (команда выше). Хореография от Temporal не
> зависит и запускается локально всегда: `go run . -mode=choreography`.
>
> `-mode=orchestration`/`both` требует поднятого Temporal; при недоступности
> сервера программа печатает понятную ошибку и подсказку и выходит с кодом 1.

## Temporal UI

http://localhost:8233 — после прогона оркестрации там виден workflow
`order-1001`: статус `Completed`, история всех четырёх activity
(`TakePayment` → `ReserveStock` → `CreateShipment` → `NotifyCustomer`) с
их входами/выходами. Это и есть иллюстрация к «отладке застрявшего заказа»:
единая точка наблюдаемости, которой у хореографии нет.

выше). Итог у обоих идентичен байт-в-байт — разная только наблюдаемость.

## Структура

```
event-coordination/
  compose/compose.yml   # Temporal dev-сервер (server start-dev), порты 7233/8233
  go/                   # module tech.khorost/event-coordination-cookbook
    go.mod
    go.sum
    main.go             # doc-заголовок, флаги, общий домен (Order, do*-шаги), резюме+ассерты
    worker.go           # подключение к Temporal, регистрация workflow+activities, воркер
    orchestration.go    # OrderWorkflow + 4 activities + runOrchestration
    choreography.go     # in-process event-bus (pub/sub) + 4 сервиса-подписчика + runChoreography
  README.md
  .gitignore
```
