# Disaster Recovery: автоматический restore-тест с замером факта восстановления

Стенд к статье [«Disaster Recovery: RTO/RPO»](https://khorost.tech/architecture/disaster-recovery-rto-rpo/)
(серия «System design: resilience»).

Главная мысль: **бэкап без проверки восстановления — не бэкап**. Стенд превращает это
в число — прогоняет реальную катастрофу и PITR-восстановление Postgres, проверяет
поднятые данные и меряет ФАКТ: сколько заняло восстановление и сколько данных
потерялось бы. RTO и RPO — это ЦЕЛИ, которые назначает бизнес; замер показывает,
укладываемся ли мы в них.

Это оркестрация Docker + Postgres (pg_basebackup, WAL-архив, `recovery_target_time`),
поэтому стенд на bash/compose, а не на Go: здесь нет алгоритма для юнит-теста —
ценность в том, что восстановление РЕАЛЬНО происходит и замерено.

## Запуск

```bash
bash restore-test.sh          # поднимает primary, ломает данные, восстанавливает, меряет
```

Нужен Docker. Скрипт самодостаточен (свой `docker-compose.yml`), за собой убирает
(включая тома) и рассчитан на **повторные** запуски — прогоняется подряд без ручной чистки.

## Что делает

1. Поднимает primary Postgres с непрерывным архивированием WAL (`archive_mode=on`).
2. Кладёт 100 заказов и делает **полный бэкап** (`pg_basebackup -X stream`).
3. Дописывает ещё 50 заказов — они живут **только в WAL** (после бэкапа).
4. **Катастрофа**: `DROP TABLE orders` (человеческая ошибка / шифровальщик).
5. **Restore-тест**: поднимает отдельный инстанс из бэкапа + WAL-архива с
   `recovery_target_time` на точку перед катастрофой, ждёт промоута — и засекает время.
6. **Проверяет** (иначе весь смысл теряется): таблица поднята, `DROP` отменён, все
   150 заказов на месте, инстанс вышел из recovery. Не сошлось — тест падает.

## Замеренный итог (пример прогона)

```
таблица поднята, DROP отменён, все 150 заказов на месте, инстанс промоутнут
  фактическое время восстановления: 6.6 с   <- сравнивать с целевым RTO; машинозависимо
  достигнутая точка восстановления: момент перед катастрофой
  фактическая потеря данных с PITR:            0 заказов
  фактическая потеря, будь только полный бэкап: 50 заказов
```

- **Фактическое время восстановления** — вся процедура: достать бэкап, подготовить
  recovery-конфиг, поднять инстанс, проиграть журнал, дождаться промоута. Это ФАКТ,
  который сравнивают с целевым RTO (RTO — цель бизнеса, а не результат замера).
- **Достигнутая точка восстановления и фактическая потеря** — PITR доводит точку до
  момента перед катастрофой, потеря **0** заказов; будь только полный бэкап без WAL,
  откатились бы к нему и потеряли **50**. Целевой RPO — это отдельная величина,
  которую назначает бизнес; замер показывает, укладываемся ли мы в неё.

## Подводные камни (решены в скрипте)

- **И data-dir, и WAL-архив — named Docker volumes**, не host-bind. Postgres требует
  unix-овнершип на каталоге данных, а bind на Windows/WSL его не держит. С архивом
  вышло ещё показательнее: сперва он был host-bind и postgres не мог туда писать
  (archive_command падал МОЛЧА, архив пуст, PITR не доходил до цели), а после chown
  каталог на хосте оставался с чужим владельцем и режимом 0700 — и ПОВТОРНЫЙ запуск
  падал на «Permission denied». Named volume снимает оба вопроса, а `down -v` в
  cleanup даёт чистый старт каждому прогону.
- **Чистим архив перед прогоном**: `archive_command` вида `test ! -f … && cp` залипает
  навсегда на уже существующем сегменте (exit 1, ретрай каждые ~60с) — сегменты прошлых
  сессий не дают заархивироваться свежим.
- **Staging базового бэкапа через `docker cp` + разворачивание внутри контейнера**
  (`cp -a … && chown && gosu postgres`): `docker cp` контейнер→контейнер не умеет,
  а флэттен на Git Bash теряет трейлинг-точку (MSYS). Разворачивает CMD контейнера.
- **`pg_switch_wal()` после катастрофы** — форсирует архивацию сегмента со всеми
  коммитами, иначе последний сегмент не доедет до архива и RPO вырастет.

## Границы стенда

Это про **восстановление после катастрофы** (RTO/RPO, restore-тест), не про HA
(переживание отказа узла без простоя) и не про предохранители под нагрузкой
(`../patterns`, `../ratelimit`, `../backpressure`). Механику самого PITR подробнее
разбирает стенд `databases/wal/pitr`; здесь акцент — на дисциплине проверки и цифрах.

## Версии

| | |
|---|---|
| Postgres | 18.4 |
| бэкап | pg_basebackup -X stream |
| восстановление | recovery_target_time (PITR), promote |

Прогон на Windows 11 + Docker 29.6.1; машинозависимо ФАКТИЧЕСКОЕ время восстановления
(целевой RTO — величина из договорённости, она от машины не зависит). `shellcheck` не прогонялся
(недоступен в окружении); скрипт под `set -euo pipefail` и проверен сквозным прогоном.
