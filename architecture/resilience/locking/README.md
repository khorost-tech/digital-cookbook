# Распределённые блокировки: почему TTL-лок не защищает без fencing

Стенд к статье [«Распределённые блокировки и координация»](https://khorost.tech/architecture/distributed-locking-coordination/)
(серия «System design: resilience»).

Главная мысль (сценарий Клеппманна): распределённый лок с TTL сам по себе не даёт
безопасности. Владелец может «уснуть» (долгая GC-пауза, сетевая задержка) дольше TTL —
лок перейдёт к другому, и **двое** будут считать, что держат его. Защищает не лок, а
**fencing-токен** на стороне ресурса: монотонный номер, ниже которого ресурс запись
отвергает. Стенд воспроизводит и порчу, и защиту.

## Запуск

```bash
go test ./...                     # детерминированное ядро (fencing), без Docker
go run ./cmd/paused-owner         # порча без fencing vs защита с fencing
go test -tags integration ./...   # Redis-лок и etcd-выборы (нужен Docker)
golangci-lint run ./...           # чисто, в т.ч. --build-tags integration
```

## Что показывает стенд

### 1. Сценарий «уснувшего владельца» (детерминированно)

`cmd/paused-owner` и `fence_test.go` проигрывают одно и то же:
A берёт лок (токен 1) и засыпает → TTL истекает → B берёт лок (токен 2) и пишет →
A просыпается и пишет со старым токеном 1.

| ресурс | итог |
|---|---|
| **без fencing** | `A-stale` — свежие данные B **затёрты** (порча) |
| **с fencing** | `B-data` — запись A с токеном 1 **отвергнута** (`ErrStaleToken`) |

Разница не в локе, а в том, проверяет ли ресурс токен. Это ядро — без времени и
гонок (детерминированные тесты, `-race` чист).

### 2. Redis: атомарная выдача токена — и почему без неё защита не работает

`redislock_test.go` (Docker): A берёт лок с TTL 200мс и токен (`INCR`=1), «спит»;
через 500мс TTL истёк — B берёт освободившийся лок и токен (`INCR`=2). Оба несут
токен к ресурсу: **A(токен 1) и B(токен 2) — двойное владение**, но fencing отвергает
запоздавшую запись A. `Unlock` снимает только свой лок (атомарный Lua-скрипт со
сравнением владельца) — чужой не тронет.

**Токен обязан выдаваться АТОМАРНО с локом.** На стенде два варианта:

- `AcquireWithToken` — правильный: один Lua-скрипт ставит лок и выдаёт токен;
- `AcquireThenTokenUnsafe` — намеренно небезопасный, оставлен для демонстрации.
  Тест `TestUnsafeTokenIssuanceCorrupts` воспроизводит порчу: A берёт лок, засыпает
  ДО получения токена, TTL истекает, B берёт лок с токеном и пишет; A просыпается,
  получает токен БОЛЬШЕ и затирает данные B, уже не владея локом.

**Границы гарантии Lua.** Скрипт исполняется изолированно, но отката нет: если вторая
команда упадёт, первая уже применена. Поэтому `INCR` вызывается через `pcall`, и при
ошибке (счётчик занят нечисловым значением) скрипт сам снимает только что поставленный
лок — иначе вызывающий получил бы ошибку, а ресурс остался бы занят до TTL
(`TestFenceCounterErrorLeavesNoLock`).

**Проверять надо не только ошибку `INCR`, но и его РЕЗУЛЬТАТ.** Счётчик может быть
испорчен отрицательным числом, и тогда команда отработает штатно, вернув мусор:

| счётчик | `INCR` вернёт | что было бы без проверки |
|---|---|---|
| `-1` | `0` | ноль означает «лок занят» — вызывающий решит, что захвата не было, хотя лок поставлен и провисит до TTL |
| `-2` | `-1` | приведение к `uint64` даст максимальный токен, и он НАВСЕГДА отравит ресурс: любой следующий честный токен окажется меньше и будет отвергнут как устаревший |

Поэтому неположительный результат считается повреждением: скрипт откатывает собственный
`INCR` через `DECR` (чтобы повторные попытки не «дотикали» счётчик до положительного и
не замаскировали проблему), снимает лок и возвращает ошибку — `TestFenceCounterNonPositive`
проверяет оба значения, отсутствие лока и неизменность счётчика после повторов.

**Идентификатор захвата обязан быть уникальным.** `Acquire`/`Release` генерируют его
случайно внутри — стабильное имя (хост, pid, `worker-1`) не годится: воркер взял лок,
TTL истёк, тот же воркер взял заново — и запоздавший `Release` от первого захвата
снял бы второй, живой лок (`TestStaleUnlockCannotDeleteReacquiredLock`).

**Redis Cluster.** Оба ключа одного скрипта обязаны лежать в одном слоте, иначе
CROSSSLOT. Ключи строит `NewLock(rdb, resource)` — сам, с общим hash tag. Пустое имя
и имена со своими скобками отвергаются: пустой тег `{}` Redis игнорирует, и `{}:lock`
с `{}:fence` уезжают в РАЗНЫЕ слоты. Тест считает слот по CRC16, как это делает Redis,
а не сверяет префикс строки.

Вывод стенда, не приговор Redlock: показан **конкретный failure mode** TTL-лока и то,
что монотонный токен (здесь — `INCR`) его закрывает.

### 3. etcd: выборы лидера + revision как готовый fencing-токен

`etcdlock_test.go` (Docker): корректный примитив вместо самодельного. Два кандидата
по очереди выигрывают выборы (`concurrency.Election`); revision ключа лидера растёт
монотонно и служит fencing-токеном даром:

```
c1 revision=2 → c2 (после resign c1) revision=4
```

etcd даёт lease с TTL (лидерство отваливается вместе с сессией) и глобально монотонную
revision — то, что в Redis приходится собирать вручную из `INCR`.

## Замечания

- Ядро (fencing) детерминировано; интеграция под тегом `integration` (Docker),
  по умолчанию `go test` быстрый и без контейнеров.
- В интеграции есть один реальный `sleep` — истечение TTL по своей природе про время;
  взят с запасом (TTL 200мс, ожидание 500мс), чтобы не был flaky.
- Границы стенда: это про **координацию и безопасность лока**, не про rate limiting
  (`../ratelimit`) и не про предохранители (`../patterns`). Часто верный ответ —
  спроектировать так, чтобы блокировка была не нужна (идемпотентность, оптимистичная
  блокировка): об этом статья, стенд же показывает, чем лок опасен, если он всё же нужен.
