# backpressure — самозащита под перегрузом на живом стенде

Примеры к статье **«Backpressure и load shedding»** на [khorost.tech](https://khorost.tech).
Чистый Go, без docker. Один модуль `tech.khorost/backpressure-cookbook`, три пакета-механизма и два демо-нагрузчика.

Идея стенда: **корректные механизмы самозащиты покрыты тестами**, которые проходят под `-race` и `goleak`; **эффект под перегрузом показывают запускаемые демо** `cmd/*`, считающие метрики в рантайме. Никаких «зашитых» чисел — абсолютные значения зависят от машины, снимайте их своим прогоном.

## Запуск

    # весь модуль: сборка, vet, тесты
    go build ./...
    go vet ./...
    go test ./...

    # с детектором гонок (нужен C-компилятор; на Windows без gcc — через контейнер)
    docker run --rm -e CGO_ENABLED=1 -v "$PWD":/src -w /src golang:1.26 go test -race ./...

    # демо-нагрузчики (числа у себя — они зависят от машины)
    go run ./cmd/unbounded-vs-bounded
    go run ./cmd/adaptive-vs-static

## Что где

| Пакет | Что демонстрирует |
|---|---|
| [`boundedqueue/`](boundedqueue) | Ограниченная очередь `BoundedQueue[T]` с четырьмя политиками переполнения: `Block` (backpressure — отправитель ждёт через ctx), `DropNewest`/`DropOldest` (сброс нагрузки), `Reject` (быстрый отказ, аналог 503). API `Offer(ctx, item) bool` / `Take(ctx)`. Счётчики `Accepted`/`Dropped`. |
| [`loadshedding/`](loadshedding) | Неблокирующий приём `Shedder.Submit` через `select { case q<-req: default: reject() }` + сигнал насыщения по длине очереди (`Saturated`) и сглаженной латентности (`EWMA`). Воркеры дренируют очередь; при `Stop` принятое доигрывается. |
| [`adaptive/`](adaptive) | Адаптивный лимитер параллелизма `Limiter` по схеме AIMD: латентность выше порога → лимит снижается мультипликативно, норма → растёт аддитивно. `Acquire`/`Release(sample)` в духе `semaphore.Weighted` — ctx-aware, без фоновых горутин и утечек. |
| [`cmd/unbounded-vs-bounded/`](cmd/unbounded-vs-bounded) | Нагрузчик: генератор быстрее потребителя. Сравнивает неограниченную очередь и `boundedqueue` с `Reject`. Печатает принято/отброшено, пик длины очереди, p50/p99 латентности обработки. |
| [`cmd/adaptive-vs-static/`](cmd/adaptive-vs-static) | Зависимость с меняющейся во времени пропускной способностью (фазы быстро → медленно → быстро). Сравнивает адаптивный лимит со статическим: печатает выполнено, req/s, avg/p99 латентности, долю перегруженных вызовов, финальный лимит. |

## Тесты: что проверяется

- `boundedqueue` — каждая политика ведёт себя как заявлено: при полной очереди `Block` ждёт и разблокируется по `Take`/отмене ctx, `DropNewest` отбрасывает новый, `DropOldest` вытесняет старый и принимает новый, `Reject` отклоняет немедленно; счётчики `Accepted`/`Dropped` точны, в т.ч. под конкурентной нагрузкой.
- `loadshedding` — под перегрузом доля отклонений растёт с нагрузкой, все принятые запросы обрабатываются (при `Stop` очередь дренируется), `EWMA` сходится к постоянному замеру и корректно реагирует на ступеньку.
- `adaptive` — на «медленных» замерах лимит снижается до `Min`, на «быстрых» восстанавливается до `Max`, не выходит за границы; `Acquire` блокируется под исчерпанным лимитом, уважает отмену ctx и пробуждается по `Release`. Замеры латентности синтетические — тест детерминирован, без пауз и реального времени.

Каждый пакет содержит `main_test.go` с единственным `TestMain` → `goleak.VerifyTestMain`: по завершении тестов проверяется отсутствие утечек горутин.

## Демо: что печатают (числа у себя)

Обе программы считают метрики в рантайме по собственным замерам. Пример вывода — иллюстративный, ваши числа будут другими (зависят от CPU, планировщика, разрешения таймера).

`cmd/unbounded-vs-bounded` — генератор ~3× быстрее потребителя. Неограниченная очередь принимает всё, но backlog и латентность обработки растут; ограниченная держит очередь короткой и латентность низкой, отклоняя избыток:

    unbounded              принято=1000  отброшено=0    пик очереди=636  p50=~1s      p99=~2s
    bounded+shed(cap=64)   принято~440   отброшено~560  пик очереди=64   p50=~210ms   p99=~215ms

`cmd/adaptive-vs-static` — зависимость проходит фазы 16→4→16. Статический лимит, выставленный под быструю фазу, в медленной раскачивает хвост латентности; адаптивный снижает лимит и держит p99 ниже ценой небольшой доли пропускной способности:

    static(lim=16)    выполнено~12000  ~4100 req/s  avg~3.2ms  p99~38ms  перегружено~3.4%  лимит=16
    adaptive[4..16]   выполнено~12000  ~4000 req/s  avg~2.4ms  p99~14ms  перегружено~3.2%  лимит=16

## Версии

Модуль объявляет `go 1.25.0`. Локально `go build ./...`, `go vet ./...`, `go test ./...` зелёные на **Go 1.26.3**; демо печатают реальные метрики. `go test -race ./...` — через контейнер **golang:1.26** (на машине автора нет C-компилятора, поэтому детектор гонок гоняется в контейнере).

Зависимости: только stdlib + `go.uber.org/goleak v1.3.0` (проверка утечек горутин в тестах).
