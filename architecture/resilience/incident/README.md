# Инцидент-процесс: шаблоны

Приложение к статье [«Инциденты и постмортемы»](https://khorost.tech/architecture/incident-response-postmortems/)
(серия «System design: resilience»).

Здесь нет кода — надёжность зрелой команды это не только предохранители, но и процесс.
Два готовых к присвоению шаблона:

- **[postmortem-template.md](postmortem-template.md)** — блеймлесс-постмортем: таймлайн,
  первопричины и способствующие факторы (система, а не человек), action items с
  владельцем и сроком, runbook. Заполняется после инцидента.
- **[error-budget-policy.md](error-budget-policy.md)** — пример политики error budget:
  SLO, severity, burn-rate алерты и правило заморозки релизов при исчерпании бюджета.

Как пользоваться: скопируйте под свой сервис, подставьте свои SLO/пороги/severity.
Смысл не в бланке, а в дисциплине — безобвинительный разбор (иначе прячут причины) и
заранее согласованное правило «когда чиним надёжность вместо фич».

Связанное: circuit breaker / retry / bulkhead — в стенде `../patterns`; сброс нагрузки —
`../backpressure`; восстановление после катастрофы — `../dr`. Этот артефакт — про
SRE-сторону: что происходит, когда предохранители всё же не удержали.
