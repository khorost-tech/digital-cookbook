# Resilience-паттерны: предохранители против каскадного отказа

Стенд к статье [«Resilience-паттерны»](https://khorost.tech/architecture/resilience-patterns/)
(серия «System design: resilience»).

Три механизма изолируют отказ, чтобы один медленный сервис не обрушил всё:

- `breaker/` — **circuit breaker** (closed/open/half-open), время инъектируется → переходы тестируются детерминированно;
- `retry/` — **backoff + полный джиттер + retry-бюджет** против retry-шторма;
- `bulkhead/` — **изоляция отсеков** (семафор на раздел): жадный потребитель не съедает общий пул.

## Запуск

```bash
go test ./...                  # детерминированные юнит-тесты механизмов
go run ./cmd/cascade           # каскадный отказ: без breaker vs с breaker (реальная нагрузка)
go run ./cmd/retrystorm        # усиление retry-шторма и его гашение бюджетом
golangci-lint run ./...        # чисто
```

## Что показывает стенд

### 1. Circuit breaker против каскадного отказа

`cmd/cascade`: зависимость «висит» (каждый вызов блокируется на 200мс и падает —
худший случай, не быстрый отказ). Сервис с пулом 20 воркеров; генератор подаёт
нагрузку в open-loop с ФАКТИЧЕСКИМ темпом около 1850 rps — номинальные 4000 из
`Sleep(250µs)` недостижимы, поэтому стенд темп меряет, а не декларирует.

| режим | отдано ответов | отклонено | ответов/с | p50 | p99 |
|---|---|---|---|---|---|
| **без breaker** | 120 | 1880 | ~99/с | 200мс | 201мс |
| **с breaker** | 1646 | 354 | ~1527/с | 0мс | 200мс |

Без предохранителя каждый запрос занимает воркера и висит на мёртвой зависимости;
воркеры кончаются, пул исчерпан, goodput упирается в `пул / латентность` (20/200мс ≈ 100/с),
остальное отклоняется. Breaker после серии отказов размыкает цепь — запросы мгновенно
уходят в fallback, не трогая зависимость и не держа воркеров: сервис продолжает
отвечать, p50 падает с 200мс до 0.

Две оговорки. «Ответов/с» здесь — это ответы-ЗАГЛУШКИ (fallback); полезность такого
ответа стенд не моделирует. И кратность машинозависима не меньше абсолютных чисел:
на другой машине тот же стенд даёт разницу вдвое-втрое меньше. Устойчив качественный
вывод (без предохранителя упираемся в пул, с ним — нет), разы снимайте своим прогоном.

### 2. Retry-шторм и retry-бюджет

`cmd/retrystorm` (детерминированно): зависимость лежит, 1000 запросов, наивно по 3 повтора.

| стратегия | ударов по зависимости | усиление |
|---|---|---|
| наивный повтор | 4000 | **×4.0** |
| с retry-бюджетом (0.1) | 1100 | **×1.10** |

Наивный повтор умножает нагрузку на лежащую зависимость вчетверо — и мешает ей встать
именно потому, что её добивают. Бюджет (доля повторов к обычному трафику, как retry
throttling в gRPC) ограничивает усиление до доли обычной нагрузки.

### 3. Bulkhead: изоляция отсеков

Отсеки с независимой ёмкостью. Заполненный отсек «heavy» возвращает `ErrFull`, но соседний
«light» не затронут — в общем пуле жадный потребитель забрал бы всё. Проверяется тестом
(`TestIsolation`), release идемпотентен (не крадёт чужой слот).

### 4. Джиттер и backoff

`retry/`: экспоненциальный backoff с потолком и «полный джиттер» — задержка равномерно в
`[0, backoff]`. Джиттер разносит одновременно упавших клиентов, чтобы они не ломились
повторно синхронно (проверяются расписание удвоения и границы джиттера).

## Замечания

- Механизмы (breaker/retry/bulkhead) тестируются детерминированно: время инъектируется,
  джиттер проверяется по границам, бюджет — по числам. Без сна и без гонок (`-race` чист).
- Демо (`cmd/*`) гоняют реальную нагрузку — абсолютные секунды/goodput зависят от машины.
- Границы стенда: backpressure/load shedding/adaptive concurrency — в соседнем `../backpressure`;
  распределённый лимит частоты — в `../ratelimit`. Здесь — предохранители от каскада.
- Retry-бюджет использует эпсилон в сравнении: `ratio` вроде 0.1 не сходится к целому
  сложением float (0.1×10 = 0.999…), и бюджет не должен терять токен на дрейфе.
