# Rate limiting: пять алгоритмов на одном интерфейсе + распределённый на Redis

Стенд к статье [«Rate limiting и throttling»](https://khorost.tech/architecture/rate-limiting-throttling/)
(серия «System design: resilience»).

Все алгоритмы реализуют один интерфейс `Limiter` с **явным временем** —
`AllowAt(now time.Time)`. Время не берётся из `time.Now()` внутри, а передаётся
снаружи, поэтому замеры детерминированы: «на стыке окон прошло 200 при лимите 100» —
воспроизводимый факт из теста, а не гонка с настенными часами.

## Запуск

```bash
go test ./...                              # детерминированное ядро, без Docker
go run ./cmd/measure                       # печатает таблицы ниже
go test -tags integration ./...            # распределённый лимит на Redis (нужен Docker)
golangci-lint run ./...                    # чисто, в т.ч. --build-tags integration
```

## Что показывает стенд

### 1. Стык окон: фиксированное окно пропускает 2× лимита

Лимит 100/сек. Шлём 100 запросов в конце одного окна (`+900ms`) и ещё 100 в начале
следующего (`+1000ms`) — всё внутри интервала в 100 мс:

| алгоритм | пропущено за стык |
|---|---|
| fixed-window | **200** (2× лимита) |
| sliding-log | 100 (= лимит) |
| sliding-counter | 100 (= лимит) |

Фиксированное окно выровнено по часам и обнуляет счётчик на границе — отсюда всплеск
вдвое. Скользящее окно (точное на метках или приближённое на двух счётчиках) держит
лимит в **любом** интервале длиной окна. Цена точного варианта — память: до `limit`
меток на ключ; приближённый счётчик — O(1), но на краю может ошибаться на доли лимита.

### 2. Форма всплеска: token пропускает burst, leaky сглаживает

10 запросов в один и тот же момент:

| алгоритм | пропущено разом |
|---|---|
| token bucket (ёмкость 5) | **5** — всплеск до ёмкости |
| leaky bucket (5/сек, строгий) | **1** — остальное сглажено в темп |

Token bucket копит токены и разрешает всплеск до размера ведра; дырявое ведро выдаёт
ровный поток `rate/сек`. Выбор между ними — это выбор «терпим ли короткие всплески».

### 3. Зачем распределённый лимит (Redis)

Три «инстанса» сервиса, общий лимит 100/сек, каждый шлёт 100 запросов разом:

| где считаем | пропущено |
|---|---|
| локально (у каждого своё ведро) | **300** — глобальный лимит нарушен втрое |
| общий ключ в Redis (Lua token bucket) | **100** — лимит соблюдён |

Локальные лимитеры не знают друг о друге, поэтому N инстансов пропускают N×лимит.
Общий счётчик в Redis (весь token bucket внутри атомарного Lua-скрипта) держит один
глобальный лимит — ценой round-trip к Redis (порядка ~1 мс/вызов; число машинозависимо).

**У общего лимита должен быть ОДИН источник времени.** Скрипт берёт время командой
`TIME` самого Redis, а не с часов инстанса. Почему это принципиально, показывает
`TestInstanceClockSkewBreaksSharedLimit`: вариант с часами инстанса
(`AllowWithInstanceClock`, оставлен намеренно) ломается при рассинхроне — запрос от
отставших часов сам не проходит, но сдвигает отметку `ts` назад, после чего следующий
запрос начисляет токены повторно и лимит пропускает вдвое больше. С `TIME` часы
инстансов на решение не влияют вовсе.

### 4. Корректный отказ

`Middleware` на отклонённом запросе отдаёт `429 Too Many Requests` и заголовок
`Retry-After` в секундах — честный отказ вместо тихой потери или зависшего коннекта.

## Замечания

- Всё детерминированное ядро тестируется без сна и без Docker — время инъектируется.
- Интеграционный тест под тегом `integration` (нужен Docker); по умолчанию `go test`
  быстрый и не тянет Redis.
- Границы стенда: adaptive concurrency и load shedding — в соседнем стенде
  `../backpressure`; защита L3/L4 (DDoS) — тема отдельной статьи. Здесь — прикладной
  лимит частоты запросов.
