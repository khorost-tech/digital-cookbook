# Стенд: веб-фреймворки — поведение по умолчанию

Стенд к статье серии «Поперёк языков» о веб-фреймворках. Двенадцать приложений — пары «минимальный —
полный» в шести экосистемах — реализуют один и тот же маленький API:

- `GET /items/{id}` — 200 и `{"id": …, "name": "item"}`;
- `POST /items` — тело `{"name": строка, обязательно; "qty": число}`, ответ 201;
- `GET /boom` — обработчик бросает исключение (паникует).

Контракт, по которому читаются результаты:

- `id` — десятичное целое, весь сегмент пути; `0` допустим, `1abc` — нет;
- `name` — обязательный ключ со строкой; пустая строка допустима;
- `qty` — целое число; строка (в том числе числовая, `"1"`) и дробь — ошибка клиента;
- тело — ровно один JSON-объект, остаток после него — ошибка клиента;
- ошибка клиента — 400 или 422, а не 201 и не 500.

Каждое приложение — короткий идиоматичный код **без библиотек сверх самого фреймворка**, как в его руководстве
для начала работы. Ответ — это поведение **фреймворка вместе с кодом примера**: где пример сам выбирает правило
(`binding:"required"` в Gin, `Integer.parseInt` в Javalin, обращение `item["name"]` во Flask), это сказано в статье.
У Javalin есть второй маршрут `/typed/items/{id}` со штатным `pathParamAsClass` — контроль того, что 500 даёт
выбранный в примере `parseInt`, а не сам фреймворк.

«Минимальный» и «полный» — рабочая классификация, а не мера качества: минимальный — роутер и разбор запроса,
остальное подключается отдельно; полный — сам несёт модель приложения (контейнер зависимостей, контроллеры или
модели данных, конвейер обработки запроса). HTTP-ответы стенда полноту не определяют — они показывают умолчания.

## Оси

| ось | вопрос |
|---|---|
| `control` | корректный POST — 201 и `name` в ответе, GET — 200 и `id` в ответе у всех: приложения работают по контракту |
| `routing` | DELETE на существующий путь (405 или 404, есть ли `Allow`), GET и POST со слэшем в конце (для перенаправления — `Location` и повтор POST по нему), id `abc`, `1abc`, `0`, неизвестный путь, штатный валидатор Javalin |
| `validation` | битый JSON, тело без обязательного поля, `name` пустой строкой, `qty` непреобразуемой строкой `"many"`, числовой строкой `"1"` и дробью `1.5`, мусор после JSON |
| `limits` | серия тел чуть ниже и чуть выше известных порогов (100 КБ, 1 000 000 байт, 2 МиБ, 30 000 000 байт) и 40 МиБ: принял ли **этот обработчик** тело такого размера. Ограничения JSON-парсера (длина строки, вложенность) — отдельная тема, серия их не разделяет |
| `errors` | исключение в обработчике: статус или класс обрыва (`closed`, `timeout`), утечка метки `marker-7f3a9c` из сообщения или стека (сырой текст, HTML-раскодированный, строки разобранного JSON; у детектора — свои контроли), раскрывает ли сервер себя в заголовках |
| `footprint` | время до первого ответа полного фреймворка к минимальному — только соотношения внутри экосистемы |

Абсолютные миллисекунды и мегабайты одной машины стенд не публикует — только соотношения, и те в полях `~`
(шумные). Гипотезы — в `expected.json` до первого запуска приложений, пересмотры (`revision_*`) — до сессий.

Зависимости закреплены не моложе двух недель на 19.10.2026: `go.sum`, `Cargo.lock` (каждый крейт проверен по
дате), `requirements.txt` из `uv pip compile --exclude-newer 2026-10-05`, `package-lock.json` из
`npm install --before=2026-10-05`, версии Maven — явные. Образы сборки — по дайджесту (`images.json`).

## Запуск

```bash
scripts/run-all.sh                          # сборка, все оси, сводка сессии, маркер, тесты, диверсии
python3 scripts/run-checks.py validation    # одна ось, без записи фикстуры
```

Приложения слушают `127.0.0.1:18100–18111` только на время опыта.

## Уборка

```bash
docker image rm $(docker image ls -q 'web-fw-*')
docker volume rm web-fw-gomod web-fw-cargo
rm -rf out
```
