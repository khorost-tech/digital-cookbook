# event-payload — notification vs event-carried state transfer

Живой стенд к статье [«Что кладём в событие: notification vs event-carried state
transfer»](https://khorost.tech/architecture/event-notification-vs-state-transfer/)
на khorost.tech.

Один и тот же поток «заказ оплачен» проигрывается в двух формах события и
сравнивается по трём **измеримым** осям.

## Что демонстрирует

- **Notification (тонкое событие).** Событие несёт только `{orderId}`. Каждый из
  N консьюмеров на каждое событие синхронно идёт в источник за деталями
  (`source.Get(orderId)`). Считаем обращения — это «GET-storm»: N консьюмеров ×
  каждое событие. Дополнительно показываем **временну́ю связанность**: если
  источник недоступен, консьюмер вообще не может обработать событие.
- **State transfer (толстое событие).** Событие несёт полный снимок состояния
  `{orderId, status, amount, currency, items…}`. Консьюмеры автономны — **0**
  обращений к источнику. Цена: (1) больший payload (стенд печатает фактические
  байты обоих вариантов); (2) **staleness** — источник меняет заказ уже ПОСЛЕ
  публикации события (`PAID → REFUNDED`), и толстый консьюмер работает по
  устаревшему снимку, тогда как тонкий при своём ленивом `Get` видит свежий статус.

Итог — таблица `вариант | обращений к источнику | размер payload | видит ли
свежие данные`. Инварианты проверяются в коде (`log.Fatalf` при расхождении):
notification → `>0` обращений (и ровно `N` — GET-storm) и свежие данные;
state-transfer → `0` обращений, но staleness; толстый payload крупнее тонкого.

## Инфраструктура

Всё **in-process**, без брокеров и docker:

- источник истины — мапа под мьютексом со счётчиком обращений (`Source`);
- «шина» — сериализованный срез байтов события;
- консьюмеры — обычные функции в цикле.

Этого достаточно, чтобы показать суть контраста. NATS (стенд `../nats/`) добавил
бы сетевой транспорт, но не изменил бы ни одной из трёх измеряемых осей —
поэтому здесь сознательно выбран in-process вариант.

Сценарий продублирован на **двух языках** — Go и Java. Обе реализации проигрывают
один и тот же поток, печатают одинаковую таблицу и совпадают по размеру payload
байт-в-байт (40 и 161). Java намеренно сериализует JSON вручную (без внешних
зависимостей), чтобы совпасть с Go.

## Как запустить

### Go

```bash
cd event-payload/go
go mod tidy
go build ./... && go vet ./...
go run .
```

### Java

Host-mvn не нужен — компиляция и прогон через Docker:

```bash
cd event-payload/java
docker run --rm -v "$PWD":/app -w /app maven:3.9-eclipse-temurin-21 \
  mvn -q -DskipTests compile
docker run --rm -v "$PWD":/app -w /app maven:3.9-eclipse-temurin-21 \
  mvn -q exec:java
```

Обе реализации печатают идентичный вывод (ниже) и завершаются с кодом `0`, если
все инварианты выполнены; при расхождении — ненулевой exit.

## Ожидаемый вывод (сверено живьём 2026-07-08)

```
Стенд: notification vs event-carried state transfer
Поток «заказ оплачен», 4 консьюмера(ов) на событие, заказ ORD-42 (status=PAID)

[notification] источник недоступен → консьюмер не может обработать событие: source unavailable: cannot fetch ORD-42
[state-transfer] источник уже содержит status=REFUNDED, но консьюмер увидел status=PAID (staleness)

──────────────────────────────────────────────────────────────────────────
вариант          | обращений к источн.  | payload, байт  | свежие данные
──────────────────────────────────────────────────────────────────────────
notification     | 4                    | 40             | да
state-transfer   | 0                    | 161            | нет (staleness)
──────────────────────────────────────────────────────────────────────────

notification  payload (40 байт): {"type":"order.paid","orderId":"ORD-42"}
state-transfer payload (161 байт): {"type":"order.paid","order":{"orderId":"ORD-42","status":"PAID","amount":1599900,"currency":"RUB","items":["keyboard-noon-edition","wrist-rest","usb-c-cable"]}}
толстое событие тяжелее в 4.0× (+121 байт)

OK: все инварианты выполнены.
```

Читается так: тонкое событие в 4× легче, но платит 4 обращениями к источнику на
одно событие (GET-storm) и ломается при его недоступности; толстое событие
автономно (0 обращений) ценой размера и того, что консьюмер не увидел свежий
`REFUNDED`.
