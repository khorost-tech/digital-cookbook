# Стенд Event Sourcing: глубокое погружение

Живой event store на PostgreSQL, KurrentDB и Kafka к серии
«Event Sourcing: глубокое погружение» на
[khorost.tech](https://khorost.tech/architecture/es-event-store-internals/).

Домен: учёт кислорода в резервуарах лунной базы. Стрим = резервуар. События
`TankRegistered` / `OxygenAdded` / `OxygenConsumed`. Инвариант: баланс не
уходит в минус.

Стенд отдаёт числа для статей, а не иллюстрирует пересказ теории. Все числа,
попавшие в текст, зафиксированы в [`FIXTURES.md`](FIXTURES.md) вместе с
оговорками — это единственный источник чисел для серии, ничего в статьи не
попадает мимо него.

## Профили стенда

| `scripts/03-projections.sh` | проекция с чекпоинтом в одной транзакции с применением события переживает обрыв процесса без потерь и дублей; сверка `FULL OUTER JOIN` ловит потерю стрима целиком | проекции и чекпоинты |
| `scripts/04-versioning.sh` | цена цепочки upcaster'ов на чтении: полевой замер (fetch+upcast целого стрима) и изолированный микробенчмарк (аллокации детерминированы, время — нет) | версионирование событий и upcasting |
| `scripts/05-testing.sh` | replay-тест против зафиксированной истории (доказано, что ловит внесённую регрессию, а не только проходит), given-when-then, тот же агрегат на Axon Framework для контраста моделей | тесты для событийной модели |

| `scripts/07-projector-safety.sh` | контрпримеры к проектору и их защиты: потеря события при курсоре по `BIGSERIAL`, разрыв версий на новом стриме, неизвестный тип события, противоречие `event_type` и `data->>'type'` — каждый с контролем | проекции и чекпоинты (регрессия) |

использует `python3 -m json.tool`, а в Windows Git Bash `python3` не

проверки JSON. Паттерн унаследован от `databases/cockroachdb/scripts/verify-static.sh`
(тот же образец), это общая особенность гейтов репозитория, а не дефект

## Порты и как их поменять

Смена одной только левой части `ports:` в `compose/compose.yml` НЕ
ДОСТАТОЧНА: скрипты (`scripts/lib.sh`, `scripts/probe.sh`) подключаются к
захардкоженным по умолчанию портам, а не парсят compose-файл. Порт нужно
поменять в ДВУХ местах — в `compose/compose.yml` и через переменную
окружения для скриптов, иначе `up.sh`/`probe.sh`/профили упадут с "connection
refused" на старый порт.

| сервис | порт хоста по умолчанию | переменная окружения для скриптов | что ещё поменять в compose |
|---|---|---|---|
| Postgres | `15453` → `5432` в контейнере | `PG_PORT` (или целиком `PG_DSN`) | левая часть `ports:` у сервиса `postgres` |
| KurrentDB | `12113` → `2113` в контейнере | `ESDB_PORT` (или целиком `ESDB_URL`) | левая часть `ports:` у сервиса `kurrentdb` |
| Kafka | `49092` → `9094` в контейнере | `KAFKA_PORT` (или целиком `KAFKA_BROKER`) | левая часть `ports:` у сервиса `kafka` **и** `KAFKA_ADVERTISED_LISTENERS` (там же зашит `127.0.0.1:49092` для внешнего листенера — рассинхронизация с портом в `ports:` сломает подключение с хоста) |

`scripts/lib.sh` читает `PG_PORT`/`ESDB_PORT`/`KAFKA_PORT` (либо готовые
`PG_DSN`/`ESDB_URL`/`KAFKA_BROKER` целиком, если нужен нестандартный DSN —
например, другой хост) из окружения и строит из них DSN/URL для всех
скриптов профилей и для `probe.sh`. Пример смены порта Postgres на `15454`:

```bash
# 1) compose/compose.yml: ports: "15454:5432" у сервиса postgres
# 2) пересобрать стенд и передать новый порт скриптам
bash scripts/down.sh
bash scripts/up.sh
export PG_PORT=15454
bash scripts/probe.sh
```

Порты по умолчанию проверены свободными во всех compose-стендах репозитория
на 2026-08-13. После смены порта — пересобрать стенд (`bash scripts/down.sh
&& bash scripts/up.sh`), а не `restart`: листенеры Kafka читаются один раз
при старте контейнера.

## Ловушки

Собрано по ходу постройки стенда (задачи 1–8 плана,
`.superpowers/sdd/2026-08-13-event-sourcing-deep-stand-phase1/task-*-report.md`
в репозитории `khorost.tech`):

- **`docker-credential-desktop.exe` не найден в WSL2.** Docker Desktop для
  Windows не кладёт credential-хелпер в WSL `$PATH`. Публичные образы
  реальных кредов не требуют — достаточно на время команды добавить
  `export PATH="$PATH:/mnt/c/Program Files/Docker/Docker/resources/bin"`.
- **Windows Git Bash не видит проброшенные порты Docker-контейнеров** —
  `dial tcp 127.0.0.1:PORT: connectex`. Все команды, которым нужен живой
  стенд (Go-профили, `psql`, `verify-static.sh` с поднятым compose),
  запускать из WSL2, не из Windows-оболочки.
- **Исполняемый бит `.sh`-скриптов слетает при `git add` на Windows-стороне**
  (drvfs не хранит unix-права так, как ожидает git). После коммита
  проверять `git ls-files -s scripts/` для ВСЕХ скриптов и доставлять
  `git update-index --chmod=+x <файл>`, где режим не `100755`. Именно эту
  ловушку и ловит первая проверка `verify-static.sh`.
- **Postgres 18 меняет точку монтирования тома**: `/var/lib/postgresql`
  вместо `/var/lib/postgresql/data` в более ранних мажорах — старый путь
  образ отвергает при старте.
- **KurrentDB — переменные окружения `KURRENTDB_*`**, не переходный
  префикс `EVENTSTORE_*` (продукт переименован из EventStoreDB). Заработал
  сразу на `KURRENTDB_INSECURE`/`KURRENTDB_RUN_PROJECTIONS`/
  `KURRENTDB_START_STANDARD_PROJECTIONS`.
- **`kafka-broker-api-versions.sh` не годится для вывода версии Kafka** —
  первая строка его вывода содержит id брокера и таблицу версий протокола
  API, а не версию продукта. Источник версии в `probe.sh` —
  `kafka-topics.sh --version`, отдаёт чистую строку `4.3.1`.
- **Клиент KurrentDB v1.4.1 сигналит конфликт версии иначе, чем ожидалось
  по названию пакета**: не как `*kurrentdb.ErrorWrongExpectedVersion` (это
  API старого пакета `EventStore-Client-Go`), а как общий `*kurrentdb.Error`
  с кодом `ErrorCodeWrongExpectedVersion`/`ErrorCodeStreamRevisionConflict`.
- **`kgo.PollFetches` (клиент Kafka без consumer-группы) не сигналит
  «партиция вычитана до конца»** — блокируется до появления данных или
  истечения контекста. «Конец» детектируется коротким локальным таймаутом
  (250 мс) на каждый отдельный опрос, отдельно от общего дедлайна команды.
- **`TRUNCATE` без `RESTART IDENTITY` не сбрасывает `BIGSERIAL`-сиквенс**
  (`events_global_pos_seq`) — чекпоинт (абсолютная позиция в сиквенсе)
  после такого `TRUNCATE` сравнивается со счётчиком строк от другой точки
  отсчёта, постусловие падает на величинах из разных шкал.
  `03-projections.sh` использует `TRUNCATE ... RESTART IDENTITY`.
- **Сверка проекции со свёрткой через `INNER JOIN` не ловит потерю стрима
  целиком** — если проекция теряет строку для `stream_id` полностью, `JOIN`
  тихо выбрасывает её из результата, `diff_rows` остаётся 0. Исправлено на
  `FULL OUTER JOIN` — расхождением считается и числовая разница, и
  односторонний `NULL`. Проверено прямой порчей данных (см. `FIXTURES.md`,
  «Артефакт 03, фикс-раунд 1»).
- **Локальный репозиторий Maven по умолчанию (`~/.m2/repository`) в этом
  WSL принадлежит `root`** — сборка от пользователя падает `AccessDenied`.
  Обход — отдельный локальный репозиторий:
  `-Dmaven.repo.local=/tmp/m2-esdeep` (в `05-testing.sh` — переопределяемая
  переменная `M2_REPO`).
- **`axon-eventsourcing` — отдельный Maven-модуль**, не часть
  `axon-modelling`: без явной зависимости сборка падает на `compile`
  (`package org.axonframework.eventsourcing does not exist`).
  `AggregateTestFixture` из `axon-test` использует Hamcrest matchers, но
  объявляет их `optional` — без явной зависимости `org.hamcrest:hamcrest:2.2`
  сборка падает на `testCompile`.
- **Replay-тест с ЕДИНСТВЕННОЙ проверкой доменного инварианта не поймал
  внесённую регрессию** на зафиксированной истории — каждый стрим засеян
  избытком (`1e9` литров), регрессия (`-=` заменено на `+=`) только
  ускоряла рост остатка, в минус баланс не уходил. Тест переделан на
  сверку итогового состояния КАЖДОГО стрима с golden-снимком
  (`testdata/expected.json`) вдобавок к проверке инварианта — это ловит
  регрессию независимо от знака результата. Golden-снимок дополнительно
  перепроверен независимо (прямым SQL-агрегатом по `events`, в обход
  всего Go-кода) — 0 расхождений на 40 из 40 стримов.
- **Голое «порядка» в русском тексте FIXTURES ловится гейтом только рядом
  с числом** (`~[0-9]`, `около [0-9]`, `примерно [0-9]`, `порядка [0-9]`) —
  буквальный поиск подстроки «порядка» заворачивал бы честные формулировки
  вроде «порядок событий» или «инверсия порядка».
- **Числовые усилители без посчитанного отношения рядом** («заметно шире»,
  «на порядок») ловятся только ревью, не гейтом — «на порядок» в одном из
  черновиков означало не кратное 10 отношение, а произвольно широкий
  разброс; заменено на посчитанные множители (см. `FIXTURES.md`,
  «Артефакт 01, фикс-раунд 2»).

## Схема event store

Оптимистичная блокировка версии стрима реализована через
`PRIMARY KEY (stream_id, version)`: конкурентная запись одной и той же
версии даёт конфликт по ключу (`SQLSTATE 23505`), без строковых локов и
`SELECT ... FOR UPDATE`. Чекпоинт проектора двигается в той же транзакции,
что и применение события.

## Профиль 01: три движка под одной нагрузкой

```bash
bash scripts/01-store.sh
```

Три замера в `go/main.go` через реальную диспетчеризацию по `-mode`
(неизвестный режим — это `die()`, а не тихий фолбэк): append с ожидаемой
версией на Postgres/KurrentDB/Kafka, точечное чтение одного агрегата,
catch-up-подписка. Числа — в `FIXTURES.md`, раздел «Артефакт 01».

Клиент KurrentDB: `github.com/kurrent-io/KurrentDB-Client-Go` (первый
вариант из брифа, v1.4.1) — заработал сразу, откатываться на
`EventStore-Client-Go/v4/esdb` не понадобилось. Важно: в v1.4.1 конфликт
версии приходит НЕ как `*kurrentdb.ErrorWrongExpectedVersion` (это API
старого пакета `EventStore-Client-Go`), а как общий `*kurrentdb.Error` с
кодом `ErrorCodeWrongExpectedVersion` или `ErrorCodeStreamRevisionConflict` —
код это учитывает (`go/kurrent.go`).

Клиент Kafka: `github.com/twmb/franz-go/pkg/kgo`, без группы потребителей
(читаем весь топик сами, не отдаём офсеты). `kgo.PollFetches` не сигналит
«партиция вычитана до конца» — он блокируется до появления данных или
истечения контекста. Детектируем «конец» коротким локальным таймаутом
(250 мс) на каждый отдельный опрос, отдельно от общего дедлайна команды —
иначе время чтения включало бы весь оставшийся `-duration`, а не реальное
время чтения (`go/kafkastore.go`, `consumeAllAvailable`).

В `01-store.sh` для `catchup-compare` стоит `-duration 30s`, в брифе задачи
было `20s` — безвредное отклонение (замер на практике укладывается в ~11с
на все три движка), но не задокументированное сразу; исправлено фикс-раундом.

Фикс-раунд 1 (по замечанию ревью): раздел C в `FIXTURES.md` пересчитан на
6 независимых прогонах вместо одного — на суб-миллисекундной шкале
единичный замер зашумлён (GC, планировщик ОС) сильнее, чем сама измеряемая
разница. См. «Фикс-раунд 1» в `FIXTURES.md` и в `task-5-report.md`.

## Профиль 05: тесты и Axon на контрасте

```bash
bash scripts/05-testing.sh
```

Прогоняет `go test ./...` (включая replay-тест
`TestReplayAgainstRecordedHistory` против зафиксированной истории
`go/testdata/history.jsonl`) и `mvn test` в `java/` (тот же агрегат
«резервуар» на Axon Framework, given-when-then через
`AggregateTestFixture`). Числа и оба исхода replay-теста (сломанный код
FAIL / целый код PASS) — в `FIXTURES.md`, раздел «Артефакт 05».

Фактические версии, отличающиеся от исходной формулировки задачи:

- **Java в WSL — 17.0.19** (OpenJDK, Ubuntu-сборка; `java -version`), не
  21. В доступном окружении WSL установлена только ветка 17 — Java 21 там
  нет. `pom.xml` (`java/pom.xml`) выставляет `maven.compiler.release=17`
  под фактическую версию.
- **Axon — 4.13.2** (последняя в ветке 4.x на момент прогона), не Axon 5.
  Причина не в доступности пакета (5.3.0 в Maven Central есть), а в
  несовместимости API: задача просит аннотации `@AggregateIdentifier` /
  `@CommandHandler` / `@EventSourcingHandler` над простым
  POJO-классом-агрегатом — это стиль модели Axon 4
  (`axon-modelling`+`axon-eventsourcing`+`AggregateTestFixture` из
  `axon-test`). В Axon 5 модель агрегата и API тестового фикстура
  переписаны заново и с этим стилем не совпадают; смешивать версии значило
  бы подменить контраст, который просит задача.
- Локальный репозиторий Maven по умолчанию (`~/.m2/repository`) в этом
  WSL принадлежит `root` — сборка от пользователя `khap` падает
  `AccessDenied`. Обход — отдельный локальный репозиторий:
  `-Dmaven.repo.local=/tmp/m2-esdeep` (в `05-testing.sh` — переменная
  `M2_REPO`, по умолчанию тот же путь).
