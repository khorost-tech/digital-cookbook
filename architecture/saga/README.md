# Saga на практике — стенд

Живой стенд к статье [«Saga на практике»](https://khorost.tech/architecture/saga-in-practice/)
на [khorost.tech](https://khorost.tech).

Оркестрация-based сага «оформить заказ» на **Temporal** с компенсациями. Один
воркфлоу-оркестратор (`OrderSaga`) явно ведёт последовательность шагов и — при
сбое — запускает компенсирующие действия в **обратном** порядке.

## Что демонстрирует

Шаги саги и их классификация (явно отражена в коде и логах):

| # | Шаг | Класс | Компенсация |
|---|-----|-------|-------------|
| 1 | ОПЛАТА | `compensatable` | возврат средств |
| 2 | РЕЗЕРВ | `compensatable` | снятие резерва |
| 3 | ОТГРУЗКА | **PIVOT** (необратим) | нет — за пивотом только вперёд |
| 4 | УВЕДОМЛЕНИЕ | `retriable` (best-effort) | нет — сбой не валит сагу |

Ключевые свойства, которые видно в живом прогоне:

- **Компенсация ≠ rollback.** Это семантически обратные *бизнес-действия*, а не
  откат транзакции БД. При сбое они выполняются в **обратном** порядке относительно
  прямых шагов: сначала снять резерв, затем вернуть оплату.
- **Идемпотентность шагов И компенсаций.** Ретрай активити (Temporal ретраит сам)
  не задваивает эффект. Оплата в успешном сценарии намеренно «теряет ответ шлюза»
  на первой попытке → Temporal повторяет активити → благодаря ключу идемпотентности
  списание происходит **ровно один раз** (баланс уходит на `amount`, а не `2×amount`).
- **Semantic lock.** Заказ держится в статусе `PENDING` на время саги; параллельный
  «читатель» опрашивает статус и видит промежуточный `PENDING`, а по завершении —
  `CONFIRMED` (успех) или `CANCELLED` (откат).

Два сценария в одном прогоне:

- **A — успешный путь:** оплата (с транзиентным сбоем и ретраем) → резерв → отгрузка
  (PIVOT) → уведомление → `CONFIRMED`.
- **B — отказ на резерве:** оплата проходит → резерв **применяет эффект, но проваливает
  пост-проверку** (симуляция бизнес-отказа, non-retryable) → сага откатывается:
  компенсации в обратном порядке (снятие резерва, затем возврат оплаты) → `CANCELLED`,
  баланс возвращён, резерв снят.

> Почему в сценарии B компенсируются **оба** шага, а не только оплата: инъекция
> сбоя на резерве сделана так, что резерв **сначала применяется**, и лишь потом
> срабатывает пост-проверка. Поэтому в откат попадают обе завершённые компенсируемые
> операции — это и позволяет показать именно **обратный порядок** из двух компенсаций,
> а не одну. Компенсации регистрируются в стек **до** выполнения шага, чтобы
> частично применённый эффект тоже был компенсирован; идемпотентность делает
> компенсацию no-op, если эффект по факту не применился.

## Как поднять и прогнать

### 1. Поднять dev-сервер Temporal

```bash
docker compose -f saga/compose/compose.yml up -d
docker compose -f saga/compose/compose.yml ps        # дождаться "healthy"
```

Один контейнер `saga-temporal` (`server start-dev`): gRPC frontend на хосте —
**`localhost:7243`**, Web UI — **http://localhost:8243**. Порты `7243/8243` выбраны,
чтобы не конфликтовать с соседним стендом `event-coordination` (`7233/8233`).

### 2. Прогнать сагу (Go)

Собственного Go-тулчейна на хосте не требуется — можно собрать образом `golang:1.25`.

```bash
# с хоста (если проброс порта на localhost:7243 работает на вашей машине):
cd saga/go && go run .

# надёжный способ на этой машине — прогнать клиент ИЗНУТРИ контейнера на сети стенда
# (см. заметку про host-подключение ниже):
docker run --rm --network saga_default \
  -e TEMPORAL_HOSTPORT=saga-temporal:7233 \
  -v "$(pwd)/go:/app" -w /app golang:1.25 \
  sh -c "go run ."
```

Адрес Temporal переопределяется переменной `TEMPORAL_HOSTPORT` (по умолчанию
`127.0.0.1:7243`). Процесс поднимает воркера и клиента в одном бинаре, прогоняет
оба сценария и печатает ассерты.

### 3. Снести стенд

```bash
docker compose -f saga/compose/compose.yml down
```

> **Заметка про подключение с хоста (Windows).** На машине автора локально
> собранный Go-бинарь не смог подключиться к проброшенному порту: `localhost`
> резолвится сначала в IPv6 `[::1]`, а проброс Docker по `::1` не отвечает
> (тайм-аут). После перехода на `127.0.0.1` соединение всё равно блокировалось
> на уровне ОС/файрвола (тот же симптом задокументирован в стенде `kafka`), хотя
> `docker` и bash `/dev/tcp` до порта достукиваются. Надёжный способ, которым и
> проверен стенд, — прогон клиента внутри контейнера на сети `saga_default`
> (адрес `saga-temporal:7233`). На другой машине прямой `go run .` с хоста, скорее
> всего, заработает без обходного пути.

## Ожидаемый вывод (проверено живьём 2026-07-08)

Прогон против живого `saga-temporal` (Temporal Server 1.31.1). Ниже — ключевые
строки (полный лог включает служебные записи Temporal SDK).

**Сценарий A — успешный путь.** Оплата списывается на 1-й попытке, «теряет ответ»,
Temporal ретраит — на 2-й попытке активити видит применённый ключ идемпотентности
и **повторно не списывает**:

```
[ЧИТАТЕЛЬ] заказ order-success виден в статусе PENDING — semantic lock держит сагу
ОПЛАТА [compensatable]: списано                      (Attempt 1, amount 1000)
ОПЛАТА: ответ платёжного шлюза «потерян» (симуляция) — Temporal повторит активити
ОПЛАТА [compensatable]: идемпотентный повтор — эффект уже применён, повторно НЕ списываем  (Attempt 2)
РЕЗЕРВ [compensatable]: товар зарезервирован          (sku sku-widget, qty 2)
ОТГРУЗКА [PIVOT]: точка невозврата пройдена — компенсации нет
УВЕДОМЛЕНИЕ [retriable]: клиент оповещён
semantic lock снят: ... status CONFIRMED
[ЧИТАТЕЛЬ] заказ order-success перешёл в терминальный статус CONFIRMED
наблюдённые читателем статусы: [PENDING CONFIRMED]
итоговый результат воркфлоу: CONFIRMED
  [OK]   результат == CONFIRMED
  [OK]   статус заказа в Store == CONFIRMED
  [OK]   баланс == 4000 (списано ровно один раз, идемпотентность): получено 4000
  [OK]   резерв == 2 (отгружено, не снято): получено 2
  [OK]   оплата ретраилась Temporal-ом (>=2 физич. вызова): получено 2
```

**Сценарий B — отказ на резерве.** Резерв применяется, затем проваливает
пост-проверку (non-retryable) → компенсации в **обратном** порядке:

```
[ЧИТАТЕЛЬ] заказ order-fail виден в статусе PENDING — semantic lock держит сагу
ОПЛАТА [compensatable]: списано                       (amount 1500)
РЕЗЕРВ [compensatable]: товар зарезервирован           (sku sku-gadget, qty 3)
РЕЗЕРВ: пост-проверка не пройдена (симуляция бизнес-отказа) — сага откатывается
   Activity error ... (type: RiskCheckFailed, retryable: false)
САГА: сбой — запускаю компенсации в ОБРАТНОМ порядке   (count 2)
САГА: компенсация  order 1  step компенсация РЕЗЕРВА (снятие)   <- первой: снятие резерва
КОМПЕНСАЦИЯ резерва: резерв снят                        (sku sku-gadget, qty 3)
САГА: компенсация  order 0  step компенсация ОПЛАТЫ (возврат)   <- второй: возврат оплаты
КОМПЕНСАЦИЯ оплаты: средства возвращены                 (amount 1500)
semantic lock снят: ... status CANCELLED
[ЧИТАТЕЛЬ] заказ order-fail перешёл в терминальный статус CANCELLED
наблюдённые читателем статусы: [PENDING CANCELLED]
итоговый результат воркфлоу: CANCELLED
  [OK]   результат == CANCELLED
  [OK]   статус заказа в Store == CANCELLED
  [OK]   баланс возвращён к 5000 (компенсация оплаты): получено 5000
  [OK]   резерв снят (компенсация резерва): получено 0
  [OK]   компенсации в ОБРАТНОМ порядке [reserve payment] (снятие резерва → возврат оплаты): получено [reserve payment]

ИТОГ: все ассерты зелёные.
```

**Порядок компенсаций — главное:** прямые шаги идут `оплата → резерв`, компенсации
— строго наоборот: `снятие резерва → возврат оплаты`. Журнал компенсаций в Store
фиксирует `[reserve payment]` — обратный порядок подтверждён ассертом.

### История воркфлоу в UI

Обе саги видны в Web UI: **http://localhost:8243** (namespace `default`,
WorkflowID `saga-order-success` и `saga-order-fail`). Там же — таймлайн активити,
ретрай оплаты (две попытки `ChargePayment`) и запуск компенсирующих активити.

## Структура

```
saga/
  compose/compose.yml   # dev-сервер Temporal (server start-dev), порты 7243/8243, project name=saga
  go/                    # module tech.khorost/saga-cookbook
    go.mod / go.sum
    saga.go              # Store (in-memory), активити (шаги + компенсации), воркфлоу OrderSaga
    worker.go            # клиент + воркер, TaskQueue, HostPort (env TEMPORAL_HOSTPORT)
    main.go              # точка входа: воркер + два сценария + «читатель» semantic lock + ассерты
    .gitignore
  README.md
```

Состояние (заказы, балансы, резервы, ключи идемпотентности) — in-memory (мьютекс-мапа),
Postgres намеренно не используется: цель стенда — показать **саму сагу**, а не
хранилище. Semantic lock реализован как статус заказа в этой мапе; «читатель» из
`main` читает ту же мапу конкурентно с активити воркера.

## Возможное расширение

- **Java-стенд** (`java/`, Temporal Java SDK) — тот же сценарий на другом SDK, по
  образцу двуязычных стендов серии (`kafka/`, `event-sourcing/`). В этом стенде
  **не реализован** — сознательно, чтобы не раздувать пример.
- Замена in-memory Store на Postgres (реальная строка заказа в `PENDING`, читатель
  в отдельной транзакции `READ COMMITTED` видит промежуточный статус).
- Хореография вместо оркестрации — контрастный стенд к соседней статье серии.
