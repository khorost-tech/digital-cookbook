# architecture/realtime — WebSocket, SSE и polling счётом исходов

Стенд к статье [«Realtime: WebSockets, SSE и long-polling»](https://khorost.tech/architecture/realtime-websockets-sse/).
Два сервера с одним протоколом — на Go и на Java — за Angie, шины Redis и NATS,
клиент-проба на Go. Каждая ось считает **исход**: сколько байт стоит событие,
дошло ли оно, что потеряно при разрыве, заметил ли сервер медленного клиента.
Задержки на ноутбуке не публикуются; единственная величина — память на
соединение (ось 6), и она идёт с оговорками.

## Что внутри

```
server-go/     net/http + coder/websocket; шины none, redis, redis-streams, nats, jetstream
server-java/   Spring Boot 4.1 (WebFlux, Netty), Lettuce, jnats — тот же протокол
probe/         клиенты SSE (поднабор: числовые id, Last-Event-ID; не браузерный EventSource),
               WS, polling; считающий и
               рвущий TCP-прокси; сценарии осей подкомандами
probes/flate/  проба compress/flate Go к оси 1
angie/         конфиги Angie на каждый вариант осей 2, 3, 5
scripts/       раннеры осей, разборы с контролями, проверки, реестр диверсий
fixtures/      замеры *.jsonl; manifests/ — сводки сессий; RUN-COMPLETE — маркер
expected.json  ожидания, записанные до прогона
images.json    сторонние образы по дайджесту
```

Протокол обоих серверов: `GET /sse`, `GET /ws`, `GET /poll?after=N`,
`GET /longpoll` (курсор в памяти инстанса по cookie `sid`), `POST /publish?id=N`,
`GET /healthz`, `GET /debug/stats`, `POST /debug/gc`. Поведение задаётся
переменными окружения `RT_*` — список в начале `server-go/main.go`. Что протокол
один, проверяет `fixtures/protocol.jsonl`: один набор запросов к обоим серверам
даёт одинаковые наблюдения.

## Как прогнать

Нужны Docker и Python 3.8+; Go, Java и Maven — в образах.

```sh
bash scripts/run-all.sh                            # всё разом, маркер последним
```

Один вариант любой оси — одной командой; её и показывает статья:

```sh
python3 scripts/run-wire.py go ws-deflate          # ось 1: байт на событие
python3 scripts/run-proxy.py go idle ws short-idle # ось 2: простой за прокси
python3 scripts/run-scale.py go fanout ws none     # ось 3: два инстанса без шины
python3 scripts/run-reconnect.py go gap redis      # ось 4: разрыв подписки на шину
python3 scripts/run-slow.py go sse disconnect buffered   # ось 5: медленный клиент
python3 scripts/run-idle.py java ws                # ось 6: память на соединение
```

Проверки и диверсии:

```sh
python3 -m unittest discover -s scripts -p "test_*.py"                    # без Docker
STAND_WITH_DOCKER=1 python3 -m unittest discover -s scripts -p "test_*.py"
python3 scripts/sabotage.py         # каждая проверка обязана покраснеть от своей поломки
```

## Что замерено

Подробности и сырые выводы — в `fixtures/`; две сессии полного прогона совпали
по опубликованным величинам (`fixtures/manifests/`).

**Ось 1 — цена события на проводе** (`wire.jsonl`; нагрузка 64 байта, событие
раз в 100 мс, цена — разностью прогонов на 20 и 120 событий). Байт от сервера на
событие у Go / Java: WebSocket 113 / 113, SSE 132 / 130, long polling 247 / 211
плюс 120 от клиента — по запросу на событие. Short polling платит за опрос: при
опросе раз в 50 мс — больше двух запросов и около одного пустого ответа на
событие; раз в 500 мс — пять событий на запрос, но каждое ждёт опроса. Сжатие
зависит от реализации: `coder/websocket` по умолчанию не сжимает сообщения короче
128 байт (WS + deflate у Go — те же 113 байт, у Java — 13,5); `compress/flate`
Go на уровне по умолчанию при сбросе после каждого события почти не находит
повторов (`flate.jsonl`: 76 байт на 111-байтное сообщение против 15 на уровне 9),
и gzip потока SSE у Go даёт 80 байт против 25 у Java — с уровнем 9 те же 25.

**Ось 2 — прокси** (`proxy.jsonl`). При буферизации Angie по умолчанию все
события SSE дошли в окне при открытом потоке — с gzip и без; то же у nginx 1.27
(проба при разборе оси). Задержку опыт не мерил. Без проксирования `Upgrade`/`Connection` рукопожатие WebSocket не проходит
(Go отвечает 426, Java — 400). Простой дольше `proxy_read_timeout` Angie
закрывает и WS, и SSE, у WS — без кадра закрытия; heartbeat раз в секунду
соединение сохраняет.

**Ось 3 — два инстанса** (`scale.jsonl`). Без шины событие получают ровно
клиенты инстанса, в который его опубликовали; с Redis pub/sub и NATS — все.
Long polling с курсором в памяти инстанса без привязки клиента даёт десятки
дублей на десять клиентов; со sticky по cookie — ни дублей, ни пропусков.

**Ось 4 — разрыв и реконнект** (`reconnect.jsonl`). Пока подписка инстанса на
шину порвана, Redis pub/sub и NATS core теряют все события разрыва, Redis
Streams и JetStream их догоняют. Брокер при этом работает; JetStream на стенде
держит поток в памяти, и перезапуск NATS опыт не проверяет. SSE-клиент, вернувшийся с `Last-Event-ID`, без
истории на сервере теряет свой разрыв, с историей в Streams или JetStream — нет. Стык истории и живого потока проверен управляемым барьером: сервер
прочитал журнал и ждёт, события публикуются в это время — у Streams и
JetStream ни пропусков, ни дублей; контроль с подпиской после чтения журнала
(`RT_SUBSCRIBE_LATE`) теряет все события барьера. Ошибка чтения журнала
(`RT_HISTORY_FAIL`) — отказ 503 до начала ответа, а не поток с пропуском.
Клиент, ушедший во время чтения журнала, снимается из хаба у Go и Java (у Java
до исправления оставался — опыт `cancel` это ловит).
Шторм после рестарта инстанса: без джиттера все 200 клиентов переподключаются в
одной корзине 100 мс, с джиттером до 2 с — не больше двух десятков в корзине.

**Ось 5 — медленный клиент** (`slow.jsonl`; 3000 событий по 1 КБ). Напрямую и
через Angie без буферизации политика очереди срабатывает: очередь без границы
растёт до тысяч событий, вытеснение выбрасывает, отключение отключает. **SSE через
Angie с буферизацией по умолчанию — сервер медленного не замечает вовсе**:
очередь не выше пары событий, ни одна политика не срабатывает, поток копит прокси
(в памяти и во временном файле). WebSocket через тот же Angie ведёт себя как
напрямую: после рукопожатия прокси его не буферизует.

**Ось 6 — память на простаивающее соединение** (`idle.jsonl`; 5000 соединений,
после сборки мусора). RSS / куча на соединение (куча у Go — `HeapInuse`, у Java — heap used, напрямую
не сравниваются): Go WS ≈ 32 / 17 КБ, Go SSE ≈ 34 /
21 КБ, Java WS ≈ 17 / 10 КБ, Java SSE ≈ 30 / 18 КБ.

## Чего эти числа не значат

- **Ничего о задержке.** Окна ожидания — постановка опыта, а не величина.
- **Одна машина:** macOS arm64, Docker Desktop; сеть — мост Docker, без потерь
  пакетов и без расстояния между узлами.
- **Версии:** Go 1.27.1, coder/websocket 1.8.15, Spring Boot 4.1.1 на Java 21,
  Angie 1.12.2, Redis 8.8, NATS 2.14 (`images.json`, `go.mod`, `pom.xml`).
- **Память на соединение** — у простаивающего соединения после сборки мусора,
  у JVM с фиксированной кучей 256 МБ; под нагрузкой картина другая.
