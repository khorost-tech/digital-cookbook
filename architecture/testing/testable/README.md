# testable — как писать тестируемый код, на живом стенде

Примеры к статье [«Как писать тестируемый код»](https://khorost.tech/architecture/writing-testable-code/) на khorost.tech.
Go, модуль `tech.khorost/testable-cookbook`, только stdlib. Тестопригодность здесь показана как свойство **дизайна**: один и тот же код до и после введения швов, чистое ядро против оболочки, и заход в легаси через «золотой мастер».

Парный стенд — [`testing/flaky`](../flaky): там чинят недетерминизм в тестах, здесь — проектируют код так, чтобы недетерминизм был инъецируемым.

## Запуск

    go test ./...                     # весь модуль зелёный
    go test -cover ./...              # покрытие по пакетам

    # по-функционально: 100% у слабого IssueBefore против 100% у точного Issue
    go test -coverprofile=c.out ./beforeafter/ && go tool cover -func=c.out

    # устойчивость: глобальная подмена в тесте «до» не течёт в соседние
    go test -count=3 -shuffle=on ./...

    # золотой мастер (перегенерация — ОСОЗНАННО, только при намеренной смене поведения)
    go test ./characterization/ -run GoldenMaster -update

## Что где

| Подкаталог | Приём | Содержимое |
|---|---|---|
| [`beforeafter/`](beforeafter) | Швы и инъекция недетерминизма | одна фича (выпуск купона + уведомление) в двух вариантах: `IssueBefore`/`NotifyBefore` с зашитыми внутрь `time.Now()`, `rand` и `http.Post` — и `Issuer` с инъецированными `Clock`/`IDGen`/`Sender` |
| [`functionalcore/`](functionalcore) | Functional core, imperative shell | `Decide` — чистая функция правил скидки (тестируется таблицей **без единого дублёра**); `Service` — тонкая оболочка с I/O: тесты на проводку + все три ветки ошибок границ |
| [`characterization/`](characterization) | Легаси и «золотой мастер» | легаси-печать чека с историческими багами: golden снят с ИСХОДНОЙ версии → код отрефакторен (разложен + получил шов) → golden зелёный. Исходная версия сохранена (`legacy_before.go`), эквивалентность old-vs-new доказана тестом на корпусе + 2000 рандомизированных чеках |

## Главное: покрытие врёт, а дизайн — нет (сверено)

`go tool cover -func` по пакету `beforeafter` (go1.26.3), итог по пакету — **86.2%**:

| Функция | Покрытие | Что тест реально может |
|---|---|---|
| `IssueBefore` (до) | **100.0%** | даже **строжайший возможный** тест берёт только ФОРМАТ (`^CPN-[0-9]{6}$`) и ГРАНИЦЫ времени вокруг вызова. Значение ID случайно, точное время недоступно, а инвариант `ExpiresAt == IssuedAt+TTL` **недоказуем**: внутри два разных `time.Now()` |
| `NotifyBefore` (до) | **83.3%** | тест **возможен, но только через подмену глобального `http.DefaultClient.Transport`**: процессный шов — нельзя `t.Parallel()`, ломает чужие тесты при забытом restore, опирается на деталь реализации (`http.Post` = `DefaultClient`), URL-константу не подставить |
| `Issue` (после) | **100.0%** | ID, `IssuedAt`, `ExpiresAt` — **точным равенством**, плюс захваченный факт отправки и ветка ошибки. Локальные фейки, никакой глобальной подмены, безопасно параллельно |
| `HTTPSender.Send` (адаптер) | **86.7%** | контракт: форма, метод, заголовок, проброс `ctx`, **non-2xx → ошибка**. Здесь был **реальный баг**: `Send` возвращал `nil` на HTTP 500 — считал недоставленное доставленным. Поймал контрактный тест |
| `formatCouponID` (чистая) | **100.0%** | контракт формата вынесен из генератора и проверен **детерминированно, на границах** (0 → `CPN-000000`, 999999 → `CPN-999999`) |
| `RandomIDGen.NewID` (адаптер) | **100.0%** | ветвлений нет, но контракт есть; формат доказан выше, генератору остаётся отдать номер из диапазона через форматтер |
| `SystemClock.Now` | 0.0% | **вот здесь** ноль защитим: `return time.Now()` — своего контракта нет, только делегирование stdlib |

Три вывода, и два из них — исправление собственных заблуждений:

1. **Покрытие врёт.** У `IssueBefore` те же 100%, что у `Issue`, — а доказывает он несравнимо меньше: форму вместо значений. Покрытие меряет, что строка исполнилась, а не что тест придирчив (та же мысль, что в [mutation-разделе](../tdd-bdd) соседнего стенда).
2. **«Герметично не протестировать» — неправда.** `http.Post` ходит через глобальный `http.DefaultClient`, и его `Transport` подменяем: тест `TestNotifyBefore_ТолькоЧерезГлобальнуюПодмену` реально перехватывает запрос без сети. Честная формулировка не «невозможно», а **«возможно только через хрупкую глобальную подмену»**; явный локальный шов даёт то же без процессных побочек.
3. **«В адаптере ломаться нечему» — тоже неправда, и это стоило бага.** У `HTTPSender.Send` есть свой контракт (форма, метод, заголовок, `ctx`, трактовка статуса), и трактовка статуса была сломана. Адаптеру нужно **меньше** тестов, чем доменной логике, но **не ноль**.

Правильный критерий — не «есть ли ветвление», а **«есть ли наш собственный контракт»**. У генератора ID ветвлений нет ни одного, но он задаёт префикс, диапазон и формат `%06d`: смените `%06d` на `%6d` — и потребители, разбирающие ID, молча поедут. Поэтому у него тест, а не ноль. А вот `SystemClock.Now` — чистое делегирование stdlib без единого своего решения: тут ноль честен.

И ещё один виток той же мысли: сначала формат проверялся выборкой из 500 случайных ID — тест не мигал, но регрессию `%06d` → `%6d` (видна только на малых номерах) ловил бы **вероятностно**. Поэтому формат вынесен в чистую функцию `formatCouponID` и проверяется **на границах**, детерминированно. Это ровно приём из `functionalcore`: вынести решение из окружения недетерминизма — и оно становится тривиально проверяемым.

## Чистое ядро против оболочки (сверено)

Пакет `functionalcore` — **100.0%** покрытия операторов. Правила скидки (`Decide`) закрыты таблицей из 7 случаев, включая границы тиров, усечение и просрочку, — **без единого фейка**, потому что зависимостей у чистой функции нет вовсе. Оболочке (`Service.Process`) остались тесты на проводку и на **все три** ветки ошибок границ (`Load` / `SaveDiscount` / `Notify`) — у них разные последствия: после ошибки `Notify` скидка уже сохранена, и тест фиксирует этот частично применённый эффект как осознанное поведение. Отдельный тест закрепляет чистоту ядра: два вызова с теми же входами дают тот же результат и не меняют вход (это проверка выбранного свойства, а не доказательство чистоты в математическом смысле).

## Золотой мастер: рефакторинг под защитой (сверено)

`characterization` — **100.0%** покрытия. Порядок был ровно такой:

1. Написана легаси-функция печати чека с историческими странностями.
2. `go test ./characterization/ -run GoldenMaster -update` снял golden **с исходной версии** — вместе с багами:
   - `Шоколад молочный с фундуком` → `Шокола` (обрезка по **байтам**, не рунам: «12 символов» превратились в 6);
   - скидка усекается: `199.99` → `-9.99` (999.95 коп. → 999);
   - при недоплате печатается отрицательная сдача: `СДАЧА: -275.00`.
3. Код отрефакторен: разложен на `formatLine`/`truncName`/`DefaultDiscount`, появился **шов** — `Printer.Discount` (правило скидки стало подменяемым), прежняя точка входа `FormatReceipt` сохранена.
4. `go test ./characterization/` — **golden зелёный, файл не трогали**.

Но одного golden для доказательства **мало**, и это важно понимать: он сверяет текущий код с текущим файлом. Прогони кто-нибудь `-update` вместе с правкой поведения — тест остался бы зелёным. Поэтому в стенде исходная реализация сохранена дословно и **самодостаточно** (`legacy_before.go`, включая собственный `moneyLegacy`: звала бы она текущую `money`, регрессия внутри `money` одинаково изменила бы обе стороны и тест остался бы зелёным). Эквивалентность проверяется **исполняемым тестом** `TestRefactor_ЭквивалентностьСтаройРеализации`: старая и новая версии сравниваются на том же корпусе **плюс на 2000 рандомизированных чеках** с фиксированным seed (детерминированно, но шире шести ручных случаев). Вот это уже доказательство, что рефакторинг не изменил поведение.

Golden фиксирует поведение **вместе с багами** — он не утверждает, что оно правильное, он не даёт ему измениться незаметно. Починка байты→руны — отдельное осознанное изменение, которое обязано обновить golden.

## Честные оговорки

- **У тестопригодности есть цена**: каждый шов — это интерфейс и индирекция. Интерфейс на каждый чих превращает код в шум. Швы вводят там, где реально нужна подмена: часы, случайность, I/O, чужой SDK — то есть на **границах**, а не между внутренними функциями.
- **«За швом тонкий адаптер, тестировать нечего» — опасная формулировка.** Критерий — наличие **своего контракта**, а не ветвлений. Ноль защитим только для чистого делегирования (`SystemClock.Now`). Как только адаптер что-то решает сам — формат, кодирование, статусы, таймауты, ретраи, — у него есть что ломать: `HTTPSender.Send` считал HTTP 500 доставкой, а `RandomIDGen.NewID` без единого ветвления задаёт формат ID. Адаптерам нужно **меньше** тестов, чем логике, но не ноль.
- **Тесты доказывают контракт только для выбранных свойств и сценариев.** «Issue проверен точно» означает «точно для полей ID/времени и факта отправки на этих входах», а не «доказан для всех». Это верно и для эквивалентности рефакторинга: 2000 случайных чеков — сильная проверка, но не формальное доказательство.
- **Characterization-тест ≠ проверка корректности.** Он — сеть безопасности на время рефакторинга и фиксирует в том числе баги. Не путать с тестом, утверждающим «так правильно».

## Версии

Проверено 2026-07 на **Go 1.26.3** (локально): `go build/vet/test ./...` зелёные (в т.ч. под `-count=3 -shuffle=on` — глобальная подмена в тесте «до» восстанавливается через `t.Cleanup` и не течёт в соседние тесты), golden и эквивалентность old-vs-new воспроизводятся, числа покрытия сняты `go tool cover -func`. Модуль объявляет `go 1.25.0` (минимум). Зависимостей нет — только stdlib (`testing`, `time`, `math/rand/v2`, `net/http`, `fmt`, `strings`, `os`, `flag`).
