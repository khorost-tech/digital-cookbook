# Тестирование в разных языках: один домен, четыре приёма, три экосистемы

Стенд к статье [«Тестирование в разных языках»](https://khorost.tech/architecture/testing-across-languages/).

Одна и та же задача решена на **Go**, **Java** и **Python**. В каждом языке —
одни и те же четыре приёма, чтобы сравнивать не задачи, а экосистемы:

1. **Табличный юнит-тест** — примеры выбирает человек;
2. **Дублёры** — фейк, мок, стаб на одной границе;
3. **Property-based** — генератор, инвариант и шринкинг;
4. **Testcontainers** — настоящий Postgres вместо фейка.

## Домен

Объёмная скидка по тирам (всё в копейках):

| сумма заказа | скидка |
|---|---|
| до 100.00 | нет |
| от 100.00 | 5% |
| от 200.00 | 10% |

Ровно этот код лежит в `go/pricing`, `java/.../Pricing.java` и `python/pricing.py`.

## Запуск

### Go (go 1.26.3)

```bash
go test ./...                              # юниты + property (инвариант)
go test -tags=bug ./service/               # демо: слабая проверка вызовов пропускает дефект
go test -tags=property_demo ./pricing/     # демо: наивный vs доменный генератор
go test -tags=integration ./store/         # Testcontainers + Postgres
```

### Java (JDK 21, Maven)

```bash
mvn test                                                    # юниты + property + дублёры
mvn test -Ddiscount.bug=true                                # демо: слабая проверка вызовов пропускает дефект
mvn test -Dgroups=property-demo -Dexcluded.groups=          # демо: генераторы (оба бюджета)
mvn test -Dgroups=integration -Dexcluded.groups=            # Testcontainers + Postgres
```

### Python (3.12)

```bash
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt
./.venv/bin/pytest                         # юниты + property (инвариант) + дублёры
DISCOUNT_BUG=1 ./.venv/bin/pytest          # демо: слабая проверка вызовов пропускает дефект
./.venv/bin/pytest -m property_demo        # демо: генераторы
./.venv/bin/pytest -m integration          # Testcontainers + Postgres
```

По умолчанию интеграционные тесты и демо-свойства **не запускаются**: первым нужен
Docker, вторые падают намеренно.

## Что показывает каждое демо

### Дублёры: дело не в дублёре, а в утверждении

Под флагом (`-tags=bug` / `-Ddiscount.bug=true` / `DISCOUNT_BUG=1`) сервис теряет
скидку — клиент платит полную сумму. Одинаково во всех трёх языках:

| тест | что утверждает | под багом |
|---|---|---|
| на **фейке** | читает заказ обратно: цена 9500 | **падает** |
| на моке, **слабая** проверка | `save` позвали один раз | зелёный — дефект пропущен |
| на моке, **захват аргумента** | что понесли в `save`: цена 9500 | **падает** |

Напрашивающийся вывод «фейк умеет, мок не умеет» — неверен, и стенд это
показывает: мок с захватом аргумента (`ArgumentCaptor`, `call_args`, поле `Saved`
в Go) ловит тот же дефект. Пропускает не мок, а **слабое утверждение**.

Разница между фейком и моком — не в силе, а в предмете: фейк утверждает про
результат, мок — про вызов. Отсюда разная привязка: тест на вызовах связан с
**протоколом взаимодействия** (сколько раз позвали, в каком порядке, с чем),
тест на фейке — с **наблюдаемым результатом**.

Пока порт стабилен, оба живут спокойно: подменить Postgres на другое хранилище
за тем же интерфейсом не заметит ни один. Поменяется сам интерфейс — править
придётся обоих дублёров. Расходятся они там, где поведение осталось прежним, а
протокол изменился (один `Save` вместо двух, кэш перед портом, переставленные
вызовы): тест на фейке продолжит утверждать своё, тест на вызовах покраснеет,
хотя ломать было нечего.

### Property-based: генератор решает всё

Свойство «заказ на большую сумму не может стоить дешевле» **нарушено**: на 99.99
скидки нет (платим 99.99), на 100.00 сразу 5% (платим 95.00).

Замеры на этом стенде. Перед каждым прогоном чистится кэш упавших примеров
(`testdata/rapid`, `.jqwik-database`, `.hypothesis`) — иначе движок переигрывает
прошлую находку первой, и замер показывает не «нашёл заново», а «помнил».

| движок | наивный, бюджет по умолчанию | наивный, 20 000 примеров | доменный, бюджет по умолчанию |
|---|---|---|---|
| rapid 1.3.0 (Go) | **0 из 20** (дефолт 100 примеров) | 5 из 5 | **5 из 5**, за 2–31 пример |
| jqwik 1.9.3 (Java) | **5 из 40** (дефолт 1000 попыток) | 4 из 5 | **5 из 5** |
| Hypothesis 6.156.6 (Python) | **0 из 20** (дефолт 100 примеров) | 5 из 5 | **5 из 5** |

Строка jqwik выбивается, и объяснение напрашивается: дефолтный бюджет у неё
вдесятеро больше. Контроль на равных бюджетах (`EQUAL_BUDGET=1 ./property-matrix.sh`):

| движок | @100 | @1000 | @20 000 |
|---|---|---|---|
| rapid | 0 из 20 | 0 из 20 | 5 из 5 |
| jqwik | **0 из 20** | 5 из 40 | 4 из 5 |
| Hypothesis | 0 из 20 | 0 из 20 | 5 из 5 |

На сотне все три дали ноль из двадцати — но объявить на этом основании, что
разницу дефолтов объясняет бюджет, нельзя: **нулевая выборка не доказывает
равенства**. «0 из 20» у каждого означает лишь, что верхняя граница
двустороннего 95% интервала — около 17% (Клоппер–Пирсон), а не «вероятности
равны».

На тысяче jqwik даёт 5 из 40, rapid и Hypothesis — 0 из 20, и хочется заключить
«генератор jqwik лучше». Тоже нельзя: 5 из 40 — это 12.5% [4.2%, 26.9%], а
0 из 20 — [0%, 16.9%]; **интервалы перекрываются**.

Аккуратно из матрицы следует ровно одно, зато твёрдо:

- **бюджет повышает наблюдаемую частоту находок** — у каждого движка она растёт
  монотонно, от нуля на сотне до почти всегда на двадцати тысячах;
- отделить вклад разных дефолтных бюджетов от вклада стратегий генерации и
  случайного разброса эта серия **не позволяет**. Разные дефолты вклад вносить
  могут; доказать, что дело в них, — нужны сотни прогонов, а не двадцать.

Итог: на настройках по умолчанию наивное свойство находит дефект **ненадёжно во
всех трёх экосистемах**. «0 из 20» — не «никогда», а «редко»: тот же интервал
[0%, 16.9%] означает, что вероятность находки за прогон может доходить до одной
шестой.

Число прогонов: 20 на ячейку; у jqwik на дефолте — 40 (два захода по 20, дали 4
и 1 находку). Воспроизвести именно 40: `JQWIK_RUNS=40 ./property-matrix.sh`.

Причина, по которой генератор редко попадает в нужную полосу, видна замером
распределения — инструментирован только rapid, внутрь jqwik и Hypothesis не лезли:

```
go test -tags=property_demo -run Распределение ./pricing/ -rapid.checks=200000 -v

черновиков=200000
в полосе [9500..10500]: 1706 (0.85%) — при равномерном было бы ~3.3%
>= 10000 (порог 1-го тира): 34178 (17.1%) — при равномерном было бы ~66.7%
```

Лечится не «побольше примеров», а генератором, который знает **структуру домена**
(у скидки есть пороги), но не знает про нарушение. Тогда находят все три, за
десятки примеров.

Шринкинг ужимает случайную находку до контрпримера на границе тира — но
минимальность **локальная**: в разных прогонах выходят разные пары. Почему
шринкер останавливается там, где остановился, не утверждаем: это требует
трассировки шринкера, а мы её не делали.

- `9501 → 10000` — истинный минимум: платим 95.01 — отдаём 95.01; платим 100.00 —
  отдаём 95.00. Hypothesis доходил до него 5 раз из 5, rapid — 2 из 5;
- `18948 → 20000`: 189.48 стоит 180.01, а 200.00 — 180.00;
- `19500 → 20000`: заметно дальше от истинного минимума — ужатый пример читаем
  и попадает в нужную окрестность, но глобально наименьшим быть не обязан.

### Testcontainers: одинаковая идея, разные умолчания

Все три части поднимают **один и тот же** `postgres:18.1-alpine` и проверяют то,
чего фейк не знает: что заказ доезжает до диска через SQL и что дубль ID
отклоняется первичным ключом. Контейнер — один на пакет, изоляция — `TRUNCATE`.

Цена приёмов — порядок величин, а не точные секунды: юнит-набор меряется долями
секунды или единицами секунд (у Java заметную часть съедает инициализация
Mockito), два интеграционных теста — секундами, и почти всё их время это старт
контейнера, а не проверки. Сам SQL отрабатывает за миллисекунды.

Точных межъязыковых секунд здесь нет намеренно: они меряют окружение, а не язык.
Один и тот же Python-набор на этой машине дал **0.33 с на нативной ФС и 4.13 с
при запуске с примонтированного диска** (интеграционный — 4.0 с против 7.8 с).
Разница в 12 раз, и к Python она отношения не имеет.

Свои числа снимайте скриптом — методика в нём явная (медиана N прогонов, время
по отчёту раннера, прогрев, `-count=1` у Go, проверка кода возврата: упавший
прогон не превращается в «рекордно быстрый набор»):

```bash
./timing-matrix.sh              # 5 прогонов, все языки
./timing-matrix.sh 5 go         # только Go — если тулчейны в разных окружениях
```

Что от замеров осталось твёрдого и от машины не зависит: контейнер на КАЖДЫЙ
тест вместо одного на пакет стоил Go-части **25.5 с вместо 6.4** — вчетверо
больше на тех же двух проверках. Поэтому в стенде контейнер один на пакет, а
изоляция — через `TRUNCATE`.

**Testcontainers Java и Docker 29.** Из коробки java-клиент на dockerd 29.6.1
не стартует вовсе:

```
Could not find a valid Docker environment.
  UnixSocketClientProviderStrategy: failed with exception BadRequestException
  (Status 400: client version 1.32 is too old.
   Minimum supported API version is 1.40, please upgrade your client)
```

docker-java по умолчанию говорит на API 1.32, а Docker 29 поддержку всего ниже
1.40 убрал. Go- и Python-клиенты на том же демоне работают сразу.

Лечится одной строкой — она уже стоит в `pom.xml`, так что стенд заводится на
Docker 29 без ручных действий:

```xml
<argLine>-javaagent:${org.mockito:mockito-core:jar} -Dapi.version=1.40</argLine>
```

Свойство `api.version` — из docker-java; его же можно положить в
`~/.docker-java.properties`. Переменная `DOCKER_API_VERSION` — **не** тот рычаг:
docker-java её так не читает, и с ней конфигурация не собирается вовсе. Версию
1.40 понимают демоны начиная с Docker 19.03, так что флаг безопасен.

Второй флаг в той же строке — `-javaagent` для Mockito. Без него Mockito цепляет
агент к себе на ходу: сейчас это работает, но с предупреждением, и JDK обещает
запретить динамическую загрузку агентов по умолчанию.

Ещё деталь: без биндинга SLF4J Testcontainers молча проглатывает диагностику —
остаётся «Please see logs», а логов нет. Поэтому в `pom.xml` есть `slf4j-simple`.
Если java-клиент «не видит Docker» — сначала включите логи.
