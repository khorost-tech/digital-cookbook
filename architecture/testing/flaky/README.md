# flaky — flaky-тесты: почему мигают и как чинить, на живом стенде

Примеры к статье [«Flaky-тесты: почему мигают и как чинить»](https://khorost.tech/architecture/flaky-tests-diagnose-and-fix/) на khorost.tech.
Go, модуль `tech.khorost/flaky-cookbook`, только stdlib. Пять классов flaky, у каждого — **починенная версия в обычных тестах** (зелёные при любом числе прогонов и под `-race`) и **мигающая версия под build-тегом `flaky`** (видна с `-count`/`-race`/`-shuffle`). Так `go test ./...` всегда зелёный, а мигание можно вызвать явно.

## Запуск

    go test ./...                 # только починенные — всегда зелёный
    go test -race ./...           # починки чисты и под детектором гонок

    # мигающие версии (build-тег flaky) — чтобы увидеть flake своими глазами:
    go test -tags=flaky -count=200 ./timedep/               # время
    go test -tags=flaky -count=200 ./race/                  # гонка (значение)
    go test -tags=flaky -race       ./race/                 # гонка (детектор; нужен C-компилятор)
    go test -tags=flaky -count=200 ./async/                 # sleep вместо синхронизации
    go test -tags=flaky -count=200 ./maporder/              # порядок обхода map
    go test -tags=flaky -shuffle=on ./order/               # порядок и изоляция (перезапускать заново, НЕ -count — см. ниже)

На Windows без C-компилятора `-race` гоняется в контейнере: `docker run --rm -v "$PWD:/src" -w /src -e GOPROXY=$GOPROXY golang:1.26 go test -tags=flaky -race ./race/`.

## Пять классов flaky

| Подкаталог | Причина | Чем ловится | Как чинится (в тесте-фиксе) |
|---|---|---|---|
| [`timedep/`](timedep) | зависимость от времени | `-count` (изредка), CI | время — параметр, а не `time.Now()` внутри; без `Sleep` |
| [`race/`](race) | гонка данных | `-race`, `-count` | `atomic`/`sync.Mutex` |
| [`async/`](async) | «синхронизация» через `Sleep` | `-count` | синхронизация каналом по факту готовности |
| [`maporder/`](maporder) | порядок обхода `map` | `-count` | сортировка ключей / сравнение как множеств |
| [`order/`](order) | общее состояние, зависимость от порядка | `-shuffle=on` | изоляция (свой экземпляр) + `t.Cleanup` |

## Частота мигания (сверено, go1.26.3 windows/amd64)

Ориентировочно, один прогон под лёгкой нагрузкой:

| Класс | Команда | Мигало |
|---|---|---|
| `timedep` | `-tags=flaky -count=200 ./timedep/` | ~11/200 (~5%) |
| `race` | `-tags=flaky -count=200 ./race/` | ~23/200 (~12%) |
| `async` | `-tags=flaky -count=200 ./async/` | ~198/200 (~99%) |
| `maporder`| `-tags=flaky -count=200 ./maporder/` | ~20/200 (~10%) |
| `order` | `-tags=flaky -shuffle=on ./order/` (перезапускать заново) | падает/проходит ~через раз |

**Сами частоты недетерминированы** — между прогонами и на разных машинах они плавают (у `timedep` — от **0/200** на linux/amd64 до 11/200 на windows/amd64 в наших замерах: на быстрой машине временно́й flaky может не проявиться вовсе). Это и есть суть flaky: не только тест мигает, но и «насколько часто». Поэтому `timedep` особенно коварен — локально выглядит стабильным, а на нагруженном CI частота взлетает.

Отдельно про `order`: его частоту **нельзя** мерить через `-count` — общее пакетное состояние (`shared`) копится между итерациями в одном процессе, и после первого «наследившего» теста падение становится постоянным (артефакт `-count`, а не рост flakiness). Честная оценка — перезапускать `go test -tags=flaky -shuffle=on ./order/` заново (свежий процесс), тогда падает/проходит примерно через раз в зависимости от выпавшего порядка.

## Детектор гонок (сверено, контейнер golang:1.26)

`go test -tags=flaky -race ./race/` печатает настоящий `WARNING: DATA RACE` на небезопасном инкременте `counter.go:14` (`c.n++`):

    ==================
    WARNING: DATA RACE
    Read at 0x00c0000cc1d8 by goroutine 14:
      ...race.(*UnsafeCounter).Inc()
          /src/race/counter.go:14 +0x7d
    Previous write at 0x00c0000cc1d8 by goroutine 9:
      ...race.(*UnsafeCounter).Inc()
          /src/race/counter.go:14 +0x8f
    ==================

Починенный `SafeCounter` (на `atomic`) под тем же `-race` чист — `go test -race ./...` зелёный.

## Ретраи и карантин — оговорка

Стенд намеренно чинит недетерминизм в корне, а не прячет его. Ретрай (`t.Retry`-обёртки, `--rerun-fails`) и карантин (вынести flaky из блокирующего прогона) уместны только для **честно-внешнего** недетерминизма (сеть, чужой сервис) и с логированием — иначе они маскируют и гниль в тесте, и настоящий редкий баг. В стенде таких примеров нет, потому что все пять причин устранимы детерминизмом.

## Версии

Проверено 2026-07 на **Go 1.26.3** (локально; `-race` — в контейнере `golang:1.26`): `go test ./...` и `go test -race ./...` зелёные. Все пять классов имеют flaky-версии под `-tags=flaky`; четыре (`race`, `async`, `maporder`, `order`) воспроизводятся стабильно, а `timedep` на быстрой машине может не проявиться вовсе (в замерах на linux/amd64 — 200/200 зелёных) — это нормально для временно́го flaky и подчёркнуто выше. Модуль объявляет `go 1.25.0` (минимум). Зависимостей нет — только `testing`, `sync/atomic`, `time`, `sort`.
