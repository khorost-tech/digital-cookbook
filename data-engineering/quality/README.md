# data-engineering/quality — проверки качества против эталона плохих строк

Стенд к статье [«Data quality и контракты данных: проверки, SLA и валидация»](https://khorost.tech/databases/data-quality-contracts/).
PostgreSQL 18 (база `dwh`: партия в `raw`, модели dbt в `staging` и `marts`,
карантин в `quarantine`, модели оси контракта в `contract`) и контейнер `tools`
с генератором, dbt-core 1.12 + dbt-postgres 1.11 и Great Expectations 1.24.
Генератор кладёт партию заказов за 10.09.2026 с одним подсаженным дефектом и
**сам** знает плохие строки; проверки сверяются с ним.

## Что внутри

```
generator/gen.py   партия с дефектом и эталон плохих id; время выгрузки — от момента загрузки
dbt/               sources (freshness), staging с тестами, сингулярный тест диапазона,
                   витрины, карантин, модели с контрактом и без
checks/ge_suite.py набор Great Expectations: построчные ожидания, среднее суммы, число строк
scripts/           раннеры осей, разбор с контролями, проверки, диверсии
fixtures/          замеры; manifests/ — сводки сессий; RUN-COMPLETE — маркер
expected.json      гипотезы до прогона и факты проб
```

## Как прогнать

Нужны Docker и Python 3.8+.

```sh
bash scripts/run-all.sh             # всё разом, маркер последним
FRESH=1 bash scripts/run-all.sh     # то же с пустых томов
python3 scripts/run-detect.py shift          # один вариант
python3 -m unittest discover -s scripts -p "test_*.py"
python3 scripts/sabotage.py
```

## Что замерено

Две сессии полного прогона (вторая — с пустых томов) совпали по
опубликованному (`fixtures/manifests/`).

**Ось 1 — что чем ловится** (`detect.jsonl`). Пустой клиент, повтор заказа,
отрицательная сумма, неизвестный статус — ловят и тесты dbt, и ожидания GE.
Клиента нет в справочнике и устаревшая партия — только dbt (`relationships`,
source freshness). Треть сумм в рублях вместо копеек и партия в 30 строк —
только проверки партии целиком в GE (среднее суммы, число строк): каждое
значение по отдельности допустимо. Чистая партия не роняет ни одной проверки.

**Ось 2 — реакция** (`reaction.jsonl`). 15 плохих строк из 287: `fail` —
витрина не построена, 245 хороших заказов задержаны; `warn` — витрина
построена вместе с 15 плохими; карантин — в витрине 245 хороших, в карантине 15.
`fail` поверх прошлой успешной загрузки (`fail-kept`): витрина-таблица не
пересобрана и отдаёт прошлую загрузку — 259 заказов вместо 245 хороших новой
партии, без признака устаревания. Партия с пустым статусом и пустой суммой
(`nullfields`): флаг `is_valid` без `coalesce` (`stg_orders_flagged_naive`)
теряет 12 строк — ни среди валидных, ни в карантине; с `coalesce` валидные
строки до бизнес-фильтров и агрегации + карантин = все 287 строк (контроль
сохранения).

**Ось 3 — контракт** (`contract.jsonl`). Смена типа суммы и удаление колонки:
модель с `contract: enforced` не строится; без контракта смена типа проходит,
удаление ломает витрину уровнем ниже. Рубли вместо копеек при том же типе:
контракт пропускает, выручка ×0,01; ожидание среднего GE падает.

## Чего эти числа не значат

- **Наборы проверок — типичные, не исчерпывающие:** dbt с пакетами расширений
  проверяет объём, GE — свежесть.
- **Коридор среднего задан вручную** (±20% от среднего чистых партий).
- **Версии:** dbt-core 1.12.5, dbt-postgres 1.11.0, Great Expectations 1.24.0,
  PostgreSQL 18.6.
