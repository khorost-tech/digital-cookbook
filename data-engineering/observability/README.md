# data-engineering/observability — lineage и мониторы данных против эталона инцидентов

Стенд к статье [«Data observability и lineage: наблюдаемость самих данных»](https://khorost.tech/databases/data-observability-lineage/).
PostgreSQL 18 (база `dwh`: заказы в `raw`, модели dbt в `staging` и `marts`,
метрики мониторов в `monitor`; база `marquez`), Marquez 0.51.1 — сервер
lineage OpenLineage — и контейнер `tools` с генератором, мониторами,
dbt-core 1.12 + dbt-postgres 1.11 и `dbt-ol` (openlineage-dbt 1.53).
Генератор кладёт 28 дней заказов (18.08–14.09.2026) с недельной сезонностью и
четырьмя подсаженными инцидентами и **сам** знает их дни; мониторы и lineage
сверяются с ним и с манифестом dbt.

Образ Marquez собран только под linux/amd64: на arm64 он работает через
эмуляцию, первый старт — несколько минут.

## Что внутри

```
generator/gen.py    28 дней загрузок; инциденты объёма, свежести, схемы, распределения
dbt/                источники, staging, промежуточная модель, 4 витрины; колонки описаны в YAML
monitors/monitor.py метрики дня на момент проверки и 8 детекторов
scripts/            раннеры осей, разбор с контролями, проверки, диверсии
fixtures/           замеры; manifests/ — сводки сессий; RUN-COMPLETE — маркер
expected.json       гипотезы до прогона, факты проб, эталон по семействам
```

## Как прогнать

Нужны Docker и Python 3.8+.

```sh
bash scripts/run-all.sh                      # всё разом, маркер последним
FRESH=1 bash scripts/run-all.sh              # то же с пустых томов
python3 scripts/run-monitors.py volume-static  # один детектор
python3 -m unittest discover -s scripts -p "test_*.py"
python3 scripts/sabotage.py
```

Порты наружу не открыты: к API Marquez (порт 5000 в сети compose) стенд
обращается из контейнера `tools`. Веб-интерфейс Marquez в стенд не входит.

## Что замерено

Две сессии полного прогона (вторая — с пустых томов) совпали по
опубликованному (`fixtures/manifests/`).

**Ось 1 — lineage** (`lineage.jsonl`). `dbt-ol run` в чистую базу Marquez.
Ниже `raw.orders` по графу Marquez 6 наборов — ровно как по манифесту dbt
(контроль). Lineage колонок, построенный обходом фасетов `columnLineage`: от
`raw.orders.amount` — 5 полей в 5 наборах, витрина `status_counts` не задета.
От `raw.orders.status` фасеты видят 3 набора, хотя SQL читает `status` в 6:
три денежные витрины фильтруют по нему в `WHERE`, а косвенных зависимостей
`dbt-ol` 1.53 не передаёт. Раннер ждёт, пока Marquez сохранит все фасеты:
запись асинхронная, без ожидания граф колонок выходит неполным.
API `/api/v1/column-lineage` Marquez 0.51.1 на этом графе отвечает 500.

**Ось 2 — мониторы** (`monitors.jsonl`). Оценка 01–14.09. Порог «меньше 200
строк» ловит оба провала объёма и даёт 4 ложные тревоги — все выходные. Провал
будня 02.09 (184 строки) лежит внутри нормы выходных: даже наименьший порог,
подобранный задним числом («меньше 185»), тревожит в воскресенье 06.09 (167).
Порог по тому же дню недели — без ложных.

Сценарий `drift` (`python3 -m generator.gen load DAY drift`): с 02.09 каждый
день треть сумм в рублях. Детектор среднего против ±3σ истории ловит 2 дня из
13 — сбой входит в историю и становится нормой; тот же детектор с историей без
дней, где он уже тревожил, — 13 из 13. Свежесть ловят оба порога, новую колонку —
сравнение схемы со вчерашней. Построчный диапазон суммы не замечает рубли
вместо копеек, среднее против ±3σ истории — замечает.

## Чего эти числа не значат

- **Пороги заданы вручную** (70%, 3σ, окно 14 дней), не подобраны под данные.
- **Четыре инцидента за две недели** — характер детектора, не его точность.
- **Ошибка API lineage колонок** — Marquez 0.51.1 и этот граф.
- **Версии:** dbt-core 1.12.5, dbt-postgres 1.11.0, openlineage-dbt 1.53.0,
  Marquez 0.51.1, PostgreSQL 18.6.
