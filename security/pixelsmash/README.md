# PixelSmash / CVE-2026-8461: аудит и изоляция FFmpeg-декодеров

Приложение к статье [«PixelSmash: как один видеофайл кладёт декодер FFmpeg»](https://khorost.tech/security/pixelsmash-ffmpeg/).

Это **оборонительный** стенд: набор аудит-скриптов и пример песочницы для FFmpeg-декодеров,
затронутых CVE-2026-8461 (heap out-of-bounds write в `libavcodec/magicyuv.c`, публично
известна как «PixelSmash»). Здесь **нет** боевого файла-эксплойта, шелл-кода или
воспроизведения краша — это не входит в замысел стенда. Задача — показать, (а) как
проверить, затронута ли ваша система, (б) где именно недоверенный медиаконтент
автоматически встречает FFmpeg-декодер без явного действия пользователя, и (в) как
изолировать такую точку, если обновление FFmpeg по какой-то причине откладывается.

## Что за уязвимость (кратко)

Декодер MagicYUV в FFmpeg до версии 8.1.2 (и до backport-фикса 8.0.3 в старой стабильной
ветке) неверно проверяет высоту среза (`slice_height`) относительно вертикального
поддискретизирования (`vshift`) chroma-плоскостей. При рассинхронизации декодер пишет
за пределы аллоцированного буфера — heap out-of-bounds write, CVSS 3.1 8.8 (HIGH),
CWE-787. Подробности и разбор по коммитам-фикселя — в
`.superpowers/sdd/2026-07-30-pixelsmash-ffmpeg/pixelsmash-facts.md` в основном репозитории
и в самой статье.

Два канала автоматического срабатывания декодера без явного открытия видео
пользователем:

1. **Desktop-thumbnailer.** `ffmpegthumbnailer` — типичный бэкенд генерации превью
   в GNOME (Nautilus), KDE (Dolphin) и XFCE (Thunar) через freedesktop.org
   thumbnailer-спецификацию. Превью строится при простом просмотре папки.
2. **Server-side library scan.** Медиасерверы (Jellyfin, Nextcloud, Immich,
   PhotoPrism и т.п.) сами сканируют библиотеку и генерируют превью новых файлов —
   это активный процесс приложения, не «пассивное лежание файла в папке», но тоже
   без ручного воспроизведения видео пользователем.

## Версии инструментов (снимок)

- **FFmpeg** — порог фикса в **апстриме**: **8.1.2** (релиз 17.06.2026) на основной
  ветке, либо **8.0.3** — backport в ветке 8.0.x. **Апстрим-сборки** ниже этих
  порогов уязвимы. Для пакетов дистрибутивов и вендорских сборок (jellyfin-ffmpeg
  и т.п.) номер версии вердикта не даёт — проверяйте advisory вендора и changelog
  пакета (см. ниже про `check-ffmpeg-version.sh`).
- **bubblewrap (bwrap)** — **0.11.2** (использовался при подготовке и проверке
  `sandbox-thumbnailer/run.sh`).
- **shellcheck** — **0.11.0** (использовался для проверки всех `.sh`-скриптов
  этого стенда).
- Дата снимка: **2026-07-31**.

## Как запустить

### `check-ffmpeg-version.sh`

Определяет версию FFmpeg в хост-системе и в каждом запущенном Docker-контейнере,
сравнивает с порогами фикса (8.1.2 / 8.0.3) и печатает вердикт по каждой установке:
`OK` / `ТРЕБУЕТ ПРОВЕРКИ` / «версия не распознана».

**Почему не `УЯЗВИМО`.** Номер версии решает вопрос только для сборок из апстрима.
Дистрибутивы (Debian, Ubuntu, RHEL и др.) обычно бэкпортят патч, **не поднимая**
upstream-версию: в NVD, например, значится исправленный пакет Red Hat на базе
FFmpeg 6.1.6 — по «правилу 8.1.2» он ложно попал бы в уязвимые. Поэтому при
версии ниже порога скрипт сначала ищет следы бэкпорта в changelog пакета
(`rpm -q --changelog`, `apt-get changelog`, `changelog.Debian.gz`), и лишь если
не нашёл — просит свериться с бюллетенем вендора, а не выносит приговор.

**Три правила, которые не дают выдать ложный `OK`:**

1. **Контекст.** Для контейнера бэкпорт ищется **внутри контейнера**
   (`docker exec`), а не в пакетах хоста. Пропатченный хост и уязвимый FFmpeg
   в образе — обычное сочетание, и путать их нельзя.
2. **Владелец.** Прежде чем верить changelog, скрипт сопоставляет реальный путь
   бинарника (`command -v` + `readlink -f`) с пакетом-владельцем через
   `dpkg -S` / `rpm -qf`. Changelog пакета — доказательство только для файлов
   **этого** пакета.
3. **Непакетная сборка.** Если бинарник не принадлежит ни одному пакету
   (самосборный `/usr/local/bin/ffmpeg`, вендорский бандл), механизм changelog
   к нему неприменим — вердикт всегда `ТРЕБУЕТ ПРОВЕРКИ`, со ссылкой на строку
   `configuration` из `ffmpeg -version` и на фикс `pr/23159`.

Оба кейса проверены живьём: пакетный `/usr/bin/ffmpeg` определяется как пакет
`ffmpeg`; самосборный бинарник, лежащий в `PATH` **рядом** с пакетным, корректно
опознаётся как непакетный и чужой вердикт не получает.

```bash
./check-ffmpeg-version.sh
```

Требует: `bash`, `sort -V` (coreutils). Docker — опционально: если демон недоступен,
скрипт молча пропускает проверку контейнеров и завершается без ошибки.

### `audit-decoders.sh`

Строит карту трёх типов точек, где недоверенный контент может автоматически
встретить FFmpeg-декодер:

1. установленные `*.thumbnailer`-файлы (`/usr/share/thumbnailers`,
   `/usr/local/share/thumbnailers`) и наличие бинарника `ffmpegthumbnailer`;
2. бинарники в `PATH`, **динамически** слинкованные с `libavcodec` — по записи
   `NEEDED` в ELF-заголовке, читается через `readelf -d`, **не через `ldd`**
   (`ldd` запускает динамический загрузчик и может выполнить код недоверенного
   бинарника — небезопасно для этой задачи).
   **Граница метода:** запись `NEEDED` бывает только при динамической линковке.
   Статически собранные приложения и те, что бандлят собственный FFmpeg
   (например `jellyfin-ffmpeg`), так не находятся — их ловит пункт 3 и ручная
   проверка вендорских сборок;
3. известные медиасерверы (Jellyfin/Nextcloud/Immich/PhotoPrism/Emby/Kodi) среди
   запущенных контейнеров `docker ps`.

```bash
./audit-decoders.sh
```

Требует: `bash`, `readelf` (обычно из `binutils`) для пункта 2; Docker — опционально,
как и в `check-ffmpeg-version.sh`.

### `sandbox-thumbnailer/run.sh`

Обёртка `bwrap` для запуска произвольной команды декодирования/thumbnailer'а в
изоляции: read-only корень, `--unshare-all` + `--unshare-net` (нет сети),
`--cap-drop ALL`, `--die-with-parent`, приватный `/tmp`, доступ только к явно
переданному входному файлу (read-only) и выходному каталогу.

```bash
cd sandbox-thumbnailer
./run.sh /path/to/suspicious.mkv ./out -- \
  ffmpegthumbnailer -i /sandbox/in/suspicious.mkv -o /sandbox/out/thumb.png -s 256
```

Требует: `bwrap` (пакет `bubblewrap`). Команда, переданная после `--`, должна быть
доступна в `/usr/bin` хост-системы (пробрасывается в песочницу как read-only).

### `sandbox-thumbnailer/docker-compose.yml`

Пример hardened-контейнера с той же целью: `read_only: true`, `network_mode: none`,
`cap_drop: [ALL]`, `security_opt: [no-new-privileges:true]`, `tmpfs` для `/tmp`,
входной файл смонтирован `ro`. Комментарии в файле поясняют каждую границу
изоляции. Адаптируйте образ/команду под свой конкретный thumbnailer или
медиасервис перед использованием — файл дан как иллюстрация набора границ, а не
как готовый к продакшену сервис.

```bash
cd sandbox-thumbnailer
mkdir -p in out
cp /path/to/suspicious.mkv in/suspicious-input.mkv
docker compose up
```

## Чего здесь нет и почему

- **Файла-эксплойта** (crafted AVI/MKV/MOV, эксплуатирующего рассинхронизацию
  `slice_height`/`vshift`) — стенд оборонительный, воспроизведение краша не входит
  в задачу приложения к статье.
- **Готового production-сервиса** — `docker-compose.yml` в `sandbox-thumbnailer/`
  это иллюстрация набора границ изоляции, а не готовый к раскатке медиасервис.
- **Патча для FFmpeg** — обновление до 8.1.2 (или 8.0.3 в ветке 8.0.x) делается
  штатным способом через пакетный менеджер дистрибутива или сборку из исходников;
  здесь только диагностика того, нужно ли это обновление.
