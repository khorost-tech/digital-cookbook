# Конвейер для недоверенных файлов

Приложение к статье [«Конвейер для недоверенных файлов: архитектура, а не флаг»](https://khorost.tech/security/untrusted-file-pipeline-architecture/) — третьей в серии «Недоверенный ввод».

Рабочий конвейер приёма файлов, где **каждая граница изоляции доказана экспериментом**, а не объявлена в конфиге.

## Устройство

```
клиент → api ──→ Redis ──→ supervisor ──файлы──→ parser (ffprobe)
         ↑                 ↑                     ↑
    принимает байты,   очередь,            разбирает содержимое;
    НЕ открывает их    файлы не открывает   сети нет вообще
```

| Сервис | Что делает | Сеть | Файлы |
|---|---|---|---|
| `api` | принимает байты, **не открывает их** | `pipeline` + `edge` (наружу) | пишет в `input` |
| `supervisor` | держит очередь, **не открывает файлы** | `pipeline` (internal) | `jobs`, `done` |
| `parser` | разбирает содержимое (`ffprobe`) | **нет вообще** (`network_mode: none`) | `input` только на чтение, `jobs`, `done` |

Разделение проходит по одной линии: **кто разбирает содержимое**. Если в парсере сработает уязвимость вроде CVE-2026-8461 (см. [«PixelSmash»](https://khorost.tech/security/pixelsmash-ffmpeg/)), выполнение кода произойдёт там, где нет ни сети, ни прав, ни возможности подменить разбираемый файл.

## Почему ролей три, а не две

Первая версия стенда обходилась одним воркером, подключённым к internal-сети ради Redis, — и утверждение «парсер лишён сети» было неточным. `internal` убирает выход наружу, но участники такой сети продолжают видеть друг друга. Проба `network_internal` показывала это прямо: воркер дотягивался и до Redis, и до API. Скомпрометированный парсер мог бы читать и править очередь.

Сеть отняли у парсера целиком (`network_mode: none`), а разговор с очередью вынесли в супервизор. Связь между ними — файлы в общем томе.

## Запуск

```bash
./run-all.sh
```

Один запуск — один снимок. Все артефакты помечаются общим `RUN_ID`, а маркер `results/COMPLETE` появляется только после успешного прохождения всех шагов: смешать файлы разных прогонов не выйдет.

Отдельными шагами:

```bash
docker compose build && docker compose up -d
./check-boundaries.sh     # матрица границ
./check-failure.sh        # сценарии аварий
docker compose down
```

## Как читать матрицу границ

`results/boundaries.tsv` — три замера на каждую пробу:

- **без границ** — контроль, операция должна проходить. Если контроль не прошёл, проверка останавливается: отказ при ограничении ничего не доказывает, если операция не работала и без него;
- **только эта граница** — включено **ровно одно** изучаемое ограничение;
- **полный набор** — все флаги, как в `docker-compose.yml`.

Колонки 2 и 3 разделены потому, что при полном наборе отказ `chmod` одинаково объясняется и seccomp, и `cap_drop`, и непривилегированным uid. Пока не выключено всё, кроме одного, вывод «это seccomp» — догадка.

Строка `normal_work` — обязательная: `ffprobe` должен отработать при **всех** включённых ограничениях. Защита, ломающая работу, не защищает: её снимут при первом же инциденте, обычно вместе со всем остальным профилем.

## Сценарии аварий

`results/failure-mode.txt` — четыре сценария: контроль на исправном конвейере, приём файла при **остановленном** парсере, **авария** парсера с автоматическим восстановлением и падение **супервизора** посреди взятой задачи.

Приём при неработающем парсере вынесен в отдельный сценарий не для красоты. Раньше загрузка шла сразу после аварии, но функция, роняющая контейнер, возвращает управление, лишь дождавшись перезапуска, — к моменту загрузки парсер был уже жив. Проверка называлась «приём при мёртвом парсере», а измеряла приём при живом. Теперь парсер останавливается явно (`docker stop` не поднимает контейнер обратно), состояние `exited` подтверждается до загрузки, а задача после приёма ищется напрямую в `tasks` и `processing`.

Авария вызывается сигналом главному процессу **изнутри** контейнера. Факт аварии фиксируется счётчиком `RestartCount`: к моменту проверки контейнер уже поднят политикой restart и показывает `running` с кодом выхода 0 — по мгновенному снимку состояния кажется, что ничего не случилось.

Проверки строгие: сверяются код HTTP, статус в теле ответа и совпадение `task_id`. Условия «ответ пришёл» недостаточно — под него подходит и ошибка. В конце все три списка (`tasks`, `processing`, `poison`) обязаны быть пустыми: непустой `processing` означал бы зависшую задачу. Оборванный отчёт без итоговой строки считается недостоверным целиком.

### Семантика доставки

Задача берётся через `BLMove` в список `processing` и остаётся там до явного подтверждения. `BRPop` не годится: он удаляет элемент сразу, и падение между чтением и результатом теряет задачу навсегда.

Обратная сторона — доставка **не меньше одного раза**. Задача, не подтверждённая до падения, будет обработана повторно, и обработчик обязан быть идемпотентным. Для генерации превью это естественно (результат зависит только от входа), для записи в биллинг или отправки уведомления — нет.

Возврат из `processing` идёт одной Lua-операцией: наивная пара `LREM` + `LPUSH` имеет окно, в котором задача исчезает из обеих очередей. Счётчик попыток живёт в Redis, а не в памяти супервизора, иначе перезапуск обнулял бы его и poison-очередь не ограничивала бы ничего.

Тайминги в `docker-compose.yml` укорочены **для стенда** (`PARSE_DEADLINE=12s`, `STALE_AFTER=10s`), чтобы сценарий проверялся за секунды. Значения по умолчанию в коде — 45s и 2m: при коротком дедлайне затянувшийся разбор большого файла будет принят за зависший и уйдёт на повторную обработку.

## Что остаётся возможным при компрометации парсера

Стенд не изображает неприступность. Атакующему, выполнившему код в парсере, остаётся:

- **запись в тома `jobs` и `done`** — они смонтированы на запись, иначе парсер не смог бы отдать результат. Значит, он может подделать ответ на чужое задание, положить вместо файла символическую ссылку или именованный канал, отдать ответ размером в гигабайт или дописать после правильного объекта чужой. Как это закрыто — ниже, в отдельном разделе;
- **чтение всех файлов во входном томе** — там лежат чужие загрузки;
- **исчерпание ресурсов в пределах лимитов** — 256 МиБ, 1 CPU, 64 процесса.

- **накопление файлов** — обработанные загрузки не удаляются, очистки, квот и срока хранения в стенде нет. В рабочем сервисе это обязательная часть, иначе входной том со временем становится архивом чужих файлов.

Чего не остаётся: сети в любую сторону, записи во вход, изменения прав, повышения привилегий, выхода за лимиты — это и показывает матрица границ.

## Как читается ответ из недоверенной зоны

Порядок операций в `readAnswer` — часть защиты, а не стиль:

```
open(O_RDONLY | O_NOFOLLOW | O_NONBLOCK)
  → Fstat УЖЕ ОТКРЫТОГО дескриптора
  → требование обычного файла
  → проверка размера
  → чтение не более maxResultBytes+1
  → разбор JSON с DisallowUnknownFields
  → требование EOF после первого объекта
  → сверка task_id и статуса
```

Проверять по имени до открытия недостаточно: между проверкой и открытием объект подменяется, и проверенное имя описывает уже не то, что открыто. `Lstat` в `waitResult` отвечает только на вопрос «ответ появился?».

`O_NOFOLLOW` закрывает символические ссылки, `O_NONBLOCK` — именованные каналы: от FIFO `O_NOFOLLOW` не спасает, а открытие канала без писателя блокируется навсегда, и супервизор встаёт в системном вызове.

Тесты (`go test ./supervisor/`) покрывают: обычный файл, размер ровно на пределе и на байт больше, символическую ссылку, FIFO (с требованием, чтобы чтение завершилось), каталог, подмену объекта после проверки по имени, неизвестное поле, чужой `task_id`, неизвестный статус, два объекта подряд и мусор после объекта.

Тесты проверены намеренной поломкой: без `O_NONBLOCK` FIFO-тест зависает и падает по сроку, без `O_NOFOLLOW` падают тесты ссылки и подмены, без требования EOF проходят два объекта. **Чего тесты не ловят:** замену `Fstat` открытого дескриптора на повторный `Lstat` по имени — подмену в тесте отсекает флаг открытия раньше, чем дело доходит до проверки типа. Окно между `open` и проверкой детерминированно не воспроизводится, а гонка «в цикле, авось поймается» дала бы плавающий тест. `Fstat` здесь обоснован построением, а не измерением, и это сказано прямо в комментарии к тесту.

## Дефекты, которые поймал сам стенд

Каждый выглядел как рабочая проверка и каждый измерял не то, что заявлял.

**1. Seccomp сломал работу.** Первая версия профиля запрещала `socket` — воркер после этого не мог подключиться к очереди и не брал ни одной задачи. Именно отсюда выросло разделение на супервизор и парсер: сеть нужна очереди, а не разбору файлов, и отнимать её надо у того, кто разбирает.

**2. Проба измеряла не то (процессы).** `process_spawn` запускал `/bin/true`, который завершается мгновенно: процессы не накапливались, и 200 запусков проходили даже при `pids_limit=64` — матрица показывала «граница не действует», хотя граница работала. Теперь запускаются долгоживущие процессы, удерживающие слоты в таблице.

**3. Проба измеряла не то (capabilities).** `chown(path, 0, 0)` под root — не изменение владельца, а пустая операция: ядро разрешает её без `CAP_CHOWN`. Проба показывала «разрешено» при снятой capability и «запрещено» в полном наборе, где процесс работает под 65534 и вызов становится настоящим изменением. Поймала это раздельная проверка границ, причём верный вывод был не «закрывает другая граница», а «проба измеряет не то». Теперь владелец меняется на чужой uid.

**4. Модель аварии была неверной.** Падение вызывалось через `docker kill` снаружи — Docker считает это намеренной остановкой и не применяет политику перезапуска, поэтому воркер не восстанавливался. Реальный крах моделируется сигналом главному процессу **изнутри** контейнера.

**5. Отчёт показывал уже перезапущенный контейнер как невредимый.** Состояние снималось сразу после аварии, когда контейнер был поднят политикой restart: `running`, код выхода 0. Факт аварии берётся из `RestartCount`.

**6. Сценарий «приём при мёртвом парсере» измерял приём при живом** — загрузка шла после функции, которая сама дожидалась перезапуска. Сценарий разделён надвое: явная остановка для проверки приёма и авария для проверки восстановления.

**7. Предел размера ответа применялся после чтения файла в память.** `os.ReadFile` шёл до сверки с пределом, то есть предел не ограничивал ничего. Проверка размера перенесена до чтения, чтение ограничено, добавлены `O_NOFOLLOW` и требование обычного файла.

## Что стенд НЕ доказывает

- **Это не пентест.** Пробы спрашивают у окружения «можно ли», а не пытаются обойти защиту. Стойкость seccomp к обходам, побеги из контейнера и уязвимости ядра здесь не проверяются.
- **Профиль seccomp — компромисс.** Он построен как «разрешить по умолчанию, запретить лишнее». Это слабее, чем allow-list по реальному профилю вызовов, зато не ломает `ffprobe` и читается. Для продакшена стоит строить allow-list — но тогда обязателен нагрузочный прогон: пропущенный вызов уронит обработку.
- **Границы проверены для этой конфигурации.** Другая версия Docker, другое ядро, rootless-режим или иная файловая система могут вести себя иначе.
- **Версия `ffmpeg` — не рекомендация.** Она пришла с базовым образом. Стенд показывает, что даёт изоляция, а не что даёт обновление; в рабочем сервисе нужны оба.
- **Конвейер учебный.** Нет аутентификации, квот на пользователя, backoff между попытками, метрик и очистки старых файлов — всё это нужно в реальном сервисе и намеренно опущено, чтобы не заслонять предмет.

## Артефакты

```
results/
  RUN_ID              метка прогона
  COMPLETE            маркер успеха — появляется последним
  environment.txt     версии образов, роли, границы, версия ffmpeg
  boundaries.tsv      матрица границ
  boundaries.log      журнал проверки границ
  failure-mode.txt    сценарии аварий
  failure.log         журнал сценариев
  raw/                сырые ответы проб (по три файла на пробу)
```
