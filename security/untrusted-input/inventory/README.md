# Инвентаризация: кто видит FFmpeg внутри образа

Приложение к статье [«SBOM видит, сканер молчит: слепое пятно вендоренных зависимостей»](https://khorost.tech/security/vendored-dependencies-blind-spot/) — первой в серии «Недоверенный ввод».

Стенд отвечает на один вопрос: **если компонент попал в образ мимо пакетного менеджера, узнают ли о нём инструменты, которым вы доверяете безопасность?**

FFmpeg поставляется в образы пятью разными способами, после чего по ним прогоняются четыре инструмента. Три цели — показательные случаи «как бывает в жизни», ещё две — контролируемая пара, где один и тот же бинарник отличается только именем пакета. Ничего не эксплуатируется и не атакуется — стенд только читает и сканирует.

## Главный результат

Компонент можно прекрасно **видеть** и при этом не знать **ни одной его уязвимости**. Это разные операции, и путать их нельзя.

Причина установлена контрольным экспериментом, а не выведена из корреляции. Один и тот же бинарник (побайтово идентичный), одна база, одна версия — меняется только имя пакета:

| Цель | Пакет | grype (уник. CVE по FFmpeg) | trivy | osv-scanner v2 |
|---|---|---|---|---|
| `deb-canonical` | `ffmpeg 8.1` | **65** | **41** | **75** находок |
| `deb-renamed` | `acmecorp-ffmpeg7 8.1` | **0** | **0** | **0** |

На реальном образе это выглядит так: у `jellyfin/jellyfin:10.11.9` syft видит компонент `jellyfin-ffmpeg7@7.1.3-6-trixie`, а grype даёт 380 находок в образе и **0** по FFmpeg, trivy — 393 и **0**, osv-scanner — 384 и **0**. Инструменты исправны: они просто не знают, что `jellyfin-ffmpeg7` — это FFmpeg.

Сопоставление с базами advisory идёт по идентичности компонента (имя, версия, тип пакета, namespace дистрибутива, purl/CPE и правила матчинга), а не по содержимому файла.

## Версии инструментов (снимок)

Syft, grype и trivy запускаются **контейнерами с пиновыми версиями** — ставить их не нужно. Osv-scanner ставится бинарником (почему — ниже), тоже с фиксированной версией и проверкой контрольной суммы.

| Инструмент | Версия | Роль |
|---|---|---|
| syft | `anchore/syft:v1.50.0` | SBOM — инвентаризация |
| grype | `anchore/grype:v0.116.1` | уязвимости по образу |
| trivy | `aquasec/trivy:0.72.0` | уязвимости по образу |
| osv-scanner | бинарник `v2.4.0`, режим `scan image` | уязвимости по образу |

osv-scanner ставится бинарником, а не контейнером: стабильных образов ветки v2 в ghcr на дату снимка нет, а ветка 1.x умеет работать только по SBOM и манифестам — сравнивать её со сканерами образов было бы некорректно. Версия 2.4.0 сканирует образы напрямую, поэтому все четыре инструмента получают одинаковый вход. Бинарник скачивается скриптом и **проверяется по sha256** из `scanners.env`.

Базы уязвимостей grype и trivy кэшируются в `.cache/`. Без кэша база качается при каждом запуске контейнера, и сорвавшаяся загрузка даёт пустой результат, который легко принять за «уязвимостей нет» — `run-scan.sh` дополнительно проверяет структуру каждого артефакта и помечает недостоверные.

Дата снимка: **2026-07-31**. Docker 29.6.1. Точные версии, digest'ы целевых образов и размеры — в `results/environment.txt`.

## Цели

Пять целей делятся на две группы, и путать их выводы нельзя.

**Показательные случаи** — как бывает в жизни. У них различаются и версии FFmpeg, и дистрибутивы, поэтому по ним нельзя изолировать влияние *имени пакета* от всего остального:

| Метка | Как поставлен FFmpeg | Зачем |
|---|---|---|
| `distro` | `apt install ffmpeg` в Debian 12 | контрольная точка: сканер обязан найти |
| `vendored` | бинарник скопирован в образ мимо пакетного менеджера | модель вендорской сборки |
| `jellyfin` | `jellyfin/jellyfin:10.11.9` — настоящая вендорская сборка | главный практический кейс |

**Контролируемый эксперимент** — здесь зафиксировано всё, кроме одной переменной. Один и тот же бинарник (побайтово, проверяется `sha256sum`), одна база `ubuntu:24.04`, одна версия `8.1`. Отличается **только имя пакета** в базе dpkg:

| Метка | Пакет в базе dpkg | Владелец `/usr/bin/ffmpeg` |
|---|---|---|
| `deb-canonical` | `ffmpeg 8.1` | `ffmpeg` |
| `deb-renamed` | `acmecorp-ffmpeg7 8.1` | `acmecorp-ffmpeg7` |

Выводы об идентификаторе делаются именно по этой паре: разница в результате может быть вызвана только именем, потому что больше ничего не менялось.

Версия Jellyfin выбрана намеренно: именно на **10.11.9** исследователи JFrog продемонстрировали RCE через CVE-2026-8461 (см. статью [«PixelSmash»](https://khorost.tech/security/pixelsmash-ffmpeg/)).

Цель `vendored` собрана на той же базе Alpine 3.20, что и донор, поэтому бинарник там **рабочий**, а не декоративный:

```
$ docker run --rm --entrypoint /opt/vendored/bin/ffmpeg ui-inv-vendored-binary:local -version
ffmpeg version 8.1 ...
$ docker run --rm --entrypoint sh ui-inv-vendored-binary:local -c 'apk info | grep -c ffmpeg'
0
```

FFmpeg работает — пакетный менеджер о нём не знает.

## Как воспроизвести

```bash
# 1. Собрать цели (локальные) и стянуть внешнюю
docker build -t ui-inv-distro-package:local  targets/distro-package
docker build -t ui-inv-vendored-binary:local targets/vendored-binary
# тег может переехать на другую сборку — для точного повтора берите digest
docker pull jellyfin/jellyfin@sha256:bc9fa8e1462fffe3d8d4255fc62af478602641f4c0e5f4875fea8563d1189837
docker tag jellyfin/jellyfin@sha256:bc9fa8e1462fffe3d8d4255fc62af478602641f4c0e5f4875fea8563d1189837 jellyfin/jellyfin:10.11.9

# контрольная пара: один Dockerfile, два имени пакета
docker build --build-arg PKGNAME=ffmpeg           -t ui-inv-deb-canonical:local targets/deb-repack
docker build --build-arg PKGNAME=acmecorp-ffmpeg7 -t ui-inv-deb-renamed:local   targets/deb-repack

# 2. Прогон четырёх сканеров по пяти целям (~20 минут; первый запуск дольше —
#    качаются базы уязвимостей и бинарник osv-scanner)
./run-scan.sh

# 3. Зафиксировать окружение — без этого числа невоспроизводимы
./record-environment.sh

# 4. Сводные таблицы
./analyze.sh > results/summary.md
```

Готовый результат прогона лежит в `results/` — его можно читать, не запуская ничего.

Сырые JSON хранятся сжатыми (26 МБ несжатых артефактов в репозитории с примерами — перебор), но остаются полностью перепроверяемыми:

```bash
# любое утверждение из сводки можно проверить руками
zcat results/jellyfin/syft.json.gz | jq '[.artifacts[] | select(.name|test("ffmpeg";"i"))]'
zgrep -c CVE-2026-8461 results/*/grype.json.gz
```

`analyze.sh` читает и сжатые, и обычные файлы, поэтому сводку можно перегенерировать как из готового снимка, так и после свежего прогона.

## Что внутри

| Файл | Роль |
|---|---|
| `scanners.env` | пины версий сканеров |
| `targets.env`, `targets/*/Dockerfile` | цели и способы поставки FFmpeg |
| `lib.sh` | обёртки над сканерами |
| `run-scan.sh` | прогон, сырые JSON без интерпретации |
| `record-environment.sh` | версии, digest'ы, дата |
| `analyze.sh` | разбор JSON в таблицы |
| `results/` | артефакты прогона и `summary.md` |

Разбор намеренно отделён от прогона: сырые JSON остаются рядом, поэтому любую строку сводки можно перепроверить руками — и это стоит делать.

## Защита от самообмана

Утверждение «сканер не нашёл» ничего не стоит, если компонента в образе нет. Поэтому перед сканированием `run-scan.sh` **проверяет, что FFmpeg физически присутствует** в каждой цели, и пишет результат в `results/<цель>/ffmpeg-present.txt`. Во всех пяти целях — `present`.

Для контрольной пары проверяется ещё и **идентичность самого бинарника**: `run-scan.sh` сверяет `sha256sum` файла `/usr/bin/ffmpeg` в обеих целях и пишет вердикт в `results/control-binary-identity.txt`. Если хеши разойдутся, вывод «разница только в имени пакета» станет неверным — поэтому это проверяется, а не декларируется.

Артефакты дополнительно валидируются структурно: `grype.json` без `.matches`, `trivy.json` без `.Results`, `osv.json` без `.results` помечаются в `errors.txt` как недостоверные. Это не теория — на первом прогоне у цели `distro` сорвалась загрузка базы grype, и без проверки пустой результат выглядел бы как «уязвимостей нет».

Вторая страховка — колонка «всего находок». Она показывает, что инструмент отработал и образ увидел: 380 находок у grype в Jellyfin при нуле по FFmpeg означают слепое пятно, а не сломанный прогон.

Третья — сырой `grep` по JSON мимо `jq`-фильтров при разборе результатов. Ложное «не нашёл» из-за кривого фильтра обесценило бы весь стенд.

## Границы эксперимента

- **Механизм воспроизводим, точные числа — нет.** Это разные вещи, и их стоит развести явно.

  Воспроизводится **устройство эксперимента**: версии сканеров пиновые, донор и базовый образ закреплены по digest, бинарник osv-scanner проверяется по sha256, идентичность бинарника в контрольной паре сверяется прогоном. Повторив шаги, вы получите тот же **вывод**: переименование пакета обнуляет покрытие.

  Не воспроизводятся **конкретные числа**. Базы уязвимостей живые: grype и trivy обновляют свои БД, osv-scanner вообще обращается к данным OSV.dev онлайн, а версии пакетов в `debian:12-slim` и `jellyfin/jellyfin:10.11.9` со временем получают новые advisory. Поэтому «657 находок» — это снимок на **2026-07-31**, а не константа. Состояние баз на момент прогона записано в `results/environment.txt`.

  Практический вывод: сравнивайте не абсолютные числа, а разницу внутри одного прогона — именно она и доказывает механизм.
- **Не рейтинг инструментов.** У syft другая задача — инвентаризация, а не поиск уязвимостей, поэтому его результаты стоят в отдельной таблице. Grype, trivy и osv-scanner v2 сравниваются на равных: все три получают один и тот же образ.
- **Ветка osv-scanner важна.** Версии 1.x работали только по SBOM и манифестам, и сравнивать их со сканерами образов было бы некорректно. Здесь используется 2.4.0 с режимом `scan image`, который читает образ напрямую.
- **SPDX-экспорт к сканированию отношения не имеет.** Файл `syft-spdx.json` сохраняется как переносимый SBOM для внешних потребителей. В поиске уязвимостей он не участвует: osv-scanner v2 читает образ напрямую. (В ветке 1.x всё было наоборот — она умела работать только по SBOM, и нативный `syft-json` не принимала: `JSON document does not contain spdxVersion field`.)
- **Alpine 3.20 помечен как EOL** — grype об этом честно предупреждает, данные по нему могут быть неполными. На вывод это не влияет: цель `vendored` нужна для проверки идентификации компонента, а не полноты advisory.

## Побочная находка: тег образа не равен версии внутри

При подготовке стенда выяснилось, что образ `jrottenberg/ffmpeg:8.1.2-alpine320` содержит FFmpeg, который представляется как **8.1**, и не содержит фикса CVE-2026-8461.

Проверка — по маркеру из коммита `374b726f`, добавившего сообщение об ошибке `slice_height ... is not aligned to chroma vertical subsampling`:

| Источник | `aligned to chroma` | `impossible slice height` |
|---|---|---|
| исходники FFmpeg `n8.1.2` | есть | есть |
| исходники FFmpeg `n8.1` | **нет** | есть |
| собранный пакет Alpine `ffmpeg-libavcodec 8.1.2` (`libavcodec.so.62.28.102`) | есть | — |
| `jrottenberg/ffmpeg:8.1.2-alpine320` | **нет** | есть |

Две проверки, без которых вывод был бы шатким:

1. **Маркер сверен с исходниками.** `impossible slice height` существует и до фикса — по ней вывод получился бы обратным. Уникальна для 8.1.2 только `aligned to chroma`.
2. **Маркер переживает компиляцию.** В реальной собранной 8.1.2 из репозитория Alpine строка на месте, при этом контрольный запрос по той же библиотеке находит `magicyuv` (2 вхождения) — метод рабочий, а не «ничего не находит в принципе».

Независимо это подтверждает grype: он помечает бинарник из образа как подверженный CVE-2026-8461.

Вывод практический: **тег образа — не доказательство версии содержимого**, и проверять надо сам артефакт.
