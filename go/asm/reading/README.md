# reading — как снять дизасм-листинги

Материал для статьи «Как читать дизассемблер» (серия «Go assembly», статья №2).

## Как снять листинги

```bash
cd digital-cookbook/go-asm
chmod +x reading/gen_listings.sh
./reading/gen_listings.sh
```

Скрипт кладёт результат в `reading/listings/`:

- `dotGeneric.txt` — `-S`-дамп функции `dotGeneric` (чистый Go, golden-реализация).
- `dotAVX2_objdump.txt` — дизасм рукописного `dotAVX2` (`dot_amd64.s`) из тестового бинарника.
- `dotAVX2_objdump_raw.txt` — сырой вывод `go tool objdump` без исправлений (см. ниже).
- `dotprod_all.txt` — полный `-S`-дамп пакета `dotprod` (сырьё, из которого вырезан `dotGeneric.txt`).
- `bench.txt`, `bench-benchstat.txt` — числа для статьи №4 (см. корневой README).

## Что искать в листингах

**`dotGeneric.txt`** — доказательство, что компилятор Go **не** авто-векторизует
скалярный цикл `for i := range a { s += a[i]*b[i] }`:

```
MULSD	(DI)(CX*8), X1
ADDSD	X1, X0
```

Скалярные SSE2-инструкции (`MULSD`/`ADDSD`, работают с одним `float64` за раз),
никаких `VFMADD…`/`VMULPD…` (AVX/AVX2, несколько `float64` за раз) в листинге нет —
это ключевой факт статьи №2: за автовекторизацию идиоматичного Go-цикла
рассчитывать нельзя, руки нужны свои (или avo, см. статью №4).

**`dotAVX2_objdump.txt`** — рукописный `dot_amd64.s` использует AVX2+FMA:

```
vfmadd231pd ymm0, ymm1, ymm2   ; горячий цикл, 4 float64 за такт
vfmadd231sd xmm0, xmm1, xmm2   ; скалярный хвост (n % 4)
```

`VFMADD231PD`/`VFMADD231SD` — fused-multiply-add за одну инструкцию
(`Y0 += Y1*Y2`), это то самое ускорение, которое статья №3 объясняет вручную,
а статья №4 — через генерацию avo.

## Известное ограничение тулчейна (важно для статьи)

На хосте, где сняты эти листинги (Go 1.26.3, windows/amd64), встроенный
`go tool objdump` (пакет `golang.org/x/arch/x86/x86asm`) **не распознаёт
VEX-кодированные FMA3-инструкции** (`VFMADD231PD`/`VFMADD231SD`). Байты
читаются корректно, но начиная с первой `VFMADD` мнемоники "уплывают" —
вместо `VFMADD231PD` и последующих инструкций печатается мусор
(`RORB`, `ADCB`, `LRET`…). Смотри `dotAVX2_objdump_raw.txt` — это сырой,
непочиненный вывод, оставлен как есть для сравнения/демонстрации проблемы.

`gen_listings.sh` детектирует эту ситуацию и, если доступен `python`
(`python3` или `python`) с пакетом `capstone` (`pip install capstone`),
передекодирует те же самые байты через Capstone 5 — у него декодер VEX/AVX2/FMA3
полный и корректный. Итоговый (починенный) листинг уходит в
`dotAVX2_objdump.txt`. Если `capstone` не установлен, скрипт использует сырой
вывод `objdump` как есть, с предупреждением в шапке файла — для статьи в этом
случае нужно установить `capstone` и перегенерировать листинги.

Это не баг стенда — это реальное ограничение `go tool objdump` на данной
версии Go, само по себе интересный факт для статьи №2 (инструменты для чтения
дизасма тоже могут врать, если инструкция для них экзотическая).
