# go-net-http — сервисы на стандартной библиотеке Go

Живые примеры к статье про `net/http` на [khorost.tech](https://khorost.tech). Тезис
статьи и стенда простой: **для большинства HTTP-сервисов достаточно стандартной
библиотеки** — стандартный роутер Go 1.22 (метод + путь в паттерне) плюс
middleware-функции покрывают маршрутизацию, сквозную логику, таймауты и клиента.
Фреймворк (gin, chi, echo) — осознанный выбор под конкретную нужду, а не
обязательная отправная точка. Поэтому здесь **только stdlib**, без единой внешней
зависимости — контраст с фреймворками разбирается в статье концептуально.

Один модуль `tech.khorost/go-net-http-cookbook`, четыре подкаталога — по узлам
типового сервиса: маршрутизация, middleware, сервер, клиент.

## Запуск

    # весь модуль: сборка, vet, тесты
    go build ./...
    go vet ./...
    go test ./...

Тесты не поднимают блокирующий сервер: маршруты и middleware проверяются через
`net/http/httptest` (`NewRequest` + `NewRecorder`), клиент — против управляемого
`httptest.Server`. Тест сервера поднимает слушатель на `:0` (свободный порт от
ОС) и сразу инициирует graceful-shutdown.

## Что где

| Подкаталог | Тема | Содержимое |
|---|---|---|
| [`router/`](router) | Маршрутизация | `http.ServeMux` с паттернами Go 1.22 `"GET /users/{id}"`, извлечение сегмента через `r.PathValue("id")`, отдельный `POST /users` |
| [`middleware/`](middleware) | Сквозная логика | middleware как `func(http.Handler) http.Handler`: логирование (счётчик), `Recover` (паника → контролируемый 500), `RequestID` в `context`; `Chain` склеивает слои |
| [`server/`](server) | HTTP-сервер | `http.Server` с явными `ReadTimeout`/`ReadHeaderTimeout`/`WriteTimeout`/`IdleTimeout` и graceful-shutdown через `srv.Shutdown(ctx)`; комментарий про опасность `ListenAndServe` без таймаутов (Slowloris) |
| [`client/`](client) | HTTP-клиент | `http.Client` с таймаутом (`http.DefaultClient` его не имеет) и `http.NewRequestWithContext` — отмена по context |

## Что доказывают тесты

| Тест-набор | Проверяет |
|---|---|
| `router` | верный метод+путь → 200 и корректный `id` из `PathValue`; чужой метод → 405; несуществующий путь → 404; `POST /users` с валидным JSON → 201 |
| `middleware` | `Recover` превращает панику обработчика в контролируемый 500 (сам `net/http.Server` панику и так перехватывает и обрывает соединение — слой нужен ради аккуратного ответа и логов/метрик, не ради спасения процесса); `RequestID` доносит id через контекст; `Chain` применяет все слои (счётчик логгера = 1, id доходит, ответ 200) |
| `server` | сконструированный сервер отвечает 200 на живой запрос; graceful-shutdown завершается штатно, `Serve` возвращает `http.ErrServerClosed` |
| `client` | GET против `httptest.Server` возвращает тело; отмена контекста прерывает запрос к медленному серверу с `context.DeadlineExceeded` |

## Таблица версий

| Возможность | Требует | Примечание |
|---|---|---|
| Method-роутинг в `ServeMux` (`"GET /path"`, `{id}`, `PathValue`) | **Go 1.22+** | Ключевая причина, по которой сторонний роутер больше не обязателен для базовых нужд |
| `errors.Is`/`errors.As`, `%w`-обёртывание (в тесте клиента) | Go 1.13+ | Для распаковки ошибки контекста сквозь транспорт |
| Модуль стенда | Go 1.25.0 | Значение из `go.mod`; ниже 1.22 method-роутинг не соберётся |

Всё остальное (`http.Server`, таймауты, `Shutdown`, `http.Client`,
`NewRequestWithContext`, `httptest`) — давно в stdlib и не требует свежих версий.
