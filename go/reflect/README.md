# go-reflect — цена рефлексии на живом стенде

Примеры к статье [«reflect в Go: когда оправдана рефлексия и чего она стоит»](https://khorost.tech/go/go-reflect/) на khorost.tech.
Чистый Go, без docker, только stdlib (`reflect`). Модуль `tech.khorost/go-reflect-cookbook`.

Идея стенда: **операции рефлексии (чтение полей, теги, изменение через адресуемый Value, три «закона») покрыты тестами, а цена — бенчмарками** прямой доступ vs reflect.

## Запуск

    go build ./...
    go vet ./...
    go test ./...

    go test -bench=. -benchmem -run=^$ ./access/    # прямой доступ vs reflect

## Что где

| Подкаталог | Тема | Содержимое |
|---|---|---|
| [`access/`](access) | Type/Value/Kind | чтение поля по имени, сбор `json`-тегов (как сериализаторы), изменение поля через **адресуемый** `reflect.Value` (нужен указатель; неэкспортируемые нельзя), `Kind`-switch по динамическому типу; бенчи цены |

## Три «закона рефлексии» (из тестов)

1. `reflect.ValueOf`/`TypeOf` — из значения в `reflect.Value`/`Type`.
2. `.Interface()` — обратно из `reflect.Value` в `any` (с боксингом).
3. **Чтобы менять значение через reflect, оно должно быть адресуемым** — нужен указатель (`SetString` на `User{}` без `&` даёт ошибку), а неэкспортируемые поля неизменяемы (`CanSet() == false`).

## Числа: цена рефлексии (сверено)

`access/bench_test.go` на `go1.26.3 windows/amd64`, `-count=3`, ориентировочно:

| Бенчмарк | ns/op | allocs | Во сколько раз дороже прямого |
|---|---|---|---|
| `BenchmarkReadDirect`        | ~1.4  | 0 | 1× (эталон) |
| `BenchmarkReadFieldByIndex`  | ~10   | 0 | **~7×** — reflect по заранее известному индексу поля |
| `BenchmarkReadFieldByName`   | ~80   | 0 | **~55×** — поиск поля по строковому имени на каждом вызове |
| `BenchmarkSetDirect`         | ~2.5  | 0 | 1× (эталон) |
| `BenchmarkSetReflect`        | ~72   | 0 | **~28×** — запись через `FieldByName(...).SetString` |
| `BenchmarkToMapDirect`       | ~210  | 4 (368 B) | 1× (эталон) |
| `BenchmarkToMapReflect`      | ~360–530 | 2 (336 B) | **~2×** — сериализация структуры в `map[string]any` |

Как читать:

- **на чистом доступе к полю reflect дороже в разы-десятки раз** — ~7× по индексу, ~55× по имени. Поиск поля по строке (`FieldByName`) — самая дорогая часть; сериализаторы кешируют индексы полей один раз, отсюда `ByIndex` вместо `ByName`;
- **на реалистичной сериализации в map разрыв сжимается до ~2×** — там доминирует аллокация самой карты и боксинг значений, а не reflect; поэтому «reflect всегда убивает перформанс» — упрощение, надо мерить конкретный путь;
- аллокации на чтении/записи — 0: reflect не аллоцирует сам по себе, аллокации приходят от боксинга результата в `any` и построения структур данных.

Практический вывод: reflect оправдан там, где тип неизвестен на этапе компиляции (сериализация, ORM, валидаторы, DI) и вызывается не в самом горячем цикле. В горячем пути — кешируйте `reflect.Type`/индексы полей, а лучше сгенерируйте код (`go generate`, `easyjson`-подход) или используйте дженерики, где тип известен.

## Версии

Проверено 2026-07 на **Go 1.26.3** (локально): тесты зелёные, бенчи воспроизводятся. Модуль объявляет `go 1.25.0` (минимум). Зависимостей нет — только `reflect`, `strings`, `fmt`.
