Стенд json-v2: сводные находки
===============================

Три конфигурации на одном payload (`payload.All()`: small / large-array /
deep-nested / map-heavy), Go 1.27.0, windows/amd64, AMD Ryzen 7 5800X3D:

  v1-old    — encoding/json на прежнем движке (GOEXPERIMENT=nojsonv2)
  v1-on-v2  — encoding/json в 1.27 как есть, без правок кода (умолчание)
  v2-api    — явный переход на encoding/json/v2

Важная оговорка про саму колонку v1-old: это Go 1.27, собранный с флагом
отката, а НЕ Go 1.26. Замер отвечает на вопрос «что даёт флаг отката»,
а не «чем 1.27 отличается от 1.26» — это разные вопросы, и первый
результат легко принять за второй.

Серия — ПЯТЬ полных прогонов (`scripts/bench-all.sh 5`), не два: разброс
на двух прогонах оказался недостаточным, чтобы отличить эффект от шума
машины (см. `results/01-bench.txt`). Ниже — числа медианного прогона.

ГЛАВНЫЕ ЧИСЛА
-------------

Обновление тулчейна (v1-old -> v1-on-v2, код не менялся) стабильно
замедляет DECODE во всех четырёх формах:

  Decode/small          1064 -> 2114 нс/оп     (1.99x, разброс ~20%)
  Decode/large-array  1015398 -> 1988132 нс/оп (1.96x, разброс ~20%)
  Decode/deep-nested    49489 -> 79966 нс/оп   (1.62x, разброс 11-31%)
  Decode/map-heavy    3200386 -> 4891576 нс/оп (1.53x, разброс 13-24%)

Encode/small тоже устойчиво медленнее: 278.5 -> 466.5 нс/оп (1.68x,
разброс 1.8% и 15.9% на краях — эффект больше разброса в обоих случаях).

Аллокации — детерминированы (разброса между прогонами нет), и именно они
показывают выигрыш v2 API:

  Encode/map-heavy, allocs/op: 4002 (v1-old) -> 2005 (v1-on-v2) -> 4 (v2-api)

Промежуточная точка (v1-on-v2) уже вдвое экономнее v1-old по аллокациям
кодирования карт — сам движок под неизменным encoding/json стал здесь
эффективнее. Явный переход на v2 API убирает почти все аллокации
кодирования этой формы (4 против 4002 у v1-old — эффект на три порядка).
По decode аллокации у v2-api тоже ниже, чем у v1-old, на всех формах
(например Decode/large-array: 15005 -> 11012 allocs/op), но там выигрыш
на десятки процентов, а не на порядки.

НЕ ДОКАЗАНО, вывод отозван: «v2 API быстрее прежнего движка по ВРЕМЕНИ».
На первый взгляд время decode у v2-api ниже, чем у v1-old:
  Decode/small:      946.5 (v2-api) против 1064 (v1-old)     — разница 11%
  Decode/map-heavy: 2960816 (v2-api) против 3200386 (v1-old) — разница 7.5%
Но разброс внутри серии — 19-20% на small и 10-13% на map-heavy: эффект
меньше шума. По времени v2-api откатывает decode примерно к уровню
v1-old (после того как переход на 1.27 без правок кода его удвоил), но
заявлять, что v2 API БЫСТРЕЕ прежнего движка, пять прогонов не позволяют.

Формулировка для статьи: обновление тулчейна замедляет декодирование в
полтора-два раза; переход на v2 API возвращает время decode примерно к
прежнему уровню, но не доказанно ниже него. Выигрыш v2 API доказан
только по аллокациям.

СТРОГОСТЬ encoding/json ПОВЕРХ v2 (задача 4, results/02-strictness.txt)
-------------------------------------------------------------------------

Проверено на шести случаях (duplicate-keys, unknown-field,
case-insensitive-match, invalid-utf8, trailing-data, null-into-int) —
это не полная матрица поведения JSON-парсера, а выборка.

1. Совместимость encoding/json (v1-old против v1-on-v2): совпадают по
   всем 6 случаям. encoding/json, работающий поверх v2, сохраняет
   прежнюю (нестрогую) семантику Unmarshal — код, который не
   переписывали под v2 API, ведёт себя как раньше.

2. Строгость explicit encoding/json/v2 против encoding/json в той же
   сборке (v1-on-v2, где пакет v2 доступен): различаются по 2 из 6
   случаев. duplicate-keys и invalid-utf8 — encoding/json принимает,
   encoding/json/v2 отвергает. unknown-field, case-insensitive-match,
   null-into-int — оба API принимают. trailing-data — оба отвергают
   (это поведение json.Decoder, не специфика v2).

Вывод: строгость v2 реальна и проверяема на этих случаях — но живёт в
API (encoding/json/v2), а не в движке (encoding/json поверх v2).
Обновление тулчейна поведение encoding/json НЕ меняет.

Дополнительный факт про откат: под GOEXPERIMENT=nojsonv2 пакеты
encoding/json/v2 и encoding/json/jsontext исключаются build-ограничениями
ЦЕЛИКОМ (см. `bench_v2_test.go`, `stream_test.go` — оба под тегом
`goexperiment.jsonv2`). Откат на прежний движок отнимает не только новое
поведение encoding/json, но и сами пакеты — вместе с возможностью
сравнить их с прежним движком в одной сборке.

ПОТОКОВЫЙ ЗАМЕР (results/03-stream.txt)
-----------------------------------------

10000 строк NDJSON (`payload.NDJSON(10000)`), два прогона:

  BenchmarkStreamV1Decoder: 19.6M / 19.4M нс/оп, 4814327 B/op, 150018 allocs/op
  BenchmarkStreamJSONText:   1.73M / 1.88M нс/оп,    8744 B/op,     18 allocs/op

Разница на порядок и по времени, и по аллокациям — но важно, ЧТО именно
сравнивается. `decodeAllV1` разбирает каждую строку в `map[string]any`
через `json.Decoder.Decode` — полноценная материализация Go-значений.
`decodeAllJSONText` читает `jsontext.NewDecoder.ReadValue` — это проход по
сырым JSON-значениям БЕЗ распаковки в Go-структуры. Это не «v2 декодирует
быстрее», а «проход по токенам без материализации значений дешевле, чем
материализация в map[string]any» — ожидаемый результат, показывающий,
для какой задачи годится потоковый API jsontext (фильтрация/пересылка
без полного анмаршалинга), а не общее ускорение decode в v2.

ЧТО ЗДЕСЬ ДОКАЗАТЕЛЬНО, А ЧТО НЕТ
-----------------------------------

Доказательно (переживает разброс по пяти прогонам или детерминировано):
  - обновление тулчейна (1.27 без правок кода) замедляет decode в 1.5-2x
    на всех четырёх формах payload;
  - Encode/small тоже устойчиво медленнее после обновления (1.68x);
  - v2 API снижает аллокации кодирования map-heavy на три порядка
    (4002 -> 4) и аллокации decode на десятки процентов на всех формах;
  - encoding/json без переписывания кода не меняет строгость на
    проверенных 6 случаях; строгость v2 реальна, но требует явного
    перехода на пакет encoding/json/v2;
  - GOEXPERIMENT=nojsonv2 исключает пакеты v2 и jsontext из сборки
    целиком, не только их поведение;
  - потоковое чтение через jsontext на порядок дешевле по времени и
    аллокациям, чем полный анмаршалинг той же строки в map[string]any
    (но это сравнение разного объёма работы, см. раздел выше).

НЕ доказано (эффект в пределах разброса серии или не проверялось):
  - что v2 API быстрее прежнего движка (v1-old) по ВРЕМЕНИ decode —
    разница 7.5-11% при разбросе 10-20%, вывод отозван;
  - что разброс 15-31%, видный на отдельных формах, — свойство
    какой-то одной конфигурации: на пяти прогонах он проявился во
    всех трёх конфигурациях, включая v1-old (Decode/deep-nested 30.8%)
    и v2-api (Decode/deep-nested 15.3%) — это свойство машины (Windows,
    шумная ОС без изоляции ядер), а не движка.

ЧЕГО ЗАМЕР НЕ ПОКАЗЫВАЕТ
--------------------------

  - Строгость проверена на шести случаях — не полная матрица поведения
    парсера; для случаев за пределами списка выводов нет.
  - Потоковый замер снят на однородном NDJSON фиксированной длины строки
    (`payload.NDJSON`) — разница поведения аллокатора не доказывает
    константность на другом профиле данных (переменная длина строк,
    вложенные структуры, редкие большие записи).
  - Retained-память после сборки мусора не мерилась — `TotalAlloc` и
    `allocs/op` считают ВСЕ выделения за время работы, а не то, что
    осталось живым к концу. Про пиковое или итоговое потребление памяти
    процессом замер ничего не говорит.
  - Замер выполнен на одной машине (Windows, AMD Ryzen 7 5800X3D) —
    абсолютные числа и наблюдаемый разброс могут не переноситься на
    Linux/производственное окружение с другой политикой планировщика.
  - CPU-профиль не снимался: где именно уходит время внутри decode/encode
    (аллокатор, парсинг, рефлексия) — вопрос вне этого стенда.
