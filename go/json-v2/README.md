# json-v2 — стенд к статьям про JSON-движок Go 1.27

Три конфигурации JSON-кодека на одном payload: прежний движок (флаг
отката), `encoding/json` в Go 1.27 без единой правки кода и явный переход
на `encoding/json/v2`. Плюс отдельный замер строгости и потоковое чтение
через `encoding/json/jsontext`.

Статья: https://khorost.tech/go/go-json-v2/

## Что внутри

| Файл/каталог | Что |
|---|---|
| `payload/payload.go` | четыре формы данных (small/large-array/deep-nested/map-heavy) и генератор NDJSON для потокового замера |
| `buildmode/buildmode.go` | режим сборки читается из `debug.ReadBuildInfo()`, а не из переменной окружения (см. «Ловушки») |
| `cmd/buildmode-check` | контроль: подтверждает, что бинарник собран именно в ожидаемом режиме, ДО того как замер начнётся |
| `cmd/strictness-demo` | шесть случаев (duplicate-keys, unknown-field, case-insensitive-match, invalid-utf8, trailing-data, null-into-int) через `encoding/json` и, где доступен, `encoding/json/v2` |
| `bench_v1_test.go` | `BenchmarkV1Encode`/`BenchmarkV1Decode` через `encoding/json` — собираются в обоих режимах |
| `bench_v2_test.go` | `BenchmarkV2Encode`/`BenchmarkV2Decode` через `encoding/json/v2`, тег `goexperiment.jsonv2` — под откатом файл не собирается вовсе |
| `stream_test.go` | потоковое чтение NDJSON: `json.Decoder` в `map[string]any` против `jsontext.ReadValue`, тег `goexperiment.jsonv2` |
| `scripts/bench-all.sh` | гоняет все три конфигурации по N прогонов, пишет `results/01-bench.txt` |
| `scripts/verify-strictness.sh` | гоняет `strictness-demo` в обоих режимах, пишет `results/02-strictness.txt`, падает с `rc=1`, если v2 API не строже encoding/json ни на одном случае |
| `results/` | сырые прогоны и `00-findings.txt` — сводные находки со всеми оговорками |

## Проверка

```bash
GOTOOLCHAIN=go1.27.0 go vet ./... && GOTOOLCHAIN=go1.27.0 go test ./...
```

Оба режима (`GOEXPERIMENT=""` и `GOEXPERIMENT=nojsonv2`) собираются и
проходят тесты — build-теги на файлах с импортом v2/jsontext следят,
чтобы под откатом эти файлы просто не участвовали в сборке, а не падали.

Замеры снова не гонять без нужды — числа уже сняты и лежат в `results/`:

```bash
./scripts/bench-all.sh 5          # -> results/01-bench.txt
./scripts/verify-strictness.sh    # -> results/02-strictness.txt
GOTOOLCHAIN=go1.27.0 go test -run '^$' -bench BenchmarkStream -benchmem .
# ^ без GOEXPERIMENT=nojsonv2 — стриминг собирается только под умолчание
#   1.27 (goexperiment.jsonv2 включён по умолчанию), под откатом файла
#   с этими бенчами в сборке нет вовсе, см. «Ловушки» ниже.
```

## Ловушки

**`GOEXPERIMENT` — флаг сборки, а не рантайма.** Собранный не в том
режиме бинарник молча померяет не то: «разницы нет» и «флаг не
применился» на выходе выглядят одинаково. Поэтому текущий режим стенд
читает не из переменной окружения (её могли не передать конкретно в
команду сборки бенча), а из самого бинарника — `buildmode.Current()`
парсит `debug.ReadBuildInfo()`, где значение `GOEXPERIMENT` вшито при
компиляции. `cmd/buildmode-check` подтверждает режим ДО замера в
`bench-all.sh`; `verify-strictness.sh` делает то же самое по заголовку
вывода `strictness-demo`.

**Под откатом пакеты v2 исключены build-ограничениями целиком.**
`GOEXPERIMENT=nojsonv2` убирает не только новое поведение
`encoding/json` — пакеты `encoding/json/v2` и `encoding/json/jsontext`
в этой сборке отсутствуют вовсе. Файл, который их импортирует, в режиме
отката не собрался бы и утащил бы за собой весь тестовый пакет, включая
уже рабочие бенчи v1. Поэтому `BenchmarkV2*` (`bench_v2_test.go`) и
потоковый замер (`stream_test.go`) разведены по тегу
`//go:build goexperiment.jsonv2` — под откатом они просто выпадают из
сборки, а не ломают её.

**Пустая секция отчёта — это не ошибка с точки зрения `go test`.**
`go test -bench` возвращает `rc=0`, даже если паттерн `-bench` не
совпал ни с одной функцией: опечатка в имени или файл, случайно
исключённый тегом сборки, дают тихий пустой прогон, неотличимый от
успеха, пока кто-то не откроет файл руками. Поэтому `bench-all.sh`
пишет каждый прогон во временный файл и проверяет наличие `ns/op` ДО
того, как строка попадёт в общий отчёт — падает с `rc=1`, если секция
оказалась бы пустой.

**Числа снимаются сериями, не одним прогоном.** Два прогона поначалу
выглядели так, будто нестабилен именно `v1-on-v2` — но на пяти прогонах
широкий разброс (15-31%) оказался во всех трёх конфигурациях, включая
`v1-old` и `v2-api`. Это свойство машины (Windows, шумная ОС), не
движка. Если разброс шире эффекта — вывода нет, и `results/00-findings.txt`
говорит об этом прямо, а не молчит. Замер при этом блочный (`bench-all.sh`
гонит пять прогонов `v1-old`, затем пять `v1-on-v2`, затем пять `v2-api`,
а не вперемешку) — конфигурация совпадает с положением на оси времени, и
это не проконтролировано: то, что `v2-api` шёл последним и всё же оказался
быстрее всех, эту проблему НЕ снимает и версию «машина грелась» не
опровергает — `v2-api` гоняет другой API и другой набор бенчмарков, а не
контрольную точку того же измерения. Для выводов о своей машине нужен
замер с чередованием или рандомизацией конфигураций, которого здесь нет.

**`v1-old` — это Go 1.27 с флагом отката, а не Go 1.26.** Замер отвечает
на вопрос «что даёт GOEXPERIMENT=nojsonv2 в текущем тулчейне», а не «чем
1.27 отличается от предыдущей версии».
