# go-memory — память Go вглубь на живом стенде

Примеры к статье [«Память Go: указатели, стек, куча, escape-анализ»](https://khorost.tech/go/) на khorost.tech. Стенд показывает **не на словах, а через реальный вывод компилятора**, что уходит в кучу, а что остаётся на стеке: строки escape-анализа (`go build -gcflags=-m`) и аллокации в бенчмарках (`allocs/op`).

Чистый Go, без docker, только stdlib. Один модуль `tech.khorost/go-memory-cookbook`, подкаталог `escape/` — набор показательных функций, каждая иллюстрирует одно правило escape-анализа.

Идея стенда: **корректное поведение покрыто тестами (`go test ./...` всегда зелёный), а «на стеке или в куче» видно глазами** — либо в строках `-gcflags=-m`, либо в колонке `allocs/op` бенчей.

## Запуск

    # весь модуль: сборка, vet, тесты
    go build ./...
    go vet ./...
    go test ./...

    # escape-анализ: что осталось на стеке, что ушло в кучу
    go build -gcflags=-m ./...
    # детальнее (почему именно так):
    go build -gcflags='-m -m' ./...

    # бенчмарки аллокаций (числа снимайте у себя)
    go test -bench=. -benchmem -run='^$' ./escape/

> Для go-команд в этом стенде: `GOPROXY=https://go.khorost.tech,direct`.

## Как читать escape-анализ

`go build -gcflags=-m ./...` печатает решения escape-анализа по каждой функции. Флаг `-m` можно удвоить (`-m -m`) — компилятор объяснит цепочку рассуждений подробнее. Ключевые строки:

| Строка `-gcflags=-m` | Что значит |
|---|---|
| `X does not escape` | значение/аргумент не переживает вызов — остаётся на **стеке**, аллокации нет |
| `X escapes to heap` | значение переживает вызов — размещается в **куче** |
| `moved to heap: X` | локальная переменная перенесена со стека в **кучу** (например, вернули её адрес) |
| `inlining call to …` | функция заинлайнена — сопутствующая информация, не про escape |

Правило по сути одно: **уходит в кучу то, что переживает свой кадр стека** (вернули указатель, положили ссылку в долгоживущую структуру, упаковали в интерфейс, захватили замыканием). «Указатель» сам по себе кучу не означает — локальный указатель, не покидающий функцию, живёт на стеке.

## Функции и правила

Каждая функция в [`escape/escape.go`](escape/escape.go) иллюстрирует одно правило. Таблица — что покажет `go build -gcflags=-m ./escape/` (заполнить фактическим выводом):

| Функция | Где живёт | Почему | Ожидаемая строка `-gcflags=-m` |
|---|---|---|---|
| `newOnStack` | стек | адрес локали не покидает функцию | `&Point{...} does not escape` |
| `newOnHeap` | куча | возвращается указатель на локаль | `moved to heap: p` |
| `boxIntoInterface` | куча | боксинг значения в `any` | `x escapes to heap` |
| `leakViaSlice` | куча | ссылка утекает в пакетный срез | `moved to heap: p` |
| `stackArg` | стек | `*Point`-аргумент только читается | `p does not escape` |
| `closureCapture` | куча | переменная захвачена замыканием, переживающим вызов | `moved to heap: n; func literal escapes to heap` |
| `sizeVarMake` | куча | `make([]byte, n)` с непостоянным размером (эскейп по РАЗМЕРУ, не времени жизни) | `make([]byte, n) does not escape` — но бенч даёт 1 alloc |
| `sizeConstMake` | стек | `make([]byte, 64)` с константой | `make([]byte, 64) does not escape` — 0 allocs |

> Плейсхолдеры замените точным выводом `go build -gcflags=-m ./escape/` на своей версии Go — формулировки компилятора могут слегка отличаться между релизами.
>
> Пара `sizeVarMake`/`sizeConstMake` показывает важный нюанс: `-gcflags=-m` метит **обе** как «does not escape», но `SizeVarMake` всё равно даёт **1 alloc/op** (размер-переменную нельзя разложить на стеке), а `SizeConstMake` — 0. «does not escape» ≠ «без аллокации»; окончательный вердикт даёт `allocs/op` в бенче (`go test -bench='Size' -benchmem -run='^$' ./escape/`).

## Числа бенчмарков

Числа ниже сверены на `go1.26.3 windows/amd64` (`-benchmem -count=3`, ориентировочно). Бенчи в [`escape/escape_test.go`](escape/escape_test.go) печатают `allocs/op` — прямое доказательство «стек vs куча». Стековые функции дают 0 аллокаций, убегающие — >0. Значения аккумулируются в `sink`-переменные, чтобы компилятор не выкинул вызовы как мёртвый код.

Команда: `go test -bench=. -benchmem -run='^$' ./escape/`. Заполнить фактическим выводом:

| Бенчмарк | ns/op | allocs/op | Что показывает |
|---|---|---|---|
| `BenchmarkOnStack` | ~0.24 | 0 | значение остаётся на стеке — аллокаций нет |
| `BenchmarkOnHeap` | ~16 | 1 (16 B) | указатель на локаль → 1 аллокация в куче на вызов |
| `BenchmarkBoxInterface` | ~13 | 1 (8 B) | боксинг в `any` → аллокация упаковки (значения > 255; малые int кэшируются → 0) |
| `BenchmarkStackArg` | ~0.53 | 0 | `*T`-аргумент не утекает — аллокаций нет |

## Связка со сборкой мусора и профилированием

Escape-анализ — это про **давление на сборщик мусора (GC)**. Всё, что уходит в кучу, потом кто-то должен освободить: чем больше значений «убегает», тем чаще и дольше работает GC, тем выше latency под нагрузкой. Стековые значения освобождаются бесплатно при возврате из функции — GC их не касается. Поэтому убрать лишний escape (например, не возвращать указатель там, где хватит значения) — частый и дешёвый способ снять нагрузку с GC на горячем пути.

Как измерять у себя:

- **`go test -benchmem`** — колонки `allocs/op` и `B/op` в бенчах: сколько аллокаций и байт на операцию. Первый экран диагностики.
- **`go build -gcflags=-m`** — почему именно эти аллокации: какая переменная и по какой причине ушла в кучу.
- **pprof alloc-профиль** — `go test -memprofile=mem.out`, затем `go tool pprof -alloc_space mem.out` (или `-alloc_objects`): где в коде рождаются аллокации кучи под реальной нагрузкой.

Типовой цикл оптимизации: нашли горячую аллокацию в `-benchmem`/pprof → посмотрели причину в `-gcflags=-m` → убрали escape (значение вместо указателя, переиспользование буфера, `sync.Pool`) → перемерили.

## Версии

Проверено на **Go 1.25+** (`go build/vet/test ./...` зелёные). Модуль объявляет `go 1.25.0` — минимальная версия. Зависимостей нет — только стандартная библиотека (`testing`). Точные строки `-gcflags=-m` и числа бенчмарков машинозависимы и зависят от версии компилятора — снимайте их на своей сборке.
