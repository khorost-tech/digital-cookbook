# generics — дженерики Go на живом стенде

Примеры к статье про дженерики в Go на khorost.tech.
Чистый Go, без docker, без внешних зависимостей — только stdlib.
Один модуль `tech.khorost/generics-cookbook`, три подкаталога — по одному сюжету.

Идея стенда: показать **реальное** поведение дженериков Go, а не идеализированное.
Реализация в Go — это **GC-shape stenciling + словари**: компилятор генерирует
копию кода не на каждый тип (как мономорфизация в C++), а на каждую «форму»
(shape); типы одной формы делят одну копию плюс скрытый словарь (dictionary) с
метаданными и указателями на методы. Отсюда три следствия, каждое в своём пакете.

## Запуск

    # весь модуль: сборка, vet, тесты корректности
    go build ./...
    go vet ./...
    go test ./...

    # бенчмарки (числа снимайте у себя — в стенде их намеренно нет)
    go test -bench=. -benchmem ./...

    # размер бинарей (сюжет binsize)
    mkdir -p bin
    go build -o bin/generic ./binsize/cmd/generic
    go build -o bin/iface   ./binsize/cmd/iface
    ls -l bin/            # сравнить размеры

## Что где

| Подкаталог | Сюжет | Что демонстрирует |
|---|---|---|
| [`numeric/`](numeric) | Дженерики **выигрывают** | Сумма числового среза: дженерик специализируется по форме (int/float64) и по скорости ≈ рукописному коду, а `interface{}` вынужден боксить элементы — заметно медленнее и с аллокациями |
| [`dispatch/`](dispatch) | **Контринтуитивный** случай | Вызов метода через constraint для **указательных** типов идёт через словарь и НЕ девиртуализируется — дженерик не быстрее обычного интерфейсного dispatch (иногда чуть медленнее) |
| [`binsize/`](binsize) | **Размер бинаря** | Инстанцирование дженерика для многих типов раздувает бинарь **скромно** (shape stenciling шарит копии по форме), в отличие от полной мономорфизации C++ |

## Сюжет 1 — numeric: где дженерики выигрывают

`numeric.go`:
- `SumGeneric[T Number](xs []T) T` — дженерик по constraint `Number` (`~int | ... | ~float64`);
- `SumInt([]int) int`, `SumFloat64([]float64) float64` — рукописные эталоны;
- `SumIface(xs []any) float64` — версия через `interface{}` с type switch (боксинг).

Гипотеза: для value-типов компилятор специализирует код по форме, поэтому
`_Generic ≈ _Handwritten` при нулевых аллокациях, а `_Iface` заметно медленнее
и аллоцирует (каждый элемент упаковывается в интерфейсное значение; упаковка
чисел > 255 идёт с аллокацией на куче — значения < 256 рантайм кэширует).

Бенчи (`go test -bench=Sum -benchmem ./numeric/`):

| Бенчмарк | ns/op | B/op | allocs/op | Что показывает |
|---|---|---|---|---|
| `BenchmarkSumInt_Generic`        | ~1400  | 0     | 0    | дженерик по форме int |
| `BenchmarkSumInt_Handwritten`    | ~3200  | 0     | 0    | рукописный эталон int |
| `BenchmarkSumInt_Iface`          | ~100000| 96256 | 3841 | боксинг int → аллокации |
| `BenchmarkSumFloat64_Generic`    | ~3300  | 0     | 0    | дженерик по форме float64 |
| `BenchmarkSumFloat64_Handwritten`| ~3700  | 0     | 0    | рукописный эталон float64 |
| `BenchmarkSumFloat64_Iface`      | ~95000 | 98296 | 4096 | боксинг float64 → аллокации |

## Сюжет 2 — dispatch: контринтуитивный случай

`dispatch.go`:
- интерфейс `Shape { Area() float64 }`, реализации указательного вида `*Circle`, `*Rect`;
- `SumAreasGeneric[T Shape](xs []T) float64` — вызывает `x.Area()` через constraint;
- `SumAreasIface(xs []Shape) float64` — обычный интерфейсный dispatch.

Гипотеза (ключевой сюрприз про stenciling): все указатели имеют одну форму и
делят одну копию специализации, поэтому вызов метода внутри дженерика идёт через
**словарь**, а не превращается в прямой вызов. Итог — дженерик **не быстрее**
интерфейса, иногда чуть медленнее из-за лишнего косвенного обращения к словарю.

Бенчи (`go test -bench=Area -benchmem ./dispatch/`):

| Бенчмарк | ns/op | B/op | allocs/op | Что показывает |
|---|---|---|---|---|
| `BenchmarkArea_Generic` | ~12300 | 0 | 0 | вызов Area() через словарь специализации |
| `BenchmarkArea_Iface`   | ~12900 | 0 | 0 | вызов Area() через интерфейсную таблицу |

## Сюжет 3 — binsize: размер бинаря

- `binsize/cmd/generic/main.go` — инстанцирует дженерик-функции (`SumTwoGeneric[T]`,
  `Zero[T]`) для многих типов: int, int8/16/32/64, uint*, float32/64, string;
  результаты печатаются, чтобы компилятор не выкинул вызовы;
- `binsize/cmd/iface/main.go` — то же через одну функцию `SumTwoIface(any, any) any`.

Гипотеза: у Go разница в размере **скромная**. Дженерик генерирует копию кода на
каждую отдельную форму, но типы одной формы её делят, и это не полная
мономорфизация «копия на каждый тип», как в C++. Интерфейсная версия — одна копия
кода на все типы (диспетчеризация в рантайме).

Сборка и сравнение:

    go build -o bin/generic ./binsize/cmd/generic
    go build -o bin/iface   ./binsize/cmd/iface

| Бинарь | Размер | Комментарий |
|---|---|---|
| `bin/generic` | 2 467 328 Б | инстанцирование дженерика по многим формам |
| `bin/iface`   | 2 467 328 Б | одна interface{}-функция |
| разница | **0 байт** в этом прогоне (Windows/go1.26.3) | без раздувания; на Linux у ревьюера ~500 Б из ~2.4 МБ |

## Числа (сверено прогоном)

> Числа в таблицах выше **сверены прогоном** на `go1.26.3 windows/amd64` (`go test -bench=. -benchmem -count=3 ./...` + `go build`). Они ОРИЕНТИРОВОЧНЫЕ и зависят от машины/версии Go/флагов — снимайте у себя. Робастные выводы (а не абсолютные ns): дженерик и рукописный — один порядок и **0 аллокаций** (на int дженерик на этой сборке даже быстрее — артефакт инлайна/кодогена, не общее правило); `interface{}` — в десятки раз дороже и с тысячами аллокаций от боксинга; на указательных типах дженерик **не быстрее** интерфейса (словарь); размер бинаря дженерик vs interface — в этом прогоне **байт-в-байт**, на др. ОС возможна малая разница; порядок вывода — раздувания нет (не мономорфизация).

Проверено: `go build ./... && go vet ./... && go test ./...` — зелёные.
Модуль объявляет `go 1.25.0`. Зависимостей нет — только stdlib.
