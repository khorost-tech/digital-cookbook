# go-slog — структурированное логирование на живом стенде

Примеры к статье [«slog: структурированное логирование в стандартной библиотеке Go»](https://khorost.tech/go/go-slog/) на khorost.tech.
Чистый Go, без docker, только stdlib (`log/slog`). Модуль `tech.khorost/go-slog-cookbook`.

Идея стенда: **вывод логов проверяется тестами** (пишем в `bytes.Buffer`, парсим JSON, сверяем поля), а «как это выглядит вживую» показывает демо `cmd/output`.

## Запуск

    go build ./...
    go vet ./...
    go test ./...

    # реальный вывод разных хендлеров
    go run ./cmd/output

    # бенчмарки способов записи
    go test -bench=. -benchmem -run=^$ ./basic/

## Что где

| Подкаталог | Тема | Содержимое |
|---|---|---|
| [`basic/`](basic) | Базовый slog | JSON/text-хендлеры, уровни и фильтрация, типизированные атрибуты, группы (вложенный объект), `With` (постоянный атрибут), `LogAttrs`; бенчи способов записи |
| [`handler/`](handler) | Свой Handler | `ContextHandler` — декоратор, подставляющий `request_id` из `context` в каждую запись; реализует все 4 метода `slog.Handler` (Enabled/Handle/WithAttrs/WithGroup) |
| [`redact/`](redact) | Маскировка секретов | `LogValuer`-типы (`Secret` → `REDACTED`, `Card` → хвост из 4 цифр) и `RedactKeys` для `ReplaceAttr` (маска по имени ключа); тест `TestBoundaryStructLeaks` закрепляет честную границу — поле типа `Secret` (тот же LogValuer, что как отдельный атрибут даёт `REDACTED`) внутри структуры, отданной в `slog.Any` целиком, **утекает сырым**: LogValue поля не вызывается, `REDACTED` не появляется |

## Реальный вывод (`go run ./cmd/output`, сверено)

JSON-хендлер:

    {"time":"...","level":"INFO","msg":"http request","method":"GET","path":"/users/42","status":200}

Группа `db` становится вложенным объектом:

    {"time":"...","level":"WARN","msg":"slow query","db":{"query":"SELECT ...","took":0}}

`With` подставляет `service`/`request_id` во все записи; кастомный `ContextHandler` добавляет `request_id` из контекста без ручной передачи в каждый вызов.

Маскировка секретов — `LogValuer`-тип подставляет маску сам, `ReplaceAttr` ловит по имени ключа:

    {"...","msg":"login","user":"alice","token":"REDACTED","card":"**** **** **** 1234"}
    {"...","msg":"request","user":"alice","password":"***","authorization":"***"}

Честная граница (закреплена тестом): поле типа `Secret` внутри структуры, отданной в `slog.Any` целиком, не маскируется ни тем, ни другим способом — LogValue вложенного поля не вызывается, секрет утекает сырым —

    {"...","msg":"leak","creds":{"User":"alice","Token":"s3cr3t"}}

## Числа: способы записи (сверено)

`basic/bench_test.go` на `go1.26.3 windows/amd64`, вывод в `io.Discard` (мерим сборку записи, не I/O), ориентировочно:

| Бенчмарк | ns/op | allocs | Что показывает |
|---|---|---|---|
| `BenchmarkInfoKV`        | ~1150–1250 | 0 | `Info("msg","k",v,...)` — вариативные пары; здесь аргументы константны и не «убегают», escape-анализ держит `[]any` на стеке → **0 аллокаций** |
| `BenchmarkLogAttrs`      | ~1150–1200 | 0 | `LogAttrs(ctx, level, msg, slog.String(...))` — `[]any` не строится вовсе; время близко к `InfoKV` |
| `BenchmarkDisabledLevel` | ~24        | 0 | запись НИЖЕ порога уровня — slog отбрасывает её рано (`Handler.Enabled`), ~**50× дешевле** активной |

Честный вывод: миф «`LogAttrs` заметно экономит аллокации» на этом сценарии не подтверждается — обе версии дают 0 аллокаций, время близко. Настоящая ценность `LogAttrs` — предсказуемость (не зависим от того, оставит ли компилятор `[]any` на стеке), а `String/Int/...` дают типобезопасность против «нечётного числа аргументов». Главная же экономия — **дешёвые выключенные логи**: `Debug` в горячем пути при уровне `Info` почти ничего не стоит.

## Версии

Проверено 2026-07 на **Go 1.26.3** (локально): тесты зелёные, демо и бенчи воспроизводятся. Модуль объявляет `go 1.25.0` (минимум; сам `slog` доступен с Go 1.21). Зависимостей нет — только `log/slog`, `context`, `io`, `bytes`, `encoding/json`.
