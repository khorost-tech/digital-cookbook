# ml-dataset

Общий датасет серии «Классический ML в проде»: поток платежей, на котором
сервис авторизации спрашивает модель «похоже ли на мошенничество». Стенды
серии (`ai/ml-features`, `ai/ml-registry`, `ai/ml-serving`, `ai/ml-drift`,
`ai/ml-retraining`) генерируют его заново из этого каталога — файлов
данных в репозитории нет, идентичность проверяется хешем вывода. Первая
статья серии — [«Признаки в проде: feature store и train/serve skew»](https://khorost.tech/ai/ml-feature-store-and-skew/).

## Повторение

Docker, Python 3 и свободное место (не меньше 2 ГБ). Запуск из этого
каталога: `FRESH=1 bash scripts/run-all.sh` — два раза. Сравнение сессий:
`python3 scripts/run-manifest.py compare fixtures/manifests/A.json fixtures/manifests/B.json`.
Образ собирается из `Dockerfile`: Python 3.12, numpy 2.5.3 и scikit-learn
1.9.1 по `requirements.txt` с хешами. `scripts/lock.sh` пересобирает его из
`requirements.in` с отсечкой `--exclude-newer 2026-10-03`. CSV ложатся в
`out/` (в git не хранятся).

## Данные

`gen/dataset.py`, зерно 20261109, день 0 — 01.05.2026 (UTC), 120 дней,
2000 пользователей.

| что | как |
|---|---|
| обычные платежи | пуассоновский поток на пользователя, в среднем 1,2 в день; выходные — больше платежей и суммы крупнее на 15 % |
| захват аккаунта | серия 3–8 крупных платежей за 2 часа, чаще с нового устройства и из чужой страны |
| новый сегмент (с дня 100) | мелкие покупки `digital_goods`, половина — из Казахстана; доля растёт 15 дней |
| проверка карты (с дня 105) | 10–20 мелких платежей за 30 минут со своего устройства |
| разметка | мошенничество — chargeback через 10–60 дней; легитимный платёж подтверждается закрытием окна в 60 дней |

Эталон признаков — состояние **до** платежа по предыдущим платежам того же
пользователя: `tx_count_24h`, `amount_avg_30d`, `minutes_since_prev`,
`amount_ratio`, плюс поля запроса `amount`, `device_new`, `foreign` и счёт
мошенничества, известного к моменту платежа. Считается векторно, сверяется
с перебором.

`gen/train.py`: `HistGradientBoostingClassifier` на эталоне, обучение на
днях 0–74, валидация на 75–89, порог — 1 % флагов на валидации; обучение
однопоточное (`OMP_NUM_THREADS=1`), чтобы прогон воспроизводился побитово.

## Проверки

| проверка | что мерит |
|---|---|
| `controls` | размеры, доля мошенничества, задержка разметки, сдвиги с нужного дня; два прогона генератора совпали побайтно |
| `reference` | векторный эталон против перебора на 2000 платежах; отрицательный контроль — окно со своим платежом перебор ловит |
| `labels` | доля размеченных платежей последних 30 дней к концу датасета |
| `model` | два обучения дают одинаковые предсказания; AUC и порог на валидации |

## Контракт опыта

`expected.json` записан до первого прогона. Результат — `fixtures/checks.jsonl`,
точная команда в `cmd`, в конце COMPLETE. `python3 scripts/run-checks.py
<проверка>` повторяет опыт и выводит одну строку, не перезаписывая фикстуру.
Время помечено `~`; сравнение сессий его исключает. Тесты держат ожидания
независимо от `expected.json`; диверсии ломают каждую проверку на копии
стенда. Маркер ставит только `run-marker.py`.

## Границы

Данные синтетические: схемы мошенничества и сдвиги заложены руками, чтобы
стендам серии было что мерить. Это не модель реального платёжного трафика.
