# Тестирование в Rust: шесть приёмов на одном домене

Стенд к статье [«Тестирование в Rust»](https://khorost.tech/rust/rust-testing/).

Домен намеренно тот же, что в стенде `architecture/testing/across-languages`
(Go, Java, Python) — объёмная скидка по тирам, — чтобы Rust-приёмы можно было
сравнивать с соседями напрямую, а не на разных задачах.

| сумма заказа | скидка |
|---|---|
| до 100.00 | нет |
| от 100.00 | 5% |
| от 200.00 | 10% |

## Запуск

```bash
cargo test                                        # юниты + tests/ + doc-тесты
cargo test --lib --features bug                   # демо: кто поймает потерянную скидку
cargo test --features prop_demo --test property   # демо: наивный vs доменный генератор
cargo test --test integration_pg -- --ignored     # Testcontainers + Postgres (нужен Docker)
bash measure-doctests.sh                           # воспроизводит таблицы «цены doc-тестов»
```

Интеграционный тест помечен `#[ignore]`, демо падают намеренно — по умолчанию
`cargo test` остаётся быстрым и зелёным.

Для property-демо: перед каждым прогоном удаляйте `rm -f tests/*.proptest-regressions`.
Иначе proptest переиграет сохранённый контрпример (`successes: 0`, replay) и покажет
«помнил», а не «нашёл заново» — а весь смысл демо в том, насколько надёжно наивный
генератор находит нарушение с нуля. По той же причине файл не в репозитории
(`.gitignore`), хотя сам proptest советует его коммитить.

## Что показывает каждый приём

### 1. Часть тестов не пишется — она становится ошибкой компиляции

`Money` — newtype с приватным полем и единственным входом `try_new`. Отрицательную
сумму не построить, поэтому теста «а что если сумма отрицательная» здесь нет.

**Важная история.** Сначала `try_new` отвергал только отрицательные, и `expect` в
`pricing::discount` обосновывался так: «`d ∈ [0, c]`, а `c >= 0` по типу». Это
оказалось ложью: `Money::try_new(i64::MAX)` возвращал Ok, а `c * 10` внутри
discount переполняло i64 — паника «attempt to multiply with overflow». Тип снял
ЗНАК, но не ДИАПАЗОН. Property-тест не ловил, потому что генератор обрезан на 1e9.
Лечится доведением типа до реального инварианта: `MAX_CENTS = 1_000_000_000`.
Теперь c*10 <= 1e10 — до i64::MAX далеко, и `expect` доказуемо безопасен.
Регрессия: `верхняя_граница_закрывает_переполнение`.

Второе слабое место — приватность поля: сделают `pub`, и дыра откроется молча.
Против этого есть `compile_fail` doc-тест:

```rust
/// ```compile_fail
/// use rust_testing::money::Money;
/// let m = Money(-500); // поле приватное → ошибка компиляции
/// ```
```

Тест зелёный ровно тогда, когда код **не** собирается. Уникально тут не сама
проверка — статически компилируемые соседи умеют не меньше (в Java берут
compile-testing, в Go собирают код компилятором из теста, в Python гоняют mypy).
Уникально, что в Rust это встроено в штатный раннер, без зависимостей, и живёт
прямо в документации.

Честная граница приёма: `compile_fail` зелёный при ЛЮБОЙ ошибке компиляции
сниппета. Переименуете модуль или опечатаетесь в `use` — тест останется зелёным,
хотя проверять перестал. Он утверждает «не собирается», а не «не собирается по
нашей причине». Нужна причина — trybuild сверяет текст ошибки с эталоном.

### 2. `#[cfg(test)] mod tests` и `tests/` — разные миры

Не стиль, а физика: модуль рядом с кодом видит приватное, `tests/` — нет.

- `src/money.rs`: тест `видим_приватное_поле` читает `m.0` — законно;
- `tests/black_box.rs`: та же строка даёт `error[E0616]: field 0 is private`.

Файл в `tests/` — отдельный крейт, он подключает библиотеку как чужой код.
Что нельзя проверить оттуда — то и не контракт крейта.

**Следствие, на которое легко напороться:** `#[cfg_attr(test, mockall::automock)]`
раскрывается только при сборке крейта с `cfg(test)`, то есть для юнитов.
Интеграционный тест собирает библиотеку как обычную зависимость — без
`cfg(test)`, — и моков там просто нет:

```
error[E0432]: unresolved import `rust_testing::service::MockStore`
```

Это не баг mockall. Моки трейтов — инструмент юнит-теста; нужны снаружи —
выносите генерацию под отдельную feature.

### 3. Doc-тесты: документация, которая не врёт — но платная

Примеры в `///` компилируются и запускаются вместе с тестами. Устареть молча
они не могут: соврал в примере — упал `cargo test`.

Цена устроена не так, как у остальных тестов: обычные компилируются вместе с
крейтом и кешируются в `target/`, а doc-тесты rustdoc собирает НА КАЖДОМ
прогоне. Поэтому на прогретом стенде они — самый долгий набор (Rust 1.97.1,
WSL2, нативная ФС):

| набор | тестов | раннер |
|---|---|---|
| юниты (`--lib`) | 10 | 0.00 с |
| `tests/black_box.rs` | 3 | 0.00 с |
| `tests/property.rs` (инвариант) | 1 | 0.01 с |
| **doc-тесты** | **5** | **0.09 с** |

«Самый долгий» — это 0.09 с. Весь прогретый `cargo test` — 0.28 с (медиана 5
прогонов), первый прогон после clone — 34 с (компиляция зависимостей).

Механизм виден только на масштабе. На edition 2021 каждый doc-тест — отдельный
бинарник, цена линейна (~10 мс/тест); на edition 2024 rustdoc их сливает, и
кривая плоская (несливаемыми остаются compile_fail и примеры со своим main):

| doc-тестов | edition 2021 | edition 2024 |
|---|---|---|
| 10 | 0.16 с | 0.08 с |
| 35 | 0.38 с | 0.07 с |
| 110 | 1.36 с | 0.08 с |

Обе таблицы воспроизводит `measure-doctests.sh` — на вашем тулчейне числа будут
свои, форма (2021 линейно, 2024 плоско) сохранится.

ВНИМАНИЕ, ловушка замера. Те же 5 doc-тестов: 0.09 с в нативной ФС и несколько
секунд при сборке в /mnt/g (drvfs из WSL). Множитель машинозависим — у нас
×70…80, на менее удачной конфигурации видели ×250, — но порядок один. В первом
черновике статьи стояло «7.12 с» и вывод «doc-тесты съедают больше половины
прогона»: число снято с раннера честно, но мерило цену файловой системы, а не
doc-тестов. Собирайте в нативной ФС; `measure-doctests.sh` из /mnt/g покажет обе
цифры рядом.

Вывод: на публичном API doc-тесты пишите не задумываясь — секунда на сотню
примеров не та цена, ради которой стоит отказываться от документации, которая
не врёт.

### 4. Property-based: proptest

Свойство «заказ на большую сумму не может стоить дешевле» **нарушено**: на 99.99
скидки нет (платим 99.99), на 100.00 сразу 5% (платим 95.00). Это **не баг в
коде** — код точно по спецификации, немонотонна сама таблица тиров. Property-тест
ищет дыру в постановке.

Замер: 20 прогонов, перед каждым удаляется `tests/*.proptest-regressions` —
иначе proptest переигрывает прошлую находку, и замер показывает «помнил», а не
«нашёл заново».

| генератор | бюджет | нашёл |
|---|---|---|
| наивный (`0..30_000`) | 256 (дефолт proptest) | **7 из 20** |
| доменный (знает про пороги) | 256 | **20 из 20** |

Шринкинг ужимает случайную находку до границы тира: `20000 / 18948`,
`19500 / 20000`, `19059 / 20000` — в разных прогонах разные пары, то есть
минимальность **локальная**.

Для сравнения — те же 20 прогонов на том же домене в соседнем стенде:
rapid @100 (дефолт Go) 0 из 20, Hypothesis @100 (дефолт Python) 0 из 20,
jqwik @1000 (дефолт Java) 5 из 40 (там прогонов было сорок).

Точечно proptest выглядит лучше всех, но **заявлять этого нельзя**, и главная
причина не статистическая: это сравнение ДЕФОЛТОВ, а не движков — 256 против 100
против 1000. Что тут вклад стратегии генерации, а что «дали больше попыток», по
одному свойству на одном домене не разделить. Вторая причина — короткая серия:
7/20 это 35% [15.4%, 59.2%], 0/20 — [0%, 16.8%] (Clopper-Pearson).

Вывод тот же, что у соседей: на настройках по умолчанию наивное свойство находит
нарушение **ненадёжно**.

### 5. Дублёры: mockall против фейка

Под `--features bug` сервис теряет скидку — клиент платит полную сумму.

| тест | что утверждает | под багом |
|---|---|---|
| на **фейке** | читает заказ обратно: цена 9500 | **падает** |
| на моке, `times(1)` | `save` позвали один раз | зелёный — дефект пропущен |
| на моке, `withf(...)` | что понесли в `save`: цена 9500 | **падает** |

Напрашивающееся «фейк умеет, мок не умеет» — неверно: mockall с `withf` ловит
тот же дефект. Пропускает не мок, а **слабое утверждение**. Разница фейка и мока
не в силе, а в предмете: фейк про результат, мок про вызов.

Фейк здесь — десяток строк (`Vec<Order>` + два метода), и это типично: в Rust
трейт-границы делают ручной фейк дешёвым, так что mockall берут не «чтобы не
писать фейк», а когда нужно утверждать про сам вызов.

### 6. Testcontainers: настоящий Postgres

Тот же образ `postgres:18.1-alpine`, что в стенде across-languages, и та же
проверка: доезжает ли заказ до диска через SQL и отклоняет ли база дубль ID —
про первичный ключ фейк не знает вовсе.

**testcontainers-rs 0.27.3 с Docker 29.6.1 работает из коробки**: ~3.1 с, ни
одного флага. Отмечено потому, что на ТОМ ЖЕ демоне java-клиент Testcontainers
1.21.3 не стартует вовсе: Docker 29 сообщает `API 1.55, min 1.40`, а docker-java
по умолчанию говорит на 1.32 → `client version 1.32 is too old`; лечится
`-Dapi.version=1.40` (см. argLine в стенде architecture/testing/across-languages).
Go-, Python- и Rust-клиенты в тех же условиях — без вопросов. Это наблюдение с
двух стендов на одном демоне, а не свойство экосистемы.
