# cpp/correctness-and-operations — счёт исходов, без замеров скорости

Стенд к волне C серии cpp-deep-dive — статьям про C++ в продакшене,
профилирование и бенчмарки без самообмана, тестирование. Каждая ось
считает **исход**, а не время: поймал ли детектор дефект, осталась ли
измеряемая работа в бинарнике бенчмарка, дослужил ли сервис запросы при
`SIGTERM`, отказал ли он на битой конфигурации, теряет ли дескрипторы на
пути ошибки, остаются ли JSON-логи JSON, что показывает покрытие при живой
ошибке.

Скорость здесь не меряется нигде — ни числом, ни словом «быстрее». Счёт
исходов не зависит от шума машины, на которой его снимают.

## Что внутри

```
defects/      ось 1: семь программ с засеянным дефектом и чистая программа,
              тест GoogleTest как детектор, вход libFuzzer
bench/        ось 2: тело бенчмарка в пяти записях; run-all.sh — весь прогон
service/      оси 3–5: сервис на Boost.Asio, варианты — переменными окружения
logs/         ось 6: запись spdlog с шаблоном-«JSON» и с экранированием
lib/, tests/  ось 7: маленькая библиотека разбора ввода и тесты GoogleTest;
              valid_port в lib/port.cpp с ошибкой на границе (-DPLANTED=ON)
images/       базовый образ (debian:trixie-slim по дайджесту, base.json) и
              образ сервиса
probes/       пробы инструментов до записи ожиданий
scripts/      раннеры осей, разборы с контролями, проверки, реестр диверсий
fixtures/     замеры *.jsonl; manifests/ — сводки сессий; RUN-COMPLETE — маркер
expected.json ожидания, записанные до прогона
```

## Как прогнать

Нужны Docker и Python 3.8+; компиляторы и инструменты — в образе.

```sh
bash bench/run-all.sh                     # всё разом, маркер последним
```

Одна строка любой оси — одной командой, её и показывают статьи:

```sh
bash scripts/detect.sh asan O2 heap_overflow        # ось 1: детектор × уровень × программа
bash scripts/detect.sh ubsan O2 heap_overflow --disasm   # тот же бинарник, дизассемблер
bash scripts/disasm-bench.sh clang++ O2 body_opaque_input   # ось 2
python3 scripts/run-shutdown.py no-handler-init     # ось 3: один вариант
python3 scripts/run-config.py naive out-of-range    # ось 4: один вход
python3 scripts/run-fds.py raw 1                    # ось 5
bash scripts/logs.sh pattern quote                  # ось 6
bash scripts/coverage.sh on show                    # ось 7: какое условие не покрыто
```

Проверки и диверсии:

```sh
python3 -m unittest discover -s scripts -p "test_*.py"                    # без докера
STAND_WITH_DOCKER=1 python3 -m unittest discover -s scripts -p "test_*.py"
python3 scripts/sabotage.py               # каждая проверка обязана покраснеть от своей поломки
```

## Что замерено

Подробности и сырые выводы — в `fixtures/`; ниже — что из них следует.
Версии: g++ 14.2, clang 19.1.7, valgrind 3.24, GoogleTest 1.16, Google
Benchmark 1.9.1, Boost 1.83, spdlog 1.15 (`fixtures/tools.jsonl`). Машина —
macOS arm64, Docker Desktop.

**Ось 1 — дефекты против детекторов.** Матрица 7 дефектов и чистая
программа × обычный запуск, тест GoogleTest, ASan, UBSan, TSan, valgrind ×
`-O0`/`-O2`, плюс libFuzzer. Чистая программа не тронула ни один детектор.
Каждый дефект присутствует в сборке `-O0`; на `-O2` оптимизатор выкидывает
утечку и чтение неинициализированного у обоих компиляторов, а выход за
границу кучи — у clang, — и такие ячейки идут в таблицу как «нет в
бинарнике», а не как пропуск. Присутствие читается по дизассемблеру ТОГО
ЖЕ бинарника, который получил детектор: инструментация меняет то, что
выкидывает оптимизатор (UBSan на `-O2` оставляет `malloc`).
Тест GoogleTest ловит гонку только на `-O0` — по неверному счёту, строгим
`EXPECT_EQ(…, 200000)`; на `-O2` g++ сворачивает цикл потока в одно
сложение, и потерянных обновлений нет. Колонка теста — исход его
утверждений: до рецензии 05.10 там стояло `EXPECT_LE`, и гонку он не ловил.

**Ось 2 — бенчмарк, который мерит пустоту.** На `-O2` и `-O3` у g++ и clang
работу теряют все три записи тела, включая `DoNotOptimize` и
`ClobberMemory`: сумма считается при компиляции. Работа остаётся только при
спрятанной от компилятора границе — и у clang даже тогда цикл заменён
формулой.

**Ось 3 — завершение по `SIGTERM`.** Сервис без обработчика как PID 1 в
контейнере сигнал не замечает; под `--init` обрывает всё в полёте; с
дослуживанием и достаточным сроком дослуживает всех и выходит с кодом 0; со
сроком короче работы обрывает остаток — и тоже выходит с кодом 0.
Большой ответ медленному читателю (пять повторов на строку) дослуживается
каждый раз, только если запрос снимается с учёта по пустой очереди
отправки сокета (`SIOCOUTQ == 0`, режим по умолчанию) — и с обычным
клиентом, и с закрывшим отправку (`SHUT_WR`) сразу после запроса. По EOF
от клиента — дослуживается с обычным клиентом и обрывается с ранним
`SHUT_WR`; по завершении `async_write` — обрывается; до отправки —
обрывается всегда. Счёт двух недетерминированных строк различается между
сессиями (`fixtures/manifests/`) и помечен в фикстуре `nondeterministic`.

**Ось 4 — отказ на старте.** `atoi` молча стартует на всех восьми битых
значениях порта (70000 → 4464, -1 → 65535, `abc` → случайный порт);
`from_chars` + `std::expected` отказывает на всех восьми с причиной.

**Ось 5 — дескрипторы.** Сырой дескриптор с закрытием в конце обработчика
теряет ровно один на каждый запрос с ошибкой; RAII — ноль.

**Ось 6 — JSON-логи.** Шаблон `{"msg":"%v"}` ломает JSON на кавычке,
обратном слеше и переводе строки; с экранированием разбираются все.

**Ось 7 — покрытие.** Строки 100%, ошибка на границе на месте. Ветви и
MC/DC меньше 100%, но непокрытое условие — другое: условие с ошибкой
покрыто в обе стороны.

## Чего стенд не утверждает

- **Ничего о скорости** — ни числом, ни словом.
- **Матрица детекторов — про эти программы и эти версии инструментов**, а не
  про классы ошибок вообще. «ASan ловит выход за границу» верно для
  засеянного дефекта, а не для любого.
- **Что найдёт valgrind или фаззер у вас** — из стенда не следует.
- **Ось 2 — про то, что осталось в бинарнике**, а не про то, насколько врёт
  время бенчмарка. Признак работы — умножение во вложенном цикле в
  дизассемблере arm64.
- **Ось 3 — про один способ остановки** (`SIGTERM` контейнеру), не про любой
  оркестратор и не про `SIGKILL`.
- **Механизм не выводится из кода возврата.** Код 143 — наблюдение «убит
  сигналом 15», а не объяснение, почему.
