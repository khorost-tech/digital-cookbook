# cpp/service-and-postgres — три слоя HTTP над одним сервисом

Стенд к серии cpp-deep-dive (волна B). Один и тот же сервис на C++ с тремя
ручками собирается тремя слоями HTTP — Boost.Beast на корутинах C++20,
Drogon, Crow — и отвечает на два вопроса:

1. **Сколько обработчиков вариант держит в полёте разом** при заданном
   числе рабочих единиц (ручка `/block`, ожидание в обработчике);
2. **Занимает ли рабочую единицу ожидание В БАЗЕ** (ручка `/q`, ожидание
   уходит в PostgreSQL через `pg_sleep`);
3. **Сколько соединений с базой открыто на самом деле** при названном
   размере пула — счётом из `pg_stat_activity`, а не по объявлению
   драйвера.

Главное требование постановки: **варианты различаются только слоем HTTP**.
Один базовый образ, закреплённый дайджестом, один компилятор, одна версия
libpqxx, один и тот же `main.cpp`, один и тот же текст SQL. Это не
объявлено, а замерено: версии инструментов и флаги сборки общей библиотеки
снимаются в каждом собранном образе и лежат в фикстуре.

## Занятость читается, а не выводится из времени

Первая редакция стенда делила ответы на «волны» по длительности: проба,
уложившаяся в одно ожидание, считалась обслуженной сразу, остальные —
дождавшимися. Чтобы отличить волну от дрожания машины, ожидание пришлось
растянуть до пятнадцати секунд, а полный прогон занимал около
четырнадцати часов. Так стенд мерил рабочую машину, а не варианты.

Теперь занятость **читается**:

* сервис ведёт счётчик обработчиков в полёте — он растёт на входе, падает
  на выходе (в том числе при выходе исключением) и кладёт своё значение
  на момент входа в контрактную строку ответа;
* маршрут живости `/healthz` отдаёт текущую занятость и **себя не
  считает**: им её спрашивают, и наблюдатель, попавший в наблюдаемое,
  завышал бы ответ на единицу;
* вторым, **независимым** источником служит счёт активных запросов
  варианта в самой базе — `pg_stat_activity` по `application_name`,
  снятый пока пробы в полёте.

Дрожание после этого ничего не значит для СЧЁТА: ответ может прийти хоть
через восемь секунд, счётчик всё равно скажет, сколько обработчиков было
внутри в момент входа. Ожидание — секунда, полный прогон обеих
фикстур — около пяти с половиной минут.

**Риск назван заранее.** Счётчик — измеряющий код ВНУТРИ предмета, то
есть слепой заодно с ним. Поэтому у него контроли снаружи:

* **положительный** — счётчик обязан идти за числом рабочих единиц при
  прочем равном: при одной единице читаться единицей, при трёх — больше;
* **отрицательный** — в постановке, где пробы уходят по очереди и не
  перекрываются, он обязан читаться единицей при любом числе единиц;
* **граница клиента** — у каждого обращения к маршруту живости рядом
  лежит число проб, которые клиент ЕЩЁ считает отправленными и не
  завершёнными, снятое ДО обращения. Прочитанная занятость не имеет
  права её превысить: это верхняя оценка, посчитанная СНАРУЖИ сервиса и
  не зависящая от того, что докладывает сам счётчик.

Без всех трёх ось недействительна, и таблица не печатается. Это записано
полем `axis_1_publishable`, а не обещанием.

**У маршрута живости своя оговорка.** Он тоже обычный запрос и способен
встать в очередь за занятыми обработчиками; ответ, пришедший из очереди,
показывает занятость уже ПОСЛЕ того, как одна из единиц освободилась, а
не в момент вопроса. Стенд не берётся утверждать «ответил под нагрузкой»
из этого — он кладёт в фикстуру СЫРУЮ задержку каждого обращения
(`liveness.max_delay_ms`) и оставляет чтение читателю. См. раздел ниже.

## Что внутри

```
service/      общая логика (main.cpp, dispatch.cpp) + три точки входа
images/       базовый образ, три построчно симметричных файла слоёв,
              postgres.json — образ базы, закреплённый дайджестом
scripts/      измерители, проверки, реестр диверсий;
              pg.py — единственное место, где поднимается PostgreSQL и
              читаются счётчики из него
bench/        run-all.sh — весь прогон одной командой, маркер последним
fixtures/     замеры: variants.jsonl, db-wait.jsonl, pool.jsonl,
              prepared.jsonl, cancel.jsonl;
              RUN-COMPLETE — маркер полного прогона;
              manifests/ — сводки величин по сессиям
expected.json ожидания, записанные до прогона (и отозванные — с причиной)
```

**Счётчики из базы, и чего среди них нет.** `pg_stat_activity` отвечает
про соединения варианта и про его живые запросы; `pg_stat_statements` —
про число вызовов (расширение включается флагом при СТАРТЕ сервера, и
без него чтение отвечает ошибкой, а не нулём). А вот число
ПОДГОТОВЛЕННЫХ запросов варианта снаружи не читается вовсе:
`pg_prepared_statements` — представление сессии без `pid` и
`application_name`. Замер: пока одна сессия держала подготовленный
запрос, отдельная сессия читала оттуда ноль. Поэтому `pg.prepared`
отказывается отвечать из чужой сессии вместо того, чтобы вернуть
правдоподобный ноль, — подробности в докстринге функции.

## Как прогнать

Всё разом — одной командой; она же ставит маркер полного прогона:

```sh
bash bench/run-all.sh
```

Шаг за шагом (порядок важен: ось ожидания в базе сверяет сумму точки
входа с фикстурой оси занятости):

```sh
python3 scripts/run-variants.py   # занятость по настройкам → variants.jsonl
python3 scripts/run-db-wait.py    # ожидание в базе → db-wait.jsonl
python3 scripts/run-pool.py       # соединения по размеру пула → pool.jsonl
python3 scripts/analyze-pool.py   # контроль первым, таблица — если сошёлся
python3 scripts/run-prepared.py      # параметр против литерала → prepared.jsonl
python3 scripts/analyze-prepared.py  # отрицательный контроль первым
python3 scripts/run-cancel.py        # обрыв клиента → cancel.jsonl
python3 scripts/analyze-cancel.py    # контроль первым, объяснение — с пометкой
python3 scripts/run-manifest.py      # сводка: опубликованные величины
python3 scripts/run-marker.py        # маркер полного прогона (ПОСЛЕ проверок)
python3 -m unittest discover -s scripts -p "test_*.py"
STAND_WITH_DOCKER=1 python3 -m unittest discover -s scripts -p "test_*.py"
python3 scripts/sabotage_source.py run   # диверсии: докер-независимо
python3 scripts/sabotage_source.py run --with-docker имя …   # и живые
```

Нужны докер и Linux (на Windows — через WSL).

**У прогона диверсий ДВА прохода, и число без области видимости ничего не
значит.** Штатный проход идёт без докера, и живые проверки в нём
пропускаются: «столько-то из стольких-то» в нём — утверждение про
докер-НЕЗАВИСИМУЮ часть набора. Это не теория: диверсия, отключающая
фильтр по `application_name` припиской ` OR true` к условию, проходит без
докера зелёной (подменный исполнитель фильтрует сам, приписки не видя) и
краснеет с докером на живой проверке с двумя именами приложения. Проход
`--with-docker` идёт по одной копии за раз: теги образов вариантов и имена
контейнеров глобальны для демона.

## Что замерено

| вариант | 1 единица | 2 единицы | 3 единицы (публикуется) | ёмкость устойчива | строка оси 1 |
|---|---|---|---|---|---|
| beast (корутины) | 1 | 2 | 3 | да | печатается |
| crow | 1 | 1 | 2 | да | печатается |
| drogon | 1 | 2 | 1 (залпы 2, 1, 3) | **нет** | печатается |

Число drogon при трёх единицах **не устойчиво** (поле `capacity_stable`):
в последнем прогоне из трёх залпов вышло 2, 1, 3. Публикуется
наименьшее — утверждение «держит разом столько-то» обязано выдерживать
каждый залп, а не лучший из них. Число, стоящее в этой таблице, —
результат ОДНОГО прогона; следующий прогон вправе дать другое, и это не
противоречило бы записанному здесь, а подтвердило бы неустойчивость.

**Задержка маршрута живости под полной занятостью — сырое число, а не
вывод «отвечал».** В последнем прогоне:

| вариант | обращений к живости | ответов | наибольшая задержка |
|---|---|---|---|
| beast | 151 | 151 | 1002 мс |
| crow | 7 | 7 | 2002 мс |
| drogon | 15 | 14 | 2003 мс |

Задержка сравнима с самим ожиданием залпа (1000 мс) или кратна ему, а не
близка к нулю: маршрут живости делит рабочие единицы с пробами и встаёт в
очередь.

**У drogon одно обращение из пятнадцати осталось БЕЗ ответа** (поле
`every_call_got_a_value` в фикстуре — `false`). Прежняя редакция этого
абзаца утверждала обратное — «не отказывает и не виснет, держится у всех
трёх», — и утверждение пережило перезамер, потому что поле не читала ни
одна проверка. Теперь таблица выше сверяется с фикстурой проверкой, а не
переписывается руками. Величина при этом неустойчива: независимый
перезамер дал у drogon 12 ответов из 12, то есть полные. Стенд поэтому
говорит только то, что видел: у beast и crow ответ получило каждое
обращение, у drogon в этом прогоне — не каждое.

Стенд не утверждает «сервер под занятостью отличим от умершего
мгновенно»: он утверждает, что маршрут в конце концов отвечает, и кладёт
задержку в фикстуру для читателя, а не превращает её в готовый вердикт.

**Ожидание в базе занимает рабочую единицу у всех трёх вариантов.** При
одной единице ни в одном из пятнадцати залпов в полёте не было двоих.

**Что занята именно единица, а не сервис целиком**, подтверждено
контролем при трёх единицах — и подтверждено не у всех: в последнем
прогоне у beast пробы перекрылись во всех пяти залпах, а у crow и у
drogon — в трёх из пяти. Запас контроля (`control_headroom`) у crow равен
нулю, у drogon отрицателен: ёмкость на контрольной настройке не превышает
числа проб, и одного неперекрывшегося залпа хватает, чтобы «разошёлся
всегда» стало ложью. Их строки идут с `publishable: false` — вывод для них
не подтверждён. Само число «три из пяти» свойством варианта не называется
— оно меняется между сессиями.

**Два источника занятости — счётчик в сервисе и счёт активных запросов
в самой базе — сошлись во всех тридцати залпах ручки `/q`** в последнем
прогоне. Источник опрашивается отдельным потоком со своим шагом, не
деля цикл с опросом живости: иначе он рисковал вовсе не успеть спросить,
пока пробы ещё внутри, и «сошлись» значило бы «не поймали момент», а не
«совпало». Оба исхода теперь различены в фикстуре (`sources.disagreed` и
`sources.missed`).

**Обе фикстуры сверены по сумме точки входа.** `db-wait.jsonl` несёт
`entry_binary_sha256`, снятый заново в своей сессии докера, и сверяет его
с суммой из `fixtures/variants.jsonl` — без этого запас контроля читался
бы из чужой сборки молча.

## Сколько соединений открыто на самом деле

**Пула не было ни у одного слоя.** До этой оси соединение открывалось на
каждый запрос и закрывалось вместе с ним — у всех трёх, включая drogon.
Это замерено пробой, а не прочитано в коде: во время залпа соединений было
ровно столько, сколько запросов было В ПОЛЁТЕ — по одному на запрос, — а
после залпа ноль. Именно в полёте, а не «сколько рабочих единиц»: в
полёте бывало и меньше, чем единиц (перезамер на том же коммите дал у
crow семь при восьми единицах), и почему — стенд не установил. Контроль «пул
на 1 против пула на 8» был бы при таком устройстве декоративен: ручка ни
на что не влияла бы. Пул написан здесь же, в общей логике сервиса, ОДИН на
три слоя; размер приходит при запуске переменной `STAND_POOL`.

| вариант | пул 1 | пул 8 | в полёте при пуле 8 | залпы при пуле 8 | обслужено |
|---|---|---|---|---|---|
| beast | 1 | 8 | 8 | 8, 8, 8 | 24 из 24 |
| crow | 1 | 7 | 7 | 7, 7, 7 | 24 из 24 |
| drogon | 1 | 6 | 6 | **5, 5, 6** | 24 из 24 |

Восемь одновременных запросов `/q?sleep_ms=1000`, восемь рабочих единиц,
три залпа на настройку; число снимается из `pg_stat_activity` по
`application_name` во время залпа и сразу после. Печатается наибольшее по
залпам: обещание «столько-то открыто» обязано выдерживать каждый залп.

**Число drogon — не величина, а наблюдение этого прогона.** По залпам оно
дало 5, 5, 6 (`connections_stable: false`). Это то же свойство, что и
неустойчивая ёмкость drogon на оси 1, и говорить «drogon открывает шесть»
нельзя: следующий прогон вправе дать другое. У beast и crow число внутри
сессии устойчиво.

**Два числа стоит прочитать вместе.** При пуле на 8 crow и drogon до
восьми не дошли — и ровно столько же у них оказалось обработчиков в полёте
(7 и 6). Пул открывает новое соединение, только когда все уже открытые
выданы, а возвращённое не закрывает, а держит среди простаивающих. Поэтому
открытых не бывает больше, чем обработчиков разом держало соединения, и
пул до своего потолка не дошёл: восемь разом у него не просили. Почему при
восьми одновременных запросах разом в полёте оказалось семь или шесть,
стенд **не установил**: предел слоя, распределение соединений между
потоками и недогруженная проба дают одно и то же равенство, а контроля
насыщения со стороны клиента нет. Число в столбце — открытые соединения
варианта в `pg_stat_activity` в любом состоянии, включая простаивающие в
пуле; это не число выданных и не число активных запросов.

**Ожидание свободного слота занимает рабочую единицу.** При пуле на 1
занятость читается 8, 7 и 7 — то есть все, кто стоит в очереди за слотом,
единицу удерживают, включая корутинный слой.

**И это свойство ЭТОГО пула, а не технологии.** Ожидание слота здесь
блокирующее, и так сделано намеренно: отдать его планировщику корутин
можно было бы только у одного слоя из трёх, и ось мерила бы тогда разницу
ожиданий, а не размер пула. Пул, отдающий ожидание планировщику, дал бы у
beast другое число — и наблюдение выше к корутинам как таковым отношения
не имеет. С осью 1 (где единицу занимает синхронный `libpqxx`) это
совпадает по виду, но не по причине.

**У Drogon пул свой — и это проверено замером, а не объявлено.**
`drogon::orm::DbClient` с числом соединений идёт за своей настройкой так
же (1 → 8). Но в ось эта строка НЕ входит и помечена
`used_in_axis: false`: собственный клиент ходит в базу через libpq самого
фреймворка, а три варианта оси — через общий для них libpqxx, и в одной
таблице сравнивались бы драйверы, а не слои HTTP. Асимметрия, которую
ожидала спека, в стенде поэтому снята: пул у всех трёх одинаковый и
написан руками.

## Параметр или литерал — что видно снаружи

**Вопрос пришлось переписать, и это часть оси.** Задумывалась она как счёт
строк в `pg_prepared_statements` на соединение. Так спросить нельзя ни с
одной стороны, и обе замерены: снаружи это представление СЕССИИ, без `pid`
и без `application_name`, и отдельная сессия видит там ноль, пока другая
держит подготовленный запрос; изнутри сервис шлёт запрос через
`exec_params`, то есть расширенным протоколом без именованного `PREPARE`,
и строк там не создаёт вовсе. Отрицательный контроль на таком счёте прошёл
бы одинаково у обоих участников — подтверждая устройство ВОПРОСА, а не
устройство драйвера.

Ось снята на признаке, ВИДИМОМ СНАРУЖИ: пока запрос выполняется, его текст
целиком лежит в `pg_stat_activity`.

| участник | режим | текстов снято | с параметром | с величиной | вызовов в базе | текст запроса |
|---|---|---|---|---|---|---|
| beast | param | 36 | 36 | 0 | 4 | `SELECT pg_sleep($1)` |
| crow | param | 37 | 37 | 0 | 4 | `SELECT pg_sleep($1)` |
| drogon | param | 39 | 39 | 0 | 4 | `SELECT pg_sleep($1)` |
| literal-sql-probe | literal | 40 | 0 | 40 | 4 | `SELECT pg_sleep(1.500)` |

Четыре одновременных запроса `/q?sleep_ms=1500` на вариант, пул на четыре;
пока запросы в полёте, отдельный поток читает тексты живых запросов по
`application_name`. Число вызовов — прирост суммы `calls` в
`pg_stat_statements` по ТОЧНОМУ вхождению подстроки `pg_sleep`
(`position`, не `LIKE`: в `LIKE` подчёркивание — метасимвол, и на этом
замер уже давал сумму 2 вместо 1).

**Отрицательный контроль — отдельная ПРОБА, а не четвёртый вариант.** Три
штатных варианта параметризованы: так требуют остальные оси, и трогать это
нельзя. Первая редакция этой оси завела четвёртый ВАРИАНТ СЕРВИСА с
переменной режима — и уронила чужие оси: текст запроса живёт в общей
логике (`service/main.cpp`), одной на три слоя, и ветка с литералом
изменила бинарник всех трёх. Его сумма записана в фикстурах остальных осей
и сверяется свежей сборкой; живая проверка покраснела сразу, а переснятие
тех замеров сдвинуло опубликованные числа оси 1. Правка отозвана.

Поэтому контроль устроен как проба (`service/literal_sql_probe.cpp`) —
ровно по образцу пробы собственного пула Drogon: отдельный бинарник,
собираемый ВНУТРИ образа варианта тем же компилятором и тем же libpqxx
(линковка снята с бинарника через `ldd`, а не объявлена), сервиса не
касающийся вовсе. Он шлёт тот же запрос с вклеенной величиной.

**Что контроль доказывает:** чтение из `pg_stat_activity` различает
параметр и вклеенную величину — у того же клиента базы, в том же образе,
на той же базе. **Чего не доказывает:** что сервис МОГ БЫ прислать
литерал. Сервис шлёт параметр, и это его свойство, а не наше наблюдение о
нём.

**Ось оказалась скучной — так и записано.** Варианты и проба дали ровно
ожидаемое различие, и ничего сверх этого замер не показал: слой на текст
запроса не влияет (у трёх слоёв он один и тот же — ручки и клиент базы
общие), число вызовов у всех четырёх участников совпало с числом запросов.
Риск «находки может не быть» назван в спеке до прогона; вытягивать её из
оси силой нечего, и ось остаётся контролем: текст, доехавший до базы, —
это то, что написано в `exec_params`.

**Одно следствие стоит прочитать отдельно.** `pg_stat_statements` хранит
текст НОРМАЛИЗОВАННЫМ, и литеральный запрос лежит там как
`SELECT pg_sleep($1)` — неотличимо от параметризованного, только с другим
`queryid`. То есть представление, к которому тянется рука за «сколько раз
выполнялся запрос», на вопрос «параметризован ли он» не отвечает вовсе.
Отвечает только `pg_stat_activity`, и только пока запрос живой.

## Переживает ли запрос уход клиента

Клиент шлёт `/q?sleep_ms=3000`, через секунду **жёстко** закрывает свой
сокет (`SO_LINGER` в ноль, то есть RST), и ещё через секунду счёт активных
запросов варианта снимается из `pg_stat_activity` по `application_name`.

| вариант | после ответа (контроль) | до обрыва | после обрыва | через всё окно |
|---|---|---|---|---|
| beast | 0 | 1 | 1 | 0 |
| crow | 0 | 1 | 1 | 0 |
| drogon | 0 | 1 | 1 | 0 |

Запрос переживает уход клиента у всех трёх слоёв: через секунду после
обрыва он всё ещё виден активным. И он **кончается сам** — через полное
окно ожидания активных ноль, то есть речь не о застрявшей навсегда
сессии.

**Контроль — отдельное плечо, а не оговорка.** Клиент, дождавшийся
ответа, даёт ноль активных у всех трёх: счёт видит СВОИ запросы, а не
чужие. Плюс три условия, без которых наблюдение не наблюдение: запрос был
виден активным ДО обрыва (иначе «остался активным» читалось бы из нулевых
данных), байт от сервиса до обрыва пришло **0** (клиент действительно ушёл
раньше ответа), счёт снят по имени приложения ИМЕННО этого варианта.

**Сервис ради этой оси не тронут вовсе.** Обрыв делает проба своим
сокетом; ручки «оборвать» у сервиса нет. Это прямое следствие урока оси
подготовленных запросов: плечо, заведённое внутри общей логики, меняет
бинарник всех трёх вариантов и роняет замеры соседних осей.

**Наблюдение и механизм разведены, и запрет механический.** «Запрос
остался активным после обрыва» — факт. Объяснение по чтению кода:
обработчик синхронно ждёт ответа базы, и пока идёт этот вызов, за разрывом
соединения никто не следит — сокет не читается, отмены в libpq никто не
передаёт. Точнее всего сказать так: в этой реализации RST не остановил
запрос в наблюдаемом окне. Остановила бы его другая реализация — стенд не
проверял. Печать объяснения идёт только через функцию, которая
не пропускает слова `libpq` и «отмена (не) доходит» без пометки
`ОБЪЯСНЕНИЕ (не замер)`; диверсии «снять пометку» и «выпотрошить запрет»
обе краснят.

## Полный прогон, маркер и сводка

У каждой оси свой замер, и четыре фикстуры, снятые в разное время,
выглядят ровно так же, как четыре фикстуры одной сессии. Поэтому есть
две отдельные вещи.

**Маркер `fixtures/RUN-COMPLETE`** держит СОСТОЯНИЕ, при котором прогон
объявлен полным: суммы sha256 всех пяти фикстур, число проверок в наборе
и число диверсий. Он снимается первым делом (`bench/run-all.sh` удаляет
его на старте) и ставится последним шагом — после всех осей, разборов,
сводки и всего набора проверок. Правка фикстуры или новая проверка делают
маркер красным, а не тихо устаревшим: его читает
`scripts/test_run_marker.py`.

**Сводка `fixtures/manifests/<сессия>.json`** держит ОПУБЛИКОВАННЫЕ
ВЕЛИЧИНЫ — ровно те, что стоят в таблицах выше, — и сравнивает две
сессии. Не хеши: в фикстурах лежат длительности каждого ответа и число
заглядываний наблюдателя, и сравнение файлов краснело бы всегда. Рядом с
текущей сводкой лежит замороженная сводка прошлой сессии
(`commit-92c3b1d` — фикстуры того коммита), и сравнение с ней показало
следующее:

* величины оси занятости и оси ожидания в базе сошлись полностью;
* на оси пула разошлось одно число: у drogon при пуле на 1 в полёте
  оказалось 6 против 7. Это та же неустойчивость, что и у его ёмкости;
  расхождение названо поимённо в `scripts/test_run_manifest.py`, а не
  спрятано исключением поля — у beast и crow оно продолжает сверяться;
* числа, которые стенд САМ объявил неустойчивыми (`capacity_stable`,
  `connections_stable`), не сравниваются вовсе, и каждый такой пропуск
  печатается отдельной строкой.

**Различие сессий доказано, а не предположено.** Сумма длительностей
ответов оси пула исключена из сравнения по замыслу — это время — и ровно
поэтому взята свидетелем: у двух РАЗНЫХ прогонов она различается по
построению. Совпала — значит сводки сняты одним прогоном, и вывод «числа
держатся между сессиями» ложен. Диверсия подкручивает свидетеля в
сохранённой сводке под текущий: обе проверки краснеют.

**Каждое поле фикстуры либо публикуется, либо исключено с причиной.**
Поле, не попавшее ни туда, ни туда, роняет сборку сводки: иначе величина
выпадала бы из сравнения молча, а сверка сличает то, что в сводках ЕСТЬ,
и об отсутствующем не знает ничего.

## Чего стенд не утверждает

- **Почему** ожидание в базе занимает единицу. Синхронность клиента базы —
  правдоподобное объяснение, но замером оно не является: снято следствие.
- **Какой слой лучше.** Одно и то же число рабочих единиц значит у трёх
  слоёв разное, и это записано, а не усреднено.
- **Что маршрут живости отвечает быстро под полной занятостью.** Он
  встаёт в очередь наравне с пробами; задержка это показывает, и стенд
  печатает задержку, а не «ответил».
- **Что пул побольше лучше.** Стенд печатает, сколько соединений открыто
  при названном размере, и ничего о скорости: ни пропускной способности,
  ни задержки он не меряет.
- **Что число при пуле на 8 — ёмкость пула.** У crow и drogon оно равно
  числу запросов, которые слой держал разом, а не числу слотов.
- **Что занятость при пуле на 1 — свойство слоя или корутин.** Это
  свойство пула, написанного в этом стенде: ожидание слота в нём
  блокирующее. Другой пул дал бы другое число.
- **Что число соединений drogon воспроизводимо.** Оно плавает и между
  залпами одного прогона, и между сессиями.
- **Устойчивость чисел у drogon.** Ёмкость при трёх единицах плавает и
  между залпами одного прогона, и между сессиями. Публикуется наименьшее
  наблюдённое, а не типичное или ожидаемое.

- **Сколько запросов подготовлено.** Снаружи это не видно
  (`pg_prepared_statements` — представление сессии), а `exec_params` строк
  там не создаёт вовсе. Стенд считает не подготовку, а видимый текст.
- **Что какой-то слой шлёт литералы.** `literal-sql-probe` — наша
  собственная проба, написанная ради контроля, а не поведение слоя или
  библиотеки. И она не доказывает, что сервис мог бы прислать литерал:
  ручки текста запроса у него нет вовсе.
- **Что прирост `calls` принадлежит участнику.** `pg_stat_statements` по
  участникам не разделяется никак; прирост привязан к участнику только
  тем, что они меряются по очереди и в базу в это время не ходит никто
  другой.

- **Что запрос переживает ЛЮБОЙ уход клиента.** Замерен ОДИН способ:
  жёсткое закрытие сокета клиентом, то есть RST. Про вежливый `FIN`, про
  таймаут прокси между клиентом и сервисом и про обрыв сети отсюда не
  следует ничего — это разные события и для сокета, и для слоя HTTP.
- **Почему** запрос переживает обрыв. Обработчик за разрывом не следит и
  отмены в libpq не передаёт — это чтение кода, а не замер: снято
  следствие.
- **Что запрос нельзя оборвать вовсе.** Стенд не пробовал ни
  `pg_cancel_backend`, ни отмену средствами клиента базы; он говорит
  только, что САМ ПО СЕБЕ уход клиента запрос не прекращает.
- **Что число «через секунду» — граница.** Интервалы обрыва и счёта
  выбраны с запасом внутри трёхсекундного ожидания. Стенд не мерил, как
  долго запрос живёт после обрыва: он мерил, что через секунду он ещё
  жив, а к концу окна его уже нет.
- **Что сводка двух сессий доказывает воспроизводимость на другой
  машине.** Обе сессии сняты в одном окружении (Linux через WSL, один и
  тот же демон докера). Сводка отвечает на вопрос «держатся ли числа
  между прогонами», а не «держатся ли они у другого читателя».
- **Что маркер полного прогона доказывает верность чисел.** Он
  доказывает только, что все пять фикстур, набор проверок и реестр
  диверсий — те самые, при которых прогон объявлен полным. Верность
  чисел держат проверки, а не маркер.

## Проверки и диверсии

Проверки идут тремя ярусами: текст (симметрия файлов слоёв, закрепление,
запреты), поведение (логика собирается и отвечает на конкретные входы;
измеритель гоняется на подменном исполнителе — модели сервиса с
семафором, у которой ЕСТЬ ЧЕМ СОЛГАТЬ: счётчик, докладывающий настройку,
не убывающий на выходе, считающий сам себя, докладывающий больше, чем
клиент считает отправленным, и заниженный или ослепший второй источник)
и замер (фикстуры, сведённые с сырыми числами, и сверенные между собой по
сумме точки входа).

Каждая проверка уронена диверсией: `scripts/sabotage_source.py` применяет
подмену к копии стенда, требует падения и убирает копию. Диверсия, которая
не применилась, считается ПРОВАЛЕННОЙ проверкой, а не пройденной.

**Есть и четвёртый ярус — текст.** README сверяется с фикстурами
проверкой: обе таблицы (соединения по размеру пула и живость) читаются
отсюда и сравниваются с числами замера. Завёлся он не из любви к
симметрии: перезамер сдвинул живость drogon, README продолжал утверждать
прежнее, и расхождение прошло молча — поле не читала ни одна проверка.
Читатель статьи видит именно текст, и текст поэтому проверяется так же,
как код.
