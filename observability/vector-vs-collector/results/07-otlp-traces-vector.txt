Замер 5: OTLP и трейсы в Vector
Дата: 2026-07-29
Образы: timberio/vector:0.57.0-debian, otel/opentelemetry-collector-contrib:0.157.0
Нагрузка: 100 спанов и 100 записей логов, генератор в режиме -otlp

Это ядро главного тезиса статьи: «у Vector трейсы — сигнал второго класса».
Ниже проверка, а не пересказ.

────────────────────────────────────────────────────────────────────────
1. КОНТРОЛЬНАЯ ТОЧКА: генератор исправен

  Прежде чем судить о Vector, тот же поток отправлен в Collector:

  $ docker compose run --rm loadgen -otlp -endpoint http://otelcol:4318 -spans 100 -otlp-logs 100
  трейсы: отправлено 100 спанов (31000 байт) → HTTP 200, ответ: {"partialSuccess":{}}
  логи: отправлено 100 записей (31164 байт) → HTTP 200, ответ: {"partialSuccess":{}}

  Collector обработал ровно 200 записей (100 Span # + 100 LogRecord # в выводе
  debug-экспортёра), Trace ID читаются:
    Trace ID       : 4b843edf61a58870d3f96fe7dc8c6d04

  Без этого шага любой отказ на стороне Vector можно было бы принять за
  свойство Vector, тогда как дефект мог быть в отправителе.

────────────────────────────────────────────────────────────────────────
2. Vector НЕ ПРИНИМАЕТ OTLP/HTTP в JSON-кодировании

  Тот же самый запрос, отправленный в Vector:

  $ docker compose run --rm loadgen -otlp -endpoint http://vector:4318 -spans 100 -otlp-logs 100
  трейсы: отправлено 100 спанов (31000 байт) → HTTP 500, ответ: 1Rejection(InvalidHeader { name: "content-type" })
  логи: отправлено 100 записей (31164 байт) → HTTP 500, ответ: 1Rejection(InvalidHeader { name: "content-type" })

  Спецификация OTLP/HTTP допускает и protobuf, и JSON. Collector принимает
  оба, Vector — только protobuf.

  Практический смысл: инструментированное приложение или экспортёр, шлющий
  OTLP/JSON (а это законный вариант, часто применяемый в браузерных и
  скриптовых клиентах), просто не сможет отдать данные в Vector напрямую.

────────────────────────────────────────────────────────────────────────
3. Через protobuf Vector принимает и трейсы, и логи

  Чтобы проверить поведение ПО СУЩЕСТВУ, а не упереться в кодировку, сигнал
  пропущен через Collector в роли конвертера (otelcol/otlp-bridge.yaml):
  генератор шлёт JSON → Collector принимает → отдаёт по OTLP/gRPC в protobuf
  → Vector.

  После этого приём работает. То есть «Vector не умеет OTLP» — неверно;
  верно «Vector не умеет OTLP/JSON».

────────────────────────────────────────────────────────────────────────
4. ГЛАВНОЕ: use_otlp_decoding работает ОБРАТНО интуиции

  Настройка есть у источника opentelemetry, все три сигнала по умолчанию
  в false. Название подсказывает, что false — это «не разбирать». На деле
  наоборот.

  use_otlp_decoding: false (УМОЛЧАНИЕ) — 100 спанов и 100 логов, каждый
  отдельным событием, поля разложены в плоскую модель Vector:

  {"attributes":{"http.method":"GET","pipeline":"loadgen"},
   "dropped_attributes_count":0,"dropped_events_count":0,"dropped_links_count":0,
   "end_time_unix_nano":"2026-07-28T12:00:00.006Z",
   "ingest_timestamp":"2026-07-28T22:27:17.918622887Z","kind":2,
   "name":"POST /api/orders","parent_span_id":"",
   "resources":{"deployment.environment":"vector-vs-collector","service.name":"loadgen"},
   "span_id":"79af10aa16c45...

  Запись лога в том же режиме, полностью:

  {"attributes":{"pipeline":"loadgen","service":"api"},"dropped_attributes_count":0,
   "message":"db query slow","observed_timestamp":"2026-07-28T22:27:17.918609513Z",
   "resources":{"deployment.environment":"vector-vs-collector","service.name":"loadgen"},
   "scope":{"name":"loadgen"},"severity_number":17,"severity_text":"ERROR",
   "source_type":"opentelemetry","span_id":"af10aa16c45b102d",
   "timestamp":"2026-07-28T12:00:00Z","trace_id":"843edf61a58870d3f96fe7dc8c6d0479"}

  Идентификаторы в hex и читаются. Все 100 записей логов несут trace_id —
  корреляция лога со спаном сохраняется.

  use_otlp_decoding: true — ОДНА запись на весь пакет вместо 100 событий,
  внутри структура OTLP как есть, идентификаторы сырыми байтами:

  {"resourceSpans":[{"resource":{"attributes":[{"key":"service.name", ...
   "spans":[{"attributes":[...],"endTimeUnixNano":1785240000006000000,
   "kind":"SPAN_KIND_SERVER","name":"POST /api/orders",
   "spanId":"y???[", ... "traceId":"K?>?a??p??o??m"}

  То есть при включённом декодировании весь ExportTraceServiceRequest
  становится ОДНИМ событием Vector, и ни отфильтровать отдельный спан, ни
  прочитать его traceId в таком виде нельзя.

  Вывод: для практической работы нужен режим ПО УМОЛЧАНИЮ. Название
  настройки в этом смысле обманчиво, и человек, включивший её «чтобы Vector
  правильно разобрал OTLP», получит ровно противоположное.

────────────────────────────────────────────────────────────────────────
5. Источник opentelemetry выдаёт ТРИ ИМЕНОВАННЫХ ВЫХОДА

  Сослаться на источник целиком нельзя:

  x Input "otlp" for sink "archive" doesn't match any components.

  Работают только otlp.logs, otlp.traces и otlp.metrics — проверено все три,
  код возврата 0. Причём это НЕ зависит от use_otlp_decoding: конфигурация
  со всеми false ведёт себя так же.

  Отдельно: `vector generate 'opentelemetry//file'` выдаёт пример с
  inputs: [source0], то есть со ссылкой на источник целиком. Этот
  сгенерированный конфиг валидацию не проходит (там же вылезает и вторая
  ошибка, про пустые объекты в выводе генератора, — до конца её не
  разбирал). Полагаться на вывод generate как на рабочий образец для этого
  источника нельзя.

────────────────────────────────────────────────────────────────────────
ИТОГ ДЛЯ СТАТЬИ

Тезис «у Vector трейсы — сигнал второго класса» подтверждается, но не в том
виде, в каком он обычно звучит. Vector трейсы ПРИНИМАЕТ, раскладывает по
плоской модели, сохраняет trace_id и span_id и позволяет их обрабатывать
как обычные события. Ограничения конкретные:

  - только protobuf, OTLP/JSON отвергается;
  - у источника три раздельных выхода, целиком на него не сослаться;
  - настройка декодирования названа так, что её естественное прочтение
    приводит к неработоспособной конфигурации;
  - встроенный генератор конфигов для этого источника даёт нерабочий пример.

Ни одно из этих ограничений не является непреодолимым, но все вместе они
и есть та разница, которая отличает основной сигнал инструмента от
второстепенного.
