# Vector против OpenTelemetry Collector: сравнительный стенд

Один и тот же поток логов проходит через четыре конвейера, чтобы сравнение
опиралось на замеры, а не на маркетинг.

Стенд к статье [«Vector или OpenTelemetry Collector: где чей инструмент»](https://khorost.tech/observability/vector-vs-otel-collector/).

Соседний стенд — [`observability/vector-pipeline`](../vector-pipeline/): там
сквозной контур логов на одном только Vector. Генератор здесь — **копия
`vector-pipeline/loadgen`** с добавленным режимом OTLP-клиента; файлы логов и
формат манифеста те же, поэтому числа двух стендов сопоставимы.

## Что сравнивается

### Три сравниваемых конвейера

| Профиль | Конвейер | Индекс в OpenSearch |
|---|---|---|
| `vector` | файлы → VRL → OpenSearch | `logs-vector` |
| `otelcol` | файлы → OTTL → OpenSearch | `logs-otelcol` |
| `fluentbit` | файлы → parsers/filters → OpenSearch | `logs-fluentbit` |

Задача у этих трёх одна: распарсить nginx combined и JSON приложения,
проставить поле `pipeline`, отсечь запросы к `/health`. Совпадение набора
прикладных полей на выходе проверяется `scripts/compare-docs.sh` — только
поэтому их ресурсы и сравнимы между собой.

**Дедупликации в общей трансформации нет намеренно.** У Fluent Bit прямого
аналога `dedupe` не существует, и включение её сломало бы эквивалентность.

### Два профиля, которые НЕ участвуют в сравнении

| Профиль | Что проверяет | Индекс |
|---|---|---|
| `combo` | доходит ли поток через стык Vector → OTLP → Collector | `logs-combo` |
| `otlp` | что Vector делает с принятыми по OTLP трейсами и логами | — |

У них другая задача, и мерить их наравне с тремя основными нельзя. `combo`
собирает событие в другую схему полей (всё событие уходит в `body` строкой,
время берётся из `now()`), поэтому его результат — только счётчик
доставленного, без сверки полей и без замера ресурсов. `otlp` вообще не
пишет в OpenSearch: он сравнивает два положения `use_otlp_decoding` по
содержимому выходных файлов.

## Запуск

```bash
./scripts/up.sh vector      # или otelcol | fluentbit
docker compose run --rm loadgen -rate 5000 -duration 60s
./scripts/down.sh
```

У профилей `combo` и `otlp` конфигов больше одного, поэтому вторым аргументом
задаётся вариант:

```bash
./scripts/up.sh combo otlp   # связка с ручной сборкой OTLP — работает
./scripts/up.sh combo json   # наивная связка — поток теряется целиком
./scripts/up.sh otlp decoded # приём OTLP, use_otlp_decoding: true
./scripts/up.sh otlp raw     # то же с умолчанием false
```

Без второго аргумента берутся рабочие варианты (`combo otlp`, `otlp decoded`).
Переменные `VECTOR_CONFIG` и `OTELCOL_CONFIG`, заданные снаружи, имеют
приоритет — на них опираются скрипты замеров.

Поднимается **всегда ровно один** конвейер: `up.sh` гасит остальные. Это не
предосторожность на всякий случай — одновременная работа двух конвейеров
превращает замер CPU в конкуренцию за ядра.

Генератор сидит в профиле `gen` и сам не стартует: без этого
`docker compose up -d` поднимал бы его вместе со всем остальным и молча портил
любой замер.

## Замеры

| Скрипт | Что делает |
|---|---|
| `scripts/compare-docs.sh` | критерий эквивалентности: наборы прикладных полей на выходе всех трёх конвейеров |
| `scripts/bench.sh <конвейер> <full\|passthrough> <rate>` | замеры 1 и 2: ресурсы и цена трансформации |
| `scripts/fail-backend.sh <конвейер> <rate> <простой>` | замер 3: потери при недоступном бэкенде |
| `scripts/restart-pipeline.sh <конвейер> <keep\|wipe>` | замер 4: перезапуск с сохранением и без состояния |
| `scripts/footprint.sh` | замер 7: размер образа, объём конфига, валидация |

Сырые выводы — в `results/`. Ни одно число в статье не взято мимо этих файлов.

### Критерий эквивалентности

Замеры CPU сопоставимы, только если конвейеры делают одинаковую работу.
Проверяется это не обещанием, а `compare-docs.sh`: он берёт по документу из
каждого индекса и сверяет набор **прикладных** полей.

Служебные поля из сверки исключены осознанно — у каждого инструмента своя
модель записи (у Vector четыре плоских поля, у Collector обёртка OTel, у
Fluent Bit одно `@timestamp`), и требовать их совпадения значило бы требовать,
чтобы инструменты перестали быть собой.

## Что выяснилось

Коротко, с указанием файла результатов. Подробности и дословные логи — там.

**Ресурсы** (`results/11-bench-analysis.txt`). При 5000 событий/с: Fluent Bit
5% CPU и 25 МиБ, Vector 12% и 330 МиБ, Collector 34% и 110 МиБ. При 20000 —
8%, 45% и 94% соответственно, потерь нет ни у кого. Между Vector и Collector
не превосходство, а размен: втрое меньше процессора ценой вчетверо большей
памяти.

**Умолчания, тихо портящие данные.** Два таких найдено, оба не поднимают
никакого сигнала — ни ошибки в логе, ни метрики:

- `force_flush_period` у `file_log` (500 мс) режет строку активно
  пишущегося файла надвое. Тринадцать строк уехали двадцатью шестью
  обрывками; расхождение объясняется полностью, соотношение проверено
  отдельным опытом — `scripts/line-split-probe.sh`, `results/10-*.txt`;
- `buffer_size` у выхода `opensearch` Fluent Bit (512 КБ) не вмещает ответ
  OpenSearch на bulk, и чанки теряются целиком с `cannot be retried`.
  Симптом выглядит сетевым (`http_do=-1`), хотя сеть исправна
  (`results/03-fluentbit-pipeline.txt`).

**Отказ бэкенда** (`results/12-fail-backend-analysis.txt`). Vector и Fluent Bit
не потеряли ничего в обоих режимах. У Collector две разные причины потерь:
переполнение очереди лечится явным `queue_size` (46% → 0), а исчезновение
DNS-записи он считает ПОСТОЯННОЙ ошибкой и выбрасывает данные до попадания в
очередь — размер очереди не помогает совсем (79% в обеих конфигурациях).

**Перезапуск** (`results/13-restart-analysis.txt`). Все трое ведут себя
одинаково: с сохранённым состоянием ни одного дубля, с удалённым — ровное
удвоение.

**OTLP и трейсы** (`results/07-otlp-traces-vector.txt`). Vector трейсы
принимает и раскладывает по своей модели, сохраняя `trace_id`. Но: только
protobuf (OTLP/JSON отвергается), источник выдаёт три именованных выхода
(`.logs`, `.traces`, `.metrics`) и сослаться на него целиком нельзя, а
настройка `use_otlp_decoding` работает обратно интуиции — умолчание `false`
даёт разобранные события, а `true` кладёт весь пакет одним событием с
нечитаемыми идентификаторами.

**Связка работает, но не наивно** (`results/08-combo.txt`). У синка
`opentelemetry` есть кодек `otlp`, кодирующий в protobuf, — тот формат,
который источник и принимает. Однако кодек НЕ преобразует событие Vector в
OTLP: он ожидает событие, уже имеющее поля верхнего уровня `resourceLogs`,
и на обычном разобранном логе отказывается сериализовать. Если уложить
событие в proto-модель вручную (трансформация `to_otlp` в
`vector/combo-agent-otlp.yaml`, ~25 строк VRL), связка доставляет поток
полностью: 36 627 при ожидании 36 627, потерь нет.

Профиль `combo` поднимается двумя конфигами: `combo-agent.yaml` с
`codec: json` — не работает, поток теряется целиком при валидных конфигах и
чистом старте; `combo-agent-otlp.yaml` с ручной сборкой структуры —
работает. Оба оставлены намеренно: разница между ними и есть содержание
замера.

## Дисциплина замеров

Правила унаследованы от `vector-pipeline` и стоили там ошибок:

- прогоны строго последовательные, по одному конвейеру;
- `docker stats` снимается непрерывным потоком, без `--no-stream`: разовая
  выборка давала расхождение до 5.8×;
- перед каждым прогоном чистятся **и** состояние конвейера, **и** файлы логов,
  **и** целевой индекс. Кратное ожиданию число в индексе — признак неполной
  чистки, а не дублирования событий инструментом;
- `docker volume rm` на томе остановленного, но существующего контейнера
  молча не срабатывает: нужен `docker compose rm -sf <сервис>`;
- числа CPU подаются как порядок величины: разброс повторов на соседнем
  стенде составлял 2.8–8.2%.

## Ловушки платформы

- **Windows/Git Bash:** `docker run` с bind-mount требует `MSYS_NO_PATHCONV=1`,
  иначе пути переписываются **внутри** контейнера. Скрипты выставляют это сами.
- **Проброшенные порты.** Скрипты ходят в OpenSearch изнутри docker-сети
  (`docker compose exec -T opensearch curl … https://localhost:9200/…`), а не
  через порт на хосте. На машине сборки проброс портов Docker Desktop не
  работал вовсе — включая контейнеры посторонних проектов. Порты в
  `docker-compose.yml` оставлены для ручного просмотра там, где проброс исправен.
- **Том состояния Collector.** Образ Collector — единственный из трёх, который
  запускается непривилегированным (`uid 10001`), и падает на named volume,
  созданном docker'ом от root. `up.sh` готовит том перед стартом — так же, как
  это делает initContainer в k8s. Понижать Collector до root ради удобства
  стенда неправильно: непривилегированность по умолчанию — его достоинство.
