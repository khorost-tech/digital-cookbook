Замер: поведение Kafka при остановленном подписчике (Task 7, вторая половина замера 7)
Дата: 2026-07-28
Стенд: docker-compose.yml, профиль kafka (vp-kafka, vp-agent на agent-kafka.yaml,
       vp-agg на aggregator-kafka.yaml). Без холостого NATS — каждый транспорт
       поднимает только свой брокер, у агента и агрегатора свой конфиг на
       транспорт (agent.yaml/agent-kafka.yaml, aggregator.yaml/aggregator-kafka.yaml).

Те же команды, что использовались для NATS (results/07-transport-nats.txt), без
изменений процедуры — иначе сравнение было бы некорректным:

1. Сквозной прогон (агрегатор поднят раньше агента, rate=2000, duration=10s,
   всего сгенерировано 20000 событий nginx+app) дал в архиве 10545 строк —
   ровно столько, сколько ожидалось (verify.sh: "OK: доехало ровно столько,
   сколько должно"; ожидалось 10545 = nginx 8267 + app 2278).
2. Зафиксировано количество строк в архиве ДО отключения подписчика: 10545.
3. Агрегатор (consumer group vp-aggregator) остановлен: `docker compose stop aggregator`.
4. При остановленном агрегаторе сгенерирована новая партия: rate=2000, duration=5s
   -> сгенерировано nginx=5000 app=5000, итого 10000 событий. Агент Vector продолжал
   работать и публиковал их в Kafka as usual (topic logs-pipeline).
5. Агрегатор запущен обратно: `docker compose start aggregator`, выдержана пауза 20с.
6. Количество строк в архиве ПОСЛЕ рестарта подписчика: 14678.

Числа:
  в архиве до остановки подписчика:       10545
  сгенерировано при отключённом агрегаторе: 10000 (nginx=5000, app=5000)
  в архиве после рестарта подписчика:     14678
  прирост:                                 4133

Разбор прироста (проверено по содержимому archive/events.log, не только по wc -l):
  nginx в архиве всего: 12400 = 8267 (прогон 1) + 4133 (прогон 2, ВЕСЬ, без потерь
    транспортом — это ровно nginx_expected второй партии по манифесту генератора)
  app   в архиве всего:  2278 = 2278 (прогон 1) +    0 (прогон 2)
  12400 + 2278 = 14678 — сходится с wc -l без остатка.

Почему прирост app равен 0, и это НЕ потеря сообщений в Kafka:
dedupe_app — трансформация в АГЕНТЕ, ДО синка, то есть выше по потоку от транспорта.
Агент — один непрерывно работающий процесс на протяжении обоих прогонов генератора
(его никто не перезапускал — это те же команды, что и для NATS). Его кеш dedupe
(num_events: 5000) от первого прогона всё ещё хранит все ~2278 различимых комбинаций
полей match, которые вообще существуют в словаре генератора для app-событий. Когда
генератор во второй партии производит app-события, они используют тот же конечный
словарь комбинаций — и все они уже находятся в кеше агента с первого прогона, поэтому
дедуп на стороне агента отбрасывает их ДО публикации в Kafka: агент физически не
отправил в топик ни одного нового app-события во втором прогоне. Это подтверждено
манифестом генератора для второй партии (nginx_expected=4133, app_expected=1927 —
т.е. генератор насчитал 1927 различимых app-комбинаций, если бы кеш дедупа был пуст)
и прямым разбором архива (0 новых app-записей). app_expected=1927 не сбылось не
из-за транспорта, а из-за состояния кеша дедупа, унаследованного от прогона 1 —
манифест этого не знает, он считает так, как если бы кеш был чист.
Для nginx это не имеет значения: drop_health — стейтлес-фильтр без кеша, каждое
событие оценивается независимо, и весь ожидаемый прирост (4133 из 4133) дошёл
до архива без потерь.

Итоговый транспортный сигнал: 4133 nginx-события, опубликованные агентом в Kafka
ПОКА агрегатор был остановлен, ДОЕХАЛИ до архива после его перезапуска — Kafka
удержала их в топике logs-pipeline, и consumer group vp-aggregator с
auto_offset_reset: earliest дочитала их с отставания при повторном подключении.
Ноль по app-ветке — не про транспорт, а про дедуп выше по потоку (см. разбор
выше); транспортных потерь по app-ветке этот прогон не демонстрирует и не
опровергает — для этого нужен был бы прогон с иным словарём/перезапуском агента,
что сломало бы сравнимость с замером NATS.

Сопоставление с NATS (results/07-transport-nats.txt, тот же сценарий, тот же
объём генерации 5000+5000=10000 при остановленном подписчике):
  NATS:  доехало 0 из 10000 отправленных агентом событий (полная потеря)
  Kafka: доехало 4133 из 4133 фактически новых nginx-событий (полная сохранность
         части потока, которая физически ушла в топик; app-часть в этом
         конкретном прогоне была подавлена дедупом ДО транспорта, не после)

Вывод:
Kafka (в отличие от NATS core) удерживает опубликованные сообщения в топике даже
когда ни один консьюмер не подключён, и consumer group с committed offset +
auto_offset_reset: earliest гарантирует, что при повторном подключении подписчик
дочитывает всё, что было опубликовано в его отсутствие, начиная с последнего
подтверждённого места. Это свойство персистентного лога партиций, а не "здесь и
сейчас" подписки (contrast с NATS core, Task 6). Ценой этой персистентности —
отдельный процесс (брокер с диском/сегментами) вместо лёгкого in-memory сервера.
