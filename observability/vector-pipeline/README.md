# Стенд: pipeline логов на Vector

Учебный стенд к статье [«Pipeline логов на Vector»](https://khorost.tech/observability/vector-data-pipeline/)
на [khorost.tech](https://khorost.tech). Разворачивает сквозной конвейер сбора
логов на [Vector](https://vector.dev) 0.57 и снимает на нём числа: пропускную
способность, цену VRL-трансформаций, поведение при недоступном синке и брокере,
потери и дубли при перезапуске агента, ограничения confinement-шаблонов.

Этот README — единственный документ, по которому стенд поднимается: если для
воспроизведения замера понадобился шаг, которого здесь нет, это ошибка README,
а не то, что нужно обходить руками.

## 1. Что это

```
loadgen → файлы (nginx-access.log, app.log)
        → agent (Vector: file source → VRL parse/filter/dedupe)
        → NATS | Kafka
        → aggregator (Vector: remap → archive + OpenSearch)
        → OpenSearch (индекс logs-app-*) + Prometheus (метрики самого Vector)
        → файловый архив (/archive/events.log, синк file без шаблона)
```

`loadgen` — генератор синтетических логов на Go (сервис `loadgen`, профиль
`gen`, запускается только явно через `docker compose run`). Пишет два файла
через общий том `logs`: nginx-access.log (combined-формат, включая обращения
к `/health`) и app.log (JSON-строки с намеренными повторами). Флаг `-seed`
фиксирует псевдослучайную последовательность (набор строк и их порядок), но
НЕ гарантирует побайтово идентичный файл между прогонами с одним и тем же
seed: таймстемпы в каждой строке берутся из реального времени на момент
записи, а не генерируются детерминированно. `agent` читает
оба file source, парсит VRL, отфильтровывает `/health`, дедуплицирует app-поток
и публикует в транспорт. `aggregator` подписан на транспорт, помечает поток
(`pipeline_stage: aggregated`) и параллельно пишет в файловый архив и в
OpenSearch. Оба Vector-процесса отдают собственные метрики (`internal_metrics`)
на `:9599` (agent) и `:9598` (aggregator) — их собирает `prometheus`.

Транспорт выбирается целиком: NATS core (без JetStream) или Kafka — у каждого
свой конфиг агента (`agent.yaml` / `agent-kafka.yaml`) и агрегатора
(`aggregator.yaml` / `aggregator-kafka.yaml`), см. раздел 5 про то, почему они
не объединены в один файл с двумя источниками.

## 2. Требования

- Docker с Docker Compose v2 (`docker compose`, не `docker-compose`).
- Около 4 ГБ свободной RAM: OpenSearch держит 1 ГБ heap
  (`OPENSEARCH_JAVA_OPTS=-Xms1g -Xmx1g`), плюс Kafka, NATS, Prometheus, два
  процесса Vector.
- Логи `loadgen` живут в именованном томе Docker (`logs`), не в bind-mount на
  хостовую ФС. На Windows это не только гигиена: на `drvfs`/сетевых ФС (WSL
  `/mnt/*` и подобные) файловый I/O искажает замеры пропускной способности —
  генератор и file source агента упираются в файловую систему хоста, а не в
  Vector. Именованный том снимает эту переменную независимо от того, где
  физически лежит Docker Desktop VM.
- Образы пинуются: Vector `timberio/vector:0.57.0-debian`, OpenSearch
  `opensearchproject/opensearch:3.5.0`. Другие версии не проверялись — часть
  описанных ниже ограничений (раздел 5) специфична для Vector 0.57.

## 3. Быстрый старт

```bash
cd observability/vector-pipeline

# 1. Поднять инфраструктуру + агрегатор + агент. Порядок важен: агрегатор
#    обязан подняться и стартовать РАНЬШЕ агента — NATS core не хранит
#    сообщения, опубликованные до появления подписчика, они теряются
#    безвозвратно. up.sh это соблюдает сам (ждёт "Vector has started" в
#    логах агрегатора, прежде чем поднимать агента) — вызывать сервисы
#    вручную в другом порядке не нужно и не рекомендуется.
./scripts/up.sh nats

# 2. Сгенерировать нагрузку. Профиль gen — страховка: без него `docker
#    compose up -d` поднял бы loadgen с дефолтной командой и молча портил
#    любой замер. -out не указывать (том logs и так смонтирован в /logs).
#    rate не меньше 100 (генератор сам откажет иначе).
docker compose run --rm loadgen -rate 2000 -duration 10s

# 3. Подождать, пока поток дойдёт до архива и индекса (пайплайн асинхронный),
#    и сверить самопроверкой: точное ожидание по манифесту генератора против
#    архива и индекса, а не порог в процентах (см. раздел 7, почему порог
#    здесь принципиально не годится).
sleep 20
./scripts/verify.sh

# 4. Погасить стенд (удаляет тома, в т.ч. checkpoints агента).
./scripts/down.sh
```

Ожидаемый финал `verify.sh`:

```
ожидалось: N (nginx M1 + app M2)
в архиве:  N
в индексе: N
OK: доехало ровно столько, сколько должно
```

Для Kafka — то же самое с `./scripts/up.sh kafka`.

Полезные адреса при поднятом стенде: OpenSearch — `https://localhost:9224`
(`admin` / `VectorDemo#2026`, self-signed TLS), Prometheus —
`http://localhost:9097`, GraphQL API агента — `http://localhost:8686`,
агрегатора — `http://localhost:8687`.

## 4. Замеры

Все скрипты живут в `scripts/`, результаты — в `results/`. Каждый скрипт сам
гасит и поднимает стенд перед прогоном (кроме `verify.sh` и `bench.sh`,
которые ожидают уже поднятый/поднимаемый ими стенд) — запускать их изолированно,
не полагаясь на состояние от предыдущего замера.

| Скрипт | Что измеряет | Файл(ы) в `results/` |
|---|---|---|
| `bench.sh <nats\|kafka> <agent\|passthrough\|nofilter> <rate>` | Пропускная способность и CPU/RAM агента и агрегатора при разной нагрузке и разных вариантах конвейера (замеры 1, 2, 3, 4, 7 — цена VRL-трансформаций, транспорт, нагрузка) | `bench-summary.txt` (сводка по каждому прогону) + `bench-*.csv` (сырые кадры `docker stats`) |
| `fail-sink.sh <block\|drop_newest>` | Поведение дискового буфера синка OpenSearch при недоступном OpenSearch: `block` создаёт обратное давление, `drop_newest` роняет события на входе в переполненный буфер (замер 5) | `05-fail-sink-block.txt`, `05-fail-sink-drop-newest.txt` |
| `restart-agent.sh <persistent\|ephemeral>` | Потери/дубли при перезапуске агента: `persistent` сохраняет том `data_dir` (checkpoints целы), `ephemeral` имитирует его потерю вместе с контейнером (замер 6) | `06-restart-agent.txt` |
| `up.sh nats` + ручной прогон (см. `results/07-transport-nats.txt` для точных команд) | Поведение источника при недоступном подписчике/брокере: NATS core теряет события безвозвратно, Kafka удерживает их в топике (замер 7, транспортная часть) | `07-transport-nats.txt`, `07-transport-kafka.txt` |
| `docker run … vector validate` / `vector --config …` на `vector/variants/unconfined-index.yaml` (см. `results/08-confinement.txt` для точных команд) | Template confinement синка OpenSearch: полная `vector validate` ошибку ловит (код 78), а `validate --no-environment` её пропускает (замер 8) | `08-confinement.txt` |
| `curl :9598/metrics`, `curl :9599/metrics`, `vector top` (см. `results/09-internal-metrics.txt` для точных команд) | Внутренние метрики самого Vector (`internal_metrics` source) и их сбор Prometheus (замер 9) | `09-internal-metrics.txt` |
| `up.sh nats` + `AGENT_CONFIG=/etc/vector/variants/passthrough.yaml` (см. `results/11-passthrough-opensearch-template-error.txt`) | Что происходит, когда шаблон индекса ссылается на отсутствующее поле события: событие роняется в этом синке, но доезжает в другие (архив) — побочный результат замеров 1/2 (`bench.sh … passthrough …`) | `11-passthrough-opensearch-template-error.txt` |
| `docker run … validate` / `vector --config …` на минимальном конфиге с `buffer.max_size` ниже минимума (см. `results/13-min-disk-buffer.txt` для точных команд и конфига) | Минимальный размер дискового буфера (268435488 байт) и то, что `validate --no-environment` это ограничение пропускает, а полная `vector validate` — ловит; второй независимый пример того, что даёт флаг, после `08-confinement.txt` (замер 13) | `13-min-disk-buffer.txt` |

Замеры 1–4 и 7 (пропускная способность/CPU/RAM/транспорт) технически один
скрипт `bench.sh`, запущенный с разными аргументами — отдельных файлов на
каждый номер замера нет, все они попадают в `bench-summary.txt` и
`bench-*.csv`.

## 5. Ограничения Vector 0.57

**`${VAR}` больше не интерполируется по умолчанию.** В конфигах Vector
(`vector/*.yaml`, `vector/variants/*.yaml`) переменных нет вовсе — это
осознанное решение, а не то, что можно было бы упростить. `${AGENT_CONFIG}` и
`${AGG_CONFIG}`, которые видны в `docker-compose.yml` в секции `command`
сервисов `agent`/`aggregator`, — это переменные **docker compose**, а не
Vector: их подставляет compose при разворачивании команды контейнера, ДО его
старта, из shell-окружения или `.env`. К моменту, когда Vector внутри
контейнера читает свой YAML, там уже нет никаких `${...}` — только готовый
путь к файлу в аргументе `--config`. Различие тонкое и легко спутать, потому
что визуально это одна и та же нотация `${VAR}` в двух разных местах одного
проекта.

Если секрет всё же нужен внутри самого YAML Vector, штатных обходов
отключённой интерполяции два: препроцессинг конфига до старта Vector
(`envsubst` или аналогичный шаблонизатор разворачивает `${VAR}` заранее,
Vector получает уже готовый файл) или встроенный секрет-бэкенд Vector
([Secrets](https://vector.dev/docs/reference/configuration/secrets/)). По
способу подстановки бэкенд НЕ отличается от `${VAR}`: значение так же
подставляется текстом в конфиг до его разбора, поэтому источнику секрета
нужно доверять так же осторожно (значение с YAML-синтаксисом внутри может
исказить разобранный конфиг). Отличие — в другом: секрет из бэкенда никогда
не попадает в окружение процесса Vector и не виден через
`/proc/<PID>/environ`, а обычная переменная окружения — видна. Этот стенд не
использует ни один из двух обходов: пароль OpenSearch в
`vector/aggregator*.yaml` — литерал, см. раздел 8 «Что здесь demo-only». Для
продакшна ни литерал, ни отсутствие секрет-бэкенда не годятся.

**Routing-шаблоны синков требуют литерального префикса, и флаг
`--no-environment` эту ошибку прячет.** Синк `elasticsearch`/`opensearch` с
шаблоном индекса, целиком состоящим из поля события (`bulk.index:
"{{ service }}"`, без статического префикса), не даёт Vector вывести «базу
confinement» — набор индексов, которые синк потенциально может задеть.
Полная `vector validate` это ловит и завершается с кодом 78. А вот
`validate --no-environment` — тот самый вызов, который удобно ставить в CI,
чтобы не тянуть доступ к брокерам и хранилищам, — пропускает и печатает
«Validated»:

```
√ Loaded ["/etc/vector/variants/unconfined-index.yaml"]
√ Transforms configuration
                                              Validated
```

Без флага та же команда — и полная валидация, и реальный старт — даёт ошибку
на этапе сборки компонентов:

```
ERROR vector::topology::builder: Configuration error. error=Sink "opensearch":
template references event fields (["service"]) but has no literal string
prefix to derive a confinement base from. Add a static prefix to your
template, or set `dangerously_allow_unconfined_template_resolution: true`
to opt out.
```

Воспроизводится: `vector/variants/unconfined-index.yaml` (намеренно
сломанный конфиг, не использовать в контуре). Рабочий вариант — литеральный
префикс, как в `vector/aggregator.yaml`: `bulk.index: "logs-app-{{ service }}"`.
Полный лог всех трёх команд — `results/08-confinement.txt`.

**Следствие для CI:** гейтом ставьте полную `vector validate` — она поймает и
этот дефект, и слишком маленький дисковый буфер (`results/13-min-disk-buffer.txt`).
Если `--no-environment` нужен, чтобы проверка не ходила в сеть, помните, что
он ослабляет её на целый класс ошибок конфигурации, и не оставляйте его
единственной защитой перед выкаткой.

**Шаблон индекса, ссылающийся на отсутствующее поле, роняет событие в этом
синке, но не в других.** Если событие не несёт поле, участвующее в шаблоне
(например, поток из `vector/variants/passthrough.yaml`, который не парсит
и не проставляет `service`), синк `opensearch` не может отрендерить
`bulk.index` и роняет именно это событие — `error_type="template_failed"`,
`component_events_dropped intentional=false`. При этом синк `archive` (файл
без шаблона в пути) получает тот же поток целиком. Проверено живьём: 3000
событий дошли до архива, 0 — до индекса `logs-app-*` (индекс не создался
вообще). Полный лог — `results/11-passthrough-opensearch-template-error.txt`.

**Источники `nats` и `kafka` ведут себя асимметрично при недоступном
брокере.** `nats` на этапе сборки топологии синхронно вызывает `connect()`
без повторных попыток — если брокер недоступен, вся сборка конфигурации
падает как `Configuration error`, процесс завершается кодом 78 (тот же код
семейства ошибок конфигурации, что и у провала confinement выше), утаскивая
за собой любые другие источники в том же конфиге. `kafka` в тех же условиях
остаётся жив, логирует ошибки подключения и переподключается. Поэтому в
`vector/`: `agent.yaml`/`aggregator.yaml` (NATS) и
`agent-kafka.yaml`/`aggregator-kafka.yaml` (Kafka) — раздельные файлы, а не
общий конфиг с обоими источниками сразу.

## 6. Почему `api_version: v7` у синка OpenSearch

`vector/aggregator*.yaml`, синк `opensearch`, задаёт `api_version: v7`
явно, не полагаясь на автоопределение. OpenSearch 3.5.0 — форк Elasticsearch
7.10 и не реализует API восьмой версии, а корневой ответ OpenSearch (`GET /`)
не отдаёт поле `build_flavor`, по которому Vector пытается определить версию
API автоматически — из-за этого автоопределение ненадёжно и может выбрать не
тот диалект bulk-протокола. Явный `v7` убирает эту неопределённость.

## 7. Как читать числа замеров

**«Доля доехавших» не константа** — это не деградация под нагрузкой, а
арифметика двух независимых механизмов выше по потоку от транспорта. Фильтр
`drop_health` срезает ровно запросы к `/health` — у генератора это 1 путь из
6 равновероятных, то есть константная 1/6 nginx-потока отсекается всегда,
вне зависимости от объёма. Дедупликация `dedupe_app` работает иначе: у
генератора всего 2400 различимых комбинаций полей `service`/`level`/`msg`/
`duration_ms` (кэш дедупа держит 5000 записей, этого достаточно, чтобы
удержать их все) — как только партия становится заметно больше 2400
app-событий, почти все следующие app-строки оказываются повторами уже
виденных комбинаций и отбрасываются. Поэтому вклад app-ветки в трафик,
доходящий до транспорта, с ростом партии асимптотически стремится к
константе (~2400 событий), а не растёт линейно вместе с nginx-веткой — и
суммарная доля «доехавших от сгенерированного» падает с объёмом партии:
около 70% на партии 5 тысяч, около 52% на 20 тысячах, асимптотически к
41.7% на очень больших партиях. Это одно и то же поведение на всех
объёмах, не деградация под нагрузкой. Именно поэтому `verify.sh` сверяет
**точное ожидание**, которое генератор сам считает по построению (поля
`nginx_expected`/`app_expected` в манифесте), а не порог в процентах —
порог около асимптоты рано или поздно даёт ложный провал на больших
прогонах, там, где проверка нужнее всего. По той же причине сравнивать
конфигурации между собой имеет смысл только на одинаковом объёме
генерации: «% доехавших» — не характеристика транспорта, фильтр и дедуп
стоят до него.

**CPU в замерах — порядок величины, не точное значение.** Разброс между
повторами одного и того же прогона (`nats/agent/5000` и `kafka/agent/5000`,
снятые дважды) — от 2.8% до 8.2% относительных. Отдельно от этого: сырой
поток `docker stats` перерисовывает каждое обновление дважды (двойной
кадр на одно реальное измерение), и усреднение по всем сырым кадрам против
усреднения по кадрам, дедуплицированным вручную «по предыдущему кадру того
же контейнера», расходится до 8.8% относительных на тех же данных. Оба
источника шума не меняют порядок и направление выводов (какой вариант
дороже, какой транспорт легче), но воспринимать вторую значащую цифру CPU
в `bench-summary.txt` как точную не стоит.

**`internal_metrics` сам стоит около 150 событий в секунду фонового
расхода.** Source `internal_metrics` в обоих процессах Vector непрерывно
генерирует и прогоняет через `metrics_out` (`prometheus_exporter`) свои
собственные метрики — живьём это ~156 событий/с независимо от нагрузки на
основной конвейер (см. `vector top`, компонент `internal`, в
`results/09-internal-metrics.txt`). Часть CPU, который показывает
`bench.sh` даже на фазе `idle`, — это именно он, не простой.

**Дисковый буфер: `max_size` не означает, что столько данных помещается в
очередь.** У синка `opensearch` в `aggregator*.yaml` настроен
`max_size: 268435488` (256 MiB, номинально место на два сегмента). На
практике буфер Vector пишет append-only файлами (сегментами) с потолком
128 MiB на файл, и в прогонах `fail-sink.sh` реально используемая ёмкость
до начала потерь стабилизировалась на 128 MiB, то есть один сегмент, а не
два.

ВНИМАНИЕ на единицы: `du -sk` отдаёт **КиБ**, а не КБ. Замер дал
131 096 КиБ = 134 242 304 байта = 128,02 MiB — это НЕ «~131 МБ», как
здесь было написано раньше; читать 131 096 как мегабайты и ставить
результат рядом со 128 MiB значит превратить совпадение в мнимое
расхождение. Независимая метрика Vector
(`vector_buffer_received_bytes_total{buffer_id="opensearch"}`) в режиме
`drop_newest` дала 134 217 320 байт = 128,0 MiB — расхождение с границей
сегмента 128 MiB (134 217 728 байт) всего 408 байт. То есть снаружи по
файловой системе и изнутри по счётчику Vector получается одно и то же
число, и оно совпадает с документированным потолком одного сегмента с
точностью 0,02%.

Потолок 128 MiB и минимальный размер дискового буфера (~256 MiB) заданы
в документации: https://vector.dev/docs/architecture/buffering-model/
(«append-only log files that grow to a maximum file size of 128MiB and
are deleted once they have been processed fully»). Минимум
воспроизведён живьём — см. `results/13-min-disk-buffer.txt`.

Почему второй сегмент не задействуется, пока обрабатывается первый, при
настроенном месте на два, — открытый вопрос, документацией Vector не
объяснённый; в исходники Vector не заглядывали.

## 8. Что здесь demo-only

Стенд для локального прогона и статьи, не образец продакшн-конфигурации:

- пароль OpenSearch — литерал в `docker-compose.yml`
  (`OPENSEARCH_INITIAL_ADMIN_PASSWORD`) и в `vector/aggregator*.yaml`
  (`VectorDemo#2026`), не секрет из внешнего хранилища;
- `tls.verify_certificate: false` у синка `opensearch` — self-signed
  сертификат OpenSearch не проверяется;
- OpenSearch поднят как `discovery.type=single-node`, без реплик и без
  отказоустойчивости;
- Kafka (`apache/kafka` в режиме KRaft, один брокер) — без аутентификации
  и без TLS между клиентами и брокером.

## 9. Windows и Git Bash

На Windows под Git Bash оболочка (MSYS) переписывает любой аргумент или
значение переменной окружения, похожее на абсолютный POSIX-путь, в путь
Windows — `/logs` превращается в что-то вроде `C:/Program Files/Git/logs`,
`/etc/vector/agent.yaml` — в аналогичный мусор. Docker получает уже
испорченное значение и падает с ошибкой вида «файл/путь не найден» —
внешне это выглядит как проблема с содержимым конфига или монтирования, а
не с переписыванием аргумента оболочкой, и уводит отладку не туда.

Лечится переменной `MSYS_NO_PATHCONV=1` перед командой, которая эту
конвертацию отключает. Все скрипты стенда (`up.sh`, `bench.sh`,
`restart-agent.sh` и т.д.) уже экспортируют её сами — при вызове через
`./scripts/*.sh` дополнительно ничего делать не нужно. Она нужна только
при ручных `docker run`/`docker compose` командах в обход скриптов
(например, воспроизводя вручную команды из `results/08-confinement.txt`):

```bash
MSYS_NO_PATHCONV=1 docker run --rm -v "$PWD/vector:/etc/vector:ro" \
  timberio/vector:0.57.0-debian validate --no-environment /etc/vector/agent.yaml
```

На Linux и macOS переменная ничего не значит — там MSYS нет, и скрипты
стенда переносимы без изменений.
