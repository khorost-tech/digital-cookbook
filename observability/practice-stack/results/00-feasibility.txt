3. Сигналы доезжают: проверено, а не предположено
--------------------------------------------------
«Контейнеры живы» ничего не доказывает про связанность конфигов, поэтому
через Collector отправлены три пробных OTLP-документа (JSON на 4318) и
найдены в бэкендах:

  ТРЕЙС   POST otelcol:4318/v1/traces  -> 200
          GET tempo:3200/api/traces/<id>    -> спан task0-check найден
          GET tempo:3200/api/v2/traces/<id> -> тот же спан (оба API живы)

  ЛОГ     POST otelcol:4318/v1/logs    -> 200
          Loki query_range {service_name="task0-probe"} -> запись найдена
          Единственный лейбл индекса Loki: service_name
          trace_id, span_id, severity_*, scope_name пришли как STRUCTURED
          METADATA, а не как лейблы — то есть модель хранения ровно такая,
          на какую рассчитан derived field в Grafana (matcherType: label)

  МЕТРИКА POST otelcol:4318/v1/metrics -> 200
          otelcol:8889/metrics -> task0_probe_total{...} 7
          Prometheus query task0_probe_total -> значение 7
          Все четыре цели Prometheus health=up

  Побочная находка для статьи про метрики: resource-атрибут service.name
  Collector экспонирует как лейбл job, и Prometheus при скрейпе переименовывает
  его в exported_job — свой job у него уже занят (otelcol-apps).

4. Дефолтный протокол Java-агента — http/protobuf, не gRPC
-----------------------------------------------------------
При запуске с OTEL_EXPORTER_OTLP_ENDPOINT=http://otelcol:4317 агент 2.30.0
сам предупредил:

  WARN io.opentelemetry.exporter.otlp.internal.OtlpConfigUtil - OTLP exporter
  endpoint port is likely incorrect for protocol version "http/protobuf".
  The endpoint http://otelcol:4317 has port 4317. Typically, the
  "http/protobuf" version of OTLP uses port 4318.

То есть у Java-агента по умолчанию http/protobuf, и порт 4317 в переменной
окружения — распространённая ошибка переноса примеров из Go. Материал для
раздела «gRPC 4317 против HTTP 4318» статьи 1.

5. Шум на старте, который не является ошибкой
----------------------------------------------
Проверено на логах: слова error/fatal в первые секунды есть у четырёх
компонентов, ни одно не мешает работе.

  Tempo       backendworker: "no jobs found" от backend-scheduler — на пустом
              стенде компактить нечего; повторяется с backoff
  Loki        ratestore: "error getting ingester clients: empty ring" — гонка
              инициализации кольца; /ready отдаёт 503 первые ~20 с, потом ready
  Grafana     слово error встречается в ИМЕНАХ миграций схемы
              ("add snapshot error_string column") — это не ошибки
  PostgreSQL  "FATAL: the database system is shutting down" — штатный рестарт
              официального образа после initdb

Практический вывод для скриптов: критерий готовности — /ready и health-эндпоинты,
а не отсутствие слова error в логах.

6. Проброс портов на хост работает С ПЕРЕБОЯМИ
-----------------------------------------------
Подтверждено ограничение, записанное в плане. Один и тот же запрос к Loki
через хост: 200, 200, затем таймаут 6 с. Задержка проброса ~1 с на запрос,
изнутри сети — единицы миллисекунд.

  http://127.0.0.1:9302/ready    (Tempo)       200 (3.0 с)
  http://127.0.0.1:9303/ready    (Loki)        200, 200, 000
  http://127.0.0.1:9304/-/ready  (Prometheus)  200 (1.0 с)
  http://127.0.0.1:9305/api/health (Grafana)   200 (1.0 с)
  http://127.0.0.1:9301/metrics  (Collector)   200 (1.0 с)

Порты 9300-9310 не заняты другими процессами, в зарезервированных Windows
диапазонах не лежат (проверено `netsh int ipv4 show excludedportrange`:
исключены 5357, 27339, 49704-49903, 50000-50159) — причина в самом пробросе
Docker Desktop.

Следствия, обязательные для остальных задач:
  - все проверочные скрипты обращаются к сервисам ИЗНУТРИ docker-сети
    (`docker run --network practice-stack_default` или `compose exec`);
  - порты на хост объявлены для человека (Grafana на 9305), опираться на них
    в автоматике нельзя;
  - `/tmp` Git Bash в контейнер не монтируется — файлы для bind-mount кладём
    в каталог стенда и монтируем через MSYS_NO_PATHCONV=1 с $(pwd).
