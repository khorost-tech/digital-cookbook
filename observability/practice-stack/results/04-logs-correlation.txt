Логи и корреляция: проверки
============================
Проверено 2026-08-06 на стенде practice-stack.

Замер кардинальности вынесен в 06-cardinality.txt (пишется bench-cardinality.sh),
опыт с service.instance.id — в 05-instance-id-labels.txt (bench-instance-id.sh).
Сюда correlation-probe.sh дописывает свои протоколы.

1. Структурный лог и коррелируемый лог — не одно и то же
--------------------------------------------------------
Java: агент кладёт контекст в MDC, а Spring Boot выводит ECS-формат сам, без
сторонних библиотек (logging.structured.format.console: ecs):

  {"@timestamp":"...","log":{"level":"INFO","logger":"...InventoryController"},
   "service":{"name":"java-backend","version":"1.0.0","environment":"stand"},
   "message":"найден товар sku=SKU-0001 quantity=1000",
   "trace_id":"a6b86467c24ec17a3c8c7a6653a5b72d","span_id":"122dfa15b7202df6",
   "trace_flags":"03","ecs":{"version":"8.11"}}

Go в первой редакции стенда давал в stdout структурный, но НЕ коррелируемый лог:

  {"time":"...","level":"INFO","msg":"заказ создан","order_id":"ord-SKU-0001-1",
   "sku":"SKU-0001","quantity":1,"reserved":true}

trace_id здесь нет. Мост otelslog кладёт контекст в OTLP-поток, а JSON в stdout
остаётся без него — то есть конвейер, читающий файл (Vector, Fluent Bit), связать
запись с трейсом не сможет. Лечится своим хендлером на десяток строк
(traceContextHandler в apps/go-frontend/logging.go). В Java этого делать не
приходится — агент делает сам.

2. Опыт: логи без контекста запроса
------------------------------------
Режим ./scripts/up.sh all otel logctx, прогон 100 запросов:

  записей «заказ создан» без trace_id:  86      все записи этого прогона
  записей «заказ создан» с trace_id:   276      от предыдущих прогонов
  логов java-backend с trace_id:       778      Java не пострадал

Ошибка в Go-коде НЕ задела Java-сервис: агент прикладывает контекст независимо от
того, как логирует сосед. То есть корреляция бывает ЧАСТИЧНОЙ — по трейсу
найдутся логи одного сервиса и не найдутся логи другого. Выглядит это как «логи
иногда пропадают».

Приложение при этом полностью работоспособно: все 100 запросов обслужены, факт
совпал с планом. Ломается только возможность отладки.

3. LogQL для логов, пришедших по OTLP
--------------------------------------
Привычный приём `| json | level="ERROR"` не работает, но НЕ так, как принято
думать. Сам `| json` пустоту не возвращает — он возвращает записи с
диагностической парой полей:

  запись:            заказ создан
  __error__:         JSONParserErr
  __error_details__: Value looks like object, but can't find closing '}' symbol

Пусто получается на СЛЕДУЮЩЕМ шаге, при фильтре по полю, которого парсер не
создал:

  {service_name="go-frontend"} | json                   -> записи есть, у каждой __error__
  {service_name="go-frontend"} | json | level="ERROR"   -> 0 стримов

Практическая разница: __error__="JSONParserErr" — это подсказка, что неверен
запрос, а не данные. Если сразу писать фильтр и смотреть на пустой результат,
подсказку не увидишь.

Причина в структуре записи: тело — само сообщение, а поля лежат в structured
metadata, разобранные заранее:

  тело записи:      заказ создан
  метаданные:       deployment_environment, detected_level, flags, order_id,
                    quantity, reserved, scope_name, service_name, service_version,
                    severity_number, severity_text, sku, span_id, trace_id,
                    telemetry_sdk_*, observed_timestamp

Проверенные запросы и их фактические результаты (окно 1 час):

  sum by (severity_text) (count_over_time({service_name="go-frontend"}[1h]))
      ERROR 26, INFO 283

  sum by (detected_level) (count_over_time({service_name=~"go-frontend|java-backend"}[1h]))
      error 39, info 851, warn 13

  sum by (service_name) (count_over_time({...} | severity_text="ERROR" [1h]))
      go-frontend 26, java-backend 13

  sum(rate({service_name="go-frontend"} | severity_text="ERROR" [5m]))
      0,0867 записей в секунду

  sum(count_over_time({service_name="go-frontend"} | reserved="false" [1h]))
      32   — заказы, где товара не хватило

  sum(count_over_time({service_name="go-frontend"} | sku="SKU-0004" [1h]))
      22   — записи по медленному SKU

Важное следствие: `| json` остаётся нужен для ФАЙЛОВОГО маршрута, где Vector или
Fluent Bit читают JSON-строку целиком и кладут её в тело. Один и тот же лог,
доставленный двумя путями, требует разных запросов.

4. Корреляция трейс <-> лог: ловушка ведущего нуля
---------------------------------------------------
scripts/correlation-probe.sh делает два независимых перехода: из трейса в логи
(со сверкой order_id) и обратно. Первый сначала не работал вовсе:

  trace_id из Tempo:  3e27ea5aee6e8fe069ba880695f6167    (31 символ)
  trace_id из лога:  03e27ea5aee6e8fe069ba880695f6167    (32 символа)

Tempo отдаёт идентификатор БЕЗ ведущих нулей. В логах он полный, как определяет
спецификация OTLP. Значит переход «из трейса в логи» подстановкой значения из API
Tempo не находит ничего у каждого шестнадцатого трейса — ровно у тех, чей
идентификатор начинается с нуля. Лечится дополнением до 32 символов. Дефект
проявляется редко и потому выглядит как «иногда логи не находятся».

Протоколы прогонов дописываются ниже.

Корреляция трейс <-> лог в обе стороны, метка corr-1786000738
============================================================
1) трейс -> логи
   trace_id из Tempo: b2b925631e17f1f68d8d8a21035cffc3 (32 символов)
   записей в Loki по этому trace_id: 3
   сервисы в найденных записях: ['go-frontend', 'java-backend']
     java-backend   найден товар sku=SKU-0001 quantity=1000
     java-backend   заказ сохранён order_id=ord-SKU-0001-545 sku=SKU-0001
     go-frontend    заказ создан
   order.id из атрибутов спана: ord-SKU-0001-545
   тот же order_id встречается в логах: да

2) лог -> трейс
   trace_id, взятый ИЗ ЗАПИСИ лога: b2b925631e17f1f68d8d8a21035cffc3
   трейс по этому id найден в Tempo: да, спанов 10

ИТОГ: связка работает в обе стороны. По трейсу находятся логи ОБОИХ сервисов того же запроса, по логу находится трейс.
