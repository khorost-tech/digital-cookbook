3. EXEMPLARS: ЦЕПОЧКА СОБИРАЕТСЯ — ГОДЕН
-----------------------------------------
Три условия, каждое из которых ломает цепочку МОЛЧА (метрики при этом
исправны, и по ним отказ не виден):

  1) prometheus, флаг            --enable-feature=exemplar-storage
  2) exporters.prometheus        enable_open_metrics: true
  3) connectors.spanmetrics      exemplars.enabled: true

При всех трёх выполненных:

  /api/v1/query_exemplars по traces_span_metrics_duration_milliseconds_bucket
    серий с exemplars: 32
    exemplars всего:   32
    пример labels:     {'span_id': '9498cc6147b2c6c2',
                        'trace_id': '6bafcccf084c9c2543a814f35a2e38c7'}
    значение:          8.092924

Второе звено — резолв trace_id в Tempo — тоже работает:

  GET /api/traces/6bafcccf084c9c2543a814f35a2e38c7 -> HTTP 200, 9853 байта
  сервисов в трейсе: go-frontend, java-backend
  операций: POST /order, create_order, GET /inventory/{sku}, HTTP GET,
            SELECT orders.inventory, INSERT orders.orders,
            orders.created publish, orders.created process, orders

То есть прыжок из точки метрики ведёт в осмысленный трейс, а не в пустой экран.

ЛОВУШКА ОКРУЖЕНИЯ (стоила одного ложного вывода). `innet -o файл` пишет файл
ВНУТРИ контейнера curl, на хосте его нет. И отдельно: $PYTHON_BIN — это python
для Windows, для него пути вида /tmp/... не существуют. Оба следствия
одинаковы: скрипт выглядит сломанным, хотя данные получены. Работать через
stdout и stdin.


4. ГЕНЕРАТОР МЕТРИК TEMPO: НАСТРАИВАЕТСЯ — ГОДЕН
-------------------------------------------------
Конфиг tempo/tempo-metrics-generator.yaml, включается переменной TEMPO_CONFIG
из .env (тот же приём, что у конфигов Collector).

Существенно: процессоры генератора включаются НЕ в блоке metrics_generator, а
в overrides.defaults.metrics_generator.processors. Без этой секции генератор
настроен, стартует без ошибок и НИЧЕГО НЕ ДЕЛАЕТ — молча.

Приёмнику remote-write нужен флаг Prometheus --web.enable-remote-write-receiver.

Метрики появились (лейбл source=tempo задан через registry.external_labels,
иначе серии двух генераторов было бы не различить):

  traces_spanmetrics_calls_total, traces_spanmetrics_latency_{sum,count,bucket},
  traces_spanmetrics_size_total,
  traces_service_graph_request_total, traces_service_graph_request_failed_total,
  traces_service_graph_request_{client,server}_seconds_{sum,count,bucket}

`-config.verify` у Tempo 3.0.2 НЕТ (флаг выводит справку и код 2). Конфиг
проверяется только подъёмом.


5. ГЛАВНАЯ НАХОДКА: ДВА ГЕНЕРАТОРА НЕСОВМЕСТИМЫ ПО ФОРМЕ
---------------------------------------------------------
Источник данных у путей один — те же спаны. Но результат отличается во всём,
что нужно дашборду:

  ЧТО              COLLECTOR                          TEMPO
  имя              traces_span_metrics_calls_total    traces_spanmetrics_calls_total
  латентность      ..._duration_milliseconds_*        ..._latency_*
  единица          миллисекунды                       СЕКУНДЫ
  границы бакетов  5,10,25,50,100,250,500,1000,2000   0.002,0.004,...,16.384
                   (заданы явно в конфиге)            (дефолт, экспоненциальные)
  имя сервиса      service_name                       service
  число лейблов    33                                 7

Практическое следствие: дашборд или алерт, написанный на одном пути, на другом
НЕ РАБОТАЕТ. Не совпадает ни имя метрики, ни единица измерения, ни даже имя
лейбла с сервисом. Это не деталь оформления: переключение пути генерации
требует переписывания всего, что поверх.


6. ВТОРАЯ НАХОДКА: КОНВЕНЦИЯ СОБЛЮДАЕТСЯ НЕРАВНОМЕРНО
------------------------------------------------------
В конфиг заданы размерности http.route и http.response.status_code. Доехали:

  span_name=POST /order            http_route=ОТСУТСТВУЕТ  status=201
  span_name=POST /order            http_route=ОТСУТСТВУЕТ  status=404
  span_name=POST /order            http_route=ОТСУТСТВУЕТ  status=502
  span_name=GET /inventory/{sku}   http_route=/inventory/{sku}  status=200

У Java-сервиса (агент OTel) http.route проставлен, у Go-сервиса — нет.
Соглашение существует и одинаково понимается обеими сторонами, но заполняет
атрибут только одна. Дашборд «латентность по маршрутам» для Go-сервиса окажется
пустым — при полностью исправной телеметрии.


7. ТРЕТЬЯ НАХОДКА: МОСТИК К СТАТЬЕ 8
-------------------------------------
У метрик Collector 33 лейбла против 7 у Tempo. Причина — включённый
resource_to_telemetry_conversion: КАЖДЫЙ ресурсный атрибут становится лейблом.
Среди них:

  container_id, host_name, os_description, os_version,
  process_command_args, process_executable_path, process_pid,
  service_instance_id, telemetry_distro_version, ...

process_pid и service_instance_id меняются при каждом перезапуске процесса —
то есть каждый рестарт сервиса порождает полный новый набор серий. Это ровно
тот механизм, который в волне 1 измерен на лейблах Loki
(results/05-instance-id-labels.txt), но здесь он работает на МЕТРИКАХ, где
цена серии выше.
