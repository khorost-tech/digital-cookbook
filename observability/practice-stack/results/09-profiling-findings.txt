Непрерывное профилирование: что выяснилось на замерах
======================================================
Проверено 2026-08-06 на стенде practice-stack.
Pyroscope 2.2.0, pyroscope-go 1.4.1, otel-profiling-go 0.6.0,
агент Pyroscope для Java 2.9.0, режим сэмплирования Java ITIMER.


1. СВЯЗКА ПРОФИЛЬ↔ТРЕЙС ДАЁТ span_name, А НЕ span_id
------------------------------------------------------
Ожидание было такое: otelpyroscope навешивает на профиль метку с span_id, и из
конкретного трейса можно перейти в профиль именно этого запроса.

Фактический набор меток профилей go-frontend:

  __name__  __period_type__  __period_unit__  __profile_type__
  __service_name__  __type__  __unit__
  environment  pyroscope_spy  service_name  span_name

Метки span_id НЕТ. Запрос значений span_id возвращает пустой список. Есть
span_name, и у него РОВНО ОДНО значение:

  span_name = "POST"

То есть переход «из этого конкретного трейса в его профиль» невозможен. Возможен
переход «из этого ВИДА операции в профиль этого вида операции». Причина понятна и
та же, что в статьях 3 и 4: span_id — идентификатор, и метка по нему дала бы по
серии на каждый запрос.

Что связка при этом работает — проверено: профиль по span_name="POST" содержит
370 фреймов, среди них main.(*Service).CreateOrder, main.(*Service).handleOrder,
main.(*natsPublisher).Publish, main.(*httpInventory).Lookup.


2. МЕТКА СТАВИТСЯ ТОЛЬКО КОРНЕВОМУ СПАНУ, И ИМЯ БЕРЁТСЯ НА МОМЕНТ СТАРТА
-------------------------------------------------------------------------
Профиль по вложенному спану пуст:

  span_name="POST"          -> 370 фреймов
  span_name="create_order"  ->   1 фрейм (только total, то есть пусто)

create_order — ручной спан бизнес-операции, он существует и виден в Tempo. Метки
для него нет: otelpyroscope размечает только корневой спан.

Второе, менее очевидное. Фактические имена спанов одного трейса (из Tempo):

  java-backend   GET /inventory/{sku}
  java-backend   SELECT orders.inventory
  java-backend   INSERT orders.orders
  java-backend   orders.created process
  go-frontend    orders.created publish
  go-frontend    create_order
  go-frontend    HTTP GET
  go-frontend    POST /order          <- корневой спан

Корневой спан называется "POST /order", а метка профиля — "POST". Расхождение не
случайное: otelhttp создаёт спан с именем по методу, а маршрут дописывает позже,
когда роутер его разрешил. Метка снимается на СТАРТЕ спана, то есть до
переименования.

Практическое следствие: у сервиса с несколькими POST-эндпоинтами все они
сольются в одну метку span_name="POST", и разрезать профиль по эндпоинту через
otelhttp не получится. Разрез по конкретной операции требует своего корневого
спана с осмысленным именем, заданным сразу.


3. ЛОВУШКА, СТОИВШАЯ ДВУХ ПРОГОНОВ ПРОВЕРКИ
--------------------------------------------
Первые две версии verify-profiles.sh сообщали «фреймов 0» по всем сервисам, при
том что ручные запросы к тому же Pyroscope возвращали 600-5000 фреймов.

Причина в шелле, а не в Pyroscope. Селектор сам содержит двойные кавычки:

  {service_name="go-frontend"}

При подстановке такого значения внутрь JSON-строки склейкой кавычки не
экранируются, и уходит сломанное тело:

  {"label_selector":"{service_name="go-frontend"}"}

Pyroscope отвечает внятной ошибкой:

  {"code":"invalid_argument","message":"unmarshal message: ... proto: syntax
   error (line 1:98): invalid value go-frontend"}

А разбор ответа, который просто берёт d['flamegraph']['names'], получает пустой
список и печатает «фреймов 0». То есть ОШИБКА ЗАПРОСА превратилась в вывод
«профиля нет», и полтора часа ушло на поиск несуществующей задержки доставки.

Исправлено двумя вещами, и обе обязательны:
  1) тело запроса формирует json.dumps — экранирование корректно по построению;
  2) разбор отличает ошибку сервера (поля code/message) от честной пустоты и
     возвращает -1 вместо 0.

ВАЖНО: сначала я записал, что задержка доступности профилей была артефактом
этого дефекта — на исправленном запросе ожидание составило 28 с для Go и 3 с для
Java. Это оказалось НЕВЕРНЫМ выводом из удачного совпадения: окно запроса тогда
захватывало данные предыдущих прогонов, которые уже осели. Отдельный замер (п. 11)
показал, что задержка реальна и составляет минуты.

Ошибка в рассуждении поучительна сама по себе: устранив одну причину, я приписал
ей весь наблюдаемый эффект, не проверив остаток. Проверка на чистом окне это
опровергла.


4. ЛОЖНО-ПОЛОЖИТЕЛЬНЫЕ КРИТЕРИИ НА ПУСТЫХ ДАННЫХ
-------------------------------------------------
Пока профили были пусты, два критерия проверки рапортовали ГОДЕН:

  ГОДЕН   ожидание pg_sleep НЕ в CPU-профиле       0 (ожидалось 0)
  ГОДЕН   CreateOrder отсутствует в профиле покоя  0 (ожидалось 0)

Оба — суждения об ОТСУТСТВИИ, а на пустом профиле не найдётся ничего. Критерий
проходил, ничего не проверив.

Общее правило, которое из этого следует: любое утверждение «X в данных нет»
требует отдельной проверки, что данные вообще есть. В скрипте это сделано
явно — вывод про pg_sleep объявляется недействительным, если в профиле Java
меньше 500 фреймов.


5. ОЖИДАНИЕ НЕ ПОПАДАЕТ В CPU-ПРОФИЛЬ
--------------------------------------
На стенде есть медленный путь: pg_sleep внутри запроса к БД. В трейсе он виден
как длинный спан. В CPU-профиле Java при 645 фреймах строки с pg_sleep НЕТ.

Это ровно то различие, из-за которого профиль не заменяет трейс: процессор во
время ожидания в БД не занят, и профилировщик честно ничего не показывает.
Искать «где тормозит» по CPU-профилю в этом случае бесполезно — нужен трейс.


6. ПРОФИЛЬ В ПОКОЕ ПРОТИВ ПРОФИЛЯ ПОД НАГРУЗКОЙ
------------------------------------------------
  покой (20 с без нагрузки):  1 фрейм, CreateOrder отсутствует
  под нагрузкой (3000 запросов, 2687 успешных):
      go-frontend  639 фреймов, CreateOrder присутствует
      java-backend 645 фреймов, InventoryController присутствует

Без первой половины опыта нельзя утверждать, что фрейм появился ИЗ-ЗА нагрузки.
В покое в профиле остаётся только служебное: сборка мусора и периодический
reader OTel SDK.


7. ТИПЫ ПРОФИЛЯ У GO И JAVA РАЗНЫЕ
-----------------------------------
Полный список типов, которые отдаёт стенд:

  block:contentions:count:contentions:count
  block:delay:nanoseconds:contentions:count
  goroutines:goroutine:count:goroutine:count
  memory:alloc_objects:count:space:bytes
  memory:alloc_space:bytes:space:bytes
  memory:inuse_objects:count:space:bytes
  memory:inuse_space:bytes:space:bytes
  mutex:contentions:count:contentions:count
  mutex:delay:nanoseconds:contentions:count
  process_cpu:cpu:nanoseconds:cpu:nanoseconds
  process_cpu:samples:count:cpu:nanoseconds

По сервисам:
  go-frontend  -> block, goroutines, memory, mutex, process_cpu
  java-backend -> ТОЛЬКО process_cpu
  pyroscope    -> block, goroutines, memory, mutex, process_cpu (профилирует сам себя)

У Java только CPU потому, что PYROSCOPE_PROFILING_ALLOC и PROFILING_LOCK не
заданы: в режиме ITIMER они не включаются сами.

Общий для двух языков тип один — process_cpu:cpu:nanoseconds:cpu:nanoseconds.
Именно на нём строится сравнение. Запрос Java по типу
process_cpu:samples:count:cpu:nanoseconds отвечает HTTP 200, одним фреймом и
numTicks 0 — то есть выглядит как «профиля нет», хотя профиль есть.


8. БЛОКИРОВОЧНЫЕ ПРОФИЛИ GO ТРЕБУЮТ ДВУХ ВЫЗОВОВ
-------------------------------------------------
  runtime.SetMutexProfileFraction(5)
  runtime.SetBlockProfileRate(5)

По умолчанию оба выключены, и без них типы mutex/block в Pyroscope просто не
появятся — молча, без предупреждений. Значение 5 означает не «включить», а
«сэмплировать каждое пятое событие»: полное сэмплирование блокировок само по
себе заметно дороже.


9. ДВА JAVAAGENT В ОДНОЙ JVM СОСУЩЕСТВУЮТ
------------------------------------------
  JAVA_TOOL_OPTIONS: -javaagent:/app/opentelemetry-javaagent.jar
                     -javaagent:/app/pyroscope.jar

Работает без конфликтов: OTel занимается трейсами и метриками, Pyroscope —
профилями, точки инструментирования у них разные. В логе видно оба:

  Picked up JAVA_TOOL_OPTIONS: -javaagent:... -javaagent:/app/pyroscope.jar
  Config: Config{... profilerType=ASYNC, profilingEvent=ITIMER, format=JFR ...}
  Profiling started

Режим сэмплирования по умолчанию ITIMER, и это существенно: он не требует
perf_events и работает в контейнере без capabilities (проверено при разведке —
perf_event_paranoid=2, CapEff=0). Режим CPU включается переменной
PYROSCOPE_PROFILER_EVENT=cpu; имя важно, PYROSCOPE_PROFILING_EVENT не читается и
молча оставляет ITIMER.


10. ЦЕНА ПРОФИЛИРОВАНИЯ: ИЗМЕРИМ ТОЛЬКО ОДИН ЭФФЕКТ
----------------------------------------------------
Замер: 20 000 запросов, concurrency 8, два прохода на режим, телеметрия OTel
включена во всех режимах (меряется надбавка за профили, а не сумма).
Полные числа — в results/10-profiling-overhead.txt.

ЛАТЕНТНОСТЬ — вывода нет ни по одному перцентилю:

  p50:  noprof 5.5, 5.1 | goprof 4.8, 5.5 | bothprof 6.3, 5.2
  p90:  noprof 14.2, 13.5 | goprof 12.0, 14.1 | bothprof 16.6, 14.0
  p99:  noprof 29.3, 25.8 | goprof 24.5, 27.6 | bothprof 34.2, 28.1

Разброс между проходами одного режима шире разницы между режимами. Показателен
goprof-1: 4.8 против 5.5 у noprof-1, то есть «с профилированием быстрее» — это
шум, а не эффект.

Вывод: на этом профиле нагрузки цена профилирования по латентности меньше
разрешающей способности замера. Заявление документации про «единицы процентов»
НЕ подтверждено и НЕ опровергнуто — оно просто не проверяется этими числами.

ПАМЯТЬ GO — единственный измеримый эффект:

  noprof    26.1, 30.2 МиБ (разброс 4.1)
  goprof    44.0, 45.9 МиБ (разброс 1.9)
  bothprof  42.5, 45.3 МиБ (разброс 2.8)
  надбавка +16.8 МиБ — превышает разброс 4.1

Около 60% от исходных 28 МиБ. Для сравнения, телеметрия в волне 1 стоила
8-12 МиБ на тот же процесс: профили дороже по памяти примерно вдвое.

CPU GO — вывода нет: +1.6% при разбросе 2.5%.

ПАМЯТЬ JVM — вывода нет, и причина поучительна: разброс между двумя проходами
режима noprof составил 213 МиБ (727.3 против 514.0). Это свойство сборщика
мусора, а не профилирования: снимок попадает то до сборки, то после. Измерять
надбавку в десятки мегабайт такой метрикой нельзя, и увеличение числа прогонов
этого не исправит — нужна устойчивая метрика (jvm_memory_used_bytes после
принудительной сборки), а не потребление контейнера.

Ровно то же было в волне 1 с памятью JVM. Правило подтверждается: метрика,
разброс которой шире искомого эффекта, для этого эффекта непригодна.

ПОБОЧНОЕ: вывод скрипта в отчёт шёл в кодировке консоли Windows и был нечитаем.
Лечится PYTHONIOENCODING=utf-8 перед вызовом питона внутри скрипта.


11. ЗАДЕРЖКА ДОСТУПНОСТИ ПРОФИЛЕЙ — МИНУТЫ, А НЕ СЕКУНДЫ
---------------------------------------------------------
Замер: 4000 запросов, затем опрос окна [начало нагрузки .. сейчас] каждые 15 с.
Искали рост числа фреймов и появление функции CreateOrder.

  +21 с    фреймов   1
  +57 с    фреймов   1
  +75 с    фреймов   8
  +112 с   фреймов  20
  +129 с   фреймов  41
  +202 с   фреймов  43
  +238 с   фреймов  76
  +292 с   фреймов 110
  +365 с   фреймов 139
  +438 с   фреймов 142    CreateOrder так и не появился

При этом Pyroscope профили ПРИНЯЛ, и это видно по его же метрикам:

  pyroscope_distributor_received_compressed_bytes_sum{type="process_cpu"} 994311
  pyroscope_distributor_received_compressed_bytes_sum{type="jfr"}        2151822
  отказов и отбраковки нет

Сравнение по ширине окна в тот же момент:

  окно  60 с -> фреймов  10, CreateOrder нет
  окно 120 с -> фреймов  53, CreateOrder нет
  окно 180 с -> фреймов  85, CreateOrder нет
  окно 300 с -> фреймов 112, CreateOrder нет
  окно 600 с -> фреймов 651, CreateOrder ЕСТЬ

То есть свежие данные видны частично и с большим отставанием, а полная картина
доступна только для окна, отстоящего на минуты. Причина в архитектуре записи:
профили оседают в сегментах и становятся доступны после сброса и компакции.

Следствия:
  - самопроверку нельзя строить на коротком ожидании: получишь ложный вывод
    «профиля нет» при полностью исправном конвейере. Лимит поднят до 600 с;
  - порог по числу фреймов завышать нельзя — он тогда меряет скорость
    компактора, а не работу профилировщика. Содержательный критерий — наличие
    КОНКРЕТНОЙ функции, а не количество;
  - в проде это означает, что профиль только что случившегося всплеска будет
    доступен не мгновенно. Для разбора инцидента это приемлемо, для реакции в
    реальном времени — нет, и рассчитывать на профиль как на оперативный сигнал
    не стоит.


12. ПРОВЕРКА ПОДТВЕРЖДАЛА СТАРЫЕ ДАННЫЕ (найдено ревью, 2026-08-06)
-------------------------------------------------------------------
Критерии искали функции в окне последнего часа. На тёплом стенде это значит, что
CreateOrder находится за секунды — но ИЗ ПРОШЛЫХ ПРОГОНОВ. Проверка при этом
рапортовала успех и выглядела как доказательство свежести. Симптом был виден
прямо в её выводе: «профиль покоя» содержал 650 фреймов и ту самую функцию, а
итог оставался ГОДЕН.

ИСПРАВЛЕНО: два режима, каждый со своим вопросом и своей формулировкой итога.

  PIPELINE (по умолчанию) — «конвейер подключён и отдаёт ожидаемые функции».
    Окно час. В отчёте и в итоге прямо написано, что свежести НЕ доказывает.

  FRESH (./scripts/verify-profiles.sh fresh) — «профиль ЭТОГО прогона доехал».
    Контейнер Pyroscope пересоздаётся, хранилище у него внутри контейнера (тома
    нет), поэтому старые данные исчезают физически. Окно начинается от старта
    проверки.


13. ПРОФИЛИРОВЩИК СЭМПЛИРУЕТ ВРЕМЯ, А НЕ ЗАПРОСЫ
-------------------------------------------------
Первый прогон FRESH дал полезный отказ, который вывел на факт, неочевидный до
замера. При 6000 запросов (проходят за 15 с) в профиле go-frontend осталось 179
фреймов ЧИСТО СЛУЖЕБНОГО — сборка мусора и периодический reader OTel SDK — и НИ
ОДНОЙ прикладной функции. Ожидание до 600 с не помогало: их там не было.

Причина не в задержке доступности и не в объёме запросов. CPU-профилировщик
снимает стек 100 раз в секунду, то есть сэмплирует ВРЕМЯ. 15 секунд дают около
1500 сэмплов на весь процесс, и у сервиса, который почти всё это время ЖДЁТ
ответа соседа, прикладные кадры в такую выборку не попадают.

Проверено прямо: та же нагрузка, растянутая циклом на 120 с, даёт

  фреймов: 1158, своих (main.*): 13, CreateOrder: True
    main.main
    main.(*Service).handleOrder
    main.(*Service).fail
    main.fanoutHandler.Handle
    main.traceContextHandler.Handle

Поэтому FRESH-режим меряется СЕКУНДАМИ нагрузки (FRESH_LOAD_SECONDS, по умолчанию
120), а не числом запросов, и держит нагрузку циклом.

Асимметрия языков на этом же прогоне: у java-backend 3780-4230 фреймов почти
сразу — он делает саму работу (SQL, JSON, JDBC), его CPU занят.

СЛЕДСТВИЕ ДЛЯ ЧТЕНИЯ ПРОФИЛЕЙ (важнее самого скрипта): тонкий по CPU сервис в
профиле выглядит пустым не потому, что бездействует, а потому, что ждёт. Прокси,
гейтвеи, агрегаторы дают мало сэмплов. Пустой профиль такого сервиса — это ответ
«процессор не при чём, ищите в трейсе», а не признак поломки сбора.

ФИНАЛЬНЫЙ ПРОГОН FRESH (все критерии):
  CreateOrder в профиле Go                  1
  InventoryController в профиле Java        1
  фреймов в профиле Go                    356
  фреймов в профиле Java                 3780
  CreateOrder в профиле по корневому спану  1
  pg_sleep НЕ в CPU-профиле                 0
  CreateOrder отсутствует в профиле покоя   0   (на чистом хранилище критерий осмыслен)
  ИТОГ: профили ЭТОГО прогона доехали.


14. PYROSCOPE ГОТОВ ЧЕРЕЗ ТРИ ФАЗЫ, И ПОДЪЁМ ПАДАЛ ПО ТАЙМАУТУ
---------------------------------------------------------------
Записанное ранее «две паузы по 15 с» неполно. Тело ответа /ready показывает ТРИ
последовательные фазы:

  Metastore not ready: 14.99s before reporting readiness
  Ingester not ready: waiting for 15s after being ready
  Segment Writer not ready: waiting for 30s after being ready

15+15+30 = минута чистого ожидания плюс запуск модулей; фактически около четырёх
минут от старта контейнера. Ожидание в up.sh стояло 120 с — подъём стенда падал
по таймауту на ИСПРАВНОМ компоненте.

ИСПРАВЛЕНО:
  - Pyroscope вынесен в профиль compose (`profiles: ["profiling"]`) и поднимается
    только при `up.sh ... go|both`. Статьям 4 и 5 он не нужен; подъём без него
    занимает 109 с;
  - ожидание поднято до 360 с и делается только когда он поднят;
  - wait_ready при отказе печатает ТЕЛО ответа: без него отказ выглядел как
    «просто не поднялся», и было непонятно, ждать или искать поломку;
  - зависимость go-frontend от pyroscope убрана — с профилем она делала конфиг
    невалидным, и она не нужна: отказ профилировщика не должен задерживать старт;
  - down.sh гасит с `--profile "*"`: иначе `docker compose down` НЕ трогает
    сервисы профилей, и контейнер Pyroscope переживал «погашенный» стенд, попадая
    в следующий прогон со старыми профилями.


15. FRESH-РЕЖИМ СТИРАЛ РЕЗУЛЬТАТ ПОСЛЕ НАГРУЗКИ (найдено ревью, 2026-08-06)
----------------------------------------------------------------------------
Порядок в скрипте был такой:

  строка 253  замер покоя
  строка 274  нагрузка
  строка 292  цикл нагрузки 120 с
  строка 318  ПЕРЕСОЗДАНИЕ Pyroscope (то есть стирание хранилища)

То есть очистка стирала ровно то, что прогон только что собрал, и никакой новой
нагрузки после неё не было. При этом проверка ЗАКАНЧИВАЛАСЬ УСПЕХОМ: часть
профилей доезжала уже после пересоздания, окно WIDE_START было снято до него, и
критерии выполнялись. «Свежесть» снова оказалась заявленной, а не доказанной —
ровно та ошибка, ради исправления которой режим и заводился.

Исправлено: блок очистки перенесён ДО замера покоя и любой нагрузки, плюс
добавлена контрольная точка — сразу после пересоздания хранилище проверяется на
пустоту, и если CreateOrder там находится, скрипт останавливается с явной
причиной («очистка не сработала, свежесть недоказуема»).

Урок общий: в проверке, где важен ПОРЯДОК операций, порядок и есть предмет
проверки. Его надо утверждать явно (контрольной точкой), а не полагаться на то,
что код читается сверху вниз.
