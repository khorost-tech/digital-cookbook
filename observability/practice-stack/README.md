# Стенд серии «Наблюдаемость на практике»

Локальный стек наблюдаемости и подопытная система на двух языках: сигналы
порождаются, сшиваются в трейс и связываются с логами — всё проверяемо
скриптами, а не на глаз.

Статьи серии:

- [Инструментирование OpenTelemetry в Go и Java](https://khorost.tech/observability/otel-instrumentation-go-java/)
- [Распределённый трейсинг end-to-end](https://khorost.tech/observability/distributed-tracing-tempo/)
- [Логи и корреляция: trace_id и Loki](https://khorost.tech/observability/logs-correlation-loki/)

## Что нужно на машине

| Инструмент | Зачем | Проверка |
|---|---|---|
| Docker + compose v2 | весь стенд | `docker compose version` |
| `python3` | скрипты разбирают им ответы бэкендов | `python3 --version` |
| `bash` | скрипты | — |

Скрипты выбирают интерпретатор сами: сначала `python3`, потом `python`. Имя не
зашито намеренно — в Git Bash на Windows команда называется `python`, а в обычном
Linux (проверено на Ubuntu 24.04 в WSL) её нет вовсе, есть только `python3`.
Если Python не найден, `lib.sh` останавливает прогон сразу и говорит, чего не
хватает, а не падает посреди проверки. Переопределить можно переменной:
`PYTHON_BIN=/usr/bin/python3.12 ./scripts/verify-signals.sh`.

Стенд проверен и из Git Bash на Windows, и из WSL Ubuntu 24.04.

## Быстрый старт

```bash
./scripts/up.sh all              # стек и приложения, телеметрия включена
./scripts/verify-signals.sh      # проверка: три сигнала доехали, числа сходятся
./scripts/down.sh clean          # погасить и стереть данные
```

Grafana для человека: <http://127.0.0.1:9305>. Все четыре источника данных
(Prometheus, Tempo, Loki, Pyroscope) и переходы между сигналами настроены
provisioning. Pyroscope напрямую — <http://127.0.0.1:9314>, Alertmanager —
<http://127.0.0.1:9312>.

⚠️ Pyroscope поднимается дольше остальных, и это ТРИ фазы, а не две: metastore
15 с, ingester 15 с, segment-writer 30 с — плюс запуск модулей, фактически около
четырёх минут. `up.sh` ждёт его отдельно (360 с) и только когда профилирование
включено; при отказе печатает тело ответа `/ready`, где прямо написано, чего он
ждёт. Ожидание в 120 с роняло подъём на исправном компоненте.

## Режимы подъёма

```bash
./scripts/up.sh all              # телеметрия включена (Go SDK + Java-агент)
./scripts/up.sh all off          # БЕЗ телеметрии — базовая линия для замеров
./scripts/up.sh all http         # Go SDK по OTLP/HTTP вместо gRPC
./scripts/up.sh all tail         # + tail sampling в Collector
./scripts/up.sh all otel http    # + разрыв трейса на HTTP-границе
./scripts/up.sh all otel nats    # + разрыв на асинхронной границе
./scripts/up.sh all otel logctx  # + логи без контекста (пустой trace_id)
./scripts/up.sh all otel none go    # + профилирование Go
./scripts/up.sh all otel none both  # + профилирование Go и Java
./scripts/up.sh all spanmetrics     # + span-метрики двумя путями и exemplars
CARDINALITY_BOMB_MAX=500 ./scripts/up.sh all cardinality      # + взрыв кардинальности
CARDINALITY_BOMB_MAX=500 ./scripts/up.sh all cardinality-cut  # + взрыв и резка
```

Четвёртый аргумент — профилирование, отдельно от телеметрии: у него своя цена, и
`bench-profiling-overhead.sh` меряет именно её, оставляя телеметрию включённой во
всех режимах.

Режим и поломки задаются **переменными**, а не правкой кода и не разными
образами: иначе замер сравнивал бы разные сборки, а опыт нельзя было бы повторить
одной командой.

## Проверки

| Скрипт | Что проверяет |
|---|---|
| `verify-signals.sh` | все три сигнала доехали, и числа сходятся с планом нагрузки |
| `trace-probe.sh` | целостность трейса: один трейс, оба сервиса, все участки |
| `trace-probe.sh broken` | что разрыв воспроизвёлся (при подъёме с поломкой) |
| `correlation-probe.sh` | связка трейс ↔ лог в обе стороны |
| `bench-overhead.sh` | накладные расходы: без телеметрии, gRPC, HTTP |
| `bench-cardinality.sh` | последствия высокой кардинальности в лейблах Loki |
| `bench-instance-id.sh` | во что обходится `service.instance.id` в индексных лейблах: рестарты Java-сервиса при дефолтном и безопасном наборе |
| `verify-metrics.sh` | правила RED/USE считаются, дают значения (не пустоту и не `NaN`) и покрывают все сервисы; попутно — фактическая цена гистограммы в сериях |
| `verify-alerts.sh` | SLO-алерт срабатывает на деградации, доезжает до приёмника **и не горит в покое**; замер задержки до `firing`; подавление производных; фаза 4 — реальная остановка `java-backend` и проверка `ServiceDown` |
| `SKIP_SERVICEDOWN=1 ./scripts/verify-alerts.sh` | то же без фазы 4: она занимает несколько минут, потому что метрика мёртвого сервиса исчезает не сразу |
| `verify-profiles.sh` | режим PIPELINE: конвейер подключён и отдаёт ожидаемые функции (окно час, свежести НЕ доказывает) |
| `verify-profiles.sh fresh` | режим FRESH: хранилище Pyroscope стирается до прогона, поэтому найденное принадлежит только этому прогону |
| `verify-spanmetrics.sh` | span-метрики означают то же, что RED статьи 4: оба генератора (коннектор Collector и metrics-generator Tempo) учли ровно столько запросов, сколько отправлено, и согласны между собой |
| `verify-spanmetrics.sh sampling` | во сколько раз span-метрики занижают объём при head-сэмплинге 10 %; требует 1000 запросов, иначе разброс шире эффекта |
| `verify-exemplars.sh` | прыжок metric → trace: exemplar хранится, `trace_id` резолвится в Tempo, трейс содержит **ту самую** операцию |
| `bench-metric-cardinality.sh` | взрыв кардинальности метрик и цена резки: серии, память, время запроса на трёх прогонах с чистыми томами |
| `bench-wide-events.sh` | объём одного широкого события против числа постоянных серий метрик, описывающих тот же запрос |
| `bench-profiling-overhead.sh` | цена непрерывного профилирования сверх телеметрии: без профилей, Go, Go и Java |

Режимы волны 3 задаются вторым аргументом (там же, где телеметрия) и **не меняют базовый
прогон** — иначе поехали бы числа волн 1 и 2:

| Режим | Что включает |
|---|---|
| `spanmetrics` | коннектор `span_metrics` в Collector + `metrics-generator` в Tempo одновременно, exemplars до Grafana |
| `cardinality` | лейбл `order_id` на бизнес-счётчике (предел задаётся `CARDINALITY_BOMB_MAX`) |
| `cardinality-cut` | тот же взрыв, но Collector сворачивает лейбл обратно с агрегацией |

Про режим `cardinality` важно: верхняя граница уникальных значений обязательна.
Без неё серии множатся до исчерпания памяти Prometheus, и вместо результата
получается мёртвый контейнер.

Фаза 4 останавливает `java-backend` по-настоящему, поэтому в `verify-alerts.sh`
есть `trap` на `EXIT`, `INT` и `TERM`: прерывание или ошибка посреди фазы поднимут
сервис обратно, а не оставят стенд лежать. Одна оговорка про запуск: если
запустить проверку фоном (`... &`), оболочка выставит `SIGINT` в игнорирование ещё
до старта скрипта, и перехватить его будет уже нельзя — прерывайте фоновый прогон
через `kill -TERM`, а не Ctrl+C.

Критерии везде **точные равенства**, а не «данные появились» и не «не меньше».
Разница принципиальна: «не меньше» проходит и при дублировании сигнала, и при
постороннем трафике, то есть скрывает как раз те дефекты, которые проверка должна
ловить. Стенд изолирован, прогон помечен своим идентификатором — значит точное
равенство достижимо. Пример вердикта:

```
== вердикт
  ГОДЕН   метрика заказов (дельта)     186 (ожидалось ровно 186)
  ГОДЕН   логи о заказах (дельта)      186 (ожидалось ровно 186)
  ГОДЕН   трейсы create_order          200 (ожидалось ровно 200)
  ГОДЕН   трейсы с ошибкой              14 (ожидалось ровно 14)
  ГОДЕН   логи без trace_id              0 (ожидалось ровно 0)
```

Получено больше ожидаемого — тоже отказ, с пометкой «ЛИШНЕЕ: дубли или
посторонний трафик».

Числа не случайны: 186 — успешные заказы, 200 — все запросы (спан `create_order`
создаётся и на ошибочных), 14 — ровно ошибочные из плана.

## Ловушки, на которые ушло время

Собраны здесь, чтобы повторяющий не потратил то же самое.

**Инфраструктура и платформа**

- **PostgreSQL 18 сменил точку монтирования.** Том нужен на `/var/lib/postgresql`,
  а не на привычном `/var/lib/postgresql/data`: данные лежат в подкаталоге с
  мажорной версией. Старый путь образ отвергает и выходит с кодом 1.
- **Tempo 3.0 не принимает конфиг 2.x.** Legacy ingesters удалены, вместо них
  live-store и block-builder; секции `ingester` и `compactor` на верхнем уровне
  отвергаются. Для переноса есть `tempo-cli migrate config`. Зато дефолты 3.0
  подходят стенду: свежий трейс находится поиском через секунды.
- **Spring Boot 4 принёс Jackson 3** (пакет `tools.jackson.*`,
  `com.fasterxml.jackson.databind` в classpath отсутствует) и **вынес тестовые
  слайсы** из `starter-test` в отдельные артефакты: `@WebMvcTest` живёт в
  `spring-boot-webmvc-test`, пакет `org.springframework.boot.webmvc.test.autoconfigure`.
- **search.maven.org отдаёт устаревший индекс** (для Spring Boot — версии июня
  2025). Источник истины — `maven-metadata.xml` в repo1.
- **Git Bash переписывает POSIX-пути** в значениях аргументов и переменных:
  `-javaagent:/app/...` доезжало до JVM как `-javaagent:C:/Program Files/Git/app/...`.
  Поэтому режим пишется в `.env` (его читает compose, конверсии нет), а обмен
  итогом прогона идёт через stdout, а не через файл в контейнере.
- **Проброс портов Docker Desktop работает с перебоями**: один и тот же запрос к
  Loki давал 200, 200, таймаут. Все проверки обращаются к сервисам изнутри
  docker-сети; порты на хост объявлены для человека.
- **`/tmp` Git Bash в контейнер не монтируется** — файлы для bind-mount кладём в
  каталог стенда и монтируем с `MSYS_NO_PATHCONV=1`.

**Платформа, продолжение**

- **`python` есть не везде.** В Git Bash он есть, в Ubuntu 24.04 — только
  `python3`. Скрипты выбирают имя сами и проверяют его до начала работы.
- **`grep` в `$(...)` при `set -e` роняет скрипт молча.** Проверка «какой конфиг
  выбран» читает `.env` грепом; когда строки там нет (обычный режим её не
  пишет), grep возвращает 1 и подъём обрывается без единого сообщения. Нужен
  `|| true` — поймано на себе через минуту после добавления проверки.

**Замеры, которые врали правдоподобно**

- **Потоковый `docker stats` под нагрузкой отдавал `-- / --` в 97 % строк**, а
  парсер считал прочерк нулём: получалось «ОЗУ ср 0,4 МиБ при максимуме 17,5».
  Лечится циклом снимков `--no-stream` и явным подсчётом отброшенных точек.
- **`awk` сравнивал загрузку процессора как строки**: `"104.32"` лексикографически
  меньше `"8.7"`, отчего максимум оказывался меньше среднего. Лечится `+0`.
- Общий признак обеих ошибок — **среднее больше максимума**. Стоит закладывать
  такую проверку в сам скрипт.
- **`limit=200` в запросе к Tempo молча обрезал счёт.** Контроль «200 трейсов из
  200 запросов» выглядел доказательством исправности, хотя показал бы те же 200
  при любом реальном числе.
- **TraceQL `duration` относится к СПАНУ, а не к трейсу.** Политику `latency` в
  Collector надо сверять с `trace:duration`: на одних данных 34 против 80.
- **`pg_sleep` в `WHERE` возвращает ноль строк** (функция возвращает `void`, и
  условие `IS NULL` не выполняется): существующий товар получал 404. Поймано
  сверкой факта с планом нагрузки, а не глазами.

**Телеметрия**

- **Дефолтный протокол Java-агента — `http/protobuf`**, не gRPC. Порт 4317 в
  `OTEL_EXPORTER_OTLP_ENDPOINT` он встречает предупреждением.
- **В Go SDK gRPC и HTTP — разные модули экспортёров**, переменная
  `OTEL_EXPORTER_OTLP_PROTOCOL` сама ничего не переключает: выбор делает код.
- **`slog.Info` вместо `slog.InfoContext`** тихо даёт записи с пустым `trace_id`.
  Критерий проверки — **ноль** записей без `trace_id`, а не наличие записей с ним.
- **Мост `otelslog` не трогает stdout.** Структурный лог получается, коррелируемый —
  нет; для файлового маршрута нужен свой хендлер (`traceContextHandler`).
- **Дефолтный набор индексных лейблов Loki НЕ безопасен.** В
  `default_resource_attributes_as_index_labels` у 3.7.5 **восемнадцать**
  атрибутов. Надёжно текучи два: `service.instance.id` (новый UUID при каждом
  старте процесса) и `k8s.pod.name` (у пода Deployment; у StatefulSet имя
  стабильно — `app-0`, `app-1`). Ещё три — `k8s.replicaset.name`, `k8s.job.name`
  и `container.name` — стоит считать **потенциально текучими**: поведение зависит
  от контроллера, окружения и того, что проставляет атрибут. В Kubernetes
  `container.name` обычно совпадает с `k8s.container.name`, который берётся из
  шаблона Pod и стабилен между репликами. Имена контроллеров
  (`k8s.deployment.name` и прочие) и `k8s.container.name` стабильны.
  Три рестарта java-backend дали 2, 3, 4, 5 потоков ОДНОМУ сервису — см.
  `./scripts/bench-instance-id.sh`. Набор задан явно, с `ignore_defaults: true`;
  instance.id остаётся в structured metadata и доступен для фильтров.
  Кардинальность своих лейблов смотреть через `/loki/api/v1/series` и
  `/loki/api/v1/label/<name>/values`, а НЕ агрегацией LogQL: `count by (...)` с
  большим окном упирается в «maximum number of series (500) reached» независимо
  от индекса — проверено на стенде с двумя потоками.
- **`| json` на OTLP-логах не возвращает пустоту** — он возвращает записи с
  `__error__="JSONParserErr"`, потому что тело записи это само сообщение, а поля
  уже разобраны и лежат в structured metadata. Пусто получается на следующем шаге,
  при фильтре по полю, которого парсер не создал. Диагностический сигнал легко
  пропустить, если писать фильтр сразу.
- **Go SDK не выставляет `service.instance.id`, Java-агент выставляет.** Из-за
  этого первая версия опыта (рестартовали Go-сервис) не показала ничего, и вывод
  получился бы противоположный истине.
- **OTTL `set(resource.attributes[...])` в контексте `log` меняет ресурс всей
  группы записей**, а не отдельной записи. Чтобы получить атрибут на запись,
  нужен `groupbyattrs`.
- **Tempo отдаёт trace id без ведущих нулей** (31 символ вместо 32). Переход «из
  трейса в логи» ломается у каждого шестнадцатого трейса; дополняйте до 32.
- **`health: "ok"` у правила Prometheus не значит, что правило работает.** Оно
  значит только, что выражение не упало. Правило может успешно вычислять пустоту:
  на дашборде «No data», алерт поверх не срабатывает никогда.
- **Селектор `{http_response_status_code=~"5.."}` замалчивает здоровые сервисы.**
  Серии с 5xx у сервиса, который их ни разу не отдал, просто не существует — это
  не «ноль», это отсутствие данных. Лечится `or on (service_name) (0 * <общий
  rate>)`; `or vector(0)` не годится, у него нет лейблов.
- **`histogram_quantile` от нулевого `rate` возвращает `NaN`**, и `NaN` не
  проходит ни одно сравнение: на простое сервиса не срабатывает ни `p95 > порог`,
  ни обратная проверка `p95 < порог`. Молчание алерта выглядит как здоровье.
- **Квантили двух гистограмм с разными границами сравнивать нельзя.** У бизнес-
  операции и HTTP-запроса кумулятивные доли совпали ТОЧНО на всех общих границах,
  а p95 разошёлся (0,17414 против 0,17241) — целиком из-за сетки бакетов.
  Квантиль внутри бакета не измеряется, а интерполируется: точность равна ширине
  бакета.
- **Менять границы гистограммы на живой метрике — несовместимое изменение.** Пока
  окно `rate` накрывает смену, новые серии `le` начинаются с нуля посреди окна, и
  квантиль в этом окне даёт то завышенное число, то `NaN`.
- **`sum(...)` без `by` в алерте на пропажу трафика ломает две вещи сразу.** Алерт
  видит только остановку ВСЕГО стенда (молчание одного сервиса теряется в сумме),
  и у него нет лейбла `service_name` — поэтому `inhibit_rules` с
  `equal: [service_name]` не совпадает никогда, подавление молча не работает.
  Лечится инвентарём ожидаемых сервисов (`label_replace(vector(1), ...)`) и
  `unless`. По метрикам инвентарь не построить: у сервиса без запросов серии нет,
  и «умер» от «никогда не было» метрики не отличают.
- **Покрытие сервисов в правиле ≠ пригодность значений.** Серия может быть, а
  значение — `NaN`; `count()` покажет полное покрытие, критерий пройдёт, алерт
  поверх правила будет молчать. Проверять надо и покрытие, и конечность каждого
  значения.
- **`docker compose run` поднимает всю цепочку `depends_on`** и возвращает к жизни
  сервис, который вы намеренно остановили для опыта. Нужен `--no-deps`.
- **`docker compose down` не трогает сервисы из профилей**, если профиль не указан:
  контейнер переживает «погашенный» стенд. Нужен `docker compose --profile "*" down`.
- **Готовность Pyroscope — ТРИ фазы, не две**: metastore 15 с, ingester 15 с,
  segment-writer 30 с, плюс запуск модулей — фактически около четырёх минут.
  Ожидание в 120 с роняло подъём стенда на исправном компоненте. При отказе
  обязательно печатать тело ответа `/ready`: там прямо написано, чего он ждёт.
- **Тонкий по CPU сервис в профиле выглядит пустым, потому что ждёт, а не потому
  что бездействует.** `go-frontend` — прокси: на чистом хранилище при 4000
  запросов его функция в профиле не появилась вовсе, при 6000 — появилась через
  54 с. У Java обратная картина: 4200 фреймов почти сразу.
- **Селектор Pyroscope сам содержит кавычки, и склейка JSON в шелле его ломает.**
  `{"label_selector":"{service_name="go-frontend"}"}` — сломанное тело; Pyroscope
  отвечает `invalid_argument`, а наивный разбор ответа превращает это в «фреймов
  0», то есть ошибка запроса выглядит как отсутствие профиля. Тело надо строить
  `json.dumps`, а разбор — отличать ошибку сервера от честной пустоты.
- **Суждение «X в данных нет» требует проверки, что данные есть.** Критерии
  «pg_sleep не в профиле» и «в покое пусто» рапортовали ГОДЕН на ПУСТЫХ профилях.
- **Связка профиль↔трейс даёт метку `span_name`, а не `span_id`**, и только для
  КОРНЕВОГО спана. Имя берётся на момент старта: корневой спан называется
  `POST /order`, а метка — `POST`, потому что `otelhttp` дописывает маршрут позже.
  Все POST-эндпоинты сольются в одну метку.
- **Блокировочные профили Go не появятся без двух вызовов** —
  `runtime.SetMutexProfileFraction` и `runtime.SetBlockProfileRate`. По умолчанию
  оба выключены, типов mutex/block в Pyroscope просто не будет, молча.
- **У оператора `or` приоритет НИЖЕ, чем у деления, а `promtool` этого не видит.**
  Выражение `A or on(...) (0 * B) / B` читается как `A or ((0*B)/B)`, то есть
  основная ветка на знаменатель не делится. Замерено: без внутренних скобок
  burn rate 16,79 вместо 100. Дефект не проявляется при проверке «алерт зажёгся»,
  потому что 16,79 тоже выше порога — но зависит уже от абсолютного RPS.
- **Alertmanager вырезает `url` приёмника из `/api/v2/status`** как секрет:
  проверить «куда настроена доставка» через API нельзя, только по факту получения.
- **Приёмник алертов обязан отвечать HTTP-ответом.** Заглушка на `netcat`
  получает тело, но не отвечает, и Alertmanager считает доставку неудачной —
  шесть попыток и явный отказ в логах. Поэтому приёмник здесь — сервис на Go.
- **Алерт гаснет дольше, чем зажигается.** Замер: до `firing` 70-84 с, затухание
  259-272 с — примерно длина окна `rate` после прекращения деградации. После
  починки алерт горит ещё около окна, и это не поломка.
- **`otelhttp` в Go знает шаблон маршрута.** Он попадает в имя спана и в лейбл
  метрики `http_route` (проверено: 5 запросов к `/order/ord-N` дали одну серию
  `/order/{id}`), но отдельным атрибутом спана не дублируется — в отличие от
  Java-агента. Источник шаблона — `http.ServeMux` (`r.Pattern`, Go 1.22+);
  самописный роутер без шаблонов положит в лейбл конкретный путь.

## Дисциплина замеров

Принята по итогам этого и предыдущих стендов:

1. Между режимами стенд поднимается заново с чистыми томами.
2. Перед замером — прогрев и пауза: у JVM без прогрева измеряется разогрев.
3. Окно сбора ресурсов синхронизировано с прогоном.
4. Первый снимок отбрасывается — он снят до разгона нагрузки.
5. Каждый режим прогоняется дважды, в отчёт идут оба числа.
6. Утверждение, для которого разброс шире эффекта, не делается вовсе — вместо
   вывода пишется, почему вывода нет (так вышло с памятью JVM).

## Что стоит посмотреть в Grafana

1. Explore → Tempo → поиск `{name="create_order"}` → открыть трейс: видно все
   участки, включая асинхронную ветку.
2. В спане `SELECT` — атрибуты `db.*`; литералы обезличены агентом.
3. Из трейса — переход в логи (кнопка «Logs for this span»); обратно из строки
   лога — «Открыть трейс».
4. Explore → Prometheus → `khorost_tech_orders_created_total` — бизнес-метрика с
   лейблом `reserved`.
