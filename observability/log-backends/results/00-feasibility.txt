Выполнимость стенда log-backends: три бэкенда логов на одной машине
====================================================================
Дата: 2026-08-19. Проверка идёт ДО постройки стенда, потому что два её
пункта (имена полей и способ счёта объёма) могли изменить состав замеров.


1. ВЕРСИИ ПО БИНАРНИКАМ
------------------------
  grafana/loki:3.7.5                     -> loki, version 3.7.5 (revision 052f8ee9)
  opensearchproject/opensearch:3.5.0     -> берётся из стенда vector-vs-collector,
                                            там версия уже сверена
  victoriametrics/victoria-logs:v1.52.0  -> victoria-logs-20260716-022232-tags-v1.52.0

ПРО ТЕГ VictoriaLogs. У образа есть `latest`, и на момент проверки он указывает
на v1.52.0. В compose пинуется ИМЕННО v1.52.0: `latest` через месяц будет
другим, и числа замеров перестанут соответствовать стенду.


2. ПАМЯТЬ: ТРИ БЭКЕНДА РАЗОМ
-----------------------------
Подъём без Vector, генератора и Grafana, в покое, через 45 секунд после старта:

  lb-vlogs (VictoriaLogs)    11.5 МиБ
  lb-loki  (Loki)            44.7 МиБ
  lb-os    (OpenSearch)    1745.0 МиБ   <- при OPENSEARCH_JAVA_OPTS=-Xms1g -Xmx1g
  --------------------------------------
  итого                    ~1.8 ГиБ

Соотношение в покое — 150:1 между OpenSearch и VictoriaLogs. Это ещё не
результат замера (нагрузки не было), но сразу задаёт масштаб: два из трёх
бэкендов в покое занимают меньше, чем OpenSearch тратит на разогрев JVM.

С Vector, Grafana и генератором ожидается ~2.1-2.2 ГиБ. Стенд подъёмный.
Для читателя с меньшей машиной в README будет сказано, как урезать heap
OpenSearch до 512m.


3. ПРИЁМ В VictoriaLogs: РАБОТАЮТ ОБА ПУТИ
-------------------------------------------
Проверено отправкой записи и чтением её обратно.

а) jsonline:
   POST /insert/jsonline?_stream_fields=service&_msg_field=message&_time_field=timestamp
   Content-Type: application/stream+json
   -> HTTP 200, запись читается

б) elasticsearch bulk (ЭТОТ путь и нужен синку Vector `elasticsearch`):
   POST /insert/elasticsearch/_bulk?_msg_field=message&_time_field=timestamp&_stream_fields=service
   Content-Type: application/x-ndjson
   -> {"took":0,"errors":false,"items":[{"create":{"status":201}}]}, запись читается

ВНИМАНИЕ на параметры запроса. `_stream_fields` определяет, что VictoriaLogs
считает ПОТОКОМ, — то есть напрямую задаёт его модель кардинальности. Указать
там высококардинальное поле значит устроить VictoriaLogs ровно ту же беду, что
Loki устраивает высококардинальная метка. Для замера 4 это ключевой параметр.

Чтение: POST /select/logsql/query с телом `query=<LogsQL>`.


4. ГЛАВНАЯ НАХОДКА: ИМЕНА ПОЛЕЙ РАСХОДЯТСЯ У ВСЕХ ТРЁХ
--------------------------------------------------------
Отправлена ОДНА И ТА ЖЕ запись:
  {"timestamp": ..., "service": ..., "message": ..., "level": "error"}

Что получилось на приёме:

  БЭКЕНД         ПОЛЯ ПОСЛЕ ДОСТАВКИ
  OpenSearch     level, message, service, timestamp      <- как отправили
  VictoriaLogs   _msg, _stream, _time, level, service    <- message->_msg, timestamp->_time
  Loki           service, level, service_name, detected_level  <- ДОБАВИЛ два своих

Три разных исхода из одной записи:
  - OpenSearch сохранил как есть;
  - VictoriaLogs ПЕРЕИМЕНОВАЛ служебные поля в свои (_msg, _time), остальные
    оставил;
  - Loki ДОБАВИЛ поля, которых не было: service_name (из service) и
    detected_level (вывел из содержимого сам).

СЛЕДСТВИЕ ДЛЯ ЗАМЕРА 3. «Один и тот же запрос на трёх языках» невозможен не
только из-за разного синтаксиса — у бэкендов разные ИМЕНА полей для одного и
того же. Запрос придётся писать под каждый, и это не недостаток стенда, а факт,
который в статье надо назвать прямо: переносимость запросов между бэкендами
логов отсутствует на уровне модели данных, а не только грамматики.

Отдельно про detected_level: Loki самостоятельно определяет уровень записи. Для
замера кардинальности это значит, что число меток у него будет больше, чем
задано конфигурацией, — и это надо учесть, а не списать на ошибку.


5. КАК СЧИТАТЬ ОБЪЁМ
---------------------
`du` внутри контейнера НЕ РАБОТАЕТ для двух бэкендов из трёх: образы Loki и
VictoriaLogs собраны без шелла (distroless).

  docker exec lb-loki  du ... -> exec: "sh": executable file not found in $PATH
  docker exec lb-vlogs du ... -> то же
  docker exec lb-os    du ... -> работает, 706073 байта в /usr/share/opensearch/data

Решение: данные каждого бэкенда кладутся в ИМЕНОВАННЫЙ ТОМ, а размер меряется
снаружи вспомогательным контейнером:

  docker run --rm -v <том>:/data alpine:3.21 du -sb /data

Проверено на пробном томе — способ работает и одинаков для всех трёх, то есть
числа сравнимы между собой. Это важнее удобства: разные способы измерения дали
бы разницу метода вместо разницы бэкендов.

Метрики самих бэкендов для этого не годятся: у VictoriaLogs есть vl_storage_*,
но они про чтение блоков, а не про размер на диске, и у трёх систем они разные
по смыслу.


ВЕРДИКТ
--------
ГОДЕН по всем пунктам, состав замеров не меняется. Два уточнения, которые
войдут в стенд и в статью:

1. Запросы для замера 3 пишутся ПОД КАЖДЫЙ бэкенд (разные имена полей), а
   критерием остаётся совпадение ЧИСЛА в ответе.
2. Объём меряется снаружи через вспомогательный контейнер на именованных
   томах — одинаково для всех трёх.
