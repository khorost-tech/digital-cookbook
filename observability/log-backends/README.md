# Стенд: три бэкенда логов на одном потоке

Один генератор пишет файл, один Vector читает его и разливает **тремя синками
из одного источника** — в Loki, OpenSearch и VictoriaLogs. Трансформация стоит
до ветвления, поэтому во все три приезжает буквально одно и то же событие.

Статья: [Где хранить логи: Loki vs OpenSearch vs VictoriaLogs](https://khorost.tech/observability/log-backends-loki-opensearch-victorialogs/)

## Что внутри

```
docker-compose.yml              три бэкенда, Vector, генератор, Grafana
vector/agent.yaml               источник, одна трансформация, три синка
vector/agent-highcard.yaml      + уникальное поле объявлено МЕТКОЙ (замер 4)
vector/agent-isolated.yaml      + явная политика буферов у синков (замер 6)
vector/agent-tuned.yaml         + запись в индекс со строгим маппингом (замер 5)
loki/loki.yaml                  Loki с короткими интервалами сброса чанков
loki/loki-tuned.yaml            + discover_log_levels: false
opensearch/index-template-tuned.json   строгий маппинг: keyword вместо text
loadgen/                        генератор JSON-логов с манифестом ожиданий
scripts/                        подъём, останов и пять замеров
results/                        сырые выводы всех прогонов
```

## Быстрый старт

```bash
./scripts/up.sh                      # поднять на значениях по умолчанию
./scripts/verify-equivalence.sh      # проверка: во все три приехало одно и то же
./scripts/down.sh clean              # погасить И СТЕРЕТЬ тома
```

Порты: Loki 9401, OpenSearch 9402, VictoriaLogs 9403, Grafana 9405 (профиль
`ui`), Vector API 9406. Диапазон 94xx выбран потому, что 93xx занят стендом
`practice-stack` этой же серии — два стенда должны подниматься одновременно.

## Режимы подъёма

```bash
./scripts/up.sh              # значения по умолчанию
./scripts/up.sh highcard     # уникальное поле в метке Loki и в потоке VictoriaLogs
./scripts/up.sh isolated     # то же + when_full: drop_newest у синка Loki
./scripts/up.sh tuned        # строгий маппинг OpenSearch, discover_log_levels: false
./scripts/up.sh default ui   # плюс Grafana для человека
```

## Замеры

| Скрипт | Что доказывает | Отчёт |
|---|---|---|
| `verify-equivalence.sh` | во все три бэкенда приехал ОДИН И ТОТ ЖЕ набор, и один вопрос на трёх языках даёт одно число | `01-equivalence.txt` |
| `bench-storage.sh` | объём одного потока в трёх бэкендах: данные отдельно от журналов, медиана серии с разбросом | `02-storage.txt` |
| `bench-resources.sh` | память в покое и под нагрузкой; почему CPU этими средствами не меряется | `03-resources.txt` |
| `bench-cardinality.sh` | три сценария: поля нет, поле в теле, поле в метке. Момент отказа Loki | `04-cardinality.txt` |
| `bench-tuned.sh` | что даёт настройка и чего она стоит | `05-tuned.txt` |
| `bench-isolation.sh` | что на самом деле изолирует отказ синка: раздельность буферов или политика переполнения | `06-isolation.txt` |
| `verify-partial-accept.sh` | сохраняет ли Loki строки из запроса, на который ответил 429 | `07-partial-accept.txt` |

Скрипты с приставкой `verify-` — **проверки**: при неподтверждённом результате
они возвращают ненулевой код, а не печатают «не получилось» и выходят успешно.
Иначе регрессия бэкенда или поломка стенда дала бы зелёный запуск и молча
переписала бы отчёт, который ничего не доказывает. У `verify-partial-accept.sh`
условие тройное: ответ `429`, рост существующего потока И пустой новый — без
последнего «предел не действовал» выглядело бы как успех опыта.

**Проверка сопоставимости идёт первой.** Пока не доказано, что во все три
приехал один и тот же набор записей, мерить объём и ресурсы бессмысленно:
числа будут описывать разные данные, а разницу спишут на модели индексации.

Замеры `bench-cardinality.sh` и `bench-tuned.sh` умеют запускаться по одному
сценарию — прогон со взрывом кардинальности занимает больше десяти минут:

```bash
./scripts/bench-cardinality.sh 100000 42 plain
./scripts/bench-cardinality.sh 100000 42 body
./scripts/bench-cardinality.sh 100000 42 label
./scripts/bench-cardinality.sh 100000 42 report   # собрать отчёт из готовых
```

## Что нужно на машине

| Инструмент | Зачем | Проверка |
|---|---|---|
| Docker + compose v2 | весь стенд | `docker compose version` |
| `python3` | скрипты разбирают им ответы бэкендов | `python3 --version` |
| Go 1.26+ | только чтобы гонять тесты генератора | `go version` |

Оперативной памяти нужно около 2,2 ГиБ: OpenSearch один занимает полтора
гигабайта ещё до первой записи. На машине поменьше уменьшите ему heap в
`docker-compose.yml` (`OPENSEARCH_JAVA_OPTS=-Xms512m -Xmx512m`) — но тогда на
сотне тысяч записей он начнёт тормозить на слияниях, и замер объёма поймает
нехватку памяти вместо устройства индекса.

## Ловушки, на которые ушло время

Каждая стоила отдельного прогона; описаны подробно в соответствующих
`results/*-findings.txt`.

**Замер объёма Loki ловил журнал, а не данные.** По умолчанию
`chunk_idle_period` — 30 минут: на коротком прогоне чанки остаются в памяти, в
томе лежит только WAL, каталога `chunks` нет вовсе. Поэтому в конфигурации
стенда интервалы сброса укорочены — это **условие замера**, а не оптимизация.
Обратная сторона: мелкие чанки сжимаются хуже, и объём Loki здесь скорее
завышен относительно продового режима.

**Размер на диске не стабилизируется.** Фоновые слияния меняют его в обе
стороны минутами позже окончания потока: наблюдалось 2,30 → 2,30 → 2,31 →
3,56 МБ. Критерий «N одинаковых замеров подряд» ловит паузу между операциями, а
не их конец, поэтому берётся медиана серии с явным разбросом.

**`forcemerge` возвращается до окончания слияния.** Без
`wait_for_completion=true` объём OpenSearch скакал между прогонами: 20,7 / 6,0 /
4,3 / 2,9 МиБ на одних и тех же данных.

**Разброс внутри серии не описывает воспроизводимость.** После починки метода
серия даёт 0–2,2 %, но два полных прогона одной конфигурации разошлись на 5 % по
VictoriaLogs и дали кратность 22,4× против 23,9×. Каждый прогон — своя история
фоновых слияний, поэтому в статью идёт порядок величины, а не точное число.

**Потери считаются двумя способами, и они обязаны совпасть.** Сведение по
буферу синка (принял минус отдал минус держит) и прямой счётчик
`vector_buffer_discarded_events_total` с метками `buffer_id`, `stage`,
`intentional`. Прежняя редакция этого файла утверждала, что такого счётчика
в Vector 0.57 нет, — это неверно: он есть, но его серия появляется только
после первого выброса, а сам выброс при `drop_newest` Vector пишет в лог
лишь на уровне debug. Прогон 2026-10-16 дал по обоим способам одно число.

**Утверждение о потерях обязано замыкать баланс.** Первая редакция замера
изоляции считала потери как «буфер принял минус отдал минус держит» и оставляла
5639 событий без объяснения: «буфер отдал» — это не «Loki принял», между ними
события в повторах. Теперь снимается вся цепочка, и замер падает, если сумма
частей не сходится с принятым. Заодно: метрики Vector размечены `buffer_id` и
`stage`, поэтому серии надо **суммировать**, а не брать по `component_id`.

**Loki принимает запрос частично, и счётчик отправителя этого не видит.**
Запрос с хотя бы одним отвергнутым потоком завершается ошибкой целиком, события
из него не попадают в `vector_component_sent_events_total` — но строки в потоки,
помещавшиеся в лимит, Loki сохраняет. Поэтому в Loki видно больше, чем синк
насчитал доставленным. Доказано опытом `scripts/verify-partial-accept.sh`: при
занятом пределе один запрос из существующего и нового потока получает `429`,
запись в существующий поток проходит, а в новый — нет. Числа последнего прогона
— в `results/07-partial-accept.txt`; здесь они не дублируются, чтобы копия не
разошлась с отчётом.

Осторожно с объяснением «у отправителя батчи, у получателя строки»: оно звучит
убедительно, но `component_sent_events_total` считает **события**, а не запросы,
поэтому ничего не объясняет. Батчи считает только счётчик HTTP-ответов.

**Вывод python по умолчанию идёт в кодировке консоли.** На Windows это cp1251, а
`echo` пишет UTF-8 — отчёт получался в смешанной кодировке, и «532.6 КиБ»
читалось как «532.6 ???». В `scripts/lib.sh` теперь `export PYTHONIOENCODING=utf-8`.

**Опыт с высокой кардинальностью требует флага генератора.** Без
`-high-cardinality` поле `request_id` не пишется, метка не создаётся, и все три
бэкенда принимают поток целиком — «изоляция сработала» выглядит точно так же,
как «ломать было нечем». Поэтому в `bench-isolation.sh` есть контроль наличия
поля, причём ОЖИДАЮЩИЙ: спрошенный сразу маппинг OpenSearch отвечает «поля нет»
просто потому, что индекса ещё не создано.

**Loki добавляет метки, которых вы не отправляли, и набор зависит от способа
доставки.** При прямом push появляются `service_name` и `detected_level`; через
синк Vector — только `service_name`. Ранняя проверка выполнимости снимала набор
при прямом push, и её вывод сначала перенесли на конвейер стенда — то есть в
отчёте оказалась метка, которой в замерах не было. Теперь набор снимает
`verify-equivalence.sh` у живых бэкендов и сверяет точным равенством.

**`du` внутри контейнера не работает** у Loki и VictoriaLogs: образы собраны без
шелла. Размер меряется снаружи вспомогательным контейнером — одинаково для всех
трёх, иначе сравнивались бы методы измерения.

**Vector 0.57 требует статический префикс в шаблонах.** Для меток Loki это
избыточно (метка не адресует хранилище), поэтому в конфиге стоит явный отказ от
confinement с объяснением.

**Записи «из будущего» принимаются, но не находятся.** Генератор сначала писал
фиксированную дату на два месяца вперёд: VictoriaLogs показывал
`vl_rows_ingested_total 5000` и ноль в ответе на запрос. База времени стала
параметром.

## Дисциплина замеров

- Критерии — точные равенства там, где они достижимы.
- Между прогонами `./scripts/down.sh clean`, а не `down.sh`: без аргумента тома
  сохраняются, и замер «на чистых томах» идёт на грязных.
- Прежде чем судить по числу, проверяется, что измеряемое вообще существует и
  доехало полностью.
- Если разброс шире эффекта — вывода нет, и отчёт говорит об этом прямо. Так
  вышло с CPU: три прогона одной конфигурации дали пик 662 %, 70 % и 514 %.
