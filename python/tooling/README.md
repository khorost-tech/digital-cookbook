# Инструменты Python: упаковка, образы, тесты

Стенд к двум статьям:

* [Упаковка Python: uv, Poetry и pip на одном
  наборе](https://khorost.tech/python/python-packaging-uv-poetry/) — установка
  зависимостей и сборка образа;
* [Тесты в Python: моки, настоящая база и
  property-based](https://khorost.tech/python/python-testing/) — кто ловит
  подсунутый дефект и во что это обходится.

Отвечает на три вопроса, и ни один из них не про «что быстрее» в чистом виде:

1. Сколько стоит установка зависимостей у **uv, Poetry и pip** — и отдельно
   в каждом из трёх состояний кэша, потому что «холодная установка» и
   «повторный install» — это разные задачи, а не одна с разбросом.
2. Что даёт каждая **стратегия сборки образа** — при условии, что все
   образы отвечают одинаково.
3. Кто ловит подсунутый дефект: **моки, фейк на SQLite, настоящая база в
   контейнере, property-based набор** — и во что обходится каждый ответ.

Версии пинованы и печатаются из самих пакетов: Python 3.14.7,
uv 0.12.5, Poetry 2.3.1, pip 26.0, PostgreSQL 18.4, SQLAlchemy 2.0.52,
pytest 9.1.1, hypothesis 6.165.10, testcontainers 4.15.0, Docker 29.7.2.

## Как обеспечена сопоставимость

**Сеть за скобками.** Все установки идут из локального индекса: колёса
скачиваются один раз и дальше отдаются по HTTP с диска. Иначе разброс сети
перекрыл бы разницу между инструментами.

Индекс отдаёт `Cache-Control` и `ETag`, и это не украшение. Штатный
`http.server` шлёт только `Last-Modified`; uv на этом работает — у него
свой кэш артефактов, — а pip нет: его HTTP-кэш построен на CacheControl и
без этих заголовков не сохраняет ничего. Замер это показал так: у pip
тёплый прогон почти не отличался от холодного, а каталог кэша оставался
пустым. Вывод «pip не выигрывает от тёплого кэша» напрашивался сам и был
бы неверным — он не выигрывал от кэша, которого стенд не позволял создать.

Отдельно пришлось чинить страницы индекса: для пути вида `/simple/six/`
`os.path.isfile` ложно, ветка с заголовками не срабатывала, и кэшировались
только колёса. По объёму недостача почти незаметна, а влияет она ровно на
ту часть работы, которую и сравниваем.

**Порядок состояний ротируется, и это главное в устройстве сценария.**
Первая версия гоняла состояния строго подряд — cold, warm, noop, — исходя
из того, что «тёплый» означает «после холодного» и порядок задан смыслом.
Рассуждение неверное: кэш можно наполнить ВНЕ ЗАМЕРА, а потом привести
окружение к нужному состоянию, и тогда любое состояние достижимо на любой
позиции.

Цена ошибки была не в аккуратности, а в выводе: при фиксированном порядке
разность `cold − warm` включала и эффект кэша, и эффект позиции — прогрев
процессора, страничный кэш ОС, — а отделить одно от другого было нечем.

Теперь перед КАЖДЫМ замером идёт одинаковый неучитываемый прогон, и лишь
потом состояние доводится до нужного:

```
cold   prime, затем кэш инструмента очищается, окружение удаляется
warm   prime, затем удаляется только окружение
noop   prime, и больше ничего
```

Дальше ротируются ДВА порядка, и они обязаны быть независимы.

Первая попытка развести их провалилась незаметно: порядок состояний
брался тем же латинским квадратом со смещением на номер инструмента, и
казалось, что смещение развязывает ротации. На деле оно связало их
намертво — у uv «состояние на первой позиции» означало ровно «uv
запускается третьим, после Poetry и pip»:

```
круг 1: pip, poetry, uv   -> у uv warm на 1-й позиции
круг 2: poetry, uv, pip   -> у uv warm на 3-й позиции
круг 3: uv, pip, poetry   -> у uv warm на 2-й позиции
```

Разложение времени по позиции состояния было в точности разложением по
позиции инструмента, и приписать наблюдение одному из двух факторов было
нельзя.

Теперь ключа два и они независимы: порядок инструментов — циклический
сдвиг по `(r-1) % 3`, порядок состояний — одна из ШЕСТИ перестановок по
`(r-1) // 3`. За 18 кругов каждая пара «сдвиг × перестановка» встречается
ровно один раз. Шесть перестановок вместо трёх циклических взяты не для
красоты: при циклических холодный замер стоял бы раньше тёплого в двух
кругах из трёх, а при полном переборе — ровно в половине.

В каждую строку пишутся обе позиции плюс сквозная позиция замера в круге.
Разбор проверяет и сбалансированность каждого фактора, и то, что ни один
из них не оказался функцией другого.

**Первый круг отбрасывается.** Кэши переживают прогоны, и их СОДЕРЖИМОЕ
зависит от того, чем закончился прошлый сеанс: после плеча против PyPI кэш
uv весил 154,55 МиБ вместо установившихся 138,28, и первый круг мерил
установку по нему.

**Холодным считается кэш инструмента, а не страничный кэш ОС.** Последний
прогрет одинаково перед всеми тремя состояниями и потому из сравнения
выпадает. Измеряется «первый install там, где пакетов ещё не скачивали», а
не «install на только что загруженной машине» — это разные величины, и
вторую стенд не даёт.

**Задача одна на всех: от отсутствия окружения до окружения с набором.**
Не «время команды install». Poetry управляет окружением сам и чужой путь
игнорирует, поэтому либо окружение создают все три плеча, либо у одного
этап есть, а у двух других нет.

**Набор проверяется хешем.** Снимок `dist-info` считается после каждой
установки, и хеш уходит в каждую строку фикстуры. Это защита от того,
чтобы «быстрее» когда-нибудь означало «поставлено меньше». Проверка
опробована сбросом: удаление одного `dist-info` даёт код 2 и имя пакета.

**Холодный кэш проверяется по фикстуре, а не по памяти автора.** Размеры
всех кэшей записываются ДО каждого прогона. Прогон, в котором очищено три
кэша из четырёх, измеряет четвёртый и выглядит совершенно нормально.

**Образы сверяются по ответу.** Шесть стратегий поднимают одно и то же
приложение, у каждого спрашивается `/answer`, и хеш ответа обязан
совпасть. В ответе лежат и результат вычисления, и версии зависимостей.
Ужать образ, выкинув нужное, — обычный способ выиграть на весах.

**Дефект задаётся переменной окружения, а не правкой файла.** Иначе
«поймал» и «не поймал» оказались бы про разные версии кода.

**Предупреждения об устаревании — ошибки.** В `tests/pytest.ini` стоит
`filterwarnings = error::DeprecationWarning`. Поводом было живое
предупреждение в самом стенде: `testcontainers.postgres` в 4.15.0 оставлен
ради совместимости и просит перейти на `testcontainers.community.postgres`.
Прогон при этом был зелёным, и заметить это можно было только вчитавшись в
вывод. Теперь любой устаревший вызов роняет прогон, а исключения
перечисляются в том же файле поимённо.

## Что здесь считается размером образа

Docker показывает три разных числа за одним словом, и на этом стенде они
разошлись втрое:

```
docker image inspect .Size      108,1 МиБ   сжатые слои: что едет по сети
сумма docker history            235,7 МиБ   распакованные слои: что на диске
docker images                   360 MB      сумма первых двух (343,8 МиБ)
```

`docker images` печатает десятичные мегабайты: 343,8 МиБ — это 360,5 MB.
Смысл чисел зависит от версии Docker: таблица снята на 29.7.2. На Docker
Desktop 29.8 `inspect .Size` отдаёт сжатый размер только до первого запуска
контейнера, после распаковки — ту же сумму, что и `docker images`.

Третье — не ошибка и не другая оценка: при containerd-хранилище узел
держит и сжатые блобы, и распакованный снимок. Тождество проверяется на
всех шести стратегиях сразу.

Первая версия сценария смешала два семейства в одной строке: размер образа
брался из `inspect`, а самый толстый слой — из `history`. Получилось, что
отдельный слой весит 87 МБ при образе в 61 МБ. Ни одна проверка не
сработала, потому что проверки на это не было; теперь «часть не больше
целого» стоит в вердикте.

На classic-графдрайвере `inspect` отдаёт распакованный размер, и колонки
меняются местами. Поэтому хранилище записано в фикстуру.

## Результаты

### Установка: время, с (медиана по 18 кругам)

```
инструмент     cold      warm      noop
uv             2.74      0.58      0.01
poetry         3.59      3.03      0.75
pip           11.17     10.21      0.55
```

`cold` — кэш пуст, окружения нет: новая машина, первый прогон CI.
`warm` — кэш полон, окружения нет: CI с восстановленным кэшем.
`noop` — кэш и окружение на месте: повторный install у разработчика.

**Порядок инструментов проверяется знаком по кругам, а не размахами.**
Первая версия проверки объявляла порядок ненадёжным, если размах одной
клетки налезал на размах другой. Размах — статистика по худшему
одиночному чтению, и одного выброса хватило, чтобы забраковать порядок,
который держится в семнадцати кругах из восемнадцати: у `pip/noop` два
значения из восемнадцати выпали в область Poetry.

Порядок — утверждение о том, кто быстрее, и проверяется он тем же
способом, каким стенд считает всё остальное: в каждом круге отдельно, а
затем знаковым тестом. В снятой фикстуре все пары дают 18 из 18, кроме
`pip` против `Poetry` при `noop` — там 17 из 18.

Порог разброса 1,5x остался, но теперь он только сообщает. У `uv/noop`
медиана в сотых долях секунды, и отношение макс/мин там говорит о
разрешении таймера, а не о нестабильности.

#### Отдельное плечо: против настоящего PyPI

Числа выше сняты с локального индекса, то есть в условиях, которых в жизни
не бывает. Отдельным плечом сделан холодный прогон против настоящего PyPI —
и он **помечен в фикстуре как невоспроизводимый**, потому что таким и
является:

```
инструмент   по повторам, с   локально (медиана)
uv                 6.3, 4.5                 2.74
pip              21.7, 79.1                11.17
poetry        не измеряется    источник записан в pyproject.toml и lock
```

Два повтора подряд разошлись здесь всего на 10 %, и полагаться на это
нельзя: они идут один за другим, в одних и тех же условиях сети. В разных
сеансах тот же замер давал pip 18,6 и 60,8 секунды, а uv — 3,4 и 31,4.
Ранжировать инструменты по этому плечу нельзя — оно показывает порядок
надбавки, и только.

**Poetry здесь не измеряется, и это записано строкой в фикстуре, а не
пропуском.** Источник у него объявлен в `pyproject.toml` и продублирован в
`poetry.lock`; сменить его снаружи нечем, а правка проекта означала бы
другую задачу.

Первая версия плеча этого не знала и выставляла
`POETRY_REPOSITORIES_LOCAL_URL` — переменную, которая задаёт адрес для
ПУБЛИКАЦИИ, а не для установки. Poetry её игнорировал, ставил из локального
индекса и показывал 4,2 секунды «против PyPI»: ровно столько же, сколько
без сети. Число выглядело правдоподобно и было бы опубликовано.

Поэтому перед каждым замером этого плеча проверяется, что переопределение
адреса вообще действует: установка с заведомо мёртвого адреса обязана
упасть. Ручка, которая молча ничего не делает, — худший вид неисправности,
потому что замер при ней выглядит удавшимся.

### Образы

```
стратегия        сжатый  распакованный  толстый слой  слоёв  старт, с
naive            462.4         1250.4         661.8     12      0.66
slim             108.1          235.7          83.4      9      0.69
multistage        58.3          188.0          83.4      7      1.23
uv                48.5          156.3          83.4      7      2.35
uv-compiled       54.6          174.7          83.4      7      1.31
distroless        49.2          157.8         105.8     19      2.06
```

Размеры в МиБ. Все шесть отвечают побайтово одинаково.

**Строка slim снята с ошибкой сборки, и это оставлено намеренно.** В той
редакции `images/slim.Dockerfile` колёса копировались в образ (`COPY
index/packages /wheels`) и удалялись `rm` в том же `RUN`, что и установка.
Удаление не помогает: архивы уже лежат в слое `COPY`, 50,9 МиБ из 235,7.
Сейчас колёса подключаются к `RUN` через `--mount=type=bind` и слоя не
оставляют. Исправленный вариант снят отдельно, `scripts/slim-ab.sh` →
`fixtures/images-slim-ab.txt`, вместе с прежним slim и multistage на той же
базе для сверки (Docker Desktop 29.8, amd64 на arm64-хосте):

```
стратегия             сжатый  распакованный  слой /wheels
slim, COPY + rm        108.1          236.0          50.9
slim, --mount           58.1          185.1             —
multistage              58.4          188.2             —
```

Дрейф базы между прогонами — 0,2–0,3 МиБ на образ. Вывод меняется:
многоступенчатая сборка к исправленной тонкой базе по размеру ничего не
добавляет, прежняя разница была слоем с колёсами.

Распакованный размер после пересборки с `--no-cache` совпадает побайтово у
всех шести. Сжатый плавает до 505 байт — сжатие не повторяемо побайтово, — но это в
три с лишним тысячи раз меньше расстояния между ближайшими стратегиями.

**Абсолютное время старта переносу не подлежит, отношения — подлежат.**
Между двумя прогонами этого стенда все медианы старта выросли почти вдвое
(машина была занята), а покруговые отношения к базовой стратегии остались
на месте: 1,76 и 1,78 у multistage, 3,20 и 3,54 у uv. Поэтому рядом с
медианами печатается знаковый счёт: `naive` неотличим от `slim`, остальные
четыре медленнее его во всех 7 кругах.

**Тождество трёх размеров проверяется по фикстуре, а не заявляется.**
`docker image ls` опрашивается наравне с остальными, и разбор сверяет его
с суммой сжатого и распакованного — с допуском, потому что печатает он
округлённо:

```
стратегия      сжатое + распакованное   docker image ls
naive                       1795.9 MB             1.8GB
slim                          360.5 MB            360MB
multistage                    258.3 MB            258MB
uv                            214.7 MB            215MB
uv-compiled                   240.4 MB            240MB
distroless                    217.1 MB            217MB
```

**Digest базовых образов записывается в фикстуру — и не один, а два.**
В Dockerfile базы заданы тегами, а тег — плавающая ссылка: обновление
`python:3.14-slim` сдвинет все шесть размеров разом. Digest не делает
сборку воспроизводимой (для этого теги надо пиновать), но позволяет
понять, то же ли самое собирается.

Спрашивая тег, реестр отдаёт digest ИНДЕКСА — списка манифестов под разные
платформы, — а собирается ровно один из них. Поэтому рядом пишется digest
манифеста для `linux/amd64`.

Существенно и КОГДА он снимается. Первая версия спрашивала реестр уже
после сборки, а сборка шла без `--pull`: при локально закешированной базе
записанный digest мог относиться к образу, которого сборка не видела.
`--no-cache` тут не помогает — он не переиспользует слои сборки, но базу
из локального кэша берёт по-прежнему.

Порядок сейчас такой:

```
1. docker pull --platform linux/amd64 — по одному разу на каждую базу
2. digest снимается с ЛОКАЛЬНЫХ копий: RepoDigests и Id образа
3. сборки идут без --pull: базы уже свежие, тянуть их заново нечего
4. после прогона Id локальных копий сверяется с записанным
```

Полей записывается четыре, и путать их не стоит:

```
repo_digest   ссылка вида python@sha256:… у локальной копии после pull
image_id      Id локального образа
index         digest индекса из реестра
platform      digest манифеста linux/amd64 из реестра
```

**`image_id` при containerd-хранилище совпадает с digest ИНДЕКСА, а не
манифеста платформы** — проверено на всех пяти базах стенда. То есть по
локальным полям видно, какой мультиплатформенный образ вытянут, но не
какой из его манифестов пошёл в сборку. Однозначно отвечает на это только
`platform`, и потому он записывается отдельно, а не выводится из
остального.

Локальные поля всё равно нужны: они снимаются с того, что реально лежит на
диске, тогда как реестр за время прогона может отдать уже другое.
Спрашивать про `RepoDigests` локальный демон до явного `docker pull`
бесполезно — buildkit тянет базы в кэш сборки, и там их нет.

Пункт 3 — не экономия, а необходимость. Сперва я поставил `--pull` на
каждую сборку: шесть стратегий, каждая собирается дважды (обычно и с
`--no-cache`), у каждой одна-две базы — под шесть десятков обращений к
реестру за прогон. Docker Hub отвечает `429 Too Many Requests`, и замер
останавливается на середине.

Пункт 4 сверяет именно локальные копии. Реестр за время прогона обновиться
может — это его право и на собранное не влияет; а вот смена локальной базы
означала бы, что часть образов собрана из одной, часть из другой.

**Про байт-код.** `uv` без `--compile-bytecode` дописывает 252 файла `.pyc`
при первом импорте и стартует 2,35 с против 1,31 с у скомпилированного.
Дописанное живёт в записываемом слое контейнера и исчезает вместе с ним:
эту работу платит каждый запуск, а не только первый.

Проба смотрит не на счётчик файлов, а на время их изменения. Устаревший
байт-код Python компилирует НА МЕСТЕ — файл тот же, число файлов не
меняется, и счётчик показал бы «+0» ровно там, где работа делается на
каждом запуске.

**Про distroless.** Он собрался и не запустился: `pydantic_core` просит
`libgcc_s.so.1`, которой в базе нет. Сборка при этом не сказала ни слова.
Колёса с нативным кодом рассчитывают найти системные библиотеки в
дистрибутиве, а в distroless дистрибутива нет; список узнаётся не на
сборке, а на первом запуске.

**Чего этот замер не объясняет.** Плечи с venv (`multistage`,
`uv-compiled` — около 1,05 с) стартуют дольше плеч, ставящих в системный
интерпретатор (`slim`, `naive` — около 0,58 с). Байт-код здесь ни при чём:
у всех четырёх он на месте, ничего не дописывается и не переписывается.
`-X importtime` показывает, что дороже обходятся ТЕ ЖЕ модули, включая
стандартную библиотеку по тому же пути. Это указывает скорее на чтение с
диска, чем на работу интерпретатора, — но указывает, а не доказывает.

### Тесты: кто ловит подсунутый дефект

```
состояние кода   моки    фейк    база  hypothesis
none             зел.    зел.    зел.        зел.    контроль
null-filter       нет  поймал  поймал      поймал    <> вместо IS DISTINCT FROM
like-case         нет     нет  поймал      поймал    LIKE вместо lower(...) LIKE
group-by          нет     нет  поймал      поймал    колонка вне GROUP BY
n-plus-1       поймал     нет     нет         нет    запрос на каждого автора
```

Контроль зелёный у всех четырёх. Без него «поймал» ничего не значит:
набор, красный всегда, ловит любой дефект и ни одного.

Строка `n-plus-1` появилась после того, как набор на моках не поймал
ничего в первой версии матрицы. Три «нет» подряд читались бы приговором
подходу, хотя означали лишь, что своего дефекта он не встретил: N+1 не
меняет результат, поэтому оба плеча, сверяющие результат, молчат — включая
настоящую базу.

Фейк на SQLite тоже не пустышка и не панацея. `null-filter` он ловит
по-настоящему: NULL он трактует как PostgreSQL. `like-case` и `group-by`
пропускает — у него LIKE регистронезависим для ASCII, а несгруппированную
колонку он разрешает. Оба раза он зелёный, и оба раза неправ.

### Property-based: примеров до ошибки

```
состояние кода   без сжатия   со сжатием   поймал
none                    100          100      нет
null-filter               4           27       да
like-case                 4           47       да
group-by                  2           12       да
n-plus-1                100          100      нет
```

Считать примеры можно только на прогоне без сжатия: после первого падения
hypothesis прогоняет тело ещё десятки раз, СОКРАЩАЯ пример, и счётчик
покажет работу сжатия, а не поиска.

База примеров отключена (`database=None`). Иначе падавший пример
подставляется первым, и «нашлось со второго примера» окажется свойством
кэша.

Числа в левой колонке от прогона к прогону меняются: генератор
случайный. Устойчиво тут другое — порядок величин и то, какие состояния
кода вообще достижимы за отведённый предел.

Сокращённый контрпример для `like-case`:

```
Failing test case: test_rules_hold_for_any_dataset(
    pg_engine=Engine(postgresql+psycopg://test:***@.../test),
    data=([{'author': 'lem', 'title': 'AAA', 'status': 'done', 'id': 1}], 'a'),
)
```

Одна задача с названием `AAA` и запрос `'a'`. «Сокращённый» не значит
«наименьший возможный»: hypothesis упрощает, пока упрощение сохраняет
падение, и останавливается на достигнутом.

### Цена прогона

```
набор                   область    медиана, с   стартов контейнера
моки                          —           0.9                    0
фейк (SQLite)                 —           0.9                    0
база (Testcontainers)  function          13.5                    3
база (Testcontainers)   session           6.2                    1
```

Одни и те же три теста стоят вдвое с лишним дороже, если контейнер
поднимается на каждый тест. Старты считаются в `conftest` и пишутся в фикстуру: выводить
их из области видимости («session — значит один раз») значит проверять
своё представление о pytest, а не pytest.

## Как запустить

Сценарий установки идёт в контейнере, два других — на хосте: образам
и Testcontainers нужен доступ к демону Docker.

```bash
bash scripts/build-index.sh     # один раз: скачать колёса в локальный индекс
docker compose up -d            # индекс и контейнер замера

bash scripts/run-install.sh     # установка: 3 инструмента x 3 состояния кэша
bash scripts/run-images.sh      # образы: 6 стратегий сборки
bash scripts/run-tests.sh       # тесты: 4 набора x 5 состояний кода
```

Образы собираются под `linux/amd64`, и колёса в индексе должны быть той же
платформы. На arm64-хосте (Mac на Apple Silicon) индекс колёс для
сценария образов собирают под неё явно — иначе в нём окажутся колёса
`aarch64`, и сборка образа упадёт на `pip install`:

```bash
DOCKER_DEFAULT_PLATFORM=linux/amd64 bash scripts/build-index.sh
```

Сценарию установки нужен индекс под платформу контейнера замера, поэтому
на таком хосте перед ним индекс пересобирают без этой переменной.

Каждый сценарий заканчивается разбором и **останавливается с кодом 2**,
если замер негоден. Разбор вызывается напрямую, без конвейера: `script |
tail` в этой серии дважды съедал код возврата, и отбитый прогон дважды
выглядел успешным.

Разборы можно запускать и отдельно по готовым фикстурам:

```bash
python scripts/analyze-install.py
python scripts/analyze-images.py
python scripts/analyze-tests.py
```

Предохранители самих разборов закрыты тестами:

```bash
python scripts/test_install_analysis.py
python scripts/test_images_analysis.py
python scripts/test_tests_analysis.py
python scripts/test_installed.py
```

Настройки прогонов — переменными окружения: `ROUNDS`, `SEED`,
`HYP_MAX_EXAMPLES`. Порог занятости машины в `scripts/preflight.sh` —
`MIN_IDLE`.

## Что лежит в фикстурах

```
fixtures/install.txt    162 измерения: инструмент, состояние, ПОЗИЦИЯ в
                        круге, время, размеры кэшей ДО прогона, число
                        пакетов и хеш набора; плюс строки плеча против
                        PyPI с пометкой reproducible: false
fixtures/images.txt     размеры всех трёх семей, слои, время старта,
                        проба байт-кода, проверка пересборки без кэша,
                        digest базовых образов, хранилище и DriverStatus
fixtures/tests.txt      матрица поимок, число примеров у hypothesis,
                        контрпримеры дословно, время и старты контейнера
```

Фикстуры — сырые записи прогонов, а не сведённые таблицы. Всё, что
напечатано выше, пересчитывается из них разборами.
