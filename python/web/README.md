# web

Стенд к серии «Python: backend, данные и ML»: во что обходится сам фреймворк,
когда эта цена перестаёт быть заметной, и что происходит при эксплуатации —
воркеры, корректное завершение, отказ на старте.

## Как обеспечено равенство условий

Это первое, что стоит проверить в любом сравнении фреймворков, поэтому оно
здесь первым разделом.

**Побайтовое равенство ответов — блокирующая проверка.** Пять целей отдают
одинаковые тела на шести случаях, включая отвергаемый ввод. Любое расхождение
останавливает замер. Без этого сравнивался бы объём работы, а не фреймворки:
она сразу поймала три расхождения умолчаний — Flask дописывал перевод строки
и экранировал не-ASCII, применял компактные разделители в `response()`, а не
в `dumps()`, а FastAPI отдавал подробный формат ошибки pydantic.

**Отклонения от умолчаний фреймворков и почему они сделаны.** У Django пустой
список middleware, ни одного установленного приложения, ORM не подключён.
Это НЕ «Django как его разворачивают» — это Django, приведённый к тому же
объёму работы, что у двух других. Его цифру надо читать именно так: цена
маршрутизации и сериализации, а не цена полноценного Django. У FastAPI
отключена автодокументация и ответ отдаётся `JSONResponse`, иначе он прошёл
бы через pydantic-сериализацию, которой нет у остальных. У Flask заменён
провайдер JSON: сортировка ключей, экранирование и перевод строки — его
умолчания, а сериализует по-прежнему он сам.

**Валидация выровнена по объёму, а не по реализации.** У FastAPI она
pydantic-овская — это его идиома и его цена, которую замер и должен показать.
У Flask и Django те же проверки вручную: набор полей закрыт, `id`
положительный, длина имени 1..64, не больше 16 строковых тегов. Формат ответа
на отвергнутый ввод общий: приводить ручные проверки к формату pydantic
значило бы навесить на них работу, которой у них нет.

**Контрольные плечи вместо сравнения через разные серверы.** FastAPI и Django
идут под uvicorn, Flask под gunicorn, и разницу серверов из результата не
вычесть. Поэтому в стенде есть голое ASGI- и голое WSGI-приложение с тем же
контрактом и той же валидацией: они дают пол, над которым цена фреймворка
читается как надбавка к своему серверу, а не как разница с чужим.

**Нагрузчик не является узким местом на том числе процессов, которым сняты
фикстуры.** Формулировка длинная намеренно: «где-то есть полка» и «полка
есть на рабочих четырёх процессах» — разные утверждения, и доказывать нужно
второе. `scripts/check-loader.sh` гоняет голую ASGI-цель нагрузчиком с 2, 4,
8 и 12 процессами, по три повтора на ступень, и требует, чтобы ни одна
ступень выше рабочей не давала прибавки больше 15%:

```
процессов  2: медиана 5287,2   повторы 5228 5287 5503
процессов  4: медиана 5495,3   повторы 5268 5495 5729  <- рабочее
процессов  8: медиана 5572,0   повторы 5487 5572 5582
процессов 12: медиана 5440,5   повторы 4532 5440 5548
прирост 4 -> 8: 1,01x, 4 -> 12: 0,99x
```

Проверка умеет отвечать «не состоялась»: если разброс повторов внутри
ступени выше 1,25x, вердикт не выносится вовсе — на неустойчивых числах
полку не доказать. В прогоне выше ступень на двенадцати процессах подошла
близко к этой границе (1,22x), остальные держались в пределах 1,09x.

Первая версия проверки была слабее вывода, который делала: она мерила
каждую ступень ОДИН раз, смотрела прирост только между двумя последними
ступенями и объявляла рабочим то число процессов, где случайно вышел
максимум. На серии 5117 / 3477 / 4049 / 4230 она отчиталась успехом и
выбрала два процесса, хотя фикстуры снимаются четырьмя, а от четырёх к
двенадцати там был рост 22%.

Забраковать работу проверка успела дважды: однопроцессный httpx давал 251
запрос в секунду против 852 у четырёх параллельных, многопроцессный httpx не
выходил на полку даже на четырнадцати ядрах. Порог при этом не трогался —
вместо этого написан узкий HTTP/1.1-клиент на asyncio (`bench/httpfast.py`).

**Цель и нагрузчик разведены по непересекающимся ядрам** (`bench/pin.py`):
иначе нагрузчик отбирает процессор у измеряемого, и пропускная способность
цели падает тем сильнее, чем сильнее её обстреливают.

## 1. Цена фреймворка и когда она перестаёт быть заметной

`fixtures/endpoints.txt`, 495 замеров, 11 кругов, порядок целей по латинскому
квадрату. Перед каждым плечом идёт двадцатисекундный разогрев, результат
которого отбрасывается. Три эндпоинта различаются объёмом полезной работы: `/ping` —
пустой ответ, `/echo` — разбор JSON с валидацией и сериализацией, `/wait` —
то же плюс ожидание 20 мс вместо похода в базу.

Пропускная способность при одновременности 64, rps:

| цель | /ping | /echo | /wait |
|---|---|---|---|
| raw-asgi | 5561,1 | 4785,2 | 2806,5 |
| fastapi | 4027,6 | 3233,8 | 2808,7 |
| django | 743,8 | 726,0 | 746,1 |
| raw-wsgi | 3592,0 | 3363,0 | **48,2** |
| flask | 2621,8 | 2318,3 | **47,9** |

Разложение — доля от СВОЕГО пола:

Медиана по 11 кругам и наблюдённый размах. Доля считается ПОКРУГОВО —
отношение цели к своему полу в каждом круге, и уже из этих отношений медиана
и размах. Отношение медиан дало бы другое число (74% против 72%): фреймворк
и его контроль меряются в одном круге, поэтому общее состояние машины из
парного отношения частично сокращается, а из отношения медиан нет. Печатает
эту таблицу `scripts/analyze-endpoints.py`, способ счёта закреплён в
`scripts/test_paired_shares.py`:

| фреймворк | /ping | /echo | /wait |
|---|---|---|---|
| fastapi | 74% (66–85) | 70% (61–76) | **102% (94–107)** |
| django | 14% (12–15) | 16% (13–18) | 27% (25–30) |
| flask | 71% (54–118) | 69% (56–74) | **99% (97–101)** |

**Главный вывод.** У FastAPI и Flask треть накладных расходов на пустой ручке
перестаёт измеряться, как только появляется поход в базу: 102% и 99% от
голого приложения на том же сервере, то есть от контроля они неотличимы.
Вопрос «какой фреймворк быстрее» поставлен неверно — разница тонет в
реальной работе, и это показано числами, а не заявлено.

**Разрешающая способность у стенда разная на разных ручках, и общей цифры
у неё нет.** На ручке с ожиданием размахи узкие (94–107% против 25–30%),
там кратное различие читается с запасом. На быстрых ручках доля гуляет
широко — у flask на /ping от 54% до 118%, и разброс самих абсолютных чисел
в этой клетке 1,71x у raw-wsgi, то есть анализатор её к ранжированию не
допускает вовсе. На пяти тысячах запросов в секунду замер начинает мерить
состояние машины; лечить это пробовали удлинением окна и двадцатисекундным
разогревом перед каждым плечом — у одних клеток разброс падал, у других
рос.

Рабочее правило: сравнивать плечи можно там, где РАЗМАХИ НЕ ПЕРЕСЕКАЮТСЯ, и
только на том масштабе, который переживает размах. «У Django накладные
расходы кратно больше» фикстуры выдерживают, «FastAPI на три процента
дороже Flask» — нет.

**Django — исключение и требует оговорки.** 14–15% от пола, впятеро хуже
соседей, при том что с него сняты middleware и ORM. Какая доля отставания
приходится на `Transfer-Encoding: chunked` — он единственный отдаёт ответы
так, — стенд не проверял. Это гипотеза, а не вывод.

**Разрыв в 58 раз на `/wait` — не про фреймворки.** WSGI с одним синхронным
воркером упирается в 48 запросов в секунду при любой одновременности, потому
что воркер занят всё время ожидания целиком. Это разница моделей, и ей
посвящён следующий раздел.

## 2. Воркеры: ответ зависит от типа нагрузки

`fixtures/workers.txt`, 240 замеров, 5 кругов, одновременность 64. Перед
каждой конфигурацией идёт двадцатисекундный разогрев, результат которого
отбрасывается: без него первые круги мерят машину на разгоне.

Ожидание 20 мс:

| способ | w=1 | w=8 | рост |
|---|---|---|---|
| `uvicorn --workers` | 2921,7 | 915,3 | **0,31x** |
| `gunicorn` + uvicorn-воркеры | 2927,1 | 2934,7 | 1,00x |
| `gunicorn` sync | 48,2 | 390,7 | **8,11x** |
| `gunicorn` gthread | 391,1 | 1849,9 | 4,73x ⚠️ |

⚠️ gthread на ручке с ожиданием НЕПРИГОДЕН для ранжирования: разброс по
кругам 1,85x при четырёх воркерах и 2,24x при восьми (877/1513/1519/1609/1625
и 1177/1574/1850/2462/2632) против 1,01–1,10x у остальных плеч. Множитель
роста из этих фикстур брать нельзя, качественный вывод «между синхронной и
асинхронной моделью» — можно.

Счёт 21 мс:

| способ | w=1 | w=8 | рост |
|---|---|---|---|
| `gunicorn` sync | 54,1 | 367,7 | **6,80x** |
| `gunicorn` gthread | 74,3 | 330,2 | 4,44x |
| `uvicorn --workers` | 53,5 | 289,6 | 5,41x |
| `gunicorn` + uvicorn-воркеры | 54,7 | 330,1 | 6,03x |

Пустая ручка (нужна как вторая точка для надбавки способа запуска):

| способ | w=1 | w=8 | рост |
|---|---|---|---|
| `gunicorn` + uvicorn-воркеры | 4274,4 | 27205,8 | 6,37x |
| `uvicorn --workers` | 4219,2 | 1283,6 | **0,30x** |
| `gunicorn` sync | 2744,7 | 12524,4 | 4,56x |
| `gunicorn` gthread | 1678,0 | 14357,3 | 8,56x |

**Синхронные воркеры совпали с формулой с точностью до процента**:
48,2/96,6/193,6/390,7 против потолка «воркеров ÷ задержка» 50/100/200/400.
Цена видна в задержке: p50 равен 329 мс, потому что 64 запроса стоят в
очереди к четырём воркерам.

**Асинхронной модели воркеры на ожидании не нужны** — 1,00x. Один цикл
событий уже держит 2927 rps.

**На счёте картина переворачивается**: воркеры нужны всем моделям, потому что
это процессы и они обходят GIL. Синхронные дают 6,80x при восьми воркерах —
согласуется с соседним стендом `python/concurrency`, где восемь процессов
дали 6,53x на счётной задаче.

**Аномалия `uvicorn --workers`.** При двух и более воркерах распределение
задержек получает ступень около 50 мс, и от числа воркеров она не зависит.
Точнее всего ступень видна на медиане: p50 равен ровно 50,00 мс на `/ping` и
ровно 70,00 на `/wait` при двух, четырёх и восьми воркерах. На p95 она
держится (50,3–50,5 и 70,2), а хвост сидит ещё десятью миллисекундами выше:
p99 около 60 и 80. Поэтому «добавляет каждому запросу ровно 50 мс» сказать
нельзя — это ступень распределения, а не одинаковая надбавка. При ОДНОМ воркере её нет: 4219 против 4274 rps, разница задержек
0,25 мс. Тот же FastAPI, те же четыре воркера под gunicorn с
uvicorn-воркерами дают 16905 rps против 1283 — в тринадцать раз больше на
пустой ручке и в три с четвертью на ручке с ожиданием. Без
второго плеча вывод звучал бы как «воркеры не помогают ASGI», что грубо
неверно: не помогает конкретный способ запуска. Оба плеча оставлены в стенде
намеренно.

Три клетки `gunicorn-gthread` разбор пометил непригодными для ранжирования
(разброс между кругами до 2,90x).

## 3. Корректное завершение: что именно оно защищает

`fixtures/shutdown.txt`, 30 замеров, 3 круга, одновременность 32.

Считается судьба запросов, **бывших в полёте** в момент сигнала. Начавшиеся
после сигнала потерями не считаются: сервер вправе их не принимать.

Контроль обязателен и идёт первым: каждый сервер гасится и `SIGTERM`, и
`SIGKILL`. При обрыве все пятеро теряют ровно 32 из 32 — значит потери в
принципе видны, и ноль у uvicorn настоящий.

| сервер | воркеров | в полёте | уцелело при SIGTERM |
|---|---|---|---|
| gunicorn | 1 | 32 | **1** |
| gunicorn | 2 | 32 | **2** |
| gunicorn | 4 | 32 | **4** |
| gunicorn | 8 | 32 | **8** |
| uvicorn | — | 32 | **32** |

**Что измерено буквально.** Замер видит происходящее глазами клиента: из 32
запросов, бывших в полёте, ответ получили ровно столько, сколько у сервера
воркеров, — на всех четырёх точках. Состояние очереди внутри ядра стенд не
наблюдает: для этого нужна инструментация на стороне сервера или сети, и её
здесь нет.

**Механизм, который это объясняет, остаётся гипотезой.** Воркер держит один
запрос; остальные соединения установлены, но их никто не взял, и дренажу с
ними делать нечего. Совпадение числа выживших с числом воркеров на всех
четырёх точках такое объяснение хорошо поддерживает, но клиентскими
наблюдениями его не доказать.

Отсюда осторожная формулировка вывода: на ЭТОЙ конфигурации «мы включили
graceful shutdown» у синхронной модели означало, что уцелело столько
запросов, сколько воркеров. Увеличение таймаута дренажа не помогло — время
завершения 0,26 с при 1, 2 и 4 воркерах и 0,36 при восьми, то есть упирались
не в него. Переносить это на произвольный сервер и произвольную нагрузку
стенд оснований не даёт.

У асинхронной модели `uvicorn` сохранил все 32 из 32. Объясняется это тем,
что цикл событий держит все принятые запросы одновременно, и дренировать есть
что, — но это объяснение, а не измеренный механизм.

Важнее оговорка про конфигурацию. Замер снят на `uvicorn` БЕЗ ограничений: не
заданы ни предел одновременных задач, ни предел соединений, ни свой таймаут
дренажа. Всё это настраивается и меняет картину: с ограничением
одновременности лишние соединения окажутся ровно в том же положении, что у
синхронной модели, а короткий таймаут оборвёт то, что не успело. Так что
«асинхронная модель дренирует всё» — вывод не про модель, а про эту
конфигурацию без лимитов.

## 4. Отказ на старте при неполной конфигурации

`fixtures/config.txt`, 24 замера, 3 круга. Два режима с ОДНОЙ И ТОЙ ЖЕ
проверкой, различается только момент вызова: при импорте или при обработке
запроса.

| режим | конфигурация | поднялся | /health | /work | код выхода |
|---|---|---|---|---|---|
| naive | корректная | да | 200 | 200 | — |
| naive | сломанная | **да** | **200** | 500 | — |
| strict | корректная | да | 200 | 200 | — |
| strict | сломанная | **НЕТ** | — | — | **78** |

**Главное не в том, что строгий режим падает раньше.** Наивный проходит
проверку здоровья, будучи нерабочим: она написана обычным образом и не
заглядывает в конфигурацию. Оркестратор считает такой экземпляр исправным,
переводит на него трафик и получает пятисотки.

Разница по времени мала — 0,20 с против 0,37 — и аргумент «строгая проверка
экономит время» здесь не работает. Разница в том, что́ система сообщает
наружу: отказ или ложную готовность.

## Запуск

```bash
docker compose up -d --build
```

Блокирующая проверка равенства ответов:

```bash
bash scripts/smoke.sh
```

Нагрузчик не должен быть узким местом на рабочих четырёх процессах
(возвращает 0 — полка, 1 — полки нет, 3 — вердикт невозможен из-за разброса):

```bash
bash scripts/check-loader.sh
```

Сценарии. Каждый начинается с `preflight.sh` и откажется мерить при беглых
серверах прошлого прогона, занятых портах или занятом процессоре:

```bash
ROUNDS=7 bash scripts/run-endpoints.sh
```

```bash
ROUNDS=5 bash scripts/run-workers.sh
```

```bash
ROUNDS=3 bash scripts/run-shutdown.sh
```

```bash
ROUNDS=3 bash scripts/run-config.sh
```

Разбор:

```bash
python scripts/analyze-endpoints.py
```

```bash
python scripts/analyze-shutdown.py
```

Ненулевой код возврата означает, что числам верить нельзя. У разбора
завершения код 3 отдельно означает, что контроль не сработал: обрыв не дал
потерь, и «ноль потерь при штатном завершении» ничего не доказывает.

Если прогон был прерван, серверы останутся жить. `preflight` намеренно
ОТКАЗЫВАЕТ в такой ситуации, а не подчищает молча: иначе факт, что прошлый
прогон не доработал, остался бы незамеченным вместе с его частичными данными
в фикстуре. Уборка — явное действие:

```bash
bash scripts/cleanup.sh
```

Остановка:

```bash
docker compose down
```

### Windows / Git Bash

Пути вида `/opt/...` превращаются в `C:/Program Files/...`, поэтому скрипты
сами выставляют `MSYS_NO_PATHCONV=1`. При ручных вызовах `docker compose exec`
делайте то же самое.

## Известные ограничения

- Числа сняты на WSL2 под Windows, 16 ядер. Абсолютные значения на нативном
  Linux будут другими; соотношения устойчивее абсолютных величин.
- Django приведён к общему объёму работы (без middleware и ORM), поэтому его
  число НЕ характеризует Django как его обычно разворачивают.
- Доля отставания Django, приходящаяся на chunked-кодирование, не измерена.
- Накладные расходы OpenTelemetry и структурного логирования стенд не меряет.
- Плечо `gunicorn-gthread` неустойчиво в трёх клетках из восьми, по ним
  сравнивать нельзя.
- Таймаут принудительного завершения не измерялся: эндпоинт `/slow` в
  приложениях есть, отдельного плеча под него в сценарии нет.
