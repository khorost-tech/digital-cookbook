# Типизация и данные в Python: два счётных вопроса

Стенд к двум статьям:

* [Современный Python: type hints, mypy, pydantic и pattern
  matching](https://khorost.tech/python/python-modern-typing/) — кто ловит
  дефект и чего не видит никто;
* [Данные и ML в проде на Python](https://khorost.tech/python/python-data-ml-in-production/)
  — кто не полез в данные, которые ответу не нужны.

## Чего в этом стенде нет: времени

Ни одна его величина не измеряется секундами. Это не упущение и не
экономия — это устройство.

Соседние стенды серии (`python/concurrency`, `python/web`,
`python/data-access`, `python/tooling`) меряют время, и на методику
временных величин там ушло больше сил, чем на всё остальное: ротации,
контрбалансировка, знаковые тесты, отбрасываемые круги, разбор эффекта
позиции. Всё это нужно потому, что время зависит от машины, соседей по
процессору и того, что происходило минуту назад.

Здесь величины другие:

```
поймал или нет      целое да/нет по коду возврата
дошёл до ответа     целое да/нет
совпал ли ответ     хеш
```

Такие числа переживают перезамер на другой машине и не требуют ни
прогревов, ни ротаций. Цена — стенд не говорит ничего о скорости, и там,
где это важно, сказано прямо.

Версии пинованы и печатаются из самих пакетов: Python 3.14.7, mypy 2.3.1,
pyright 1.1.413, pydantic 2.13.4, pandas 3.0.5, polars 1.44.0,
pyarrow 25.0.1.

## Сценарий 1: кто ловит подсунутый дефект

Один модуль с правилом расчёта заказа, пять проверяющих, шесть состояний
кода.

```
состояние кода        mypy mypy --strict  pyright  pydantic  выполнение
none                  зел.         зел.     зел.      зел.        зел.
wrong-return        поймал       поймал   поймал       нет      поймал
untyped-body           нет       поймал   поймал       нет         нет
optional-unchecked  поймал       поймал   поймал       нет         нет
external-data          нет          нет      нет    поймал         нет
runtime-only           нет          нет      нет       нет      поймал
```

Читать таблицу стоит как карту слепых зон, а не как турнирную таблицу.
Каждое плечо ловит хотя бы один дефект, каждый дефект пойман хотя бы одним
— это условия годности замера, и вердикт их проверяет.

**Дефект — правка исходника, а не флаг в коде.** Статические анализаторы
читают файл, а не выполняют его: ветка `if os.environ[...]` не переключила
бы состояние, mypy увидел бы сразу все варианты и пожаловался на все.
Правка применяется к копии, и каждая замена обязана найтись ровно один
раз.

**Все пять плеч видят один файл, и это доказано.** Хеш исходников
снимается до первого плеча и после последнего; расхождение означало бы,
что проверяющий переписал код под собой. У шести состояний шесть разных
хешей — значит правка каждый раз применилась.

**Расхождение с замыслом блокирует замер.** Стенд объявляет в
`app/defects.py`, кто какой дефект обязан поймать. Молчаливо подстроить
ожидание под наблюдение значило бы превратить проверку в зеркало: она
стала бы подтверждать любые данные.

Одно ожидание замер уже поправил. `wrong-return` я считал чисто
статическим — тип объявлен `Decimal`, возвращается `float`. Выполнение
падает следом: `subtotal` складывает результат с `Decimal`, а
`Decimal + float` в Python запрещён.

### Что стоит за строками

**`untyped-body` — обычный mypy молчит, строгий видит и саму ошибку.**
Полный вывод строгого mypy (поле `output` в `fixtures/typing.txt`):

```
orders.py:47: error: Function is missing a type annotation  [no-untyped-def]
orders.py:54: error: Unsupported operand types for + ("str" and "int")  [operator]
Found 2 errors in 1 file (checked 1 source file)
```

pyright на том же дефекте сообщает ту же ошибку, без требования аннотации:

```
/work/orders.py:54:12 - error: Operator "+" not supported for types "Literal['строк: ']" and "int" (reportOperatorIssue)
```

`--strict` включает `--check-untyped-defs`: тело функции без аннотаций
проверяется, и ошибку сложения строгий mypy находит так же, как pyright, —
плюс требует аннотацию. Обычный mypy тела нетипизированных функций не
проверяет вовсе и молчит. (Раньше фикстура хранила только первую строку
диагностики, и по ней строгий mypy выглядел «отказавшимся проверять»;
теперь сохраняется полный вывод.)

**`optional-unchecked` видят только статические.** В данных стенда скидка
задана у всех заказов, поэтому путь с `None` выполнение просто не
проходит. Тип допускает `None`, данные его пока не содержат — и это
типичная ситуация, а не подстроенная.

**`external-data` видит только граница.** Поле объявлено `bool`,
аннотация верна, а в JSON лежит строка `"false"`. Статический анализ
проверяет код, а не данные; выполнение получает истинное значение из
непустой строки и считает дальше — итог выходит правдоподобным, но
неверным. Проверки инвариантов такое не ловят: они ловят нарушенное
правило, а не правдоподобно неверное число.

**`runtime-only` не видит никто, кроме выполнения.** Скидка больше суммы,
итог уходит в минус. Типы в порядке, данные в порядке.

### Про строгость pydantic

Строгость включена там, где тип в JSON однозначен (`int`, `str`, `bool`), и
снята для `Decimal`: десятичного типа в JSON нет, деньги передают строкой
именно поэтому.

Первая версия включала строгость сплошь и отвергала `"240.00"` — то есть
браковала корректные данные. Контроль это поймал сразу: на исправном
наборе плечо обязано быть зелёным, а оно краснело.

## Сценарий 2: кто не полез в лишние данные

Один вопрос к разбитому на разделы набору Parquet, пять способов его
задать.

```
плечо            всё доступно   лишнее закрыто   что делает
pandas-full             дошёл  отказ в доступе   прочитать всё, отобрать в памяти
pandas-columns          дошёл  отказ в доступе   названы столбцы, разделы — нет
pandas-filters          дошёл            дошёл   отбор передан читателю файлов
polars-eager            дошёл  отказ в доступе   прочитать всё, отобрать в памяти
polars-lazy             дошёл            дошёл   план строится целиком
```

Набор: 200 000 строк, 20 разделов, хеш `dd606381bdd3474a`; запрос берёт
разделы до пятого.

### Почему доказательство, а не измерение

Первая версия сценария мерила прочитанное в байтах через `/proc/self/io`.
Величина оказалась несопоставимой между движками:

```
pandas-full     3 181 377 Б
polars-eager       23 280 Б
```

Два порядка на одной и той же работе — потому что polars **отображает файл
в память**, а счётчик считает только системные вызовы чтения. Числа
настоящие, означают у двух плеч разное, и опубликовать их как сравнение
было бы неправдой.

Обойти не вышло: у `scan_parquet` нет параметра отключения отображения, а
подсунуть свой считающий файловый объект — значит лишить polars проброса,
то есть сломать ровно то, что измеряется.

Поэтому мера сменилась на «а можно ли было прочитать». Разделы, которые
запрос обязан отбросить, делаются **нечитаемыми**. Дошедшее до ответа
плечо тем самым доказало, что в них не заглядывало. Это устроено
одинаково для обоих движков и не зависит ни от способа чтения, ни от
страничного кэша.

### Что пришлось поправить по ходу

**Отбор перевёрнут на ранние разделы.** Сперва закрывались ранние, и
падали все пять плеч, включая умеющие отбрасывать: схему набора движок
выводит по первому найденному файлу, до всякого отбора, и первым
оказывался закрытый раздел. Это не изъян движков, а свойство любого набора
без объявленной схемы.

**Плечи выполняются от непривилегированного пользователя.** Для root права
доступа не действуют — замер под ним показал бы, что справляются все.

**Совпадение ответа проверяется отдельно, и это главная проверка.** Плечо,
отбросившее лишнее вместе с нужным, выглядит как самый расторопный
участник: дошёл там, где другие упали. Без сверки хеша это прошло бы за
успех.

### Границы вывода

Измерено, ЧИТАЛ ли движок лишнее, а не сколько времени он потратил. Плечо,
не полезшее в закрытые разделы, не обязано быть быстрее — оно именно что не
сделало работу. Про скорость этот стенд не говорит ничего.

Набор данных порождается арифметикой без случайности и в репозитории не
хранится: он воспроизводится побайтово, а его хеш записан в фикстуру как
часть условий.

## Как запустить

```bash
bash scripts/run-typing.sh    # матрица: кто ловит дефект
bash scripts/run-data.sh      # чтение: кто не полез в лишнее
```

Каждый сценарий заканчивается разбором и **останавливается с кодом 2**,
если замер негоден. Разбор вызывается напрямую, без конвейера: `script |
tail` в этой серии дважды съедал код возврата.

Разборы можно запускать отдельно по готовым фикстурам:

```bash
python scripts/analyze-typing.py
python scripts/analyze-data.py
```

Предохранители самих разборов закрыты тестами:

```bash
python scripts/test_typing_analysis.py
python scripts/test_data_analysis.py
python scripts/test_readme_matches_fixtures.py
```

## Что лежит в фикстурах

```
fixtures/typing.txt   6 состояний кода: исход каждого из пяти плеч,
                      выдержка из вывода, полный вывод (output) и хеш
                      исходников до и после
fixtures/data.txt     2 состояния набора по 5 плеч: дошло ли плечо до
                      ответа, хеш ответа, вид ошибки, закрытые разделы;
                      плюс строка условий с версиями и хешем набора
```

Фикстуры — сырые записи прогонов, а не сведённые таблицы. Всё, что
напечатано выше, пересчитывается из них разборами.
