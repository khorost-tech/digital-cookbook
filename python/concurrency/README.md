# concurrency

Стенд к серии «Python: backend, данные и ML»: где GIL действительно связывает
выполнение, что даёт сборка без него и чем за неё платят.

## Что показывает стенд

Одна и та же нагрузка прогоняется в трёх моделях исполнения — asyncio, потоки,
процессы — на двух интерпретаторах одной версии: обычном и free-threaded
(PEP 703). Это разделяет два вопроса, которые обычно путают: «какая модель
подходит задаче» и «мешает ли GIL».

Все числа ниже — медианы кругов из фикстур в `fixtures/`. Порядок моделей
внутри круга задаёт латинский квадрат: при фиксированном порядке первая
модель систематически получает более холодную машину, и повторами это
смещение не убирается.

### 1. Счётная нагрузка: где GIL связывает

Рост пропускной способности при переходе от 1 к 8 воркерам
(`fixtures/cpu-gil.txt`, `fixtures/cpu-nogil.txt`):

| модель | сборка с GIL | сборка без GIL |
|---|---|---|
| asyncio | 212,2 → 208,9 ops/s (0,98x) | 196,5 → 201,4 ops/s (1,02x) |
| threads | 190,9 → 213,3 ops/s (**1,12x**) | 201,1 → 1359,3 ops/s (**6,76x**) |
| processes | 187,0 → 1220,6 ops/s (6,53x) | 201,2 → 1265,2 ops/s (6,29x) |

Под GIL потоки на счётной задаче не дают почти ничего, процессы дают 6,5x.
Free-threading переводит потоки в лигу процессов. asyncio не масштабируется
ни на одной сборке: цикл событий однопоточен, и отсутствие GIL этого не меняет.

Задача намеренно написана на чистом Python-байткоде. Библиотечные функции
(`math`, `hashlib`, `zlib`) не годятся: многие отпускают GIL, и замер показал
бы поведение библиотеки, а не границу GIL. Проверка встроена в разбор: если
под GIL потоки дадут заметный рост, `analyze-cpu.py` объявит замер негодным.

Под GIL пропускная способность не растёт никогда, но проявляется это
по-разному в зависимости от того, как длина задачи соотносится с интервалом
переключения GIL (5 мс по умолчанию). Фикстуры `cpu-slow-*.txt`, задача
примерно 50 мс, 3 круга:

| плечо | p50 при 1 воркере | p50 при 8 | рост p50 | рост ops/s |
|---|---|---|---|---|
| gil/threads, задача ~50 мс | 50,1 мс | **354,6 мс** | 7,1x | 1,06x |
| gil/threads, задача ~5 мс | 5,14 мс | 10,02 мс | 1,9x | 1,12x |
| nogil/threads, задача ~50 мс | 48,4 мс | 57,0 мс | 1,2x | **6,70x** |

Длинная задача под GIL растягивается почти пропорционально числу потоков:
восемь потоков — семикратная задержка при той же пропускной способности.
Короткая успевает завершиться за один-два кванта, и рост задержки почти не
виден. Наивная формулировка «восемь потоков делят GIL, значит операция идёт
в восемь раз дольше» верна лишь для задач длиннее кванта.

### 2. Цена free-threading

Изолирует её ТОЛЬКО плечо asyncio, и это не мелочь. `probe_threads.py`
показывает, что при `workers=1` в родительском процессе живёт 1 поток у
asyncio, 2 у потоков и 3 у процессов. У двух моделей из трёх сборка с GIL
платит за его передачу между потоками уже при одном воркере, и их отношение
смешивает два разных эффекта с разными знаками.

`fixtures/cpu-cost-gil.txt`, `fixtures/cpu-cost-nogil.txt`, 15 кругов:

| плечо | gil | nogil | отношение | p |
|---|---|---|---|---|
| asyncio (1 поток) | 210,5 ops/s | 201,5 ops/s | **0,957x** | 0,0005 |
| processes (3 потока) | 189,2 | 201,2 | 1,063x | 0,0013 |
| threads (2 потока) | 197,8 | 202,7 | 1,025x | 0,0459 |

Цена интерпретатора — строка asyncio: около 4% на этих замерах. Числу не стоит
доверять до десятых: предыдущая серия в менее чистой среде дала 7%. Между
сессиями разброс больше, чем внутри, поэтому честная величина — **порядка
4–7%**, того же порядка, что заявленные разработчиками ~10%.

Внутрисборочное сравнение, где цена интерпретатора сокращается, согласуется с
гипотезой о передаче GIL: плечо потоков при одном воркере медленнее asyncio на
6,0% под GIL (p=0,006) и не медленнее без него (p=0,35). Но цену передачи GIL
оно не изолирует: между asyncio и `ThreadPoolExecutor` меняются ещё
диспетчеризация, очереди, `Future` и сбор результатов, а у процессов счёт идёт
вне родительского GIL. Для подтверждения нужен контроль, меняющий только число
потоков, — его в стенде нет.

### 2b. Вынос счёта из цикла событий: в потоки или в процессы

Совет «унеси счёт из цикла событий в `run_in_executor`» верен, но исполнитель
выбирается по сборке. Оба плеча меряются СИММЕТРИЧНО — одна работа, одна
обвязка asyncio, различается только класс пула. `fixtures/executor-*.txt`,
400 операций, 5 кругов:

| воркеров | gil / потоки | gil / процессы | nogil / потоки | nogil / процессы |
|---|---|---|---|---|
| 1 | 200,3 | 188,9 | 188,2 | 192,0 |
| 2 | 202,4 | 358,7 | 387,2 | 377,9 |
| 4 | 199,7 | 668,7 | 718,0 | 725,5 |
| 8 | **201,1** | **1067,6** | **1221,7** | **1214,5** |

На обычной сборке процессы дают 5,3x против потоков. На free-threaded оба
исполнителя равны по пропускной способности (1221,7 против 1214,5, различие в
пределах разброса) — выбирать надо по другим свойствам, а не по скорости.

Про расход ресурсов этот замер не отвечает: для этого есть отдельный
сценарий `run-footprint.sh`.

### 2c. Чего стоит одновременность: память и дескрипторы

`fixtures/footprint-*.txt`, 64 одновременных ожидания по 20 мс, 3 круга.
Каждое плечо живёт в собственном процессе интерпретатора.

Память считается по **PSS** (`/proc/<pid>/smaps_rollup`), а не по сумме RSS:
сумма RSS учитывает общие страницы заново в каждом процессе. Рядом печатается
и она — разрыв показывает масштаб двойного учёта, — плюс память cgroup как
независимая перекрёстная проверка.

| модель | PSS (gil) | сумма RSS | завыш. | cgroup | дескр. | проц. |
|---|---|---|---|---|---|---|
| asyncio | 22,9 МБ | 23,9 | 1,04x | 38,6 | 7 | 1 |
| threads | 48,1 МБ | 49,1 | 1,02x | 66,0 | 7 | 1 |
| processes | **340,3 МБ** | **1329,8** | **3,91x** | 366,8 | **988** | **67** |

| модель | PSS (nogil) | сумма RSS | завыш. | cgroup | дескр. | проц. |
|---|---|---|---|---|---|---|
| asyncio | 37,8 МБ | 38,8 | 1,03x | 69,0 | 7 | 1 |
| threads | 320,2 МБ | 321,2 | 1,00x | 354,4 | 7 | 1 |
| processes | **517,4 МБ** | **2195,1** | **4,24x** | 564,7 | **988** | **67** |

Разброс между кругами 1,00–1,04x, поэтому ранжировать можно всё:

- процессы против потоков на обычной сборке — **7,1x** по памяти и 988
  дескрипторов против семи;
- asyncio легче потоков в 2,1 раза на обычной сборке и в 8,5 на free-threaded;
- 64 потока стоят **6,7x** больше памяти на free-threaded (48,1 против
  320,2 МБ). Заявленные 15–20% относятся к интерпретатору, а не к цене
  потока. Настолько, что на free-threaded разрыв потоков с процессами почти
  исчезает: 320,2 против 517,4 МБ.

Колонка «завыш.» — это цена наивной метрики: на плече процессов сумма RSS
завышает результат почти вчетверо, и cgroup подтверждает, что права PSS.
`analyze-footprint.py` отвергает замер, если cgroup и PSS расходятся более
чем вдвое.

Это обещание проверяется тестом, а не остаётся словами: предохранитель уже
один раз оказался мёртвым — он взводился, но печать и код возврата стояли
выше по коду, и разбор всё равно завершался нулём. Поэтому
`scripts/test_analyze_footprint.py` строит синтетические фикстуры под каждый
предохранитель и требует конкретного кода возврата:

```bash
python scripts/test_analyze_footprint.py
```

| случай | код |
|---|---|
| чистый набор | 0 |
| плечо стартовало не в одиночестве | 2 |
| фикстура старого формата, без PSS | 2 |
| cgroup и PSS расходятся более чем вдвое | 3 |
| направление расхождения профайлеров непостоянно | 4 |

ПОЧЕМУ ПЛЕЧИ ИЗОЛИРОВАНЫ. Первая версия мерила три модели в одном
интерпретаторе подряд: `ProcessPoolExecutor` поднимает forkserver, который
переживает закрытие пула, а наблюдатель суммировал все процессы python. В
фикстуре это выглядело как «разброс» потоков 46,3 -> 84,8 МБ и трактовалось
как шум, хотя было систематической ступенькой. Теперь каждое плечо печатает
`baseline_procs`, и разбор отвергает фикстуру, где хоть одно стартовало не в
одиночестве.

### 3. Ожидание: где GIL ни при чём

Доля от теоретического потолка «одновременность / задержка»
(`fixtures/io-gil.txt`, `fixtures/io-nogil.txt`, задержка 20 мс). Слева сборка
с GIL, справа без него:

| модель | w=1 | w=8 | w=64 | w=256 |
|---|---|---|---|---|
| asyncio | 99% / 100% | 99% / 99% | 93% / 94% | 84% / 88% |
| threads | 99% / 100% | 99% / 99% | 95% / 96% | 65% / 50% |
| processes | 99% / 99% | 98% / 99% | 64% / 75% | не запускается |

На ожидании GIL не узкое место: до 64 одновременных операций все три модели
держат 93–100% потолка на обеих сборках. Расходятся они выше, и первым
отваливается плечо процессов.

Числа при 256 потоках сравнивать НЕЛЬЗЯ, и разбор помечает это сам. Прицельная
проверка на 15 кругов (`fixtures/io-hi-*.txt`) показала, что в этой точке
пропускная способность гуляет более чем вдвое (4238…9190 ops/s), а различие
сборок неразличимо (p=0,15). По трём кругам оттуда получалось, будто
free-threading хуже — это был шум.

Плечо процессов при 256 воркерах не запускалось намеренно (`PROC_MAX=64`):
число воркеров равно числу процессов ОС, и в расчёте на то, что 256 процессов
мерили бы скорее исчерпание памяти, чем модель, их не запускали. Это
ограничение стенда, а не измеренный отказ.
Каждый пропуск отмечен в фикстуре отдельной строкой, а не выпадает молча.

### 4. Профилирование: почему два инструмента дают разное

`fixtures/profile.txt`, 7 кругов. Нагрузка построена как ловушка для
детерминированного профайлера: две функции сопоставимой суммарной
длительности, но `tiny_step` вызывается 6 000 000 раз, а `chunky_step` 3000.

Цена самого инструмента:

| режим | медиана | к прогону без профайлера |
|---|---|---|
| без профайлера | 3,628 с | 1,00x |
| cProfile | 4,671 с | **1,29x** |
| py-spy | 3,727 с | 1,03x |

Картины на одной и той же нагрузке:

| функция | вызовов | cProfile | py-spy |
|---|---|---|---|
| tiny_step | 6 000 000 | 18,2% | 15,2% |
| chunky_step | 3 000 | 64,2% | 77,7% |

Направление постоянно во всех 7 кругах из 7, а вот множитель называть нельзя:
у `tiny_step` он гуляет 1,07…1,37. Разброс идёт от шума сэмплирования — у
cProfile доли стабильны (18,0…18,5%), а py-spy на меньшей доле имеет
пропорционально меньше сэмплов.

Эталонной доли здесь не существует: измерить «истинную» долю функции можно
только ещё каким-нибудь профайлером. Поэтому корректная формулировка —
«инструменты расходятся», а не «cProfile ошибается».

### 5. Сколько даёт устранение вызова

Детерминированный профайлер завышает долю мелкой частой функции, и отсюда
типичный совет «убрать вызов». `fixtures/inline.txt`, 7 кругов, порядок
вариантов сдвигается каждый круг:

| вариант | медиана | к варианту с вызовом |
|---|---|---|
| вызов функции | 0,084 с | 1,00x |
| тело прямо в цикле | 0,073 с | **1,15x** |
| весь цикл одним вызовом | 0,070 с | 1,20x |

Контрольные суммы всех трёх вариантов совпадают: сравнивается скорость, а не
объём работы.

Оговорка, без которой число вводит в заблуждение: замер сделан на цикле,
состоящем ТОЛЬКО из вызовов мелкой функции. В реальной нагрузке доля такого
цикла меньше, и выигрыш разбавляется пропорционально. Долю из профиля и этот
множитель перемножать нельзя.

### 6. Какие права нужны py-spy

`fixtures/pyspy-perms.txt`, сценарий `scripts/check-pyspy-perms.sh`. Три
случая прогоняются БЕЗ `CAP_SYS_PTRACE` и с ней:

| сценарий | без возможности | с возможностью |
|---|---|---|
| root, py-spy сам запускает цель | работает | работает |
| root присоединяется к соседнему процессу root | работает | работает |
| `nobody` присоединяется к процессу root | Permission Denied | **Permission Denied** |

Возможность на контейнере не помогает, когда профайлер запущен от другого
пользователя: она выдана root'у контейнера, а не `nobody`.

ВАЖНО про воспроизводимость: результат зависит от ядра хоста. Здесь модуль
Yama не включён (`/proc/sys/kernel/yama/ptrace_scope` отсутствует), и сценарий
печатает это в шапке фикстуры. На ядре с `ptrace_scope=1` — умолчание многих
дистрибутивов — вторая строка должна измениться, но проверить это на текущем
ядре нельзя, и стенд такого утверждения не делает.

Поэтому `cap_add: SYS_PTRACE` в compose оставлен: в нашей конфигурации он не
понадобился, но снимать его значило бы сломать стенд там, где Yama включён.

## Запуск

```bash
docker compose up -d --build
```

```bash
bash scripts/smoke.sh
```

`smoke.sh` проверяет, что в образе действительно два РАЗНЫХ интерпретатора:
обычный сообщает о включённом GIL, free-threaded о выключенном, и версии у них
совпадают. Третья проверка нужна, чтобы замер не сравнил разные версии Python
вместо модели памяти.

Сценарии. Каждый начинается с `preflight.sh` и откажется мерить на занятой
машине или при беглых процессах от прошлого прогона:

```bash
bash scripts/run-cpu.sh
```

```bash
TAG="-cost" WORKERS="1" ROUNDS=15 bash scripts/run-cpu.sh
```

```bash
bash scripts/run-io.sh
```

```bash
bash scripts/run-profile.sh
```

Матрица CPU и сценарий ожидания идут примерно по десять минут каждый.

Разбор. Каждый скрипт сначала проверяет признаки негодного замера и только
потом печатает выводы; ненулевой код возврата означает, что числам верить
нельзя:

```bash
python scripts/analyze-cpu.py
```

```bash
python scripts/analyze-cost.py
```

```bash
python scripts/analyze-io.py
```

```bash
python scripts/analyze-profile.py
```

Остановка:

```bash
docker compose down
```

### Windows / Git Bash

Пути вида `/opt/...` превращаются в `C:/Program Files/...`, поэтому скрипты
сами выставляют `MSYS_NO_PATHCONV=1`. При ручных вызовах `docker compose exec`
делайте то же самое.

| CPython free-threaded | 3.14.7, `sys._is_gil_enabled()` = False |
| uv | 0.12.5 |
| py-spy | 0.4.2 |
| pytest | 9.1.1 |
| образ | Debian GNU/Linux 12 (bookworm) |
| ядро | Linux 5.15.167.4-microsoft-standard-WSL2 |
| ядер в контейнере | 16 |
| стартовый метод multiprocessing | forkserver |

Официальных docker-тегов free-threaded сборок не существует, оба интерпретатора
ставит `uv`. `forkserver` — умолчание Python 3.14 на Linux, а не `fork`; это
влияет на цену старта процессов.

## Известные ограничения

- Числа сняты на WSL2 под Windows. На нативном Linux абсолютные значения будут
  другими; соотношения между моделями устойчивее абсолютных величин.
- Цена free-threading измерена как разница между сборками на однопоточном
  плече. Расход памяти (заявленные +15–20%) стенд не измеряет.
- Плечо процессов не поднимается выше `PROC_MAX=64` воркеров.
- Нативные расширения и их взаимодействие с free-threading вне охвата.
  Загруженное C-расширение без поддержки free-threading включает GIL обратно;
  `run.py` отвергает такое плечо, но своего расширения стенд не собирает.
- py-spy требует `cap_add: SYS_PTRACE`; там, где эта возможность запрещена,
  сценарий профилирования не пойдёт.
- `init: true` в compose обязателен: без него PID 1 — это `sleep infinity`,
  который не вызывает `wait()`, и осиротевшие воркеры пула процессов остаются
  зомби навсегда (за один прогон матрицы их набегало 48).
