# Доступ к данным из Python: сколько стоит каждый слой

Стенд к статье [Данные в Python: SQLAlchemy 2.0, asyncpg и миграции через
Alembic](https://khorost.tech/python/python-data-access-sqlalchemy/).

Отвечает на четыре вопроса, и первый из них — не тот, с которого обычно
начинают:

1. Сколько стоит слой доступа и **когда эта цена перестаёт существовать**.
2. Во что обходится N+1 — в запросах, а не в миллисекундах.
3. Что происходит с ленивой загрузкой в асинхронной сессии.
4. Что видит автогенерация Alembic и **возвращает ли откат схему назад**.

Версии пиновани и печатаются из самих пакетов: PostgreSQL 18.4,
Python 3.14.7, SQLAlchemy 2.0.52, asyncpg 0.31.0, psycopg 3.3.4,
Alembic 1.19.1.

## Как обеспечена сопоставимость

**Пять плеч, и каждое сравнение меняет ровно одно.** Напрашивающийся набор
из четырёх — сырой драйвер, Core, ORM async, ORM sync — смешал бы две
переменные: синхронное плечо пришлось бы вести на psycopg, потому что у
asyncpg синхронного интерфейса нет, и разница «синхронный против
асинхронного» стала бы неотделима от разницы драйверов.

```
raw-asyncpg  ->  core-asyncpg  ->  orm-asyncpg     слой, драйвер тот же
orm-asyncpg  ->  orm-psycopg-async                 драйвер, слой тот же
orm-psycopg-async -> orm-psycopg-sync              модель, всё прочее то же
```

**Равенство результата проверяется, а не предполагается.** Пять плеч обязаны
отдать побайтово одинаковый сериализованный результат; проверка блокирует
замер. Она сразу поймала настоящее расхождение: в SQLAlchemy 2.0 три способа
поделить на сто дают три разных SQL.

```
pages / 100          ->  books.pages / CAST(100 AS NUMERIC)   истинное деление
pages // 100         ->  books.pages / %(pages_1)s            со связанным параметром
pages.op("/")(100)   ->  books.pages / 100                    как в сыром SQL
```

Оператор `/` переносит в SQL семантику Python, где деление истинное, тогда
как в сыром SQL на целых операндах оно целочисленное. Плечи считали разные
величины при одинаковом на вид коде.

**Набор данных неизменен, и это сверяется.** Посев детерминированный, хеш
считается по содержимому и читается ИЗ БАЗЫ — иначе проверялась бы
детерминированность генератора, а не состояние базы. Сверка ловит подмену
одного значения при неизменном числе строк.

**Плечо поднимается один раз на всю пачку.** Первая версия измерителя
открывала соединение на каждую итерацию и выдавала 23 мс на запрос одной
строки при 0,015 мс работы сервера. Плечо-двойник с переподключением на
итерацию даёт 131x к длительности — на таком фоне разница между слоями не
проявилась бы вовсе.

**Ротация двойная, а порядок контролируемой пары ещё и контрбалансирован.**
Порядок плеч внутри круга — латинский квадрат; порядок запросов внутри
плеча ротируется так же, со смещением от номера плеча.

Одной ротации оказалось мало, и это выяснилось не сразу. Циклический сдвиг
балансирует ПОЗИЦИИ, но не относительный порядок пары: `heavy-rows` стоит в
списке третьим, `heavy-entities` четвёртым, и лишь один сдвиг из пяти
меняет их местами — за одиннадцать кругов выходило 9:2. Для контролируемой
пары это почти то же самое, что не ротировать вовсе.

Поэтому относительный порядок пары задаётся явно и чередуется по кругам. В
снятой фикстуре получилось 5:6 или 6:5 у каждого плеча — и это проверяется
по самому файлу, а не по коду.

Прочее перенесено из стенда `python/web`, где каждое появилось после
осечки: разогрев и проба по времени, размер пачки от измеренной скорости,
окно по размаху самих итераций, хеш результата в каждой строке фикстуры.

## Карта разрешения: где цену слоя измерять можно

Главный риск этой волны — что время сервера заглушает цену слоя. Поэтому
стенд знает свою разрешающую способность и печатает её:
`scripts/check-db-share.sh`.

| запрос | клиент, мс | сервер, мс | доля сервера |
|---|---|---|---|
| one-row | 0,1795 | 0,0076 | 4% |
| many-rows | 19,3620 | 3,4124 | 18% |
| heavy-sql | 14,9386 | 14,5919 | **98%** |
| heavy-rows | 13,7112 | 12,4225 | **91%** |
| heavy-entities | 12,9950 | 11,7882 | **91%** |

Все три тяжёлых запроса для измерения самой цены слоя в лоб непригодны и
остаются в наборе намеренно: они показывают, ЧТО происходит с этой ценой,
когда работает база.

`heavy-rows` и `heavy-entities` — это ОДИН И ТОТ ЖЕ SQL под двумя именами.
Сервер выполняет одинаковую работу (91% и 90% времени), а различается
только то, строит ли ORM объекты или отдаёт отображения строк. Эта пара и
есть единственное в стенде контролируемое сравнение для цены
материализации: в ней меняется ровно одно.

`heavy-sql` остаётся как случай, где материализовать нечего вовсе: агрегат
не ложится на сущность, и ORM-плечи выполняют там выражение Core.
Сравнивать его с `heavy-entities` как «тот же запрос, только с объектами»
НЕЛЬЗЯ — это разные запросы, с разной группировкой и разным временем
сервера.

## 1. Цена слоя и когда она исчезает

`fixtures/layers.txt`, 275 замеров, 11 кругов.

Время одной операции, медиана по кругам, мс:

| плечо | one-row | many-rows | heavy-sql | heavy-rows | heavy-entities |
|---|---|---|---|---|---|
| raw-asyncpg | 0,1726 | 17,8295 | 14,8046 | 12,9102 | 12,9355 |
| core-asyncpg | 0,2621 | 23,4512 | 15,0495 | 13,8829 | 13,3063 |
| orm-asyncpg | 0,8183 | 67,8341 | 16,1230 | 14,8983 | 17,1368 |
| orm-psycopg-async | 0,9593 | 60,4835 | 16,5829 | 14,6888 | 17,5709 |
| orm-psycopg-sync | 0,7074 | 59,3863 | 15,9867 | 14,6858 | 16,8310 |

Доля от сырого драйвера — покругово, медиана и наблюдённый размах:

| плечо | one-row | many-rows | heavy-sql | heavy-rows | heavy-entities |
|---|---|---|---|---|---|
| core-asyncpg | 1,53x (1,46–1,74) | 1,30x (1,07–1,52) | 1,02x (0,99–1,15) | 1,09x (1,00–1,22) | 1,06x (0,91–1,32) |
| orm-asyncpg | 4,75x (4,55–5,11) | 3,73x (3,38–4,10) | 1,09x (1,03–1,34) | 1,17x (1,07–1,45) | **1,37x (1,16–1,55)** |
| orm-psycopg-async | 5,54x (5,20–5,90) | 3,41x (2,78–3,93) | 1,11x (1,03–1,19) | 1,14x (1,07–1,31) | **1,34x (1,17–1,60)** |
| orm-psycopg-sync | 4,12x (3,91–4,24) | 3,25x (2,93–3,85) | 1,11x (1,00–1,15) | 1,14x (1,05–1,27) | **1,28x (1,13–1,50)** |

Непригодных для ранжирования клеток в этом прогоне нет: разброс нигде не
превысил 1,5x.

### Цена материализации, изолированная

`heavy-rows` и `heavy-entities` — дословно один запрос, и после введения
ротации порядок их выполнения тоже перестал быть постоянным. Разность
считается ПОКРУГОВО: оба запроса одного круга сняты при общем состоянии
машины, и уже из разностей берётся медиана. Разность двух медиан такой
связи не сохраняет.

Главный столбец здесь — ЗНАК разности. Полные размахи портят один-два
выброса, и по ним вывод не построить; знак к выбросам нечувствителен. Если
эффекта нет, знак должен делиться примерно пополам.

| плечо | знак + | медиана | межквартильный размах | полный размах |
|---|---|---|---|---|
| raw-asyncpg | 7/11 | +0,146 | −0,656 … +1,163 | −0,770 … +1,342 |
| core-asyncpg | 3/11 | −0,476 | −0,813 … +0,047 | −1,475 … +3,875 |
| orm-asyncpg | **11/11** | +2,452 | +1,351 … +3,052 | +0,980 … +3,766 |
| orm-psycopg-async | **11/11** | +2,756 | +2,472 … +2,882 | +1,538 … +4,473 |
| orm-psycopg-sync | **11/11** | +2,420 | +1,801 … +2,918 | +1,465 … +3,713 |

Контрольные плечи ведут себя как положено: знак гуляет (7 и 3 из 11),
медианы у нуля. У всех трёх ORM-плеч знак положителен во ВСЕХ одиннадцати
кругах.

Складывать три плеча в одну вероятность нельзя: они меряются на одной
машине, делят кэши и попадают в одни и те же провалы, то есть независимыми
свидетельствами не являются. Но каждое по отдельности показывает одно и то
же, и ни одно не спорит с остальными.

**Главный вывод.** Цена ORM не исчезает, когда работает база: при 91%
времени на сервере построение 516 объектов стоит 2,4–2,8 мс.

**Почему опора на знак, а не на размах.** Полные размахи перекрываются: у
Core один выброс растянул его до +3,875, и он накрывает размахи всех
ORM-плеч. Межквартильные размахи не пересекаются вовсе — ни один
ORM-квартиль не заходит в контрольный. Так что вывод строится на знаке и
межквартильном размахе, а полный оставлен в таблице, чтобы было видно, чем
он испорчен.

**И оговорка, которая важнее вывода.** Те же 516 объектов дают около 5 мкс
на объект, тогда как из `many-rows` (5000 строк) выводится 8,2–9,9. Одна и
та же операция, два способа измерить — расхождение почти вдвое. Значит
«цена пропорциональна числу строк» — грубое правило, а не закон.

**Цена материализации одной строки** — разность времени на пяти тысячах
строк и на одной, делённая на 4999. Так уходит всё, что не растёт с числом
строк: путь до базы, разбор ответа, накладные расходы запроса.

| плечо | мкс на строку | во сколько раз |
|---|---|---|
| raw-asyncpg | 3,532 | 1,00x |
| core-asyncpg | 4,639 | 1,31x |
| orm-asyncpg | 13,406 | 3,80x |
| orm-psycopg-async | 11,907 | 3,37x |
| orm-psycopg-sync | 11,738 | 3,32x |

Сравнивайте с изолированным замером выше: там тот же объект обошёлся
примерно в 5 мкс. Число отсюда — верхняя оценка.

**Разведение переменных окупилось.** На одной строке синхронное плечо
дешевле асинхронного при том же драйвере и слое — 4,12x против 5,54x,
размахи (3,91–4,24 и 5,20–5,90) не пересекаются. Разница драйверов на этом
прогоне тоже разошлась: 4,75x у asyncpg против 5,54x у psycopg, размахи
4,55–5,11 и 5,20–5,90 не перекрываются. В предыдущем прогоне они
перекрывались на краях, так что вывод про драйверы держится слабее, чем
про sync/async, — он зависит от прогона.

На пяти тысячах строк разница sync/async исчезает (3,25x против 3,41x,
размахи перекрываются): постоянная надбавка тонет в работе, которая растёт
с числом строк. Тот же механизм, что топит цену слоя на тяжёлых запросах,
только в миниатюре.

## 2. N+1: считается запросами, а не временем

`fixtures/nplus1.txt`, 15 замеров, 5 кругов.

Число запросов — целое и не зависит ни от машины, ни от разогрева, ни от
соседей по хосту. Считается на СТОРОНЕ БАЗЫ через `pg_stat_statements`:
счётчик по событиям SQLAlchemy видел бы только то, что она сама отправила.

Загрузка 20 авторов со всеми их книгами и отзывами:

| стратегия | запросов | строк с сервера | мс |
|---|---|---|---|
| lazy | **221** | 2215 | 113,1 |
| selectinload | **3** | 2215 | 32,6 |
| joinedload | **1** | 1995 | 31,4 |

Загружено при этом одинаково — 200 книг, 1995 отзывов, — и это проверяется:
стратегия, обошедшаяся одним запросом потому, что ничего не загрузила,
выглядела бы в таблице лучшей.

221 запрос складывается как один за авторами, 20 за их книгами и 200 за
отзывами к каждой книге. Это **N+1+M**, а не N+1: уровней вложенности два, и
цена растёт по каждому отдельно. На одном уровне этой разницы не увидеть.

**Чего стенд не измеряет: байты по проводу.** Поэтому цена `joinedload`
видна не полностью — он отдаёт меньше строк, но в каждой повторяет столбцы
автора и книги столько раз, сколько у них отзывов. Меньшее число строк у
него не означает меньшего трафика.

## 3. Ленивая загрузка в асинхронной сессии

`fixtures/lazy-async.txt`, 2 записи. Это фиксация поведения, а не замер.

Обращение к незагруженной связи в `AsyncSession` на SQLAlchemy 2.0.52:

```
MissingGreenlet: greenlet_spawn has not been called; can't call await_only()
here. Was IO attempted in an unexpected place?
```

Синхронная сессия в этот момент молча сходила бы в базу — так и возникает
N+1. Асинхронная сходить не может: обращение к атрибуту синхронно по своей
природе, а поход в базу требует ожидания.

Проверка двусторонняя намеренно: та же связь, предзагруженная
`selectinload`, отдаёт свои 15 книг без ошибки. Без второй половины
доказывалось бы лишь то, что код умеет падать.

## 4. Alembic: что видит и что возвращает откат

`fixtures/alembic.txt`, 18 замеров, 9 изменений схемы в двух режимах
сравнения.

| изменение схемы | умолчания | строгое сравнение |
|---|---|---|
| контроль: изменений нет | операций нет | операций нет |
| столбец с `server_default` | откат вернул | откат вернул |
| смена типа `integer -> bigint` | откат вернул | откат вернул |
| переименование индекса | откат вернул | откат вернул |
| ограничение `CHECK` | откат вернул | откат вернул |
| частичный индекс | откат вернул | откат вернул |
| сужение `text -> varchar(64)` | откат вернул | откат вернул |
| смена умолчания у столбца | **НЕ ВИДИТ** | откат вернул |
| переименование столбца | **видит, НЕ СМОГ** | **видит, НЕ СМОГ** |

Строгое сравнение — это `compare_type=True` и `compare_server_default=True`.

**Два результата, разных по природе.** Смена `server_default` у
существующего столбца проходит мимо миграции молча, пока сравнение умолчаний
не включено явно. Переименование столбца обнаруживается, но предложенная
миграция на непустой таблице не исполняется вовсе: `drop_column` плюс
`add_column NOT NULL` даёт `NotNullViolation`. Обнаружение и
работоспособность — разные вещи.

**Откат проверяется снимком системного каталога**, а не текстом миграции и
не самой автогенерацией. Спросить у Alembic, совпадает ли база с описанием,
было бы кругом: он не увидел бы ровно того, чего не видит по построению, и
объявил бы откат удачным.

**Контрольный случай идёт первым и обязателен.** Автогенерация сравнивает
базу с описанием целиком, и расхождение в мелочи подмешало бы лишние
операции в каждый случай. На неизменённом описании операций ноль — значит
описание точно соответствует схеме.

Ожидание перед прогоном было, что с умолчаниями Alembic не сравнивает ни
типы, ни умолчания. Замер поправил его наполовину: смену типа 1.19.1 видит
и с умолчаниями.

## Что здесь может соврать

Список не для скромности: каждый пункт — то, на чём стенд уже спотыкался
или может споткнуться.

- **Цена слоя на тяжёлых запросах не измеряется в лоб.** 90–98% времени
  принадлежит серверу; изолировать её удаётся только парой `heavy-rows` и
  `heavy-entities`, где различается ровно одно.
- **Линейность по строкам приблизительная.** Цена объекта из замера на 5000
  строк и из изолированной пары на 516 расходится в полтора раза.
- **Полные размахи парных разностей перекрываются.** Один выброс у Core
  растягивает его размах до +3,875 мс. Вывод строится на знаке разности и
  межквартильном размахе; полный оставлен в таблице как есть.
- **Разница драйверов зависит от прогона.** В одном размахи разошлись, в
  другом перекрылись на краях. Про sync/async такого не было ни разу.
- **Модель простая.** Шесть скалярных полей, без JSON, UUID,
  `TypeDecorator`, отложенных колонок, связей и событий. Всё перечисленное
  цену меняет, и числа стенда на такие модели не переносятся.
- **На `heavy-sql` у ORM-плеч нет сущностей.** Агрегат не ложится на
  модель, они выполняют выражение Core и отдают mappings. Совпадение с Core
  там — про накладные расходы сессии, а не про материализацию.
- **Байты по проводу не измеряются.** Компромисс `joinedload` виден лишь
  наполовину.
- **Сеть между клиентом и базой отсутствует.** Оба в одном хосте; на
  реальной сети постоянные издержки вырастут и доля цены слоя упадёт.
- **Пул не измеряется.** У каждого плеча одно соединение: поведение пула —
  отдельный сюжет, и мешать его с ценой слоя нельзя.
- **Числа привязаны к версиям.** Особенно поведение Alembic и текст
  исключения SQLAlchemy: и то, и другое версионно.

## Как повторить

```bash
docker compose up -d
bash scripts/seed.sh                # посев и сверка контрольной суммы
bash scripts/check-equivalence.sh   # блокирующая проверка равенства
bash scripts/check-db-share.sh      # карта разрешения стенда
bash scripts/run-layers.sh          # цена слоёв, 11 кругов
bash scripts/run-nplus1.sh          # N+1 и ленивая загрузка в async
bash scripts/run-alembic.sh         # автогенерация и откат
```

Разбор фикстур:

```bash
python scripts/analyze-layers.py
python scripts/analyze-nplus1.py
python scripts/analyze-alembic.py
```

Тесты стенда — предохранители заведены вместе со случаями, которые их
роняют:

```bash
python -m unittest discover -s scripts -p "test_*.py"
```
