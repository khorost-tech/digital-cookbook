Семь политик из namespace-install, и все семь селектят поды САМОГО ArgoCD. git-server
не попадает ни под одну, а под, не выбранный ни одной политикой, в Kubernetes открыт всем.

Складываем с тем, как поднят демон (05-git-server.yaml: --export-all --enable=receive-pack,
у протокола git:// нет ни аутентификации, ни авторизации) и получаем цепочку:

  любой под кластера -> push в наш git -> манифест с hostPath или privileged ->
  ArgoCD применяет его сам -> под с доступом к узлу

В M1 цепочку разрывает ручной sync: между чужим коммитом и подом стоит человек.
В M2 включается automated + selfHeal — и не разрывает уже ничего.
Права ArgoCD ограничены одним namespace (11-rbac.yaml), но hostPath и privileged — это
выход ЗА namespace, на узел; namespace-граница их не держит.

3. ЗАМОК ВТОРОЙ: NetworkPolicy к git-серверу
================================================================================
Замер ДО политики. Временный под в ЧУЖОМ namespace cookbook-k8s клонирует наш репозиторий:

# cmd: kubectl -n cookbook-k8s run netprobe-before --image=alpine/git:v2.49.1 --restart=Never \
#        --command -- sh -c 'time timeout 30 git clone git://git-server.cookbook-argocd.svc.cluster.local/demo.git /tmp/demo; echo "rc=$?"'
# cmd: kubectl -n cookbook-k8s logs netprobe-before
Cloning into '/tmp/demo'...
real	0m 0.10s
user	0m 0.00s
sys	0m 0.00s
rc=0

Сто миллисекунд из чужого namespace. Дыра не теоретическая.

Ставим политику (manifests/05-git-server.yaml: podSelector app=git-server, ingress 9418/TCP
только из namespace с меткой kubernetes.io/metadata.name=cookbook-argocd):

# cmd: bash apply.sh manifests/05-git-server.yaml
configmap/git-seed unchanged
deployment.apps/git-server unchanged
service/git-server unchanged
networkpolicy.networking.k8s.io/git-server-allow-stand-only created
applied: manifests/05-git-server.yaml

# cmd: kubectl -n cookbook-argocd get netpol git-server-allow-stand-only -o yaml
spec:
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: cookbook-argocd
    ports:
    - port: 9418
      protocol: TCP
  podSelector:
    matchLabels:
      app: git-server
  policyTypes:
  - Ingress

Замер ПОСЛЕ, оба направления, одной и той же командой. Датаплейн здесь Cilium (eBPF),
поэтому «политика создана» и «политика работает» проверяются отдельно:

--- из ЧУЖОГО namespace (cookbook-k8s) ---
# cmd: kubectl -n cookbook-k8s run netprobe-after --image=alpine/git:v2.49.1 --restart=Never \
#        --command -- sh -c 'time timeout 30 git clone git://git-server…/demo.git /tmp/demo; echo "rc=$?"'
# cmd: kubectl -n cookbook-k8s logs netprobe-after
Cloning into '/tmp/demo'...
Command terminated by signal 15
real	0m 30.00s
user	0m 0.00s
sys	0m 0.00s
rc=15

--- из СВОЕГО namespace (cookbook-argocd) ---
# cmd: kubectl -n cookbook-argocd run netprobe-own --image=alpine/git:v2.49.1 --restart=Never \
#        --command -- sh -c 'time timeout 30 git clone git://git-server…/demo.git /tmp/demo; echo "rc=$?"'
# cmd: kubectl -n cookbook-argocd logs netprobe-own
Cloning into '/tmp/demo'...
real	0m 0.10s
user	0m 0.00s
sys	0m 0.00s
rc=0

0.10 s против 30.00 s и rc=15 (SIGTERM от `timeout`) — характерная картина именно
для NetworkPolicy: пакеты не отбиваются RST, а молча дропаются, и клиент висит на
connect до собственного таймаута. Отказа в доступе клиент не видит — он видит тишину.

Временные поды после снятия вывода удалены:
# cmd: kubectl -n cookbook-k8s delete pod netprobe-before netprobe-after
# cmd: kubectl -n cookbook-argocd delete pod netprobe-own

Egress политикой не ограничен намеренно: git daemon сам никуда не ходит, а запрет egress
сломал бы ему DNS. Пробы у контейнера exec, а не tcpSocket, — kubelet в ingress не нуждается.

4. ПРАВА argocd-server СУЖЕНЫ ДО АПСТРИМНОГО НАБОРА
================================================================================
Было: широкая Role `*/*/*` привязана к ОБОИМ ServiceAccount с обоснованием «те же права,
что даёт боевая ClusterRole». Для контроллера это правда; для argocd-server — нет.
Разбор install.yaml v3.4.1 (fixtures/10-argocd.txt, раздел 3) показывает у ClusterRole
argocd-server на `*/*` глаголы delete,get,patch — без create и update.

Стало: отдельная Role cookbook-argocd-server-ns с тем же набором и отдельный RoleBinding.

# cmd: bash apply.sh manifests/11-rbac.yaml

rolebinding.rbac.authorization.k8s.io/cookbook-argocd-server-ns created
applied: manifests/11-rbac.yaml

# cmd: kubectl -n cookbook-argocd get rolebinding cookbook-argocd-manage-ns -o jsonpath='{.subjects}'

# cmd: kubectl -n cookbook-argocd get rolebinding cookbook-argocd-server-ns -o jsonpath='{.subjects}'
[{"kind":"ServiceAccount","name":"argocd-server","namespace":"cookbook-argocd"}]

Разница в правах, замер:

# cmd: kubectl auth can-i <verb> deployments -n cookbook-argocd --as=system:serviceaccount:cookbook-argocd:<sa>

get     deployments  controller=yes  server=yes

Узкие правила апстрима на месте:
get     pods/log     server=yes
create  jobs         server=yes
list    events       server=yes

Два уточнения, чтобы вывод не читался шире, чем есть.

а) `create secrets --as=…:argocd-server` тоже даёт yes — но НЕ от нашей роли. Это Role
   argocd-server из namespace-install, права на собственное хозяйство сервера:
   # cmd: kubectl -n cookbook-argocd get role argocd-server -o jsonpath='{range .rules[*]}…{end}'
   [""] ["secrets","configmaps"] ["create","get","list","watch","update","patch","delete"]
   ["argoproj.io"] ["applications","appprojects","applicationsets"] ["create","get","list","watch","update","delete","patch"]
   [""] ["events"] ["create","list"]

б) Граница по namespace никуда не делась:
   # cmd: kubectl auth can-i delete deployments -n argocd --as=…:argocd-server
   no

Почему server беднее контроллера и при этом работает: живое состояние он берёт из кэша
контроллера, а к API ходит только за действиями из UI и CLI.
